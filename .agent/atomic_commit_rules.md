# 📝 原子化提交規則 (Atomic Commit Rules)

> 每個功能/修改意圖各自獨立一個 commit，保持提交歷史清晰可追溯。

---

## 核心原則

### 1. 一個功能 = 一個 commit
- 即使多個功能在**同一個檔案**中修改，也必須分開提交
- 每個 commit 只包含**單一、明確的修改意圖**

### 2. Commit 粒度判定標準

| 情況 | 分開提交？ | 範例 |
|------|-----------|------|
| 同一功能的前端 + 後端 | ✅ 分開 | API 端點一個 commit，前端呼叫一個 commit |
| 同一檔案中的不同功能修改 | ✅ 分開 | 檔案 A 改了 login 邏輯和 register 邏輯 → 兩個 commit |
| 同一功能的多檔案修改 | ❌ 可合併 | 同一個 feature 涉及三個檔案 → 一個 commit |
| 邏輯性拆分（重構） | ✅ 分開 | 移除 deprecated code 一個 commit，新增替代方案一個 commit |

### 3. Commit 規範

- **每個 commit 必須能獨立通過編譯 / 測試**
- **Commit message 要清楚描述該功能是什麼**
- 格式建議：`<type>(<scope>): <description>`

### 4. Type 分類

| Type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修正 |
| `refactor` | 重構（不改變外部行為） |
| `style` | 純格式 / lint 修正 |
| `docs` | 文件變更 |
| `test` | 測試補充或修正 |
| `chore` | 建置、CI 等雜項 |

## 實作範例

### ❌ 錯誤做法：一個大 commit 包含所有修改
```
commit: "Add user system"
  - 新增 /api/users 端點
  - 新增前端用戶列表頁面
  - 修正登入頁面表單驗證
  - 更新 README
```

### ✅ 正確做法：拆分為多個原子化 commit
```
commit 1: "feat(api): Add user list endpoint"
commit 2: "feat(frontend): Add user list page"
commit 3: "fix(auth): Fix login form validation"
commit 4: "docs: Update README with user system info"
```

---

## 注意事項

1. **避免 `git add -A`**：只 staging 與當前 commit 相關的檔案
2. **善用 `git add -p`**：同檔案中只 stage 屬於該功能的 hunk
3. **Commit 前先確認**：`git diff --cached` 確認 staging 內容是否正確
4. **如果發現漏提交**：用 `git commit --amend` 補上，而不是開新 commit
