## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

### 1.1 案情境況：WAF 綠燈下的全站數據暗度陳倉
某跨國電商核心生產叢集的 Kubernetes Tomcat Pod 在深夜 02:40 觸發了出站流量異常總量偏離告警：
> *Alert: Data Exfiltration Anomaly - Destination: 104.244.78.33:8443, Outbound Volume: 4.8 GB over HTTP POST, Source Pod: `app-catalog-tomcat-7d9bb864f-4x2kl`.*

當值 SOC L1/L2 工程師立刻介入調查：
1. **WAF 檢視**：檢視企業級 NGFW / WAF 設備，過去 6 小時內針對該 Pod 的告警數量為 **0**。所有請求均回傳 `HTTP 200 OK`，無任何常見的 `cmd.exe`、`whoami`、`/bin/sh`、`system()` 或 SQLi 等明文特徵。
2. **主機端磁碟掃描**：使用 ClamAV 與企業級主機防毒軟體對應用根目錄 `/usr/local/tomcat/webapps/ROOT/` 進行全盤掃描，雜湊比對與 Yara 掃描結果均為 **100% 純淨**，未找到任何新增的 `.jsp`、`jspx` 或惡意後門檔案。
3. **HTTP 存取日誌 (Access Log)**：發現海量向靜態資源或常規 API 發起的 POST 請求，形如：
   ```http
   POST /favicon.ico HTTP/1.1
   Host: api.victim-shop.com
   User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36
   Content-Type: application/x-www-form-urlencoded
   Content-Length: 32768
   
   pass=k9A2%2Fj...[大量 Base64/二進位編碼字串]...
   ```
   伺服器對 `/favicon.ico` 的 POST 請求竟然回應 `HTTP 200 OK`，且回應體長度達數十 KB 二進位串流！

這正是現代 APT 與高級紅隊最慣用的致命手法：**全加密通訊管理工具（冰蠍 Behinder / 哥斯拉 Godzilla）** 結合 **磁碟無落地 Java 記憶體馬 (Memory WebShell / Dynamic Filter Injection)**！
攻擊者已完全規避了基於靜態特徵匹配的 WAF 與主機防毒軟體，在記憶體中掌控伺服器核心執行緒，並透過動態金鑰 AES/XOR 加密傳輸指令與滲透數據。

```
[ 外部紅隊/攻擊者 ] (Behinder / Godzilla Client)
         │
         │ 1. 利用既有漏洞動態注入記憶體馬 (無落地檔案)
         │ 2. 動態金鑰交換握手 (Key Exchange / Dynamic AES/XOR)
         ▼
[ 邊界 WAF / 反向代理 ] ── (只見合法 POST /favicon.ico，密文流過，無明文關鍵字，全部放行)
         │
         ▼
[ Web 容器: Tomcat JVM 記憶體空間 ]
         ├── [ ApplicationFilterChain (全域請求過濾鏈) ]
         │       ├─ StandardFilter1
         │       ├─ ★ EvilMemoryFilter (動態掛載於記憶體首位，劫持所有路徑)
         │       └─ StandardFilter2
         │
         ├── 解密 Payload ──► 反射執行任意 Java Bytecode (Class.forName/Unsafe)
         └── 加密輸出執行結果 ──► 回應給攻擊者 (暗度陳倉)
```

## 🔬 第一動：破譯本質——底層機制全景圖

### 2.1 冰蠍 (Behinder) 加密通訊機制演進
冰蠍是最早普及動態 AES 對稱加密的 WebShell 管理客戶端，其各版本通訊特徵截然不同：

```
[ 冰蠍 v2.0 握手階段 (動態金鑰交換) ]
Client ─── GET /shell.jsp?pass=123 ───► Server (JSP 生成隨機 16-byte Key 存入 Session)
Client ◄── 16-byte AES Key (明文) ────── Server
後續通信：Client/Server 使用該 AES Key 進行 AES-128-CBC 加密 (Padding: PKCS5)

[ 冰蠍 v3.0 / v4.0 (取消動態握手，自定協定) ]
Client/Server 預先約定密碼 (預設 rebeyond)
金鑰計算：Key = MD5(passphrase)[0:16]
Client ─── POST /shell.jsp (AES-128-CFB/ECB 加密之 Java Bytecode) ───► Server
Server ─── 利用預設 Key 解密，透過自定義 ClassLoader 動態載入執行 ───► 密文回傳
```

### 2.2 哥斯拉 (Godzilla) 加解密與載荷封裝
哥斯拉採用了更靈活的模組化架構，常見的傳輸協定包括 `JAVA_AES_BASE64`、`JAVA_AES_RAW` 與 `PHP_XOR_BASE64`：
1. **金鑰衍生**：`Key = MD5(Passphrase)[0:16]`。
2. **Payload 雙重封裝**：
   - 原始 Java 位元組碼 (Bytecode) 經過 AES-128-CBC 加密（IV 通常全為 `0x00`）。
   - 加密後的二進位數據再經過 Base64 編碼，前後可能包裹隨機前綴與後綴字元（例如 `pass=<random_hex><base64_data><random_hex>`）以規避正則檢測。
3. **記憶體動態執行**：服務端接收後，解碼還原出 `byte[]` 陣列，直接呼叫 `java.lang.ClassLoader.defineClass()` 在記憶體中定義類別並透過反射實例化。

### 2.3 Java 記憶體馬 (Memory Shell) 注入型態
記憶體馬不依賴於磁碟上的 `.jsp` 檔案，完全常駐於 JVM 執行緒與資料結構中：

```
                              [ HTTP 請求到達 Tomcat Engine ]
                                             │
                                             ▼
                          ┌─────────────────────────────────────┐
                          │ 1. Listener 記憶體馬 (最先觸發)      │
                          │    實作 ServletRequestListener       │
                          └──────────────────┬──────────────────┘
                                             │
                                             ▼
                          ┌─────────────────────────────────────┐
                          │ 2. Filter 記憶體馬 (最廣泛使用)     │
                          │    注入 ApplicationFilterConfig 鏈  │
                          └──────────────────┬──────────────────┘
                                             │
                                             ▼
                          ┌─────────────────────────────────────┐
                          │ 3. Servlet 記憶體馬                 │
                          │    向 StandardContext 動態添加路由  │
                          └──────────────────┬──────────────────┘
                                             │
                                             ▼
                          ┌─────────────────────────────────────┐
                          │ 4. Agent / Bytecode Hook 記憶體馬   │
                          │    利用 Instrumentation 修改現有類   │
                          └─────────────────────────────────────┘
```

| **Filter 優先級置頂** | 未知名稱之動態 Filter 被強制插入到過濾鏈第 0 位，且匹配路徑為全域 `/*`。 | 商業框架之業務 Filter 依序排布，安全攔截器遵循標準 Spring Security 順序。 | 🔴 **極高 (Critical)** |

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 3.1 冰蠍 v3.0 / 哥斯拉加密流量自動化爆破與還原工具 (`webshell_traffic_carver.py`)
在實際鑑識中，資安分析師需從 PCAP 或 Proxy 紀錄中萃取 Base64 密文。本腳本實作常見密碼字典爆破與 Java 位元組碼 (0xCAFEBABE) 還原：

```python
#!/usr/bin/env python3
"""
webshell_traffic_carver.py - 冰蠍 / 哥斯拉 加密流量還原與 Class 提取工具
"""
import sys
import hashlib
import base64
from Crypto.Cipher import AES

COMMON_PASSWORDS = [
    "rebeyond", "pass", "admin", "123456", "godzilla",
    "cmd", "root", "test", "password", "superadmin", "default"
]

def derive_key(pwd: str) -> bytes:
    """計算 MD5(passphrase) 前 16 位作為 AES Key"""
    return hashlib.md5(pwd.encode('utf-8')).hexdigest()[:16].encode('utf-8')

def attempt_decrypt(ciphertext_b64: str, pwd: str) -> bytes:
    key = derive_key(pwd)
    try:
        raw_cipher = base64.b64decode(ciphertext_b64)
    except Exception:
        return b""
    
    # 模式 A: AES-128-ECB (冰蠍 v3 預設)
    try:
        cipher_ecb = AES.new(key, AES.MODE_ECB)
        data = cipher_ecb.decrypt(raw_cipher)
        if b'\xca\xfe\xba\xbe' in data:
            return data
    except Exception:
        pass

    # 模式 B: AES-128-CBC, IV 全零 (哥斯拉 JAVA_AES 預設)
    try:
        cipher_cbc = AES.new(key, AES.MODE_CBC, b'\x00' * 16)
        data = cipher_cbc.decrypt(raw_cipher)
        if b'\xca\xfe\xba\xbe' in data:
            return data
    except Exception:
        pass

    return b""

def main():
    if len(sys.argv) < 2:
        print("用法: python3 webshell_traffic_carver.py <Base64_Payload_String>")
        sys.exit(1)

    payload = sys.argv[1].strip()
    print(f"[*] 開始對傳輸載荷進行密鑰字典碰撞 (候選密碼數: {len(COMMON_PASSWORDS)})...")
    
    found = False
    for pwd in COMMON_PASSWORDS:
        recovered = attempt_decrypt(payload, pwd)
        if recovered and b'\xca\xfe\xba\xbe' in recovered:
            print(f"\n[+] 🎯 成功解密！WebShell 密碼為: 【 {pwd} 】")
            print(f"[+] 對應 AES Key: {derive_key(pwd).decode('utf-8')}")
            
            # 定位 Java Class 魔術字元 0xCAFEBABE 並切除 Padding
            start_idx = recovered.find(b'\xca\xfe\xba\xbe')
            class_bytes = recovered[start_idx:]
            
            output_file = f"dumped_payload_{pwd}.class"
            with open(output_file, "wb") as f:
                f.write(class_bytes)
            print(f"[+] 惡意 Java Class 已成功提取並儲存至: {output_file}")
            print(f"[+] 分析建議：執行 'javap -c {output_file}' 檢視反彙編指令。")
            found = True
            break

    if not found:
        print("[-] 字典密碼碰撞失敗。建議透過主機 JVM 記憶體進行活體 Class 導出。")

if __name__ == "__main__":
    main()
```

## 🧭 第四動：研判分流——SOC 8 問與決策樹

### 4.1 SOC 分析師研判 8 問
| 編號 | 檢驗問題 | 惡意/失陷指標 (True Positive) | 良性/誤報指標 (False Positive) |
|:---:|:---|:---|:---|
| **Q1** | 靜態資源（如 `/favicon.ico`）是否持續接收到 HTTP POST 請求？ | 極高危：冰蠍/哥斯拉典型偽裝手法 | 業務前端開發錯誤，但通常為偶發 |
| **Q2** | 伺服器針對該靜態資源的回應長度是否出現劇烈跳動（數 KB ~ 數十 KB）？ | 100% 異常：代表伺服器在執行動態代碼並回傳數據 | 回應長度完全恆定或回傳 405 Method Not Allowed |
| **Q3** | POST Body 是否具備 Base64 密文或高夏農熵 (>5.8) 特徵？ | 典型對稱加密 WebShell 載荷傳輸 | 正常表單或 JSON 格式明文字串 |
| **Q4** | 流量解密測試是否成功捕獲 Java Class 魔術字元 `0xCAFEBABE`？ | 鐵證：確實在傳輸並執行 Java 位元組碼 | 解密出亂碼且無二進位特徵 |
| **Q5** | Tomcat 容器記憶體中是否存在無實體 `.class` 檔案對應之 Filter/Servlet？ | 典型 Java 記憶體馬 (Memory Shell) 駐留特徵 | 所有類別均有實體 JAR 包對應 |
| **Q6** | 該異常 Filter 是否掛載於 `ApplicationFilterChain` 首位並攔截 `/*`？ | 惡意記憶體馬確保優先劫持所有流量之標準配置 | 業務 Filter 具備特定路徑前綴 (如 `/api/*`) |
| **Q7** | Web 容器進程（`java`）是否有衍生子進程（如 `sh`, `bash`, `whoami`）？ | 確定攻擊者已執行作業系統指令 | 無子進程衍生，僅執行純 Java 記憶體邏輯 |
| **Q8** | Web 容器是否有對非業務外網 IP 建立反彈連線或大量上傳連線？ | 攻擊者正在進行反彈 Shell 或數據外洩 | 容器僅對內部資料庫與微服務發起連線 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 5.1 應急處置階段 (Immediate Containment & Evidence Preservation)

#### 1. 記憶體活體取證與 Heap Dump (Memory Preservation First!)
**嚴禁在未執行記憶體轉儲前直接重啟 Web 容器或 Kubernetes Pod！** 記憶體馬僅存在於 JVM 記憶體結構中，容器重啟將導致攻擊載荷、金鑰與攻擊痕跡完全滅失：

```bash
# 步驟 1：使用 jmap 轉儲目標 Java 進程之完整 Heap Dump (以 PID 1234 為例)
jmap -dump:live,format=b,file=/tmp/evidence_heap_1234.hprof 1234

# 步驟 2：利用 Arthas dump 指令將記憶體中載入的惡意 Class 存盤
# dump -d /tmp/evidence_classes/ *Filter*

# 步驟 3：在邊界防火牆下發 C2 阻斷規則
iptables -I INPUT -s 104.244.78.33 -j DROP
```

#### 2. 記憶體馬線上動態熱拔除 (Hot-Unloading Memory Shell)
若生產環境無法立即重啟，可使用 Java Agent 或 Arthas 動態修改類別定義進行邏輯清空：
1. 透過 Arthas 的 `retransform` 功能，載入一個空的同名 Filter 類別替換惡意邏輯。
2. 或調用開源工具（如 `Copagent`、`java-memshell-scanner`）發送反註冊命令從 Tomcat `StandardContext` 卸載過濾器。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 6.1 實驗環境架設：模擬冰蠍 v3.0 加密流量互動
本實驗將使用 Python 建立一個受控的模擬端點，完整模擬冰蠍客戶端與服務端之間的 AES 加密流量傳輸與還原。

```python
# lab_sim_webshell.py - Educational Simulation of Encrypted WebShell Handshake
import os
import hashlib
import base64
from Crypto.Cipher import AES

def run_simulation():
    passphrase = os.environ.get("BEHINDER_PWD", "rebeyond")
    key = hashlib.md5(passphrase.encode('utf-8')).hexdigest()[:16].encode('utf-8')
    print(f"[*] 1. 設定 WebShell 密碼: {passphrase} (AES Key: {key.decode()})")

    # 模擬攻擊者傳輸的 Java Bytecode (以 0xCAFEBABE 開頭)
    fake_bytecode = b"\xca\xfe\xba\xbe\x00\x00\x00\x34\x00\x10\x07\x00\x02\x01\x00\x10" + b"EvilPayloadDemo"
    
    # 執行 PKCS7 填充
    pad_len = 16 - (len(fake_bytecode) % 16)
    padded = fake_bytecode + bytes([pad_len] * pad_len)

    # AES-128-ECB 加密
    cipher = AES.new(key, AES.MODE_ECB)
    encrypted = cipher.encrypt(padded)
    payload_b64 = base64.b64encode(encrypted).decode('utf-8')
    
    print(f"[+] 2. 模擬生成之加密 POST Body:\n{payload_b64}")
    return payload_b64

if __name__ == "__main__":
    run_simulation()
```

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：為什麼傳統的靜態 WAF 在面對冰蠍 (Behinder) v3.0 與哥斯拉 (Godzilla) 時完全失去防禦能力？**  
  *考核核心*：冰蠍 v3.0 與哥斯拉採用完全自定義的對稱加密（AES/XOR）或自定義序列化協定。HTTP 請求 Body 在網路傳輸過程中表現為高熵的隨機二進位密文或 Base64 字串，不存在任何常見的 `cmd.exe`、`whoami`、`eval()` 等明文特徵。WAF 若無伺服器端動態金鑰，無法在線即時解密，導致特徵匹配機制徹底失效。

- [ ] **Q2：什麼是 Java「記憶體馬 (Memory Shell)」？它與傳統的 `.jsp` WebShell 在磁碟與 JVM 層面有何本質區別？**  
  *考核核心*：傳統 WebShell 必須在 Web 伺服器磁碟上寫入實體檔案（如 `shell.jsp`），請求時由 Web 容器解析執行，容易被主機防毒或檔案完整性監控 (FIM) 捕獲。記憶體馬則是利用反序列化或 RCE 漏洞，直接調用 Servlet API 或 Java Instrumentation，向記憶體中的 `StandardContext` 動態註冊 Filter、Servlet 或掛鉤字節碼。磁碟上 **不存在任何實體檔案**，重啟容器後即消失，具備極高的匿蹤性。

- [ ] **Q3：在排查 Java Filter 型記憶體馬時，為什麼檢查 `ApplicationFilterChain` 的過濾順序與 ClassLoader 至關重要？**  
  *考核核心*：攻擊者為了確保記憶體馬能夠優先攔截所有傳入的 HTTP 請求，通常會將惡意 Filter 動態插入至 `ApplicationFilterConfig` 陣列的第 0 位（置頂），並將匹配 URL 設定為全域 `/*`。同時，該類別是由漏洞觸發時臨時定義的（透過自定義 ClassLoader 或動態字節碼載入），在 JVM 中其 `CodeSource` 或實體 JAR 映射通常為 `null`，與常規由 Spring/Tomcat 載入的實體類別形成鮮明對比。

- [ ] **Q4：發現 Tomcat 容器疑似被植入記憶體馬時，為什麼第一時間直接重開機或刪除 Pod 是嚴重的處置失誤？**  
  *考核核心*：記憶體馬的所有二進位代碼、攻擊者下達的歷史指令、反彈 C2 的 Session 金鑰以及解密密碼全部僅存在於 JVM 的揮發性 RAM 記憶體中。一旦直接重啟或刪除容器，所有關鍵證據瞬間灰飛煙滅，資安團隊將永遠無法得知攻擊者的真實身分、利用了哪一個入口漏洞以及竊取了哪些機密數據。

- [ ] **Q5：哥斯拉 (Godzilla) 的 `JAVA_AES_BASE64` 傳輸協定在加密前，其有效載荷的基本結構是什麼？**  
  *考核核心*：哥斯拉客戶端會先將要執行的 Java 指令包裝為標準的 Java 二進位位元組碼（以 `0xCAFEBABE` 魔術字元為頭部的 Class 檔案），接著使用約定密碼的 MD5 前 16 位作為 Key 進行 AES-128-CBC 加密，最後經過 Base64 編碼發送。服務端記憶體馬收到後解密出原始二進位，利用 `ClassLoader.defineClass` 在記憶體中動態加載並執行該類別的 `equals()` 或靜態初始化塊。
