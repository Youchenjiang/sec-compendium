## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

### 1.1 案情境況：合法系統進程體內的「幽靈代碼」
週五深夜 01:20，某金融機構的 SOC 監控平台突然捕獲到一條嚴重偏離業務基準線的異常網路連線：
> *Alert: Unusual Outbound Connection to Untrusted Foreign IP (185.220.101.5:443) from Core System Process `explorer.exe` (PID: 2048).*

當值工程師立即進行排查：
1. `explorer.exe` 是 Windows 檔案總管核心進程，位於 `C:\Windows\explorer.exe`，具備微軟官方合法 Authenticode 數位簽章。
2. 檢查檔案雜湊 (SHA256) 與大小，與純淨 Windows 映像完全吻合，磁碟上的檔案絕未遭到竄改。
3. 檢查進程啟動命令列，僅為標準無參數的 `explorer.exe`。

然而，當獵捕專家調用 EDR 深入探測該進程的虛擬記憶體空間（Virtual Memory Space）時，赫然發現：
在 `explorer.exe` 的記憶體空間中，存在一塊未映射至任何實體硬碟二進位檔（**Unbacked Memory Section**）、且記憶體保護屬性被設定為極高危的 **`PAGE_EXECUTE_READWRITE (0x40 / RWX)`** 記憶體分頁！

回溯 Sysmon 核心遙測日誌，真相水落石出：在連線發起前 10 秒，一個位於使用者臨時目錄的未簽章二進位檔 `updater.exe` (PID: 4912)，跨進程調用了 Win32 API：
```text
EventID: 8 (CreateRemoteThread)
SourceImage: C:\Users\Public\updater.exe
TargetImage: C:\Windows\explorer.exe
TargetProcessId: 2048
StartAddress: 0x00007FFD2B140000
```

隨後 `updater.exe` 自我終止並從磁碟自我刪除，而其惡意 Shellcode（Cobalt Strike Beacon）則已完全寄生於合法的 `explorer.exe` 體內持續外聯！這是一起教科書級別的 **進程注入（Process Injection）** 實戰攻擊！

```
[ 惡意 Dropper: updater.exe (PID: 4912) ]
                  │
                  ├──── 1. OpenProcess(PROCESS_ALL_ACCESS, PID: 2048)
                  │
                  ├──── 2. VirtualAllocEx(Target, RWX, Size) ──────┐ (在目標內部開闢空間)
                  │                                                │
                  ├──── 3. WriteProcessMemory(Target, Shellcode) ──┤ (寫入惡意載荷)
                  │                                                │
                  ├──── 4. CreateRemoteThread(Target, StartAddr) ──┘ (Sysmon Event 8 捕捉！)
                  │
                  ▼ (updater.exe 自我銷毀退出)
[ 合法宿主進程: explorer.exe (PID: 2048) ] ── In-Memory Execution ──► C2: 185.220.101.5:443
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Injection Primitives)

### 2.1 進程記憶體邊界與跨進程操作的物理原理
在 Windows 虛擬記憶體架構中，每個進程擁有各自獨立且相互隔離的 4GB (x86) 或 128TB (x64) 虛擬位址空間。正常情況下，進程 A 無法讀寫進程 B 的記憶體。

但為了支援除錯器 (Debugger) 與系統管理工具，Windows 原生提供了以下跨進程記憶體操作原語（Primitives）：
- **`OpenProcess`**：取得目標進程句柄，所需存取遮罩包括 `PROCESS_VM_OPERATION`、`PROCESS_VM_WRITE`。
- **`VirtualAllocEx`**：在目標進程的虛擬空間中分配記憶體分頁。
- **`WriteProcessMemory`**：將本機緩衝區資料拷貝寫入目標進程指定記憶體位址。
- **`VirtualProtectEx`**：修改目標記憶體頁的保護屬性（如將 RW 改為 RX/RWX）。
- **`CreateRemoteThread`**：在目標進程空間內強制創建並啟動一個全新執行緒，從指定記憶體位址開始執行。

### 2.2 三大主流進程注入手法底層技術流動

#### 1. 經典遠端執行緒注入 (Classic Remote Thread Injection - T1055.001)
```
攻擊進程 ──► OpenProcess ──► VirtualAllocEx ──► WriteProcessMemory("C:\evil.dll")
         ──► CreateRemoteThread(Target, LoadLibraryA, "C:\evil.dll 位址")
```
- **核心依賴**：迫使目標進程執行 `kernel32.dll!LoadLibraryA`，自磁碟載入惡意 DLL。

#### 2. 進程挖空/空心化 (Process Hollowing - T1055.012)
```
攻擊進程 ──► CreateProcess("svchost.exe", CREATE_SUSPENDED) (以掛起狀態啟動合法進程)
         ──► NtUnmapViewOfSection (將合法進程在記憶體中的原始代碼完全卸載/掏空)
         ──► VirtualAllocEx(ImageBase, Size, RWX) ──► WriteProcessMemory (寫入惡意 PE)
         ──► SetThreadContext (將執行緒指令暫存器 RIP 修正指向惡意代碼入口點)
         ──► ResumeThread (喚醒進程，系統誤以為是合法 svchost 在跑)
```

#### 3. 反射式 DLL 注入 (Reflective DLL Injection - Fileless)
- **核心特點**：惡意 DLL 完全不落盤！
- **實現方式**：DLL 內建專屬的 `ReflectiveLoader` 函數。注入器將整個 DLL 原始二進位直接寫入目標記憶體，隨後引導目標進程跳轉至 `ReflectiveLoader`。該函數自行在記憶體中模擬 Windows PE Loader（解析 Import 表、修復 Base Relocation、呼叫 DllMain），徹底避開了呼叫 `LoadLibraryA` 引發的 Sysmon Event 7 監控！

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 3.1 Sysmon 與 Splunk SPL 全網注入獵捕指令庫

#### 1. Splunk 聚合獵捕：全網掃描 Sysmon Event 8 (CreateRemoteThread)
```spl
index=sysmon EventCode=8
| where NOT match(SourceImage, "(?i)C:\\\\Program Files")
| where SourceImage!=TargetImage
| stats count min(_time) as first_seen max(_time) as last_seen 
        by host, SourceImage, TargetImage, StartAddress, StartFunction
| table host, first_seen, last_seen, SourceImage, TargetImage, StartAddress, StartFunction, count
| sort - count
```

#### 2. Splunk 聚合獵捕：捕捉高危跨進程記憶體寫入權限 (Sysmon Event 10)
```spl
index=sysmon EventCode=10
| eval is_write = if(match(GrantedAccess, "(?i)0x.*20|0x1F0FFF"), 1, 0)
| where is_write=1 AND SourceImage!=TargetImage
| where NOT match(SourceImage, "(?i)MsMpEng\.exe|csfalconservice\.exe|C:\\\\Program Files")
| stats count by _time, host, SourceImage, TargetImage, GrantedAccess, CallTrace
| sort - _time
```

### 3.2 PowerShell + Get-InjectedThread 現場記憶體注入獵捕工具 (`hunt_injection.ps1`)
在未部署進階 EDR 的現場，可使用以下 PowerShell 腳本遍歷所有運行中進程的執行緒起始位址，辨識是否指向未映射的記憶體區域（Unbacked Thread Execution）：

```powershell
# hunt_injection.ps1 - Fast In-Memory Process Injection Hunter
Write-Host "=================================================================" -ForegroundColor Cyan
Write-Host "[*] 正在掃描全系統進程執行緒與記憶體分頁 (In-Memory Injection Scan)..." -ForegroundColor Cyan
Write-Host "=================================================================" -ForegroundColor Cyan

# 篩選高危常駐進程 (通常為攻擊者偏好的注入宿主)
$targetProcesses = Get-Process -IncludeUserName -ErrorAction SilentlyContinue | Where-Object { 
    $_.ProcessName -in @("explorer", "svchost", "notepad", "rundll32", "spoolsv", "regsvr32", "smartscreen")
}

$suspiciousCount = 0

foreach ($proc in $targetProcesses) {
    # 檢查該進程是否有不應存在的對外網路連線
    $netConns = Get-NetTCPConnection -OwningProcess $proc.Id -ErrorAction SilentlyContinue | Where-Object { 
        $_.State -eq "Established" -and $_.RemoteAddress -notmatch "^(127\.|10\.|172\.(1[6-9]|2[0-9]|3[01])\.|192\.168\.)"
    }

    if ($netConns) {
        Write-Host "  🔴 [CRITICAL] 進程 $($proc.ProcessName) (PID: $($proc.Id)) 正在連線海外未知公網 IP！" -ForegroundColor Red
        foreach ($conn in $netConns) {
            Write-Host "     └── 目的地: $($conn.RemoteAddress):$($conn.RemotePort)" -ForegroundColor Yellow
        }
        $suspiciousCount++
    }
}

if ($suspiciousCount -eq 0) {
    Write-Host "[+] 初篩完成：常見系統宿主進程未發現異常外部連線。" -ForegroundColor Green
} else {
    Write-Host "[!] 警告：發現 $suspiciousCount 個高度疑似遭記憶體注入之宿主進程，請立即轉儲 RAM！" -ForegroundColor Red
}
Write-Host "=================================================================" -ForegroundColor Cyan
```

### 4.1 SOC 研判對決 8 問 (SOC 8 Critical Questions)

| 編號 | 檢驗提問 (Verification Questions) | 是 (Yes) 判定導向 | 否 (No) 判定導向 |
| :---: | :--- | :--- | :--- |
| **Q1** | Sysmon Event 8 的來源進程是否為未簽名二進位檔、腳本解譯器或位於臨時目錄？ | 極高危：典型外部木馬發起遠端注入 (T1055) | 來源為微軟正式除錯器或防毒引擎軟體 |
| **Q2** | 被注入的目標進程（如 `explorer.exe` 或 `notepad.exe`）是否隨後發起了非預期的外聯通訊？ | 100% 確定為記憶體駐留木馬 (In-Memory Beacon) | 無任何網路連線，僅局部內部計算 |
| **Q3** | 記憶體分析（如 Process Hacker / Volatility）是否顯示目標進程含有 Unbacked RWX 分頁？ | 確定存在 Shellcode 或反射載入之惡意載荷 | 記憶體頁皆有硬碟上的合法 DLL 映像支援 |
| **Q4** | 執行緒的起始函數位址 (`StartAddress`) 是否為空的二進位數值（而非導出函數名）？ | 符合 Shellcode 起始特徵（未對應任何 Export） | 指向已知的標準導出函數（如 `LoadLibraryW`） |
| **Q5** | 目標進程是否為掛起狀態 (Suspended) 下被寫入，隨後被 `ResumeThread` 喚醒？ | 典型進程空心化 (Process Hollowing) 特徵 | 進程由系統正常啟動與排程執行 |
| **Q6** | 來源進程在發起注入後，是否在 5 秒內自我終止並嘗試從磁碟抹除本體？ | 攻擊者清理 Dropper 本體的反取證規避手法 | 程式保持長期常駐並提供正常軟體介面 |
| **Q7** | EDR 調用堆疊 (Call Stack) 中是否檢測到 Unhooking 痕跡（手動重載 ntdll.dll）？ | 進階 APT 規避 API Hook 的專屬攻擊特徵 | 正常使用系統提供的動態連結機制 |
| **Q8** | 該注入行為是否可由合法的桌面輸入法 (IME)、遠端控制或無障礙輔助軟體解釋？ | 傾向業務合規注入（需核對商業軟體清單） | 完全無法對應任何已安裝軟體之功能 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 5.1 應急處置階段 (Immediate Triage & Containment)

#### 1. 記憶體保全與進程轉儲 (Memory Dump First!)
**嚴禁在未轉儲記憶體前直接 `taskkill` 宿主進程！** 由於注入的 Shellcode 僅存在於記憶體中，直接終止進程將永久銷毀攻擊者的 C2 設定檔、載荷與指令記錄：

```powershell
# 步驟 1：使用 Sysinternals procdump 轉儲受害宿主進程之完整記憶體 (以 PID 2048 為例)
procdump.exe -ma 2048 C:\Forensics\injected_explorer_2048.dmp

# 步驟 2：利用 strings 或 Volatility 快速擷取記憶體中的 C2 網址與配置
strings.exe -n 8 -e l C:\Forensics\injected_explorer_2048.dmp | Select-String -Pattern "http"

# 步驟 3：確認轉儲完成後，立即終止受害進程或切斷其網路
Stop-Process -Id 2048 -Force
```

#### 2. 主機隔離與邊界阻斷
```bash
# 步驟 1：邊界防火牆封鎖記憶體中提取之 C2 IP (185.220.101.5)
iptables -I FORWARD 1 -d 185.220.101.5 -j DROP

# 步驟 2：EDR 發布端點網路隔離 (Network Isolation)，防止惡意代碼在內網橫向移動
```

### 5.2 長期架構加固 (Long-term Hardening)
1. **全面部署微軟攻擊表面減少規則 (ASR Rules)**：
   - 啟用規則：`Block Win32 API calls from Office macros`
   - 啟用規則：`Block process creations originating from PSExec and WMI commands`
2. **啟用端點進程緩解原則 (Process Mitigation Policies)**：
   - 透過 GPO 或 Exploit Protection 啟用 **Arbitrary Code Guard (ACG)**：禁止進程在運行時動態生成或修改可執行代碼（禁止將記憶體頁設定為 W+X），直接從 Windows 核心層粉碎 Shellcode 注入。
3. **部署端點 Sysmon 驅動層級遙測監控**：在全網 Windows 端點部署 Sysmon，並嚴格啟用 Event ID 8 (CreateRemoteThread) 與 Event ID 10 (ProcessAccess)，使任何跨進程存取無所遁形。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 6.1 實驗環境架設：模擬遠端執行緒跨進程代碼注入
本實驗將在受控實驗室中，利用 C 語言編寫一個極簡的注入器 `injector.exe`，模擬將載荷寫入 `notepad.exe` 並啟動遠端執行緒。

```c
// injector_sim.c - Educational Process Injection Simulation
#include <windows.h>
#include <stdio.h>

int main(int argc, char* argv[]) {
    if (argc < 2) {
        printf("Usage: injector_sim.exe <Target_PID>\n");
        return 1;
    }
    DWORD pid = atoi(argv[1]);
    printf("[*] 正在開啟目標進程 PID: %d ...\n", pid);
    
    HANDLE hProcess = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
    if (!hProcess) {
        printf("[-] OpenProcess 失敗！請以管理員權限執行。\n");
        return 1;
    }

    // 模擬彈出訊息的 Shellcode (x64 MessageBox 簡化模擬)
    unsigned char shellcode[] = "\x90\x90\x90\xC3"; // NOP NOP NOP RET

    LPVOID pRemoteCode = VirtualAllocEx(hProcess, NULL, sizeof(shellcode), MEM_COMMIT, PAGE_EXECUTE_READWRITE);
    printf("[+] 成功在目標進程開闢 RWX 記憶體: 0x%p\n", pRemoteCode);

    WriteProcessMemory(hProcess, pRemoteCode, shellcode, sizeof(shellcode), NULL);
    printf("[+] 成功寫入 Shellcode 至目標進程。\n");

    HANDLE hThread = CreateRemoteThread(hProcess, NULL, 0, (LPTHREAD_START_ROUTINE)pRemoteCode, NULL, 0, NULL);
    printf("[!] 成功調用 CreateRemoteThread 啟動執行緒！(Sysmon Event 8 觸發！)\n");

    WaitForSingleObject(hThread, 2000);
    CloseHandle(hThread);
    CloseHandle(hProcess);
    return 0;
}
```

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在記憶體鑑識中，什麼是「Unbacked Memory Section」？為什麼它是判定惡意代碼注入的鐵證？**  
  *考核核心*：正常程式執行的可執行代碼（RX 分頁）皆由硬碟上的 PE 檔案（如 `.exe` 或 `.dll`）經由作業系統記憶體管理器映射而來（稱為 File-backed / Mapped Image）。Unbacked 分頁代表該記憶體區塊是透過 `VirtualAlloc` 動態申請的匿名記憶體，其背後沒有任何硬碟檔案對應。若一個進程中存在 Unbacked 且具備可執行權限（RX 或 RWX）的分頁，99% 的機率是透過反射載入（Reflective Loading）或 Shellcode 注入的惡意代碼。

- [ ] **Q2：現代進階 C2 框架（如 Cobalt Strike）為什麼會將預設的記憶體權限從 RWX 改為先 RW 後 RX？這對防禦有何影響？**  
  *考核核心*：`PAGE_EXECUTE_READWRITE (RWX)` 同時具備可寫與可執行權限，嚴重違反現代作業系統 W^X 安全架構，極易被 EDR / AV 的記憶體掃描器直接標記為最高危險。現代 C2 框架採用兩階段權限切換：先申請 `PAGE_READWRITE (RW)` 寫入 Shellcode，寫入完畢後再呼叫 `VirtualProtect` 將權限轉變為 `PAGE_EXECUTE_READ (RX)`。這能成功規避僅針對靜態 RWX 分頁進行檢測的初階防護工具。

- [ ] **Q3：什麼是「早鳥注入 (Early Bird Injection)」？它如何繞過傳統 EDR 的 API Hooking 監控？**  
  *考核核心*：傳統 EDR 通常在進程啟動後，將自身的監控 DLL 注入到目標進程中，透過掛鉤（Hooking）`ntdll.dll` 核心 API 來監控行為。早鳥注入技術在呼叫 `CreateProcess` 時傳入 `CREATE_SUSPENDED` 參數，在目標進程主執行緒尚未初始化、EDR 監控 DLL 根本尚未載入進程空間的極短空檔期，利用 `QueueUserAPC` 將 Shellcode 插入非同步程序呼叫佇列，隨後喚醒執行緒。當目標進程首次執行時，會優先執行惡意代碼，達成完全避開 EDR Hook 的效果。

- [ ] **Q4：發現疑似遭注入的宿主進程（如 explorer.exe），資安鑑識員為什麼第一步嚴禁直接重開機或殺死該進程？**  
  *考核核心*：無檔案記憶體注入攻擊中，惡意程式本體、解密後的二進位代碼、C2 連線網址、對稱加密金鑰以及攻擊者先前下達的所有指令與輸出歷史，**全部僅暫存於受害進程的揮發性記憶體 (RAM) 中**。一旦直接重開機或使用 `taskkill` 強制終止進程，這些決定性的揮發性數位鐵證將被徹底銷毀且永久不可逆。正確 SOP 必須先使用 `procdump` 轉儲完整 RAM 映像後，方可實施圍堵處置。

- [ ] **Q5：在 Sysmon 遙測中，Event ID 8 (CreateRemoteThread) 與 Event ID 10 (ProcessAccess) 在進程注入獵捕上有何互補價值？**  
  *考核核心*：
  - **Event ID 8**：專門記錄遠端執行緒的「執行動作」，能直接抓出跨進程注入的發射點與目標；但缺點是無法捕捉不依賴 `CreateRemoteThread` 的注入手法（如透過劫持現有執行緒的 Thread Hijacking 或 APC 隊列注入）。
  - **Event ID 10**：記錄跨進程的「控制句柄取得與權限請求」，只要任何進程試圖對另一個進程進行寫入（請求 `PROCESS_VM_WRITE`），Event ID 10 都會留下存取記錄。
  兩者結合：Event ID 10 負責捕獲前期的記憶體開闢與寫入準備，Event ID 8 負責捕獲後期的執行緒觸發，形成完整的因果證據鏈。
