## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

### 1.1 案情境況：魔鬼藏在 1 個位元組——鑑識鏡像的翻車現場
某金融機構的核心資料庫遭植入定時抹除炸彈，數百萬筆交易紀錄瞬間清空。鑑識團隊扣押了疑似被用作攻擊中繼跳板的本機實體 SSD 硬碟（512GB NVMe）。
資安專員小陳信心滿滿地將這塊 SSD 接上了一台 Linux 鑑識筆電，準備製作位元串流 (Bit-stream) 鏡像。

然而，小陳犯下了三個看似細微卻足以毀滅全案的致命操作：
1. **防寫失效直連**：小陳圖一時方便，直接使用普通的 USB-to-NVMe 轉接盒連接鑑識機，未串接任何 **硬體防寫設備 (Hardware Write Blocker)**。當 Linux 桌面環境偵測到新硬碟時，系統的 `udisks2` 背景守護行程自動發送了掛載探測，並將硬碟上的日誌檔案系統 (Journaling File System) 自動進行了日誌重放 (Journal Replay)！
2. **存取時間戳靜默污染**：僅僅這一次未經防寫的物理插入，硬碟中超過 8,000 個關鍵系統檔案的最後讀取時間 (`atime`) 被強制覆寫為「小陳插入硬碟的當下時間」，徹底抹除了黑客在案發時實際存取檔案的真實時間線！
3. **無事前事後雙雜湊比對**：小陳使用 `dd` 指令製作完 `evidence.raw` 鏡像後，僅對鏡像檔計算了一次 SHA-256，未在製作前對「原始實體硬碟」進行先期雜湊計算。

在法庭審理時，被告技術專家當場出示系統時間日誌，指出硬碟在被執法扣押後仍有數千處寫入痕跡，且原告無法提供「原始物理介質 vs 鏡像複本」的一致性雜湊證明。
法官當庭裁定：**「無法確認本案送檢映像是否與案發當下狀態一致，檢方提交之鑑識鏡像因完整性存疑，不具證據能力！」**

這場慘痛教訓證明：**數位鑑識的第一道鐵壁是「永遠不信任預設系統環境」，必須透過「硬體防寫隔離 + 位元級精確複製 + 事前事後雙雜湊驗證」形成無可辯駁的數學證明鏈！**

```
                  [ 原始涉案實體硬碟 (Original Physical Media) ]
                                         │
                                         ▼
            ┌─────────────────────────────────────────────────────────┐
            │ ★ 物理防護層：硬體防寫設備 (Hardware Write Blocker)     │
            │ (物理阻斷所有 ATA / SCSI / NVMe Write Commands 寫入信號) │
            └────────────────────────────┬────────────────────────────┘
                                         │ (100% 唯讀位元流)
                                         ▼
            ┌─────────────────────────────────────────────────────────┐
            │ ★ 獲取運算層：Forensic Bit-Stream Acquisition (E01/RAW)  │
            │ 1. 採集前原始磁碟計算：Hash_Pre (MD5 + SHA-256)         │
            │ 2. 執行逐磁區映像克隆：Bit-by-Bit Cloning              │
            │ 3. 採集後原始磁碟計算：Hash_Post (驗證磁碟未遭寫入)      │
            │ 4. 映像副本檔案計算  ：Hash_Image (驗證鏡像無瑕疵)      │
            └────────────────────────────┬────────────────────────────┘
                                         │
                                         ▼
         【 完整性黃金等式：Hash_Pre == Hash_Post == Hash_Image 】
```

## 🔬 第一動：破譯本質——底層機制全景圖

### 2.1 位元串流映像 (Bit-Stream Image) vs 邏輯備份
在普通 IT 運維中，使用 Ghost 或檔案總管複製貼上稱為「邏輯備份」；而在數位鑑識中，必須使用 **位元串流精確鏡像 (Bit-Stream Image)**：

```
[ 實體儲存媒介內部結構 ]
┌─────────────────┬─────────────────┬─────────────────┬─────────────────┐
│ 開機磁區 (MBR)  │ 分區表 (GPT)    │ 已分配空間      │ 未分配空間      │
│ Sector 0        │ Partition Table │ (現存正常檔案)  │ (★已刪除檔案殘留)│
└─────────────────┴─────────────────┴─────────────────┴─────────────────┘
   │                 │                 │                 │
   ▼                 ▼                 ▼                 ▼
【 鑑識位元串流鏡像 (Bit-Stream Image) 逐磁區 1:1 完整獲取，絕不遺漏任何磁區！】
```
- **已分配空間 (Allocated Space)**：目前正在使用的正常業務檔案。
- **未分配空間 (Unallocated Space)**：檔案被黑客刪除後，檔案指標被移除，但二進位內容仍然殘留於磁碟扇區中。**普通邏輯備份完全不會備份未分配空間，只有 Bit-Stream 鑑識鏡像能夠將其完整克隆以供後續檔案雕刻 (File Carving)！**
- **磁區殘餘 (Slack Space)**：最後一個磁區未填滿之空白區塊，常隱藏黑客隱寫或臨時緩衝數據。

### 2.2 鑑識映像格式對比：RAW (DD) vs E01 (Expert Witness Format)
| 特徵維度 | RAW (DD / IMG / 001) | E01 (EnCase / Expert Witness Format) | 實戰鑑識推薦 |
| :--- | :--- | :--- | :--- |
| **檔案結構** | 純二進位磁區逐一連續排列，無任何標頭 (Header) 或中繼資料。 | 包含完整的案件中繼資料、採集時間、操作員姓名、分塊雜湊與壓縮演算法。 | 👑 **首選推薦 E01** |
| **內建校驗** | 無！若鏡像檔本身在傳輸中損壞 1 個位元組，無法察覺哪裡損壞。 | **每 64 磁區 (32KB) 內嵌一個 32-bit CRC 校驗碼**，能精確定位損壞區塊。 | 🔴 **E01 具備自體完整性** |
| **壓縮能力** | 不支援壓縮（512GB 硬碟必生成 512GB 檔案）。 | 支援無損壓縮（平均壓縮率 40% ~ 60%），大幅節省儲存空間。 | 🟢 **E01 節省鑑識空間** |
| **通用相容** | 全世界所有工具（Autopsy, FTK, Volatility, Linux CLI）100% 支援。 | 主流商業與開源鑑識工具均原生支援讀取。 | 兩者相容性皆極佳 |

### 2.3 硬體防寫設備 (Hardware Write Blocker) 工作原理
作業系統在連接儲存裝置時，除了發送「讀取 (Read)」指令，還會頻繁發送：
- `WRITE (10)`, `WRITE (16)`, `WRITE (32)`
- 磁碟重置、日誌更新、電源管理寫入指令
硬體防寫器內部搭載專用韌體微控制器 (Microcontroller)，實體串聯在原始硬碟與鑑識機之間：
- **讀取指令 (Read)**：透明雙向傳輸，正常回傳磁區數據。
- **寫入指令 (Write)**：在硬體層直接丟棄 (Drop) 或回傳硬體層錯誤，**任何寫入信號絕對無法穿透該晶片到達原始硬碟磁頭**！

## 🧭 第二動：解碼意圖——異常特徵速查表

| 檢驗指標 | 鑑識級合格映像 (Forensic Standard) | 瑕疵/不合格操作 (Defective Practice) | 風險後果 |
| :--- | :--- | :--- | :--- |
| **原始磁碟防寫驗證** | 硬體防寫設備綠燈常亮，系統日誌確認裝置為 `ro (read-only)`。 | 直連 USB 轉接線，系統自動掛載為 `rw` 讀寫模式。 | 🔴 **原始證據遭寫入污染 (致命)** |
| **雜湊計算時機** | 採集前先算、採集時邊克隆邊算、採集後針對鏡像再算（全吻合）。 | 僅事後對產出的映像檔計算單一雜湊，無原始硬碟對照。 | 🔴 **無法證明鏡像忠於原始硬碟** |
| **壞軌 (Bad Sectors) 處置** | 使用專用參數（如 `conv=noerror,sync`），壞軌處以 Null bytes (0x00) 填充對齊。 | 遇到壞軌時指令直接報錯中斷退出，或跳過磁區造成偏移量錯亂。 | 🔴 **分區表錯位，檔案系統無法解析** |
| **中繼資料宣告** | 映像內嵌案件編號、採集人員、硬碟序號、製造商與韌體版本。 | 僅有孤零零的一個 `disk.img`，無任何案件關聯資訊。 | 🟡 **法庭鏈條交代不清** |
| **儲存媒介剩餘容量** | 目標儲存硬碟格式化為 NTFS/ext4/exFAT，容量 > 原始硬碟 1.5 倍。 | 誤用 FAT32 檔案系統儲存，單檔上限 4GB 導致中途崩潰中斷。 | 🟡 **取證中斷重來** |

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 3.1 Linux 鑑識工作站全自動防寫鏡像與雙雜湊驗證工具 (`forensic_imager.py`)
在現場使用 Linux 鑑識環境（如 CAINE, SANS SIFT）執行此工具，能全自動完成防寫狀態確認、逐磁區鏡像與雙雜湊固化：

```python
#!/usr/bin/env python3
"""
forensic_imager.py - Forensic Bit-Stream Acquisition & Dual-Hash Verifier
用途：自動化執行物理磁碟 RAW 映像獲取，並提供事前與事後 MD5/SHA-256 雙重校驗。
"""
import os
import sys
import subprocess
import hashlib
import datetime

def check_write_block_status(device_path: str) -> bool:
    """檢查設備是否在內核層被標記為唯讀 (Read-Only)"""
    dev_name = os.path.basename(device_path)
    ro_sys_path = f"/sys/block/{dev_name}/ro"
    if os.path.exists(ro_sys_path):
        with open(ro_sys_path, "r") as f:
            status = f.read().strip()
            return status == "1"
    return False

def hash_stream(file_or_dev_path: str, max_bytes: int = None, block_size: int = 1048576):
    """計算串流雙雜湊 (MD5 + SHA-256)"""
    md5 = hashlib.md5()
    sha256 = hashlib.sha256()
    bytes_read = 0

    print(f"[*] 正在計算雜湊: {file_or_dev_path} ...")
    with open(file_or_dev_path, "rb") as f:
        while True:
            chunk = f.read(block_size)
            if not chunk:
                break
            md5.update(chunk)
            sha256.update(chunk)
            bytes_read += len(chunk)
            if max_bytes and bytes_read >= max_bytes:
                break
    return md5.hexdigest(), sha256.hexdigest(), bytes_read

def main():
    if len(sys.argv) < 3:
        print("用法: python3 forensic_imager.py <Source_Device_e.g._/dev/sdb> <Destination_Image_Path>")
        sys.exit(1)

    src_dev = sys.argv[1]
    dest_img = sys.argv[2]

    print("=" * 75)
    print("🛡️  數位鑑識位元串流映像採集與完整性驗證程序 (ISO/IEC 27037 Compliant)")
    print("=" * 75)

    # 1. 嚴格防寫檢驗
    is_ro = check_write_block_status(src_dev)
    if not is_ro:
        print(f"[!] ⚠️  警告：設備 {src_dev} 未在核心層被識別為唯讀 (ro!=1)！")
        print("[!] 強烈建議串接硬體防寫設備 (Hardware Write Blocker) 後再繼續！")
        confirm = input("[?] 是否強制繼續採集？(y/N): ")
        if confirm.lower() != 'y':
            print("[-] 已依鑑識規範中止程序。")
            sys.exit(1)
    else:
        print(f"[+] 驗證通過：內核標記 {src_dev} 為嚴格唯讀 (Read-Only) 狀態！")

    # 2. 獲取前計算原始設備雜湊
    print("\n[階段 1] 正在計算採集前原始設備之基準雜湊 (Pre-Acquisition Hash)...")
    pre_md5, pre_sha256, total_size = hash_stream(src_dev)
    print(f"  ├─ Pre-MD5     : {pre_md5}")
    print(f"  └─ Pre-SHA256  : {pre_sha256}")

    # 3. 執行位元串流精確克隆 (使用 dd 搭配同步填充參數)
    print(f"\n[階段 2] 正在執行逐磁區克隆 (Bit-by-Bit Imaging) ➔ {dest_img} ...")
    start_clone = datetime.datetime.now()
    # 鑑識要點：使用 conv=noerror,sync 係在遭遇 I/O 壞軌時以 null (0x00) 位元組填充以防磁區偏移
    # 司法嚴格標準下，若硬碟存在壞軌，應首選 dc3dd 或 dcfldd 留存精確壞軌日誌
    dd_cmd = [
        "dd",
        f"if={src_dev}",
        f"of={dest_img}",
        "bs=64K",
        "conv=noerror,sync",
        "status=progress"
    ]
    subprocess.run(dd_cmd, check=True)
    clone_duration = (datetime.datetime.now() - start_clone).total_seconds()
    print(f"[+] 克隆完成！耗時: {round(clone_duration, 2)} 秒")

    # 4. 獲取後計算產出鏡像檔之雜湊
    print("\n[階段 3] 正在驗證產出映像檔案之雜湊 (Image Verification Hash)...")
    img_md5, img_sha256, _ = hash_stream(dest_img)
    print(f"  ├─ Image-MD5   : {img_md5}")
    print(f"  └─ Image-SHA256: {img_sha256}")

    # 5. 完整性等式判定
    print("\n" + "=" * 75)
    print("📊 完整性驗證結果報告 (Integrity Audit Report)")
    print("=" * 75)
    if pre_md5 == img_md5 and pre_sha256 == img_sha256:
        print("🎉 【驗證成功 - ALL MATCHED】")
        print("原始磁碟與獲取鏡像之 MD5 與 SHA-256 雙雜湊 100% 吻合！")
        print("本鏡像具備完備之數學一致性證明，可呈堂供法庭鑑識分析使用。")
    else:
        print("❌ 【嚴重錯誤 - HASH MISMATCH】雜湊值不一致！鏡像已受損或原始磁碟遭寫入！")
        sys.exit(1)

if __name__ == "__main__":
    main()
```

### 3.2 司法鑑識專用工具 `dc3dd` 即時雙雜湊與壞軌日誌採集
在法庭司法呈堂的高標準要求下，建議優先選用美國國防部網路犯罪中心 (DC3) 認可之 `dc3dd`，其具備克隆中即時雙雜湊計算（免二次讀取磨損原始硬碟）與精確壞軌日誌記錄（Bad Sector Log）：

```bash
# 使用 dc3dd 執行鑑識級 RAW 克隆，即時產出 MD5/SHA-256 雜湊並留下壞軌審查日誌
dc3dd if=/dev/sdb of=/mnt/evidence_storage/CASE_001_RAW.dd \
    hash=md5 hash=sha256 \
    log=/mnt/evidence_storage/dc3dd_acquisition.log \
    badsect=0x00 \
    progress=on
```

## 🧭 第四動：研判分流——SOC 8 問與決策樹

### 4.1 鑑識獲取研判 8 問
| 編號 | 檢驗問題 | 合格標準 (Standard Compliant) | 違規瑕疵 (Vulnerable to Challenge) |
|:---:|:---|:---|:---|
| **Q1** | 連接原始儲存設備時，是否具備硬體防寫設備 (Write Blocker) 或唯讀硬體開關？ | 硬體防寫設備指示燈亮起，確認寫入信號實體隔絕 | 直連普通 SATA 線或 USB 轉接盒，未接防寫設備 |
| **Q2** | 製作映像時是否採用了位元串流 (Bit-Stream) 逐磁區克隆技術？ | 完整克隆 MBR/GPT、已分配與未分配空間 (E01/RAW) | 僅使用檔案總管或 `rsync` 複製可見檔案 |
| **Q3** | 原始磁碟事前計算之雜湊是否與映像檔事後計算之雜湊 100% 相同？ | 雙雜湊完全相符，並記錄於鑑識取得日誌中 | 雜湊不一致，或辯解「因作業系統自動掛載產生微小差異」 |
| **Q4** | 面臨硬碟壞軌 (Bad Sectors) 時，工具是否採取標準填充且留存壞軌日誌？ | 記錄壞軌具體磁區位址，並以固定 Null 字元填充對齊 | 忽略壞軌造成鏡像磁區整體向前或向後錯位 |
| **Q5** | 儲存鏡像的目的地硬碟，在寫入前是否已完成「鑑識級物理擦除 (Forensic Wipe)」？ | 儲存硬碟事前以全 0x00 填充擦除，確保無先前案件殘留 | 隨手拿取含有先前其他客戶測試數據的未清理硬碟 |
| **Q6** | 分析操作是否嚴格限制在「工作複本 (Working Copy)」而非母本映像上？ | 原始母本永久唯讀封存，分析時基於母本複製工作副本 | 直接在母本映像上掛載並執行寫入操作 |
| **Q7** | 採集的映像檔是否內嵌或伴隨完整的採集日誌 (Acquisition Log)？ | 包含工具版本、磁區總數、計算耗時與系統內核日誌 | 僅有一個副檔名為 `.img` 的空二進位檔 |
| **Q8** | 鑑識工具軟體（如 `ewfacquire`, `dc3dd`）是否符合 NIST CFTT 測試規範？ | 採用經美國國家標準技術研究所 (NIST) 驗證之軟體 | 使用不知名論壇下載或未經驗證的私有打包軟體 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 5.1 鑑識鏡像「三副本 (Three-Copy) 階層保管規範」
完成位元串流克隆後，資安團隊必須落實三副本分流防護：
1. **第一副本：實體原始證物 (Original Media)**：貼上防竄改封條，直接移入恆溫防磁金庫，非經法院要求絕不再次通電！
2. **第二副本：黃金母本映像 (Master Image)**：計算雙雜湊後設定檔案為唯讀屬性 (`chmod 400`)，存放於專屬唯讀儲存伺服器，作為數位基準線。
3. **第三副本：工作鑑識鏡像 (Working Copy)**：從黃金母本克隆出來的副本，供分析師載入 Autopsy、EnCase 或 FTK 進行雕刻、反編譯與分析。分析損毀隨時可重新從母本重新克隆。

### 6.1 實驗環境架設：模擬完整鑑識映像克隆與雙雜湊驗算
本實驗將在受控實驗室中，利用檔案虛擬化一個 20MB 的虛擬儲存設備，模擬完整的鑑識克隆與雜湊比對生命週期。

python3 -c "
with open('source_disk.raw', 'wb') as f:
    f.write(b'EVIDENCE_HEADER_SECTOR_0\x00' * 1024) # 模擬 MBR

    f.write(b'CONFIDENTIAL_DATA_LEAKED_FILE_CARVE\x00' * 512) # 模擬深層未分配空間
    f.seek(20 * 1024 * 1024 - 1)

echo "[+] 模擬實體硬碟 (20MB) 建立完成: source_disk.raw"

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：什麼是「位元串流映像 (Bit-Stream Image)」？為什麼不能僅使用一般的檔案總管複製貼上或 Ghost 備份？**  
  *考核核心*：位元串流映像是從儲存設備的第 0 磁區開始，不經過作業系統檔案系統邏輯層，完全以 1:1 的形式逐磁區將所有二進位位元（包括 MBR/GPT、分區表、已分配空間、未分配空間與磁區殘餘 Slack Space）精確複製。檔案總管複製貼上或 Ghost 僅備份「現存的正常檔案」，會將已被黑客刪除但深埋在未分配空間中的關鍵惡意載荷、日誌與被刪除機密徹底遺漏，無法用於深度數位鑑識。

- [ ] **Q2：在鑑識映像格式中，RAW (DD) 格式與 E01 (Expert Witness Format) 格式有何核心技術差異？為什麼法庭鑑識首選 E01？**  
  *考核核心*：
  - **RAW (DD)**：純平鋪二進位檔案，無任何檔案標頭、中繼資料或校驗塊。若檔案在傳輸儲存中發生位元翻轉，無法得知哪一個磁區損壞。
  - **E01**：在鏡像結構中內嵌了嚴格的案件中繼資料（案件編號、採集人員、硬碟序號）、支援無損壓縮，且**每 64 磁區 (32KB) 內嵌獨立的 CRC 校驗碼**。
  首選理由：E01 本身具備「自體完整性自驗能力」，任何單一磁區的竄改都能被精確定位，在法庭證明力與存儲效率上遠勝純 RAW 格式。

- [ ] **Q3：硬體防寫設備 (Hardware Write Blocker) 是如何在實體電路與通訊協定層級防止證據遭到寫入污染的？**  
  *考核核心*：硬體防寫設備串接在原始硬碟與鑑識工作站之間，其內部微處理器韌體會即時解析作業系統發送的所有儲存指令。當收到讀取指令 (如 ATA `READ SECTORS` 或 SCSI `READ (10)`) 時正常轉發回傳；一旦收到任何寫入指令 (如 `WRITE SECTORS`, `ERASE`, `TRIM`, `SET FEATURES`)，硬體控制器會在硬體層直接阻斷丟棄該指令，或向主機假報寫入錯誤，物理上杜絕任何寫入信號抵達原始儲存媒介。

- [ ] **Q4：在鑑識克隆過程中，如果原始硬碟存在「壞軌 (Bad Sectors)」，正確的處置技術規範是什麼？**  
  *考核核心*：標準規範要求使用具備錯誤容忍與同步填充功能的鑑識工具（如 `dd` 搭配 `conv=noerror,sync`，或 `ddrescue`、`ewfacquire`）。當讀取遭遇損壞磁區時，工具不能直接報錯中斷，亦不能跳過該磁區，而必須在壞軌處以預設的 Null Bytes (0x00) 精確填充該磁區大小。這樣能確保後續磁區的物理偏移量 (Offset) 不會發生錯位，維持整個分區表與檔案系統結構的數學完整性。

- [ ] **Q5：什麼是數位鑑識的「三副本原則 (Three-Copy Rule)」？為什麼鑑識分析人員絕對不能直接在原始母本上進行操作？**  
  *考核核心*：三副本為：
  1. **原始媒介 (Original Media)**：物理封存於證物庫，非經法院令狀不通電。
  2. **黃金母本 (Master Image)**：計算雜湊後設定為唯讀存檔，作為不可動搖的數位基準線。
  3. **工作副本 (Working Copy)**：從母本克隆出以供實際分析操作。
  原因：任何鑑識軟體（如搜尋關鍵字、掛載檔案系統、跑簽章還原）都有可能在映像中留下臨時標籤或微量修改。若直接在母本操作，一旦雜湊改變，全案證據完整性直接歸零。分析操作必須永遠針對工作副本執行。
