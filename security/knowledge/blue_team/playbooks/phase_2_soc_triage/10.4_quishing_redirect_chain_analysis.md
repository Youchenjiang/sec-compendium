# 10.4 QR Code 釣魚 (Quishing) 與跳轉識別 (Quishing & Redirect Chain Deobfuscation)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

週四中午 12:15，多名員工向資安部門通報，收到一封主旨為「`[緊急通知] 公司 Microsoft 365 雙因素認證 (MFA) 設備重設通知`」的官方郵件。
傳統 Secure Email Gateway (SEG) 防毒防垃圾郵件閘道器對該郵件亮起綠燈，標記為「乾淨郵件」，完全沒有觸發任何阻斷或警報！

原因令人不寒而慄：
這封郵件的內文中，**完全沒有任何明文文字超連結（URL）**，也沒有任何可執行的二進位檔案或 Office 附件！信件正中央僅嵌著一張精美、帶有微軟 Authenticator 官方圖示的高解析度 PNG 圖片——一張黑白相間的 **QR Code（快速響應矩陣碼）**。
圖片下方用醒目的粗體字寫著：「*為防止帳號遭鎖定，請立即拿起個人智慧型手機，開啟相機掃描上方 QR Code 完成 MFA 安全綁定！*」

這是近年席捲全球企業、令傳統郵件防線全面潰敗的新型攻擊向量——**QR Code 釣魚（Quishing - QR Code Phishing）**！

攻擊者的陰險戰術意圖：
1. **致盲傳統安全檢查（Bypassing Text & URL Scanners）**：傳統 SEG 郵件閘道器專注於掃描文字字串與 HTML `<a href="...">` 標籤。面對圖片二進位點陣資料，若無內建 OCR（光學字元辨識）與電腦視覺解碼器，傳統引擎直接判定為「安全圖片」無條件放行。
2. **切斷端點安全防護（Out-of-Band Attack to Mobile Devices）**：誘導受害者「拿起個人手機掃碼」，直接**將戰場從受企業 EDR、上網行為管理與代理伺服器保護的辦公電腦，轉移到缺乏企業防禦軟體的個人行動裝置**！
3. **多重中繼跳轉逃逸（Multi-Stage Open Redirects）**：QR Code 內部解析出的網址通常不是最終釣魚網站，而是利用合法高信譽平台（如 Google, Bing, LinkedIn, Cloudflare Workers）的「開放重定向（Open Redirect）」或短網址，層層跳轉以規避沙箱檢測。

藍軍分析師面對 Quishing 的破案思考流：
1. **圖片特徵萃取與條碼幾何定位（QR Code Geometric Detection）**：理解 QR Code 的物理矩陣結構（三個角點的位置探測圖形 Position Detection Patterns），利用 Python 開源函式庫（如 `pyzbar`, `opencv`）自 EML 郵件附件或內嵌 HTML CID 圖片中瞬間提取並解碼原始 Payload。
2. **多層級重定向鏈追蹤（Unraveling Multi-Hop Redirect Chains）**：使用不帶 Cookie 與指紋的自動化鑑識客戶端，追蹤 HTTP 301/302、HTML Meta Refresh、JavaScript `window.location` 跳轉，一路逆推至最終惡意釣魚落地頁（Landing Page）。
3. **反對抗指紋鑑識（Anti-Bot Cloaking & Geofencing Evasion）**：高階釣魚頁面會檢驗存取者的 User-Agent（若為行動裝置 iOS/Android 則展示釣魚頁，若為資安分析師電腦瀏覽器則展示無害頁面）。分析師如何偽裝請求指紋拆穿攻擊者偽裝？
4. **憑證反向釣魚中繼解構（Adversary-in-the-Middle - Evilginx2 Proxying）**：識別現代釣魚頁是否具備動態轉發登入封包、即時竊取 MFA Session Cookie 的進階代理能力。
5. **縱深加固與圖片光學防禦（Computer Vision Defense）**：如何在郵件閘道器部署自動解碼管道，並推動實施 FIDO2 / WebAuthn 硬體防釣魚憑證。

### 1. QR Code 物理幾何結構與解碼原理

QR Code（Quick Response Code，ISO/IEC 18004 國際標準）是一種二維矩陣條碼，由黑白正方形模組構成：

```text
  ┌───────────┐                                                 ┌───────────┐
  │ █ █ █ █ █ │ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ │ █ █ █ █ █ │
  │ █ ┌─────┐ █ │                                                 │ █ ┌─────┐ █ │
  │ █ │ █ █ │ █ │ ◄── [位置探測圖形 A]        [位置探測圖形 B] ──►  │ █ │ █ █ │ █ │
  │ █ └─────┘ █ │     (Position Finder)       (Position Finder)   │ █ └─────┘ █ │
  │ █ █ █ █ █ │                                                 │ █ █ █ █ █ │
  └───────────┘                                                 └───────────┘
   █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █
   █                                                                         █
   █   ┌─────────────────────────────────────────────────────────────────┐   █
   █   │                     編碼資料區 (Data Payload)                   │   █
   █   │   包含二進位糾錯碼 (Reed-Solomon Error Correction: L, M, Q, H)  │   █
   █   │   真實字串: "https://evil-login.workers.dev/auth?u=cfo"         │   █
   █   └─────────────────────────────────────────────────────────────────┘   █
   █                                                                         █
  ┌───────────┐                                                 ┌───────────┐
  │ █ █ █ █ █ │                                                 │ █ █ █ █ █ │
  │ █ ┌─────┐ █ │                                                 │ █   █   █ │
  │ █ │ █ █ │ █ │ ◄── [位置探測圖形 C]             [校正圖形] ──► │ █ █ █ █ █ │
  │ █ └─────┘ █ │     (Position Finder)            (Alignment)  │ █         │
  │ █ █ █ █ █ │                                                 │ █ █ █ █ █ │
  └───────────┘                                                 └───────────┘
```

- **位置探測圖形（Position Detection Patterns）**：條碼左上、右上、左下三個大方塊。黑白寬度比例為 `1:1:3:1:1`，攝影機藉此在 360 度任意旋轉下定位條碼角度。
- **糾錯碼機制（Reed-Solomon Code）**：
  - 分為 L (7%), M (15%), Q (25%), H (30%) 四級。
  - 黑客可利用高達 30% 的容錯空間，將惡意 URL 藏在含有微軟 Logo 的自訂圖片中心，即使 Logo 遮擋了中央點陣，條碼依然能 100% 成功解碼！

### 2. HTTP 302 與 JavaScript 動態跳轉鏈物理機制

攻擊者絕少將最終釣魚 URL 直接燒錄在 QR Code 中，因為固定 URL 容易被威脅情資（CTI）秒殺。常見跳轉架構：

```text
[QR Code 解析值]
https://t.ly/AbCd (短網址短鏈服務)
       │
       ▼ (HTTP 301 Moved Permanently - 第 1 跳)
https://storage.googleapis.com/static-bucket/redirect.html (合法公有雲中繼)
       │
       ▼ (HTML Meta Refresh / JavaScript 執行 - 第 2 跳)
<script>window.location.href="https://auth-session-login.net/login/verify";</script>
       │
       ▼ (HTTP 302 Found - 第 3 跳)
https://evil-phish-domain.com/office365/login.php (最終惡意釣魚落地頁!)
```

#### 黑客反分析防禦（Cloaking / Evasion Mechanism）：
釣魚網站伺服器（如基於 Nginx / Cloudflare Workers）在回傳頁面時執行環境審查：
```javascript
// 黑客伺服器端過濾邏輯偽代碼
if (!userAgent.includes("Mobile") && !userAgent.includes("iPhone") && !userAgent.includes("Android")) {
    // 檢測到非手機 (很可能是 SOC 分析師的 Windows/Linux 工作站)
    redirect("https://www.microsoft.com"); // 偽裝成官方網站脫身！
} else {
    // 真實手機使用者掃碼，展示惡意釣魚面板
    renderPhishingPage();
}
```

### 2. Python 自動化 QR Code 提取、反混淆與跳轉逆向追蹤器 (`quish_tracer.py`)

```python
#!/usr/bin/env python3
# 藍隊專用：全自動解析圖片中的 QR Code，並模擬 iPhone 追蹤多層跳轉鏈至最終惡意釣魚頁

import sys
import os
import requests
import cv2
from pyzbar.pyzbar import decode

def decode_qr_code(image_path):
    print(f"[*] Analyzing Image for QR Code Matrix: {image_path}")
    img = cv2.imread(image_path)
    if img is None:
        print("[-] Unable to read image file.")
        return None

    # 1. 影像預處理：轉灰階 + 二值化 (增強低對比度與反色條碼辨識率)
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
    
    # 2. 執行條碼解碼
    decoded_objects = decode(gray)
    if not decoded_objects:
        # 嘗試反色處理再次解碼 (應對白黑反轉條碼)
        inverted = cv2.bitwise_not(gray)
        decoded_objects = decode(inverted)

    if not decoded_objects:
        print("[-] No valid QR Code geometric pattern detected.")
        return None

    extracted_urls = []
    for obj in decoded_objects:
        url = obj.data.decode('utf-8')
        print(f"[🎯 QR CODE DISCOVERED] Type: {obj.type} | Data: {url}")
        extracted_urls.append(url)
    return extracted_urls

def trace_redirect_chain(initial_url):
    print(f"\n[*] TRACING MULTI-HOP REDIRECT CHAIN FOR:\n    {initial_url}")
    # 偽裝成 iPhone 行動瀏覽器，穿透黑客的 Cloaking 防線
    headers = {
        "User-Agent": "Mozilla/5.0 (iPhone; CPU iPhone OS 17_4 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.4 Mobile/15E148 Safari/604.1",
        "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8"
    }

    session = requests.Session()
    try:
        response = session.get(initial_url, headers=headers, timeout=8, allow_redirects=True)
        print("\n=== Redirect Chain History ===")
        if response.history:
            for idx, resp in enumerate(response.history):
                print(f"  [Hop #{idx+1}] Status: {resp.status_code} -> URL: {resp.url}")
        else:
            print("  [Direct Connection - No HTTP 30x Hops]")

        print(f"\n[🚨 FINAL LANDING PAGE DETECTED]:\n    {response.url}")
        print(f"[+] Final HTTP Status  : {response.status_code}")
        print(f"[+] Final Content-Type : {response.headers.get('Content-Type')}")
        
        # 檢查落地頁 HTML 是否含有密碼輸入框 (特徵判定是否為釣魚表單)
        if "type=\"password\"" in response.text.lower() or "name=\"passwd\"" in response.text.lower():
            print("[⚠️ CRITICAL RISK CONFIRMED] Landing page contains credential input forms!")
        return response.url
    except Exception as e:
        print(f"[-] Connection failed during trace: {e}")
        return None

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python3 quish_tracer.py <path_to_qr_image.png>")
        sys.exit(1)

    urls = decode_qr_code(sys.argv[1])
    if urls:
        for u in urls:
            trace_redirect_chain(u)
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：郵件中的 QR Code 圖片解析出的原始 URL，是否為企業登記核准的官方網域？** | 判定是否為仿冒的物理金標準：解碼出的網址根域名是否為公司名下的正規系統？若指向未知的公有雲 Worker、動態短網址或私人海外註冊域名，**100% 判定為惡意 Quishing**！ |
| **Q2：信件內文是否刻意引導使用者「使用個人智慧型手機」進行掃碼操作？** | 社交工程攻擊意圖審查：如果內文包含「請使用個人手機」、「拿起相機掃碼」、「手機版身分驗證」等字眼，代表黑客**蓄意誘騙使用者脫離企業電腦保護網（Out-of-Band Escape）**，此特徵惡意信賴度高達 99%。 |
| **Q3：追蹤跳轉鏈路時，中間是否經過了多層短網址或無關第三方的雲端中繼？** | 規避分析特徵比對：正規企業業務通知（如電子發票、研討會報名）幾乎一律使用直連官方二級網域；若連線過程中出現連續兩次以上的 HTTP 302 重定向、且中間利用了不知名短鏈，為典型黑客隱匿技術。 |
| **Q4：模擬行動裝置 User-Agent 訪問落地頁時，是否出現了假冒 M365 / Google 的登入介面？** | 落地頁視覺鑑識：檢驗最終落地頁的 HTML 原始碼。若頁面標題（`<title>`）與微軟登入頁面完全一致，且表單目標（`action`）指向外部私人伺服器，證實為憑證竊取釣魚站！ |
| **Q5：此 QR Code 是否為合法的雙因素驗證初始化密鑰（OTP Auth URI）？** | 排除內部業務誤報：部分企業 IT 在為新進員工配置 Authenticator 時，確會透過郵件發送 QR Code。檢查其解析字串是否以 `otpauth://totp/Company:user@company.com?secret=...` 開頭。若是標準的 `otpauth://` 協定，為正規內部維運；若是 `http://` 或 `https://` 網頁連結，必屬釣魚！ |
| **Q6：發信伺服器的 SPF / DKIM 認證結果與發信時間是否異常？** | 郵件來源輔助查證：若郵件標頭 `DMARC=fail`，且發信時間為海外週末清晨，高度吻合攻擊者自外網入侵的背景特徵。 |
| **Q7：企業內部目前是否有同仁已點擊或回報在手機上輸入了帳號密碼？** | 評估失陷現況（Compromise Assessment）：立即調閱 Azure AD / Okta 登入審計日誌。在郵件送達後的 30 分鐘內，該被鎖定帳號是否有來自行動裝置的成功登入記錄，且 IP 地理位置異常？ |
| **Q8：該落地頁是否採用了 Adversary-in-the-Middle (AitM) 逆向代理伺服器架構？** | 鑑識釣魚技術等級：若使用者完成登入後，收到的 MFA 推送在手機上通過，且伺服器能實時返回企業真實的內部系統頁面，證明黑客使用了 Evilginx 等即時中間人代理，所有 Session 憑證已完全失竊！ |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. Quishing 釣魚攻擊緊急應變處置流程

一旦確認有員工遭受 Quishing 攻擊並可能已在個人手機上完成掃碼登入：

```bash
# 步驟 1：立即撤銷受害員工所有的作用中工作階段 (Azure AD / Entra ID Session Revocation)
# 透過 PowerShell 連線 Azure AD，強制撤銷 Refresh Tokens，使黑客竊得的 Session Cookie 瞬間失效！
Revoke-AzureADUserAllRefreshToken -ObjectId "user-object-id-guid"

# 步驟 2：強制重置該網域帳號密碼，並要求重新註冊 MFA 驗證設備
Set-AzureADUserPassword -ObjectId "user-object-id-guid" -Password "NewRandomTempPassword123!" -ForceChangePasswordNextLogin $true

# 步驟 3：在企業郵件伺服器中，依據 QR Code 圖片之 SHA-256 雜湊，全面搜尋並硬刪除全網信件
# (以 Exchange ComplianceSearch 為例清除含該附件雜湊之信件)

# 步驟 4：將最終跳轉落地頁之惡意域名與中繼短網址，全數同步至邊界 NGFW、DNS-RPZ 與 EDR 阻斷清單
```

### 2. 生產環境防禦 Quishing 之長遠架構加固方案

1. **部署具備電腦視覺與光學解析能力的郵件安全閘道器（Computer Vision SEG）**：
   - 升級或引入具備 OCR 與二維條碼自動解析的郵件防護產品（如 Microsoft Defender for Office 365, Abnormal Security, Mimecast）。
   - 在閘道端自動解碼郵件中的所有圖片 QR Code，將解碼後的 URL 納入沙箱分析與惡意網址對撞流程。
2. **推行抗釣魚的 FIDO2 / Passkey 硬體雙因素驗證（Phishing-Resistant MFA）**：
   - 徹底淘汰基於手機簡訊（SMS）與手機 App 數字驗證碼（TOTP）的脆弱驗證方式。
   - 強制推行 **FIDO2 硬體金鑰（如 YubiKey）** 或 **Windows Hello for Business**。FIDO2 具備**「Origin 網域繫結（Origin Binding）」**特性，即使員工被騙去假的釣魚網頁，硬體金鑰會校驗當前瀏覽器真實網域名稱，拒絕對非正版網域發送簽名，從物理上 100% 免疫 AitM 代理釣魚！
3. **推展「絕不使用個人手機掃描公務郵件二維碼」之資安意識培訓**：
   - 建立全公司紅線制度：明訂企業 IT 官方**絕不會透過郵件要求同仁使用個人手機掃描 QR Code 進行身分驗證**。

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：為什麼相較於傳統帶有文字超連結的釣魚郵件，QR Code 釣魚（Quishing）能夠如此輕易地穿透傳統 Secure Email Gateway (SEG) 郵件防護閘道器？**
  - *驗收標準*：答出傳統 SEG 核心依賴正則表達式與爬蟲引擎掃描郵件 HTML 中的文字與 URL 標籤；而 Quishing 信件內文純粹為二進位圖片點陣資料，若安全閘道器未配備光學字元辨識（OCR）與二維條碼解碼器，會將其視為普通無害圖片放行。此外，掃碼促使受害者轉向個人手機操作，徹底脫離企業端點 EDR 與代理伺服器的保護網絡。
- [ ] **Q2：簡述 QR Code 物理結構中三個角點的「位置探測圖形（Position Detection Patterns）」在掃碼解碼過程中的核心作用。**
  - *驗收標準*：答出三個角點大方塊以獨特的 `1:1:3:1:1` 黑白寬度比例存在，解碼軟體以此圖形快速在視訊幀中進行幾何定位，確定條碼的大小、傾斜度與旋轉角度（支援 360 度任意方向精確讀取），進而對內部數據模組進行座標校正與取樣。
- [ ] **Q3：在對 Quishing 釣魚網址進行跳轉鏈路逆向追蹤時，為什麼資安分析師必須將 HTTP 請求頭的 User-Agent 偽裝成「行動裝置（如 iPhone / Android）」？如果用電腦預設瀏覽器會發生什麼後果？**
  - *驗收標準*：答出攻擊者為了逃避安全分析師與自動化沙箱的檢測，常在伺服器端部署「反分析偽裝機制（Cloaking）」，會檢驗訪客的 User-Agent。若檢測到是電腦端瀏覽器，會自動跳轉至微軟正版官網脫身；只有當識別出訪客為真實手機瀏覽器時，才會展示惡意釣魚頁面。偽裝成行動裝置方能誘騙黑客伺服器展示真正的惡意載荷。
- [ ] **Q4：在分析 QR Code 內容時，如何從協定前綴瞬間區分「企業合法的 MFA 初始化配置」與「惡意 Quishing 釣魚連結」？**
  - *驗收標準*：答出合法 Authenticator 綁定的 QR Code，其內部資料為標準的 `otpauth://` 協議 URI（如 `otpauth://totp/Company:user?secret=...`），用來向 App 寫入一次性密碼密鑰，不包含任何網頁跳轉；而 Quishing 釣魚二維碼解析出來的必定是 `http://` 或 `https://` 開頭的網頁跳轉 URL，誘導使用者連線至外部網站。
- [ ] **Q5：面對日益嚴重的 Quishing 與中間人代理釣魚（AitM），為什麼即便開啟了傳統簡訊（SMS）或 App 數字驗證碼的雙因素認證（MFA）依然會被完全攻破？企業徹底根治此威脅的終極身分認證架構是什麼？**
  - *驗收標準*：答出因為中間人代理（如 Evilginx2）能夠在釣魚頁面即時轉發受害者輸入的帳號、密碼與 SMS/TOTP 驗證碼給真正的微軟伺服器，並截獲伺服器下發的 Session Cookie 完成劫持。終極根治方案是推行具備「Origin 網域綁定」特性的抗釣魚憑證——**FIDO2 硬體安全密鑰（WebAuthn）或 Windows Hello for Business**，硬體金鑰會比對當前真實網址，拒絕向釣魚網站簽署驗證。
