# 10.1 郵件認證協定與仿冒偵測 (SPF, DKIM & DMARC Spoofing Defense)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

週五下午 16:30，企業財務長的收件匣彈出一封急件，寄件人抬頭赫然顯示為公司執行長：「`CEO <ceo@megacorp.com>`」，主旨為：「`緊急商業機密收購款項撥付指示 (Strictly Confidential)`」。
信件內文語氣急促且嚴肅，要求財務長在下班前將新台幣 1,500 萬元匯入指定的海外專案信託帳戶。

財務長仔細核對了寄件人信箱，完全是執行長的真實公務信箱 `ceo@megacorp.com`，甚至個人頭像與簽名檔皆完全一致。正當財務長拿起電話準備授權放款時，一通來自 SOC 監控中心的緊急阻斷電話切了進來：「請立即暫停任何匯款操作！那封郵件是透過南美洲某台受駭的 SMTP 伺服器偽造的 CEO 仿冒信件（BEC - Business Email Compromise）！」

一線分析師震驚問道：「為什麼 Outlook 上顯示的寄件人明明是 `ceo@megacorp.com`，攻擊者是怎麼做到無密碼冒名發信的？郵件安全防護到底哪裡被穿透了？」

這起事件揭露了經典的**「SMTP 協定原始設計缺陷與郵件身分認證失效（Email Spoofing）」**。
在原始 RFC 821 SMTP 協定規範中，信件如同未封口的明信片，發信人可以在信封標頭隨意填寫任何人的名字，郵件伺服器預設不會驗證發送者是否為該網域的合法擁有者！

為了從物理架構上消滅偽造郵件，現代資安藍軍必須構築**三大郵件認證鐵三角：SPF、DKIM 與 DMARC**！

資安分析師面對郵件仿冒的標準破案思維流：
1. **雙重發信人解構（RFC 5321 MailFrom vs RFC 5322 From:）**：透徹理解「信封發件人（Envelope From / Return-Path）」與「信紙發件人（Header From）」的物理分離，看穿黑客的「借殼寄信」障眼法。
2. **SPF 來源授權驗證（Sender Policy Framework）**：查詢寄件網域之 DNS TXT 記錄，比對發信伺服器 IP 是否登記在授權清單內，掌握 `+`, `-`, `~`, `?` 機制的嚴格程度。
3. **DKIM 密碼學完整性防竄改（DomainKeys Identified Mail）**：解密郵件標頭中的非對稱數位簽章（RSA/Ed25519），驗證信件主體（Body Hash）與標頭在傳輸過程中是否遭中間人竄改。
4. **DMARC 最終裁決與對齊機制（Alignment & Enforcement）**：
   - 核心靈魂：**網域對齊（Domain Alignment）**——SPF 與 DKIM 驗證通過的網域，是否與使用者在 Outlook 畫面上看到的 `From:` 網域 100% 嚴格相符？
   - 處置原則（Policy）：`p=none`（放任觀察）、`p=quarantine`（扔入垃圾桶）、`p=reject`（直接拒收退信）。
5. **DMARC 聚合鑑識回報分析（RUA / RUF Forensics）**：解析 XML 格式的 DMARC 全球回報，掌握全球有哪些惡意節點正在瘋狂偽冒企業網域發信，反向追查 APT 社交工程源頭。

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. 雙重寄件人解剖：RFC 5321 (Envelope) vs RFC 5322 (Header)

理解郵件仿冒的根本，在於區分 SMTP 傳輸協定中的「兩個寄件人」：

```text
【實體郵件比喻】
                     ┌─────────────────────────────────────────┐
                     │ 信封 (Envelope - RFC 5321)               │
                     │ 郵差只看信封上的退件位址:               │
                     │ MAIL FROM: <attacker@evil.com>          │
                     │                                         │
                     │   ┌─────────────────────────────────┐   │
                     │   │ 信紙 (Header - RFC 5322)        │   │
                     │   │ 收件人打開信只看信紙抬頭:       │   │
                     │   │ From: "CEO" <ceo@megacorp.com>  │   │
                     │   │ To:   "CFO" <cfo@megacorp.com>  │   │
                     │   │ Subject: Urgent Wire Transfer   │   │
                     │   │                                 │   │
                     │   │ 財務長，請立即向該帳戶匯款...   │   │
                     │   └─────────────────────────────────┘   │
                     └─────────────────────────────────────────┘
```

- **RFC 5321 (Envelope From / Return-Path)**：SMTP 對話中 `MAIL FROM` 命令傳遞的位址。郵件伺服器路由退信時使用。**早期 SPF 僅驗證此位址！**
- **RFC 5322 (Header From)**：郵件內文標頭 `From:` 欄位。這也是 Outlook、Gmail、Thunderbird 等 MUA 客戶端**唯一展示給使用者眼睛看的發信人**！
- **黑客欺騙漏洞**：若企業未啟用 DMARC，黑客可以使用自己註冊的合法網域通過 SPF 檢查（信封寫 `evil.com`），但信紙上直接寫偽造的 `ceo@megacorp.com`，防護機制全面被繞過！

### 2. 三大協定物理結構與語法參數全解析

#### (1) SPF (Sender Policy Framework) — DNS TXT 記錄
`v=spf1 ip4:192.0.2.0/24 include:_spf.google.com -all`
- **機制修飾符（Qualifiers）**：
  - `+` (Pass)：完全信任授權（預設省略符號）。
  - `-` (Fail / HardFail)：**未授權直接拒絕**！藍軍最高安全基線。
  - `~` (SoftFail)：未授權但標記為垃圾郵件，仍放行。
  - `?` (Neutral)：不置可否，不做任何判斷（極度不安全）。
- **查詢上限鐵律**：SPF 規格（RFC 7208）嚴格限制 DNS 查找機制（`include`, `a`, `mx`, `ptr`, `exists`）**總計不得超過 10 次**！超過 10 次直接觸發 `PermError`（永久錯誤），導致全網發信全部驗證失敗！

#### (2) DKIM (DomainKeys Identified Mail) — 密碼學簽章標頭
發信伺服器在郵件標頭中插入加密指紋：
```http
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed;
    d=megacorp.com; s=selector1; t=1726156800;
    bh=47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=;
    h=From:To:Subject:Date:Message-ID;
    b=kO5s7D8N...[Base64加密簽名]...==
```
- `d=`：簽署該郵件的網域。
- `s=`：Selector 選擇器（收件端以此名稱向 DNS 查詢公開金鑰，如 `selector1._domainkey.megacorp.com`）。
- `bh=`：Body Hash，郵件內文經過 SHA-256 雜湊後的摘要值。
- `b=`：以私密金鑰對指定標頭與 Body Hash 計算出的數位簽章。

#### (3) DMARC 終極審判機制與網域對齊 (Alignment)
收件端在同時比對 SPF 與 DKIM 後，必須通過**網域對齊（Alignment）**：
- **SPF 對齊**：RFC 5321 Return-Path 網域必須與 RFC 5322 Header From 網域完全相同。
- **DKIM 對齊**：`DKIM-Signature` 中的 `d=` 網域必須與 RFC 5322 Header From 網域完全相同。
- **DMARC 記錄格式**：
  `v=DMARC1; p=reject; sp=reject; pct=100; rua=mailto:dmarc-rua@megacorp.com; ruf=mailto:dmarc-ruf@megacorp.com`
  - `p=`：主網域處置原則（`none`, `quarantine`, `reject`）。
  - `sp=`：子網域處置原則（防止黑客利用未設定 SPF 的子網域 `hr.megacorp.com` 繞過）。
  - `pct=100`：強制執行比例為 100%。

### 3. EML 郵件原始碼自動化驗證與仿冒偵測工具 (Python EML Inspector)

```python
#!/usr/bin/env python3
# 藍隊專用：深度解析 EML 郵件標頭，驗證 SPF/DKIM/DMARC 認證結果與網域對齊

import email
from email import policy
import sys
import re

def parse_eml_authentication(eml_file_path):
    print(f"[*] Analyzing EML Artifact: {eml_file_path}")
    with open(eml_file_path, "rb") as f:
        msg = email.message_from_binary_file(f, policy=policy.default)

    header_from = msg.get("From", "")
    return_path = msg.get("Return-Path", "")
    auth_results = msg.get("Authentication-Results", "")
    received_spf = msg.get("Received-SPF", "")
    subject = msg.get("Subject", "")

    print(f"[+] Subject       : {subject}")
    print(f"[+] Header From   : {header_from}")
    print(f"[+] Return-Path   : {return_path}")
    print(f"[+] Auth-Results  : {auth_results}\n")

    # 提取 Header From 的域名
    from_domain_match = re.search(r'@([a-zA-Z0-9.-]+)', header_from)
    from_domain = from_domain_match.group(1).lower() if from_domain_match else "UNKNOWN"

    # 提取 Return-Path 的域名
    return_domain_match = re.search(r'@([a-zA-Z0-9.-]+)', return_path)
    return_domain = return_domain_match.group(1).lower() if return_domain_match else "UNKNOWN"

    print(f"[*] Evaluating DMARC Alignment:")
    print(f"    Header From Domain : {from_domain}")
    print(f"    Return-Path Domain : {return_domain}")

    # 檢查對齊
    is_aligned = (from_domain == return_domain) and (from_domain != "UNKNOWN")
    print(f"    SPF Domain Alignment : {'✅ PASS (Aligned)' if is_aligned else '❌ FAIL (Unaligned - High Spoofing Risk!)'}")

    # 檢查是否含有 DMARC Fail 標記
    if "dmarc=fail" in auth_results.lower():
        print("\n[🚨 CRITICAL WARNING] Authentication-Results indicates DMARC FAIL!")
        print("    This email is an unauthorized spoofed email masquerading as legitimate sender!")
    elif "dmarc=pass" in auth_results.lower() and is_aligned:
        print("\n[✅ AUTHENTICATED] DMARC PASS and aligned with legitimate domain.")
    else:
        print("\n[!] DMARC status uncertain or unaligned. Proceed with extreme caution.")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python3 inspect_eml.py <path_to_email.eml>")
        sys.exit(1)
    parse_eml_authentication(sys.argv[1])
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：郵件標頭中 `Authentication-Results` 的 `dmarc` 最終裁決狀態為何？** | 判定真偽的最快標準：若明確記錄 `dmarc=fail`，代表該郵件絕對不是經授權的官方伺服器發出；若為 `dmarc=pass`，代表發信來源與簽名皆為正版。 |
| **Q2：信紙 `From:` 顯示的顯示名稱（Display Name）與真實信箱是否一致？** | 識別初級仿冒：顯示名稱寫著 `CEO <ceo@megacorp.com>`，但實際點開後真實信箱卻是 `ceo.megacorp@gmail.com` 或 `random@freehost.net`？此為典型「顯示名稱欺騙（Display Name Spoofing）」。 |
| **Q3：`Return-Path` 網域與 `From:` 網域是否相同？若不相同，是否為合規代發平台？** | 驗證網域對齊：若 `Return-Path` 為 `bounce.sendgrid.net` 或 `amazonses.com`，需確認企業是否曾簽署該 SaaS 的行銷代發合約；若為私人註冊雜湊網域，則為惡意借殼發信。 |
| **Q4：郵件最底層的第一跳 `Received` 標頭 IP 是否位於發信網域的官方登記國家？** | 路由真實性檢核：例如企業位於台灣，但第一跳 `Received` 記錄來自俄羅斯或奈及利亞的家庭寬頻動態 IP，高達 99% 為帳號遭竊或外部偽冒。 |
| **Q5：發信伺服器的反向解析（PTR 記錄 / FCrDNS）是否有效？** | 檢驗 MTA 合規性：發信 IP 是否具備有效的反向 DNS 解析，且解析後的網域名稱再次 forward 查詢時能對應回該 IP？正規商業郵件伺服器 100% 具備有效的 FCrDNS。 |
| **Q6：信件內文是否含有高度誘騙性的緊急財務轉帳、變更收款帳戶或點擊登入指示？** | 評估社交工程語意：信件是否以「保密收購」、「緊急薪資核對」、「密碼即將過期」等恐慌心理誘導點擊外部連結或執行匯款？此為典型 BEC / Phishing 意圖。 |
| **Q7：信件所帶之 DKIM 簽章網域（`d=` 欄位）是否為受信之權威網域？** | 檢驗密碼學背書：雖然有 DKIM 簽名，但簽署網域是 `d=megacorp.com` 還是黑客自己的 `d=attacker-vps.com`？若非原廠網域背書，該簽名對證明發件人毫無意義。 |
| **Q8：若該信被判定為 DMARC 失敗，目前該網域的 DMARC 原則（Policy）為何？** | 評估防護漏洞：若企業目前的 DMARC 仍設為 `p=none`，意味著收件伺服器就算發現信件是假造的，依然會「被迫放行進收件匣」！必須向管理層推動升級為 `p=reject`。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 釣魚仿冒郵件緊急圍堵 SOP

當確認有未授權仿冒信件穿透至員工收件匣時，依序執行緊急阻斷處置：

```bash
# 步驟 1：在 Microsoft 365 / Exchange 中一鍵全網搜尋並強制物理刪除該郵件 (Purge)
# 透過 PowerShell 連線 Exchange Online，依據 Message-ID 或主旨全面清除
Search-Mailbox -Filter 'MessageId -eq "<202609121630.xyz@evil.com>"' -DeleteContent -Force

# 步驟 2：在郵件安全閘道器 (SEG) 立即將發信惡意 IP 加入即時黑名單
# 例如在 Postfix 或邊界防火牆中封鎖該來源 IP
iptables -I INPUT -s 198.51.100.50 -p tcp --dport 25 -j DROP

# 步驟 3：向網域註冊商或託管平臺通報惡意 C2 網域進行 Abuse 下架 (Takedown)
```

### 2. 企業郵件認證體系根治加固方案

1. **落實嚴格的 SPF `-all` 硬阻斷策略**：
   - 堅決廢棄容忍性極高的 `~all`（SoftFail）與 `?all`（Neutral），全網主網域與發信網域統一採用 `-all`。
2. **推動 DMARC 進入終極 `p=reject` 強制阻斷態**：
   - **第一階段（監控期：1~3 個月）**：`p=none; rua=...`，透過 DMARC 分析平臺排查企業內部所有合法的第三方代發服務（Salesforce, Zendesk）。
   - **第二階段（隔離期：1 個月）**：`p=quarantine; pct=100`，未對齊郵件自動被移至垃圾信箱。
   - **第三階段（終極防護：永久）**：`p=reject; sp=reject; pct=100`，收信伺服器直接拒收一切仿冒郵件，徹底終結針對企業域名的偽造攻擊！
3. **部署反同形異義字過濾（Punycode Protection）**：
   - 在郵件閘道器中啟用規則，攔截所有包含混淆 Unicode（如西里爾、希臘字母）替換英文字元的相似註冊網域名稱。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 靶場環境說明
- **郵件伺服器**：Postfix + OpenDKIM 接收測試機 (`10.0.0.25`)
- **發信測試端**：Kali Linux (`192.168.56.101`，使用 `swaks` 郵件瑞士刀發信工具)
- **實戰目標**：模擬攻擊者偽造 `ceo@megacorp.com` 發送勒索信，分析收件端產生的標頭變化，並驗證啟用 DMARC `p=reject` 後，偽造信件如何被 SMTP 協定直接拒收！

### 實戰驗證步驟

#### 步驟 1：攻擊者發送仿冒郵件（DMARC 未啟用階段）
在攻擊機執行 `swaks`，信封使用黑客地址，但信紙抬頭偽造為 CEO：
```bash
swaks --to cfo@targetcorp.local \
      --from bounce@attacker.org \
      --h-From '"CEO" <ceo@megacorp.com>' \
      --header "Subject: Urgent Wire Transfer" \
      --body "Please wire $500,000 immediately." \
      --server 10.0.0.25
```
- **測試結果**：信件順利被郵件伺服器接收！收件者 Outlook 上斗大顯示「寄件人：CEO <ceo@megacorp.com>」，仿冒得手！

#### 步驟 2：藍軍檢視接收到的 EML 原始碼標頭
檢視 `/var/mail/cfo` 檔案：
```http
Return-Path: <bounce@attacker.org>
Received: from attacker.org (attacker.org [192.168.56.101])
    by mail.targetcorp.local with ESMTP for <cfo@targetcorp.local>; ...
From: "CEO" <ceo@megacorp.com>
Authentication-Results: mail.targetcorp.local;
    spf=pass (sender IP is 192.168.56.101) smtp.mailfrom=attacker.org;
    dmarc=fail (p=none; dis=none) header.from=megacorp.com
```
- **鑑識發現**：SPF 雖然 Pass（因為比對的是 `attacker.org`），但 DMARC 明確標記 `dmarc=fail`！因為 `attacker.org` 與 `megacorp.com` **未對齊（Unaligned）**！

#### 步驟 3：防禦加固——在 DNS 啟用 DMARC `p=reject`
在 DNS 伺服器為 `megacorp.com` 新增嚴格 DMARC 政策：
```dns
_dmarc.megacorp.com. IN TXT "v=DMARC1; p=reject; pct=100; rua=mailto:dmarc@megacorp.com"
```

#### 步驟 4：攻擊者再度嘗試發動完全相同的偽造攻擊
再度執行 `swaks` 命令：
```bash
swaks --to cfo@targetcorp.local --from bounce@attacker.org --h-From '"CEO" <ceo@megacorp.com>' --server 10.0.0.25
```

#### 步驟 5：驗證阻斷結果
終端立即拋出 SMTP 拒絕錯誤代碼：
```text
<~ 550 5.7.1 Unauthenticated email from megacorp.com is not accepted due to domain's DMARC policy. Please contact administrator.
~> QUIT
```
**實戰結論**：DMARC `p=reject` 策略在 SMTP 交握階段即刻將未對齊的偽造信件物理擊落，徹底消滅仿冒威脅！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在電子郵件通訊中，RFC 5321（MailFrom / Return-Path）與 RFC 5322（Header From）有何本質區別？黑客如何利用兩者的分離實施 SPF 繞過？**
  - *驗收標準*：答出 RFC 5321 是 SMTP 傳輸信封發件人，用於伺服器路由與退信回報；RFC 5322 是信紙抬頭，是使用者客戶端唯一可見的寄件者。黑客可以利用自己擁有的合法網域註冊 SPF 作為 RFC 5321 信封（通過 SPF 檢查），但信紙抬頭隨意填寫被仿冒企業的 CEO 地址（RFC 5322），若無 DMARC 對齊檢查，此仿冒信件將被完全放行。
- [ ] **Q2：簡述 DMARC 協定中的「網域對齊（Domain Alignment）」機制。它如何解決單純 SPF 與 DKIM 無法防範仿冒的問題？**
  - *驗收標準*：答出網域對齊要求 SPF 驗證的網域（Return-Path）或 DKIM 簽名網域（`d=` 欄位）必須與使用者眼睛看到的 Header From 網域嚴格或放寬匹配一致。只有當密碼學驗證通過且網域完全一致時，DMARC 才判定合格，徹底阻斷了借用外部合法網域為偽造抬頭「借殼背書」的漏洞。
- [ ] **Q3：在 SPF 記錄中，結尾的 `-all`、`~all` 與 `?all` 分別代表什麼物理意涵？為什麼藍軍強烈要求生產環境必須配置為 `-all`？**
  - *驗收標準*：答出 `-all` 代表 HardFail（硬失敗，未授權直接拒收退信）；`~all` 代表 SoftFail（軟失敗，標記可疑但放行進入收件箱）；`?all` 代表 Neutral（中立不做任何判斷）。若配置為 `~all` 或 `?all`，當黑客偽冒發信時，收件端仍會將郵件放入使用者信箱，喪失防禦主動性；只有 `-all` 才能提供強硬的阻斷防禦基線。
- [ ] **Q4：為什麼 SPF 協定規範（RFC 7208）嚴格限制 DNS 查詢機制總數不得超過 10 次？如果超過 10 次會導致什麼致命後果？**
  - *驗收標準*：答出限制 10 次是為了防止攻擊者利用 SPF 進行分散式阻斷服務（DNS Amplification / DoS 放大攻擊）。如果 DNS 查找次數超過 10 次，收件端郵件伺服器會直接拋出 `PermError`（永久錯誤），此時多數安全閘道器會將該網域發出的所有正常業務信件全數拒收或判定為垃圾郵件，造成嚴重的全域業務中斷。
- [ ] **Q5：企業推動 DMARC 部署時，為什麼必須依序遵循 `p=none` ➔ `p=quarantine` ➔ `p=reject` 的三階段原則？直接上線 `p=reject` 有何重大業務風險？**
  - *驗收標準*：答出因為現代企業廣泛使用外部第三方 SaaS（如電子薪資單、Salesforce、EDM 行銷代發）以公司網域名義發信。若未經 `p=none` 監控期收集 RUA 報表清查所有合法第三方並補齊 DKIM/SPF 對齊，直接啟用 `p=reject` 會將公司所有正常的行銷推播、系統通知與業務外部信件全數誤殺拒收，引發災難性業務事故。
