## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

### 1.1 案情境況：急件通報中的漏洞優先級評定爭議
資安運維中心 (SOC) 週五下午接獲資安通報平台 (CERT) 發布的兩起最新重大 0-day 弱點報告：
- **漏洞 A (內部 ERP 系統反序列化 RCE)**：外部無法直連，需擁有 Domain User 帳號，但一旦觸發可直接獲取伺服器 SYSTEM 權限並橫向突破至底層 VMware ESXi 虛擬化宿主機。
- **漏洞 B (對外形象官網 Reflected XSS)**：公網任何人皆可存取，但需誘導管理員點擊特定構造的釣魚連結，成功後僅能竊取該管理員於官網的 Session Cookie。

管理階層與 L1 值班人員急於封鎖外部攻擊，傾向將「公網可達、任何人皆能打」的漏洞 B 列為緊急修補 (Critical)，而將漏洞 A 視為內部問題暫緩。

然而，精通 CVSS 評分機制的 L2 資安工程師介入：
1. **漏洞 A**：`CVSS:3.1/AV:A/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H` ➔ **Base Score: 9.0 (Critical)**。因為其具備 **Scope: Changed (S:C)**（容器/虛擬化逃逸突破權限邊界），且三項衝擊指標皆為 High！
2. **漏洞 B**：`CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N` ➔ **Base Score: 6.1 (Medium)**。需使用者互動 (UI:R) 且僅造成部分機密性與完整性衝擊。

若不理解底層 CVSS 指標量化公式，資安團隊將陷入「表面直覺判定」的重大盲區，導致真正致命的內網橫向與虛擬化逃逸漏洞被延遲修復。

```
[ 傳統直覺誤區 ]
"公網無身分可連 (AV:N/PR:N) = 必定是 Critical" ──► 誤將低衝擊 XSS 升級為緊急通報 (疲於奔命)

[ CVSS 嚴謹量化架構 ]
可利用性指標群 (Exploitability) ──┐
                                  ├──► [ 核心演算法 (Roundup) ] ──► Base Score (0.0 ~ 10.0)
衝擊指標群 (Impact: C / I / A) ────┤                                 └── Scope 狀態 (Unchanged vs Changed)
                                  │
權限範圍邊界 (Scope: S:U vs S:C) ─┘
```

### 1.2 SOC 研判心智模型 (Mental Workflow)
```
[收到弱點揭露 (CVE / N-day / 滲透測試報告)]
                   │
                   ▼
[第一步：可利用性維度評定 (Exploitability Metrics)]
         ├── 攻擊路徑 (AV)：Network(N) / Adjacent(A) / Local(L) / Physical(P)
         ├── 攻擊複雜度 (AC)：Low(L) / High(H)
         ├── 所需身分權限 (PR)：None(N) / Low(L) / High(H)
         └── 使用者互動 (UI)：None(N) / Required(R)
                   │
                   ▼
[第二步：安全權限範圍判定 (Scope Metric - S)]
         ├── 脆弱元件與受害元件是否處於同一權限控制範圍？
         └── 是否發生跨租戶突破、虛擬化逃逸、沙箱突破？➔ Changed (S:C)
                   │
                   ▼
[第三步：三大衝擊面維度評定 (Impact Metrics - CIA)]
         ├── 機密性 (C)：High / Low / None (資料全部洩漏 vs 部分洩漏 vs 無)
         ├── 完整性 (I)：High / Low / None (任意篡改代碼/資料庫 vs 局部修改)
         └── 可用性 (A)：High / Low / None (完全拒絕服務/關機 vs 效能降低)
                   │
                   ▼
[第四步：演算法計算與等級映射 (Base Score & Severity Rating)]
         ├── 0.0: None | 0.1~3.9: Low | 4.0~6.9: Medium | 7.0~8.9: High | 9.0~10.0: Critical
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Mathematical Formulas)

### 2.1 CVSS v3.1 基本指標公式數學模型 (Mathematical Breakdown)
CVSS v3.1 基本評分由 **衝擊子分數 (Impact Sub-Score, $ISS$)** 與 **可利用性子分數 (Exploitability Sub-Score, $ESS$)** 結合計算。

#### 1. 可利用性子分數 ($Exploitability$) 計算：
$$Exploitability = 8.22 \times \text{MetricWeight}(AV) \times \text{MetricWeight}(AC) \times \text{MetricWeight}(PR) \times \text{MetricWeight}(UI)$$

- **AV (Attack Vector)**：$N=0.85,\; A=0.62,\; L=0.55,\; P=0.20$
- **AC (Attack Complexity)**：$L=0.77,\; H=0.44$
- **UI (User Interaction)**：$N=0.85,\; R=0.62$
- **PR (Privileges Required)**：*注意！權重取決於 Scope 是否變更*：
  - 若 $Scope = Unchanged (S:U)$：$N=0.85,\; L=0.62,\; H=0.27$
  - 若 $Scope = Changed (S:C)$：$N=0.85,\; L=0.68,\; H=0.50$

#### 2. 衝擊子分數 ($Impact$) 計算：
首先計算中間衝擊變數 $ISS_{base}$：
$$ISS_{base} = 1 - [(1 - \text{Weight}(C)) \times (1 - \text{Weight}(I)) \times (1 - \text{Weight}(A))]$$
其中各項衝擊權重：$High = 0.56,\; Low = 0.22,\; None = 0.0$。

接著根據 Scope 決定最終 $Impact$：
- 若 **$Scope = Unchanged (S:U)$**：
  $$Impact = 6.42 \times ISS_{base}$$
- 若 **$Scope = Changed (S:C)$**：
  $$Impact = 7.52 \times (ISS_{base} - 0.029) - 3.25 \times (ISS_{base} - 0.02)^{15}$$

#### 3. 最終基礎分數 (Base Score) 計算：
若 $Impact \le 0$，則 $\text{BaseScore} = 0.0$。否則：
- 若 **$Scope = Unchanged (S:U)$**：
  $$\text{BaseScore} = \text{Roundup}(\min(Impact + Exploitability,\; 10.0))$$
- 若 **$Scope = Changed (S:C)$**：
  $$\text{BaseScore} = \text{Roundup}(\min(1.08 \times (Impact + Exploitability),\; 10.0))$$

> **特別規定：Roundup 函數定義**  
> CVSS 規範中的 `Roundup` 為無條件進位至小數點後第一位（例如：$4.02 \to 4.1$, $4.00 \to 4.0$）。

### 2.2 CVSS v4.0 最新進化與架構變更剖析
2023 年底發布的 **CVSS v4.0** 針對 v3.1 的多項結構性弱點進行了顛覆性升級：
1. **取消單一 Scope 指標**：v3.1 的 Scope (S) 容易造成評估人員主觀爭議。v4.0 將衝擊指標拆分為雙層架構：
   - **易受攻擊系統衝擊 (Vulnerable System Impact)**：$VC / VI / VA$
   - **後續關聯系統衝擊 (Subsequent System Impact)**：$SC / SI / SA$
2. **新增攻擊複雜度與攻擊需求拆分**：
   - $AC$ (Attack Complexity)：專注於防禦技術逃逸（如 ASLR/DEP 繞過）。
   - $AT$ (Attack Requirements)：專注於目標先決條件（如特定 Race Condition 或中繼劫持）。
3. **使用者互動細分**：$UI:N$ (None), $UI:P$ (Passive - 受害者僅造訪頁面即中招), $UI:A$ (Active - 受害者需特意輸入密碼或按確認)。
4. **巨量矩陣宏觀向量評分 (MacroVector / Lookup Tables)**：v4.0 捨棄了連續小數公式乘法，改採預先驗證並校準的**巨量多維查找表 (Lookup Tables)**，消除了 v3.1 公式曲線非線性的數學瑕疵。

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 3.1 Python 實戰工具：CVSS v3.1 向量解析與精確計分器 (`cvss_calculator.py`)
資安分析師可使用此遵循 FIRST 官方數學標準的 Python 腳本，手動輸入向量或直接導入 CVE 向量字串進行即時解析與驗證。

```python
#!/usr/bin/env python3
"""
cvss_calculator.py - CVSS v3.1 Official Specification Calculator
嚴格依照 FIRST CVSS v3.1 規範實作 Roundup 函數、Exploitability、Impact 與 Base Score 計算。
"""
import sys
import math
import re

def roundup(val):
    # CVSS v3.1 規範定義之 Roundup (無條件進位至小數點第一位)
    int_input = round(val * 100000)
    if (int_input % 10000) == 0:
        return int_input / 100000.0
    else:
        return (math.floor(int_input / 10000) + 1) / 10.0

def calculate_cvss31(vector_str):
    metrics = {
        "AV": {"N": 0.85, "A": 0.62, "L": 0.55, "P": 0.20},
        "AC": {"L": 0.77, "H": 0.44},
        "PR_U": {"N": 0.85, "L": 0.62, "H": 0.27},
        "PR_C": {"N": 0.85, "L": 0.68, "H": 0.50},
        "UI": {"N": 0.85, "R": 0.62},
        "S": {"U": "U", "C": "C"},
        "C": {"H": 0.56, "L": 0.22, "N": 0.0},
        "I": {"H": 0.56, "L": 0.22, "N": 0.0},
        "A": {"H": 0.56, "L": 0.22, "N": 0.0}
    }

    # 解析向量字串: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
    parts = vector_str.strip().split('/')
    parsed = {}
    for part in parts:
        if ':' in part:
            k, v = part.split(':', 1)
            parsed[k] = v

    try:
        av = metrics["AV"][parsed["AV"]]
        ac = metrics["AC"][parsed["AC"]]
        scope = parsed["S"]
        pr = metrics["PR_C"][parsed["PR"]] if scope == "C" else metrics["PR_U"][parsed["PR"]]
        ui = metrics["UI"][parsed["UI"]]
        c = metrics["C"][parsed["C"]]
        i = metrics["I"][parsed["I"]]
        a = metrics["A"][parsed["A"]]
    except KeyError as e:
        print(f"[-] 錯誤：向量字串缺少欄位或存在未知值: {e}")
        return

    # 1. 計算可利用性 (Exploitability)
    exploitability = 8.22 * av * ac * pr * ui

    # 2. 計算衝擊值 (ISS & Impact)
    iss_base = 1.0 - ((1.0 - c) * (1.0 - i) * (1.0 - a))
    
    if scope == "U":
        impact = 6.42 * iss_base
    else:
        impact = 7.52 * (iss_base - 0.029) - 3.25 * ((iss_base - 0.02) ** 15)

    # 3. 計算 Base Score
    if impact <= 0:
        base_score = 0.0
    else:
        if scope == "U":
            base_score = roundup(min(impact + exploitability, 10.0))
        else:
            base_score = roundup(min(1.08 * (impact + exploitability), 10.0))

    # 判定嚴重性等級 (Severity Rating)
    if base_score == 0.0:
        severity = "None"
    elif 0.1 <= base_score <= 3.9:
        severity = "Low"
    elif 4.0 <= base_score <= 6.9:
        severity = "Medium"
    elif 7.0 <= base_score <= 8.9:
        severity = "High"
    else:
        severity = "Critical"

    print("=" * 70)
    print(f"CVSS v3.1 Vector: {vector_str}")
    print("=" * 70)
    print(f"可利用性子分數 (Exploitability): {exploitability:.2f}")
    print(f"基礎衝擊子分數 (ISS Base)      : {iss_base:.4f}")
    print(f"最終衝擊子分數 (Impact)        : {impact:.2f}")
    print(f"權限範疇變更 (Scope)          : {'Scope Changed (S:C)' if scope=='C' else 'Scope Unchanged (S:U)'}")
    print("-" * 70)
    print(f"👉 最終 CVSS 基礎評分 (Base Score) : {base_score:.1f} [{severity}]")
    print("=" * 70)

if __name__ == "__main__":
    if len(sys.argv) < 2:
        default_vector = "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H"
        print(f"[*] 未提供參數，計算預設 Log4Shell 滿分向量: {default_vector}\n")
        calculate_cvss31(default_vector)
    else:
        calculate_cvss31(sys.argv[1])
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### 4.1 SOC 研判對決 8 問 (SOC 8 Critical Questions)

| 編號 | 檢驗提問 (Verification Questions) | 是 (Yes) 判定導向 | 否 (No) 判定導向 |
| :---: | :--- | :--- | :--- |
| **Q1** | 攻擊者是否可在完全不需要任何憑證與帳號的情況下發起攻擊？ | 評定為 `PR:N` (None)，大幅拉高利用性 | 需驗證為普通用戶 (`PR:L`) 或管理員 (`PR:H`) |
| **Q2** | 攻擊封包是否能從公網穿越多個 L3 路由器直接抵達目標？ | 評定為 `AV:N` (Network) | 需同網段 (`AV:A`) 或本機登入 (`AV:L`) |
| **Q3** | 攻擊觸發是否需依賴特定受害者點擊郵件超連結或確認彈窗？ | 評定為 `UI:R` (Required) | 評定為 `UI:N` (完全無需使用者互動) |
| **Q4** | 漏洞成功利用後，是否能突破容器、虛擬機或宿主機核心邊界？ | 評定為 `S:C` (Scope Changed)，觸發加成倍率 | 評定為 `S:U` (Scope Unchanged，侷限本地) |
| **Q5** | 該漏洞是否會造成系統關鍵服務完全停擺、崩潰或無法響應？ | 評定為 `A:H` (Availability: High) | 僅短暫抖動 (`A:L`) 或完全無損 (`A:N`) |
| **Q6** | 攻擊是否能完全讀取系統所有敏感檔案、記憶體密鑰或資料庫全表？ | 評定為 `C:H` (Confidentiality: High) | 僅局部無害資訊洩漏 (`C:L`) 或無 (`C:N`) |
| **Q7** | 攻擊是否能在目標系統寫入任意檔案或直接獲取作業系統 Shell？ | 評定為 `I:H` (Integrity: High) | 僅局部無害欄位竄改 (`I:L`) 或無 (`I:N`) |
| **Q8** | 漏洞利用是否依賴難以預測的 Race Condition 或 ASLR 隨機基址？ | 評定為 `AC:H` (Attack Complexity: High) | 評定為 `AC:L` (低複雜度，高確定性) |

```

                                      ▼

                                      │
                                      ▼
                    [ Q4: 是否突破安全元件邊界 (如容器逃逸)? ]
                        ├── YES ──► [ S:C (Scope Changed) ➔ 啟用 1.08 加成與高權重 PR ]
                        └── NO  ──► [ S:U (Scope Unchanged) ]
                                      │
                                      ▼
                    [ Q6/Q7: 是否達成任意遠端代碼執行 (RCE)? ]
                        ├── YES ──► [ C:H / I:H / A:H ➔ 衝擊值最大化 ]
                        │               └── 若同時滿足 AV:N + PR:N + UI:N ➔ 🚨 滿分 10.0 Critical!
                        └── NO  ──► [ 依據具體資料洩漏或 DoS 狀況設定 C/I/A ]
```

### 5.1 基於 CVSS 分數的 SLA 修補時效處置 SOP
企業脆弱性管理規範中，必須將 CVSS 分數與工單處理時效 (SLA) 進行嚴格綁定：

| 嚴重性等級 | CVSS v3.1 評分區間 | 業務系統修補 SLA (緊急修訂標準) | 應急處置方案 |
| :--- | :--- | :--- | :--- |
| **🚨 Critical** | **9.0 ~ 10.0** | **24 ~ 48 小時內** (立即發布緊急熱修補) | 1. 立即下線受害服務或防火牆封鎖相應端口<br>2. 部署 WAF/IPS 虛擬補丁 (Virtual Patching)<br>3. 全網排查是否已遭入侵橫向 |
| **🔴 High** | **7.0 ~ 8.9** | **7 天以內** | 1. 排定維護窗口更新軟體版本或套用官方補丁<br>2. 限制來源存取網段 (ACL 白名單) |
| **🟡 Medium** | **4.0 ~ 6.9** | **30 天以內** | 納入例行系統版本升級週期修復 |
| **🟢 Low** | **0.1 ~ 3.9** | **90 天以內 / 最佳努力 (Best Effort)** | 評估業務相容性，可隨大版本升級時再行修正 |

### 5.2 系統架構加固 (Long-term Hardening)
1. **阻斷 Scope: Changed 的外溢路徑**：
   - 容器部署強制啟用 `--security-opt=no-new-privileges` 與唯讀根檔案系統 (`--read-only`)，阻斷容器逃逸。
   - 虛擬化平台嚴格隔離管理網段 (Management VLAN) 與虛擬機通訊網段。
2. **網路微隔離削弱 AV 指標**：
   - 將原本曝露於公網之管理後台收斂至內網 VPN 或零信任 (ZTNA) 閘道之後，強制將外部潛在漏洞的 `AV:N` 降級為 `AV:L` 或具備嚴密身分驗證的 `PR:H`。
3. **實施最小權限原則 (Least Privilege) 削弱 PR 衝擊**：
   - 執行服務進程一律禁止使用 `root` 或 `LocalSystem`，改以受限專屬服務帳戶 (如 NetworkService 或虛擬服務帳號) 運作，使攻擊者即使 RCE 也無法立即竄改核心系統。

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：為什麼在 CVSS v3.1 中，當 Scope 由 Unchanged (S:U) 變更為 Changed (S:C) 時，Required Privileges (PR) 的權重數值反而變大（如 PR:L 由 0.62 變為 0.68）？**  
  *考核核心*：在未跨越權限邊界 (S:U) 時，管理員帳號 (PR:H) 攻擊自身受管軟體通常被視為設計內行為；但當發生 Scope Changed (S:C) 時，攻擊者即使僅以低權限甚至高權限入侵當前應用程式，卻能一併摧毀底層作業系統、鄰近租戶或虛擬機宿主，其危害遠超預期。因此 CVSS v3.1 公式對 S:C 下的登入身分給予了更高的危害權重加成。

- [ ] **Q2：Reflected XSS 與 Stored XSS 在 CVSS v3.1 基本指標評估上，哪一項指標通常存在決定性的差異？**  
  *考核核心*：使用者互動 (User Interaction - UI)。Reflected XSS 嚴格要求受害者點擊惡意構造之特定 URL (`UI:R`)；而 Stored XSS 儲存於伺服器資料庫中，任何正常使用者只要造訪合法頁面即在無感知情況下被動執行，在許多評估情境下可評為 `UI:N`（或依觸發條件評為最低互動），從而顯著提高 Stored XSS 的可利用性分數。

- [ ] **Q3：若一個 SQL 注入漏洞可以執行 `xp_cmdshell` 直接獲取伺服器作業系統 Shell，它的 Scope 應該評定為 S:U 還是 S:C？為什麼？**  
  *考核核心*：評定為 `Scope: Changed (S:C)`。脆弱元件 (Vulnerable Component) 為資料庫軟體 (MSSQL)，其原本的安全授權範疇僅限於資料庫內部表與檢視表；透過 `xp_cmdshell` 突破了資料庫的沙箱邊界，使受影響元件 (Impacted Component) 轉移到了宿主作業系統 (Windows OS) 的權限範疇，權限授權實體發生了轉移，完全符合 S:C 的定義。

- [ ] **Q4：CVSS v4.0 為什麼要廢除單一 Scope 指標，改為劃分「Vulnerable System」與「Subsequent System」雙重衝擊？**  
  *考核核心*：在 v3.1 中，Scope 的二元劃分 (Changed vs Unchanged) 存在極大主觀模糊性，評估人員常常為了某個跨元件呼叫是否算 Scope Changed 爭論不休，且 S:C 會將整個分數非線性膨脹。v4.0 採用雙重衝擊矩陣（本體系統 VC/VI/VA vs 連帶系統 SC/SI/SA），精確區分「漏洞發生元件」與「連帶遭殃元件」各自的 CIA 損失，使評分客觀性與粒度大幅提升。

- [ ] **Q5：企業在安排修補優先級時，為什麼不能只依賴 CVSS Base Score，而必須結合 EPSS (Exploit Prediction Scoring System) 與 CISA KEV (Known Exploited Vulnerabilities)？**  
  *考核核心*：CVSS Base Score 衡量的是漏洞在「理論實驗室環境下」的內在技術嚴重性，無法反映現實威脅生態。許多 CVSS 9.8 的漏洞在真實世界中從未出現公開 Exploit 或黑客攻擊；反之，某些 CVSS 7.0 甚至 5.0 的漏洞卻已被勒索軟體與 APT 組織大規模自動化武器化。結合 EPSS（預測未來 30 天被利用機率）與 CISA KEV（確定已被在野利用清單），才能將寶貴的修補資源精準集中於真正存在在野威脅的漏洞上。
