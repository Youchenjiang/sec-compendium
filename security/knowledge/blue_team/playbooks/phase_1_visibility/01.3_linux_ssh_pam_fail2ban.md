# 01.3 帳號安全與 SSH 遠端登入硬化 (SSH Key-Only, Fail2ban, PAM Limits)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

邊界暴露的 Linux 主機（如跳板機 Bastion Host、Web 邊界反向代理或測試雲主機）常年承受來自公網的自動化殭屍網路暴力破解與字典攻擊。SOC 監控大盤突然告警：一台承載關鍵資料庫連線的 Bastion 主機，在 10 分鐘內觸發了數萬次來自境外未知 IP 的 Failed password for invalid user 紀錄，隨後日誌中突然出現一筆 Accepted publickey for deployer from <境外IP>，緊接著出現 PAM 提權日誌與未知背景連線。

面對公網暴力撞庫與潛在憑證洩漏突破，藍軍工程師的直覺處置切入點應為：
1. **驗證入侵真實性**：確認是否有連線成功登入（Accepted password 或 Accepted publickey）？登入的使用者身分為何？是否為非預期來源 IP？
2. **阻斷外網暴破源**：動態封鎖當前正在進行密集掃描與暴力破解的來源 IP 位址，阻斷密碼窮舉與資源耗盡（DoS）。
3. **消除弱口令攻擊面**：徹底廢除密碼認證機制（PasswordAuthentication no），推行強金鑰認證（Ed25519）與金鑰密碼短語（Passphrase）強制規範。
4. **收縮 Root 與特權入口**：全面禁止 root 透過 SSH 直接遠端登入（PermitRootLogin no），強制透過跳板帳號 + sudo 審計。
5. **部署防禦深度**：透過 Fail2ban 動態監控 uth.log / secure 並驅動 iptables/nftables 動態阻斷；藉由 PAM pam_tally2 / pam_faillock 實施本機登入鎖定，杜絕密碼撞庫風險。

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. SSH 金鑰身分驗證協定握手流程 (RFC 4252)

OpenSSH 的公鑰認證（Public Key Authentication）基於非對稱加密與數位簽章技術，客戶端無需在網路中傳送私鑰：

1. **版本與演算法協商 (Key Exchange)**：
   - 用戶端與伺服端透過 Diffie-Hellman (如 curve25519-sha256) 協商出對稱連線加密金鑰（Session Key）與會話雜湊值（Session ID），後續通訊全程加密。
2. **身分驗證請求 (Auth Request)**：
   - 用戶端傳送欲登入的帳號名稱及公鑰演算法、公鑰資料（ssh-userauth，包含 public key blob），伺服端查詢該帳號家目錄下的 ~/.ssh/authorized_keys。
   - 若找不到匹配的公鑰，伺服器直接回傳 SSH_MSG_USERAUTH_FAILURE。
3. **挑戰與簽章驗證 (Challenge & Signature Verification)**：
   - 伺服端產生一段包含 Session ID、使用者帳號名稱、認證協定名稱及隨機亂數的挑戰資料（Challenge Data）。
   - 用戶端接收後，調用本地端的 SSH 私鑰（Private Key）對挑戰資料進行數位簽章（Digital Signature），並將簽章回傳給伺服端。
   - 伺服端使用預先儲存的對應公鑰（Public Key）驗證該簽章。若簽章有效，伺服端回傳 SSH_MSG_USERAUTH_SUCCESS 並建立 PTY 終端會話。

### 2. PAM (Pluggable Authentication Modules) 架構與認證鏈

PAM 是 Linux 系統身分驗證的中心骨幹。當任何程式（如 sshd、sudo、login）需要對使用者進行身分認證、權限判定、憑證管理或建立會話時，會調用 /etc/pam.d/ 內對應的設定檔。

#### PAM 模組類型 (Module Interface)
- auth：身分認證（如密碼輸入、生物識別、雙因子 OTP）。
- account：帳號有效性檢查（如帳號是否過期、密碼是否需強制變更、登入時間限制、特定登入點限制）。
- password：密碼維護更新（如強制密碼複雜度、密碼歷史長度限制）。
- session：會話環境準備與銷毀（如掛載家目錄、寫入登入審計日誌、資源 limits 限制生效）。

#### 控制旗標 (Control Flags) 執行語意
- required：必須通過。若失敗，該模組會記錄失敗，但認證鏈會繼續執行下去，直到所有模組完成後才回傳失敗。
- requisite：必須通過。若失敗，立即終止認證鏈並直接回傳失敗，不再執行後續模組。
- sufficient：充分條件。若該模組通過，且先前沒有其他 required 模組失敗，則立即終止認證鏈並回傳成功；若失敗，則忽略並繼續向下執行。
- optional：可選條件。其回傳值通常不影響最終成功或失敗，除非整條鏈只有此模組存在。

### 3. Fail2ban 的運作原理與日誌驅動機制

Fail2ban 是一個守護程式（Daemon），其核心工作流程為：日誌監聽（Filter） ➔ 閾值判定（Failure Detection） ➔ 處置聯防（Action / Jail）。

1. **Filter (正則表達式解析)**：
   Fail2ban 透過 inotify 或 polling 即時追蹤 /var/log/auth.log (Debian/Ubuntu) 或 /var/log/secure (RHEL/CentOS)。它內建了多組針對 SSH 錯誤特徵的正則表達式。
2. **Jail (監獄規則配置)**：
   定義了特定的監控範圍：findtime（時間窗口，如 600 秒）、maxretry（最大容忍失敗次數，如 5 次）、bantime（封鎖時長，如 3600 秒或 -1 永久封鎖）。
3. **Action (防火牆處置)**：
   當某來源 IP 在 findtime 內累積失敗次數達到 maxretry 時，Fail2ban 調用 Linux 防火牆介面（iptables / nftables），在專屬的 f2b-sshd 鏈中動態插入一條拒絕規則：
```bash
iptables -I f2b-sshd 1 -s <Attacker_IP> -j REJECT --reject-with icmp-port-unreachable
```

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 1. SSH 入侵特徵快速篩選與統計

```bash
# 1. 快速統計攻擊次數最多的來源 IP TOP 10
LOG_FILE="/var/log/auth.log"
[ ! -f "$LOG_FILE" ] && LOG_FILE="/var/log/secure"

grep -E "Failed password|Invalid user" "$LOG_FILE" | grep -oE "from [0-9]+\.[0-9]+\.[0-9]+\.[0-9]+" | awk '{print $2}' | sort | uniq -c | sort -nr | head -n 10

# 2. 檢索歷史日誌中所有「成功登入」的紀錄
grep "Accepted " "$LOG_FILE" | awk '{print $1,$2,$3, $9, "from", $11, "port", $13, "method", $7}'

# 3. 檢查當前線上的 SSH 會話與登入終端
who -a
w -i
last -n 20 -F -a

# 4. 檢查失敗登入歷史與來源（使用 lastb，讀取 /var/log/btmp）
lastb -n 20 -F -a
```

### 2. OpenSSH 生產環境安全硬化配置範本

修改 `/etc/ssh/sshd_config` 或於 `/etc/ssh/sshd_config.d/99-hardened.conf` 加入以下加固參數：

```bash
# 備份原始配置
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# 寫入生產硬化標準配置
cat << 'EOF' > /etc/ssh/sshd_config.d/99-hardened.conf
Port 22222
Protocol 2
AddressFamily inet
ListenAddress 0.0.0.0

PermitRootLogin no
MaxAuthTries 3
MaxSessions 5
LoginGraceTime 30
PermitEmptyPasswords no
PasswordAuthentication no
AuthenticationMethods publickey
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys

AllowGroups ssh-users ops-admin

X11Forwarding no
AllowTcpForwarding no
AllowAgentForwarding no
GatewayPorts no

ClientAliveInterval 300
ClientAliveCountMax 2

KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group16-sha512,diffie-hellman-group18-sha512
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
EOF

# 測試設定檔語法是否正確
sshd -t
# 語法驗證通過後平滑載入配置
systemctl reload sshd || systemctl reload ssh
```

### 3. Fail2ban 動態聯防安裝與配置

```bash
# 安裝 Fail2ban
apt-get update && apt-get install -y fail2ban

cat << 'EOF' > /etc/fail2ban/jail.d/sshd-protection.local
[sshd]
enabled = true
port = 22,22222
filter = sshd
logpath = %(sshd_log)s
backend = systemd
maxretry = 3
findtime = 600
bantime = 86400
ignoreip = 127.0.0.1/8 ::1 192.168.1.0/24 10.10.0.0/16
banaction = iptables-multiport
EOF

systemctl restart fail2ban
systemctl enable fail2ban

# 查看目前 sshd 監獄狀態與已封鎖的 IP
fail2ban-client status sshd

# 緊急處置：手動解封誤鎖的合法 IP
fail2ban-client set sshd unbanip 192.168.1.150

# 手動將可疑惡意 IP 加入封鎖清單
fail2ban-client set sshd banip 203.0.113.88
```

### 4. PAM 安全防護：帳號登入失敗鎖定 (pam_faillock)

```bash
# 查看帳號鎖定狀態與失敗紀錄
faillock --user deployer

# 重設並解鎖特定帳號
faillock --user deployer --reset

cat << 'EOF' >> /etc/security/faillock.conf
deny = 3
fail_interval = 900
unlock_time = 1800
even_deny_root = no
EOF
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：登入日誌是否出現 `Accepted` 成功關鍵字？** | 這是判定是否從「探測攻擊」升級為「資安事故」的核心分水嶺。若全為 `Failed password`，屬於未遂阻斷；若出現 `Accepted publickey` 或 `Accepted password`，代表防線失守，應立即啟動 IR。 |
| **Q2：成功登入的帳號是否具備特權（root 或 wheel/sudo）？** | 檢查該帳號的 UID/GID 與 `/etc/sudoers` 權限。若為具備無密碼 sudo 特權的帳號（如 `ansible`、`deploy`），威脅等級等同於 root 被直接攻破。 |
| **Q3：登入成功來源 IP 是否落在授權白名單或企業 VPN 網段？** | 比對企業 CMDB、外網出口 IP 清單、辦公室靜態 IP 或員工 VPN 池。若是來自非授權之公網 IP（尤其為 IDC 機房、境外高危地區、Tor 節點），必為真實憑證洩漏威脅。 |
| **Q4：登入成功後執行的首批指令行為為何？** | 檢視 `/var/log/audit/audit.log` (EXECVE)、`~/.bash_history` 或 EDR 行程樹。若一登入立即執行 `curl ... | sh`、`whoami`、`id`、`uname -a`、搜尋敏感設定檔（`grep -rn password`），為標準攻擊者枚舉行為；若為自動化維運腳本固定指令，則為業務行為。 |
| **Q5：Fail2ban 告警 IP 是否為內部監控或弱點掃描工具？** | 檢查被封鎖之 IP 是否為企業內部的 Nessus、Qualys、Zabbix、Prometheus 或資安維運跳板機。若是，屬於內部業務漏報白名單造成的誤觸發，需加入 `ignoreip`。 |
| **Q6：公鑰登入所使用的 Key Fingerprint 是否登錄在企業資產庫中？** | 檢查 `auth.log` 中記錄的 publickey fingerprint（如 `SHA256:abc...`），比對是否屬於離職員工、外部協力廠商，或是未向 IT 資安部報備登記的私人私鑰。 |
| **Q7：是否出現短時間內針對大量不同使用者帳號的遍歷（Password Spraying）？** | 統計失敗日誌中，同一 IP 是否在極短時間內依序嘗試 `guest`, `oracle`, `mysql`, `ftp`, `ubuntu`, `test` 等數十個預設帳號。若有，為標準外部掃描器自動化字典攻擊。 |
| **Q8：登入驗證失敗原因是否為金鑰權限過於開放（Permissions are too open）？** | 檢視 `/var/log/secure` 是否出現 `bad ownership or modes for file /home/user/.ssh/authorized_keys`。若是，通常為維運人員手動搬移檔案時權限設為 `777` 導致 OpenSSH 安全機制拒絕讀取，屬設定問題引發之業務誤報。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 檢測到異常活躍 SSH 會話之緊急阻斷流程

若發現有未授權的 SSH 連線正在主機中活動，依序執行以下處置：

```bash
# 步驟 1：確認可疑連線的 PTS 終端與行程 PID
w -i
ss -tupn '( dport = :22 or sport = :22 or dport = :22222 or sport = :22222 )'

# 步驟 2：強制殺死惡意 SSH 會話 (假設其 sshd 子行程 PID 為 18923)
kill -9 18923
pkill -kill -t pts/2

# 步驟 3：即時防火牆阻斷該來源 IP
iptables -I INPUT 1 -s 203.0.113.50 -j DROP

# 步驟 4：檢查並清理被植入的公鑰
stat /root/.ssh/authorized_keys
ls -la /home/*/.ssh/authorized_keys
```

### 2. SSH 權限與重要檔案安全基準

OpenSSH 守護行程具備嚴格的目錄權限檢查（`StrictModes yes`），若檔案權限過寬，OpenSSH 會拒絕使用公鑰登入：

```bash
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
chmod 600 /etc/ssh/ssh_host_*_key
chmod 644 /etc/ssh/ssh_host_*_key.pub
chmod 644 /etc/ssh/sshd_config

chmod 700 /home/deployer/.ssh
chmod 600 /home/deployer/.ssh/authorized_keys
chown -R deployer:deployer /home/deployer/.ssh
```

### 3. 金鑰生命週期管理規範
- **演算法淘汰**：全面淘汰 `ssh-rsa`（RSA 2048 以前及 SHA-1 雜湊），強制改用 `Ed25519` 或 `ECDSA (nistp384/521)`。
- **產生強金鑰指令**：
  ```bash
  ssh-keygen -t ed25519 -a 100 -C "ops-admin-2026@company.com"
  ```
- **禁止共用金鑰**：每一位管理員必須擁有各自獨立的 Key Pair，禁止在生產環境共用同一把 Private Key。

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在 `/etc/ssh/sshd_config` 中將 `PasswordAuthentication` 設為 `no`，但使用者依然可以使用密碼登入，最常見的原因是什麼？**
  - *驗收標準*：答出可能原因包含：未重新載入/重啟 sshd 服務、`sshd_config.d/*.conf` 載入順序覆蓋、或 PAM 相關設定 `UsePAM yes` 搭配 `KbdInteractiveAuthentication yes`（鍵盤互動式認證仍調用了密碼模組）。
- [ ] **Q2：Fail2ban 封鎖攻擊者 IP 後，為什麼原本已經建立連線的 SSH 會話沒有被中斷？**
  - *驗收標準*：答出 Linux `iptables` 預設的狀態追蹤機制通常在最前端配置了 `-m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT`。Fail2ban 新增的阻斷規則僅能攔截**新發起**的 SYN 封包，無法主動關閉既有的 TCP 連線，需要管理者手動透過 `kill` 或 `ss -K` 殺死會話。
- [ ] **Q3：若攻擊者成功入侵系統並取得 root 權限，他最常透過修改哪一個 PAM 設定檔，實現「無密碼後門（PAM Backdoor）」？**
  - *驗收標準*：指出 `/etc/pam.d/common-auth` (Debian) 或 `/etc/pam.d/system-auth` (RHEL) / `/etc/pam.d/sshd`。攻擊者通常在最前方針對特定密碼（Magic Password）注入 `auth sufficient pam_permit.so` 或惡意自編譯的 `pam_unix.so`。
- [ ] **Q4：OpenSSH 公鑰驗證機制中，伺服端儲存的 `authorized_keys` 是否包含使用者的私鑰？若伺服器被整台拖庫，使用者的本機私鑰是否會洩漏？**
  - *驗收標準*：答出 `authorized_keys` 僅儲存使用者的公鑰（Public Key），絕不包含私鑰。非對稱密碼學保證伺服器被拖庫後，攻擊者僅能取得公開金鑰，無法逆向推導出使用者的私鑰（私鑰自始至終僅留存在用戶端設備上）。
- [ ] **Q5：當配置 `PermitRootLogin prohibit-password`（或 `without-password`）時，與 `PermitRootLogin no` 有何具體差異？**
  - *驗收標準*：答出 `prohibit-password` 僅禁止 root 使用「密碼」遠端登入，但**仍允許** root 使用「公鑰（SSH Key）」直接連線；而 `PermitRootLogin no` 則是徹底封鎖 root 透過 SSH 進行任何形式的直接登入，必須先以普通使用者登入再提權。
