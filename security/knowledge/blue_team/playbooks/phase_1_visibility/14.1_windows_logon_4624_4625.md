# 📘 實戰手冊 14.1：Windows 身分驗證與暴力破解日誌 (Event ID 4624 / 4625)

---

## 🚨 案發現場破題 (The Incident Scenario)

> **情境帶入**：  
> 週二凌晨 03:14，你值勤的 SOC 儀表板突然亮起一條紅字高危告警：  
> `[Rule Alert] Potential Brute Force Attack Followed by Successful Logon on Host: SRV-FINANCE-01`  
>
> 你的心跳開始加速。這是一台存放公司財務敏感資料的核心伺服器。現在夜深人靜，所有人都在睡覺，為什麼這台伺服器突然在短時間內出現密集的驗證失敗，緊接著出現了「登入成功」？  
> 攻擊者得逞了嗎？這是一次外部黑客的 RDP 暴力破門？還是內網受感染主機正在用 SMB 橫向移動？抑或只是備份排程搞錯了密碼的虛驚一場？
>
> **本手冊的使命**：帶著你從打開終端機的第一秒開始，順著專業調查員的思考脈絡，一步步拆解日誌、查對權威代碼表、找出攻擊路徑、判定災情並給出阻斷決策。

```
[調查心智脈絡流]
🚨 接到警報 
  ↳ 🔍 第一動：日誌解剖（實戰真實 XML 範例 ➔ 鎖定 4 大核心維度）
      ↳ 🧭 第二動：解碼意圖（Logon Type 實戰速查表 ➔ SubStatus 錯誤代碼全集）
          ↳ 💻 第三動：現場追兇（PowerShell 現場快篩 ➔ Splunk SPL 關聯分析）
              ↳ ⚖️ 第四動：研判分水嶺（SOC 8 大黃金提問檢核 ➔ 誤報決策樹）
                  ↳ 🛡️ 第五動：處置阻斷（未遂處置 vs 失陷應變 SOP）
```

## 🧩 第一動：日誌解剖——第一眼該看什麼？

面對混亂的 Windows Event Log，新手往往迷失在幾十行 XML 裡。實際上，調查身分驗證事件，你的眼睛只需要依序盯住 **4 個關鍵維度**：

### 1.1 一筆真實的 4625（登入失敗）日誌剖析
下面是一筆典型的黑客攻擊日誌，請看標記的 4 個致命細節：

```yaml
Event ID: 4625 (An account failed to log on)
Keywords: Audit Failure
Computer: SRV-FINANCE-01.corp.local

Subject:                           <-- [維度 1: 誰幫忙發起驗證的？]
  Security ID:  SYSTEM             <-- 通常是系統自身或服務進程代理驗證
  Account Name: SRV-FINANCE-01$

Account That Failed to Log On:     <-- [維度 2: 攻擊者想登入誰？]
  Target User Name: Administrator  <-- 目標帳號！是高權限帳號、一般員工還是服務帳戶？
  Target Domain:    CORP

Failure Information:               <-- [維度 3: 為什麼會失敗？]
  Status:           0xC000006D     <-- 普遍狀態：帳號或密碼錯誤
  SubStatus:        0xC000006A     <-- 關鍵真兇：密碼輸錯了！(若是 0x64 代表連帳號都不存在)

Network Information:               <-- [維度 4: 兇手從哪裡打過來的？]
  Logon Type:       10             <-- 致命線索：10 代表 RemoteDesktop 遠端桌面！
  Workstation Name: KALI-ATTACKER  <-- 來源主機名稱（攻擊者可能偽造或空白）
  Source Network Address: 203.0.113.55 <-- 來源 IP！這是一顆外網公網 IP！
  Source Port:      54321
```

看到這裡，脈絡瞬間清晰了：  
**「有一台外網 IP `203.0.113.55`，正在透過遠端桌面 (Logon Type 10) 嘗試用錯誤的密碼登入本機的 `Administrator` 帳號！」**

## 🧭 第二動：解碼意圖——查對權威對照表

在日誌中看到了數字與 16 進位代碼，身為鑑識人員，你需要這兩張如同字典般精確的權威對照表來判定攻擊本質：

### 2.1 Logon Type（登入類型）核心對照表

攻擊者使用不同的滲透工具與通訊協定，會在系統底層留下截然不同的 Logon Type：

| Logon Type | 名稱 | 常見觸發場景 | 攻防鑑識關鍵意義與研判直覺 |
| :--- | :--- | :--- | :--- |
| **Type 2** | Interactive (互動式登入) | 使用者在實體鍵盤/主機螢幕前輸入密碼登入。 | 凌晨出現？是否有外包廠商或清潔人員在機房動了實體主機螢幕？需警惕 KVM 異常。 |
| **Type 3** | Network (網路登入) | 透過 SMB 存取共享資料夾、IPC$ 連線、PsExec、WMI 遠端執行。 | **內網橫向移動主戰場**！Pass-the-Hash (PtH) 攻擊最常產生此類型事件（伴隨 NTLMv2 協定與空 WorkstationName）。 |
| **Type 4** | Batch (批次登入) | Windows Task Scheduler（工作排程器）執行排程任務。 | 常用於持久化（Persistence）。分析目標帳戶是否為專用服務帳號。 |
| **Type 5** | Service (服務登入) | Service Control Manager (`services.exe`) 啟動 Windows 服務。 | 攻擊者建立惡意服務（SCM / PsExec 服務建立）時，會伴隨 Type 5 登入。 |
| **Type 7** | Unlock (解除鎖定) | 使用者在鎖定螢幕上輸入密碼解除鎖定。 | 用於鑑識終端使用者實體離開與返回座位的時間線基準。 |
| **Type 8** | NetworkCleartext | 密碼以明文方式在網路中傳輸並驗證（如 IIS 基本身分驗證、未加密之 ASP.NET 登入）。 | **高風險！** 若非特定 Legacy 應用，通常代表不安全的明文身分驗證配置。 |
| **Type 9** | NewCredentials | 使用 `runas /netonly` 指令，或 Mimikatz `sekurlsa::pth`。 | **高度可疑！** 本機進程複製現有權杖，但對遠端網路資源使用全新憑證，為典型 PtH 滲透特徵。 |
| **Type 10**| RemoteInteractive | 透過 Remote Desktop (RDP)、Terminal Services 遠端桌面登入。 | **邊界突破或跳板操作**。勒索軟體運營者人工操作時的核心特徵。若來源為公網 IP，代表 RDP 裸奔被直接爆破。 |
| **Type 11**| CachedInteractive | 筆電脫離公司網域離線登入（使用本機快取憑證）。 | 若非行動辦公同仁，伺服器出現 Type 11 需檢查網域控制站連線是否中斷。 |

### 2.2 4625 錯誤代碼全集（Status 與 SubStatus）速查表

單純看 `Status: 0xC000006D` 毫無意義，**只有 `SubStatus` 才是真正揭示攻擊手法的靈魂所在**：

| 代碼與錯誤原因（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **`0xC000006A`**<br>`STATUS_WRONG_PASSWORD` | **密碼錯誤**：<br>使用者輸入的密碼與目標帳號的 NTLM Hash 不相符。 | • **單一帳號狂噴**：傳統暴力破解 (Brute Force)。<br>• **多帳號各試 1 次**：橫向密碼噴灑 (Password Spraying)。<br>• **優先級**：中至高（需嚴密比對後續是否有 4624 成功）。 |
| **`0xC0000064`**<br>`STATUS_NO_SUCH_USER` | **使用者不存在**：<br>本機 SAM 資料庫或 Active Directory 中找不到該使用者名稱。 | • **攻擊手法**：攻擊者正在進行使用者帳號字典枚舉探測（Username Enumeration）。<br>• **優先級**：中（攻擊者尚在摸索內網帳號結構）。 |
| **`0xC0000234`**<br>`STATUS_ACCOUNT_LOCKED_OUT` | **帳戶已遭鎖定**：<br>密碼錯誤次數已觸發群組原則（GPO）中的「帳戶鎖定閾值」。 | • **攻擊手法**：暴力破解已達上限，已導致業務 DoS 中斷。<br>• **優先級**：高（業務受阻，需核實受害者身分並解鎖，同時封鎖來源）。 |
| **`0xC0000072`**<br>`STATUS_ACCOUNT_DISABLED` | **帳戶已停用**：<br>該帳號已被管理員標記為停用（Disabled）。 | • **攻擊手法**：攻擊者取得離職員工清單或舊帳號字典，正在探測休眠帳號。<br>• **優先級**：中（帳號無法登入，但代表內部清單已外洩）。 |
| **`0xC0000193`**<br>`STATUS_ACCOUNT_EXPIRED` | **帳戶已過期**：<br>帳號設定的有效期限已屆滿。 | • **攻擊手法**：臨時廠商、外包專案或實習生帳號過期但仍被嘗試使用。<br>• **優先級**：低至中（核查是否為合規逾期存取）。 |
| **`0xC0000070`**<br>`STATUS_INVALID_WORKSTATION` | **登入工作站受限**：<br>帳號被限制只能在特定主機（Logon Workstations）登入，但來源主機不符。 | • **攻擊手法**：攻擊者試圖從未經授權的跳板機或外部主機存取特定帳號。<br>• **優先級**：高（典型內網越權存取特徵）。 |
| **`0xC0000071`**<br>`STATUS_PASSWORD_EXPIRED` | **密碼已過期**：<br>帳號密碼超出最長使用期限必須變更。 | • **攻擊手法**：舊密碼撞庫或排程服務使用過期憑證。<br>• **優先級**：低（通常為內部維運過期）。 |

## 💻 第三動：現場追兇——調查指令實戰操作

現在你已經看懂代碼了。身為現場分析師，你必須馬上獲取精確情報。

### 3.1 終端現場快速排查（PowerShell）
你透過 Jumpbox 連上了 `SRV-FINANCE-01`，千萬不要打開事件檢視器（幾十萬筆日誌會直接讓伺服器卡死）。直接下 PowerShell：

#### 步驟 1：揪出嘗試最頻繁的惡意來源 IP 與目標帳號
```powershell
# 用底層 API 快速提取最近 6 小時內失敗的來源 IP 與帳號
$StartTime = (Get-Date).AddHours(-6)
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4625
    StartTime = $StartTime
} | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        User        = ($data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
        LogonType   = ($data | Where-Object { $_.Name -eq 'LogonType' }).'#text'
        IpAddress   = ($data | Where-Object { $_.Name -eq 'IpAddress' }).'#text'
        SubStatus   = ($data | Where-Object { $_.Name -eq 'SubStatus' }).'#text'
    }
} | Group-Object IpAddress, User | 
    Select-Object Count, @{N='Ip_and_User'; E={$_.Name}} | 
    Sort-Object Count -Descending | Select-Object -First 10
```

#### 步驟 2：致命確認——攻擊者最後到底有沒有「登入成功」？
**這是整起調查最關鍵的轉折點**！如果只有 4625，那只是「有人在敲門」；但如果 4625 結束後出現了 **4624**，那就是「門被打開了」！

```powershell
# 檢查惡意來源 IP (例如 203.0.113.55) 是否在同一時期產生過 4624 (登入成功)
$SuspectIP = "203.0.113.55"
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4624
    StartTime = (Get-Date).AddHours(-6)
} | Where-Object {
    $xml = [xml]$_.ToXml()
    ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'IpAddress' }).'#text' -eq $SuspectIP
} | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    [PSCustomObject]@{
        TimeSuccess = $_.TimeCreated
        LogonUser   = ($data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
        LogonType   = ($data | Where-Object { $_.Name -eq 'LogonType' }).'#text'
        LogonID     = ($data | Where-Object { $_.Name -eq 'TargetLogonId' }).'#text'
    }
}
```
> 💡 **鑑識暗號**：注意那個 `TargetLogonId`（例如 `0x3E7`、`0x12FA34`）。這個 ID 是後續調查的鑰匙！在它登入後，主機上所有建立進程（Event ID 4688）都會帶著這個 LogonID。你可以用它查出攻擊者登入後下了什麼指令！

#### 步驟 3：現場自動化爆破檢測腳本 (`logon_hunter.ps1`)
```powershell
<#
.SYNOPSIS
    自動分析安全日誌中的暴力破解並關聯登入成功事件
#>
param (
    [int]$Hours = 12,
    [int]$Threshold = 10
)

$Since = (Get-Date).AddHours(-$Hours)
Write-Host "[*] 正在分析過去 $Hours 小時內的登入事件 (門檻: $Threshold 次失敗)..." -ForegroundColor Cyan

$Filter = @{
    LogName   = 'Security'
    Id        = @(4624, 4625)
    StartTime = $Since
}

$Events = Get-WinEvent -FilterHashtable $Filter
$Failures = @{}
$Successes = @()

foreach ($evt in $Events) {
    $xml = [xml]$evt.ToXml()
    $data = $xml.Event.EventData.Data
    $ip = ($data | Where-Object { $_.Name -eq 'IpAddress' }).'#text'
    $user = ($data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
    $logonId = ($data | Where-Object { $_.Name -eq 'TargetLogonId' }).'#text'
    $logonType = ($data | Where-Object { $_.Name -eq 'LogonType' }).'#text'
    
    if (-not $ip -or $ip -eq '-' -or $ip -eq '127.0.0.1') { continue }

    if ($evt.Id -eq 4625) {
        $sub = ($data | Where-Object { $_.Name -eq 'SubStatus' }).'#text'
        if (-not $Failures.ContainsKey($ip)) {
            $Failures[$ip] = @{ Count = 0; Users = @{}; SubStatus = @{} }
        }
        $Failures[$ip].Count++
        $Failures[$ip].Users[$user] = $true
        $Failures[$ip].SubStatus[$sub] = $true
    } elseif ($evt.Id -eq 4624) {
        $Successes += [PSCustomObject]@{
            TimeCreated = $evt.TimeCreated
            IpAddress   = $ip
            User        = $user
            LogonType   = $logonType
            LogonId     = $logonId
        }
    }
}

foreach ($ip in $Failures.Keys) {
    $count = $Failures[$ip].Count
    if ($count -ge $Threshold) {
        $users = ($Failures[$ip].Users.Keys) -join ', '
        $succ = $Successes | Where-Object { $_.IpAddress -eq $ip }
        if ($succ) {
            Write-Host "[!] 🚨 警告: 發現 IP $ip 暴力破解成功!" -ForegroundColor Red
            Write-Host "    失敗次數: $count | 嘗試帳號: $users"
            $succ | ForEach-Object {
                Write-Host "    --> 登入成功: $($_.TimeCreated) | 帳號: $($_.User) | Type: $($_.LogonType) | LogonID: $($_.LogonId)" -ForegroundColor Yellow
            }
        } else {
            Write-Host "[+] 發現 IP $ip 暴力破解未遂: $count 次失敗 ($users)" -ForegroundColor DarkYellow
        }
    }
}
```

### 3.2 SIEM 全局大局觀（Splunk SPL）
如果你是在 SOC 透過 Splunk 全網監控，你的目標是抓出「跨主機的全面性攻擊」：

#### 偵測情境 A：爆破成功致命鏈（Failures followed by Success）
> **邏輯**：10 分鐘內同一來源 IP 對單一帳號發生超過 20 次 4625 失敗，且隨後緊跟著一次 4624 成功（代表爆破成功！高危！）。

```splunk
index=wineventlog EventCode=4625 SubStatus="0xC000006A"
| bin _time span=10m
| stats count as fail_count, values(TargetUserName) as users, values(WorkstationName) as src_workstations by src_ip, _time
| where fail_count >= 20
| join type=left src_ip [
    search index=wineventlog EventCode=4624 Logon_Type IN (2, 3, 10)
    | bin _time span=10m
    | stats count as success_count, values(TargetUserName) as success_user by src_ip, _time
]
| eval Alert_Severity=if(success_count > 0, "CRITICAL: Brute Force Succeeded!", "HIGH: Brute Force Ongoing")
| table _time, src_ip, fail_count, users, success_count, success_user, Alert_Severity
```

#### 偵測情境 B：橫向密碼噴灑（Password Spraying）
> **邏輯**：10 分鐘內同一來源 IP 嘗試存取超過 15 個「不同帳號」，但每個帳號失敗次數極低（通常 1~2 次），旨在繞過帳號鎖定閾值。

```splunk
index=wineventlog EventCode=4625
| bin _time span=10m
| stats dc(TargetUserName) as distinct_targets, count as total_attempts, values(TargetUserName) as target_list by src_ip, _time
| where distinct_targets >= 15 AND (total_attempts / distinct_targets) < 3
| table _time, src_ip, distinct_targets, total_attempts, target_list
```

## ⚖️ 第四動：研判思維分水嶺——真實入侵 vs 烏龍誤報？

在 SOC 日常中，90% 的 4625 是正常人或機器搞出來的。你需要透過一套標準的問答矩陣與決策樹來排除誤報：

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 統計在特定時間窗口內的 4625 總次數、失敗頻率（規律間隔 vs 瞬間突發）。 |
| **Q2. 來源實體**（誰/哪個 IP 觸發的？） | `IpAddress` 為內部 IP、外部公網 IP、還是 `127.0.0.1`？來源主機是否有合法資產歸屬？ |
| **Q3. 目標帳號**（攻擊目標是誰？） | `TargetUserName` 為高權限帳號（Administrator, Domain Admins）、一般員工帳號、還是服務帳戶？ |
| **Q4. 失敗本質**（失敗原因是什麼？） | 比對 SubStatus：是單純輸錯密碼（`0x6A`）、嘗試不存在的帳號探測（`0x64`）、還是帳號早已被封鎖（`0x72`）？ |
| **Q5. 登入途徑**（透過何種管道連入？） | 檢視 `LogonType`：Type 10（RDP 開放在外網被爆破）、Type 3（內網 SMB/RPC 橫向移動）、Type 2（本機主控台）。 |
| **Q6. 攻擊成果**（攻擊是否成功？） | 檢視失敗事件後 15 分鐘內，同來源 IP/同帳號是否緊接出現 **4624 (LogonType 2/3/10)**。若有，視為 **P1 級帳號失陷**！ |
| **Q7. 橫向波及**（是否有其他主機受害？） | 搜尋全網 SIEM，該來源 IP 是否同時對其他主機進行相同的 4625 嘗試？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 成功者：立即於 AD 停用帳戶、踢除 Session、啟動主機端取證；2. 失敗者：於防火牆封鎖惡意來源 IP。 |

### 4.2 誤報排除決策樹

```
[研判決策樹]
收到 4625 爆破警報？
 │
 ├── Q: 來源 IP 是哪裡？
 │    ├── 外部陌生公網 IP ➔ 🔴 外部掃描/爆破（立即通報防火牆封鎖）
 │    ├── 內部員工網段 (VPN / Wi-Fi) ➔ 進入使用者行為研判
 │    └── 內部伺服器 IP (如檔案伺服器、Exchange) ➔ 進入 NTLM 轉發排查
 │
 ├── Q: 失敗特徵是什麼？
 │    ├── 該員工剛改過網域密碼？ ➔ 🟡 殘留憑證誤報（檢查 Outlook/手機 Wi-Fi/網路磁碟機掛載）
 │    ├── 固定每 5 分鐘失敗 1 次？ ➔ 🟡 排程任務 (Task Scheduler) 或服務帳號忘記更新密碼
 │    └── 短時間嘗試數十個不同人名？ ➔ 🔴 內網橫向密碼噴灑（該來源主機已淪陷！）

 └── Q: 最終是否有 4624 成功事件？
      ├── 無 ➔ 威脅已受阻，持續監控該來源
      └── 有 ➔ 🚨 帳號失陷！升級為 P1 重大資安事件，進入應變處置
```

## 🛡️ 第五動：決策處置與阻斷 SOP (Incident Response)

一旦確認為惡意攻擊，依據 PICERL 框架採取以下標準動作：

1. **若「尚未登入成功」（僅有大量 4625）**：
   - **邊界防禦**：在邊界防火牆將該攻擊來源 IP 加入封鎖黑名單。
   - **帳戶保護**：檢查受攻擊帳號是否已被鎖定，若該帳號為弱密碼帳號，主動通知管理員重設密碼。
2. **若「已登入成功」（4625 緊接 4624）——【重大事件處置】**：
   - **立即隔離**：透過 EDR 將受害主機從網路中隔離（或拔除網路線），阻斷內網橫向擴散。
   - **斬斷權杖**：在 Active Directory 中立即停用或重置該受害帳號密碼，並終止該帳號所有的 Active Sessions。
   - **痕跡追蹤**：拿著剛才查到的 `TargetLogonId`，到 Event ID 4688（Process Creation）去追蹤攻擊者登入後執行的所有 PowerShell、CMD 或惡意檔案。

## 📋 過關驗收檢查點 (Mastery Checklist)

以下為本專案的 5 大實戰驗收問題與標準專家解析：

- [x] **Q1：你在伺服器上看到大量 4625，`SubStatus` 全部都是 `0xC000006A`，而且受測帳號包含 `alex`、`bob`、`cathy`、`david`，每人只失敗 1~2 次。請問這是什麼手法？為什麼攻擊者不對 `alex` 狂試 100 次？**
  > **標準答案**：
  > 1. **攻擊手法**：這是典型的**「密碼噴灑攻擊 (Password Spraying)」**。
  > 2. **背後動機**：企業網域通常配置有「帳戶鎖定原則（Account Lockout Policy）」（例如連續失敗 5 次即鎖定帳號 30 分鐘）。如果攻擊者對單一帳號 `alex` 狂試 100 次，第 5 次就會導致帳號鎖定，不僅無法繼續嘗試，還會立刻引發使用者投訴與 SOC 高危警報。因此，攻擊者反其道而行，選擇常用弱密碼（如 `Spring2026!`、`Welcome123`），對全公司幾百個帳號各嘗試 1 次，既能避開帳戶鎖定閾值，又能暗中撞出弱密碼帳戶。

- [x] **Q2：為什麼在 4624 / 4625 紀錄中，看到 `LogonType = 10` 且來源 IP 為公網 IP 時，通常意味著企業網路架構存在嚴重疏失？**
  > **標準答案**：
  > 1. `LogonType = 10` 代表 `RemoteInteractive`（遠端桌面連線，RDP，預設 TCP 3389）。
  > 2. 合規且安全的企業網路架構嚴禁將伺服器的 RDP 通訊埠直接暴露在 Public Internet（公網）上。外部員工連入內部管理必須強制經過 SSL-VPN、零信任存取閘道（ZTNA）或專用管理跳板機（Bastion Host / PAW）。
  > 3. 若日誌中直接出現外網 IP 透過 Type 10 連入，代表邊界防火牆設定遺漏或 NAT 規則錯誤，導致伺服器暴露於公網，極易成為全球掃描器（如 Shodan、Censys）與勒索軟體團夥自動化爆破的活靶。

- [x] **Q3：某使用者反映早上進公司電腦帳號被鎖定（4625 SubStatus: `0x234`），但該使用者發誓他根本還沒開電腦。你查來源 IP 發現是內部另一台同仁的電腦，最有可能的兩大原因是什麼？**
  > **標準答案**：
  > 1. **殘留憑證自動重試（維運常見誤報）**：受害使用者先前曾在那位同仁的電腦上登入過特定資源（例如掛載共用資料夾、Outlook 委派郵箱、連線過內部印表機或排程任務），Windows 認證管理員（Credential Manager）快取了舊密碼。當該使用者前一天修改了網域密碼後，同仁電腦上的背景服務仍拿著快取的舊密碼持續對 DC 發起身分驗證，短時間內耗盡重試次數導致帳戶被鎖定。
  > 2. **內網橫向移動（真實安全事件）**：同仁的電腦已經遭到黑客入侵淪陷，攻擊者在該主機上執行了自動化滲透工具（如 CrackMapExec、BloodHound、Pass-the-Hash 工具），正在利用先前抓到的受害者憑證向內網其他主機發起批量碰撞，因而觸發了鎖定。

- [x] **Q4：登入成功事件 (4624) 裡的 `TargetLogonId` 到底有什麼神聖不可侵犯的重要性？後續主機取證如何靠它抓出黑客執行的後門進程？**
  > **標準答案**：
  > 1. **工作階段唯一標識符**：`TargetLogonId`（十六進位，如 `0x3FA2B`）代表 Windows 核心為該次登入所建立的安全工作階段（Logon Session）。同一個使用者即使登入多次，每次產生的 LogonId 都是獨一無二的。
  > 2. **進程活動全流程關聯**：在啟用命令列審計後，所有後續產生的 **Event ID 4688（新處理程序建立）** 與 Sysmon Event 1，欄位中都會忠實記錄衍生該進程的 `SubjectLogonId`。
  > 3. **取證實戰威力**：鑑識人員只需在日誌搜尋中過濾 `SubjectLogonId == <TargetLogonId>`，就能精確過濾掉系統其他背景服務的雜訊，將攻擊者自登入後所敲下的每一行 CMD 指令、執行的 PowerShell 腳本或下載的後門二進位檔案完整按時間線拼裝出來。

- [x] **Q5：在 PowerShell 中，為什麼調查幾十萬筆日誌時，絕對不能用 `Get-EventLog` 或用 `Where-Object` 在 Pipeline 後端慢慢濾？應該怎麼做才專業？**
  > **標準答案**：
  > 1. **架構缺陷與效能災難**：`Get-EventLog` 是舊版 API，僅支援經典日誌且效能極差；而在 Pipeline 後端使用 `Where-Object`（客戶端過濾）會迫使 Windows 將磁碟上成千上萬筆事件日誌全部解碼為物件並傳送給 PowerShell 管道，這會造成伺服器 CPU 飆升至 100%、記憶體耗盡，甚至直接導致取證工作逾時中斷。
  > 2. **專業實務標準**：必須使用現代化的 `Get-WinEvent`，搭配 **`-FilterHashtable`** 或 **`-FilterXPath`**。
  > 3. **底層核心原理**：`FilterHashtable` 會將過濾條件直接下推至 Windows 核心日誌子系統引擎，日誌在磁碟二進位層級就被篩選完成，只會將符合條件的少數目標事件回傳，查詢速度提升百倍以上，且不會對生產環境伺服器造成負擔。
