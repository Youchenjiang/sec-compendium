# 01.4 排程作業與自啟動項排查 (/etc/cron*, crontab -l, systemd timers)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

在一次主機異常流量警報處置中，SOC 分析師發現一台對外提供 API 服務的 Linux 伺服器，每逢整點的第 15 分鐘，其 CPU 使用率便會飆升至 100%，並建立連往東歐某 IP 的加密連線。維運工程師在終端機執行了 `kill -9` 強制殺死可疑行程 `kworker_crypto`，並手動刪除了 `/tmp/.sys_daemon` 執行檔。然而，正好一個小時後，同一路徑下的惡意二進位檔再度詭異復活，反彈 Shell 與挖礦行程重新咆哮。

「殺了又起、刪了又生」是主機安全應變中最典型的**持久化駐留（Persistence）**特徵。攻擊者在突破防線後，首要任務便是確保就算系統重開機、連線被中斷或行程遭終端管理員終結，其後門程式依然能夠週期性或隨事件自動喚醒。

藍軍安全工程師面對此類「殺不死的後門」，必須建立體系化的排查思維心法：
1. **排程作業維度（Cron Jobs）**：從使用者層級的 `crontab -l` 到系統全域的 `/etc/crontab`、`/etc/cron.*`，甚至 `/var/spool/cron/crontabs/` 幽靈檔案，逐層清查時間觸發點。
2. **現代化排程守護（Systemd Timers & Services）**：Systemd 時代的定時觸發早已超越 Cron。攻擊者極擅長偽裝成系統核心服務（如 `systemd-journald-sync.timer`）悄無聲息地週期拉起惡意腳本。
3. **終端與使用者環境劫持（Profile & Shell RC）**：管理員每次 SSH 登入都會自動載入 `/etc/profile`、`~/.bashrc`、`~/.bash_profile`，這常被利用為無特權或跨會話自啟動通道。
4. **底層動態鏈接劫持（LD_PRELOAD & ld.so.preload）**：終極匿蹤手法——攻擊者利用 `/etc/ld.so.preload` 劫持 `libc` 基本系統呼叫（如 `readdir`, `execve`），讓 `ps`, `top`, `ls`, `crontab` 本身就對管理員說謊，隱匿惡意排程與行程。

```
                       [ 攻擊者植入持久化通道 ]
                                  │
    ┌────────────────┬────────────┴────────────┬────────────────┐
    ▼                ▼                         ▼                ▼
[ Cron 排程層 ]  [ Systemd 服務層 ]      [ Shell 環境層 ]   [ 函式庫劫持層 ]
/etc/cron*       /etc/systemd/system/    /etc/profile       /etc/ld.so.preload
/var/spool/cron/ /lib/systemd/system/    ~/.bashrc          (攔截 readdir/execve)
crontab -l       *.timer / *.service     /etc/environment   (ps/top 工具集隱形)
    │                │                         │                │
    └────────────────┼─────────────────────────┴────────────────┘
                     │ (觸發時鐘訊號 / 事件喚醒 / 登入掛載)
                     ▼
          [ 惡意行程重新生成 / 反彈 Shell 復活 ]
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. Linux Vixie-Cron 守護行程輪詢機制與檔案拓撲

Linux 系統的排程服務（通常由 `cron` 或 `crond` 守護行程承載）在啟動後會以常駐 Daemon 模式運行，其底層遵循嚴格的定時輪詢生命週期：

1. **分鐘輪詢週期 (Minute Wakeup)**：
   `cron` 守護行程每隔 60 秒透過 `sleep()` 或高精度定時器被核心喚醒一次，檢查系統時鐘。
2. **目錄狀態監控 (Inotify / Stat Scan)**：
   每次喚醒時，`cron` 會比對以下核心目錄的 `mtime`（修改時間）：
   - `/etc/crontab`（系統全域主設定檔，格式含 `user-name` 欄位）
   - `/etc/cron.d/`（各獨立軟體包存放的排程設定檔）
   - `/var/spool/cron/` 或 `/var/spool/cron/crontabs/`（各 Linux 使用者專屬的個人排程檔，檔名即為使用者名稱）
   - `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, `/etc/cron.monthly/`（週期執行腳本目錄，由 `run-parts` 解析執行）
3. **語法解析與分叉執行 (Fork & Exec)**：
   若某個條目的時間條件（分、時、日、月、週）與當前時間匹配，`cron` 守護行程會調用 `fork()` 產生子行程，透過 `setuid()` / `setgid()` 切換至目標使用者權限，並調用 `/bin/sh -c "<command>"` 執行作業，同時將標準輸出與錯誤透過郵件（sendmail）或 syslog 記錄。

```
+-----------------------------------------------------------------------+
| cron daemon (每 60 秒喚醒一次)                                        |
+-----------------------------------┬-----------------------------------+
                                    │
       ┌────────────────────────────┼───────────────────────────┐
       ▼                            ▼                           ▼
/etc/crontab & /etc/cron.d/   /var/spool/cron/crontabs/   /etc/cron.{hourly,daily}/
(系統級排程：需指定使用者)    (使用者個人排程：crontab -e)(由 run-parts 週期調用)
       │                            │                           │
       └────────────────────────────┼───────────────────────────┘
                                    │ (比對當前時間撮符合條件)
                                    ▼
       fork() ──> setuid(target_user) ──> execve("/bin/sh", ["-c", cmd])
```

### 2. Systemd Timers 事件觸發架構

在現代 Linux（Systemd 架構）中，Systemd Timers 提供了比傳統 Cron 更精密（奈秒級精度、單調時鐘、相依性追蹤、資源 cgroup 隔離）的定時排程能力。

- **Timer 檔案與 Service 檔案的綁定關係**：
  每個 `*.timer` 檔案必須對應一個同名的 `*.service` 檔案（例如 `update-checker.timer` 預設觸發 `update-checker.service`）。若名稱不同，則需在 `[Timer]` 區塊顯式宣告 `Unit=other.service`。
- **時鐘觸發類型**：
  - **Realtime Timers (`OnCalendar=`)**：類似 Cron 的絕對曆法時間，例如 `OnCalendar=*-*-* 04:00:00`（每日凌晨 4 點）。
  - **Monotonic Timers (`OnBootSec=`, `OnUnitActiveSec=`)**：相對時鐘，例如系統開機後 15 分鐘 (`OnBootSec=15min`)，或服務上次執行完成後每隔 1 小時 (`OnUnitActiveSec=1h`)。
- **防禦排查優勢**：Systemd 具備記憶體內狀態樹與日誌流（journald），所有 Timer 觸發的服務均受 cgroup 約束，即便惡意指令隱蔽執行，亦會在 Systemd 的執行單元記錄中留下殘影。

### 3. 動態鏈接劫持：/etc/ld.so.preload 隱形原理

攻擊者為防止其 Cron 或持久化後門被管理員發現，常利用動態加載器（dynamic linker / loader，即 `/lib64/ld-linux-x86-64.so.2`）的預加載機制：

1. 任何動態鏈接的 ELF 程式在執行時，動態鏈接器會優先讀取 `/etc/ld.so.preload` 內宣告的動態函式庫（`.so`）。
2. 攻擊者編譯一個惡意 `.so`，覆寫（Hook）標準 C 函式庫中的關鍵 API：
   - `readdir()` / `getdents64()`：過濾特定檔名（如過濾含有 `evil`、`crypto`、特定 PID 的目錄），導致 `ls`, `crontab -l`, `ps` 完全看不到惡意檔案與行程！
   - `execve()`：在其他程式執行時注入惡意行為。
3. **排查啟示**：在可疑受害主機上，使用純靜態編譯的工具（如 BusyBox 靜態二進位檔）或透過 `/lib64/ld-linux-x86-64.so.2 --library-path ... /bin/ls` 繞過預加載，才能看到真實的檔案系統與行程表。

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 1. 全方位排程作業排查指令庫 (Cron Deep Inspection)

```bash
# 1. 檢查所有本機使用者的 Crontab 排程（遍歷 /etc/passwd，防止 crontab -l 漏檢）
for user in $(cut -f1 -d: /etc/passwd); do
    crontab -u "$user" -l 2>/dev/null | grep -v '^#' | grep -v '^$' && echo -e "==> Found active crontab for user: [1;31m$user[0m"
done

# 2. 檢視底層 spool 實體檔案與隱藏屬性（防禦檔名混淆與不可見字元）
ls -la /var/spool/cron/ /var/spool/cron/crontabs/ 2>/dev/null

# 3. 系統全域 Cron 配置檔案與目錄全面稽核
cat /etc/crontab | grep -v '^#' | grep -v '^$'
ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/

# 4. 檢查最近 7 天內被修改過的 Cron 設定檔（鎖定入侵時間軸）
find /etc/cron* /var/spool/cron/ -type f -mtime -7 -ls

# 5. 排查 Cron 檔案中的特殊隱藏屬性（如 chattr +i，防止管理員直接刪除）
lsattr -d /etc/cron* /var/spool/cron/* 2>/dev/null
```

### 2. Systemd 定時器與持久化服務深挖

```bash
# 1. 列出系統中所有正在運行的 Systemd 定時器及其下一次觸發時間
systemctl list-timers --all

# 2. 搜尋自訂或非系統發行版自帶的 Unit 檔案（重點排查 /etc/systemd/system/）
find /etc/systemd/system/ /lib/systemd/system/ -name "*.timer" -o -name "*.service" | while read unit; do
    # 搜尋內含 curl, wget, python, /tmp, /dev/shm, bash -i 等高危特徵之服務
    grep -EHn "(curl|wget|python|perl|/tmp|/dev/shm|bash -i|nc |socat)" "$unit" 2>/dev/null
done

# 3. 檢查開機自啟動已啟用的服務（Enabled Services）
systemctl list-unit-files --type=service --state=enabled | grep -v "@"

# 4. 追蹤特定 Timer 所觸發的日誌紀錄 (以 suspicious.timer 為例)
journalctl -u suspicious.service -n 50 --no-pager
```

### 3. Shell 環境變數與自啟動掛載點稽核

```bash
# 1. 檢查全域與個人環境變數設定檔
CHECK_FILES=(
    "/etc/profile"
    "/etc/bash.bashrc"
    "/etc/environment"
    "/etc/rc.local"
    "/root/.bashrc"
    "/root/.bash_profile"
    "/root/.profile"
)
for f in "${CHECK_FILES[@]}"; do
    if [ -f "$f" ]; then
        echo "=== Checking: $f ==="
        grep -En "(http|curl|wget|sh|python|perl|base64|eval)" "$f" 2>/dev/null
    fi
done

# 2. 檢查所有使用者家目錄下的隱藏 rc 檔案修改時間
find /home/ /root/ -maxdepth 2 -name ".*rc" -o -name ".*profile" -mtime -3 -ls 2>/dev/null
```

### 4. 底層劫持防禦：動態鏈接庫（LD_PRELOAD）排查與還原

```bash
# 1. 檢查是否存在動態加載劫持設定檔
cat /etc/ld.so.preload 2>/dev/null

# 2. 檢查系統動態庫目錄是否有異常新增之 .so 檔案
ls -lt /etc/ld.so.conf.d/
find /lib /lib64 /usr/lib /usr/lib64 -name "*.so*" -mtime -3 -ls 2>/dev/null

# 3. 若懷疑本地指令（ls, ps）已被劫持，使用動態鏈接器直接呼叫（繞過 preload）
/lib64/ld-linux-x86-64.so.2 --library-path /lib64 /bin/ls -la /etc/ld.so.preload
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：排程或服務執行的二進位檔案是否位於暫存目錄？** | 若執行目標路徑為 `/tmp/`、`/var/tmp/`、`/dev/shm/`、`/run/user/` 等具備可寫權限的暫存目錄，**99% 為惡意攻擊**。正規商業軟體與系統排程絕不會長期將常駐程式安裝在重開機即被清空的目錄。 |
| **Q2：排程內容是否包含網路下載並直接管線執行（Pipe-to-Shell）？** | 檢查是否包含 `curl -s ... \| bash`、`wget -q -O- ... \| python` 或 `base64 -d \| sh`。這是典型無檔案（Fileless）或隨機拉取最新 Payload 的特徵，屬極高危惡意行為。 |
| **Q3：排程建立的檔案修改時間（mtime）是否與告警爆發時間吻合？** | 比對 `/etc/cron*` 或 `/etc/systemd/system/` 檔案的 `stat` 變更時間。若變更時間精確落在 Web 伺服器遭受 SQLi/RCE 攻擊的同一個 5 分鐘窗口內，即為確鑿的入侵駐留項。 |
| **Q4：該定時作業是否能在企業維運自動化庫（如 Ansible/GitLab）中溯源？** | 比對企業 CMDB、DevOps 配置管理庫或套件管理員紀錄（`dpkg -S <file>` 或 `rpm -qf <file>`）。若該設定檔隸屬於標準軟體包（如 `logrotate`, `certbot`, `sysstat`），且雜湊值未被竄改，則判定為合法業務維運。 |
| **Q5：Systemd Timer 所啟動的服務是否綁定了反彈 TCP 連線？** | 檢視對應 `.service` 檔案中 `ExecStart=` 參數，或觀察該服務觸發時所產生的子行程。若發起主動外連且目標為公網不可信 IP、高位隨機埠或已知 C2 節點，屬於真實威脅。 |
| **Q6：Crontab 檔案中是否存在大量的空白行、無效註解或不可見 Unicode 字元？** | 攻擊者為了防止管理員直接 `cat` 或 `crontab -l` 發現惡意條目，常在檔案前部填充 100 行換行符，或利用特殊退格符隱藏。正規排程檔格式嚴整、註解清晰。 |
| **Q7：該定時任務執行頻率是否極端異常（例如每 1 秒或每 1 分鐘執行一次）？** | 業務備份、報表統計通常為每日（Daily）或每週（Weekly）。若出現 `* * * * *`（每分鐘）或死迴圈排程，且執行的是守護腳本，多為惡意軟體維護自身進程不死的「看門狗（Watchdog）」。 |
| **Q8：排程作業中使用的帳號是否為過期、離職或已被停用之系統帳號？** | 檢查執行排程的使用者在 `/etc/shadow` 中的狀態（是否為 `!` 或 `*` 鎖定）。若已被禁用的帳號依然在執行排程，需排查是否為歷史遺留殭屍作業，或遭攻擊者借屍還魂。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 惡意排程與看門狗之原子化清除流程

面對具備自動拉起機制的惡意排程，處置順序極為關鍵。**切忌直接 kill 行程，否則下一秒即被 Cron 重新拉起！**

```bash
# 步驟 1：立即暫停 Cron 與關聯的 Systemd 定時守護程式（阻斷自動重生能力）
systemctl stop cron crond systemd-journald-sync.timer 2>/dev/null

# 步驟 2：解除惡意檔案的防刪除鎖定 (chattr -i)
# 很多惡意程式會下 chattr +i 防止 root 刪除其排程
chattr -i -a /etc/cron.d/malicious_job /var/spool/cron/crontabs/* 2>/dev/null

# 步驟 3：備份惡意排程與 Service 樣本（以供留證取證）
mkdir -p /root/ir_backup/
cp -a /etc/cron.d/malicious_job /root/ir_backup/ 2>/dev/null

# 步驟 4：徹底物理刪除排程與服務單元
rm -f /etc/cron.d/malicious_job
rm -f /var/spool/cron/crontabs/victim_user
rm -f /etc/systemd/system/malicious.service /etc/systemd/system/malicious.timer
systemctl daemon-reload

# 步驟 5：終結記憶體中正在運行的惡意進程實例
pkill -9 -f "kworker_crypto"
pkill -9 -f "curl.*raw.github"

# 步驟 6：恢復乾淨的 Cron 守護程式
systemctl start cron || systemctl start crond
```

### 2. 排程權限與檔案完整性存取硬化

```bash
# 1. 嚴格限制 crontab 指令的執行權限（僅允許指定管理員）
# 建立 /etc/cron.allow，一旦此檔案存在，僅有列名之使用者可使用 cron
echo "root" > /etc/cron.allow
echo "opsadmin" >> /etc/cron.allow
chmod 600 /etc/cron.allow
rm -f /etc/cron.deny

# 2. 鎖定全域排程目錄權限（防止非 root 寫入）
chmod 700 /etc/cron.d /etc/cron.daily /etc/cron.hourly /etc/cron.monthly /etc/cron.weekly
chmod 600 /etc/crontab

# 3. 限制 /tmp 與 /dev/shm 的執行權限（noexec 掛載，徹底閹割落地腳本）
# 在 /etc/fstab 中設定：
# tmpfs /dev/shm tmpfs defaults,nodev,nosuid,noexec 0 0
mount -o remount,noexec /dev/shm
```

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 靶場環境說明
- **受害伺服器**：`192.168.56.102`（Ubuntu 22.04 LTS）。
- **實戰情境**：模擬攻擊者透過 Web 漏洞上傳 WebShell 後，建立多重持久化機制（Cron 看門狗 + Systemd Timer 備援）。

### 實戰驗證步驟

#### 步驟 1：模擬攻擊者植入 Cron 看門狗與惡意腳本
在目標主機模擬攻擊者行為：
```bash
# 1. 建立惡意 Payload 於暫存目錄
cat << 'EOF' > /dev/shm/.watchdog.sh
#!/bin/bash
while true; do
    if ! pgrep -f "sys_miner" > /dev/null; then
        echo "[!] Miner dead, respawning at $(date)" >> /tmp/miner.log
        python3 -c 'import time; time.sleep(3600)' sys_miner &
    fi
    sleep 30
done
EOF
chmod +x /dev/shm/.watchdog.sh

# 2. 寫入全域 Cron 隱匿排程 (每 5 分鐘檢查一次看門狗)
echo "*/5 * * * * root /dev/shm/.watchdog.sh >/dev/null 2>&1" > /etc/cron.d/.sys_sync
chmod 644 /etc/cron.d/.sys_sync

# 3. 鎖定檔案防止常規刪除
chattr +i /etc/cron.d/.sys_sync
```

#### 步驟 2：模擬攻擊者建立 Systemd Timer 備用持久化
```bash
# 建立備用 Service 與 Timer
cat << 'EOF' > /etc/systemd/system/sys-cache.service
[Unit]
Description=System Cache Update Service

[Service]
Type=oneshot
ExecStart=/bin/bash -c "touch /tmp/.systemd_alive"
EOF

cat << 'EOF' > /etc/systemd/system/sys-cache.timer
[Unit]
Description=Trigger System Cache Update Every 10 Minutes

[Timer]
OnBootSec=1min
OnUnitActiveSec=10min
Unit=sys-cache.service

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now sys-cache.timer
```

#### 步驟 3：藍軍工程師發現異常並執行現場排查
藍軍登入主機，執行標準獵捕 SOP：
```bash
# 1. 執行排程全面掃描腳本
find /etc/cron* -type f -exec lsattr {} + 2>/dev/null
# 發現 /etc/cron.d/.sys_sync 具有 ----i--------- 屬性，且檔名帶點（隱藏）

# 2. 檢視其內文
cat /etc/cron.d/.sys_sync
# 發現指向 /dev/shm/.watchdog.sh

# 3. 排查 Systemd Timers
systemctl list-timers | grep sys-cache
# 發現非發行版原生的 sys-cache.timer
```

#### 步驟 4：執行原子化處置與圍堵
```bash
# 1. 解鎖並刪除 Cron
chattr -i /etc/cron.d/.sys_sync
rm -f /etc/cron.d/.sys_sync

# 2. 停用並拔除 Systemd Timer
systemctl stop sys-cache.timer
systemctl disable sys-cache.timer
rm -f /etc/systemd/system/sys-cache.timer /etc/systemd/system/sys-cache.service
systemctl daemon-reload

# 3. 殺死記憶體中的行程並清除實體腳本
pkill -9 -f "sys_miner"
pkill -9 -f ".watchdog.sh"
rm -f /dev/shm/.watchdog.sh /tmp/.systemd_alive
```

#### 步驟 5：驗證清除結果
```bash
crontab -l
systemctl list-timers | grep sys-cache
pgrep -f "sys_miner"
# 均無任何輸出，主機恢復乾淨基線狀態。
```

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：當管理員執行 `crontab -l` 顯示 `no crontab for root` 時，系統是否保證沒有任何以 root 身分執行的 Cron 排程？為什麼？**
  - *驗收標準*：答出絕對不保證。因為 `crontab -l` 僅讀取 `/var/spool/cron/crontabs/root` 個人排程檔；以 root 權限執行的任務還可以隱匿在 `/etc/crontab`、`/etc/cron.d/*` 以及 `/etc/cron.{hourly,daily,weekly,monthly}/*` 中。
- [ ] **Q2：若攻擊者在排程檔案中設定了 `chattr +i` 屬性，管理員在 root 權限下直接執行 `rm -f` 會有什麼現象？應如何正確刪除？**
  - *驗收標準*：答出會報錯 `Operation not permitted`（即使是 root 也無法刪除、改名或寫入）。正確處置方式為先執行 `chattr -i <檔案>` 移除不可變更旗標，隨後再執行 `rm -f`。
- [ ] **Q3：在 Systemd 體系中，要實現「開機後 10 分鐘執行一次，隨後每隔 2 小時執行一次」的持久化駐留，Timer 檔案中應配置哪兩個關鍵參數？**
  - *驗收標準*：答出 `OnBootSec=10min`（開機後延遲時間）與 `OnUnitActiveSec=2h`（服務單元上次啟動後的週期循環時間）。
- [ ] **Q4：為什麼檢查惡意自啟動項時，絕不能只看副檔名是 `.sh` 的腳本檔案？**
  - *驗收標準*：答出 Linux 檔案系統不依賴副檔名判斷執行屬性。攻擊者常將惡意腳本命名為 `.jpg`、`.conf`、`.lock`，或直接放置編譯好的 ELF 二進位檔、Python 腳本，透過排程呼叫程程解析器（如 `python /tmp/.lock`）直接執行。
- [ ] **Q5：若受害主機被植入了 `/etc/ld.so.preload` 劫持 Rootkit，導致本地 `ls`、`ps`、`crontab` 均無法顯示惡意檔案，藍軍有哪些非侵入性的反制偵測手段？**
  - *驗收標準*：答出：(1) 直接使用動態鏈接器運行指令 `/lib64/ld-linux-x86-64.so.2 --library-path /lib64 /bin/ls` 繞過預加載；(2) 使用靜態編譯且無外部相依性的工具（如靜態編譯的 BusyBox）；(3) 檢視 `/proc/<PID>/maps` 查看行程是否加載了非預期的動態庫；(4) 將磁碟卸載掛載至分析機或 Live CD 取證環境進行離線分析。
