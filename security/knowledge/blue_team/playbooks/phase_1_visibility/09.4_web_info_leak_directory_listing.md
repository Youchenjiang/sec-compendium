> **情境帶入**：  
> 週一清晨 07:30，距離正式開工還有一個多小時。公司監控伺服器突然收到 AWS 雲端帳單緊急告警：  
> 企業的 AWS 帳戶在一夜之間被創建了 200 台高規格 GPU 運算實例，正在瘋狂挖礦！  
> 
> 雲端架構師震驚地檢查權限：「我們的 AWS Root 密碼開啟了硬體 MFA，根本沒有人登入過 AWS 控制台！黑客到底是怎麼拿到 `AKIA...` 存取金鑰（Access Key）的？」  
> 
> 分析師緊急調閱企業官網的 Nginx 存取日誌，發現昨晚 23:14，一個來自境外的 IP 使用目錄枚舉工具（如 `dirsearch`、`gobuster`），對網站發起了一連串密集的 HTTP GET 請求：  
> - `GET /.git/config HTTP/1.1` ➔ 200 OK (284 bytes)  
> - `GET /.env HTTP/1.1` ➔ 200 OK (1,240 bytes)  
> - `GET /backup.sql HTTP/1.1` ➔ 200 OK (58 MB)  
> 
> 原來，開發團隊在發布網站時，直接把本地的 `.git` 版本控制目錄與包含雲端密鑰的 `.env` 設定檔原封不動地打包上傳到了 Web 根目錄！  
> 攻擊者使用開源工具 `GitHack`，在 30 秒內將整座網站的完整原始碼、歷史提交紀錄，連同寫死在代碼裡的 AWS Access Key 與資料庫密碼，全量逆向還原並脫庫！  
> 
> 這是典型的 **敏感資訊洩漏（Information Disclosure）** 與 **Web 目錄遍歷 / 備份檔案暴露**！  
> 為什麼很多公司沒有 SQL 注入、沒有命令執行漏洞，卻依然在幾分鐘內遭到滅頂之災？身為防守方，我們該如何在日誌中捕捉目錄爆破行為，並在伺服器端徹底封死敏感路徑？
>

## 🧩 第一動：底層機制解剖——Web 伺服器的「過度慷慨」

資訊洩漏漏洞通常不是軟體代碼的語法 Bug，而是**伺服器配置疏失（Misconfiguration）與開發維運不良習慣**引發的物理暴露。

### 1.1 `.git` 目錄外洩的物理還原原理

Git 在本地倉庫的 `.git` 目錄下維護著完整的版本控制樹。只要 Web 伺服器允許存取 `/.git/`，黑客就能依序抓取：

```
/.git/
  ├── config         : 記錄遠端倉庫位址 (可能包含私有 GitLab Token 或帳號密碼！)
  ├── HEAD           : 指向當前分支 (例如: ref: refs/heads/main)
  ├── index          : 二進位檔案！記錄整座專案所有檔案的「相對路徑與 SHA-1 雜湊」！
  └── objects/       : 存儲所有檔案歷史內容的 zlib 壓縮物件！
```
- **還原工具原理（如 GitHack / dvcs-ripper）**：  
  黑客先下載 `/.git/index`，解析出整座專案的所有原始碼路徑清單；接著依據 Hash 逐個發起 HTTP 請求下載 `/.git/objects/xx/yyyy...`，在本地解壓縮，**100% 完整還原整個專案的 Git 歷史與原始碼！**

### 1.2 目錄瀏覽（Directory Listing / Indexing）

當使用者存取一個目錄（如 `https://example.com/uploads/`）而該目錄下**沒有 `index.html` 或 `index.php`** 時：
- 若 Web 伺服器開啟了目錄瀏覽功能（Apache 的 `Options +Indexes`，Nginx 的 `autoindex on`）：  
  伺服器會**自動生成一個包含該資料夾下所有檔案名稱、修改時間與檔案大小的 HTML 索引清單！**  
- 黑客可以一眼看光所有上傳的檔案、歷史文件甚至資料庫備份。

### 1.3 現代微服務暴露：Spring Boot Actuator 與 Heapdump 記憶體外洩

在雲原生與微服務體系中，Spring Boot 提供了一系列開箱即用的維運端點（Actuator）。若未配置 Spring Security 授權直接暴露出公網：
- `/actuator/env`：暴露應用程式所有環境變數，包含 Spring Cloud Config、未脫敏的資料庫密碼與雲端憑證。
- `/actuator/heapdump`：直接向客戶端串流下載整座 JVM 的完整記憶體轉儲檔案（Heap Dump）！攻擊者使用 Eclipse Memory Analyzer（MAT）打開，可在數秒內提取出駐留在記憶體中的明文 JWT 金鑰、登入密碼與私鑰。

## 💻 第三動：現場追兇——作戰指令與檢驗腳本

身為現場調查員，你必須掌握在海量 404 請求中快速找出「黑客到底偷走了什麼」的技能。

### 3.1 Linux 現場快篩 Nginx / Apache 存取日誌

#### 步驟 1：致命排查——抓出所有「成功下載（Status 200）」的敏感檔案請求！
黑客會掃描數千個不存在的檔案（404），但只要**有一個敏感檔案回傳了 200 OK，就代表大禍臨頭**：

```bash
# 篩選對敏感檔案發起、且伺服器回傳 200 OK 的請求（排除正常圖片與 JS）
grep -Ei "(\.git|\.env|\.sql|\.zip|\.tar|\.bak|\.config|swagger|actuator)" /var/log/nginx/access.log | awk '$9 == "200" {print "🚨 檔案已外洩! 來源: " $1 ", 請求: " $7 ", 大小: " $10 " bytes"}' | head -n 25
```

#### 步驟 2：揪出正在使用自動化工具掃描目錄的攻擊者 IP
```bash
# 統計 10 分鐘內觸發 404 狀態碼超過 50 次的惡意掃描源 IP
awk '$9 == "404" {print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -nr | head -n 10
```

### 3.2 Python 自動化敏感檔案暴露檢測腳本

使用 Python 腳本對企業所有網頁資產自動發起「防守方安全快篩」：

```python
#!/usr/bin/env python3
"""
敏感檔案暴露與目錄遍歷檢測工具 (sensitive_exposure_scanner.py)
功能：快篩 Web 站台是否存在 .git, .env, backup.sql, actuator 等常見洩漏點
"""
import sys
import urllib.request
import urllib.error

SENSITIVE_PATHS = [
    "/.git/HEAD",
    "/.git/config",
    "/.env",
    "/.svn/entries",
    "/.DS_Store",
    "/backup.sql",
    "/db.sql",
    "/www.zip",
    "/web.config",
    "/actuator/env",
    "/actuator/health",
    "/swagger-ui.html",
    "/v2/api-docs",
    "/phpinfo.php"
]

def scan_target(base_url):
    print(f"[*] 掃描目標網站敏感檔案暴露狀態: {base_url}")
    base_url = base_url.rstrip("/")
    leaks = []

    for path in SENSITIVE_PATHS:
        target = base_url + path
        req = urllib.request.Request(target, headers={"User-Agent": "Security-Audit-Scanner/1.0"})
        try:
            with urllib.request.urlopen(req, timeout=5) as resp:
                if resp.status == 200:
                    length = resp.headers.get("Content-Length", "未知")
                    print(f"🚨 【重大洩漏】發現敏感檔案暴露: {target} (長度: {length} bytes)")
                    leaks.append(target)
        except urllib.error.HTTPError as e:
            if e.code == 403:
                pass # 403 代表伺服器已防禦禁止存取
        except Exception:
            continue

    if not leaks:
        print("✅ 常用敏感路徑均受保護或不存在。")
    else:
        print(f"\n⚠️ 累計發現 {len(leaks)} 個高危險暴露檔案！請立即處置！")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("用法: python sensitive_exposure_scanner.py <https://target-domain.com>")
        sys.exit(1)
    scan_target(sys.argv[1])
```

### 3.3 Wireshark 封包鑑識過濾器

在捕獲的 Web 流量 PCAP 中，使用以下語法檢出資訊洩漏封包：

```wireshark
# 1. 篩選針對敏感副檔名與隱藏目錄且狀態碼為 200 的 HTTP 封包
http.response.code == 200 && http.request.uri matches "(?i)(\.git|\.env|\.bak|\.sql|\.zip)"

# 2. 搜尋回傳內容中包含目錄索引特徵的 HTML 頁面
http.response && frame matches "(?i)Index of /"

# 3. 抓取包含程式語言詳細除錯堆疊的報錯封包
http.response && (frame matches "(?i)Traceback \(most recent call last\)" || frame matches "(?i)Fatal error:")
```

### 3.4 Splunk SPL 敏感檔案外洩獵捕

#### 偵測情境：大體積備份檔或源碼遭外洩偵測
> **邏輯**：當存取 URI 包含 `.sql`、`.zip`、`.tar.gz` 等備份後綴，且狀態碼為 200、回傳位元組數大於 1MB（`bytes > 1048576`），**判定為核心資料庫或源碼包遭外洩！**

```splunk
index=web_access status=200 (uri="*.sql" OR uri="*.zip" OR uri="*.tar.gz" OR uri="*.env" OR uri="*/.git/*")
| eval size_mb=round(bytes/1024/1024, 2)
| table _time, src_ip, uri, status, size_mb, http_user_agent
| eval Alert_Level="🚨 CRITICAL: Sensitive Archive/Source File Downloaded!"
| sort - size_mb
```

## ⚖️ 第四動：研判分水嶺——正常搜尋引擎爬蟲 vs 惡意目錄遍歷？

在日常維運中，Googlebot、Bingbot 搜尋引擎爬蟲也會頻繁抓取網頁。你該如何區分是正常 SEO 爬蟲，還是黑客在掃描你的後門與原始碼？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 單一來源 IP 短時間內產生大量 404 錯誤，或敏感設定檔（`.git`, `.env`）被存取。 |
| **Q2. 來源身分**（User-Agent 與 IP 是否吻合？） | 聲稱是 `Googlebot`，但執行 `nslookup <IP>` 反查主機名稱**並非以 `.googlebot.com` 結尾**？（偽造爬蟲 User-Agent 特徵！） |
| **Q3. 請求路徑特徵**（爬取的是內容還是敏感檔案？） | 是爬取正常的產品新聞文章 URL，還是專門針對以 `.` 開頭的隱藏目錄、備份檔字典（`db.sql`, `backup.zip`）？ |
| **Q4. 請求速率**（連線的頻率與行為模式？） | 正常爬蟲會遵守 `robots.txt` 且具備合理的爬取間隔；黑客工具（如 dirsearch）每秒發送數十到數百個請求。 |
| **Q5. 存取結果**（敏感檔案是否真正被成功下載？） | 檢視 HTTP 狀態碼：如果是 403 或 404，代表威脅受阻；**如果是 200 OK 且 Response 大小正常，判定為實質資料外洩！** |
| **Q6. 洩漏數據影響**（外洩的檔案包含什麼內容？） | 若 `.env` 被下載：檢查裡面是否包含雲端 AK/SK、資料庫密碼、微信支付私鑰？ |
| **Q7. 橫向波及**（該攻擊者是否已利用洩漏密鑰？） | 立即審計全網雲端日誌（如 AWS CloudTrail）：被洩漏的 Access Key 是否已在其他境外 IP 被調用？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 立即於伺服器刪除暴露的敏感檔案；2. 封鎖攻擊者 IP；3. **立刻輪換（Rotate）所有在該檔案中出現過的所有密鑰與密碼！** |

## 🛡️ 第五動：根除與加固 SOP (Mitigation & Hardening)

防禦資訊洩漏，必須在 Web 伺服器配置與 CI/CD 流程中建立雙重保險：

### 1. 第一步：Nginx / Apache 全域阻斷隱藏檔案與敏感副檔名
在 Nginx 主設定檔（`nginx.conf`）中加入以下規則，**一秒終結全站所有 `.` 開頭檔案與備份副檔名的存取**：

```nginx
# 1. 嚴禁存取任何以 . 開頭的隱藏檔案或目錄（如 /.git, /.env, /.svn）
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}

# 2. 嚴禁存取常見敏感備份與資料庫副檔名
location ~* \.(sql|bak|inc|old|temp|backup|cfg|ini|log|tar|gz|zip)$ {
    deny all;
}

# 3. 徹底停用目錄索引瀏覽（若未配置，預設即為 off）
autoindex off;
```

### 2. 第二步：生產環境關閉所有詳細除錯報錯（Debug Mode）
- **PHP**：在 `php.ini` 設定 `display_errors = Off` 與 `log_errors = On`。
- **Python (Django/Flask)**：確保生產環境配置 `DEBUG = False`。
- 自定義全域錯誤頁面（404, 500），絕不向客戶端透露伺服器內部絕對路徑。

### 3. 第三步：CI/CD 管道自動化金鑰掃描（防源碼污染）
- 在 Git Commit 流程中引入 **Gitleaks** 進行 pre-commit 勾點檢查：
  ```bash
  # 安裝 gitleaks 並設置 commit 檢查
  gitleaks protect --staged --verbose
  ```
- 專案打包部署腳本中，強制將 `.git`、`.env` 等開發環境檔案排除在發布目錄之外。

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能回答，代表你已徹底掌握 Web 資訊洩漏防護：

- [ ] **Q1**：在 Git 版本控制系統中，為什麼黑客只要能存取 Web 根目錄下的 **`/.git/` 資料夾**，就算完全沒有目錄瀏覽權限，也能利用開源工具 100% 還原出整座網站的所有歷史原始碼？
  > **解答要點**：Git 的版本庫結構具備自我描述特性。即使 Web 伺服器關閉了目錄清單，黑客只要能下載固定的根檔案 `/.git/index`，就能解析出專案中所有檔案的相對路徑與對應的 SHA-1 雜湊物件 ID。接著依據雜湊計算出實體檔案路徑（如 `/.git/objects/4b/825dc642...`）發起精準的 HTTP GET 下載並本地解壓，便能完整拼接出歷史提交記錄與原始碼，完全不需要依賴目錄列表。
- [ ] **Q2**：在 Nginx 伺服器中，**`autoindex on;`** 配置項的作用是什麼？如果關閉該選項，當目錄下缺少 `index.html` 時，伺服器會回傳哪一種 HTTP 狀態碼？
  > **解答要點**：`autoindex on;` 會啟用伺服器目錄瀏覽索引功能。當使用者造訪一個目錄且該目錄下缺少預設首頁檔案（如 index.html 或 index.php）時，Nginx 會自動生成一個列出該目錄下所有檔案與子目錄的 HTML 頁面。如果將其關閉（`autoindex off;`），在缺少首頁檔案的情況下，Nginx 預設會拒絕展示目錄內容，並直接向客戶端回傳 **`403 Forbidden`** 錯誤狀態碼。
- [ ] **Q3**：在排查 Web 存取日誌時，如果發現黑客正在使用 `dirsearch` 進行字典爆破，為什麼分析師應該著重過濾 **HTTP 狀態碼為 200 且體積異常的請求**，而不是只看 404？
  > **解答要點**：自動化目錄爆破工具會發送成千上萬個隨機路徑，因此產生大量 404 錯誤是攻擊者的探測雜訊；但真正的攻擊威脅與成果完全取決於「是否有敏感路徑回傳了 200 OK」。分析師需特別關注返回 200 且響應位元組（Bytes Sent）較大的記錄，因為這代表備份壓縮檔（.zip）、資料庫導出檔（.sql）或敏感設定檔已被攻擊者完整接收下載，屬於已經造成的資料外洩實害。
- [ ] **Q4**：現代雲原生應用（如 Spring Boot）的 **Actuator 監控端點**（如 `/actuator/env` 或 `/actuator/heapdump`），在未設身分驗證裸露在外網時，黑客能從中獲取什麼致命情報？
  > **解答要點**：`/actuator/env` 會洩漏整座應用的環境變數，包含外部資料庫連線字串、加密金鑰與微服務授權碼；而 `/actuator/heapdump` 更加致命，它允許攻擊者直接下載 JVM 記憶體的完整快照二進位檔案。黑客使用記憶體分析工具可從中提取出當前記憶體中快取的所有明文使用者密碼、未過期的 Session Token、第三方雲端 API Key 以及解密後的敏感資料。
- [ ] **Q5**：為什麼很多開發者在代碼中刪除了密碼並重新提交（Commit），但該密碼在資安審計中依然被判定為「已經洩漏」？你該如何使用 Git 原生指令徹底抹除歷史版本中的機敏數據？
  > **解答要點**：因為 Git 是具有不可篡改歷史特性的版本控制系統，單純在最新的 Commit 中刪除密碼，該密碼依然會作為不可變的 Object 完整保留在歷史提交紀錄中，任何檢視 `git log` 或 `git diff` 的人都能調出歷史版本查看。要徹底抹除歷史記錄中的敏感數據，必須使用 `git filter-repo`（或歷史工具 `git filter-branch`）重寫全倉庫的 Commit 歷史樹，並執行 `git reflog expire --expire=now --all` 與 `git gc --prune=now` 徹底清空垃圾回收快取，同時所有涉及該密碼的線上憑證必須立即廢棄輪換。\n
