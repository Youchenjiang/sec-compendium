## 🧩 第一動：底層封包解剖——TCP 交握的核心狀態機

任何高階的網路攻擊與連線異常，本質都是對底層通訊協定狀態機（State Machine）的濫用。要精準鑑識異常，必須先在顯微鏡下看懂正常的三向交握（Three-way Handshake）與完整的 TCP 狀態轉換。

### 1.1 TCP 標頭關鍵旗標（Control Flags）解構

在 Wireshark 展開 `Transmission Control Protocol`，最核心的是這 6 個 1-bit 的控制旗標：

```
0000 0000 0000 (TCP Header Control Flags)
  ├── [SYN] (Synchronize) : 請求建立連線，同步初始序號（ISN）。
  ├── [ACK] (Acknowledgment): 確認收到資料或收到連線請求，確認號（Ack Number）欄位有效。
  ├── [FIN] (Finish)      : 發送端已無資料發送，請求優雅關閉單向連線通道。
  ├── [RST] (Reset)       : 強制中斷連線、拒絕連線請求或重設異常連線，不等待緩衝區清空。
  ├── [PSH] (Push)        : 要求接收端立即將 TCP 緩衝區資料推送給應用層（如 HTTP POST 請求）。
  └── [URG] (Urgent)      : 緊急指標有效（實務資安場景極少使用，常出現在特定掃描探針）。
```

### 1.2 正常交握的序號（SEQ）與確認號（ACK）演進數學

在底層網路鑑識中，請牢記 Wireshark 相對序號與底層 Raw Sequence Number 的演進邏輯：

```
[Client (客)]                                         [Server (服)]
   │                                                     │
   │ 1. [SYN] Seq = ISN_c                                │ 狀態: SYN_RCVD
   │ ──────────────────────────────────────────────────> │ 伺服器分配半開資源 (SYN Backlog)
   │                                                     │
   │ 2. [SYN, ACK] Seq = ISN_s, Ack = ISN_c + 1          │
   │ <────────────────────────────────────────────────── │
   │                                                     │
   │ 3. [ACK] Seq = ISN_c + 1, Ack = ISN_s + 1           │ 狀態: ESTABLISHED
   │ ──────────────────────────────────────────────────> │ 連線建立，進入全開佇列 (Accept Queue)
   │                                                     │
```

- **SYN 封包消耗 1 個序號**：因此 Server 回應的 ACK 必然是 `Client_ISN + 1`。
- **SYN-ACK 封包也消耗 1 個序號**：因此 Client 最後回應的 ACK 必然是 `Server_ISN + 1`。
- **純 ACK 且長度為 0 的封包不消耗序號**：後續封包的序號保持不變。

### 1.3 TCP 完整連線狀態轉換圖

掌握 TCP 狀態機是判斷連線異常卡滯的基礎：

```
[TCP 狀態機核心路線]
LISTEN ──(收到 SYN)──> SYN_RCVD ──(收到 ACK)──> ESTABLISHED
  │                                                    │
  │ (發送 FIN)                                         │ (主動發送 FIN)
  ▼                                                    ▼
CLOSE_WAIT <──(收到 FIN)── ESTABLISHED            FIN_WAIT_1 ──(收到 ACK)──> FIN_WAIT_2
  │                                                                            │
  └──(發送 FIN)──> LAST_ACK ──(收到 ACK)──> CLOSED <──(逾時 2MSL)── TIME_WAIT ◄┘
```
- **SYN_RCVD 卡滯**：代表伺服器發了 SYN-ACK 但遲遲等不到客戶端的 ACK，典型的 SYN Flood 症狀。
- **CLOSE_WAIT 堆積**：代表遠端已關閉連線，但本機應用程式（如 Web 程式碼漏洞）未呼叫 `close()` 釋放 Socket。
- **TIME_WAIT 暴增**：主動關閉端維持 2MSL 確保延遲封包消亡，大量短連線（如爬蟲、壓力測試）會導致本機 Port 耗竭。

## 🧭 第二動：解碼意圖——異常交握與攻擊特徵表

當攻擊者介入時，交握的正常節奏會被打破，產生三種經典攻防模式：

### 2.1 TCP 異常特徵與攻擊手法速查表

| 封包特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與鑑識防禦（怎麼應對） |
| :--- | :--- | :--- |
| **大量 SYN 只有單向發出，完全無 ACK 回應** | **TCP SYN Flood 阻斷攻擊**：<br>攻擊者偽造（Spoof）大量隨機來源 IP 發送 SYN，刻意不回送第三次 ACK，耗盡伺服器 SYN Backlog 連線佇列。 | • **影響**：伺服器 `SYN_RECV` 暴增，正常用戶連線全部超時丟棄。<br>• **防禦**：🚨 核心立即啟用 `tcp_syncookies`，網路邊界啟用 TCP SYN Proxy。 |
| **SYN 瞬間收到 RST, ACK** | **通訊埠關閉（Port Closed）** 或 **邊界攔截**：<br>目標主機沒有服務在該 Port 監聽，核心直接回彈 RST；或路徑上的防火牆主動阻斷。若連續針對不同 Port，為 **Port Scan（掃描）**。 | • **影響**：攻擊者正在探測服務暴露面與防火牆 ACL。<br>• **防禦**：比對來源 IP，若短時間連續掃描超過閾值，自動在防火牆將其暫時封鎖。 |
| **收到 SYN-ACK 後，客戶端立即回送 RST** | **TCP 半開隱形掃描（Stealth SYN Scan）**：<br>如 `nmap -sS`。客戶端騙取伺服器回送 SYN-ACK 確認 Port 開啟後，故意不走完握手，直接回彈 RST 關閉連線。 | • **影響**：企圖避開應用層（如 Web Server Access Log）連線日誌。<br>• **防禦**：必須仰賴網路層 NIDS（Snort/Suricata）或 Zeek 才能捕捉此行為。 |
| **連線進行中突然出現大量非對稱 RST** | **RST 注入攻擊** 或 **旁路審計阻斷**：<br>中間人（MITM）或旁路安全設備（如 GFW、企業 DLP）偵測到違規傳輸，偽造 RST 強行切斷連線；或連線逾時異常崩潰。 | • **影響**：合法會話被惡意中斷，或傳輸內容觸發資安審計規則。<br>• **防禦**：檢查 RST 封包的 TTL 與 MAC 位址是否與前後正常封包一致以鑑別偽造。 |
| **同一來源 IP 對同一 Port 出現大量 SYN 重傳** | **目標主機宕機** 或 **伺服器佇列滿載丟包**：<br>客戶端發送 SYN，但因伺服器無回應或中間封包遺失，依 TCP 逾時退避演算法（RTO）持續重發。 | • **影響**：伺服器無回應或網路黑洞。<br>• **防禦**：檢視重傳間隔是否符合指數退避（1s, 2s, 4s...），排查伺服器效能與網路狀態。 |
| **SYN 封包固定大小（如 40 bytes），無任何 TCP Options** | **Raw Socket 惡意發包工具（hping3/Scapy）**：<br>攻擊腳本手工構造最小 IP/TCP 標頭，未帶作業系統常規的 MSS、Window Scale、SACK 等選項。 | • **影響**：直接指認非自然人類使用者存取。<br>• **防禦**：透過防火牆直接 Drop 無 Options 的畸形 SYN 封包。 |

## 💻 第三動：現場追兇——Wireshark 與命令列實戰操作

在事故發生的當下，分析師必須具備在數百萬封包中「幾秒鐘過濾出元兇」的能力。

### 3.1 Wireshark 顯示過濾器（Display Filter）作戰指令

在 Wireshark 頂部過濾列直接輸入以下語法：

#### 語法 1：捕捉所有未完成的「孤兒 SYN」（SYN Flood 必備）
```wireshark
# 篩選出所有發起連線 (SYN=1)，但尚未確認連線 (ACK=0) 的封包
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

#### 語法 2：快速揪出重設連線（RST 封包）
```wireshark
# 篩選所有帶有 RST 旗標的異常中斷封包
tcp.flags.reset == 1
```

#### 語法 3：抓出疑似 Nmap 半開掃描行為（SYN 之後直接回 RST）
```wireshark
# 尋找由同一台主機發起且連線重置的封包特徵
(tcp.flags.syn == 1 and tcp.flags.ack == 0) or (tcp.flags.reset == 1)
```

#### 語法 4：分析交握延遲與封包遺失
```wireshark
# 利用 Wireshark Expert Info 抓出所有 TCP 重傳、失序封包
tcp.analysis.retransmission || tcp.analysis.lost_segment
```

### 3.2 Linux 伺服器現場終端指令（Tshark / ss / netstat）

若無法將 GB 級的 PCAP 載回本地 Wireshark，必須直接在 Linux 終端機進行排查：

#### 步驟 1：檢視目前伺服器上的 TCP 連線狀態分佈
```bash
# 統計目前所有 TCP 狀態（著重觀察 SYN-RECV 的數量）
ss -ant | awk '{print $1}' | sort | uniq -c | sort -nr
```
> 💡 **警報指標**：如果 `SYN-RECV`（或 `SYN_RECV`）高達數千甚至數萬，而 `ESTAB` 極低，**100% 確定正遭受 SYN Flood 攻擊**！

#### 步驟 2：使用 tshark 在終端機快速統計攻擊來源 IP
```bash
# 抓取 eth0 網卡 5 秒鐘內的 SYN 封包，並按來源 IP 聚合排行前 10 名
tshark -i eth0 -f "tcp[tcpflags] & (tcp-syn) != 0 and tcp[tcpflags] & (tcp-ack) == 0"        -T fields -e ip.src | sort | uniq -c | sort -nr | head -n 10
```

#### 步驟 3：檢查 Linux 核心 SYN 佇列是否溢位（Drop 統計）
```bash
# 查看系統因為 SYN Queue / Listen Queue 滿載而丟棄的連線計數
netstat -s | grep -i "listen"
# 或檢視 TCPSynDrop
cat /proc/net/netstat | awk '/Syncookies/ {print $0}'
```

### 3.3 自動化 PCAP 封包異常快篩 Python 腳本

將上述檢測邏輯封裝為一鍵執行的取證腳本 `pcap_tcp_anomaly_analyzer.py`：

```python
#!/usr/bin/env python3
"""
PCAP TCP 交握與異常分析工具 (pcap_tcp_anomaly_analyzer.py)
功能：讀取 PCAP 檔案，自動統計 SYN/ACK/RST 比例，計算半開連線率與潛在 SYN Flood / Nmap 掃描特徵
"""
import sys
import subprocess

def analyze_pcap_with_tshark(pcap_path):
    print(f"=== [1] 分析 PCAP 檔案: {pcap_path} ===")
    
    # 統計總 TCP 封包、SYN、SYN-ACK、RST
    cmd_syn = f'tshark -r "{pcap_path}" -Y "tcp.flags.syn==1 && tcp.flags.ack==0" | wc -l'
    cmd_synack = f'tshark -r "{pcap_path}" -Y "tcp.flags.syn==1 && tcp.flags.ack==1" | wc -l'
    cmd_rst = f'tshark -r "{pcap_path}" -Y "tcp.flags.reset==1" | wc -l'
    cmd_total = f'tshark -r "{pcap_path}" -Y "tcp" | wc -l'
    
    try:
        syn_count = int(subprocess.check_output(cmd_syn, shell=True).decode().strip())
        synack_count = int(subprocess.check_output(cmd_synack, shell=True).decode().strip())
        rst_count = int(subprocess.check_output(cmd_rst, shell=True).decode().strip())
        total_count = int(subprocess.check_output(cmd_total, shell=True).decode().strip())
    except Exception as e:
        print(f"執行 tshark 統計失敗: {e}")
        return

    print(f"[*] 總 TCP 封包數: {total_count}")
    print(f"[*] SYN 請求數   : {syn_count}")
    print(f"[*] SYN-ACK 回應 : {synack_count}")
    print(f"[*] RST 重設數   : {rst_count}")

    if syn_count > 0:
        half_open_ratio = (syn_count - synack_count) / syn_count
        print(f"[*] 半開連線比例 (Uncompleted Handshake Ratio): {half_open_ratio:.2%}")
        
        if half_open_ratio > 0.80 and syn_count > 1000:
            print("🚨 【嚴重警報】偵測到高強度 TCP SYN Flood 攻擊特徵！")
        elif rst_count > (syn_count * 0.5) and syn_count > 100:
            print("⚠️ 【警告】偵測到異常高比例 RST，疑似 Port Scan (Nmap -sS) 或防火牆阻斷！")
        else:
            print("✅ TCP 交握比例處於常態分佈範圍。")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("用法: python pcap_tcp_anomaly_analyzer.py <target.pcap>")
        sys.exit(1)
    analyze_pcap_with_tshark(sys.argv[1])
```

## ⚖️ 第四動：研判分水嶺——正常搶購高並發 vs 惡意 SYN Flood？

在電商促銷或重大活動上線時，伺服器也會湧入成千上萬的 SYN。你該如何區分是「真實用戶在搶購」還是「黑客在攻擊」？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 伺服器 TCP `SYN_RECV` 佇列滿載，外部連線超時率突破 20% 閾值，或 CPU 軟中斷過高。 |
| **Q2. 來源實體**（誰/哪個 IP 發起的？） | 檢視封包的 `ip.src`：是少數幾個公網 IP（固定來源），還是完全隨機、甚至包含私有 IP/未分配網段（偽造 IP 特徵）？ |
| **Q3. 目標對象**（被攻擊的對象是誰？） | 是特定提供 Web 服務的 80/443 Port，還是對伺服器全 Port (1-65535) 均勻亂撒（掃描行為）？ |
| **Q4. 失敗本質**（為什麼交握中斷？） | 是 Server 回了 SYN-ACK 但 Client 故意不理（惡意攻擊），還是 Client 的 SYN 壓根沒到 Server（網路中斷）？ |
| **Q5. 封包指紋**（封包有沒有異常特徵？） | 檢查惡意封包的 TCP Window Size、MSS、TTL。惡意工具生成的 SYN 往往有固定的 Window Size（如 65535、1024）且沒有 TCP Options（如 SACK, Window Scale）。 |
| **Q6. 攻擊成果**（伺服器是否已被癱瘓？） | 檢查伺服器 CPU 是否因軟中斷（ksoftirqd）飆高，正常業務請求是否已無法返回 HTTP 200。 |
| **Q7. 橫向波及**（周邊設備是否受害？） | 狀態檢測防火牆（Stateful Firewall）的連線狀態表（NAT/Conntrack Table）是否同步被撐爆？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 核心立即開啟 `tcp_syncookies`；2. 防火牆切換為 TCP Proxy 模式或下發 BGP Flowspec 清洗流量。 |

### 4.2 流量研判決策樹

```
[TCP 異常流量決策樹]
收到大量 SYN 封包與連線逾時告警？
 │
 ├── Q1: 是否有收到第三次交握的 ACK 封包？

 │    └── 完全沒有，伺服器卡在 SYN_RECV ➔ 進入 Q2
 │
 ├── Q2: 來源 IP 的分佈特徵為何？
 │    ├── 來源 IP 固定來自特定 1~5 個 IP ➔ 🔴 集中式 SYN 攻擊（直接在邊界防火牆 Drop 這些 IP）
 │    ├── 來源 IP 來自全球各地的真實家電/雲主機 ➔ 🔴 殭屍網路（Botnet SYN Flood，需 CDN/DDoS 清洗）
 │    └── 來源 IP 出現大量內網私有 IP (10.x, 192.168.x) 或不存在的廣播段 ➔ 🔴 IP 偽造（IP Spoofing，需啟用 uRPF）
 │
 └── Q3: 封包是否有完整的 TCP Options（SACK, MSS, Window Scale）？
      ├── 封包標頭齊全且參數多樣 ➔ 真實作業系統發出
      └── 封包極簡、長度固定 40/54 bytes、無任何 Options ➔ 🔴 攻擊工具（hping3 / Scapy 腳本偽造）
```

## 🛡️ 第五動：緩解阻斷與加固 SOP (Mitigation & Hardening)

當確認為惡意 SYN Flood 時，依據應變層級執行以下三道防線：

### 1. 第一道防線：緊急主機核心加固（Linux Kernel Sysctl）
在伺服器上立即執行以下指令，啟用 SYN Cookie 機制，使伺服器在不用分配半開記憶體佇列的情況下仍能驗證交握：

```bash
# 1. 強制啟用 SYN Cookies（核心不為半開連線分配記憶體，而是透過計算加密序號回傳）
sysctl -w net.ipv4.tcp_syncookies=1

# 2. 調大 SYN 半開連線佇列容量（預設通常只有 128 或 512，提升至 4096）
sysctl -w net.ipv4.tcp_max_syn_backlog=4096

# 3. 縮短 SYN-ACK 的重傳次數（預設重傳 5 次約 30 秒，降為 1 次以快速釋放連線）
sysctl -w net.ipv4.tcp_synack_retries=1

# 4. 永久生效寫入配置
echo "net.ipv4.tcp_syncookies = 1" >> /etc/sysctl.conf
echo "net.ipv4.tcp_max_syn_backlog = 4096" >> /etc/sysctl.conf
echo "net.ipv4.tcp_synack_retries = 1" >> /etc/sysctl.conf
sysctl -p
```

### 2. 第二道防線：主機防火牆限速丟包（iptables / nftables）
在伺服器邊界直接針對單一來源 IP 的 SYN 請求進行頻率限制：

```bash
# 針對特定 Port（如 80/443）限制每秒新建連線速率，超過部分丟棄
sudo iptables -A INPUT -p tcp --dport 443 --syn -m limit --limit 50/s --limit-burst 100 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 --syn -j DROP

# 丟棄無效的 TCP 旗標組合（畸形封包掃描）
sudo iptables -A INPUT -p tcp --tcp-flags ALL NONE -j DROP
sudo iptables -A INPUT -p tcp --tcp-flags ALL ALL -j DROP
```

### 3. 第三道防線：網路層防禦（Firewall / Anti-DDoS）
- **TCP SYN Proxy**：在硬體防火牆或雲端 WAF 開啟 SYN Proxy 功能，由防禦設備代替後端真實伺服器完成三向交握，確認收到合法 ACK 後才將連線放行至後端。
- **uRPF（反向路徑轉發檢查）**：在邊界路由器啟用 Strict uRPF，若封包來源 IP 的路由路徑不合理，直接在介面層丟棄，斬斷偽造 IP（IP Spoofing）的可能。

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能清楚回答，代表你已徹底掌握 TCP 鑑識核心：

- [ ] **Q1**：在 TCP 三向交握中，如果 Client 送出第一個 `SYN`（Seq = 1000），那麼 Server 回覆的 `SYN, ACK` 封包中，其 `Seq` 與 `Ack` 值在真實網路封包中分別代表什麼意義？
  > **解答要點**：`Seq` 代表伺服器端自己獨立隨機生成的初始序號（ISN_s），用於後續伺服器向客戶端傳送資料時的編號基礎；`Ack` 代表對客戶端 SYN 的確認號，數值嚴格等於 `Client_ISN + 1`（即 1001），表示伺服器成功收到客戶端的連線請求，並期待客戶端下一筆資料從序號 1001 開始發送。
- [ ] **Q2**：為什麼 SYN Flood 攻擊往往不需要塞爆企業的對外頻寬（例如頻寬佔用率僅 20%），卻能讓整台高規格伺服器完全無法提供網頁服務？其攻擊瓶頸到底卡在系統的哪裡？
  > **解答要點**：SYN Flood 攻擊的是伺服器作業系統核心的記憶體資源結構——半開連線佇列（SYN Backlog）。每當收到一個 SYN，核心就必須分配一塊 TCB（傳輸控制塊）記憶體並啟動定時器等待 ACK。當佇列被填滿後，核心便直接丟棄後續所有合法的 SYN 請求。因此即便頻寬仍有餘裕，連線握手已經被完全封死。
- [ ] **Q3**：在 Nmap 掃描中，`-sS`（SYN Stealth Scan）與 `-sT`（TCP Connect Scan）在封包交握層面的最大差異是什麼？為什麼藍隊分析師能一眼看出某台主機正在進行半開掃描？
  > **解答要點**：`-sT` 呼叫作業系統原生 `connect()` 系統調用，會完整走完三次交握並隨後發送 FIN 關閉，連線會被應用層（如 Nginx access.log）完整記錄；而 `-sS` 自行構造原始封包，在收到目標回覆 `SYN, ACK` 確認 Port 開啟後，立即主動發送 `RST` 撕毀連線，不建立應用層 Session。藍隊在封包中看到大量「剛收到 SYN-ACK 就立刻回彈 RST」的行為，即可判定為半開掃描。
- [ ] **Q4**：啟用 Linux 核心的 `tcp_syncookies = 1` 雖然能抵禦 SYN Flood，但它在底層會犧牲哪一個重要的 TCP 效能增強功能（提示：與 TCP Options 協商有關）？
  > **解答要點**：當 SYN Cookies 啟動且 SYN 佇列滿載時，核心不會分配記憶體記錄客戶端的 TCP Options（如大型視窗縮放 Window Scale、選擇性確認 SACK、時間戳 Timestamps 等），只能將極少數編碼資訊壓縮進 32-bit 的 SYN-ACK 初始序號中。這會導致該連線無法使用高頻寬延遲乘積（BDP）下的視窗擴展優化，在高輸送量長肥網路（LFN）環境下可能造成傳輸效能下降。
- [ ] **Q5**：在 Wireshark 中，你看到一連串通訊協定為 TCP 的封包，狀態顯示為 `[RST, ACK]`，且其序號剛好落在前一個正常封包的滑動視窗（Window）之內，但來源 MAC 位址卻是邊界防火牆而非伺服器本身。這在企業資安防禦中代表了什麼現象？
  > **解答要點**：這代表邊界入侵防禦系統（IPS/NGFW）觸發了深層封包檢測（DPI）規則（如偵測到惡意 SQLi 或違規傳輸），主動執行了「TCP Reset 注入阻斷（TCP Reset Injection）」。安全設備偽造了雙方的 IP 與符合目前 TCP 視窗內的合法序號，分別向客戶端與伺服器發送 RST 封包，強行且迅速地切斷當前危險連線。\n
