## 🧩 第一動：底層機制解剖——進程、服務與排程的底層真相

黑客可以竄改 `ps`、`top` 或 `netstat` 的輸出，但他們**無法輕易欺騙 Linux 核心原生維護的 `/proc` 虛擬檔案系統**。任何活著的進程，其底層真相都無所遁形於 `/proc` 之中。

### 1.1 `/proc/[pid]/` 核心進程鏡像解構

在 Linux 體系中，「一切皆檔案」。當一個進程被創建（經由 `fork` 與 `execve` 系統呼叫）時，核心會在 `/proc` 記憶體檔案系統下以其 PID 命名一個虛擬目錄。當懷疑某個進程是惡意程式時，**直接去 `/proc/[pid]/` 查驗真實身分**：

```
/proc/[pid]/
  ├── exe        : ★ 符號連結，直接指向硬碟上的「真實二進位執行檔」！（就算黑客改名為 [kworker]，此處仍暴露本體路徑）
  ├── cwd        : 符號連結，指向該進程當前的工作目錄（常為 /tmp, /dev/shm, /var/tmp）
  ├── cmdline    : 啟動該進程時傳入的「完整命令列參數」（以 null byte \0 分隔，非 argv 改寫後的表象）
  ├── environ    : 該進程運行時繼承的所有環境變數（常藏有被竊取的 API Key、C2 配置或 LD_PRELOAD 注入路徑）
  ├── fd/        : 目錄，列出該進程開啟的所有檔案描述符（包含網路 Socket 與正在讀寫的隱密檔案）
  ├── status     : 包含該進程的真實 UID/GID、PPID（父進程 ID）以及線程數
  └── maps / mem : 該進程的記憶體映射段（可用於記憶體取證與提取解密後的動態 Payload）
```

### 1.2 systemd 服務單元（Service & Timer）與啟動階層

現代 Linux 全面採用 `systemd` 作為 PID 1 的初始化系統。攻擊者常利用 `systemd.service` 與更隱蔽的 `systemd.timer`（定時器，功能類似 crontab 但更難被察覺）建立開機自啟或崩潰自動重啟的後門：

```
[黑客最常植入的 3 大 Systemd 目錄]
1. /etc/systemd/system/           : ★ 系統管理員手動安裝的服務（優先級最高，黑客首選藏匿點！）
2. /run/systemd/system/          : 運行時動態服務（重開機自動消失，黑客用於記憶體暫存逃避磁碟取證）
3. /lib/systemd/system/ (或 /usr): 系統預設套件安裝的服務（黑客常在此竄改合法服務如 sshd.service）

[典型惡意 Service 檔案結構範例]
[Unit]
Description=System Core Diagnostic Service   <-- 偽裝成官方核心診斷服務
After=network.target                         <-- 網路連線建立後自動觸發

[Service]
Type=simple
ExecStart=/dev/shm/.systemd-daemon           <-- ★ 真實執行的惡意木馬路徑！
Restart=always                               <-- ★ 殺掉立刻重啟！（無限復活之謎）
RestartSec=3s

[Install]
WantedBy=multi-user.target                   <-- 設定開機隨系統多用戶模式自動啟動
```

### 1.3 Crontab 的 6 大隱秘藏匿點

許多資安分析師以為排程只存在於目前使用者的 `crontab -l` 之中，這導致了大量的後門漏網。Linux 排程引擎實際讀取的是 **6 大排程路徑**：

```
[Linux 排程完整掃描面]
├── 1. /var/spool/cron/crontabs/ (或 /var/spool/cron/) : 各使用者的私有排程（crontab -l 查到的位置）
├── 2. /etc/crontab                                  : 系統全域主排程檔（需指定執行使用者帳號）
├── 3. /etc/cron.d/                                  : ★ 軟體獨立排程目錄（黑客最愛在這裡放看似官方的自定義配置）
├── 4. /etc/cron.hourly/                             : 每小時自動執行的腳本目錄（黑客常放置高頻拉取木馬）
├── 5. /etc/cron.daily/                              : 每天自動執行的維護腳本目錄
└── 6. /etc/cron.weekly/ & /etc/cron.monthly/        : 每週/每月執行的長週期後門藏匿點
```

### 1.4 LD_PRELOAD 用戶態 Rootkit 隱藏機制

攻擊者若取得 root 權限，可在 `/etc/ld.so.preload` 中填入惡意動態庫（如 `libprocesshider.so`）。當系統中的 `ps`、`top`、`netstat` 呼叫 libc 的 `readdir()` 或 `fopen()` 讀取 `/proc` 時，惡意庫會提前攔截（Hook）該函式，自動過濾掉惡意進程的 PID 與連線，使管理員眼前一片祥和。

### 3.1 戳破進程偽裝——深入 `/proc` 查驗

#### 步驟 1：找出在臨時可寫目錄中運行的可疑進程
```bash
# 檢查有哪些進程的執行檔位於 /tmp, /dev/shm 或 /var/tmp
ls -l /proc/*/exe 2>/dev/null | grep -E "(tmp|dev/shm|var/tmp)"
```

#### 步驟 2：揪出已被刪除但仍在記憶體中狂跑的幽靈進程
```bash
# 篩選帶有 (deleted) 標記的執行中檔案（黑客反取證常見特徵）
ls -l /proc/*/exe 2>/dev/null | grep "(deleted)"
```

#### 步驟 3：神仙難救的「進程逆向還原術」
若黑客已經把 `/dev/shm/.miner` 刪除了，你該如何拿到樣本？**從記憶體直接拷貝還原**：
```bash
# 只要進程還在運行，直接從 /proc/[pid]/exe 複製出來即可完整復原惡意執行檔！
sudo cp /proc/18422/exe /root/recovered_malware.bin
chmod 700 /root/recovered_malware.bin
sha256sum /root/recovered_malware.bin  # 計算雜湊進行威脅情資比對
```

#### 步驟 4：戳破 `[kworker]` 核心線程偽裝
```bash
# 真正的 Linux 核心線程，其 PPID（母進程）必為 2 (kthreadd)，且 /proc/[pid]/exe 為空
# 找出所有名稱帶中括號但 PPID 不為 2 的冒牌貨！
ps -ef | awk '$3 != 2 && $8 ~ /^\[.*\]$/ {print "🚨 偽裝進程: PID " $2 ", 命令: " $8}'
```

#### 步驟 5：檢查 LD_PRELOAD 用戶態劫持
```bash
# 檢查是否存在全域預載入庫
cat /etc/ld.so.preload 2>/dev/null

# 檢查進程環境變數是否自帶 LD_PRELOAD
strings /proc/*/environ 2>/dev/null | grep LD_PRELOAD
```

### 3.2 systemd 惡意服務單元與定時器全面清查

#### 步驟 1：列出所有開機自啟動（enabled）的非官方服務與定時器
```bash
# 查看所有已啟用的服務與定時器，排除系統核心與常見官方套件
systemctl list-unit-files --type=service,timer --state=enabled | grep -Ev "(systemd|kernel|apparmor|ufw|cron)"
```

```bash
# 列出所有排程定時器，注意其觸發間隔與背後關聯的 .service
```

```bash
# 檢查最容易被藏後門的目錄，按時間排序
find /etc/systemd/system/ /lib/systemd/system/ -name "*.service" -o -name "*.timer" -mtime -7 -ls
```

#### 步驟 4：徹底停用並粉碎惡意 systemd 服務

### 3.4 藍隊現場自動化巡檢 Python 腳本

將上述檢測邏輯封裝為一鍵執行的取證腳本 `linux_persistence_audit.py`：

```python
#!/usr/bin/env python3
"""
Linux 進程與持久化自動化稽核工具 (linux_persistence_audit.py)
功能：一鍵清查 /proc 異常執行路徑、已刪除二進位檔、systemd timers/services、Crontab 與 LD_PRELOAD
"""
import os
import glob
import re

def check_proc_anomalies():
    print("=== [1] 稽核 /proc 異常進程 ===")
    for exe_path in glob.glob("/proc/[0-9]*/exe"):
        pid = exe_path.split("/")[2]
        try:
            target = os.readlink(exe_path)
            # 檢查臨時目錄
            if re.search(r"/(tmp|dev/shm|var/tmp)/", target):
                print(f"🚨 [可疑路徑執行] PID: {pid} -> {target}")
            # 檢查已刪除二進位檔
            if "(deleted)" in target:
                print(f"⚠️ [記憶體幽靈執行 (deleted)] PID: {pid} -> {target}")
        except (PermissionError, FileNotFoundError):
            continue

def check_ld_preload():
    print("\n=== [2] 稽核動態庫預載入劫持 (LD_PRELOAD) ===")
    preload_file = "/etc/ld.so.preload"
    if os.path.exists(preload_file):
        try:
            with open(preload_file, "r") as f:
                content = f.read().strip()
                if content:
                    print(f"🚨 警告：發現 /etc/ld.so.preload 存在內容！\n{content}")
                else:
                    print("✅ /etc/ld.so.preload 為空。")
        except Exception as e:
            print(f"讀取失敗: {e}")
    else:
        print("✅ 未發現 /etc/ld.so.preload 檔案。")

def check_crontabs():
    print("\n=== [3] 稽核 6 大 Crontab 目錄 ===")
    cron_dirs = ["/etc/cron.d", "/etc/cron.hourly", "/etc/cron.daily", "/var/spool/cron/crontabs"]
    suspicious_keywords = [r"curl", r"wget", r"base64", r"sh\s", r"bash\s", r"/tmp/", r"/dev/shm/"]
    
    for cdir in cron_dirs:
        if not os.path.exists(cdir):
            continue
        for root, _, files in os.walk(cdir):
            for file in files:
                filepath = os.path.join(root, file)
                try:
                    with open(filepath, "r", errors="ignore") as f:
                        for line_no, line in enumerate(f, 1):
                            line = line.strip()
                            if line.startswith("#") or not line:
                                continue
                            for kw in suspicious_keywords:
                                if re.search(kw, line, re.IGNORECASE):
                                    print(f"🚨 [可疑排程] {filepath}:{line_no} -> {line}")
                                    break
                except Exception:
                    continue

if __name__ == "__main__":
    print("🛡️ Linux 系統服務與進程安全稽核啟動...")
    check_proc_anomalies()
    check_ld_preload()
    check_crontabs()
    print("\n[+] 稽核完成。")
```

## ⚖️ 第四動：研判分水嶺——正常業務排程 vs 惡意持久化？

在 Linux 伺服器中，備份工具（如 `rsync`、資料庫備份）、日誌輪替（`logrotate`）也會出現在排程中。你該如何一眼看穿？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | CPU 負載突破異常閾值、向未知境外 IP 建立持續長連線，或排程檔案/服務單元被非預期寫入。 |
| **Q2. 來源路徑**（執行檔存放在哪裡？） | 是正規系統路徑（`/usr/bin`, `/usr/sbin`），還是臨時目錄（`/tmp`, `/dev/shm`）、隱藏目錄（如 `/var/tmp/.hide/`）？ |

| **Q4. 網路連線**（該進程是否有異常外聯？） | 執行 `lsof -i -P -n \| grep <PID>`：是否有連往礦池常見 Port（3333, 4444, 5555）或未知境外 C2 IP？ |

## 🛡️ 第五動：連根拔除與加固 SOP (Mitigation & Hardening)

當面對具有「無限復活」特徵的頑固惡意進程時，錯誤的處置順序會導致木馬持續死灰復燃。請嚴格執行以下 **「四步封印法」**：

### 1. 第一步：先「凍結」而非「殺死」（SIGSTOP 魔法）
如果你直接下 `kill -9`，守護進程會在 0.1 秒內偵測到進程死亡並重新生成一個新 PID，導致你疲於奔命。正確做法是將其進程凍結在記憶體中：
```bash
# 發送 SIGSTOP 訊號，強制暫停該進程所有 CPU 與網路活動，但保留其 PID（守護進程以為它還活著！）
sudo kill -STOP <PID>
```

### 2. 第二步：斬斷所有自啟動根基（Disarm Launchers）
在木馬被凍結的時間窗口內，迅速清除所有自啟動項：
```bash
# 1. 註解或刪除 Crontab 惡意項目
sudo rm -f /etc/cron.d/malicious_cron /var/spool/cron/crontabs/<user>

# 2. 拔除 systemd 惡意服務與定時器
sudo systemctl disable --now badservice.service 2>/dev/null
sudo systemctl disable --now badtimer.timer 2>/dev/null
sudo rm -f /etc/systemd/system/badservice.service /etc/systemd/system/badtimer.timer
sudo systemctl daemon-reload
```

### 3. 第三步：消滅進程與執行本體（Eradicate Binary）
此時再將被凍結的進程徹底殺死，並刪除實體檔案：
```bash
# 徹底殺死凍結的進程
sudo kill -9 <PID>

# 刪除實體二進位檔案
sudo rm -f /path/to/malicious_binary
```

### 4. 第四步：設定系統檔案不可變屬性（Immutable Flag）
為了防止黑客透過其他隱密通道再次篡改 Crontab 或注入預載入庫，使用 `chattr +i` 加鎖：
```bash
# 將核心排程檔案與預載入檔案設為「連 Root 也無法修改/刪除」的鎖定狀態
sudo chattr +i /etc/crontab /etc/ld.so.preload 2>/dev/null
```

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能清楚回答，代表你已具備處理 Linux 惡意程式現場應變的能力：

- [ ] **Q1**：如果一個進程在 `ps aux` 中顯示為 `[kworker/0:0H]`，你該如何用 `/proc` 檔案系統快速判定它到底是真的 Linux 核心線程，還是黑客惡意偽裝的用戶態程式？
  > **解答要點**：真正的 Linux 核心線程是由核心線程調度器直接派生的，其父進程 PID（PPID）必定為 2（即 `kthreadd`），且其在磁碟上沒有實體二進位檔案，因此 `/proc/[pid]/exe` 軟連結為空或指向空。反之，若偽裝進程的 PPID 非 2，且 `/proc/[pid]/exe` 指向 `/tmp` 或任何硬碟路徑，即為冒牌惡意進程。
- [ ] **Q2**：為什麼黑客把位於 `/tmp/.malware` 的二進位檔案執行起來後立刻執行 `rm -f /tmp/.malware`？身為藍隊取證人員，你在磁碟上已經找不到這個檔案了，該如何從系統中完整提取出這個惡意程式二進位檔？
  > **解答要點**：黑客刪除檔案是為了對抗基於檔案系統的防毒軟體掃描與靜態取證。在 Linux 核心中，只要進程尚未終止，檔案的 inode 與資料區塊仍被核心保留在記憶體中。調查員可直接執行 `cp /proc/[pid]/exe /root/recovered_sample`，直接將核心維護的記憶體映射鏡像拷貝出來還原原始可執行 ELF 檔案。
- [ ] **Q3**：在 systemd 服務單元中，`Restart=always` 與 `ExecStartPre=` 經常被黑客用來做什麼？如果你只刪除了二進位檔案卻沒執行 `systemctl daemon-reload`，會發生什麼事？
  > **解答要點**：`Restart=always` 讓進程在崩潰或被 SIGKILL 殺死後數秒內自動由 systemd 重新啟動（無限復活）；`ExecStartPre=` 常用於在主木馬啟動前先執行混淆腳本、關閉防火牆或殺死競爭對手的挖礦進程。若只刪除二進位檔案而未執行 `daemon-reload`，systemd 仍持有記憶體配置快取，會持續嘗試重啟該服務並在系統日誌狂吐報錯，且若攻擊者透過其他途徑再次回填檔案，服務又會立刻拉起。
- [ ] **Q4**：面對具備「雙進程守護（A 死了 B 重啟 A，B 死了 A 重啟 B）」特徵的頑固木馬，為什麼下達 `kill -9` 往往無濟於事？在指令層面你該如何破解這種死鎖局面？
  > **解答要點**：單獨執行 `kill -9` 會瞬間引發守護進程的信號捕捉或輪詢機制，0.1 秒內重新派生新子進程。破解死鎖的核心是「先凍結後擊殺」：同時或依序對進程 A 與 B 發送 `kill -STOP <PID>`，讓兩個進程進入暫停狀態失去執行能力但依然保留 PID，破除輪詢判定；接著清除磁碟上的二進位檔與排程，最後再送 `kill -9` 擊斃。
- [ ] **Q5**：黑客若在 Linux 系統中配置了 `/etc/ld.so.preload`，其在作業系統底層的作用是什麼？這為什麼會導致你打 `ls`、`ps`、`netstat` 看到的都是被過濾過的「假象」？
  > **解答要點**：`/etc/ld.so.preload` 是動態連結器（ld.so）的全域預載入機制，所有動態編譯的執行檔在啟動時都會優先載入該檔案指定的動態庫。用戶態 Rootkit 會在此攔截 glibc 函式（如 `readdir`、`stat`、`fopen`），在返回目錄內容給 `ps` 或 `ls` 時，過濾掉特定名稱或特徵的進程與檔案，讓管理員看到被篡改過的虛假狀態。可使用靜態編譯的工具（如 `busybox`）或檢查環境變數繞過該劫持。\n
