## 🧩 第一動：底層機制解剖——NTLM 與 Kerberos 的物理世界

在 Windows Active Directory 網域中，身分驗證永遠圍繞著兩大協定展開：**較老的 NTLM（基於挑戰/回應）** 與 **現代的 Kerberos（基於金鑰分發中心 KDC 票證）**。

### 1.1 NTLM 核心機制：三向挑戰-回應 (Challenge-Response)

NTLM 不需要傳輸明文密碼，但它的致命弱點是：**客戶端是用密碼的 NTLM Hash 來計算回應值的！** 這意味著只要拿到 Hash，就等同於拿到了密碼（Pass-the-Hash 的物理基礎）。

```
[Client (客戶端)]                                     [Server (伺服端)]                                    [Domain Controller (DC)]
   │                                                     │                                                    │
   │ 1. Type 1 (NEGOTIATE_MESSAGE)                       │                                                    │
   │    客戶端宣告支援的 NTLM 版本與安全選項             │                                                    │
   │ ──────────────────────────────────────────────────> │                                                    │
   │                                                     │                                                    │
   │ 2. Type 2 (CHALLENGE_MESSAGE)                       │                                                    │
   │    伺服器生成一個 8-byte 隨機數 (Server Challenge)  │                                                    │
   │ <────────────────────────────────────────────────── │                                                    │
   │                                                     │                                                    │
   │ 3. Type 3 (AUTHENTICATE_MESSAGE)                    │ 4. 轉發驗證 (Netlogon 協議)                        │
   │    客戶端用自身 NTLM Hash 加密 Challenge 並回傳     │    伺服器將 Challenge 與 Response 轉發給 DC        │
   │ ──────────────────────────────────────────────────> │ ─────────────────────────────────────────────────> │
   │                                                     │                                                    │
   │                                                     │ 5. DC 比對資料庫，驗證成功回覆 OK                  │
   │ 6. 連線建立成功！                                   │ <───────────────────────────────────────────────── │
   │ <────────────────────────────────────────────────── │                                                    │
```

### 1.2 Kerberos 核心機制：六步票證分發 (Ticket-Based) 與 PAC 驗證

Kerberos 依賴網域控制站（DC）上的 **KDC（Key Distribution Center）**。它不直接在連線雙方驗證 Hash，而是透過「**買票上車**」的機制：

```
[Client]                                                    [KDC (Domain Controller)]                       [Target Server]
   │                                                                    │                                          │
   │ 1. [AS-REQ]  : 客戶端用自身密碼 Hash 加密時間戳請求 TGT            │                                          │
   │ ────────────> (身分驗證服務 AS)                                    │                                          │
   │ 2. [AS-REP]  : KDC 回傳 TGT (以 krbtgt Hash 加密) + Session Key    │                                          │
   │ <────────────                                                      │                                          │
   │                                                                    │                                          │
   │ 3. [TGS-REQ] : 客戶端出示 TGT，請求存取目標伺服器的 TGS 服務票證     │                                          │
   │ ────────────> (票證授權服務 TGS)                                   │                                          │
   │ 4. [TGS-REP] : KDC 回傳 TGS 票證 (以目標服務 SPN Hash 加密)         │                                          │
   │ <────────────                                                      │                                          │
   │                                                                    │                                          │
   │ 5. [AP-REQ]  : 客戶端拿著 TGS 票證向目標伺服器發起存取請求 ─────────────────────────────────────────────────> │
   │ 6. [AP-REP]  : 目標伺服器解密確認合法，連線建立！ (可選雙向驗證) <─────────────────────────────────────────────── │
```

- **PAC（Privilege Attribute Certificate）**：微軟在 Kerberos 票證中擴充的核心欄位，包含使用者的 SID、所屬群組權限等。KDC 會使用自身的金鑰對 PAC 簽名，防止攻擊者篡改權限。
- **Golden Ticket（黃金票證）**：攻擊者一旦取得 `krbtgt` 帳號的 NTLM Hash，就能自行偽造任意使用者的 TGT（包含將自己加入 Domain Admins 的 PAC），在網域內永久潛伏。
- **Silver Ticket（白銀票證）**：攻擊者取得目標特定服務帳號（如 MSSQL 或 CIFS）的 Hash，直接偽造該服務的 TGS 票證，繞過 KDC 進行存取。

### 1.3 致命的分水嶺：Windows 何時用 Kerberos？何時降級為 NTLM？

理解降級機制是藍隊抓出異常連線的關鍵：

```
[Windows 身分驗證決策流 (SPNEGO)]
發起網路連線請求？
 │
 ├── 存取目標是透過「IP 位址」（例如 \192.168.1.50\share）？
 │    └── ★ 必然降級為 NTLM！因為 Kerberos 無法對純 IP 尋找 SPN（服務主體名稱）！
 │
 ├── 存取目標主機「不屬於同一個 Active Directory 網域」且無樹系信任？
 │    └── 降級為 NTLM！
 │
 ├── 目標主機的 SPN 註冊重複或遺失？
 │    └── Kerberos 請求失敗（KDC_ERR_S_PRINCIPAL_UNKNOWN），自動降級為 NTLM！
 │
 └── 存取目標為完整主機名稱（如 \srv-finance-01.corp.local），且具備正常 SPN？
      └── 🟢 成功走標準 Kerberos 驗證！
```

| :--- | :--- | :--- |

## 💻 第三動：現場追兇——Wireshark 封包與 Event Log 實戰

身為現場調查員，你必須掌握在封包與伺服器日誌中精確過濾身分驗證軌跡的技能。

### 3.1 Wireshark 封包鑑識過濾器

在抓取到的內網流量 PCAP 中，輸入以下語法快速過濾：

#### 語法 1：篩選出所有的 NTLM 驗證封包（尋找潛在橫向移動）
```wireshark
# 篩選包含 NTLMSSP 協定的所有封包
ntlmssp
```

#### 語法 2：定位 NTLM Type 3 認證封包（提取使用者名稱與工作站）
```wireshark
# 篩選 NTLM Type 3 (AUTHENTICATE_MESSAGE)
ntlmssp.messagetype == 0x00000003
```

#### 語法 3：過濾 Kerberos 錯誤訊息（尋找降級原因）
```wireshark
# 篩選 Kerberos KRB-ERROR 封包（例如找不到 SPN 的錯誤 KDC_ERR_S_PRINCIPAL_UNKNOWN = 7）
kerberos.msg.type == 30
```

#### 語法 4：抓出使用弱加密 RC4-HMAC (0x17) 的 Kerberos 請求
```wireshark
# 篩選請求加密類型為 rc4-hmac 的 Kerberos 票證
kerberos.etype == 23
```

### 3.2 網域控制站核心 Event ID 深度鑑識（PowerShell 自動化審計）

在 DC 上排查身分驗證，重點看這五大事件：
- **4768**：Kerberos TGT 請求（第一階段，AS 驗證）
- **4769**：Kerberos TGS 服務票證請求（第二階段，TGS 驗證）
- **4771**：Kerberos 預先驗證失敗（Pre-Authentication Failed，常見爆破或帳號密碼錯誤）
- **4624**：登入成功（檢視 `AuthenticationPackageName` 是 NTLM 還是 Kerberos）
- **4625**：登入失敗（記錄爆破嘗試與失敗狀態碼如 `0xC000006A`）

#### 自動化 PowerShell 腳本：`ad_auth_anomaly_hunter.ps1`
```powershell
<#
.SYNOPSIS
    Active Directory 身分驗證異常與 NTLM 流量盤點工具 (ad_auth_anomaly_hunter.ps1)
#>
Write-Host "=== [1] 盤點最近 4 小時使用 NTLM 驗證的登入 (Event 4624) ===" -ForegroundColor Cyan

$NtlmEvents = Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4624
    StartTime = (Get-Date).AddHours(-4)
} | Where-Object {
    $xml = [xml]$_.ToXml()
    $pkg = ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'AuthenticationPackageName' }).'#text'
    $pkg -match "NTLM"
}

$NtlmSummary = $NtlmEvents | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        User        = ($data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
        Workstation = ($data | Where-Object { $_.Name -eq 'WorkstationName' }).'#text'
        SourceIp    = ($data | Where-Object { $_.Name -eq 'IpAddress' }).'#text'
        LogonType   = ($data | Where-Object { $_.Name -eq 'LogonType' }).'#text'
        LmPackage   = ($data | Where-Object { $_.Name -eq 'LmPackageName' }).'#text'
    }
}
$NtlmSummary | Format-Table -AutoSize

Write-Host "`n=== [2] 獵殺異常高頻 TGS 請求 (潛在 Kerberoasting - Event 4769) ===" -ForegroundColor Cyan
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4769; StartTime=(Get-Date).AddHours(-2)} | 
ForEach-Object {
    $xml = [xml]$_.ToXml()
    ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
} | Where-Object { $_ -notlike "*$" } |
Group-Object | Sort-Object Count -Descending | Select-Object -First 5 Count, Name | Format-Table
```

## ⚖️ 第四動：研判分水嶺——正常業務相容 vs 惡意 PtH 攻擊？

在企業環境中，NTLM 依然大量存在。你該如何區分是老舊業務系統，還是黑客正在橫向移動？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 網域控制站偵測到高權限網域管理員（Domain Admins）帳號透過 NTLM 發起登入請求。 |
| **Q2. 來源主體**（連線是由哪台主機發起的？） | 發起端是已知的舊版 Linux 印表機/掃描器、老舊 ERP 伺服器，還是突然出現的一般辦公終端？ |
| **Q3. 存取目標**（目標伺服器是什麼？） | 連線的目標是核心資料庫、網域控制站，還是一般共享檔案夾？ |
| **Q4. 連線方式**（是透過名稱還是 IP 連線？） | 調查來源電腦的連線指令：使用者是輸入了 `\10.0.0.5`（因 IP 直連被動降級），還是輸入 `\server.domain` 卻異常降級？ |
| **Q5. 帳號層級**（參與驗證的帳號層級？） | 涉及的帳號是一般普通帳戶，還是核心管理員（DA）？**管理員帳號絕不應在一般工作站上產生 NTLM 流量！** |
| **Q6. 密碼協定**（使用的 NTLM 版本？） | 檢視 `LmPackageName`：是相對安全的 NTLMv2，還是極度危險、早已被破解的 NTLMv1？ |
| **Q7. 橫向連鎖**（是否有連續跳板特徵？） | 該來源主機在成功登入該目標後，是否在 5 分鐘內又以該目標主機為跳板，向第三台主機發起新的登入？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 若為管理員帳號被 PtH：立刻切斷該主機連線，於 AD 強制重置該管理員密碼；2. 若為業務需要：建立 SPN 並推動 Kerberos 化。 |

## 🛡️ 第五動：收斂加固 SOP (Mitigation & Hardening)

要徹底杜絕 Pass-the-Hash 與 NTLM Relay，必須採取「**先審計、後限制、防高權限**」的三步收斂策略：

### 1. 第一步：開啟全網 NTLM 稽核模式（Audit Only，絕不直接盲禁！）
透過 GPO（群組原則）下發稽核策略，先收集所有仍在跑 NTLM 的舊設備清單：
```
電腦設定 ➔ Windows 設定 ➔ 安全性設定 ➔ 本機原則 ➔ 安全性選項
• 網路安全性: 限制 NTLM: 此網域中的 NTLM 驗證 ➔ 設定為【全部稽核】
• 網路安全性: 限制 NTLM: 稽核此網域中的連入 NTLM 流量 ➔ 設定為【啟用所有帳戶的稽核】
```
> 💡 設定後，所有 NTLM 流量會被寫入 `Applications and Services Logs/Microsoft/Windows/NTLM/Operational`，依據此日誌建立白名單。

### 2. 第二步：將高權限管理員加入「Protected Users」群組
Windows Server 2012 R2 以上內建安全神兵 **Protected Users** 群組：
- 加入該群組的帳號：**作業系統強制禁止使用 NTLM 驗證**！
- 不會在記憶體中快取 NTLM Hash，就算機器被 Dump 也拿不到 Hash，從根本上免疫 Pass-the-Hash 攻擊！
- Kerberos 不再使用弱加密 RC4，強制使用 AES-128/256。

### 3. 第三步：強制啟用全網 SMB 簽章（SMB Signing）
徹底終結 NTLM Relay（中繼攻擊）的核心配置：
```
• Microsoft 網路伺服器: 數位簽章伺服器通訊 (永遠) ➔ 設定為【已啟用】
• Microsoft 網路用戶端: 數位簽章用戶端通訊 (永遠) ➔ 設定為【已啟用】
```

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能清楚回答，代表你已徹底打通 Windows 身分驗證核心架構：

- [ ] **Q1**：為什麼在 Windows 內網中，只要攻擊者拿到了某帳號的「NTLM Hash」，就算完全不知道該帳號的明文密碼，也一樣能直接透過 SMB/WMI 登入其他電腦（Pass-the-Hash 原理）？
  > **解答要點**：因為 NTLM 協議在設計時，Type 3（AUTHENTICATE_MESSAGE）訊息計算回應值的輸入參數，就是使用該使用者的 NTLM Hash 對伺服器發出的 Challenge 進行加密運算。在整個驗證協定中，伺服器從不需要明文密碼，而是拿客戶端回傳的密文與自己算出的密文比對。因此 NTLM Hash 本質上就等同於明文密碼（Equivalent to Password），攻擊者直接傳入 Hash 即可完成交握。
- [ ] **Q2**：為什麼在 Windows 檔案總管中輸入 `\192.168.1.100\c$` 會走 NTLM 驗證，而輸入 `\fileserver.corp.local\c$` 卻能走 Kerberos 驗證？其底層判斷條件是什麼？
  > **解答要點**：Kerberos 協商的核心依賴「服務主體名稱（SPN, Service Principal Name）」向 KDC 索取特定服務的票證。SPN 必須與 Active Directory 中的電腦帳號或使用者帳號關聯（如 `cifs/fileserver.corp.local`）。由於 IP 位址不是有效的 Active Directory 物件屬性，Windows 安全機制無法為純 IP 構造有效的 SPN 查詢，SPNEGO 機制判定無法發起 Kerberos 票證請求，因此會自動回退降級為 NTLM 挑戰/回應機制。
- [ ] **Q3**：在 Kerberos 票證分發體系中，**krbtgt 帳號** 的密碼 Hash 扮演了什麼關鍵角色？如果攻擊者拿到了 krbtgt 的 Hash，會造成什麼毀滅性後果（提示：Golden Ticket）？
  > **解答要點**：`krbtgt` 帳號是網域金鑰分發中心（KDC）的專屬帳號。所有向客戶端頒發的 TGT（認證票證）都是使用 `krbtgt` 的密碼 Hash 進行對稱加密與簽名保護的。若攻擊者取得該 Hash，即可在本地任意偽造 TGT（黃金票證），自行設定任意使用者身分、有效期限以及特權群組 SID（如 Domain Admins 512），KDC 收到後無法辨識真偽，攻擊者將獲得網域內完全不可逆的最高控制權。
- [ ] **Q4**：為什麼許多企業在嘗試禁用 NTLM 時會引發大規模災情？正確且無痛收斂全網 NTLM 流量的標準 GPO 實施步驟應該是什麼？
  > **解答要點**：因為企業內往往存在大量老舊網路印表機、不支援 Kerberos 的 NAS 儲存設備、多品牌 ERP 或跨非信任網域的系統，直接禁用會導致這些系統連線即刻中斷。正確步驟是「先稽核後收斂」：第一步在 GPO 中將「限制 NTLM」設定為【全部稽核（Audit All）】，透過 Event Log 4624/NTLM 營運日誌收集持續運行 NTLM 的設備清單；第二步針對這些設備修復 SPN、配置 Kerberos 或設置 GPO 白名單例外；第三步才逐步開啟限制原則。
- [ ] **Q5**：微軟在 Active Directory 中引入的 **Protected Users（受保護的使用者）** 安全群組，在底層身分驗證層面施加了哪兩項最強力的安全限制？
  > **解答要點**：第一，**徹底停用 NTLM 驗證**：加入該群組的成員在任何情況下均無法使用 NTLM 進行身分驗證，系統不再快取該帳號的 NTLM Hash，即便攻擊者執行記憶體 Dump 也無法取得憑證；第二，**強化 Kerberos 加密**：禁止使用老舊的 RC4-HMAC 加密套件，強制僅能使用 AES 加密，且其 TGT 票證生命週期從預設的 10 小時縮短至 4 小時且無法自動更新，有效抵禦 Pass-the-Hash 與 Kerberoasting。\n
