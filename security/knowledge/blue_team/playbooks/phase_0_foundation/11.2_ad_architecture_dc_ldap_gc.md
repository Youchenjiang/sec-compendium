> 週四下午 14:10，企業內部跨國視訊會議進行中，突然多個海外分公司的員工回報：「無法存取總部的檔案伺服器，甚至無法登入電腦，提示找不到登入伺服器！」  
> 
> 網管工程師檢查各站台的 VPN 隧道，發現網路全部暢通。但一查網域控制站（DC）的事件日誌，發現大量 **Event ID 2088（DNS 名稱解析導致複寫中斷）** 與 **Event ID 13508（檔案複寫失敗）**。總部 DC 的 CPU 被一個未知的進程發起的大量 `TCP 389` (LDAP) 與 `TCP 3268` (Global Catalog) 搜尋請求徹底灌爆！  
> 
> 資安分析師深入排查發現，攻擊者在一台被植入後門的內網主機上，使用 BloodHound / SharpHound 正在發起每秒數萬次的 LDAP 搜尋，全面枚舉整個網域的所有使用者、群組巢狀關聯、以及跨樹系的信任關係（Domain Trust）！  
> 
> 這是典型的 **AD 網域大面積偵察（Active Directory Reconnaissance）**！  
> 攻擊者是如何利用 LDAP 迅速畫出通往「Domain Admins」的最短攻擊路徑？全域編錄（GC）與網域信任關係（Trust Relationship）在被攻破時，又是如何被黑客當成跨分公司橫向擴散的高速公路？
>
> **本手冊的使命**：帶你解構 Active Directory 的神經中樞，看穿網域控制站（DC）、FSMO 五大角色、LDAP 查詢樹、全局編錄（GC）與樹系信任（Forest Trust）的底層架構，掌握使用 BloodHound / LDAP 偵察的特徵日誌，並運用精準指令進行網域架構健康診斷、自動化偵察獵捕與異常枚舉防禦。

## 🧩 第一動：底層架構解剖——Active Directory 的物理骨架

Active Directory 不只是一台 Windows 伺服器，它是整個企業身分驗證的分散式資料庫體系。

### 1.1 `ntds.dit` 資料庫的三大核心目錄分割區 (Directory Partitions)

所有的使用者、密碼雜湊、電腦、群組資訊，都存放在 DC 的 `%SystemRoot%\NTDS\ntds.dit` 檔案中。該資料庫由三層邏輯分割區構成：

```
[Active Directory 資料庫 (ntds.dit)]
  ├── 1. 網域分割區 (Domain Partition)
  │      • 內容：本網域內所有的具體物件（Users, Computers, Groups, OUs）。
  │      • 複寫範圍：僅在「同一個網域」內的所有 DC 之間相互同步。
  ├── 2. 設定分割區 (Configuration Partition)
  │      • 內容：全樹系的物理架構拓撲（站台 Sites, 站台連結, 服務資訊）。
  │      • 複寫範圍：複寫給「全樹系（Forest）」中的每一台 DC。
  └── 3. 架構分割區 (Schema Partition)
         • 內容：定義所有物件的類別（Class）與屬性（Attribute）（AD 物件的藍圖）。
         • 複寫範圍：複寫給全樹系的每一台 DC（整個樹系共享一套 Schema）。
```

### 1.2 FSMO（彈性單一主機操作）五大角色職能與資安意義

雖然 AD 大多數資料採多主機複寫（Multi-Master），但有 5 個關鍵角色必須是唯一的：
1. **Schema Master（樹系唯一）**：掌控 AD 綱要藍圖的修改，被黑客奪取可能被植入隱密屬性。
2. **Domain Naming Master（樹系唯一）**：掌控新網域的加入或刪除。
3. **PDC Emulator（網域唯一，最核心！）**：掌控全網域時間同步（Kerberos 核心依賴）、密碼修改即時同步、帳號鎖定判定與 GPO 編輯核心。
4. **RID Master（網域唯一）**：分配 SID 中的相對識別碼池（RID Pool）。
5. **Infrastructure Master（網域唯一）**：負責跨網域物件群組成員的更新。

### 1.3 LDAP、LDAPS 與全域編錄（GC）的通訊埠角色分工

在分析網路流量或配置防火牆時，藍隊必須對以下通訊埠刻骨銘心：

```
[Client] ─────────────────────────────────────────────> [Domain Controller]
            TCP 389  : 標準 LDAP (明文！可被中間人監聽或中繼！)
            TCP 636  : LDAPS (基於 TLS 加密的 LDAP)
            TCP 3268 : 全局編錄 (Global Catalog, GC - 明文)
            TCP 3269 : 全局編錄 (GC - 加密 SSL)

【全局編錄 (Global Catalog) 的特殊存在】：
• 正常 LDAP (389) 只能查詢「當前網域」的物件。
• 如果大型跨國企業有多個子網域（如 us.corp, eu.corp），當使用者登入需要驗證通用群組（Universal Group）或搜尋跨國同仁時，必須存取 GC (3268)！
• GC 存放了全樹系所有網域物件的「屬性子集（Partial Attribute Set）」。
```

### 1.4 網域信任關係（Domain Trust）與票證穿越

當總公司收購子公司、或總部與海外建立跨網域協作時，依賴「信任關係」來允許跨域存取：

```
[Domain A (總公司: corp.local)]                       [Domain B (子公司: sub.local)]
          │                                                         │
          └─────────────────── 雙向可轉遞信任 ───────────────────────┘
                               (Two-way Transitive Trust)
```
- **單向信任 vs 雙向信任**：A 信任 B，代表 B 的員工可以存取 A 的資源，但反之不行。
- **信任穿越（Trust Hopping）與 SID Filtering**：  
  黑客攻陷子公司 B 的網域後，常試圖利用 **SID History** 偽造自己在總公司 A 也是 Domain Admin。如果兩域之間**未開啟「SID Filtering（SID 篩選）」**，黑客就能一秒完成「跨網域直接奪權」！

## 💻 第三動：現場追兇——AD 架構排查與日誌審計

身為網域鑑識人員，你必須能靈活調用 Windows 內建工具與專用診斷命令。

### 3.1 AD 拓撲與信任關係現場診斷（CMD / PowerShell）

#### 步驟 1：檢視全網所有網域控制站與 FSMO 五大角色歸屬


### 3.2 獵殺惡意 LDAP 枚舉行為（Event ID 1644 與 4662）

當攻擊者使用 SharpHound 時，DC 的 CPU 會瞬間飆高，並在日誌留下龐大的搜尋痕跡：

#### 步驟 1：開啟 DC 的高耗能 LDAP 查詢診斷日誌（Event ID 1644）
> 💡 *預設情況下，DC 不會記錄每一筆 LDAP 查詢。透過登錄檔開啟門檻審計（例如搜尋超過 30000 個物件的查詢）：*
```powershell
# 設置記錄搜尋物件超過 30000 筆的昂貴查詢
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\NTDS\Diagnostics" -Name "15 Field Engineering" -Value 5
```

#### 步驟 2：自動化 PowerShell 獵捕腳本：`ad_ldap_recon_detector.ps1`
```powershell
<#
.SYNOPSIS
    Active Directory 異常 LDAP 搜尋與 BloodHound 獵捕腳本 (ad_ldap_recon_detector.ps1)
#>
Write-Host "=== [1] 稽核 Directory Service 日誌中的低效/廣域 LDAP 查詢 (Event 1644) ===" -ForegroundColor Cyan

$LdapQueries = Get-WinEvent -LogName "Directory Service" -ErrorAction SilentlyContinue | 
Where-Object { $_.Id -eq 1644 } | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $eventData = $xml.Event.EventData.Data
    $retCount = ($eventData | Where-Object { $_.Name -eq 'Entries Returned' }).'#text'
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        ClientIp    = ($eventData | Where-Object { $_.Name -eq 'Client' }).'#text'
        Filter      = ($eventData | Where-Object { $_.Name -eq 'Filter' }).'#text'
        SearchCount = [int]$retCount
    }
}

$Suspicious = $LdapQueries | Where-Object { 
    $_.Filter -match "adminCount=1" -or 
    $_.Filter -match "samAccountType=" -or 
    $_.SearchCount -gt 5000 
}

if ($Suspicious) {
    Write-Host "🚨 警告：偵測到疑似 BloodHound 或大範圍 AD 枚舉行為！" -ForegroundColor Red
    $Suspicious | Format-Table -AutoSize
} else {
    Write-Host "✅ 未發現異常廣域 LDAP 搜尋。" -ForegroundColor Green
}
```

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 網域控制站 LDAP 連線數在短時間內爆發性增加，或特定工作站連續讀取數千個物件。 |

## 🛡️ 第五動：加固收斂 SOP (Mitigation & Hardening)

保護 Active Directory 核心架構免遭刺探與跨域橫向擴散，必須執行以下三道關鍵加固措施：

### 1. 第一步：強制啟用 LDAP 簽章與強制 LDAPS（防中繼與監聽）
透過群組原則（GPO）徹底終結明文 LDAP 傳輸：
```
電腦設定 ➔ Windows 設定 ➔ 安全性設定 ➔ 本機原則 ➔ 安全性選項
• 網域控制站: LDAP 伺服器簽署需求 ➔ 設定為【需要簽署 (Require signing)】
• 網域用戶端: 數位簽章伺服器通訊 (永遠) ➔ 設定為【需要簽署】
```

### 2. 第二步：強制開啟跨網域「SID 篩選（SID Filtering）」
防止黑客在跨國或外聯信任中，利用偽造的 `SID History` 橫向奪取總公司 Enterprise Admins 特權：
```cmd
:: 檢查信任關係是否啟用了 SID 篩選（Quarantine: Yes 代表安全啟用）
netdom trust corp.local /domain:sub.local /quarantine:yes
```

### 3. 第三步：推動 AD 三層式管理架構 (Tiering Model)
- **Tier 0（核心身分層）**：網域控制站、PKI CA 伺服器、ADFS。Tier 0 管理員嚴禁登入任何非 Tier 0 主機。
- **Tier 1（伺服器控制層）**：業務伺服器、資料庫、應用系統。
- **Tier 2（工作站終端層）**：一般辦公電腦、印表機。
- **效益**：切斷從一般工作站（Tier 2）直通網域管理員（Tier 0）的橫向憑證外洩鏈路。

## 🎯 第六動：靶場實戰檢驗 (Hands-on Lab Walkthrough)

請帶著剛才學到的 LDAP 結構與信任機制，進入真實 AD 架構靶場：

### 推薦靶場：[TryHackMe - Retro / VulnNet: Active Directory](https://tryhackme.com/room/vulnnetactivedirectory)
- **靶場背景**：一個具有完整階層與網域控制站的企業內網環境。
- **作戰任務**：
  1. 連入一般員工電腦，使用內建指令 `nltest /dclist:` 找出本網域的 DC 主機名稱。
  2. 使用 PowerShell ActiveDirectory 模組或 `adfind`，查詢本網域中所有具有 `adminCount=1` 屬性的高價值管理員帳號清單。
  3. 檢視該網域是否存在對外信任（`nltest /domain_trusts`），並判定該信任為單向還是雙向。
  4. 打開 DC 的事件檢視器，觀察剛才由你發起的 LDAP 查詢是否在系統中留下了足跡。

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能清楚回答，代表你已徹底掌握 AD 核心架構：

- [ ] **Q1**：在 Active Directory 的 `ntds.dit` 資料庫中，哪一個分割區（Partition）只在本網域的 DC 之間相互同步，而不會複寫給全樹系的其他網域？
  > **解答要點**：是「網域分割區（Domain Partition）」。網域分割區存放的是該網域專屬的所有物件（包含使用者、電腦、群組、組織單位 OU 等），其複寫範圍嚴格限制在同一網域的所有 DC 之間；而設定分割區（Configuration Partition）與架構分割區（Schema Partition）則會同步給全樹系（Forest）中的所有網域控制站。
- [ ] **Q2**：標準 LDAP 使用 TCP 389 通訊埠，而全局編錄（Global Catalog）使用 TCP 3268 通訊埠。在多網域的跨國企業架構中，為什麼查詢 389 找不到另一個子網域的帳號，但查詢 3268 卻能找到？
  > **解答要點**：因為 DC 上的標準 LDAP（389）僅對本機的「網域分割區」進行查詢，對跨網域物件無能為力；而全域編錄（GC, 3268）在設計上預先收集了全樹系內「所有子網域」每個物件的屬性子集（Partial Attribute Set, PAS，如帳號名稱、SID、通用群組成員資格等）。因此查詢 3268 可在單一端點跨域檢索全樹系的使用者資訊。
- [ ] **Q3**：紅隊工具 **BloodHound / SharpHound** 到底在底層呼叫了什麼協定與 API？身為藍隊分析師，若要在 DC 上捕捉這種全網枚舉行為，你會監控哪一個 Event ID？
  > **解答要點**：SharpHound 在底層主要透過 LDAP 查詢網域內所有物件屬性、ACL 存取控制清單與群組巢狀關聯，並透過 RPC/SMB（呼叫 NetSessionEnum、NetWkstaUserEnum API）探測遠端工作站上的活躍登入 Session。在 DC 端，可透過啟用目錄服務深度稽核，監控 Directory Service 日誌中的 **Event ID 1644**（高耗能/昂貴 LDAP 查詢），精準抓出大範圍枚舉使用者與群組的來源 IP。
- [ ] **Q4**：什麼是 **SID 篩選（SID Filtering）**？如果母公司與子公司建立網域信任時「未開啟」SID 篩選，攻擊者如何利用 `sIDHistory` 屬性實現跨網域直接奪取總部管理員權限？
  > **解答要點**：SID 篩選是一項安全邊界機制，用以防止跨網域傳入的 Kerberos 票證中夾帶未經授權的外部網域 SID。若未開啟 SID 篩選，攻擊者在攻陷子網域後，可利用 Mimikatz 在子網域使用者的 `sIDHistory` 屬性中惡意注入總公司網域 Domain Admins 的高權限 SID（例如 `S-1-5-21-...-512`）；當該帳號存取總公司資源時，總公司 DC 會信任並讀取其票證內的 SID History，誤將攻擊者視為本域管理員，從而造成跨域提權。
- [ ] **Q5**：為什麼企業安全基線要求全面停用明文 LDAP 並強制推行 **LDAP Signing（簽章）** 或 **LDAPS**？未簽章的 LDAP 連線容易遭受哪種致命的憑證劫持攻擊？
  > **解答要點**：未啟動簽章的明文 LDAP（TCP 389）封包內容缺乏完整性校驗與傳輸加密。攻擊者可在內網發動中間人攻擊（MITM）或 NTLM 中繼攻擊（NTLM Relay to LDAP），將截獲的高權限主機驗證請求直接中繼轉發給 DC 的 LDAP 服務，在 AD 資料庫中替自己新增高權限帳號或修改 ACL 權限（如賦予 DCSync 權限），從而無痛接管整座網域。強制 LDAP 簽章或 LDAPS 能確保傳輸通道經過金鑰簽名防篡改或 TLS 加密，徹底阻斷此類攻擊。\n
