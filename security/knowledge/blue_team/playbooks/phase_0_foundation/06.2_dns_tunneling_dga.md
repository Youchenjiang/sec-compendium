## 🧩 第一動：底層協定解剖——DNS 為何能成為黑客的「隱密高速公路」？

DNS（Domain Name System）採用 UDP 53 通訊埠（大型回應時切換為 TCP 53）。在絕大多數企業架構中，內網電腦向內部 DNS 伺服器查詢是**完全被信任且預設放行**的，這給了攻擊者可乘之機。

### 1.1 DNS Tunneling（通道外洩）底層傳輸原理

攻擊者不需要直接連線到公網。他只需要註冊一個由他控制的權威名稱伺服器（Authoritative Name Server, NS）：

```
[受害主機 (受隔離)]                 [企業內部 DNS]                 [黑客權威 DNS (公網)]
       │                                  │                                  │
       │ 1. 偷取資料並 Base32 編碼        │                                  │
       │    Query: <DATA>.attacker.com    │                                  │
       │ ───────────────────────────────> │                                  │
       │                                  │ 2. 遞迴轉發查詢 (合法放行)       │
       │                                  │ ───────────────────────────────> │
       │                                  │                                  │ 3. 黑客收到並解碼
       │                                  │ 4. 回覆 TXT/CNAME 夾帶 C2 指令   │    還原外洩資料！
       │                                  │ <─────────────────────────────── │
       │ 5. 收到 C2 指令並執行            │                                  │
       │ <─────────────────────────────── │                                  │
```

- **上行資料外洩（Exfiltration）**：受害主機將檔案切片、編碼（Base32/Base64/Hex）後，拼裝在「子網域名稱」中送出（例如：`TXkgU2VjcmV0.tunnel.evil.com`）。
- **下行遠端控制（Command & Control）**：黑客權威伺服器將執行指令（如 `whoami`、Payload Shellcode）包裝在 `TXT` 記錄、`CNAME` 記錄或 `NULL` 記錄中回覆給受害端。
- **EDNS0（RFC 6891 擴充機制）**：傳統 DNS UDP 酬載上限為 512 bytes，超過需強制切換為 TCP。但透過 EDNS0（Extension Mechanisms for DNS），客戶端可宣告支援高達 4096 bytes 的 UDP 緩衝區，黑客常藉此以極高吞吐量透過 TXT 記錄下載大型 Shellcode。

### 1.2 DGA（網域名稱生成演算法）通訊原理

不同於 Tunneling 外洩大量資料，**DGA 的目的在於「逃避靜態網址黑名單封鎖」**。
- 惡意程式內建一段數學演算法，以「當前日期（種子 Seed）」或隨機數作為輸入，每天自動計算生成數千個隨機網域名稱（例如：`xqj83kas91.biz`、`plm92nxz71.org`）。
- 黑客只要預先算好今天會生成哪一個域名，搶先註冊其中 1~2 個，即可成功與受感染主機取得聯繫。
- **鑑識特徵**：內部主機會在短時間內產生大量 `NXDOMAIN`（域名不存在，RCODE=3）的查詢失敗記錄。

### 3.2 Python 計算網域名稱夏農熵（Shannon Entropy）現場腳本

當你在 SIEM 或 PCAP 抓出大量網域名稱時，用以下 Python 腳本計算資訊熵。**熵值大於 3.8 ~ 4.0 者，高度疑似為加密外洩字串或 DGA**：

```python
import math
from collections import Counter

def shannon_entropy(domain: str) -> float:
    # 僅計算子網域名稱部分（第一級標籤）的混亂度
    subdomain = domain.split('.')[0]
    length = len(subdomain)
    if length == 0:
        return 0.0
    counts = Counter(subdomain)
    entropy = -sum((count / length) * math.log2(count / length) for count in counts.values())
    return round(entropy, 3)

# 測試範例
domains = [
    "google.com",                                      # 正常常見域名
    "login.microsoftonline.com",                       # 正常較長域名
    "a8f3b9c1e7d41d8cd98f00b204e98009.attacker.com",   # DNS Tunneling 外洩資料
    "xqj83kas91nxz.biz"                                # DGA 隨機生成
]

for d in domains:
    score = shannon_entropy(d)
    verdict = "🚨 疑似惡意/加密 (High Entropy)" if score > 3.8 else "🟢 正常/規律"
    print(f"[{score}] {d:<50} -> {verdict}")
```

### 3.3 Python 自動化還原 DNS 外洩檔案腳本

當確認遭到 DNS Tunneling 外洩時，使用 `dns_tunnel_exfil_decoder.py` 從 tshark 導出的子網域清單中自動拼裝並還原原始檔案：

```python
#!/usr/bin/env python3
"""
DNS 外洩資料自動化拼接還原腳本 (dns_tunnel_exfil_decoder.py)
用法：python dns_tunnel_exfil_decoder.py queries.txt target_parent_domain output_file
"""
import sys
import base64

def reconstruct_data(queries_file, parent_domain, output_file):
    print(f"[*] 讀取查詢清單: {queries_file}，過濾父網域: {parent_domain}")
    collected_payload = ""
    
    with open(queries_file, "r") as f:
        for line in f:
            q = line.strip().lower()
            if parent_domain in q:
                # 提取子網域名稱部分
                sub = q.replace("." + parent_domain, "")
                # 若存在多級子網域，移除序號標記
                chunks = sub.split(".")
                for c in chunks:
                    collected_payload += c
                    
    print(f"[*] 累計收集 Base32/Hex 資料長度: {len(collected_payload)} 字元")
    
    # 嘗試 Hex 解碼
    try:
        data = bytes.fromhex(collected_payload)
        with open(output_file, "wb") as out:
            out.write(data)
        print(f"✅ 成功以 Hex 還原檔案至: {output_file}")
        return
    except Exception:
        pass
        
    # 嘗試 Base32/Base64 解碼
    try:
        # 補足 padding
        pad = len(collected_payload) % 8
        if pad != 0:
            collected_payload += "=" * (8 - pad)
        data = base64.b32decode(collected_payload.upper())
        with open(output_file, "wb") as out:
            out.write(data)
        print(f"✅ 成功以 Base32 還原檔案至: {output_file}")
    except Exception as e:
        print(f"❌ 還原失敗: {e}")

if __name__ == "__main__":
    if len(sys.argv) < 4:
        print("用法: python dns_tunnel_exfil_decoder.py <queries.txt> <parent_domain> <out_file>")
        sys.exit(1)
    reconstruct_data(sys.argv[1], sys.argv[2], sys.argv[3])
```

### 3.4 Splunk SPL 大規模威脅獵捕

#### 偵測情境 A：獵殺高頻超長 DNS 查詢（Tunneling 外洩偵測）
```splunk
index=dns sourcetype="stream:dns"
| eval query_len=len(query)
| where query_len > 50
| stats count, dc(query) as unique_subdomains, avg(query_len) as avg_len by src_ip, parent_domain
| where unique_subdomains > 100 AND count > 500
| eval Alert_Level="🚨 CRITICAL: DNS Tunneling Exfiltration Suspected"
| sort - count
```

#### 偵測情境 B：獵殺突發大量 NXDOMAIN（DGA 感染主機定位）
```splunk
index=dns sourcetype="stream:dns" rcode="NXDOMAIN"
| bin _time span=10m
| stats count as nx_count, dc(query) as distinct_failed_domains by src_ip, _time
| where distinct_failed_domains > 50
| eval Alert_Level="🔴 HIGH: DGA Activity / C2 Hunting Detected"
| sort - distinct_failed_domains
```

### 4.1 SOC 8 大黃金研判問題對照表

| :--- | :--- |

## 🛡️ 第五動：阻斷與加固 SOP (Mitigation & Hardening)

一旦確認為 DNS Tunneling 或 DGA 活動，立即採取以下四道阻斷與加固防線：

### 1. 應急處置：DNS Sinkhole 與 RPZ 阻斷
- **RPZ（Response Policy Zone）**：在企業內部 DNS 伺服器（如 BIND, Windows Server DNS）直接設定 RPZ 策略，將惡意父網域解析強制改寫為 `0.0.0.0`：
  ```text
  ; BIND9 RPZ zone configuration example
  $TTL 1H
  @   IN  SOA  localhost. root.localhost. ( 1 3h 1h 1w 1h )
      IN  NS   localhost.
  *.attacker-c2.com    IN  CNAME  .
  attacker-c2.com      IN  CNAME  .
  ```
- **網關封鎖**：在邊界防火牆上嚴格阻斷未經授權之內部主機直接連線外部 DNS（封鎖非 DNS 伺服器對外的 UDP/TCP 53 流量）：
  ```bash
  # iptables 範例：僅允許指定 DNS 伺服器 (10.0.0.53) 對外連線 UDP 53
  iptables -A FORWARD -p udp --dport 53 -s 10.0.0.53 -j ACCEPT
  iptables -A FORWARD -p udp --dport 53 -j DROP
  ```

## 📋 第七動：過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能清楚回答，代表你已具備高階 DNS 鑑識能力：

- [ ] **Q1**：在嚴格的實體隔離或無外網存取權限的企業內網中，為什麼攻擊者不需要直接連上公網，只需要向企業「內部合法的 DNS 伺服器」發送查詢，就能將內部檔案成功偷渡到他在外網架設的伺服器？
  > **解答要點**：企業內部 DNS 伺服器通常具備網際網路遞迴解析權限。當內部受害端向內部 DNS 請求一個內網沒有紀錄的域名（如 `data.evil.com`）時，內部 DNS 會依據標準 DNS 階層查詢鏈，主動向公網的根伺服器、頂級網域伺服器（TLD）逐步遞迴，最終將該請求轉發到攻擊者註冊並控制的權威名稱伺服器（Authoritative Name Server）。因此內部 DNS 伺服器在不知情下扮演了資料外洩的轉發跳板。
- [ ] **Q2**：DNS 規格中，單一標籤（Label，即兩點之間的子網域名稱）與完整網域名稱（FQDN）的最大長度限制分別是多少 bytes？攻擊者在進行 Tunneling 時為什麼必須嚴格遵守這些限制？
  > **解答要點**：依據 RFC 1035 規範，單一標籤（Label）最大長度為 63 個字元（Bytes），而完整網域名稱（FQDN）包含結尾點在內最大長度為 255 個字元。攻擊者若超過此上限，DNS 封包會在抵達內部 DNS 或公網路由器時被直接視為格式錯誤（Format Error, FORMERR）並丟棄，導致通道中斷無法傳輸。
- [ ] **Q3**：在威脅獵捕中，我們常用「夏農資訊熵（Shannon Entropy）」來篩選惡意網域。為什麼正常的 `www.google.com` 資訊熵較低，而 `a9f4c8b2e1d7.c2.com` 資訊熵極高？其數學與語言學底層原因是什麼？
  > **解答要點**：夏農熵衡量的是字元分佈的混亂度與不確定性。正常的人類語言網域名稱遵循自然語言語法，字母組合有高度的規律性（如特定母音頻繁出現、特定字母組合），字元種類重複度高且可預測，因此計算出的資訊熵較低（通常 < 2.5）；而 Base32/Base64/Hex 編碼後的資料或雜湊字串，字元在有限集合內均勻且隨機分佈，極度缺乏語言規律，不確定性最大，因此資訊熵常突破 3.8 至 4.5。
- [ ] **Q4**：當內部主機感染了 DGA 惡意程式時，DNS 伺服器日誌中最明顯、最容易被 SIEM 告警規則抓到的特徵是什麼？
  > **解答要點**：最顯著的特徵是短時間內爆發大量高頻率的 `NXDOMAIN`（域名不存在，RCODE=3）解析失敗記錄。因為 DGA 演算法每天會批量生成數百到數千個隨機網域名稱，而攻擊者通常只搶註其中的 1~2 個作為當日 C2。受害者主機會依序遍歷查詢這些不存在的域名，直到命中為止，因而在 DNS 日誌中留下異常密集的 NXDOMAIN 軌跡。
- [ ] **Q5**：許多安全產品（如 Cisco Umbrella、Spamhaus）也是透過長子網域或高頻 DNS 查詢來進行雲端信譽反查。身為 SOC 分析師，你在研判時應藉由哪 2 個關鍵維度來排除這類商業安全工具的假警報？
  > **解答要點**：第一是「二級域名（SLD）信譽與擁有者」：檢查父網域是否屬於知名資安或郵件閘道廠商（如 `*.spamhaus.org`、`*.barracudanetworks.com`、`*.trendmicro.com`），且 Whois 資訊長期穩定；第二是「發起源主機的角色（Context）」：該查詢是來自企業郵件網關（Mail Transfer Agent, MTA）或安裝了官方 EDR 防毒軟體的主機，還是一台無端發起長子網域查詢的普通工作站或內部隔離資料庫伺服器。\n
