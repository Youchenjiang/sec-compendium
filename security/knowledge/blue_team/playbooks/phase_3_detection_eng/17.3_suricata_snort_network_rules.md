# 17.3 Snort/Suricata 網路入侵特徵撰寫 (Content, Offset, Depth 與協定解析實戰)

## 🚨 案發現場破題 (Incident Scenario & Mental Workflow)

某大型金融機構的邊界次世代防火牆（NGFW）突然通報一波來自境外 Tor 出口節點的異常 HTTP 連線，連線目標為企業核心支付閘道服務器（Payment API）。WAF 檢測引擎因未更新最新的 N-day 規則而被繞過；端點 EDR 亦未報警，因為惡意載荷仍在傳輸途中、尚未落地執行。

資安應變隊員緊急調閱了邊界旁路佈設的 Suricata 流量側錄原始資料（PCAP 封包），發現攻擊者正在利用 Apache Struts2 / Log4j 遠端代碼執行漏洞，透過 HTTP POST 標頭與畸形 JSON 載荷，嘗試在應用層注入 JNDI 查找字串（`${jndi:ldap://...}`）與 Cobalt Strike 記憶體反射載荷。

「封包即證據，流量即戰場。」在應用程式修補程式上線前的「黃金空窗期」，藍軍防守方阻斷大規模自動化利用的唯一微創手段，就是**在 IDS/IPS 引擎中即時撰寫高精準、低負載的 Suricata / Snort 網路特徵規則**。

藍軍網路偵測工程師的標準思維脈絡：
1. **協定層次精確錨定（Protocol Header Pinning）**：拒絕無脑比對全封包 `raw stream`，精準鎖定應用層通訊協定關鍵字（如 `http.uri`, `http.header`, `http.method`, `dns.query`），避開二進位流負載。
2. **三維字元位移約束（Offset, Depth, Distance, Within）**：利用 `offset`（起始偏移）與 `depth`（搜索深度）限定首發字元範圍；利用 `distance` 與 `within` 限定多組特徵之間的相對距離，杜絕誤判。
3. **正則表達式效能平衡（PCRE & Fast_Pattern）**：使用 `fast_pattern` 強制將長字串作為 MPM（Multi-Pattern Matcher）首選特徵，隨後再調用耗費 CPU 的 `pcre`，防止正規表示式導致 IDS 效能雪崩引發 DoS。
4. **網路流方向與閥值抑制（Flow, Threshold & Suppress）**：宣告 `flow:established,to_server` 確保只審計已完成 TCP 三向交握的單向入站流；搭配 `threshold` 限制單一 IP 告警頻率，防止警報風暴。
5. **雙模式部署決策（Alert vs Drop）**：在 IDS 旁路監聽時採用 `alert` 收集情報；在 IPS / NFQUEUE 內聯串接時精準切換為 `drop` 或 `reject` 實施微創連線阻斷。

```
                    [ 外部駭客 / 殭屍網路攻擊封包 ]
                                  │
                                  ▼ (進入 Suricata / Snort 引擎)
┌─────────────────────────────────────────────────────────────────┐
│ 1. 封包解碼與串流重組 (Packet Decode & Stream Reassembly)       │
│    ├── 驗證 IP 總和檢查碼 (Checksum)                             │
│    └── 重組 TCP 分段 (TCP Segment Streaming - 防範分段繞過)     │
└────────────────────────────────┬────────────────────────────────┘
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│ 2. MPM 多模式快速匹配 (Fast_Pattern Matcher)                    │
│    └── 快速比對高特徵長字串 (例如 fast_pattern: "jndi:ldap")    │
│        (未命中直接快速放行，完全不消耗深度正則 CPU 資源！)       │
└────────────────────────────────┬────────────────────────────────┘
                                 │ (命中 Fast_Pattern)
┌────────────────────────────────▼────────────────────────────────┐
│ 3. 深度協定欄位與相對位移比對 (App-Layer Sticky Buffers)        │
│    ├── http.header_names / http.uri                             │
│    ├── offset 0; depth 100; (絕對位置限定)                      │
│    └── distance 1; within 50; (相對距離約束)                    │
└────────────────────────────────┬────────────────────────────────┘
                                 │
                  ┌──────────────┴──────────────┐
                  ▼                             ▼
         [ 動作：alert ]               [ 動作：drop / reject ]
         產生 EVE.json 結構化告警       阻斷封包並向雙方發送 TCP RST
```

## 🧩 第一動：底層機制/協定解剖 (Mechanics & Physical Structs)

### 1. Suricata 規則基礎結構解剖

一條完整的 Suricata 規則由 **Rule Header（規則表頭）** 與 **Rule Options（規則選項）** 兩大部分構成：

```text
  [Action] [Proto] [Src_IP] [Src_Port] [Direction] [Dst_IP] [Dst_Port]  ( [Rule Options...] )
     │       │        │         │          │          │        │
   alert    http   $EXTERNAL   any        ->       $HTTP_SERVERS 80     ( msg:"..."; ...; )
```

#### A. 規則表頭核心欄位
- **Action（動作）**：
  - `alert`：記錄警告並記錄至 `eve.json`，封包正常放行（IDS 模式）。
  - `drop`：立即丟棄封包，後續不再轉發（IPS 模式，僅在 inline 模式生效）。
  - `reject`：丟棄封包，並向客戶端發送 TCP RST 旗標或向伺服端發送 ICMP Port Unreachable，迅速切斷連線。
  - `pass`：白名單放行，忽略後續所有規則比對。
- **Proto（協定）**：
  - 基礎層：`ip`, `tcp`, `udp`, `icmp`。
  - 應用層（Suricata 專屬強大解析器）：`http`, `ftp`, `tls`, `smb`, `dns`, `ssh`, `dcerpc`。
- **Direction（方向）**：
  - `->`：單向連線（絕大多數規則採用）。
  - `<>`：雙向監控（常用於資料外洩或雙向協商偵測）。

#### B. 規則選項四大基石
- `msg:"<TEXT>"`：SOC 分析師在 SIEM / IDS 儀表板上看到的第一行告警文字。
- `flow:<OPTIONS>`：追蹤 TCP 狀態機。
  - `established`：**極為關鍵！** 僅在 TCP 三向交握完成後才進行比對，過濾無效的 SYN 掃描。
  - `to_server` / `to_client`：限定只比對請求（Request）或回應（Response）。
- `classtype:<NAME>`：分類標籤（如 `web-application-attack`、`trojan-activity`），映射內建優先級。
- `sid:<ID>` 與 `rev:<REV>`：
  - `sid`（Signature ID）：規則唯一編號。< 1,000,000 為官方/開源保留；**自訂規則請一律使用 >= 1,000,000**。
  - `rev`：規則修訂版本號（由 1 開始遞增）。

### 2. 核心比對原語：絕對位置 vs 相對位置

在 Suricata 規則中，單純使用 `content` 極度容易遭受誤報或效能耗盡。必須使用以下四個參數進行三維幾何約束：

```text
[封包負載串流 (Payload Stream)]
0                   10                  20                  30                  40 Byte
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
[   offset 4; depth 8   ]               [ distance 2; within 10 ]
        ▲                                       ▲
    搜尋區間 A (絕對位置)                    搜尋區間 B (相對於 A 結尾的距離)
```

1. **絕對位置定位（Absolute Modifiers）**：
   - `content:"GET"; offset:0; depth:3;`：代表字串 `"GET"` 必須在負載的 **第 0 個 Byte 開始、長度 3 個 Byte 內（即開頭位置）** 出現。若出現在第 4 個 Byte 則判定不符合！
2. **相對位置約束（Relative Modifiers）**：
   - 必須緊接在另一個 `content` 之後使用！
   - `distance:<N>`：從**前一個 content 命中位置的最後一個 Byte 起算**，往後跳過 N 個字元才開始搜尋。
   - `within:<M>`：從開始搜尋點起算，限制必須在接下來的 M 個字元範圍內找到目標字串。
   - **實戰範例**：
     ```text
     content:"SELECT"; nocase;
     content:"FROM"; nocase; distance:1; within:50;
     ```
     （尋找包含 `SELECT` 且在其後方 1 到 50 個字元內緊跟著 `FROM` 的語句，有效避免跨區段誤傷）。

### 3. Suricata 黏性緩衝區（Sticky Buffers）現代語法

傳統 Snort 規則習慣在 `content` 後加上修飾詞（如 `content:"evil"; http_uri;`）。現代 Suricata 全面導入 **Sticky Buffers（黏性緩衝區）**，讓語法結構更加優雅、解析效能提升 300%：

```text
[傳統寫法 (Deprecated)]
content:"/admin/login.php"; http_uri; content:"POST"; http_method;

[現代 Sticky Buffer 寫法 (Recommended)]
http.method; content:"POST";
http.uri; content:"/admin/login.php"; startswith;
http.request_header; content:"User-Agent|3a 20|sqlmap"; nocase;
```

#### 常見 Sticky Buffer 速查：
- `http.method`：HTTP 請求方法（`GET`, `POST`, `PUT` 等）。
- `http.uri`：正規化後的完整 URI 路徑。
- `http.header` / `http.request_header`：HTTP 請求標頭區段。
- `http.request_body`：HTTP POST 內容載荷。
- `http.stat_code`：HTTP 伺服端回應狀態碼（`200`, `404`, `500` 等）。
- `tls.sni`：TLS 握手階段 Client Hello 中的 SNI 網域名稱。
- `dns.query`：DNS 請求解析的目標完整網域名稱。

### 2. 生產級實戰規則撰寫範本

建立檔案 `/etc/suricata/rules/local_cve_hunt.rules`：

#### 規則 A：Log4Shell (CVE-2021-44228) 深度全欄位檢測規則
```text
alert http any any -> $HTTP_SERVERS any (
    msg:"SEC-ALERT: Apache Log4j JNDI Remote Code Execution Attempt (CVE-2021-44228)";
    flow:established,to_server;
    
    // 使用 fast_pattern 鎖定最核心特徵字串，保障多模式匹配效能
    content:"jndi"; nocase; fast_pattern;
    
    // 限制協議類型，支援 ldap, rmi, dns, ldaps
    pcre:"/\$\{jndi:(ldap[s]?|rmi|dns|nis):\/\//i";
    
    classtype:web-application-attack;
    reference:cve,2021-44228;
    reference:url,attack.mitre.org/techniques/T1190/;
    metadata:created_at 2026-09-12, author BlueTeam_NetSec;
    sid:1000001;
    rev:1;
)
```

#### 規則 B：Cobalt Strike 預設特徵流量阻斷 (IPS Drop Mode)
```text
drop tcp $HOME_NET any -> $EXTERNAL_NET $HTTP_PORTS (
    msg:"SEC-DROP: Cobalt Strike Default Malleable C2 HTTP Beaconing Detected";
    flow:established,to_server;
    
    http.method;
    content:"GET";
    
    http.uri;
    content:"/match"; startswith;
    
    http.header;
    content:"Cookie|3a 20|";
    // 檢查 Cookie 後方是否跟隨 16 到 64 字元的 Base64 元件
    pcre:"/Cookie:\s+[A-Za-z0-9+\/]{20,}={0,2}/";
    
    threshold:type limit, track by_src, count 1, seconds 60;
    classtype:trojan-activity;
    sid:1000002;
    rev:2;
)
```

### 3. 自動化 PCAP 規則驗證評估腳本 (Python + Suricata)

```python
#!/usr/bin/env python3
# 藍隊測試驗證：讀取 PCAP 檔案，執行 Suricata 規則並驗證是否有漏報或語法異常

import subprocess
import json
import sys
import os

PCAP_PATH = "/tmp/test_attack.pcap"
RULE_PATH = "/etc/suricata/rules/local_cve_hunt.rules"
LOG_DIR = "/tmp/suri_verify_run"

os.makedirs(LOG_DIR, exist_ok=True)

cmd = [
    "suricata",
    "-r", PCAP_PATH,
    "-S", RULE_PATH,
    "-l", LOG_DIR,
    "--runmode", "single"
]

print(f"[*] Running Suricata verification against: {PCAP_PATH}")
res = subprocess.run(cmd, capture_output=True, text=True)

if res.returncode != 0:
    print(f"[-] Suricata execution failed:\n{res.stderr}")
    sys.exit(1)

eve_path = os.path.join(LOG_DIR, "eve.json")
matched_alerts = []

if os.path.exists(eve_path):
    with open(eve_path, "r", encoding="utf-8") as f:
        for line in f:
            try:
                data = json.loads(line)
                if data.get("event_type") == "alert":
                    matched_alerts.append(data["alert"])
            except json.JSONDecodeError:
                continue

print(f"[+] Total Alerts Triggered: {len(matched_alerts)}")
for alert in matched_alerts:
    print(f"    -> [SID: {alert['gid']}:{alert['signature_id']}] {alert['signature']} (Severity: {alert['severity']})")

if len(matched_alerts) > 0:
    print("[SUCCESS] Rule successfully verified with real packet telemetry!")
else:
    print("[WARNING] Zero alerts triggered! Please check content offset or flow conditions.")
```

## ⚖️ 第四動：研判分水嶺——真實威脅 vs 業務誤報

### SOC 研判核心問題表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1：發起連線的目標端點是否真實運行該受害軟體或中介軟體？** | 比對企業 CMDB 資產指紋：若外部 IP 向一台單純的 Nginx 靜態圖片快取伺服器發送 `Log4j` 或 `WebLogic T3` 攻擊，**此攻擊不可能成功**，屬於「無效探測（Benign Trigger / Unsuccessful Attempt）」。若目標是後端 Java 核心業務服務器，等級立即拉至 P1！ |
| **Q2：HTTP 回應碼（Status Code）是否為成功狀態（200 OK）？** | 檢視 `http.stat_code`。若伺服器回傳 `400 Bad Request`、`404 Not Found`、`500 Internal Error`，代表應用層在接收後直接報錯拒絕，未成功執行惡意代碼；若回傳 `200 OK` 且 Response Body 長度大於平常，需深度檢視是否有資料外洩。 |
| **Q3：連線完成後，伺服器是否有異常向外的主動連線（Outbound Callbacks）？** | 這是判定 RCE 是否成功的死生分水嶺！檢查該告警發生後的 60 秒內，受害伺服器是否突然主動對外（特別是外網未知 IP 的 1389, 389, 4444, 8080 等非業務埠）發起 TCP SYN 封包？若是，代表伺服器已被控制並正在反彈 Shell。 |
| **Q4：命中規則的特徵字串是否位於可被後端程式碼解析的欄位中？** | 檢視封包：攻擊字串是在真實的 URI / 參數中，還是出現在靜態圖片（如 `.jpg`）的二進位資料區塊？如果是圖片二進位內部碰巧出現了幾位元組的相似代碼，純屬特徵碰撞造成的誤報。 |
| **Q5：是否為內部漏洞掃描器（如 Nessus / Qualys）的預排探測？** | 檢查來源 IP 是否登錄在企業資安維運白名單網段中，檢查其 User-Agent 是否包含企業特定資安掃描標記。 |
| **Q6：發起該連線的來源 IP 在全局威脅情資（CTI）中聲譽為何？** | 查詢 VirusTotal、AbuseIPDB、GreyNoise。該 IP 是否被標記為已知惡意 C2、Mirai 殭屍網路、Tor 節點，還是合法的合作夥伴固定出口？ |
| **Q7：封包中的攻擊載荷是否經過了混淆（Obfuscation）但依然能被後端執行？** | 檢查如 `${lower:j}ndi`、`${env:USER:-j}ndi`。如果攻擊者使用了巢狀變數替換，常規單純匹配 `jndi` 的規則可能失效，若規則觸發需檢視其解碼後真實意圖。 |

## 🛡️ 第五動：處置圍堵與系統加固 SOP

### 1. 網路邊界微創阻斷操作指南

當在監控中發現正在進行中的利用行為時，依序執行以下邊界處置：

```bash
# 步驟 1：立即將攻擊來源 IP 加入邊界邊界阻斷名單 (以 iptables / 防火牆為例)
# 丟棄來自攻擊者 198.51.100.23 的所有封包
iptables -I INPUT 1 -s 198.51.100.23 -j DROP

# 步驟 2：在 Suricata 規則庫中將對應規則動作從 alert 改為 drop (切換為 IPS 模式)
sed -i 's/^alert http/drop http/' /etc/suricata/rules/local_cve_hunt.rules
# 平滑重載 Suricata 規則
suricatasc -c reload-rules

# 步驟 3：中斷既有的異常建立連線 (使用 ss / conntrack 清除連線狀態)
# 清除 Netfilter conntrack 中該 IP 的現存連線表項目
conntrack -D -s 198.51.100.23
```

### 2. Suricata 效能最佳化與抗規避加固

1. **強制啟用串流重組（Stream Reassembly）**：
   攻擊者常透過 TCP 分段（TCP Fragmentation，如將 `GET` 分成 3 個單字節封包）繞過未重組的簡單 IDS。必須在 `suricata.yaml` 中確認：
   ```yaml
   stream:
     reassembly:
       memcap: 256mb
       depth: 1mb
       toserver-chunk-size: 2560
   ```
2. **優化 fast_pattern 降低 CPU 負載**：
   確保規則中最長、最獨特且不包含萬用字元的字串被宣告為 `fast_pattern`，使 MPM 模組能以 O(1) 效率快速跳過無關封包。
3. **HTTP 畸形標頭寬容度設定（HTTP Evading Prevention）**：
   開啟 Suricata 的 `libhtp` 模組，配置自動解碼雙重 URL 編碼（`double-decode-path: yes`）與路徑簡化（`normalize-path: yes`），徹底在解碼層粉碎字元逃逸。

## 📋 過關驗收檢查點 (Mastery Checklist)

- [ ] **Q1：在撰寫 Suricata 規則時，為什麼 `flow:established,to_server` 對於防止誤報和維持引擎效能具有決定性意義？**
  - *驗收標準*：答出 `flow:established` 能保證只有在 TCP 完成三向交握後才進行規則比對，防止外部隨意發送偽造來源 IP 的 SYN 掃描引發大量無效誤警報；`to_server` 則限定只比對由客戶端發往伺服端的請求方向，避免將伺服端回傳的無害資料誤判為攻擊。
- [ ] **Q2：`offset` 與 `depth` 和 `distance` 與 `within` 的核心本質區別是什麼？**
  - *驗收標準*：答出 `offset/depth` 是**絕對位移修飾符**（以整個 Payload 或緩衝區的起始點 0 為基準搜尋特定範圍）；而 `distance/within` 是**相對位移修飾符**（必須緊跟在另一個 `content` 之後，以「前一個特徵命中的結束點」為基準搜尋接下來的相對範圍）。
- [ ] **Q3：什麼是 Suricata 的 `fast_pattern`？如果不手動指定，引擎會如何自動選擇它？**
  - *驗收標準*：答出 `fast_pattern` 是多模式匹配器（MPM）在進行初篩時使用的「核心特徵」。引擎先用它快速過濾無關封包。若不手動指定，Suricata 會自動評估規則中長度最長、最複雜（熵值最高）且最不可能頻繁出現的 `content` 作為預設的 fast_pattern。
- [ ] **Q4：為什麼現代 Suricata 規範強烈推薦使用 Sticky Buffers（如 `http.uri; content:"/admin";`）而不是傳統修飾符（如 `content:"/admin"; http_uri;`）？**
  - *驗收標準*：答出 Sticky Buffers 語意清晰，且允許在其後連續鏈接多個修飾符（如 `startswith`, `endswith`），更重要的是 Suricata 底層會直接在已經解碼解析好的專屬記憶體結構中進行比對，大幅減少對未解碼 raw payload 的重複遍歷，提升執行效率。
- [ ] **Q5：在生產環境中，為什麼不能隨便使用沒有字元範圍限制的貪婪正則表達式（如 `pcre:"/.*eval.*/"`）？**
  - *驗收標準*：答出會引發**正則表達式災難性回溯（ReDoS）**，導致單一連線耗盡 CPU 100% 資源，使 IDS/IPS 引擎崩潰或丟包（Packet Drop），形成阻斷服務攻擊漏洞。正確做法是使用 `fast_pattern` 限定前置字串，並在 PCRE 中使用非貪婪模式或嚴格的字元集限制（如 `[^a-z]`）。
