# 實戰手冊 11.3：傳輸加密密鑰套件降級攻擊防禦與前向保密性 (PFS) 實踐

## 案發現場破題

在企業對外服務、API Gateway 或內部微服務互聯場景中，傳輸層安全協議（TLS/SSL）是保護通訊隱私性、防止中間人竄改與維護數據完整性的基石。然而，由於歷史系統相容性妥協或組態管理疏失，許多生產環境伺服器仍允許協商已廢棄的 SSLv3、TLS 1.0、TLS 1.1，或保留支援弱加密套件（例如 RC4、3DES-CBC、靜態 RSA 密鑰交換）。

攻擊者可利用中間人（MITM）發動協商降級攻擊（如 POODLE、BEAST、Logjam、FREAK），迫使雙方降級至存在已知數學破綻的加密模式；更甚者，若未啟用完美前向保密（Perfect Forward Secrecy, PFS），一旦伺服器長期私鑰（Private Key）因伺服器滲透、憑證外洩或法律調閱而暴露，攻擊者過去監聽並儲存的所有歷史通訊流量將被全數追溯解密，造成災難性機密資料洩漏。身為藍隊防禦工程師，必須深入理解 TLS 握手演進、密鑰交換算力強度、PFS 數學原理（ECDHE），並建立起自動化密碼套件稽核與企業級硬化防禦體系。

```
TLS 密鑰交換與 Forward Secrecy 演進對比：

[靜態 RSA 密鑰交換 (無 PFS, 具高度追溯破譯風險)]
Client ---> ClientHello ---> Server
Client <--- Certificate (RSA PubKey) <--- Server
Client ---> Pre-Master Secret (使用 Server RSA 公鑰加密) ---> Server
  * 致命隱患：攻擊者只需竊錄所有流量，日後若取得 Server RSA 私鑰，
             可輕易解密所有歷史會話中的 Pre-Master Secret 與實際資料明文！

[ECDHE 密鑰交換 (具備完美前向保密 PFS)]
Client ---> ClientHello (支援 Curves 與 KeyShare) ---> Server
Client <--- ServerHello + ServerKeyExchange (ECDH Ephemeral PubKey + 數位簽名) <--- Server
Client ---> ClientKeyExchange (Client Ephemeral PubKey) ---> Server
  * 雙方依據 Diffie-Hellman 數學原理獨立計算得出 Pre-Master Secret
  * 伺服器長期憑證僅用於驗證身分合法性（防 MITM），不參與金鑰加解密！
  * Ephemeral 私鑰在握手完成後立即在記憶體銷毀，歷史流量即使獲取私鑰亦無法逆解！
```

## 第一動：密碼學原理與歷史漏洞機理

### 1.1 完美前向保密（Perfect Forward Secrecy, PFS）數學原理
- **核心定義**：在金鑰協商過程中，每次通訊會話均動態產生隨機公私鑰對（Ephemeral Key Pair），通訊結束即刻自記憶體安全清除銷毀。長期密鑰（如伺服器憑證私鑰）僅用於對握手參數實施數位簽名身分驗證，不直接參與會話主密鑰（Master Secret）的加解密。
- **代表演算法**：
  - **DHE（Ephemeral Diffie-Hellman）**：基於大質數有限域離散對數問題，安全性依賴質數群（DH Group）位元長度（至少須 >= 2048-bit）。
  - **ECDHE（Elliptic Curve Ephemeral Diffie-Hellman）**：基於橢圓曲線離散對數問題（ECDLP），計算效率極高且安全性強，主流曲線包括 Curve25519 (X25519) 與 NIST P-256 (secp256r1)。

### 1.2 經典降級攻擊與漏洞剖析
- **POODLE (Padding Oracle On Downgraded Legacy Encryption, CVE-2014-3566)**：利用 SSLv3 規範中對 CBC 模式填充字元內容未作嚴格校驗的結構缺陷，攻擊者透過注入 JavaScript 強制讓瀏覽器連線中斷並降級至 SSLv3，接著利用 CBC 填充 Oracle 逐字節竊取敏感明文 Cookie。
- **Logjam (CVE-2015-4000)**：針對 1990 年代美國出口限制遺留之 512-bit / 768-bit 弱 Export DHE 參數。攻擊者藉由中間人竄改握手封包，迫使伺服器採用廣泛通用的預算質數群，攻擊者利用數論篩法（NFS）預先計算離散對數並即時破解會話金鑰。
- **BEAST (Browser Exploit Against SSL/TLS, CVE-2011-3389)**：TLS 1.0 CBC 模式中初始化向量（IV）採用上一區塊密文（Chained IV），攻擊者可藉由選擇明文攻擊（CPA）逐步猜測還原 HTTP 請求頭。

## 第二動：封包特徵與日誌軌跡定位

### 2.1 TLS 握手封包特徵檢索（Wireshark / tshark）
- ClientHello 封包內 `cipher_suites` 列表：檢視客戶端是否企圖嘗試老舊套件。
- ServerHello 封包確認選定的協議版本與加密套件（Cipher Suite）：確認是否協商至不安全套件。
- 檢索式：
```wireshark
# 檢測協商至 TLS 1.0 (0x0301) 或 TLS 1.1 (0x0302) 或 SSLv3 (0x0300)
tls.handshake.version < 0x0303 && tls.handshake.type == 2

# 檢測未採用 PFS 之靜態 RSA 套件 (Cipher Suite 0x002f, 0x0035 等)
tls.handshake.ciphersuite == 0x002f || tls.handshake.ciphersuite == 0x0035

# 檢測弱 CBC 模式或 RC4 套件
tls.handshake.ciphersuite in {0x0004 0x0005 0x000a 0x002f 0x0035}

# 檢測降級標記 TLS_FALLBACK_SCSV (0x5600)
tls.handshake.ciphersuite == 0x5600
```

### 2.2 Web 伺服器 TLS 存取日誌格式
在 Nginx 存取日誌中記錄協商使用的 `$ssl_protocol` 與 `$ssl_cipher`：
```nginx
log_format ssl_audit '$remote_addr - $remote_user [$time_local] '
                     '"$request" $status $body_bytes_sent '
                     'SSL: $ssl_protocol / $ssl_cipher '
                     'SessionID: $ssl_session_id '
                     'Curves: $ssl_curves';
```

### 3.2 Python 自動化掃描與 PFS 支援性驗證
```python
import ssl
import socket

def audit_tls_endpoint(host, port=443):
    context = ssl.create_default_context()
    # 關閉憑證驗證以專注分析底層支援套件
    context.check_hostname = False
    context.verify_mode = ssl.CERT_NONE

    print(f"[*] 掃描目標: {host}:{port}")
    try:
        with socket.create_connection((host, port), timeout=5) as sock:
            with context.wrap_socket(sock, server_hostname=host) as ssock:
                version = ssock.version()
                cipher_name, proto, bits = ssock.cipher()
                print(f"[+] 成功建立 TLS 連線:")
                print(f"    - Protocol Version: {version}")
                print(f"    - Negotiated Cipher: {cipher_name} ({bits} bits)")

                # 判斷是否具備 PFS
                if "ECDHE" in cipher_name or "DHE" in cipher_name:
                    print(f"    - PFS Status: [PASS] 具備前向保密性 ({cipher_name.split('_')[0]})")
                else:
                    print(f"    - PFS Status: [CRITICAL] 缺乏前向保密性！使用了靜態金鑰交換。")

                if version in ["TLSv1", "TLSv1.1", "SSLv3"]:
                    print(f"    - Security Alert: [CRITICAL] 協商使用了已被廢棄之不安全協議！")
    except Exception as e:
        print(f"[-] 連線測試失敗: {e}")

if __name__ == '__main__':
    audit_tls_endpoint("localhost", 8443)
```

## 第四動：SIEM 關聯規則與告警工程（Splunk / Suricata）

### 4.1 Splunk 檢測老舊協議連線暴增（降級或爬蟲徵兆）
```spl
index=web_proxy sourcetype="nginx:ssl_audit"
| stats count by ssl_protocol, ssl_cipher, src_ip, dest_ip
| search ssl_protocol IN ("SSLv3", "TLSv1", "TLSv1.1") OR ssl_cipher="*RC4*" OR ssl_cipher="*DES*"
| eval alert_severity="HIGH"
| table _time, src_ip, dest_ip, ssl_protocol, ssl_cipher, count
```

### 4.2 Suricata 網路入侵偵測規則
```text
# 檢測 ServerHello 採用老舊 TLS 1.0 / TLS 1.1 協議
alert tls any any -> any any (msg:"ET POLICY Deprecated TLS 1.0 or 1.1 Connection Negotiated"; flow:established,to_client; tls.version:1.0,1.1; classtype:policy-violation; sid:2039101; rev:1;)

# 檢測降級協商至 CBC-SHA 弱套件
```

## 第五動：企業級防禦硬化與應急響應阻斷

### 5.1 Nginx 高安全 TLS 基準硬化配置
全面停用 TLS 1.0/1.1，強制限定 TLS 1.2 及 TLS 1.3，並強制啟用 PFS 專用套件：
```nginx
# /etc/nginx/conf.d/ssl_hardening.conf
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers on;

# TLS 1.3 預設皆具備 PFS (RFC 8446)
# TLS 1.2 限定 ECDHE 密鑰交換與 AEAD 加密演算法 (AES-GCM / CHACHA20-POLY1305)
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384';

# 產生安全之 2048-bit Diffie-Hellman 參數防止 Logjam
# 指令：openssl dhparam -out /etc/nginx/dhparam.pem 2048
ssl_dhparam /etc/nginx/dhparam.pem;

# 啟用 HSTS (HTTP Strict Transport Security) 強制瀏覽器僅能使用 HTTPS
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;

# 關閉 Session Tickets 或設定密鑰定時輪替 (避免長期 Ticket Key 破壞 PFS)
ssl_session_tickets off;
```

### 5.2 啟用 TLS_FALLBACK_SCSV 防止降級碰撞
- 在 Web Server 與反向代理層確認支援 `TLS_FALLBACK_SCSV`（RFC 7507）。當瀏覽器因連線異常嘗試降級重新連線時，伺服器若收到此信號且發現連線協議低於伺服器支援之最高版本，將直接拒絕握手（Alert 86 `inappropriate_fallback`），徹底封殺 MITM 降級攻擊。

## 靶場實戰：從弱設定到 PFS 硬化之驗證歷程

### 實驗目標
在測試伺服器上驗證 SSL 降級脆弱性，並部署硬化設定後使用 OpenSSL 與 cURL 驗證阻斷效果：

```bash
# 步驟 1：使用 OpenSSL 指定 TLS 1.0 發起握手 (預期硬化後被拒絕)
openssl s_client -connect 127.0.0.1:443 -tls1

# 步驟 2：測試不安全 CBC 密鑰套件協商 (預期被 Handshake Failure 拒絕)
openssl s_client -connect 127.0.0.1:443 -cipher "AES128-SHA"

# 步驟 3：驗證正常 TLS 1.3 / ECDHE-PFS 協商
openssl s_client -connect 127.0.0.1:443 -tls1_3

# 步驟 4：檢驗 Diffie-Hellman 位元強度 (確認 >= 2048 bits)
openssl s_client -connect 127.0.0.1:443 -cipher "DHE-RSA-AES128-GCM-SHA256" | grep "Server Temp Key"
```
