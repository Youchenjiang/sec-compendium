# 08.1 IEEE 802.11 四向交握與 EAPOL 認證流量鑑識 (802.11 4-Way Handshake & EAPOL Forensics)

## 案發現場破題

在企業內部 WiFi 無線網路環境中，**WPA2-Personal (PSK)** 是最為普及的加密認證標準。然而，攻擊者並不需要連上企業 WiFi，只需攜帶一張支援監聽模式（Monitor Mode）與封包注入（Packet Injection）的無線網卡，即可在建築物外發動 **解除認證洪水攻擊（Deauthentication Attack / T1557）**。透過偽造 AP 的 MAC 位址發送 IEEE 802.11 Deauth 管理訊框，強制合法筆電與 AP 斷線。當客戶端自動嘗試重新連線時，攻擊者便趁機側聽並完整捕獲 **EAPOL 四向交握（4-Way Handshake）** 的 4 個關鍵封包，隨後使用 Hashcat 進行離線 GPU 暴力破解，最終取得企業 WiFi 密碼並橫向滲透內部網路。

```
[攻擊者無線網卡 (aireplay-ng -0 5 -a <AP_BSSID> -c <Client_MAC>)]
       │
       ▼ (發送 802.11 Deauth 管理訊框，強迫使用者斷線)
+-------------------------------------------------------------------------------+
| 合法使用者筆電 (STA) ◄──────── 實體連線被中斷 ────────► 企業無線基地台 (AP)   |
+-------------------------------------------------------------------------------+
       │
       ▼ 【筆電發起自動重新連線：觸發 EAPOL 4-Way Handshake】
 ┌─────────────────────────────────────────────────────────────┐
 │ 訊息 1: AP ──► STA : ANonce (AP 隨機數)                     │
 │ 訊息 2: STA ──► AP : SNonce (客戶端隨機數) + MIC (訊息完整性)│ ◄── 關鍵抓包！
 │ 訊息 3: AP ──► STA : GTK (群組暫時金鑰，以 KEK 加密) + MIC  │
 │ 訊息 4: STA ──► AP : ACK 確認收到                           │
 └─────────────────────────────────────────────────────────────┘
       │
       ▼ (攻擊者取得含有 ANonce, SNonce, MACs 與 MIC 的 .cap 檔案)
[Hashcat 模式 22000 離線破解 ➔ 榨出 WPA2 明文密碼 ➔ 直闖企業內網]
```

### 痛點場景
- **實體周界完全失效**：WiFi 射頻訊號穿透牆面與玻璃窗，攻擊者位於停車場或對街咖啡廳即可發動攻擊，傳統實體門禁防護形同虛設。
- **802.11 管理訊框預設未加密**：在標準 WPA2 中，Deauth / Disassociate 屬於未加密之二層管理訊框（Management Frames），任何第三方皆可隨意偽造來源 MAC 發動連線劫持。
- **離線破解完全隱匿**：一旦四向握手資料包被捕獲，攻擊者可將運算任務轉移至本機多卡 GPU 叢集進行離線破解，企業 AP 與 SIEM 完全無從得知密碼正遭受猛烈字典攻擊。

## 第一動：PTK / GTK 金鑰階層與四向交握數學原理 (Cryptographic Key Hierarchy)

```
+-----------------------------------------------------------------------------------------------+
| WPA2 金鑰運算架構與 5 大元素                                                                   |
|                                                                                               |
| 1. 成對主金鑰 (Pairwise Master Key, PMK)                                                      |
|    - 運算公式：PMK = PBKDF2(HMAC-SHA1, Passphrase, SSID, 4096 輪疊代, 256 bits)              |
|    - 特點：由 WiFi 密碼與 SSID 運算而成，只要密碼與 SSID 不變，PMK 便固定不變。              |
|                                                                                               |
| 2. 成對暫時金鑰 (Pairwise Transient Key, PTK)                                                 |
|    - 運算公式：PTK = PRF-512(PMK, "Pairwise key expansion", Min(AA,SPA) || Max(AA,SPA) ||    |
|                             Min(ANonce,SNonce) || Max(ANonce,SNonce))                         |
|    - 核心 5 大元素：PMK, AP MAC (AA), Client MAC (SPA), AP Nonce (ANonce), Station Nonce (SNonce)|
|                                                                                               |
| 3. 訊息完整性代碼 (Message Integrity Code, MIC)                                               |
|    - 作用：STA 使用 PTK 中的 KCK（金鑰確認金鑰）對封包計算 HMAC-SHA1 產生 MIC。               |
|    - 破解途徑：猜測密碼 ➔ 計算 PMK ➔ 組合 5 大元素導出 PTK ➔ 計算 MIC ➔ 比對封包中真實 MIC！  |
+-----------------------------------------------------------------------------------------------+
```

### 四向交握 4 步驟封包欄位細部解析

| 交握步驟 (Message) | 傳輸方向 | 核心承載參數 (Payload Content) | 安全防護作用 (Security Objective) |
| :--- | :---: | :--- | :--- |
| **Message 1** | AP ➔ STA | `ANonce` (隨機數), Replay Counter | AP 向終端宣告隨機數，STA 憑此開始運算 PTK。 |
| **Message 2** | STA ➔ AP | `SNonce` (隨機數), RSN IE, **MIC** | STA 回傳自身隨機數與由 PTK 簽署之 MIC，證明知曉密碼。 |
| **Message 3** | AP ➔ STA | 加密的 `GTK` (由 KEK 保護), MIC, Install=1 | AP 通知 STA 安裝金鑰，並傳遞廣播用群組金鑰。 |
| **Message 4** | STA ➔ AP | MIC, ACK 確認序號 | STA 確認金鑰安裝完成，後續雙方全面啟用 AES-CCMP 加密。 |

### PTK 內部四組衍生密鑰結構
- **KCK (Key Confirmation Key, 128 bits)**：用於計算並校驗 EAPOL 訊框的 MIC，確保交握未遭竄改。
- **KEK (Key Encryption Key, 128 bits)**：用於在 Message 3 中加密派送群組金鑰 GTK。
- **TK (Temporal Key, 128 bits)**：用於後續單播（Unicast）數據傳輸時的 AES-CCMP 加密。
- **MIC Key (64/128 bits)**：用於 TKIP 模式（若向後相容）的完整性校驗。

## 第二動：握手捕捉模擬與 Hashcat 破解實務 (Toolchain Practice)

### 1. 抓取握手包與 Deauth 模擬 (Aircrack-ng 套件)
```bash
# 1. 將網卡切換至監聽模式
sudo airmon-ng start wlan0

# 2. 定位目標 AP 頻道並啟動抓包
sudo airodump-ng -c 6 --bssid 00:11:22:33:44:55 -w wpa_handshake wlan0mon

# 3. 發送 5 個 Deauth 訊框迫使客戶端重新握手
sudo aireplay-ng -0 5 -a 00:11:22:33:44:55 -c AA:BB:CC:DD:EE:FF wlan0mon
```
- Airodump 視窗右上角顯示：`[ WPA handshake: 00:11:22:33:44:55 ]`，代表捕獲成功。

### 2. 將封包轉換為 Hashcat 格式並進行離線破解
```bash
# 使用 hcxpcapngtool 將 .cap 轉為 hashcat 專用 22000 格式
hcxpcapngtool -o hash.hc22000 wpa_handshake-01.cap

# 啟動 Hashcat GPU 字典攻擊 (模式 22000)
hashcat -m 22000 hash.hc22000 rockyou.txt --status
```

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Sigma Rules)

### 1. Splunk SPL：偵測無線 AP 遭受 Deauth 洪水攻擊 (WIDS Alert)
```spl
index=wireless_logs sourcetype="cisco:wlc" "%DOT11-4-DEAUTH_FLOOD"
| rex field=_raw "from rogue source (?<AttackerMAC>[a-fA-F0-9\:]+) targeting client (?<TargetClient>[a-fA-F0-9\:]+)"
| stats count earliest(_time) as first_seen latest(_time) as last_seen by AP_Name, AttackerMAC, TargetClient
| where count >= 10
| convert ctime(first_seen) ctime(last_seen)
| table first_seen, last_seen, AP_Name, AttackerMAC, TargetClient, count
```

### 2. Sigma 偵測規則：Wireless Deauthentication Flood Attack

## 第五動：802.11w 保護管理訊框 (PMF) 與企業身分加固 (Hardening: PMF & 802.1X)

```
[攻擊者嘗試偽造 Deauth 訊框]
              │
              ▼ (發送未經加密簽署之管理訊框)
+-------------------------------------------------------------------------------+
| 啟用 IEEE 802.11w PMF (Protected Management Frames) 之 AP 與終端裝置           |
|  - 管理訊框由 BIP (廣播完整性協定) 進行 AES-CMAC 簽章認證                     |
|  - 辨識出訊框缺少有效金鑰 ➔ 直接丟棄！                                         |
+-------------------------------------------------------------------------------+
              │
              ▼ (連線完全不中斷，攻擊者無法迫使客戶端重發四向握手！)
[彻底封殺握手包抓取與離線破解通道]
```

### 1. 無線基地台強制啟用 IEEE 802.11w (PMF: Required)
在 Cisco WLC 或 OpenWrt 中配置：
```text
# OpenWrt 無線配置 (/etc/config/wireless)
config wifi-iface 'default_radio0'
    option device 'radio0'
    option network 'lan'
    option mode 'ap'
    option ssid 'CORP-SECURE'
    option encryption 'sae-mixed'
    option ieee80211w '2' # 2 代表強制啟用 Protected Management Frames (Required)
```

### 2. 全面淘汰 WPA2-Personal：升級至 WPA2/WPA3-Enterprise (802.1X)
- 淘汰單一共用密碼（PSK）。
- 改用 **EAP-TLS (基於客戶端 X.509 憑證)** 或 **PEAP-MSCHAPv2**，每個使用者擁有獨立動態金鑰，即便單一帳號外洩亦無法側聽全網流量。

### 3. 定期執行射頻頻譜與未授權 AP (Rogue AP) 清查
使用專業 Fluke / NetAlly 空氣分析儀，審查是否存在仿冒公司 SSID 的 Evil Twin 釣魚基地台。

## 靶場實戰：Deauth 攻擊現場抓捕與 PMF 防禦成效驗證

### 靶場環境情境
- **目標企業 AP**: `BSSID: 00:22:33:44:55:66` (SSID: `CORP-TEST`)
- **受害端點**: Windows 11 筆電連線中
- **實戰測試**: 驗證開啟 PMF 前後，攻擊者是否能強行截斷連線並抓獲握手包。

### 實戰步驟一：未設防狀態下之攻擊測試
1. AP 關閉 PMF。攻擊者執行 `aireplay-ng -0 10 ...`。
2. Windows 筆電 WiFi 瞬間斷線，重新連線，Wireshark 順利捕獲 EAPOL Message 1~4。

### 實戰步驟二：啟用 802.11w (PMF)
1. 在 AP 上將 `Management Frame Protection` 設為 `Required`。
2. 攻擊者再次發送 100 個 Deauth 訊框。
3. **結果**：Windows 11 筆電連線毫無波動，封包計數器顯示非法訊框被硬體直接丟棄，攻擊者乾等數十分鐘完全抓不到任何 EAPOL 封包！
