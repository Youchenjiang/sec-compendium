# 07.2 四大 VPN 協定安全性對決與封包取證 (VPN Protocols Security & Packet Forensics)

## 案發現場破題

在遠距辦公與多據點企業網路架構中，虛擬私有網路（Virtual Private Network, VPN）是保護公網傳輸安全的命脈通道。然而，許多企業在 VPN 協定選型與參數配置上存在致命認知偏差——誤以為「只要是 VPN 就具備絕對安全」。事實上，**PPTP、L2TP/IPsec、OpenVPN 與現代的 WireGuard** 在密碼學強度、封包封裝架構與抗中間人攻擊能力上有著天壤之別。在歷史真實資安調查中，攻擊者常透過對 PPTP 的 MS-CHAPv2 進行字典破解、或針對未啟用前向保密（PFS）的 IPsec IKEv1 進行私鑰破解，長驅直入解密所有企業核心傳輸。

```
[外部黑客 / 骨幹網路監聽節點]
       │
       ▼ (攔截公網上的 VPN 隧道封包)
+-------------------------------------------------------------------------------+
| VPN 協定安全性對抗矩陣                                                        |
|                                                                               |
|  [ 情況 A: 遺留老舊 PPTP / L2TP 無加密 ]                                      |
|    └─► MS-CHAPv2 握手 ➔ 透過 hashcat 秒破 NTLM ➔ 流量完全還原為明文！        |
|                                                                               |
|  [ 情況 B: 傳統 IPsec (IKEv1 / 3DES / SHA-1) ]                                 |
|    └─► 易受主模式 Aggressive Mode PSK 字典破解 ➔ 降級攻擊                     |
|                                                                               |
|  [ 情況 C: 現代標準 (IPsec IKEv2-AES-GCM / WireGuard Noise Protocol) ]       |
|    └─► 強制 ECDH 完美前向保密 (PFS) + ChaCha20-Poly1305 認證加密 ➔ 堅不可摧  |
+-------------------------------------------------------------------------------+
       │
       ▼ (黑客面對現代 VPN 封包：除隨機性極高的高熵密文外一無所獲)
[企業遠端連線安全固若金湯]
```

### 痛點場景
- **過期協議殘留（Legacy PPTP Vulnerabilities）**：因相容舊型手持設備或嵌入式工控機，企業邊界閘道器仍開放 PPTP（TCP 1723 / GRE 47），其依賴的 MS-CHAPv2 密碼雜湊已被證實可在數小時內被 GPU 窮舉破解。
- **IPsec AH 協定「零加密」陷阱**：許多初級工程師分不清 IPsec 的 AH（Authentication Header）與 ESP（Encapsulating Security Payload）差異，在需要資料機密性的場景下誤用 AH，導致封包雖能防竄改但內容全為明文。
- **IKEv1 預先共用金鑰（PSK）外洩**：在 IKEv1 的野蠻模式（Aggressive Mode）下，身分雜湊以未加密形式發送，攻擊者只需被動監聽 UDP 500/4500 即可捕獲 PSK 雜湊並離線爆破。

## 第一動：四大 VPN 協定架構、密碼學與封裝深度對決 (Architecture Showdown)

```
+-----------------------------------------------------------------------------------------------+
| 四大 VPN 協定特徵與密碼學架構對照                                                              |
|                                                                                               |
| 1. PPTP (Point-to-Point Tunneling Protocol)                                                   |
|    - 傳輸協定：TCP 1723 (控制通道) + IP Protocol 47 (GRE 數據封裝)                            |
|    - 加密機制：MPPE (RC4 流加密) + MS-CHAPv2 (已被算力徹底攻破)                               |
|    - 評價：【已死協定】嚴禁於任何現代環境中使用。                                             |
|                                                                                               |
| 2. IPsec (IKEv1 vs. IKEv2)                                                                    |
|    - 傳輸協定：UDP 500 / UDP 4500 (NAT-T) + IP Protocol 50 (ESP)                              |
|    - 加密機制：AES-CBC / AES-GCM，支援 Diffie-Hellman 群組交換 (DH Group 14/19/21)            |
|    - 核心關鍵：必須採用 ESP 協定 (具備加密與完整性)，嚴禁單獨使用 AH (僅認證不加密)。         |
|                                                                                               |
| 3. OpenVPN                                                                                    |
|    - 傳輸協定：自訂 UDP 或 TCP (預設 Port 1194)，具備極佳的穿透性與抗封鎖能力。               |
|    - 加密機制：依賴 OpenSSL / TLS 握手 (TLS 1.3)，支援強大的 X.509 憑證雙向認證。             |
|                                                                                               |
| 4. WireGuard                                                                                  |
|    - 傳輸協定：輕量化 UDP (單一連接埠)，代碼量僅約 4,000 行 (相較 OpenVPN 的數十萬行)。        |
|    - 加密機制：固化現代密碼套件 (Noise Protocol Framework, Curve25519, ChaCha20-Poly1305)。    |
|    - 特色：靜默無回應（Silent to unauthenticated packets），免受常規連接埠掃描發現。         |
+-----------------------------------------------------------------------------------------------+
```

### 四大協定核心參數安全決策矩陣

| 評比維度 | PPTP | L2TP / IPsec | OpenVPN | WireGuard |
| :--- | :---: | :---: | :---: | :---: |
| **傳輸層通訊埠** | TCP 1723 + GRE 47 | UDP 500, 4500 + IP 50 | UDP / TCP 1194 | 單一 UDP 埠 (自訂) |
| **對稱加密演算法** | RC4 (極弱) | 3DES (弱) / AES-GCM (強) | AES-256-GCM / ChaCha20 | ChaCha20-Poly1305 (強) |
| **完美前向保密 (PFS)** | ❌ 無 | ⚠️ 需配置 (IKEv2) | ✅ 支援 (DHE/ECDHE) | ✅ 原生強制支援 |
| **抗端口掃描 (Stealth)**| ❌ 易被掃出 | ❌ 易被掃出 | ⚠️ 需配置 tls-auth | ✅ 原生靜默無回應 |
| **代碼攻擊面 (Attack Surface)**| 極高 (歷史漏洞多) | 高 (協定過度複雜) | 中等 (代碼量龐大) | **極低 (僅 4,000 行)** |

## 第二動：封包解構與 Wireshark 取證剖析 (Packet Forensics: AH vs. ESP)

### 1. IPsec AH (Authentication Header - IP Protocol 51) 封包鑑識
在 Wireshark 中檢視 AH 封包：
- IP Header 之後緊接 `Next Header: 51 (AH)`。
- **致命弱點**：AH 僅提供 SHA 完整性校驗碼（ICV），後續的資料負載（Payload）完全以明文形式暴露在公網中！

### 2. IPsec ESP (Encapsulating Security Payload - IP Protocol 50) 封包鑑識
- IP Header 之後緊接 `Next Header: 50 (ESP)`。
- 封包內容包含：`SPI (Security Parameter Index)`、`Sequence Number` 與完全混淆的 `Encrypted Payload`。
- 不具備預先協商金鑰的分析人員無法解密任何封包內容。

## 第三動：VPN 伺服器安全遙測配置 (Telemetry Setup: StrongSwan & OpenVPN)

### 1. StrongSwan (IPsec) 審計日誌強化 (`/etc/strongswan.conf`)
```text
charon {
    filelog {
        /var/log/charon.log {
            time_format = %b %e %T
            ike = 2
            knl = 2
            net = 1
        }
    }
}
```

### 2. 關鍵日誌指紋
- **`IKE_SA establish`**：記錄連線成功的客戶端 IP 與協商之加密套件（如 `AES_GCM_16_256/PRF_HMAC_SHA2_256/MODP_2048`）。
- **`received proposals: ... NO_PROPOSAL_CHOSEN`**：客戶端嘗試使用弱密碼套件或惡意掃描器被強制拒絕。

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Sigma Rules)

### 1. Splunk SPL：偵測客戶端嘗試發起弱加密或已淘汰之 IKEv1 協商
```spl
index=vpn_logs sourcetype="strongswan:charon" "received proposals"
| rex field=_raw "proposals: (?<Proposal>[^\n]+)"
| search Proposal IN ("*3DES*", "*DES*", "*MD5*", "*SHA1*", "*MODP_1024*")
| stats count earliest(_time) as first_seen latest(_time) as last_seen by src_ip, Proposal
| convert ctime(first_seen) ctime(last_seen)
| table first_seen, last_seen, src_ip, Proposal, count
```

### 2. Splunk SPL：偵測 WireGuard 握手重放或認證失敗 (Noise Protocol Handshake)
```spl
index=os_logs kernel="wireguard" "Invalid handshake initiation"
| stats count by _time span=5m, src_ip
| where count >= 10
| table _time, src_ip, count
```

### 3. Sigma 偵測規則：Legacy Insecure VPN Protocol Connection Attempt
```yaml
title: PPTP or Insecure VPN Connection Detected
id: 6a1b2034-77cc-4112-98ab-881122aa3344
status: production
description: 偵測外網設備嘗試向防火牆建立已被淘汰之 PPTP 或弱 IPsec 連線
logsource:
    category: firewall
    product: network
detection:
    selection_pptp:
        dest_port: 1723
    selection_gre:
        ip_protocol: 47
    condition: selection_pptp or selection_gre
level: high
```

## 第五動：現代 VPN 邊界防禦加固基準 (Hardening & Golden Baseline)

```
[遠端工作者] ──► [企業邊界閘道器]
                       │
                       ├── 1. 徹底關閉 TCP 1723 (PPTP) 與 UDP 500 (強制僅允許 IKEv2 / WireGuard)
                       ├── 2. 強制前向保密 (PFS: DH Group 19 / ECP 256 以上)
                       ├── 3. 強制雙因素憑證認證 (X.509 Certificate + MFA)
                       ▼
              [建立安全不可破解之專屬加密通道]
```

### 1. StrongSwan 強制 IKEv2 與 AES-GCM 安全套件配置 (`ipsec.conf`)
```text
conn corporate-secure-vpn
    keyexchange=ikev2
    ike=aes256gcm16-prfsha384-ecp384,aes128gcm16-prfsha256-ecp256!
    esp=aes256gcm16-ecp384,aes128gcm16-ecp256!
    dpdaction=clear
    dpddelay=30s
    auto=add
```

### 2. 淘汰全網所有預先共用金鑰（Preshared Key, PSK）
全面轉型為以企業私有 PKI（如 CFSSL 或 Vault）簽發的 X.509 機器憑證或使用 WireGuard 公私鑰對，徹底消除密碼爆破風險。

## 靶場實戰：IPsec AH 明文外洩鑑識與 IKEv2 升級

### 靶場環境情境
- **企業邊界**: `FW-EDGE-01`
- **突發事件**: 內部資安稽核發現，外派同仁連線至總部時傳輸的機密 PDF 合約，遭上游電信節點直接側聽。

### 實戰步驟一：封包鑑識
1. 抓取連線封包：發現協議欄位為 `IP Protocol 51 (AH)`。
2. 追蹤 TCP 流：合約內容完全未經加密，明文赫然在目！確認配置失誤採用了「純認證不加密」的 AH 模式。

### 實戰步驟二：緊急升級處置
1. 停用 AH 轉換集（Transform Set），全面改用 `esp-aes 256` 與 `esp-sha256-hmac`。
2. 將連線協商強制切換至 IKEv2，啟用 DH Group 19（Curve25519）。

### 實戰步驟三：驗證加固
1. 重新發起 VPN 連線，抓取新封包：協定確認變更為 `Protocol 50 (ESP)`。
2. 檢視負載資料，呈現高熵密文，側聽攻擊徹底失效。
