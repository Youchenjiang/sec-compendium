## 🧩 第一動：底層機制解剖——EPROCESS 與雙向鏈表如何運作？

在 Windows 核心態（Kernel Mode）中，每一個運行的處理程序都由一個名為 **`EPROCESS` (Executive Process Block)** 的核心資料結構所代表。

### 1.1 `ActiveProcessLinks` 雙向環狀鏈表 (Circular Doubly Linked List)

為了讓作業系統能夠列舉當前運行的所有進程，Windows 將所有 `EPROCESS` 物件透過一個成員欄位 **`ActiveProcessLinks` (`LIST_ENTRY`)** 串接成一條首尾相連的環狀雙向鏈表：

```
[Windows 核心態 EPROCESS 環狀鏈表結構]

       ┌─────────────────────────────────────────────────────────────┐
       │                                                             │
       ▼                                                             │
┌──────────────┐         ┌──────────────┐         ┌──────────────┐   │
│ EPROCESS (A) │         │ EPROCESS (B) │         │ EPROCESS (C) │   │
│ [System 4]   │         │ [smss 340]   │         │ [malware]    │   │
├──────────────┤         ├──────────────┤         ├──────────────┤   │
│ ImageFileName│         │ ImageFileName│         │ ImageFileName│   │
│ UniqueProcId │         │ UniqueProcId │         │ UniqueProcId │   │
│              │         │              │         │              │   │
│ ActiveProcess│ Flink ─►│ ActiveProcess│ Flink ─►│ ActiveProcess│ Flink ─┘
│    Links     │◄─ Blink │    Links     │◄─ Blink │    Links     │◄─ Blink (繞回 A)
└──────────────┘         └──────────────┘         └──────────────┘
```

- **`Flink` (Forward Link)**：指向鏈表中下一個進程的 `ActiveProcessLinks` 位址。
- **`Blink` (Backward Link)**：指向鏈表中前一個進程的 `ActiveProcessLinks` 位址。
- **用戶態 API 的盲點**：所有 Windows 用戶態 API（如 `EnumProcesses`、`CreateToolhelp32Snapshot`）以及內建命令（`tasklist`、PowerShell `Get-Process`），本質上都是順著這條 `ActiveProcessLinks` 鏈表一路向前巡訪遍歷。

---

### 1.2 DKOM (Direct Kernel Object Manipulation) 斷鏈原理

當攻擊者的 Rootkit 驅動獲得核心權限後，執行以下指標替換操作：
1. 將進程 B 的 `Flink` 直接改為指向進程 D。
2. 將進程 D 的 `Blink` 直接改為指向進程 B。
3. 進程 C（惡意木馬）的 `ActiveProcessLinks` 徹底脫離主鏈條！

```
[DKOM 斷鏈脫鉤效果]

┌──────────────┐                             ┌──────────────┐
│ EPROCESS (B) │ ─────── Flink (跳過 C) ────►│ EPROCESS (D) │
│              │◄─────── Blink (跳過 C) ─────│              │
└──────────────┘                             └──────────────┘
                                
                 ┌──────────────┐
                 │ EPROCESS (C) │  <-- 雖然斷鏈脫鉤，但其線程 (ETHREAD) 
                 │ [惡意木馬]   │      依然被 CPU 執行緒排程器排程執行！
                 └──────────────┘      木馬仍活躍運行，但對作業系統「隱形」！
```

> 💡 **鑑識人員的破局點**：
> - 雖然進程 C 不在 `ActiveProcessLinks` 鏈表上了，但它佔用的記憶體空間並未釋放！
> - 其 `EPROCESS` 結構在實體記憶體池中依然保留著微軟的核心記憶體池標記（Pool Tag，通常為 `Proc`）。
> - **`windows.pslist`**：依循 `ActiveProcessLinks` 遍歷 ➔ **看不到隱藏進程！**
> - **`windows.psscan`**：跳過鏈表，直接在整顆記憶體中進行 Pool Tag 特徵掃描 ➔ **能找到所有活著與死去的 EPROCESS！**
> - **「`psscan` 有，但 `pslist` 沒有」= 鐵證如山的 DKOM 隱藏進程！**

## 🧭 第二動：解碼意圖——記憶體進程異常速查表

在記憶體鑑識時，分析師需要比對各種進程列舉插件的輸出，以下為常見攻擊特徵速查：

### 2.1 記憶體進程異常特徵速查表

| 記憶體鑑識特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **`psscan` 出現該 PID，但 `pslist` 完全空白** | **DKOM 雙向鏈表斷鏈（Process Unlinking）**：<br>Rootkit 核心驅動修改了 `ActiveProcessLinks`，使進程從系統鏈表中脫鉤。 | • **影響**：存在核心態 Rootkit，全機防線已潰敗。<br>• **處置優先級**：緊急（立即斷網保留 RAM，啟動離線分析）。 |
| **`ExitTime` 為空白，但進程無法在活動列表中找到** | **活動進程遭隱藏（Active Hidden Process）**：<br>若 `ExitTime` 有時間，代表是正常退出的歷史進程；若 `ExitTime` 為空，代表進程「目前依然在記憶體中活躍運行」。 | • **影響**：惡意代碼正在本機執行並消耗資源。<br>• **處置優先級**：緊急（定位其記憶體映射位址並 Dump）。 |

| **`ImageFileName` 包含非 ASCII 字符或尾隨空格** | **進程名稱混淆與字元欺騙**：<br>在二進位檔名後插入空白（如 `svchost.exe `）或利用不可見字元，迷惑管理者。 | • **影響**：常規字串匹配規則失效。<br>• **處置優先級**：高（提取完整路徑與 SHA256 比對）。 |
| **進程的 `Handles` 數量高達數萬且集中於某個核心驅動** | **驅動句柄洩漏或通訊通道（IOCTL Abuse）**：<br>木馬進程與其後門驅動維持密集的通訊，或正在批量讀取系統進程 Token。 | • **影響**：正在進行全機權限接管或憑證竊取。<br>• **處置優先級**：高（列舉 Handles 關聯驅動物件）。 |

### 3.2 自動化 DKOM 幽靈進程差集獵捕腳本 (`find_dkom.py`)

手動用眼睛看幾百個 PID 容易眼花撩亂。以下提供生產級 Python 鑑識腳本，自動比對 `pslist` 與 `psscan`，精準過濾已正常退出的歷史進程，一秒抓出**「依然活著但被 DKOM 隱藏的幽靈」**：

```python
#!/usr/bin/env python3
# find_dkom.py - 記憶體進程差異自動分析器
import sys

def parse_pslist(filepath):
    visible_pids = set()
    with open(filepath, 'r', encoding='utf-8', errors='ignore') as f:
        for line in f:
            parts = line.split()
            if len(parts) >= 3 and parts[0].isdigit():
                visible_pids.add(int(parts[0]))
            elif len(parts) >= 3 and parts[1].isdigit():
                visible_pids.add(int(parts[1]))
    return visible_pids

def analyze_dkom(pslist_file, psscan_file):
    visible_pids = parse_pslist(pslist_file)
    print(f'[*] pslist 正常鏈表進程數: {len(visible_pids)}')
    dkom_candidates = []
    with open(psscan_file, 'r', encoding='utf-8', errors='ignore') as f:
        for line in f:
            parts = line.split()
            if len(parts) < 6:
                continue
            pid = None
            for item in parts[1:3]:
                if item.isdigit():
                    pid = int(item)
                    break
            if pid is not None and pid not in visible_pids:
                is_active = ('N/A' in line or '-' in line[50:] or 'None' in line)
                dkom_candidates.append({'raw': line.strip(), 'pid': pid, 'is_active': is_active})
    print(f'🚨 DKOM 幽靈進程排查報告 (共抓獲 {len(dkom_candidates)} 個未在鏈表之物件)')
    active_count = 0
    for cand in dkom_candidates:
        if cand['is_active']:
            active_count += 1
            print(f'[!] 🔴 確鑿 DKOM 隱藏活動進程 (PID: {cand["pid"]})')
        else:
            print(f'[*] ⚪ 歷史死亡殘留進程 (PID: {cand["pid"]})')
    if active_count == 0:
        print('[+] 恭喜！未發現活體 DKOM 斷鏈隱藏進程。')
    else:
        print(f'[!] 警告: 發現 {active_count} 個高危險活體隱藏進程！')

if __name__ == '__main__':
    if len(sys.argv) < 3:
        print('用法: python find_dkom.py <pslist.txt> <psscan.txt>')
        sys.exit(1)
    analyze_dkom(sys.argv[1], sys.argv[2])
```

### 3.3 導出隱藏進程的二進位檔案與記憶體映像

一旦鎖定 DKOM 隱藏的 PID（例如 `4820`），立即導出其實體檔案進行靜態分析：

```bash
# 1. 導出該進程所有可執行的記憶體映射區塊 (Dump Memory)
vol -f SRV-OPS-CORE.raw -o output/ windows.memmap --pid 4820 --dump

# 2. 導出該進程對應的 PE 檔案 (Dump Executable)
vol -f SRV-OPS-CORE.raw -o output/ windows.dumpfiles --pid 4820

# 3. 查看該隱藏進程建立了哪些網路連線 (關聯 Netscan)
vol -f SRV-OPS-CORE.raw windows.netscan | grep 4820
```

## ⚖️ 第四動：研判分水嶺——正常短命進程 vs 惡意 DKOM 隱藏？

在記憶體鑑識中，並非所有「在 `psscan` 出現但不在 `pslist` 出現」的進程都是黑客搞的！分析師必須具備區分**「正常已終止進程殘留」**與**「真正惡意 DKOM 斷鏈」**的專業直дж：

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 主機存在未知連線，但本機進程清單完全看不到對應 PID，或 Volatility 比對發現不一致。 |
| **Q2. 退出時間戳**（ExitTime 是否為空？） | **最重要的分水嶺**！正常已死進程的 `ExitTime` 必有時間戳；而 DKOM 隱藏進程的 `ExitTime` 必為 `N/A` 或空值。 |
| **Q3. 執行緒活躍度**（該進程名下是否有活躍 ETHREAD？） | 使用 `windows.threads` 檢查：若該進程名下仍有執行緒處於 `Running` 或 `Waiting`，代表 CPU 正在執行它！ |
| **Q4. 記憶體控制代碼**（是否有開啟的網路通訊埠/檔案控制代碼？） | 使用 `windows.handles` 與 `netscan`：該進程是否持有活動的 Socket 或檔案讀寫鎖？ |
| **Q5. 進程名稱合規**（ImageFileName 是否為隨機字符或冒名？） | 是否命名為混淆名稱，或者偽造為 `svchost.exe` 但位於使用者目錄？ |
| **Q6. 伴隨核心模組**（系統中是否載入了未簽名的 .sys 驅動？） | DKOM 必須透過內核態執行。使用 `windows.modules` 與 `driverscan` 檢查是否有未簽名的黑客 Rootkit 驅動！ |
| **Q7. 橫向波及**（全網其他主機是否出現相同的連線或檔案？） | 將導出的隱藏 PE 計算 SHA256，至 SIEM 全網檢索其餘主機是否存在相同落地記錄。 |
| **Q8. 處置動作**（下一步是什麼？） | 1. 保留記憶體鏡像；2. 提取惡意二進位檔；3. 隔離主機並重灌（核心遭破壞不可輕易信任復原）。 |

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

一旦在記憶體中證實存在 DKOM 攻擊，意味著作業系統的內核防線已經徹底被擊穿，一般的殺毒軟體或工作管理員已經失去意義：

### 1. 第一步：現場應急圍堵（切勿直接按重開機）
- **保留證據**：在切斷電源前，務必先使用外接硬碟執行實體記憶體採集（如利用 DumpIt 或 FTK Imager CLI）。
- **網路實體隔離**：拔除網路線或在交換機端將埠設為 `Shutdown`，防止攻擊者遠端下達自我銷毀指令（Wipe）。

### 2. 第二步：找出下毒的幕後黑手——未簽名 Rootkit 驅動
DKOM 不可能憑空發生，必定伴隨一個內核驅動模組。在 Volatility 中定位它：
```bash
# 掃描記憶體中所有的內核驅動物件 (Driver Objects)
vol -f SRV-OPS-CORE.raw windows.driverscan > drivers.txt

# 列出所有已載入的模組並比對數位簽章
vol -f SRV-OPS-CORE.raw windows.modules
```

### 3. 第三步：根除與架構加固——啟用 HVCI 核心記憶體完整性
要從根本上杜絕 DKOM 攻擊，必須在企業環境強制推行**基於虛擬化的安全性 (VBS)**：
- **開啟核心隔離與記憶體完整性 (HVCI - Hypervisor-Protected Code Integrity)**：
  - 在 GPO 中配置：`電腦設定` ➔ `系統管理範本` ➔ `系統` ➔ `Device Guard` ➔ `開啟以虛擬化為基礎的安全性`。
  - HVCI 利用 CPU 虛擬化擴展技術（VT-x / AMD-V），將核心記憶體頁表交由 Hypervisor（微軟微內核）保護。
  - 即使攻擊者的驅動進入了 Ring 0，也**無法直接修改被標記為唯讀的核心物件指標（如 `ActiveProcessLinks`）**，直接在硬體層阻斷 DKOM 篡改！

## 📋 過關驗收檢查點 (Mastery Checklist)

以下為本專案的 5 大實戰驗收問題與標準專家解析：

- [x] **Q1：在 Windows 核心架構中，為什麼一般的用戶態工具（如工作管理員、PowerShell、甚至是普通 EDR Agent）無法看到遭到 DKOM 斷鏈隱藏的進程？**
  > **標準答案**：
  > 1. **資料存取邊界與 API 依賴**：用戶態應用程式運行於 Ring 3，受到 CPU 記憶體保護限制，無法直接讀取核心態虛擬位址空間。所有列舉進程的用戶態 API（如 Win32 `EnumProcesses`、Toolhelp32、NTAPI `NtQuerySystemInformation`）在底層都必須呼叫 Windows 核心提供的系統調用。
  > 2. **核心巡訪單一路徑**：Windows 核心的進程列舉函數，完全是依賴於遍歷由 `EPROCESS` 中的 `ActiveProcessLinks` 所串接成的雙向環狀鏈表。
  > 3. **致盲結果**：當攻擊者的 Rootkit 驅動在 Ring 0 將目標進程的前後指標跳過（斷鏈）後，核心遍歷函數自然無法在鏈表上看到該進程，進而向用戶態回傳「不存在該進程」的假象，造成所有依賴正規 API 的監控工具全部被致盲。

- [x] **Q2：Volatility 3 的 `windows.pslist` 與 `windows.psscan` 在底層探測機制上有什麼根本不同？為什麼兩者的差集能抓出 DKOM？**
  > **標準答案**：
  > 1. **`windows.pslist` 的探測機制**：
  >    它模擬了作業系統的常規列舉邏輯。它首先定位全域變數 `PsActiveProcessHead`（雙向鏈表頭部），接著順著指標 `Flink` 一個接一個地讀取每個節點的 `EPROCESS` 結構。如果某個進程脫鉤了，`pslist` 就絕對找不到它。
  > 2. **`windows.psscan` 的探測機制**：
  >    它採用「記憶體特徵池掃描（Pool Tag Scanning）」。它完全不看任何鏈表，而是從實體記憶體的起點開始，像搜尋引擎一樣逐頁掃描 4-Byte 的核心記憶體池簽章。在 64 位元 Windows 中，分配給 `EPROCESS` 的記憶體塊通常帶有標記 `Proc`。
  > 3. **差集的物理意義**：
  >    只要物件分配在記憶體中，無論它是否在鏈表上，`psscan` 都能把它掃出來。因此，`psscan` 找到的物件減去 `pslist` 找到的物件，得到的差集就是「不在主鏈表上，但依然佔用記憶體」的進程。若其尚未退出，即為確鑿的 DKOM 隱藏進程。

- [x] **Q3：在比對 `pslist` 與 `psscan` 的差異時，如果發現某個 PID 只出現在 `psscan` 中，在判定其為「惡意 DKOM 攻擊」前，你必須先檢查哪一個關鍵欄位？為什麼？**
  > **標準答案**：
  > 1. **必須檢查的關鍵欄位**：**`ExitTime`（進程退出時間戳）**。
  > 2. **背後的系統機制**：當正常進程終止時，Windows 會將其從 `ActiveProcessLinks` 鏈表中移除，並寫入 `ExitTime`。但是，只要有其他進程依然持有該進程的開啟代碼（Open Handle），或者 Windows 核心記憶體管理員（Memory Manager）尚未將該記憶體頁回收重分配，該 `EPROCESS` 結構就會繼續殘留在 RAM 中。
  > 3. **研判準則**：若 `ExitTime` 具有正常的歷史時間戳，代表這只是一個剛剛退出、尚未被垃圾回收的正常死亡進程殘留（Dead Process），絕非攻擊；**唯有當 `ExitTime` 為空（`N/A` 或 `None`），且其名下仍有活躍調度中的執行緒時，才能 100% 定性為惡意 DKOM 斷鏈隱藏**。

- [x] **Q4：如果一個進程已經被從 `ActiveProcessLinks` 雙向鏈表中斷開了，為什麼它名下的木馬代碼依然能夠持續在 CPU 上運行並與外界連線？**
  > **標準答案**：
  > 1. **排程器與鏈表職責分離**：Windows 核心的 **CPU 執行緒排程器（Scheduler / Dispatcher）從來不是根據 `ActiveProcessLinks` 來決定誰該運行的**！
  > 2. **調度單位的本質**：Windows 的最小執行調度單位是 **執行緒（`ETHREAD`）**，而不是進程。排程器管理著多個就緒佇列（Ready Queues / Dispatcher Ready Queues），這些佇列中存放的是處於等待或就緒狀態的 `ETHREAD` 指標。
  > 3. **斷鏈不影響排程**：攻擊者雖然斷開了 `EPROCESS` 鏈表，但該進程所屬的 `ETHREAD` 物件依然掛在 CPU 核心調度佇列中。時鐘中斷一到，CPU 依然會把時間片（Quantum）分給該木馬執行緒執行代碼；而該執行緒建立的 TCP Socket 也依然掛在網路傳輸控制塊（TCB）中，因此木馬能完全不受影響地持續運行與外聯。

- [x] **Q5：在作業系統層級，為什麼微軟的 HVCI（Hypervisor-Protected Code Integrity，核心記憶體完整性）能夠終結傳統的 DKOM 斷鏈手法？**
  > **標準答案**：
  > 1. **傳統 Ring 0 的防禦失效**：在沒有虛擬化安全前，Ring 0 是最高權限。一旦攻擊者的漏洞利用代碼進入 Ring 0，它與作業系統核心平起平坐，可以任意改寫核心記憶體的任何位址（包含關閉寫入保護旗標 CR0.WP）。
  > 2. **VBS / HVCI 的降維打擊**：HVCI 構建在 Type-1 Hypervisor 之上，將系統切分為 VTL 0（普通 Windows 核心）與 VTL 1（安全隔離環境）。
  > 3. **二級頁表保護（SLAT / EPT）**：HVCI 利用硬體輔助虛擬化技術，將 Windows 核心關鍵資料結構（如 CR3、核心代碼頁、重要物件安全指標）的記憶體頁屬性設置為唯讀。當位於 VTL 0 Ring 0 的惡意 Rootkit 嘗試寫入記憶體修改 `ActiveProcessLinks` 時，硬體會觸發 VM-Exit（EPT 違規中斷），直接被 Hypervisor 攔截並強制藍屏當機（BSOD），使得惡意程式再也無法在內核層肆意篡改核心物件結構。
