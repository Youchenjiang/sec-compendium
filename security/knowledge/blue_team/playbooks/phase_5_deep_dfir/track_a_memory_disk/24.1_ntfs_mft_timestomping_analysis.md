## 🧩 第一動：底層機制解剖——NTFS $MFT 與雙重時間戳體系

### 1.1 NTFS 核心架構與 $MFT 主檔案表
NTFS (New Technology File System) 是現代 Windows 系統的預設檔案系統。在 NTFS 中，**「一切皆為檔案」**。磁碟上的每一個檔案與目錄，都在一個名為 **`$MFT` (Master File Table)** 的隱藏系統元檔案（Metafile）中擁有一筆或多筆固定長度為 **1024 位元組 (1 KB)** 的記錄（MFT Record / FILE Record）。

每個 MFT 記錄的結構由一個開頭為 `FILE` (0x454C4946) 的固定標頭與多個可變長度的「屬性 (Attributes)」所組成：
```
┌───────────────────────────────────────────────────────────┐
│              1024-Byte MFT Record (FILE Record)           │
├───────────────┬───────────────────────────────────────────┤
│ Record Header │ Magic: 'FILE', LSN, Sequence Number...    │
├───────────────┼───────────────────────────────────────────┤
│ Type: 0x10    │ $STANDARD_INFORMATION ($SI)              │
│               │ 包含常規屬性 (唯讀/隱藏) 與 4 重時間戳 (MACB)│
├───────────────┼───────────────────────────────────────────┤
│ Type: 0x30    │ $FILE_NAME ($FN)                          │
│               │ 包含檔案名稱、父目錄 Record 號 與 4 重時間戳 │
├───────────────┼───────────────────────────────────────────┤
│ Type: 0x80    │ $DATA                                     │
│               │ 實際檔案內容 (常駐 Resident 或 非長駐 Non-Res) │
└───────────────┴───────────────────────────────────────────┘
```

### 1.2 雙重時間戳體系：$STANDARD_INFORMATION vs $FILE_NAME
在每個檔案的 MFT 紀錄中，記錄了兩套完整的 **MACB 時間戳**（Modified, Accessed, Created / Born, MFT Entry Modified）：
1. **`$STANDARD_INFORMATION` (`$SI`, 屬性代碼 0x10)**：
   - **面向應用程式**：提供給 Windows 用戶態 API（如 `GetFileTime`、`SetFileTime`）、檔案總管、PowerShell 使用。
   - **容易被竄改**：任何具有本機管理員或檔案寫入權限的使用者模式程式，都可以呼叫 Win32 API `SetFileTime`，隨意將 `$SI` 改成過去或未來的任何時間。
2. **`$FILE_NAME` (`$FN`, 屬性代碼 0x30)**：
   - **面向檔案系統核心**：由 NTFS 核心驅動程式（`ntfs.sys`）維護，用於目錄索引（B-Tree 檢索）與檔案路徑解析。
   - **核心鎖定保護**：Windows **沒有公開任何常規 API 允許用戶態修改 `$FN` 時間戳**！只有當檔案被「重命名（Rename）」或「搬移到不同目錄（Move across directories on same volume）」時，NTFS 核心才會將當下的時間同步更新至 `$FN`。

### 1.3 Timestomping 攻擊的物理特徵與破綻
當攻擊者使用工具將惡意後門的時間改成 2019 年時：
1. **指標衝突（Discrepancy）**：
   - 惡意工具修改的僅僅是 `$SI` 的四個時間戳。
   - `$FN` 依然固執地記錄著該檔案於 2026 年寫入磁碟時的真實時間戳！
   - **鑑識破局定理**：若一個檔案的 `$SI.Created` 遠遠早於 `$FN.Created`（例如 `$SI` 顯示為 5 年前，而 `$FN` 顯示為今天凌晨），即可 100% 判定該檔案遭到了 Timestomping 竄改！
2. **奈秒級精度填零異常 (Nanosecond Zeroing)**：
   - Windows 內部時間戳的物理精度為 **100 奈秒 (100-nanosecond intervals)**，在十六進位中以 64 位元整數表示。
   - 許多初階 Timestomping 工具（或舊版 API）在改寫時間時，只支援微秒或秒級精度，會將奈秒位元全部填零（例如結尾為 `.0000000`）。若在一堆高精度奈秒的系統檔案中出現零頭全平的時間戳，即為重大嫌疑。

### 3.2 自動化 Timestomping 差集獵捕腳本 (`detect_timestomping.py`)

以下 Python 腳本直接解析 MFTECmd 產生的 CSV 報表，自動比對 `$SI` 與 `$FN` 的時間戳差異，並揪出所有奈秒填零與時間倒掛的惡意檔案：

```python
#!/usr/bin/env python3
"""
detect_timestomping.py - Automated NTFS $SI vs $FN Timestamp Discrepancy Analyzer
Parses MFTECmd CSV exports to detect Timestomping anomalies and zeroed nanoseconds.
"""

import sys
import csv
from datetime import datetime
from pathlib import Path

def parse_iso_time(time_str: str):
    if not time_str or time_str.strip() == "":
        return None
    try:
        # Expected formats: 2026-09-14 15:40:22.1234567 or similar
        return datetime.fromisoformat(time_str.strip().replace("Z", ""))
    except ValueError:
        return None

def analyze_mft_csv(csv_path: Path):
    print(f"[*] Analyzing MFT CSV: {csv_path.name}")
    suspect_count = 0
    
    with open(csv_path, "r", encoding="utf-8-sig", errors="ignore") as f:
        reader = csv.DictReader(f)
        for row in reader:
            filename = row.get("FileName", "")
            filepath = row.get("ParentPath", "") + "\\" + filename
            
            # Extract $SI and $FN Created (Born) timestamps
            si_created_str = row.get("Created0x10", "")
            fn_created_str = row.get("Created0x30", "")
            
            si_created = parse_iso_time(si_created_str)
            fn_created = parse_iso_time(fn_created_str)
            
            if not si_created or not fn_created:
                continue
                
            # Rule 1: $SI Created is significantly EARLIER than $FN Created (> 60 seconds)
            time_diff = (fn_created - si_created).total_seconds()
            
            # Rule 2: Check for zeroed subseconds in $SI
            is_zeroed = False
            if "." in si_created_str:
                subsec = si_created_str.split(".")[-1]
                if subsec.startswith("0000") or subsec == "0000000":
                    is_zeroed = True
                    
            if time_diff > 60:
                suspect_count += 1
                print(f"\n🚨 [TIMESTOMPING DETECTED] File: {filepath}")
                print(f"    $SI Created (User API) : {si_created_str}")
                print(f"    $FN Created (Kernel NTFS) : {fn_created_str}")
                print(f"    Discrepancy Gap        : {time_diff / 86400:.1f} days earlier!")
                if is_zeroed:
                    print("    ⚠️  Nanoseconds zeroing anomaly detected!")
                    
    print("=" * 70)
    print(f"[+] Scan completed. Total Timestomping suspects identified: {suspect_count}")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python detect_timestomping.py <mftecmd_output.csv>")
        sys.exit(1)
    analyze_mft_csv(Path(sys.argv[1]))
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (操作帳號)**：檔案目前的擁有者（Security ID / SID）為何？是否屬於特權群組？
2. **What (檔案型態)**：該檔案是可執行檔（.exe/.dll/.sys）還是常規文檔？
3. **Where (目錄位置)**：檔案是否存放在敏感的系統核心目錄（如 `System32`、`SysWOW64`、`ProgramData`）？
4. **When (真實寫入時點)**：`$FN` 記錄的真實寫入時間點，是否與警報告警日誌時間重合？
5. **Why (更新理由)**：是否有 Windows Update 或軟體安裝排程在該時段執行？
6. **How (時間偽造手法)**：`$SI` 時間戳是否精確對齊至鄰近的特定系統檔案（例如故意偽裝成 `kernel32.dll` 的時間）？
7. **Impact (受害深度)**：該偽造檔案是否被加入開機自啟動註冊表或服務項目？
8. **Confidence (研判信心度)**：`$SI` 與 `$FN` 時間戳存在大於數天之差距，研判信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：製作唯讀鑑識映像保全現場
- **嚴禁於受害線上機直接分析**：即時分析操作（如查看屬性、移動檔案）會動態刷新 `$SI.Accessed` 時間戳，破壞現場。

- **解析更新序號日誌 ($UsnJrnl:$J)**：NTFS 的 USN Journal 記錄了每一次磁碟寫入、更名、刪除的事務。攻擊者就算改了 `$SI`，在 USN Journal 中依舊會留下一筆 `USN_REASON_BASIC_INFO_CHANGE` 的歷史日誌！

### 3. 第三步：清除持久化與惡意檔案
- **強制刪除惡意二進位**：在確認時間軸後，將該檔案與其父層 Dropper 完整刪除。
- **清除關聯排程**：移除利用假時間戳躲避審計的排程工作與服務。

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：為什麼在 NTFS 檔案系統中，一般用戶態的竄改工具只能修改 `$STANDARD_INFORMATION` (`$SI`)，而無法修改 `$FILE_NAME` (`$FN`)？**
  > **標準答案**：
  > 1. **API 設計邊界**：微軟公開的 Win32 API（如 `SetFileTime`）僅提供修改檔案元資料的通用介面。Windows 核心在實作該 API 時，設計上只會對 `$STANDARD_INFORMATION` 屬性區段的時間戳進行寫入。
  > 2. **NTFS 內部結構完整性依賴**：`$FILE_NAME` 屬性不僅僅儲存時間，它更作為 NTFS 檔案系統 B-Tree 目錄索引樹的鍵值（Index Entry）。為了維護磁碟索引架構的一致性與防竄改，Windows 核心驅動（`ntfs.sys`）將 `$FN` 的修改權限牢牢鎖定在核心內部，完全不對外開放修改介面。

- [x] **Q2：如果攻擊者使用直接磁碟寫入工具（Raw Disk Write）將 `$SI` 與 `$FN` 的時間戳同時改成了 2019 年，鑑識人員如何從 NTFS 檔案系統中識破這場騙局？**
  > **標準答案**：
  > 1. **透過 `$UsnJrnl` (更新序號日誌) 交叉驗證**：NTFS 的 `$UsnJrnl:$J` 依序記錄了所有檔案系統操作。攻擊者修改時間會產生一筆帶有操作時真實時間戳的 `BASIC_INFO_CHANGE` 記錄，時間戳無從抵賴。
  > 2. **透過 `$LogFile` (交易記錄檔) 還原**：NTFS 為日誌型檔案系統，任何磁碟交易在提交前均會寫入 `$LogFile`，其中保留了檔案被改寫前的前後鏡像歷史。
  > 3. **MFT 記錄號與序號反常 (Record Sequence Anomaly)**：磁碟的 MFT Record 號碼是循序遞增分配的。一個聲稱在 2019 年建立的檔案，其 MFT 記錄號卻高達數十萬，遠大於周邊 2026 年建立的檔案，在統計時序上形成無法解釋的倒掛悖論。

- [x] **Q3：何謂「奈秒微秒填零異常 (Nanosecond Zeroing)」？它為什麼能作為 Timestomping 的強烈指紋？**
  > **標準答案**：
  > 1. **Windows 內部時間精度**：NTFS 檔案時間（FILETIME）以 100 奈秒為計數單位（1 秒 = 10,000,000 個間隔）。正常的作業系統事件寫入時，其奈秒欄位必然包含隨機分佈的微細數值。
  > 2. **第三方工具的參數精度限制**：多數攻擊工具使用舊版 C 函式庫或秒級時間轉換函數，在呼叫 API 時只傳遞秒或微秒，導致剩餘的低位奈秒直接被填入 `0`（例如 `15:40:22.0000000`）。
  > 3. **指紋意義**：在成千上萬個帶有高精度小數點的正常系統檔案中，一個小數點後為全零的時間戳具有極高的異常統計顯著性，可直接視為人為竄改的鐵證。

- [x] **Q4：在進行檔案系統鑑識時，若看到某個檔案的 `$SI.Modified` 晚於 `$FN.Modified`，這是否意味著 Timestomping？請說明理由。**
  > **標準答案**：
  > 1. **不是 Timestomping，而是完全正常的日常現象**！
  > 2. **檔案編輯的自然行為**：當使用者在主機上打開已存在的文件並進行編輯存檔時，NTFS 會更新該檔案的 `$SI.Modified` 與 `$SI.Accessed` 時間戳；但是，只要檔案沒有被重新命名或跨磁區搬移，`$FN` 中的時間戳就會**保持最初建立時的數值不變**。
  > 3. **研判分水嶺法則**：**唯有當 `$SI.Created`（建立時間）「顯著早於」`$FN.Created` 時**，才符合惡意向過去偽造時間的 Timestomping 特徵！反向的晚於通常屬於常態。

- [x] **Q5：如何防範攻擊者在 Windows 端點上實施 Timestomping？企業內部可推行哪些縱深防禦措施？**
  > **標準答案**：
  > 1. **即時集中化日誌外傳 (SIEM Telemetry Streaming)**：在端點產生檔案建立與修改的瞬間，透過 Sysmon（Event ID 11 - FileCreate）即時將真實時間戳串流傳輸至中央 SIEM，讓日誌落地於遠端不可變的 WORM 儲存設備中，使後續本機的改寫無濟於事。
  > 2. **限制特權與啟用檔案系統完整性監控 (FIM)**：透過端點 EDR 監控針對系統目錄（如 `System32`）的檔案建立與屬性變更事件，警報非受信任二進位檔案呼叫 `SetFileTime`。
  > 3. **唯讀保護與微隔離**：核心系統目錄禁止一般管理員與使用者進行未經變更管制的寫入操作，阻斷惡意程式釋放與落地空間。
