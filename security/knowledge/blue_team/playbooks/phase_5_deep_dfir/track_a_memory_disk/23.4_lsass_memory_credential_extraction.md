## 🧩 第一動：底層機制解剖——LSASS 認證體系與剪貼簿暫存機制

### 1.1 LSASS (Local Security Authority Subsystem Service) 架構
`lsass.exe` 是 Windows 安全子系統的核心進程（PID 通常固定，由 `wininit.exe` 啟動）。它負責強制執行系統安全性原則、驗證本機與網域登入、以及維護目前使用者的認證憑據（Credentials）。

為了支援多樣化的認證協定，LSASS 內部載入了多個 **安全支援提供者 (Security Support Providers, SSP)** DLL：
1. **`msv1_0.dll` (MSV1_0 SSP)**：負責處理本機驗證與 NTLM 挑戰/回應協定。記憶體中快取了使用者的 LM/NTLM 雜湊值（用於跨網路驗證）。
2. **`kerberos.dll` (Kerberos SSP)**：負責 Kerberos 驗證。快取了使用者的 Kerberos AES-128/256 金鑰、TGT 認證票據以及已索取的 TGS 服務票據。
3. **`wdigest.dll` (WDigest SSP)**：早期用於 HTTP 摘要驗證。歷史版本中會直接在記憶體中存放**可逆解密的明文密碼**！
4. **`dpapisrv.dll` (DPAPI)**：提供資料保護 API 服務，快取解密瀏覽器密碼、VPN 認證、憑證私鑰所必需的 **DPAPI Master Keys**。

```
┌───────────────────────────────────────────────────────────┐
│              lsass.exe (User Mode, Ring 3)                │
├───────────────────────────────────────────────────────────┤
│  [MSV1_0.dll]     │ NTLM Hashes, LM Hashes               │
│  [Kerberos.dll]   │ TGT / TGS Tickets, AES Session Keys   │
│  [WDigest.dll]    │ 明文快取 (若 UseLogonCredential=1)     │
│  [CloudAP.dll]    │ Azure AD / Entra ID PRT Primary Token │
│  [DPAPI]          │ Master Keys (GUID + 512-bit Key)      │
└─────────────────────┬─────────────────────────────────────┘
                      │ 讀取保護 (OpenProcess / PROCESS_VM_READ)
                      ▼
        [攻擊者調用 MiniDumpWriteDump / ProcDump]
```

### 1.2 憑證抓取本質剖析 (Credential Dumping Mechanics)
攻擊者竊取 LSASS 憑證的常見手法：
1. **API 轉儲 (MiniDumpWriteDump)**：
   - 透過呼叫 `Dbghelp.dll` 的 `MiniDumpWriteDump` API，將整個 `lsass.exe` 記憶體傾印成 `.dmp` 檔案（如 Task Manager 或 Sysinternals ProcDump 的底層機制）。
2. **直接記憶體讀取 (Mimikatz / Sekurlsa)**：
   - 使用 `OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION)` 打開 LSASS 進程句柄，定位特定未公開全域變數（如 `LogonSessionList`），走訪內部鏈表直接在記憶體中解密出 NTLM Hash 或 Kerberos 票據。
3. **SSP 注入 (Skeleton Key / Malicious SSP)**：
   - 將惡意 DLL 註冊為自訂 SSP（如寫入登錄檔 `LSA\Security Packages`），隨 LSASS 啟動或動態載入，直接攔截並記錄明文密碼。

### 1.3 Windows 剪貼簿 (Clipboard) 記憶體鑑識物理機制
Windows 剪貼簿數據存放於使用者的工作階段記憶體（Session Desktop Heap）中：
- 當使用者執行 `Ctrl + C` 複製密碼、信用卡號或敏感金鑰時，內容以未加密的字元陣列（`CF_TEXT`、`CF_UNICODETEXT`）寫入 RAM。
- 在實體記憶體傾印檔中，即使剪貼簿內容已被覆蓋，歷史資料仍會殘存在未被零化的分頁池（Paged Pool）或進程私有堆疊中。

## 💻 第三動：現場追兇——作戰指令與自動化萃取工具

### 3.1 Volatility 3 與 Pypykatz 實戰指令庫

#### 步驟 1：使用 Volatility 3 匯出 LSASS 進程記憶體
```bash
# 1. 查找 lsass.exe 的正確 PID (確認其父進程為 wininit.exe)
vol -f memory.raw windows.pstree | grep -i lsass

# 2. 針對該 PID (例如 PID 680) 進行進程全記憶體導出
vol -f memory.raw -o ./lsass_dump/ windows.memmap --pid 680 --dump
```

#### 步驟 2：使用 Pypykatz 離線解密憑證金鑰
Pypykatz 是一套以純 Python 編寫的 Mimikatz 跨平台還原工具，可直接解析 Windows 實體記憶體或 MiniDump 檔案：
```bash
# 針對 Volatility 導出的 DMP 檔案提取所有 NTLM 與 Kerberos 憑據
pypykatz minidump ./lsass_dump/pid.680.dmp > credentials.txt

# 檢視提取到的使用者帳號與 NTLM 雜湊值
cat credentials.txt | grep -E "(username|domainname|NT:)" -A 1
```

#### 步驟 3：使用 Volatility 3 原生插件掃描剪貼簿
```bash
# 提取目前記憶體映像中的剪貼簿內容
vol -f memory.raw windows.clipboard
```

### 3.2 自動化剪貼簿敏感資訊記憶體雕刻腳本 (`clipboard_carver.py`)

以下 Python 腳本可在全記憶體傾印中搜尋符合密碼、JWT Token、私鑰特徵的剪貼簿殘留資料：

```python
#!/usr/bin/env python3
"""
clipboard_carver.py - In-Memory Sensitive Credential & Clipboard Carver
Carves sensitive strings, tokens, and credentials from raw memory dumps.
"""

import sys
import re
from pathlib import Path

PATTERNS = {
    "RSA Private Key": re.compile(rb"-----BEGIN (?:RSA )?PRIVATE KEY-----"),
    "JWT Bearer Token": re.compile(rb"eyJ[a-zA-Z0-9_-]{10,}\.eyJ[a-zA-Z0-9_-]{10,}\.[a-zA-Z0-9_-]{10,}"),
    "Password Assignment": re.compile(rb"(?:password|passwd|pwd)\s*[:=]\s*['\"]?([^\s'\"]{6,32})", re.IGNORECASE),
    "NTLM Hash String": re.compile(rb"[a-fA-F0-9]{32}:[a-fA-F0-9]{32}"),
    "AWS Access Key": re.compile(rb"AKIA[0-9A-Z]{16}"),
}

def scan_memory_chunk(data: bytes, base_offset: int):
    findings = []
    for label, regex in PATTERNS.items():
        for match in regex.finditer(data):
            matched_str = match.group(0)[:80]
            findings.append({
                "label": label,
                "offset": hex(base_offset + match.start()),
                "content": matched_str.decode("latin-1", errors="ignore")
            })
    return findings

def carve_credentials(file_path: Path):
    print(f"[*] Scanning memory file: {file_path} (Chunk size: 64MB)")
    chunk_size = 64 * 1024 * 1024
    offset = 0
    total_found = 0
    
    with open(file_path, "rb") as f:
        while True:
            chunk = f.read(chunk_size)
            if not chunk:
                break
            results = scan_memory_chunk(chunk, offset)
            for res in results:
                print(f"  [!] 🎯 Found {res['label']} at {res['offset']}: {res['content']}")
                total_found += 1
            offset += len(chunk)
            
    print("=" * 70)
    print(f"[+] Scan completed. Total potential credential artifacts: {total_found}")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python clipboard_carver.py <memory_or_dmp_file>")
        sys.exit(1)
    carve_credentials(Path(sys.argv[1]))
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (操作帳號)**：是哪一個使用者帳號觸發了針對 LSASS 的存取？該帳號是否具有 SeDebugPrivilege？
2. **What (調用 API)**：程式是呼叫 `MiniDumpWriteDump`、`OpenProcess(PROCESS_VM_READ)` 還是未公開的 Syscall？
3. **Where (目標檔案)**：轉儲出的 `.dmp` 檔案存放在何處（如 `C:\Windows\Temp\lsass.dmp` 或網路共用夾）？
4. **When (觸發時機)**：是否發生在特權管理員登入後 15 分鐘之內（典型的憑證嗅探手法）？
5. **Why (執行目的)**：內部是否有任何排程備份作業涉及 LSASS 轉儲？（極罕見，通常 99% 為惡意）
6. **How (呼叫鏈條)**：父進程是 PowerShell、CMD 還是未受信任的無簽名二進位檔案？
7. **Impact (影響範圍)**：受害主機上有哪些網域特權帳號的 Session 處於活躍狀態？
8. **Confidence (研判信心度)**：透過記憶體提取證實包含全域管理員之 NTLM Hash，信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：強制金鑰與票據輪換 (Creds Rotation)
- **立即輪換受害帳號密碼**：對所有曾在受害工作站登入過的管理員帳號進行強制密碼重設。
- **雙重輪換 `krbtgt` 帳號密碼**：若受害主機包含網域管理員憑證，必須在 24 小時內連續執行兩次 `krbtgt` 密碼輪換，徹底廢止全網域所有簽發中的黃金票據與 TGT！

### 2. 第二步：全面啟動 LSA 核心保護 (RunAsPPL)
透過 GPO 在全企業主機強制開啟 LSA Protected Process Light (PPL)：
```powershell
# 在註冊表開啟 RunAsPPL (防止非簽名進程開啟 LSASS 讀取控制代碼)
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name "RunAsPPL" -Value 1 -Type DWord
```
- **加固效果**：開啟後，即使攻擊者本機具備 `NT AUTHORITY\SYSTEM` 權限，若未持有微軟特定 ELAM 數位簽章，呼叫 `OpenProcess` 讀取 LSASS 將直接被 Windows 核心拒絕（回傳 `ACCESS_DENIED`）。

### 3. 第三步：啟用 Windows Defender Credential Guard (虛擬化隔離)
- **硬體隔離架構**：利用基於虛擬化的安全性 (VBS)，將包含 NTLM Hash 與 Kerberos 密鑰的模組搬遷至獨立的虛擬安全隔離環境 **LSAIso (Isolated LSA)**。
- **終極防禦**：即使攻擊者的惡意代碼取得主作業系統的 Ring 0 核心權限，也無法直接讀取 LSAIso 的記憶體空間，徹底杜絕 Mimikatz 類型的離線憑證讀取！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：在 Windows 作業系統中，為什麼攻擊者哪怕取得本機最高管理員權限 (Administrator)，依然極度熱衷於轉儲 `lsass.exe` 的記憶體？它所包含的憑證價值為何？**
  > **標準答案**：
  > 1. **單一主機到全網域提權的跳板**：本機管理員權限僅能控制該台主機；而 `lsass.exe` 快取了所有曾在該主機登入過的使用者之網域憑證（包含透過 RDP、排程工作或服務帳號存取的使用者）。
  > 2. **憑證形式的多樣性與致命性**：LSASS 記憶體中包含了可用於 Pass-the-Hash 的 NTLM Hash、可用於 Pass-the-Ticket 的 Kerberos TGT 票據、可用於解密企業私密檔案的 DPAPI Master Keys、甚至在未關閉 WDigest 的舊系統中還包含明文密碼。
  > 3. **攻擊效益極大化**：一旦某台一般工作站曾有網域管理員登入排除問題，攻擊者轉儲 LSASS 便可直接取得全網最高特權，瞬間完成域滲透。

- [x] **Q2：何謂 Windows LSA Protection (RunAsPPL)？它在作業系統核心層是如何阻斷 Mimikatz 等工具存取 LSASS 的？**
  > **標準答案**：
  > 1. **定義**：Protected Process Light (PPL) 是微軟引入的進程防護機制，將特定的關鍵系統服務標記為受保護進程。
  > 2. **核心層存取控制**：當開啟 `RunAsPPL` 後，Windows 核心在處理 `NtOpenProcess` 系統呼叫時，會檢查請求者與目標進程的簽章等級（Signer Type）。
  > 3. **阻斷效果**：即使請求者已是本機最高權限 `NT AUTHORITY\SYSTEM` 並具備 `SeDebugPrivilege`，只要其二進位檔案沒有通過微軟認證的受保護簽章，核心就會強制過濾掉 `PROCESS_VM_READ`、`PROCESS_VM_WRITE` 與 `PROCESS_DUP_HANDLE` 等危險存取權限，直接回傳「拒絕存取」，使轉儲工具無法讀取 LSASS 記憶體。

- [x] **Q3：使用 Pypykatz 或 Mimikatz 解析 LSASS 傾印檔時，MSV1_0 與 Kerberos SSP 模組所回傳的資料有何本質區別？**
  > **標準答案**：
  > 1. **MSV1_0 模組**：專門處理 NTLM 身分驗證。解析出來的主要是使用者密碼的單向雜湊值（NTLM Hash: MD4 計算值）。該雜湊值不隨時間自動過期（除非使用者修改密碼），可用於無限期重放（Pass-the-Hash）。
  > 2. **Kerberos SSP 模組**：專門處理 Kerberos 票據協議。解析出來的是記憶體快取的票據（TGT、TGS）以及用於會話加密的對稱金鑰（AES-256/AES-128 Key）。這些票據具有明確的時間戳與過期時間（預設 TGT 為 10 小時），可用於 Pass-the-Ticket 攻擊。

- [x] **Q4：為什麼微軟強烈建議在現代企業架構中啟用 Windows Defender Credential Guard？它與傳統的軟體防護有何本質飛躍？**
  > **標準答案**：
  > 1. **突破傳統 Ring 0 的局限**：傳統所有軟體防護（包含 RunAsPPL）都位於同一個 Windows 核心（Ring 0）。一旦攻擊者載入惡意內核驅動（BYOVD / Rootkit），即可在 Ring 0 清除 LSASS 的 PPL 標記。
  > 2. **基於硬體虛擬化的空間隔離 (VBS)**：Credential Guard 利用 Hyper-V 虛擬化技術，建立了硬體級別隔離的安全世界（VTL 1）。
  > 3. **LSAIso 獨立守護**：將儲存金鑰與雜湊的關鍵模組移入 `LSAIso.exe`。一般 Windows 系統（VTL 0）只存放代碼與代碼指標。即使整個 Windows 核心被黑客完全控制，其記憶體空間也無法跨越硬體二級頁表（SLAT）讀取 VTL 1 內的真憑實據，實現物理級別的終極防禦。

- [x] **Q5：在進行實體記憶體鑑識時，若使用者在數小時前清空了剪貼簿，為什麼鑑識人員依然有機會在實體 RAM 中提取出當初複製的敏感字串？**
  > **標準答案**：
  > 1. **應用程式字串駐留**：使用者複製密碼時，密碼不僅存在於 Windows 剪貼簿本身的緩衝區中，密碼管理員軟體（如瀏覽器、KeePass）、終端機視窗、或接收貼上的應用程式進程內部，都會各自在自身的私有堆疊（Private Heap）中建立字串副本。
  > 2. **惰性記憶體回收機制**：Windows 記憶體管理員（Memory Manager）在進程釋放記憶體時，為了追求效能，通常只將分頁標記為「可重分配（Free/Standby）」，而**不會立即將實體分頁內容全部填零（Zeroing）**。
  > 3. **字串殘留雕刻**：只要該分頁尚未被其他進程覆寫，鑑識人員透過全記憶體正規表達式掃描（Pattern Carving），就能完整撈出殘存於實體記憶體深處的明文字串。
