## 🧩 第一動：底層機制解剖——VSS 寫入時複製與差異集儲存

### 1.1 VSS (Volume Shadow Copy Service) 核心架構
VSS 是 Windows 內建的區塊級快照架構，由四大核心組件構成：
1. **VSS Coordinator (協調者)**：Windows 作業系統核心元件，負責協調快照生成流程。
2. **VSS Requester (請求者)**：發起快照請求的應用程式（如 Windows 備份工具或第三方備份軟體）。
3. **VSS Writer (寫入者)**：確保資料庫或應用程式在快照瞬間處於凍結與事務一致性狀態（如 SQL Server Writer、Exchange Writer、Registry Writer）。
4. **VSS Provider (提供者)**：負責在儲存底層真正建立並管理快照副本的模組（Windows 預設使用軟體提供者 `volsnap.sys`）。

### 1.2 寫入時複製 (Copy-on-Write, CoW) 物理運作原理
VSS 並不是對整個磁碟進行 1:1 的完整複製，而是採用極具效能優勢的 **寫入時複製（Copy-on-Write）** 技術：
- **建立瞬間**：快照建立時，幾乎不佔用任何額外磁碟空間，僅建立一張指標對應表（Block Allocation Table）。
- **後續寫入時**：當某個應用程式或使用者嘗試修改或刪除磁碟上的某個磁區區塊（Block A）時，`volsnap.sys` 會在原始資料被覆寫之前，先將 Block A 的原始資料「複製並暫存」至磁碟隱藏的 **差異區域 (Diff Area / System Volume Information)** 中。
- **時光機還原能力**：當鑑識人員掛載該歷史快照時，VSS 驅動程式會將當前的未變更區塊與 Diff Area 中的歷史區塊動態拼裝，呈現出「快照建立當下 100% 完整的全磁碟唯讀鏡像」！

```
┌───────────────────────────────────────────────────────────┐
│              當前活動磁區 (Volume C:)                     │
├───────────────────┬───────────────────┬───────────────────┤
│ Block 1 (已修改)   │ Block 2 (未變更)   │ Block 3 (已刪除)   │
└─────────┬─────────┴─────────┬─────────┴─────────┬─────────┘
          │ (寫入時複製 CoW)   │                   │ (寫入時複製 CoW)
          ▼                   │                   ▼
┌─────────────────────────┐   │         ┌─────────────────────────┐
│ Diff Area (舊 Block 1)  │   │         │ Diff Area (舊 Block 3)  │
└─────────┬───────────────┘   │         └─────────┬───────────────┘
          │                   │                   │
          ▼                   ▼                   ▼
┌───────────────────────────────────────────────────────────┐
│     歷史陰影複製快照 (Shadow Copy Snapshot - 唯讀時光機)    │
│     [完整還原出攻擊者刪除前的 Block 1, Block 2, Block 3]   │
└───────────────────────────────────────────────────────────┘
```

### 1.3 勒索軟體銷毀快照的手法與防禦反思
幾乎所有現代勒索軟體（如 LockBit、BlackCat、Conti）在開始加密檔案前，第一動一定是銷毀 VSS：
1. `vssadmin delete shadows /all /quiet`
2. `wmic shadowcopy delete`
3. `powershell.exe -Command "Get-WmiObject Win32_ShadowCopy | ForEach-Object { $_.Delete() }"`
- **鑑識關鍵啟示**：只要攻擊者因為權限不足、指令報錯或應變團隊及時拔網線阻斷了快照銷毀流程，磁碟陰影複製就是讓勒索軟體徹底破功的「唯一真神」！

## 💻 第三動：現場追兇——作戰指令與自動化掛載工具

### 3.1 原生命令列與符號連結掛載實戰

#### 步驟 1：列出主機上所有現存的陰影複製快照
```powershell
# 列出系統中所有的磁碟快照及其全域裝置路徑 (Shadow Copy Volume Name)
vssadmin list shadows
```
輸出關鍵範例：
```text
陰影複製識別碼: {b48a12d3-1122-3344-5566-778899aabbcc}
原始磁碟區: (C:)\\?\Volume{...}\
陰影複製磁碟區: \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy3
建立時間: 2026/9/10 上午 03:00:15
```

#### 步驟 2：利用符號連結 (Symbolic Link) 將唯讀快照掛載為目錄
在 Windows 中，我們無法直接 `cd` 進入 `\\?\GLOBALROOT`，但可以透過 `mklink` 建立目錄符號連結：
```cmd
:: 建立指向 HarddiskVolumeShadowCopy3 的符號連結 (注意末端必須加上反斜線 \)
mklink /d C:\vss_snapshot_3 \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy3\
```

#### 步驟 3：進入歷史快照提取遭刪除檔案與日誌
```cmd
:: 切換至掛載目錄，猶如穿越時空回到過去
cd C:\vss_snapshot_3\Windows\System32\winevt\Logs\

:: 提取被攻擊者清空前的原始 Security.evtx 與 System.evtx
copy Security.evtx C:\cases\recovered_logs\Security_Historical.evtx
```

### 3.2 自動化 VSS 歷史日誌與檔案快速差集提取器 (`vss_extractor.py`)

以下 Python 腳本列舉本機所有陰影複製，自動比對當前磁碟與歷史快照中的檔案差異，並提取已被刪除的目標檔案：

```python
#!/usr/bin/env python3
"""
vss_extractor.py - Automated VSS Snapshot Enumeration and Historical Log Extractor
Leverages Windows VSS shadow volumes to recover deleted files and cleared EVTX logs.
"""

import sys
import subprocess
import re
import os
import shutil
from pathlib import Path

def list_shadow_copies():
    print("[*] Enumerating Volume Shadow Copies via vssadmin...")
    try:
        output = subprocess.check_output(["vssadmin", "list", "shadows"], text=True, errors="ignore")
    except Exception as e:
        print(f"[-] Error executing vssadmin: {e}")
        return []
        
    shadows = []
    current_shadow = {}
    for line in output.splitlines():
        line = line.strip()
        if "陰影複製磁碟區:" in line or "Shadow Copy Volume:" in line:
            current_shadow["volume"] = line.split(":")[-1].strip()
        elif "建立時間:" in line or "Creation Time:" in line:
            current_shadow["created"] = line.split(":")[-1].strip()
            if "volume" in current_shadow:
                shadows.append(dict(current_shadow))
                current_shadow = {}
    return shadows

def extract_deleted_evidence(target_rel_path: str, output_dir: Path):
    shadows = list_shadow_copies()
    if not shadows:
        print("[-] No Volume Shadow Copies found on this system.")
        return
        
    print(f"[+] Found {len(shadows)} active shadow copies!")
    output_dir.mkdir(parents=True, exist_ok=True)
    
    for idx, s in enumerate(shadows, 1):
        vol_path = s["volume"] + "\\"
        created = s.get("created", "Unknown")
        print(f"\\n[*] Inspecting Shadow #{idx} (Created: {created})")
        
        # Build symbolic link
        symlink_path = Path(f"C:\\vss_mount_{idx}")
        if symlink_path.exists():
            os.rmdir(symlink_path)
            
        mklink_cmd = f'mklink /d "{symlink_path}" "{vol_path}"'
        res = subprocess.run(mklink_cmd, shell=True, capture_output=True, text=True)
        
        if res.returncode == 0:
            historical_target = symlink_path / target_rel_path
            if historical_target.exists():
                dest_file = output_dir / f"recovered_vss_{idx}_{historical_target.name}"
                shutil.copy2(historical_target, dest_file)
                print(f"  [!] 🎯 SUCCESS: Recovered historical file to {dest_file}")
            else:
                print(f"  [-] Target file did not exist in this snapshot.")
                
            # Clean up symbolic link
            os.rmdir(symlink_path)
        else:
            print(f"  [-] Failed to mount symlink: {res.stderr}")

if __name__ == "__main__":
    if len(sys.argv) < 3:
        print("Usage: python vss_extractor.py <relative_path_from_volume_root> <output_dir>")
        print("Example: python vss_extractor.py Windows\\System32\\winevt\\Logs\\Security.evtx C:\\cases\\recovered")
        sys.exit(1)
        
    extract_deleted_evidence(sys.argv[1], Path(sys.argv[2]))
```

### 4.1 核心研判決策流程
```
[偵測到主機上 VSS 陰影複製被刪除或容量歸零]

       │                                  │               │
       ▼                                  ▼               ▼
 [常態維運現象排除]              🚨 確鑿惡意攻擊行為   [排查備份軟體日誌]
                                 (勒索軟體銷毀還原點)
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (操作者權限)**：執行快照刪除指令的帳號為何？是否為非預期的本機 Administrator？
2. **What (刪除參數)**：命令是否包含 `/all /quiet` 這種無差別靜默銷毀參數？
3. **Where (執行端點)**：遭到刪除的主機是否存放關鍵生產資料庫（如 SQL / Oracle）？
4. **When (操作時間點)**：刪除動作發生在清晨、深夜還是週末？
5. **Why (業務正當性)**：是否有任何已批准的變更管理單要求清空系統還原點？
6. **How (呼叫途徑)**：是透過遠端 PsExec、WMI、還是未知的批次檔（.bat）觸發？
7. **Impact (剩餘快照)**：是否仍有未被成功刪除的歷史快照可供鑑識取證？
8. **Confidence (研判信心度)**：Sysmon Event ID 1 記錄到明確的 `vssadmin delete shadows`，信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：阻斷並保護現存陰影複製
- **保護存活快照**：若發現主機正在遭受勒索軟體攻擊，立即強制中斷其連線，切勿重新開機或執行任何可能觸發磁碟寫入的操作，防止 CoW 差異空間被耗盡。
- **唯讀掛載保全**：第一時間以 `mklink` 將現存快照掛載並將整個資料庫與日誌複製到離線外部儲存。

### 2. 第二步：限制 `vssadmin` 執行權限 (權限縮減)
許多企業透過 ACL 限制一般管理員直接呼叫 `vssadmin.exe`：
```powershell
# 限制僅有 TrustedInstaller 可存取 vssadmin.exe，防止遭滲透的 Administrator 輕易銷毀快照
icacls "C:\Windows\System32\vssadmin.exe" /deny "Administrators:(F)"
```

### 3. 第三步：架構加固——推行不可變備份 (Immutable Storage / WORM)
- **單機快照不可作為唯一依靠**：本機 VSS 始終受制於本機作業系統。
- **部署 WORM 與離線備份**：關鍵伺服器必須配置不可變物件儲存（S3 Object Lock）或實體離線磁帶備份，即便本機 VSS 遭攻擊者徹底抹除，企業仍能從雲端或離線備份於 1 小時內完整還原！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：為什麼 Windows 的 VSS 寫入時複製（Copy-on-Write）技術在建立快照的瞬間，幾乎不需要消耗任何磁碟空間？其物理空間是在何時才被真正消耗的？**
  > **標準答案**：
  > 1. **建立瞬間的指標特性**：在快照生成的初始時間點，磁碟上根本沒有發生任何資料搬移。VSS 提供者（`volsnap.sys`）只是在記憶體與元資料中建立了一張指向當前現有區塊的映射指標表，因此建立耗時僅需數秒且不佔空間。
  > 2. **空間消耗的時機點**：只有在快照建立「之後」，當作業系統或應用程式嘗試向原磁區寫入「新資料」或「修改既有區塊」時，VSS 才會在覆寫發生前的一瞬間，將原始未修改的舊區塊拷貝到隱藏的差異區域（Diff Area）。
  > 3. **空間消耗量**：差異空間的增長完全取決於「自快照建立以來，磁碟發生了多少資料變更（Data Delta）」。

- [x] **Q2：在勒索軟體事件調查中，如果攻擊者執行了 `wevtutil cl Security` 清空了線上安全日誌，鑑識人員如何利用 VSS 實現「時光倒流」，還原被刪除的歷史日誌？**
  > **標準答案**：
  > 1. **清空日誌的操作邊界**：`wevtutil cl` 操作僅作用於當前活動的 NTFS 磁碟區（Live Volume）上的 `Security.evtx` 檔案，將其標頭重設並截斷檔案內容。
  > 2. **VSS 快照的唯讀性與隔離性**：在此次清空操作發生之前所建立的任何一筆陰影複製中，其對應的磁區區塊皆已被 CoW 機制牢牢保護在 Diff Area 中，線上指令完全無法影響過去的唯讀快照。
  > 3. **還原技術路徑**：鑑識人員只要列出並掛載該歷史快照（`mklink /d`），即可直接存取該快照目錄下的 `C:\\Windows\\System32\\winevt\\Logs\\Security.evtx`，原汁原味提取出攻擊者清除日誌前所發生的所有活動軌跡。

- [x] **Q3：為什麼勒索軟體在執行加密前，極度熱衷於下達 `vssadmin delete shadows /all /quiet` 指令？身為資安人員該如何從偵測與防禦端反制？**
  > **標準答案**：
  > 1. **攻擊意圖**：勒索軟體的核心商業模式是「迫使受害者支付贖金」。如果受害者能夠透過 VSS 快照在一鍵之間還原所有被加密的檔案，勒索軟體將分文未得。因此必須在加密前徹底切斷受害者的本機還原後路。
  > 2. **偵測端反制 (Detection)**：在 EDR 與 SIEM 中建立高敏感告警規則，凡是監視到進程呼叫包含 `vssadmin` 且參數帶有 `delete` 與 `shadows`，或 WMI 呼叫 `Win32_ShadowCopy` 的 `Delete` 方法，立即觸發主機隔離與進程終結。
  > 3. **防禦端反制 (Hardening)**：透過變更 ACL 撤銷本機管理員對 `vssadmin.exe` 的直接執行權，並全面部署網路層級不可篡改的 WORM / 唯讀雲端備份，消除單點依賴。

- [x] **Q4：在進行 VSS 取證時，為什麼必須使用符號連結（`mklink /d`）而不能直接在檔案總管中點進 `\\?\\GLOBALROOT\\Device\\...`？**
  > **標準答案**：
  > 1. **Win32 名稱空間與 NT 物件名稱空間的區別**：`\\?\\GLOBALROOT\\Device\\...` 屬於 Windows 核心態的 **NT 物件名稱空間 (NT Object Manager Namespace)**。
  > 2. **用戶態子系統的限制**：Windows 檔案總管（File Explorer）以及一般的 Win32 應用程式，僅支援標準的 Win32 磁碟代號（如 `C:\\`）或 UNC 路徑格式，無法直接解析核心設備路徑。
  > 3. **符號連結的橋樑作用**：透過 `mklink /d` 在本地 Win32 檔案系統中建立一個目錄捷徑（Junction / Symbolic Link），將底層的核心設備物件映射為用戶態程式可識別的普通路徑，讓所有鑑識工具皆能無縫存取快照。

- [x] **Q5：如果某台受害主機上的 VSS 陰影複製被攻擊者成功刪除了，在磁碟底層鑑識上，是否還有最後的微小機會能還原部分快照資料？**
  > **標準答案**：
  > 1. **有機會（透過未分配空間雕刻）**！
  > 2. **差異區塊未覆寫原理**：當 VSS 快照被刪除時，Windows 只是更新了檔案系統元資料，將原本分配給 `System Volume Information` 差異區域的資料叢集（Data Clusters）標記為「未分配（Unallocated Space）」，而**不會立即對硬碟磁區進行全盤填零**。
  > 3. **鑑識救援手法**：鑑識人員可以使用專業取證工具（如 X-Ways Forensics、FTK Imager 或 PhotoRec），直接在未分配空間中針對特定檔案標頭（如 `.docx`、`.pdf`、`.evtx`）進行物理特徵雕刻（Carving），依然有很大機率搶救回部分關鍵證據！
