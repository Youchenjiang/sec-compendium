# 20.1 Java 內存馬清剿與 Filter/Servlet 運行時取證 (Java Memory Shell Forensics & Arthas Decompilation)

## 案發現場破題

在應對 APT 攻擊與進階 Web 滲透調查中，最令資安應變人員頭痛的莫過於**無檔案後門（Fileless Backdoor）——特別是 Java 內存馬（Java Memory Shell）**。攻擊者透過反序列化漏洞（如 Fastjson, Jackson, Shiro）或檔案上傳執行一次性 Payload 後，利用 Java 執行時機制（Java Instrumentation API / 反射動態註冊）將後門代碼直接注入 JVM 堆記憶體中的核心組件（如 Servlet, Filter, Listener, Valve, 或 Spring Controller）。**伺服器磁碟上不落地任何 JSP 檔案，傳統殺毒軟體（AV）與靜態掃描（WAF / SAST）完全無感**，甚至重啟容器或微服務前，該後門皆能隨意透過正常業務請求路徑執行任意指令。

```
[攻擊者發送帶有特徵 Header 的請求 (如 Cmd: whoami)]
       │
       ▼ (連線通過硬體防火牆與邊界 WAF，URL 完全是正常路徑 /index.html)
+-------------------------------------------------------------------------------+
| Tomcat / Spring Boot JVM 堆記憶體 (Heap Memory)                              |
|                                                                               |
|  [ 正常 Filter 鏈 (ApplicationFilterChain) ]                                 |
|       │                                                                       |
|       ├── 1. 惡意注入之代理 Filter (AuthBypassFilter - 無磁碟落地實體檔案)    |
|       │      ├─ 攔截請求標頭，辨識密鑰認證                                     |
|       │      ├─ 使用 Runtime.getRuntime().exec() 執行遠端代碼                 |
|       │      └─ 直接將回傳結果寫入 HttpServletResponse 並在中途中斷 (Return)  |
|       │                                                                       |
|       └── 2. 正常業務 Servlet (永遠不會被執行到，完全無異常日誌)              |
+-------------------------------------------------------------------------------+
       │
       ▼ (200 OK，包含 whoami 執行結果: root)
[攻擊者長驅直入接管伺服器，SOC 與維運人員渾然不覺]
```

### 痛點場景
- **磁碟零足跡（Zero Disk Artifacts）**：常規應急響應的第一步是 `find /var/www -name "*.jsp"` 或檢查檔案時間戳，但內存馬僅存在於記憶體中，磁碟稽核完全撲空。
- **隨機自訂觸發條件**：內存馬常與合法業務 URL 綁定（例如掛載於 `/*` 全路徑），只有當 HTTP Request 包含特定密碼學 Cookie、特定 Header 或指定參數時才喚醒執行，平時正常使用者存取毫無異狀。
- **傳統日誌無異常報錯**：由於內存馬直接在 Filter 層回傳 Response 並截斷請求，後端 Web Access Log 僅記錄一次正常的 `200 OK`，且通常不記錄 HTTP Header 內容。

## 第一動：Java 內存馬四大底層型態與原理剖析 (Java Memshell Taxonomies)

```
+-----------------------------------------------------------------------------------------------+
| Java 內存馬核心注入技術演進                                                                   |
|                                                                                               |
| 1. 傳統 Servlet / Filter / Listener 內存馬                                                   |
|    - 原理：透過反射取得當前 Web 容器的 StandardContext (Tomcat) 上下文。                     |
|    - 注入：呼叫 addFilterDef / addFilterMap 或 addServlet，將惡意類別動態插入 FilterChain 最前端|
|                                                                                               |
| 2. Spring 框架層內存馬 (Controller / Interceptor)                                            |
|    - 原理：動態向 RequestMappingHandlerMapping 註冊自訂 URL 路由與 HandlerMethod。           |
|    - 特色：不依賴底層 Servlet 容器，普遍存在於 Spring Boot 微服務中。                        |
|                                                                                               |
| 3. Agent 級字節碼無感注入馬 (Javaagent Bytecode Instrumentation)                              |
|    - 原理：利用 VirtualMachine.attach() 掛載至目標 JVM 程序。                                 |
|    - 注入：利用 ClassFileTransformer 重寫已載入核心類別 (如 ApplicationFilterChain.doFilter)  |
|    - 殺傷力：不新增任何新類別或 Filter，直接在既有正常類別位元組碼中插入後門邏輯！            |
+-----------------------------------------------------------------------------------------------+
```

### 內存馬與正常組件對比特徵

| 審查維度 | 正常合法元件 (Legitimate Component) | 惡意內存馬特徵 (Malicious Memshell) |
| :--- | :--- | :--- |
| **類別載入器 (ClassLoader)** | 來自實體 Jar 檔案或專案目錄 (`file:/app/lib/...`)。 | `codeSource` 通常為 `null`，記憶體中動態生成（`byte[]`）。 |
| **Filter 執行順序** | 依據 `web.xml` 或 Spring `@Order` 排序。 | 始終強制搶佔至 `FilterChain` 第 1 位（Index 0）。 |
| **反編譯源碼特徵** | 標準業務日誌與過濾邏輯。 | 包含 `defineClass`, `Unsafe`, `ProcessBuilder`, `Runtime.exec`。 |

## 第二動：工具鏈實戰：Arthas 動態 JVM 取證排查 (Arthas In-Memory Forensics)

阿里巴巴開源的 **Arthas** 是排查 Java 內存馬的頂級戰術神兵，可在不重啟 JVM 的情況下動態 dump 類別與反編譯：

### 1. 啟動 Arthas 並附著 (Attach) 至目標 Java 進程
```bash
# 下載並啟動 Arthas，選擇受害的 Java PID (如 Tomcat / Spring Boot)
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar
```

### 2. 枚舉所有已註冊的 Filter 與 Interceptor
```bash
# 查詢所有實作 javax.servlet.Filter 或 jakarta.servlet.Filter 的類別
sc -d *Filter

# 查詢 Spring 容器中的全部 Controller 路由對應
mbean org.springframework.boot:name=application*
```

### 3. 動態反編譯可疑類別原始碼 (Decompilation)
若發現名稱怪異、或無實體檔案對應的類別（例如 `com.example.EvilFilter`）：
```bash
# 反編譯記憶體中的位元組碼，直接檢視其原始程式碼！
jad com.example.EvilFilter

# 將記憶體中的 .class 實體導出到磁碟進行後續靜態逆向
dump com.example.EvilFilter -d /tmp/memshell_dumps/
```

## 第三動：日誌遙測與 JVM 診斷配置 (Telemetry & Diagnostics)

### 1. 開啟 JVM ClassLoader 類別載入日誌
在 Java 啟動參數中加入：
```bash
-XX:+TraceClassLoading -XX:+TraceClassUnloading
```
- 當攻擊者利用反序列化動態載入新類別時，JVM 會在 `stdout` 即時記錄：`[Loaded com.malicious.Payload from __JVM_DefineClass__]`。

### 2. WAF 存取日誌記錄全量 HTTP 標頭
由於內存馬依賴自訂 Header 觸發，需在 Nginx / ALB 中將 Request Headers 納入日誌：
```nginx
log_format combined_headers '$remote_addr - $remote_user [$time_local] '
                            '"$request" $status $body_bytes_sent '
                            'headers: "$http_x_token" "$http_cmd"';
```

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Detection Rules)

### 1. Splunk SPL：偵測 JVM 異常衍生子程序 (Java Process Spawning Shell)
```spl
index=sysmon sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
    ParentImage="*\\java.exe" Image IN ("*\\cmd.exe", "*\\powershell.exe", "*\\sh", "*\\bash")
| stats count earliest(_time) as first_exec latest(_time) as last_exec 
        values(CommandLine) as ExecutedCommands by Computer, ParentImage, Image, User
| convert ctime(first_exec) ctime(last_exec)
| table first_exec, last_exec, Computer, ParentImage, Image, ExecutedCommands, count
```

### 2. Splunk SPL：偵測 ClassLoader 動態載入來自記憶體之未知字節碼
```spl
index=jvm_logs sourcetype="java:classloading"
| search "Loaded * from __JVM_DefineClass__"
| table _time, host, app_name, loaded_class
```

### 3. Sigma 偵測規則：Java Application Spawning Command Shell
```yaml
title: Java Application Spawning Shell Process
id: 9a8c1024-5d91-4e12-8812-7819ad10245a
status: production
description: 偵測 Java (Tomcat / Spring) 服務程序異常直接衍生出系統 Shell，符合內存馬執行指令特徵
logsource:
    category: process_creation
    product: linux
detection:
    selection:
        ParentImage|endswith:
            - '/java'
        Image|endswith:
            - '/sh'
            - '/bash'
            - '/dash'
    condition: selection
level: critical
```

## 第五動：內存馬熱拔除與自適應加固 (In-Memory Hot Patching & Hardening)

```
[Arthas 動態連線]
       │
       ├── 1. 定位惡意 Filter / Valve 對應之 StandardContext
       ├── 2. 呼叫 StandardContext.removeFilterDef() 進行記憶體熱拔除
       ▼
 [惡意 Filter 自記憶體 Chain 中被移除 ➔ 立即恢復正常業務，無需中斷伺服器]
```

### 1. 利用 OGNL 表達式或 Java Agent 執行線上熱拔除 (Hot Removal via Arthas)
若無法立即重啟高併發的核心生產系統，可使用 Arthas 執行 OGNL 語法在記憶體中註銷該 Filter：
```bash
# 取得 Tomcat StandardContext 並自 FilterMaps 中拔除該惡意 Filter
ognl '#context=@org.apache.catalina.loader.WebappClassLoaderBase@class.getClassLoader().resources.context, #context.removeFilterDef(#context.findFilterDef("EvilFilter")), #context.removeFilterMap(#context.findFilterMaps()[0])'
```

### 2. 部署 RASP (執行期應用自我保護) 免疫內存馬
- 引入 **OpenRASP** 或商用 RASP 探針。
- 在底層 Hook `ClassLoader.defineClass`、`StandardContext.addFilterDef` 與 `ProcessBuilder.start`。
- 一旦偵測到未經簽名的類別試圖動態註冊進 Servlet 容器，或 Java 嘗試呼叫 `sh`/`cmd`，直接在 JVM 核心阻斷並拋出安全性例外。

## 靶場實戰：Tomcat Filter 內存馬調查與熱清理

### 靶場環境情境
- **受害主機**: `App-Server-Prod` (執行 Apache Tomcat 9.0.50)
- **警報觸發**: EDR 發出告警：`java` 程序正在執行 `/bin/sh -c cat /etc/passwd`，但磁碟全面掃描未發現任何 WebShell 檔案。

### 實戰步驟一：啟動 Arthas 記憶體審計
1. 連線至受害主機，啟動 `arthas-boot.jar` 並選取 Tomcat PID。
2. 執行 `sc -d *Filter`，逐一審查所有 Filter 的 `classLoaderHash` 與 `codeSource`。
3. 發現一個名為 `org.apache.catalina.core.DynamicAuthFilter` 的類別，其 `codeSource: null`，明顯為動態注入之未落地檔案！

### 實戰步驟二：反編譯證據保全
1. 執行 `jad org.apache.catalina.core.DynamicAuthFilter`。
2. 反編譯程式碼清晰可見：
   ```java
   String cmd = request.getHeader("X-Token-Cmd");
   if (cmd != null) {
       Process p = Runtime.getRuntime().exec(cmd);
       ...
       response.getWriter().write(output);
       return;
   }
   ```
3. 執行 `dump org.apache.catalina.core.DynamicAuthFilter -d /tmp/forensics/` 保全證據。

### 實戰步驟三：應急處置
1. 執行熱清理腳本，自 `StandardContext` 拔除該 Filter。
2. 重啟容器並修補引發代碼注入的 Jackson 反序列化漏洞。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **機制透徹**：能清楚闡述 Java 內存馬（Filter / Servlet / Agent 型）如何突破傳統磁碟檢驗機制達成無檔案常駐。
- [ ] **Arthas 診斷**：能熟練使用 Arthas 的 `sc`, `jad`, `dump`, `ognl` 指令完成 JVM 記憶體取證與原始碼反編譯。
- [ ] **特徵研判**：能依據 `codeSource == null`、ClassLoader 異常來源與 FilterChain 搶佔順序精準判定是否為惡意注入。
- [ ] **進程遙測規則**：能撰寫 Sysmon / SIEM 規則，捕捉 `java` 衍生 `sh`/`cmd` 的經典後門執行行為。
- [ ] **防禦治理**：理解 RASP（Runtime Application Self-Protection）在對抗內存馬上的核心價值與防禦阻斷點。
