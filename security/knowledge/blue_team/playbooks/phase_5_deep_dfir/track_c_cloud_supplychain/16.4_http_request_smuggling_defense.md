# 16.4 協定走私與反向代理混淆鑑識 (HTTP Request Smuggling & Reverse Proxy Desync)

## 案發現場破題

在現代企業雲端與微服務架構中，前端通常部署反向代理（Reverse Proxy）、內容傳遞網路（CDN）或 Web 應用防火牆（WAF，如 Nginx, HAProxy, AWS CloudFront），後端則為應用程式伺服器（如 Node.js, Tomcat, Gunicorn）。兩者之間為了效能最佳化，普遍採用 **HTTP 連線複用（HTTP Keep-Alive / TCP Connection Reuse）**。然而，當前端代理與後端伺服器對 HTTP 請求邊界（Request Boundaries）的長度判斷標準產生分歧時，攻擊者便能發動**HTTP 請求走私（HTTP Request Smuggling, HRS / Desync）**，將惡意請求的前綴或有害 Payload「走私」進 TCP 管道中，直接劫持下一個無辜受害者的連線會話（Session Hijacking）、繞過前端 WAF 邊界安全控制、甚至發動跨站腳本（XSS）大規模釣魚。

```
[攻擊者惡意走私請求]
       │
       ▼ (包含 Transfer-Encoding: chunked 與 Content-Length 雙標頭)
+-------------------------------------------------------------------------------+
| 前端反向代理 (Frontend: WAF / Nginx / CDN)                                   |
|  - 採用 Content-Length 判斷封包長度                                           |
|  - 研判「這是一個完整的單一請求」➔ 轉發給後端連線池 (Connection Pool)        |
+-------------------------------------------------------------------------------+
       │
       ▼ (轉發進 Keep-Alive TCP 管道)
+-------------------------------------------------------------------------------+
| 後端應用伺服器 (Backend: Tomcat / Gunicorn)                                   |
|  - 採用 Transfer-Encoding 判斷長度                                            |
|  - 只解析到 chunk 結尾，將殘餘走私的「GPOST /admin...」留在 TCP Socket 暫存區  |
+-------------------------------------------------------------------------------+
       │
       ▼ 【下一個無辜使用者的正常 GET /index.html 請求抵達！】
 ┌─────────────────────────────────────────────────────────────┐
 │ 殘留走私前綴 + 無辜請求被黏著成：                           │
 │ GPOST /admin/addUser HTTP/1.1 (帶有無辜使用者的 Cookie!)    │
 └─────────────────────────────────────────────────────────────┘
       │
       ▼
[以無辜管理員身分在後端執行越權操作 / 攻擊者竊取 Session Cookie]
```

### 痛點場景
- **邊界防線完全被旁路（WAF Bypass）**：前端 WAF 依據自身的解析邏輯認定請求無害並放行，但抵達後端時卻被解析成完全不同的惡意操作，使所有南北向 L7 檢測全數失效。
- **無辜受害者被「附身」**：攻擊者發起一個走私請求後，受害的卻是幾毫秒後發送正常請求的一般使用者，日誌將顯示正常用戶的 IP 與 Cookie 正在存取未授權資源，造成鑑識極大困擾。
- **協定規格歷史包袱**：RFC 2616 規範對 `Content-Length` 與 `Transfer-Encoding` 衝突時的處置雖然有規定，但各廠商伺服器在面對畸形空白、換行與混淆大小寫時的寬鬆容錯機制（Pardoning）各不相同。

## 第一動：走私變體原理與解析分歧矩陣 (HRS Variants & RFC 2616 Breakdown)

```
+-----------------------------------------------------------------------------------------------+
| HTTP 請求走私三大經典變體對比                                                                 |
|                                                                                               |
| 1. CL.TE (Frontend: Content-Length | Backend: Transfer-Encoding)                              |
|    - 前端看 CL：認為請求包含整個 Body 並放行。                                                |
|    - 後端看 TE：遇到 0\r\n\r\n 即結束當前請求，把後面的走私資料留給下一位使用者。             |
|                                                                                               |
| 2. TE.CL (Frontend: Transfer-Encoding | Backend: Content-Length)                              |
|    - 前端看 TE：處理 chunked 數據並轉發。                                                     |
|    - 後端看 CL：只讀取指定的長度，把超過長度之外的 chunk 殘留在 TCP 管道中。                 |
|                                                                                               |
| 3. TE.TE (雙方皆支援 TE，但其中一方可被混淆標頭欺騙降級為 CL)                                |
|    - 混淆手段：Transfer-Encoding: xchunked、Transfer-Encoding[\x0b]: chunked、多個 TE 標頭   |
|    - 攻擊成因：某一方無法識別畸形 TE 標頭而退回使用 Content-Length，轉化為 CL.TE 或 TE.CL。   |
|                                                                                               |
| 4. H2.CL / H2.TE (HTTP/2 降級為 HTTP/1.1 走私)                                                |
|    - 前端對外使用 HTTP/2 (無長度歧義)，但轉發給後端時「降級」為 HTTP/1.1，在轉譯標頭時被注入  |
+-----------------------------------------------------------------------------------------------+
```

### 經典走私封包解構 (CL.TE 範例)

```http
POST /search HTTP/1.1
Host: corp.local
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```
- **前端視角**：`Content-Length: 13`，精確覆蓋到 `SMUGGLED` 結束（包含換行符號共 13 位元組），轉發整個封包。
- **後端視角**：優先解析 `Transfer-Encoding: chunked`，讀到 `0\r\n\r\n` 便認為當前請求結束。後續的 `SMUGGLED` 留在 TCP 緩衝區，作為下一個 HTTP 請求的開頭！

## 第二動：攻擊模擬與檢測工具鏈 (Attack Emulation: HTTP Request Smuggler)

利用 Burp Suite 插件「HTTP Request Smuggler」或 Python 測試腳本進行 Desync 探測：

### 1. 探測 CL.TE 延遲差異 (Timing-based Detection)
若伺服器存在 CL.TE 脆弱性，發送以下請求將導致後端等待下一個 chunk 長度，引發長達數秒的 HTTP 讀取超時（Read Timeout）：
```http
POST / HTTP/1.1
Host: vulnerable-app.corp.local
Transfer-Encoding: chunked
Content-Length: 4

1
Z
Q
```

### 2. 探測 TE.CL 走私截獲
```http
POST / HTTP/1.1
Host: vulnerable-app.corp.local
Content-Length: 6
Transfer-Encoding: chunked

0

X
```

## 第三動：Web 伺服器日誌與封包遙測分析 (Telemetry Setup: Nginx & Wireshark)

### 1. Nginx 存取日誌格式強化 (記錄請求處理時間與管道狀態)
在 `/etc/nginx/nginx.conf` 中加入除錯欄位：
```nginx
log_format smuggling '$remote_addr - $remote_user [$time_local] '
                     '"$request" $status $body_bytes_sent '
                     'pipe=$pipe request_time=$request_time '
                     'upstream_response_time=$upstream_response_time '
                     'http_transfer_encoding="$http_transfer_encoding" '
                     'content_length="$http_content_length"';
```
- **`pipe=p`**：表示該請求來自 HTTP pipelined 管道，可作為走私研判重要依據。

### 2. Wireshark / TShark 封包抓取雙標頭異常
```bash
# 抓取同時包含 Content-Length 與 Transfer-Encoding 之畸形 HTTP 請求
tshark -i eth0 -Y 'http.content_length and http.transfer_encoding' -T fields -e ip.src -e http.host -e http.request.uri
```

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & WAF Rules)

### 1. Splunk SPL：偵測同一連線中同時攜帶 CL 與 TE 的畸形 HTTP 流量
```spl
index=web_proxy sourcetype="nginx:smuggling"
| search http_transfer_encoding=* AND content_length=*
| stats count earliest(_time) as first_seen latest(_time) as last_seen 
        values(http_transfer_encoding) as TEs, values(content_length) as CLs by client_ip, host, request
| convert ctime(first_seen) ctime(last_seen)
| table first_seen, last_seen, client_ip, host, request, CLs, TEs, count
```

### 2. Splunk SPL：偵測突發的大量 400 Bad Request 或 Unrecognized Method (走私殘留特徵)
```spl
index=web_backend status IN (400, 405, 501)
| rex field=request "^(?<http_method>[A-Z]+)"
| search NOT http_method IN ("GET", "POST", "PUT", "DELETE", "HEAD", "OPTIONS", "PATCH")
| stats count by _time span=5m, client_ip, http_method, uri
| table _time, client_ip, http_method, uri, count
```

### 3. Sigma 偵測規則：HTTP Request Smuggling Desync Indicators

## 第五動：反向代理架構加固與前端阻絕 (Architecture Hardening & Mitigation)

```
[使用者瀏覽器]
       │
       ▼ (強制端到端 HTTP/2，取消內部連線複用)
+-------------------------------------------------------------------------------+
| 前端反向代理 (Nginx / HAProxy / Cloudflare)                                  |
|  - 停用 HTTP Pipelining 連線重用                                              |
|  - 嚴格拒絕同時包含 CL 與 TE 的請求 (Reject Ambiguous Requests)              |
|  - 強制啟用 HTTP/2 End-to-End (不向後端進行 HTTP/1.1 降級轉譯)                |
+-------------------------------------------------------------------------------+
       │
       ▼ (乾淨、單一、嚴格界定的請求邊界)
[後端應用程式伺服器 (Tomcat / Node.js)]
```

### 1. Nginx 核心配置加固：禁止無效標頭與模糊連線
在 Nginx 代理配置中增加嚴格標準：
```nginx
# 嚴格禁止畸形或含底線的非標準標頭
ignore_invalid_headers on;

# 針對向後端 upstream 連線，停用可被走私利用的 keepalive reuse（高安全需求場景）
proxy_http_version 1.1;
proxy_set_header Connection "";

# 遇雙標頭直接丟棄
if ($http_transfer_encoding ~* "chunked") {
    set $te_present 1;
}
if ($http_content_length != "") {
    set $cl_present 1;
}
set $both "${te_present}${cl_present}";
if ($both = "11") {
    return 400 "HTTP Smuggling Attempt Blocked";
}
```

### 2. 全面推行端到端 HTTP/2 (End-to-End HTTP/2)
- 淘汰前端對外使用 HTTP/2、對後端降級為 HTTP/1.1 的「混合架構（H2C downgrade）」。
- 讓前端與後端全程維持二進位框架（Binary Framing Layer），因 HTTP/2 每個 Frame 明確定義長度與 Stream ID，從協定層徹底消滅 Content-Length 與 Transfer-Encoding 的長度歧異。

## 靶場實戰：CL.TE 走私會話劫持與日誌鑑識

### 靶場環境情境
- **前端代理**: HAProxy 1.8 (預設依賴 Content-Length)
- **後端服務**: Gunicorn 19.9 (存在 Transfer-Encoding 解析漏洞)
- **受害者**: 公司一般員工 `jason@corp.local`，定時發起 `GET /profile`

### 實戰步驟一：攻擊者注入走私前綴
攻擊者向 `/search` 發送 CL.TE 走私請求，偷渡惡意前綴 `GET /admin/makeAdmin?user=attacker HTTP/1.1\r\nFoo: `。

### 實戰步驟二：後端日誌解析研判
1. 觀察 Gunicorn 存取日誌：
   發現一筆奇特的連線：`GET /admin/makeAdmin?user=attacker`，其帶有 `jason@corp.local` 的 Session Cookie！
2. 緊接著下一筆請求呈現 `400 Bad Request`，原因是 Jason 的請求標頭被黏著在 `Foo: ` 後面導致語法解析異常。

### 實戰步驟三：防護阻斷與修復
1. 在 HAProxy 中開啟 `option http-server-close`，禁止後端連線複用。
2. 升級 Gunicorn 至最新版，驗證雙標頭請求立即回傳 `400 Bad Request`。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **協定歧異理解**：能精準說明 CL.TE 與 TE.CL 走私的本質差異，並繪製請求邊界在前後端解析過程中的時序圖。
- [ ] **威脅場景識別**：熟知 Request Smuggling 造成的具體威脅（Session 劫持、WAF 繞過、後端快取投毒）。
- [ ] **畸形封包分析**：能使用 Wireshark / TShark 抓取並識別同時包含 `Content-Length` 與 `Transfer-Encoding` 的異常 HTTP 流量。
- [ ] **SIEM 關聯規則**：能編寫日誌過濾規則，透過畸形 HTTP Method 與非預期 400 錯誤快速定位走私殘留攻擊。
- [ ] **架構加固防禦**：能在 Nginx / HAProxy 中配置防護策略，或推動端到端 HTTP/2 徹底杜絕長度混淆。
