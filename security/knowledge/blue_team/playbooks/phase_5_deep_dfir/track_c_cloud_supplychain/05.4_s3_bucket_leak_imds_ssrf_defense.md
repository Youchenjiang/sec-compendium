# 05.4 雲端儲存桶外洩與中繼資料 (IMDS) 劫持防護 (S3 Bucket Leaks & IMDSv2 SSRF Defense)

## 案發現場破題

2019 年知名美國第一資本銀行（Capital One）發生震驚全球的 1 億用戶資料外洩事件，其核心攻擊鏈並非傳統的 SQL 注入或主機溢位，而是**伺服器端請求偽造（Server-Side Request Forgery, SSRF）結合雲端實例中繼資料服務（Instance Metadata Service, IMDS）的完美跳躍**。攻擊者利用 WAF 反向代理的 SSRF 漏洞，強迫主機向內部專屬非繞送位址 `http://169.254.169.254/latest/meta-data/iam/security-credentials/` 發送 HTTP GET 請求，直接榨取賦予該雲端實例之 IAM Role 臨時金鑰，隨後暢行無阻地將數百個 S3 儲存桶內的客戶信貸數據打包同步（`aws s3 sync`）外洩。

```
[外部黑客] ── 1. 觸發 SSRF 漏洞 ──► [企業雲端主機 (EC2 / Azure VM)]
                                              │
                                              ├── 2. 向 169.254.169.254 請求 IAM 憑證
                                              ▼
                                 [雲端中繼資料服務 (IMDSv1)]
                                              │
                                              └── 3. 回傳 AccessKeyId, SecretAccessKey, Token
                                              ▼
[攻擊者本機終端] ◄── 4. 偷渡取得暫時憑證 ─────┘
       │
       ▼ (aws s3 sync s3://corp-credit-records ./loot)
[直接清空企業 S3 儲存桶機密資料，整個過程不登入主機、不留端點執行檔]
```

### 痛點場景
- **IMDSv1 缺乏連線保護機制（No Auth Headers）**：IMDSv1 僅需純文字 HTTP GET 即可回傳敏感金鑰，任何存在 LFI、SSRF 或 XML/XXE 漏洞的 Web 應用程式皆能輕易充當跳板。
- **過寬的 EC2 實例角色委派**：許多團隊圖方便，直接將具備 `s3:*` 或 `AdministratorAccess` 的 IAM Role 綁定給公開面對網際網路的 Web 伺服器。
- **S3 儲存桶存取控制混亂**：ACL（存取控制清單）與 Bucket Policy 雙軌並存，容易因人為誤將 `AllUsers` 或 `AuthenticatedUsers`（任何擁有 AWS 帳號的人）勾選讀取權限而導致公開暴露。

## 第一動：IMDS 演進架構與 SSRF 防禦原理 (IMDSv1 vs. IMDSv2 Mechanics)

為根治 Capital One 式的 SSRF 憑證偷渡，AWS 推出了 **IMDSv2**，要求所有請求必須具備「會話導向（Session-oriented）」且「禁止跨躍點轉發（Hop Limit = 1）」。

```
+-----------------------------------------------------------------------------------------------+
| IMDSv1 vs. IMDSv2 核心防禦機制對比                                                            |
|                                                                                               |
| 1. IMDSv1 (易受攻擊)                                                                         |
|    - 索取流程：直接 GET http://169.254.169.254/latest/meta-data/iam/security-credentials/role |
|    - 致命弱點：任何簡易 SSRF (如 http://vuln.com/?url=http://169.254.169.254/...) 均可直接得手|
|                                                                                               |
| 2. IMDSv2 (抗 SSRF 防護)                                                                      |
|    - 步驟 1 (Token 索取)：發送 HTTP PUT 請求，帶有標頭 X-aws-ec2-metadata-token-ttl-seconds: 21600|
|    - 步驟 2 (憑證存取)：發送 HTTP GET 請求，必須攜帶剛取得的 X-aws-ec2-metadata-token         |
|    - 核心屏障：絕大多數 SSRF 漏洞（如圖片抓取、URL 重導向）僅能發送 GET，無法自訂 PUT 標頭！  |
|    - 網路層防線：TTL (Hop Limit) 設為 1，封包若經過容器網路或反向代理轉發，TTL 歸零直接被丟棄。 |
+-----------------------------------------------------------------------------------------------+
```

### 雲端實例與儲存桶加固基線

| 防禦維度 | 脆弱配置 (Vulnerable State) | 安全加固標準 (Hardened Baseline) |
| :--- | :--- | :--- |
| **IMDS 版本要求** | `HttpTokens: optional` (同時接受 v1 與 v2) | 強制 `HttpTokens: required` (全面停用 IMDSv1) |
| **網路轉發限制** | `HttpPutResponseHopLimit: 2` (允許容器轉發) | `HttpPutResponseHopLimit: 1` (僅限宿主機直接存取) |
| **儲存桶存取政策** | 允許非 VPC 來源存取 | Policy 強制限定 `aws:sourceVpc` 或 `aws:PrincipalArn` |
| **全域 S3 防線** | 關閉 S3 Block Public Access | 帳號與儲存桶層級 4 項 Public Access Block 全數開啟 |

## 第二動：攻擊模擬與 IMDS 憑證偷渡重現 (Attack Emulation: IMDS & S3 Sync)

### 1. 傳統 IMDSv1 憑證榨取 (透過 SSRF 觸發)
```bash
# 模擬 SSRF 請求獲取綁定的 IAM Role 名稱
curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/
# 輸出: WebAppS3AccessRole

# 索取該 Role 的臨時 AccessKeyId 與 SessionToken
curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/WebAppS3AccessRole
```

### 2. IMDSv2 正常安全存取流程 (需兩步驟並帶標頭)
```bash
# 步驟 1: 取得有效期限 6 小時的 Session Token (PUT 挑戰)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# 步驟 2: 攜帶 Token 索取中繼資料
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/WebAppS3AccessRole
```

## 第三動：CloudTrail 與 S3 Access Logs 遙測配置 (Telemetry Setup)

### 1. 啟用 S3 伺服器存取記錄 (Server Access Logging)
監控儲存桶內所有物件的讀取與下載行為（包含調用者 IP、User-Agent 與錯誤碼）：
```bash
aws s3api put-bucket-logging --bucket corp-sensitive-data \
    --bucket-logging-status file://logging-config.json
```

### 2. 關鍵 CloudTrail 審計指標
- **`eventName: GetObject` / `ListObjects`**：由非企業 IP 發起的大規模資料讀取。
- **`userIdentity.type: AssumedRole`**：比對該 Role 是否為 EC2 實例專用 Role，但連線 IP 卻來自國外或非 AWS 機房。

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk SPL & Sigma Rules)

### 1. Splunk SPL：偵測 EC2 實例 Role 憑證被移出 AWS 外部使用 (Credential Exfiltration)
```spl
index=aws_cloudtrail sourcetype="aws:cloudtrail" userIdentity.sessionContext.sessionIssuer.userName="*EC2*"
| eval IsAWSIP=if(match(srcIP, "^(54\.|52\.|3\.|18\.|35\.)"), 1, 0)
| search IsAWSIP=0 AND NOT srcIP IN ("10.*", "172.16.*", "192.168.*")
| stats count earliest(_time) as first_seen latest(_time) as last_seen 
        values(eventName) as Actions, values(srcIP) as OutsideIPs by userIdentity.arn, userAgent
| convert ctime(first_seen) ctime(last_seen)
| table first_seen, last_seen, userIdentity.arn, OutsideIPs, userAgent, Actions
```

### 2. Splunk SPL：偵測 S3 異常高頻批次下載 (S3 Exfiltration Detection)
```spl
index=s3_access_logs operation="REST.GET.OBJECT"
| bin _time span=10m
| stats count as DownloadCount, sum(bytes_sent) as TotalBytes by _time, requester_ip, bucket_name
| where DownloadCount > 500 OR TotalBytes > 1073741824
| table _time, requester_ip, bucket_name, DownloadCount, TotalBytes
```

### 3. Sigma 偵測規則：IMDSv1 Usage Alert via CloudWatch

## 第五動：IMDSv2 強制推動與 S3 邊界加固 (Hardening: IMDSv2 & Bucket Policy)

```
[外部請求] ──► [EC2 執行個體]
                    │
                    ├── 1. 系統層強制：HttpTokens=required (停用 IMDSv1)
                    ├── 2. 網路層限制：HopLimit=1 (禁止容器/反向代理轉發)
                    ▼
          [169.254.169.254 (IMDSv2)]
                    │
                    └── (SSRF 攻擊者無法自訂 PUT Token 標頭，存取徹底失敗！)
```

### 1. 全域強制開啟 IMDSv2 並限制 HopLimit=1 (AWS CLI)
```bash
# 對現有執行個體強制升級為 IMDSv2
aws ec2 modify-instance-metadata-options \
    --instance-id i-1234567890abcdef0 \
    --http-tokens required \
    --http-put-response-hop-limit 1 \
    --http-endpoint enabled
```

### 2. 編寫 S3 儲存桶策略：僅允許指定 VPC 內部存取 (Restricting to VPC Endpoint)
徹底杜絕外洩憑證在網際網路上被直接呼叫：
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceVpcEndpointAccessOnly",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::corp-sensitive-data",
        "arn:aws:s3:::corp-sensitive-data/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:sourceVpce": "vpce-1a2b3c4d5e6f"
        }
      }
    }
  ]
}
```

## 靶場實戰：SSRF 憑證外洩鑑識與 IMDSv2 阻斷驗證

### 靶場環境情境
- **受害實例**: `i-0a1b2c3d4e5f6` (運行 Node.js 圖片處理服務，存在 SSRF 漏洞)
- **警報觸發**: AWS GuardDuty 產生告警：`UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS`，偵測到實例 Role 金鑰正從俄羅斯某 VPS 發送 S3 GetObject 請求。

### 實戰步驟一：確認憑證已外洩
1. 比對 CloudTrail 日誌，確認該金鑰所關聯之 EC2 實例 ID，並發現大量的 `GetObject` 調用 IP 來自非 AWS IP。
2. 檢查該實例的中繼資料配置：
   ```bash
   aws ec2 describe-instances --instance-ids i-0a1b2c3d4e5f6 \
       --query "Reservations[].Instances[].MetadataOptions"
   ```
   發現 `HttpTokens: optional`，確認遭受 IMDSv1 SSRF 攻擊。

### 實戰步驟二：緊急吊銷與憑證失效 (Revocation)
1. **附加內嵌阻斷策略至該 Role**，強制終止當前時間點之前簽發的所有臨時憑證：
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Deny",
         "Action": "*",
         "Resource": "*",
         "Condition": {
           "DateLessThan": {
             "aws:CurrentTime": "2026-09-14T12:00:00Z"
           }
         }
       }
     ]
   }
   ```

### 實戰步驟三：全面加固
1. 將該實例修改為 `HttpTokens: required`。
2. 在 S3 儲存桶上啟用 `aws:sourceVpce` 條件限制。
