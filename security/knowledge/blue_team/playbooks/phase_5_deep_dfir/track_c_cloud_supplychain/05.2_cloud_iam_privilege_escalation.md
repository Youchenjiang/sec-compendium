# 05.2 雲端多租戶 IAM 提權與 CloudTrail 審計日誌研判 (Cloud IAM Privilege Escalation & Audit Log Analysis)

## 案發現場破題

在公有雲（AWS, Azure, GCP）環境中，**「身分即周界（Identity is the new perimeter）」**。身分與存取管理（IAM）原則（Policy）取代了傳統防火牆與網路隔離，決定了主體（User, Role, Service Account）能對哪些雲端資產執行操作。攻擊者攻入雲端後的首要任務往往不是掃描漏洞，而是**IAM 提權（Privilege Escalation）**——利用被錯誤配置或過度寬鬆的 21 種典型 IAM 權限躍遷手法（如 `iam:CreateAccessKey`、`iam:CreatePolicyVersion`、`sts:AssumeRole`），將低權限訪客角色瞬間提升為雲端全域管理員（`AdministratorAccess`）。

```
[低特權被攻陷身分 (Dev-Contractor / Lambda Role)]
       │
       ├── 具備 iam:CreatePolicyVersion 或 iam:AttachUserPolicy 權限
       ▼
[呼叫 AWS IAM 服務 API]
       │
       ├── 1. 建立具有 {"Effect": "Allow", "Action": "*", "Resource": "*"} 之新版本
       ├── 2. 設定新版本為 Default Version (iam:SetDefaultPolicyVersion)
       ▼
[身分權限突變為全域最高特權 AdministratorAccess]
       │
       ├── 呼叫 sts:AssumeRole 橫向跳躍至跨帳號核心生產環境
       └── 關閉 CloudTrail 審計追蹤 (cloudtrail:StopLogging)，發動勒索加密或銷毀備份
```

### 痛點場景
- **IAM 邏輯隱蔽性極高**：攻擊者提權完全透過合法 AWS REST API 呼叫，不涉及任何記憶體溢位或二進位 Payload，傳統端點 EDR 視線完全被遮蔽。
- **原則語義組合炸彈**：單一 IAM 權限看似無害（例如僅能 `iam:PassRole` 加上 `ec2:RunInstances`），但組合起來即可透過建立掛載高特權 Role 的 EC2 實例完成間接提權。
- **跨帳號與多租戶跳躍複雜**：現代企業常採用 AWS Organizations 多帳號結構，攻擊者利用跨帳號信任關係（Cross-Account AssumeRole）進行橫向滲透，日誌分散在不同帳號的 CloudTrail 中，極難串聯還原。

## 第一動：AWS 核心 IAM 提權路徑與原理剖析 (IAM Privilege Escalation Vectors)

Rhino Security Labs 研究歸納出 21 種經典 AWS IAM 提權路徑，其中最常見且具致命性者如下：

```
+-----------------------------------------------------------------------------------------------+
| AWS IAM 經典提權戰術對比                                                                       |
|                                                                                               |
| 1. 直接篡改自身策略 (Direct Policy Manipulation)                                              |
|    - 觸發權限：iam:CreatePolicyVersion / iam:SetDefaultPolicyVersion                          |
|    - 攻擊手法：直接對自身附加的受管原則新增 Version 5，包含 Action: "*" 並設為預設。          |
|                                                                                               |
| 2. 存取憑證再生成 (Access Key Generation)                                                     |
|    - 觸發權限：iam:CreateAccessKey                                                            |
|    - 攻擊手法：針對具備高權限但尚未達到 2 把 Key 上限的現有管理員帳號，直接生成新 Access Key。|
|                                                                                               |
| 3. 資源委派與身分傳遞 (Resource Delegation: PassRole)                                        |
|    - 觸發權限：iam:PassRole + lambda:CreateFunction + lambda:InvokeFunction                   |
|    - 攻擊手法：建立具備 AdminRole 的 Lambda 函式，由 Lambda 代為執行給自身加權限的操作。       |
|                                                                                               |
| 4. 登入設定檔覆寫 (Login Profile Reset)                                                       |
|    - 觸發權限：iam:UpdateLoginProfile 或 iam:CreateLoginProfile                              |
|    - 攻擊手法：直接重設高權限帳號的 AWS 控制台登入密碼，實現 Web Console 橫向接管。          |
+-----------------------------------------------------------------------------------------------+
```

### 核心提權權限矩陣

| 關鍵危險權限組合 | 提權武器化手法 (Weaponization) | 權限提升結果 (Resulting Privilege) |
| :--- | :--- | :--- |
| **`iam:CreatePolicyVersion`** | 建立包含 `Action: "*"` 的新版 Policy 並設為預設。 | 瞬間升級為 AdministratorAccess。 |
| **`iam:AttachUserPolicy`** | 將現有 AWS 託管的 `AdministratorAccess` 直接附加至自己帳號。 | 瞬間取得所有雲端服務最高權限。 |
| **`iam:PutUserPolicy`** | 向自身帳號寫入 Inline Policy（內嵌策略）。 | 無需現成 Policy，自製完全存取權限。 |
| **`iam:PassRole` + `ec2:RunInstances`** | 啟動一台 EC2 並掛載具備高權限的 Instance Profile，登入該主機自 IMDS 索取權杖。 | 間接取得該 Role 的全部權限。 |

## 第二動：紅隊攻擊模擬與提權重現 (Attack Emulation: Pacu Framework)

利用開源 AWS 滲透測試框架 Pacu 模擬 IAM 提權：

### 1. 使用 Pacu 自動枚舉現有身分之潛在提權路徑
```bash
# 在已攻陷的受害 Access Key 環境下啟動 Pacu
pacu --session corp_pentest
run iam__privesc_scan
```

### 2. 手動執行 `CreatePolicyVersion` 提權指令碼
```bash
# 建立一個具有管理員特權的 Policy JSON
cat << 'EOF' > admin_policy.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "*",
            "Resource": "*"
        }
    ]
}
EOF

# 新增版本並強制設為 Default
aws iam create-policy-version \
    --policy-arn arn:aws:iam::123456789012:policy/DevLimitedPolicy \
    --policy-document file://admin_policy.json \
    --set-as-default
```

## 第三動：CloudTrail 審計遙測配置 (Telemetry Setup: Management Events)

確保 CloudTrail 完整記錄管理事件（Management Events）與資料事件（Data Events）：

### 關鍵 CloudTrail 審計事件
- **`CreatePolicyVersion`**：是否帶有 `setAsDefault: true`。
- **`AttachUserPolicy` / `AttachRolePolicy`**：附加的 `policyArn` 是否為 `AdministratorAccess` 或高權限原則。
- **`PutUserPolicy` / `PutRolePolicy`**：是否有使用者向自身注入 Inline Policy。
- **`AssumeRole`**：記錄跨帳號存取的來源 IP、Role ARN 與 Session Name。

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & Athena Queries)

### 1. Splunk SPL：偵測非預期身分呼叫 IAM 提權高危 API (EventName Monitoring)
```spl
index=aws_cloudtrail sourcetype="aws:cloudtrail"
    eventName IN ("CreatePolicyVersion", "SetDefaultPolicyVersion", "AttachUserPolicy", "AttachGroupPolicy", "AttachRolePolicy", "PutUserPolicy", "PutRolePolicy", "CreateAccessKey", "UpdateLoginProfile")
| search NOT [
    | inputlookup authorized_cloud_admins.csv 
    | rename admin_arn as userIdentity.arn 
    | fields userIdentity.arn
  ]
| stats count earliest(_time) as first_time latest(_time) as last_time 
        values(requestParameters.policyArn) as TargetPolicies,
        values(requestParameters.userName) as TargetUsers by userIdentity.arn, eventName, srcIP, awsRegion
| convert ctime(first_time) ctime(last_time)
| table first_time, last_time, userIdentity.arn, eventName, TargetPolicies, TargetUsers, srcIP, awsRegion
```

### 2. Amazon Athena：查詢異常跨帳號 AssumeRole 追蹤
```sql
SELECT 
    eventtime,
    useridentity.arn AS requesting_identity,
    requestparameters.roleArn AS assumed_role,
    requestparameters.roleSessionName AS session_name,
    sourceipaddress
FROM "cloudtrail_logs"
WHERE eventname = 'AssumeRole'
    AND requestparameters.roleArn LIKE '%AdministratorAccess%'
    AND sourceipaddress NOT LIKE '10.%'
ORDER BY eventtime DESC
LIMIT 50;
```

### 3. Sigma 偵測規則：AWS IAM Privilege Escalation via CreatePolicyVersion
```yaml
title: AWS IAM Privilege Escalation via CreatePolicyVersion
id: 6a2c9183-500b-4721-a4ef-1901a8519124
status: production
description: 偵測使用者嘗試建立具有管理者特權之新版本 IAM 原則並設為預設
logsource:
    service: cloudtrail
    product: aws
detection:
    selection:
        eventName: 'CreatePolicyVersion'
        requestParameters.setAsDefault: true
    policy_content:
        requestParameters.policyDocument|contains:
            - '"Action":"*"'
            - '"Action": "*"'
    condition: selection and policy_content
level: critical
```

## 第五動：權限邊界限制與零信任收斂 (Permissions Boundaries & Least Privilege)

```
[使用者帳號 (Dev-User)]
          │
          ├── 1. 身分型原則 (Identity-based Policy) ──► 授予特定操作
          ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 權限邊界限制 (Permissions Boundary) - 最大天花板            │
 │  - 嚴格限定該身分無論如何附加 Policy，其最大有效權限絕對    │
 │    不能超越此 Boundary (例如嚴禁任何 IAM 操作)              │
 └─────────────────────────────────────────────────────────────┘
          │
          ▼ (有效權限 = 兩者交集 Intersection)
     [安全受控的執行權限]
```

### 1. 實施 IAM Permissions Boundary (權限邊界天花板)
為所有開發者與自動化角色套用 Permissions Boundary，確保其「即使獲得 `iam:*` 也無法給自己提權超過邊界」：
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAccessToSensitiveServices",
      "Effect": "Deny",
      "Action": [
        "iam:*",
        "organizations:*",
        "cloudtrail:*"
      ],
      "Resource": "*"
    }
  ]
}
```

### 2. 使用 AWS IAM Access Analyzer 移除未使用的過寬權限
定期掃描角色與使用者的「最後存取時間（Last Accessed Information）」，將過去 90 天內未呼叫過的 API Action 自動自 Policy 中刪除。

## 靶場實戰：IAM 提權入侵研判與憑證吊銷演練

### 靶場環境情境
- **企業 AWS 帳號**: `112233445566`
- **被盜用身分**: `arn:aws:iam::112233445566:user/intern_bob`
- **警報觸發**: SOC 監控發出 Critical 警報：`intern_bob` 於 03:12 呼叫 `CreateAccessKey` 為帳號 `admin_sarah` 建立了一把全新的 Access Key，並從未知的國外 IP 發起連線。

### 實戰步驟一：審查攻擊路徑
1. 調閱 CloudTrail：確認 `intern_bob` 原有策略中包含被誤設的 `"Action": "iam:CreateAccessKey", "Resource": "*"`。
2. 攻擊者藉此產生了 `admin_sarah` 的密鑰（Key ID: `AKIAIOSFODNN7EXAMPLE`），隨後使用該密鑰列出所有 S3 儲存桶。

### 實戰步驟二：緊急止血與阻斷
1. **立即停用並刪除攻擊者產生的管理員 Access Key**：
   ```bash
   aws iam update-access-key --user-name admin_sarah --access-key-id AKIAIOSFODNN7EXAMPLE --status Inactive
   aws iam delete-access-key --user-name admin_sarah --access-key-id AKIAIOSFODNN7EXAMPLE
   ```
2. **吊銷 `intern_bob` 之所有連線與現有金鑰**：
   ```bash
   aws iam delete-login-profile --user-name intern_bob
   ```

### 實戰步驟三：防線修復
1. 修復 `intern_bob` 原則，將 Resource 限制為自身 ARN：`arn:aws:iam::112233445566:user/${aws:username}`。
2. 為全體非管理員帳號強制配置 Permissions Boundary。
