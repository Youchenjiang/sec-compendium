# 05.1 雲端運算共同責任模型實務與邊界劃分 (Cloud Security Shared Responsibility Matrix)

## 案發現場破題

在企業大步邁向多雲架構（AWS, Microsoft Azure, Google Cloud）的進程中，資安事故頻傳的最核心根源並非「雲端底層被黑客攻破」，而是「**雲端租戶使用者的錯誤配置（Misconfiguration）與對共同責任模型（Shared Responsibility Model）的認知盲區**」。許多企業誤以為只要將服務部署上雲，備份、加密、身分驗證、修補漏洞與防禦入侵就全由 CSP（雲端服務提供者）負責，最終導致 S3 儲存桶公開裸奔、IAM 權限漫天飛舞。

```
+-------------------------------------------------------------------------------+
| 傳統迷思：把主機丟上雲端，AWS/Azure 會幫我防禦一切黑客入侵？ (FATAL ERROR!)   |
+-------------------------------------------------------------------------------+
       │
       ▼ 【真實世界：共同責任分界線】
┌─────────────────────────────────────────────────────────────────────────────┐
│ 客戶責任 (Security IN the Cloud) - 永不脫責！                                │
│  - 客戶數據 (Customer Data) ── 加密、備份、資料防外洩 (DLP)                 │
│  - 身分與存取管理 (IAM) ── 帳號密碼、MFA、最小權限原則                      │
│  - 應用程式與作業系統 ── 軟體修補 (Patching)、防火牆規則 (Security Groups)   │
├─────────────────────────────────────────────────────────────────────────────┤
│ 雲端服務商責任 (Security OF the Cloud)                                       │
│  - 運算、儲存、資料庫、網路實體硬體 ── 實體機房、電力、纜線、伺服器硬體維護 │
│  - 虛擬化底層 Hypervisor ── Xen/KVM 安全隔離、微代碼更新                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 痛點場景
- **IaaS / PaaS / SaaS 權責界限混淆**：在 IaaS（如 EC2 / Azure VM）下，作業系統核心漏洞（如 Dirty COW / EternalBlue）與中繼資料保護 CSP 概不負責，企業若未打補丁即遭長驅直入。
- **身分與資料責任永久在租戶**：無論使用哪種雲端服務型態（即便使用 Microsoft 365 或 Salesforce 等 SaaS），「帳號密碼外洩」與「敏感資料外流」的法定責任（GDPR / 個人資料保護法）永遠由企業承擔。
- **跨雲合規審計難以收斂**：各雲平台名詞不一（AWS Security Group vs Azure NSG vs GCP Firewall Rules），缺乏統一的雲端安全狀態管理（CSPM）。

## 第一動：IaaS / PaaS / SaaS 責任矩陣深度解析 (Architecture Breakdown)

```
+-----------------------------------------------------------------------------------------------+
| 雲端服務模型責任矩陣對比                                                                       |
|                                                                                               |
| 服務層級 (Stack Layers)   │ IaaS (EC2/GCE/VM) │ PaaS (RDS/AppService) │ SaaS (M365/Salesforce)|
| ─────────────────────────┼───────────────────┼───────────────────────┼───────────────────────|
| 1. 資料與身分 (Data & IAM)│  👑 客戶完全負責   │    👑 客戶完全負責     │    👑 客戶完全負責    |
| 2. 應用程式 (Application) │  👑 客戶完全負責   │    👑 客戶完全負責     │    🏢 CSP 負責維護    |
| 3. 執行環境 (Runtime)     │  👑 客戶完全負責   │    🏢 CSP 負責更新     │    🏢 CSP 負責維護    |
| 4. 作業系統 (OS & Kernel) │  👑 客戶完全負責   │    🏢 CSP 自動修補     │    🏢 CSP 負責維護    |
| 5. 虛擬化網路 (VPC / FW)  │  👑 客戶配置規則   │    🤝 雙方共同分擔     │    🏢 CSP 負責架構    |
| 6. 實體硬體與機房設施     │  🏢 CSP 完全負責   │    🏢 CSP 完全負責     │    🏢 CSP 完全負責    |
+-----------------------------------------------------------------------------------------------+
```

### 關鍵權責迷思破除

| 典型誤解 | 真實技術現狀與權責歸屬 (The Reality) |
| :--- | :--- |
| 「RDS 資料庫交給 AWS，我們不需要備份與加密」 | AWS 只保證 RDS 實體儲存與 MySQL 引擎運行，但**自動備份週期、透明資料加密 (KMS)、未授權 SQL 存取**全由客戶負責。 |
| 「使用 S3 儲存檔案非常安全，不會被竊聽」 | S3 伺服器端加密 (SSE-S3/KMS) 需正確開啟，且 **Bucket Policy / ACL 的公開權限** 若被設為 Public，責任 100% 在於配置者。 |
| 「雲端主機遭黑客植入勒索軟體，CSP 應該賠償」 | 在 IaaS 架構下，端點防毒、系統漏洞補丁、SSH/RDP 存取控制屬於客戶責任範疇，CSP 免責。 |

## 第二動：雲端安全狀態配置與稽核工具鏈 (CSPM Toolchain: Prowler & ScoutSuite)

使用開源雲端安全姿態管理工具（CSPM）自動化檢驗 AWS 帳號是否違反 CIS AWS Foundations Benchmark。

### 1. 使用 Prowler 執行 CIS 基準線全域合規檢查
```bash
# 執行 Prowler 針對 IAM、S3、CloudTrail 與網路配置進行深度掃描
prowler aws --compliance cis_2.0_aws -M json,csv

# 快速檢索關鍵失敗項目 (FAIL)
cat output/prowler-output-*.json | jq '.[] | select(.Status == "FAIL") | {CheckID: .CheckID, Region: .Region, ResourceId: .ResourceId}'
```

### 2. 檢測 S3 儲存桶公開暴露狀態 (AWS CLI)
```bash
# 查詢所有停用 Public Access Block 的高危儲存桶
aws s3control get-public-access-block --account-id $(aws sts get-caller-identity --query "Account" --output text)
```

## 第三動：日誌遙測設定與審計追蹤 (Telemetry Setup: CloudTrail & VPC Flow)

確保多雲環境的所有管理操作與網路連線皆具備不可抹滅的審計軌跡：

### 1. 啟用全區域 AWS CloudTrail 多區域追蹤
```bash
aws cloudtrail create-trail --name corp-audit-trail \
    --s3-bucket-name corp-centralized-audit-logs \
    --is-multi-region-trail \
    --enable-log-file-validation
```

### 2. 關鍵審計指標
- **`CloudTrail EventName`**：
  - `PutBucketPolicy` / `PutBucketAcl`：修改儲存桶權限。
  - `AuthorizeSecurityGroupIngress`：開放安全群組入向規則（特別是 `0.0.0.0/0` 到 Port 22/3389）。
  - `CreateUser` / `CreateAccessKey`：新增 IAM 身分與存取憑證。

## 第四動：SIEM 關聯規則與即時違規偵測 (Splunk SPL & Sigma)

### 1. Splunk SPL：偵測開放 0.0.0.0/0 至管理連接埠之高危安全群組變更
```spl
index=aws_cloudtrail sourcetype="aws:cloudtrail" eventName="AuthorizeSecurityGroupIngress"
| spath path=requestParameters.ipPermissions.items{} output=rules
| mvexpand rules
| spath input=rules
| eval FromPort=fromPort, ToPort=toPort, CidrIp='ipRanges.items{}.cidrIp'
| search CidrIp="0.0.0.0/0" AND (FromPort IN (22, 3389, 445, 1433, 3306) OR isnull(FromPort))
| stats count earliest(_time) as first_time latest(_time) as last_time by userIdentity.arn, requestParameters.groupId, CidrIp, FromPort
| convert ctime(first_time) ctime(last_time)
| table first_time, last_time, userIdentity.arn, requestParameters.groupId, CidrIp, FromPort
```

### 2. Splunk SPL：偵測 S3 儲存桶被移除 Public Access Block 限制
```spl
index=aws_cloudtrail sourcetype="aws:cloudtrail" eventName IN ("DeleteAccountPublicAccessBlock", "DeleteBucketPublicAccessBlock")
| table _time, userIdentity.arn, srcIP, requestParameters.bucketName, eventName
```

### 3. Sigma 偵測規則：AWS Security Group Wide Open to Internet
```yaml
title: AWS Security Group Exposed to Internet
id: 11bf8409-77a1-432a-bc90-99120485ac55
status: production
description: 偵測 AWS 安全群組被配置對全網際網路 (0.0.0.0/0) 開放敏感連接埠
logsource:
    service: cloudtrail
    product: aws
detection:
    selection:
        eventName: 'AuthorizeSecurityGroupIngress'
        requestParameters.ipPermissions.items.ipRanges.items.cidrIp: '0.0.0.0/0'
    condition: selection
level: high
```

## 第五動：雲端防禦加固與組織層控制 (Cloud Hardening & SCPs)

```
[AWS Organizations 根節點 (Root)]
               │
               ▼ 套用服務控制原則 (Service Control Policies, SCPs)
 ┌─────────────────────────────────────────────────────────────┐
 │ 1. 全局強制禁止關閉 CloudTrail                              │
 │ 2. 全局禁止在任何帳號下建立公開 S3 儲存桶 (Enforce S3 Block)│
 │ 3. 限制僅允許特定合格區域 (Region Restriction: ap-northeast-1)│
 └─────────────────────────────────────────────────────────────┘
               │
               ├── 委派給所有子帳號 (Production, Staging, Sandbox)
               ▼
   [任何具備 Admin 權限的子帳號均無法逾越上述硬性邊界]
```

### 1. 部署組織級服務控制原則 (SCP: 禁止公開 S3)
在 AWS Organizations 中套用 SCP，從根源杜絕人為失誤：
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceBucketPublicAccessBlock",
      "Effect": "Deny",
      "Action": [
        "s3:PutBucketPublicAccessBlock",
        "s3:DeleteBucketPublicAccessBlock"
      ],
      "Resource": "*",
      "Condition": {
        "NumericLessThan": {
          "s3:BlockPublicPolicy": 1
        }
      }
    }
  ]
}
```

### 2. 啟用 AWS KMS 客戶託管金鑰 (CMK) 與自動輪替
- 對所有 S3 儲存桶、EBS 磁碟區與 RDS 資料庫強制採用 KMS CMK 加密。
- 啟用年度金鑰自動輪替（Automatic Key Rotation）。

## 靶場實戰：S3 權限漂移與雲端入侵通報處置

### 靶場環境情境
- **企業雲端帳號**: `AWS-PROD-9988112233`
- **受害資產**: S3 儲存桶 `corp-customer-invoices` (存放十萬名客戶開票 PDF)
- **警報觸發**: 雲端威脅情資平台告警，DarkWeb 出現該儲存桶公開下載連結。

### 實戰步驟一：審查儲存桶配置
1. 查詢該儲存桶 Policy：
   ```bash
   aws s3api get-bucket-policy --bucket corp-customer-invoices
   ```
   發現存在 `"Principal": "*"` 且 `"Action": "s3:GetObject"` 的公開唯讀授權。
2. 調閱 CloudTrail，發現 3 天前由離職工程師發起 `PutBucketPolicy` 操作。

### 實戰步驟二：緊急止血與阻斷
1. **立即開啟帳號層級與儲存桶層級的 S3 Block Public Access**：
   ```bash
   aws s3api put-public-access-block --bucket corp-customer-invoices \
       --public-access-block-configuration "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
   ```
2. 確認對外匿名連線已全數回傳 `403 AccessDenied`。

### 實戰步驟三：衝擊評估與合規通報
1. 透過 S3 伺服器存取日誌（Access Logs）清查被下載之 IP 列表與檔案清單。
2. 啟動事件應變通報程序，撰寫資安通報書並呈報資安長與個資主管機關。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **權責界定**：能針對 IaaS、PaaS、SaaS 精確畫出 CSP 與租戶的責任分界線，並明確說明為何「身分與資料安全永不脫責」。
- [ ] **合規檢測**：熟練使用 Prowler 或 ScoutSuite 自動化運行 CIS 基準線檢驗，精確找出未合規之雲端資產。
- [ ] **網路加固**：能撰寫嚴格的安全群組（Security Group）與網路 ACL，杜絕 `0.0.0.0/0` 對管理埠（22/3389）的暴露。
- [ ] **組織控制**：能編寫 AWS Organizations SCP（Service Control Policy），在根帳號層級強制限制高危行為。
- [ ] **日誌審計追蹤**：能熟練運用 CloudTrail 與 SIEM 關聯規則，即時獵捕未授權之儲存桶權限變更與憑證新增事件。
