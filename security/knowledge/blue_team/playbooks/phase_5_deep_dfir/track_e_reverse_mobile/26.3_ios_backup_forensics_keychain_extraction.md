# 實戰手冊 26.3：iOS 備份檔案深度取證、Manifest.db 索引逆推與鑰匙圈 (Keychain) 敏感憑證萃取

## 案發現場破題

在企業高階主管或關鍵涉密人員的行動資安調查中，Apple iOS 設備因其硬體安全隔區（Secure Enclave, SEP）、強制代碼簽名（Code Signing）與嚴格的沙盒限制（Sandbox），長期被視為相對封閉且安全的行動系統。然而，攻擊者若透過實體接觸、配對信任劫持（Pairing Lockout Bypass）或在被害端電腦植入資訊竊取木馬（Infostealer），常藉由觸發 iTunes / Finder 備份機制，將整支 iPhone 的全量資料轉儲至本機電腦。

未加密的 iOS 備份實質上是一座龐大的「數位情報金礦」——它收錄了近乎未加密的 SMS 簡訊、Call History 通話紀錄、Safari 瀏覽歷史、LINE / WhatsApp 聊天資料庫、甚至照片地理位置中繼資料（EXIF GPS）。此外，若取得了使用者備份密碼，鑑識人員更可進一步解密核心鑰匙圈（`keychain-backup.plist`），提取出明文 Wi-Fi 密碼、VPN 帳密、郵件 Token 與網站保存之登入憑證。身為藍隊高階鑑識專家，必須掌握 iOS 備份結構、Manifest.db SQLite 索引映射邏輯，並精通使用開源工具鏈完成無痕資料還原與資安侵害研判。

```
iOS 備份架構與鑑識解密流程圖：

[被害端電腦本機備份目錄]
Windows: %APPDATA%\Apple Computer\MobileSync\Backup\<UDID>\
macOS:   ~/Library/Application Support/MobileSync/Backup/<UDID>/
  │
  ├── Info.plist       (設備名稱、電話號碼、iOS 版本、最後備份時間)
  ├── Status.plist     (備份狀態、是否完整完成)
  ├── Manifest.plist   (是否加密 IsEncrypted, Keybag 金鑰袋封裝)
  ├── Manifest.db      (核心 SQLite 索引: 記錄 2位元組前綴子目錄與 SHA1 檔名映射)
  └── [00~ff]/         (數萬個以 SHA1 雜湊命名的實際資料二進位檔)
            │
            ├─ 未加密備份 ───> 讀取 Manifest.db ───> 直接還原 sms.db, CallHistory.storedata
            │
            └─ 已加密備份 (IsEncrypted=1)
                     │
                     ▼ 需取得備份密碼 (或 Hashcat 暴力枚舉 PBKDF2/scrypt 密碼)
               派生 Master Key ──> 解鎖 Keybag
                     │
                     ├── 還原所有檔案目錄
                     └── 解密 keychain-backup.plist ──> 導出明文密碼與 Token
```

## 第一動：iOS 備份檔案結構與加密保護體系

### 1.1 備份核心檔案功能清單
- **`Info.plist`**：包含設備基本元數據（Device Name, Phone Number, IMEI, Serial Number, Build Version）。
- **`Manifest.plist`**：記載備份安全性狀態：
  - `IsEncrypted`：布林值（`true` 代表備份經由使用者密碼加密保護；`false` 代表完全明文）。
  - `BackupKeyBag`：儲存經密碼加密封裝的各類資料保護類別金鑰（Protection Classes A~D）。
- **`Manifest.db`**：SQLite 3 資料庫，內含 `Files` 資料表，記錄了真實 iOS 檔案路徑（如 `HomeDomain/Library/SMS/sms.db`）與磁碟上 40 位元組十六進位雜湊檔名的對應關係。

### 1.2 檔案雜湊命名規則（SHA-1 映射演算法）
在 iOS 備份目錄中，檔案不是以原始檔名存放，而是以其 `Domain-RelativePath` 的 SHA-1 雜湊命名，並分散於前兩碼為目錄名的資料夾中：
$$\text{Storage Path} = \text{SHA1}(\text{Domain} + "-" + \text{RelativePath})$$
- 例：`HomeDomain-Library/SMS/sms.db` 的 SHA-1 雜湊為 `3d0d7e5fb2ce288813306e4d4636395e047a3d28`。
- 其在硬碟上的真實物理路徑為：`Backup/<UDID>/3d/3d0d7e5fb2ce288813306e4d4636395e047a3d28`。

## 第二動：鑰匙圈（Keychain）保護機制與資料類別

### 2.1 iOS Keychain Protection Classes（保護類別）
鑰匙圈條目儲存於 `keychain-backup.plist`，各項目依據安全性劃分不同保護等級：
- `kSecAttrAccessibleAlways`：任何時候皆可存取（極少使用，安全性最低）。
- `kSecAttrAccessibleAfterFirstUnlock`：開機後使用者輸入一次解鎖密碼即可在背景常駐存取（常見於通訊軟體接收推播）。
- `kSecAttrAccessibleWhenUnlocked`：**預設標準等級**。僅在設備處於螢幕解鎖狀態時才可存取。
- `ThisDeviceOnly` 旗標：禁止該項目隨 iCloud 或非本機備份遷移至其他硬體。

### 2.2 鑰匙圈鑑識價值指標
- 企業內部 WPA2/WPA3-Enterprise 802.1X 連線金鑰與憑證。
- Safari 自動填入的使用者網站帳號與明文密碼。
- 郵件客戶端（Exchange / Gmail）的 OAuth Refresh Token 與應用程式專用密碼。

## 第三動：手動獵捕與鑑識分析（Manifest 查詢 & Python）

### 3.1 查詢 Manifest.db 快速定位簡訊與通訊錄資料庫
```bash
# 步驟 1：進入 iOS 備份目錄
cd "/c/Users/TargetUser/AppData/Roaming/Apple Computer/MobileSync/Backup/00008030-001234567890ABCD"

# 步驟 2：使用 sqlite3 查詢 Manifest.db 中 SMS 簡訊資料庫的實際雜湊路徑
sqlite3 Manifest.db "SELECT fileID, relativePath, domain FROM Files WHERE relativePath LIKE '%sms.db';"

# 輸出範例:
# 3d0d7e5fb2ce288813306e4d4636395e047a3d28|Library/SMS/sms.db|HomeDomain

# 步驟 3：定位並複製出目標資料庫
cp 3d/3d0d7e5fb2ce288813306e4d4636395e047a3d28 /tmp/extracted_sms.db
```

### 3.2 鑑識 SMS 簡訊資料庫中的釣魚連結與驗證碼
```bash
# 查詢簡訊內容與時間戳 (Apple CoreData 紀元: 2001-01-01 起算，偏差值 978307200 秒)
sqlite3 /tmp/extracted_sms.db "
SELECT datetime(date/1000000000 + 978307200, 'unixepoch', 'localtime') AS sent_time,
       text 
FROM message 
WHERE text LIKE '%http%' OR text LIKE '%驗證碼%' OR text LIKE '%code%' 
ORDER BY date DESC LIMIT 10;"
```

### 3.3 Python 自動化遍歷 Manifest.db 還原全檔案樹腳本
```python
import os
import sys
import sqlite3
import shutil

def restore_ios_backup(backup_dir, output_dir):
    manifest_db = os.path.join(backup_dir, "Manifest.db")
    if not os.path.exists(manifest_db):
        print(f"[-] 找不到 Manifest.db: {manifest_db}")
        return

    print(f"[*] 連線 Manifest.db 並開始還原檔案結構至: {output_dir}")
    conn = sqlite3.connect(manifest_db)
    cursor = conn.cursor()

    cursor.execute("SELECT fileID, domain, relativePath, flags FROM Files WHERE flags=1")
    count = 0
    for file_id, domain, rel_path, flags in cursor.fetchall():
        # flags = 1 代表普通檔案 (2 代表目錄)
        prefix = file_id[:2]
        src_path = os.path.join(backup_dir, prefix, file_id)
        
        if os.path.exists(src_path):
            target_path = os.path.join(output_dir, domain, rel_path)
            os.makedirs(os.path.dirname(target_path), exist_ok=True)
            try:
                shutil.copy2(src_path, target_path)
                count += 1
            except Exception as e:
                continue

    conn.close()
    print(f"[+] 成功還原 {count} 個檔案至 {output_dir}")

if __name__ == '__main__':
    if len(sys.argv) > 2:
        restore_ios_backup(sys.argv[1], sys.argv[2])
    else:
        print("用法: python restore_ios.py <backup_dir> <output_dir>")
```

## 第五動：企業級防禦硬化與應急響應阻斷

### 5.1 強制實施企業 MDM 強制備份加密配置
- 透過 Apple Configurator 或 MDM 部署 Configuration Profile：
  - 勾選 `Force encrypted backups`（強制加密備份）。
  - 當此策略套用後，使用者在 Finder / iTunes 建立本機備份時，**強制必須設定密碼**，未加密選項將直接反灰禁用。
  - 即使駭客取得實體電腦硬碟，因具備 PBKDF2/scrypt 高強度密鑰封裝，無法直接讀取明文 SQLite 與鑰匙圈。

### 5.2 封鎖受管公務設備之本機配對（Host Pairing Lockout）
- 在企業 Supervised（受監管）設備上，透過 MDM 限制 `allowHostPairing=false`。設備將拒絕與任何未經企業 MDM 授權的電腦建立 USB 信任配對，徹底封殺本機備份與旁路導出資料的可能。

## 靶場實戰：從未加密備份還原通聯記錄與 Safari 瀏覽歷史

### 實驗目標
在分析機上載入靶場提供的 iOS 未加密備份資料夾 `ios_backup_evidence`，定位 Safari 瀏覽資料庫，還原受害者點擊釣魚網站的歷史記錄：

```bash
# 步驟 1：檢驗備份是否加密 (檢查 Manifest.plist)
plistutil -i ios_backup_evidence/Manifest.plist | grep -A 1 "IsEncrypted"

# 步驟 2：利用 sqlite3 查詢 Safari 瀏覽歷史之 fileID
sqlite3 ios_backup_evidence/Manifest.db \
  "SELECT fileID FROM Files WHERE relativePath='Library/Safari/History.db';"

# 輸出假設為: 8f029b3c4...
# 步驟 3：複製並查詢歷史訪問網址
cp ios_backup_evidence/8f/8f029b3c4* /tmp/History.db
sqlite3 /tmp/History.db \
  "SELECT datetime(visit_time + 978307200, 'unixepoch', 'localtime'), url, title FROM history_visits JOIN history_items ON history_visits.history_item = history_items.id ORDER BY visit_time DESC LIMIT 10;"
```
