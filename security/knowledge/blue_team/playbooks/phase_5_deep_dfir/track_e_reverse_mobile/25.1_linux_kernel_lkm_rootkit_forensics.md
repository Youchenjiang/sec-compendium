# 實戰手冊 25.1：Linux 核心模組 (LKM) Rootkit 偵測、Syscall Hooking 與斷鏈隱蔽取證

## 案發現場破題

在 Linux 伺服器的高階滲透與國家級 APT 入侵中，攻擊者一旦取得 `root` 最高權限，往往會安裝可載入核心模組（LKM, Loadable Kernel Module）層級的 Rootkit（例如 Reptile、Diamorphine）。相較於用戶態後門，LKM Rootkit 運行於 Ring 0 核心空間，具備對作業系統底層的絕對支配力。

攻擊者透過篡改系統呼叫表（System Call Table, `sys_call_table`）、使用 ftrace / kprobes 掛鉤核心函式、或從核心模組雙向鏈表（`modules` 鏈表）中將自己「摘鏈（Unhook / Unlink）」，實現對 `lsmod`、`/proc/modules`、特定連線端口、甚至檔案與進程的全面「幽靈化隱形」。傳統基於用戶態指令（如 `ps`, `netstat`, `top`）的排查手段在此全面失效。藍隊鑑識工程師必須深入 Linux 核心記憶體架構，掌握從 `kallsyms` 符號比對、CR0 暫存器寫保護分析到 Volatility 3 核心斷鏈比對的硬核反隱蔽技術。

```

[用戶態 User Space (Ring 3)]
  ps, ls, netstat, kill ───┐
                           ▼ 透過 glibc 發起系統呼叫 (e.g. sys_kill, sys_getdents64)
+──────────────────────────┼─────────────────────────────────────────────────+
| 核心態 Kernel Space (Ring 0)                                               |
|                          ▼                                                 |
|                   sys_call_table (系統呼叫表)                              |

|         [正常指向]       │       [遭 LKM Rootkit 篡改]                      |

|                          │          │  (如 "reptile_" 則自動自 dirent 抹除) |

|                          └─────> 轉發呼叫原 real_getdents64                |
```

## 第一動：核心模組運作機制與隱蔽機理

### 1.1 Syscall Hooking（系統呼叫掛鉤）原理
- Linux 早期透過修改 `sys_call_table` 陣列中的函式指針實現攔截。因為核心空間在現代架構具備唯讀保護（Write Protect），Rootkit 會透過竄改 CPU 控制暫存器 `CR0` 的第 16 位元（WP, Write Protect bit）暫時關閉保護：
  ```c
  write_cr0(read_cr0() & (~ 0x10000)); // 關閉核心寫保護
  sys_call_table[__NR_getdents64] = (unsigned long*)hooked_getdents64;
  write_cr0(read_cr0() | 0x10000);  // 恢復寫保護
  ```
- **現代掛鉤方式**：利用核心自帶的性能分析框架 `ftrace`（Function Tracer）或 `kprobes`，註冊前置回呼函式（Pre-handler），在無須修改記憶體屬性的情況下實現無痕掛鉤。

### 1.2 核心鏈表摘鏈（DKOM Unlinking）
- 核心內部使用雙向循環鏈表 `struct list_head list` 串聯所有載入的模組。
- `lsmod` 與 `/proc/modules` 透過讀取全域變數 `modules` 走訪鏈表。
- Rootkit 呼叫 `list_del(&THIS_MODULE->list)` 將自己自鏈表中移除。此時 `THIS_MODULE` 的記憶體未被釋放，其註冊的 Hook 依然生效，但 `lsmod` 完全看不到它。

### 1.3 `sysfs` 與 `kobject` 抹除
- 除了鏈表摘鏈，Rootkit 還會呼叫 `kobject_del(&THIS_MODULE->mkobj.kobj)` 刪除位於 `/sys/module/<name>` 下的目錄結構，抹除一切用戶態可見檔案軌跡。

## 第二動：異常特徵與日誌軌跡定位

### 2.1 核心日誌與崩潰紀錄（dmesg / /var/log/kern.log）
- 載入未經簽名的模組時，核心會記錄 tainted 污損標記：
  ```text
  [ 1234.567890] module: loading out-of-tree module taints kernel.
  [ 1234.567891] module: module verification failed: signature and/or required key missing - tainting kernel
  ```
- 若出現 `taints kernel` 且包含 `O`（Out-of-tree 外部編譯）或 `E`（Unsigned 模組未簽名），為關鍵前兆。

### 2.2 `/proc/kallsyms` 符號指標偏離
正常情況下，`sys_call_table` 與系統呼叫常式位址落在核心固定的代碼區段（Text Segment）。若某個系統呼叫位址落入動態模組配置的 vmalloc 區域（例如 `0xffffffffc0000000` 以上），100% 遭到外部核心模組篡改。

### 3.3 Python 腳本自製快速核心掛鉤檢測器
```python
import os
import sys

def check_syscall_hooking():
    kallsyms_path = "/proc/kallsyms"
    if not os.path.exists(kallsyms_path):
        print(f"[-] 無法讀取 {kallsyms_path}，請確認 root 權限與核心保護設定")
        return

    print("[*] 開始審查核心符號表與重要 Syscall 位址...")
    syscalls = {}
    with open(kallsyms_path, "r") as f:
        for line in f:
            parts = line.strip().split()
            if len(parts) >= 3:
                addr, sym_type, name = parts[0], parts[1], parts[2]
                if name in ["sys_call_table", "__x64_sys_getdents64", "__x64_sys_kill", "__x64_sys_read"]:
                    syscalls[name] = int(addr, 16)
                    print(f"  - 符號 [{name:25s}] 位址: 0x{addr}")

    # 判斷標準：若核心函式位址落在典型模組 vmalloc 區間 (x86_64 通常 >= 0xffffffffa0000000 但非 _stext)
    # 在此做基礎區間常識判定
    for name, addr in syscalls.items():
        if name != "sys_call_table":
            if addr == 0:
                print(f"[!] 警告: {name} 位址為 0 (可能受 kptr_restrict 保護，請設定 echo 0 > /proc/sys/kernel/kptr_restrict)")

if __name__ == '__main__':
    if os.geteuid() != 0:
        print("[-] 本工具需要 root 權限以解析核心符號")
    else:
        check_syscall_hooking()
```

## 第四動：SIEM 關聯規則與端點威脅指標工程

### 4.1 Splunk 整合 Linux Auditd 監控未授權模組載入（`init_module` / `finit_module`）
```spl
index=linux_audit type=SYSCALL (syscall=175 OR syscall=313)
| eval exe=lower(exe), comm=lower(comm)
| search NOT exe IN ("/usr/bin/kmod", "/usr/sbin/modprobe", "/usr/bin/systemd")
| stats count min(_time) as first_seen max(_time) as last_seen by host, uid, auid, comm, exe
| eval alert="Unauthorized Kernel Module Insertion Attempt (LKM Rootkit)"
| table first_seen, host, uid, auid, comm, exe, count, alert
```

## 第五動：企業級防禦硬化與應急響應阻斷

### 5.1 強制啟用 UEFI Secure Boot 與 Linux 核心模組簽名鎖定（Module Signature Verification）
- **核心編譯旗標**：
  - `CONFIG_MODULE_SIG=y`（啟用模組簽名驗證）。
  - `CONFIG_MODULE_SIG_FORCE=y`（**強制模式**：任何未經企業私鑰簽名之 `.ko` 模組一律禁止載入）。
- **啟動 Lockdown 模式**：
  在 GRUB 核心參數中加入 `lockdown=confidentiality` 或 `lockdown=integrity`，禁止透過 `/dev/mem`、`/dev/kmem`、kprobes 或 BPF 直接覆寫核心代碼空間。

### 5.2 系統全生命週期禁止動態模組載入（防禦固化）
若伺服器為固定專屬用途（如 Web Server、DB Cluster），在啟動完成所有合法硬體驅動後，透過 sysctl 徹底關閉核心模組載入通道：
```bash
# 永久停用動態載入模組 (設為 1 後無法逆轉，唯有重新開機才能復原)
sudo sysctl -w kernel.modules_disabled=1

# 固化至配置檔
echo "kernel.modules_disabled = 1" | sudo tee -a /etc/sysctl.d/99-kernel-hardening.conf
```

## 靶場實戰：編譯測試 LKM 模組並觀察符號與日誌特徵

### 實驗目標
在測試環境編寫一個最精簡的核心模組 `test_lkm.c`，載入核心並比對 `/proc/modules` 與 `dmesg` 紀錄：

```bash
# 步驟 1：編寫測試模組源碼
cat << 'EOF' > test_lkm.c
#include <linux/init.h>
#include <linux/module.h>
#include <linux/kernel.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("BlueTeam DFIR Range");
MODULE_DESCRIPTION("Benchmark LKM Forensics");

static int __init test_init(void) {
    printk(KERN_INFO "[DFIR] Test LKM Loaded at init\n");
    return 0;
}

static void __exit test_exit(void) {
    printk(KERN_INFO "[DFIR] Test LKM Unloaded\n");
}

module_init(test_init);
module_exit(test_exit);
EOF

# 步驟 2：編寫 Makefile
cat << 'EOF' > Makefile
obj-m += test_lkm.o
all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
EOF

# 步驟 3：編譯與載入測試模組
make
sudo insmod test_lkm.ko

# 步驟 4：鑑識排查 (觀察 tainted 告警與 /proc/modules 註冊條目)
dmesg | tail -n 5
grep "test_lkm" /proc/modules
sudo rmmod test_lkm
```
