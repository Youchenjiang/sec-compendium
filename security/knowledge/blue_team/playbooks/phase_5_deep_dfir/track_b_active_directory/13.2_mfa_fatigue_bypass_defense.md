# 13.2 多因素驗證疲勞轟炸與即時中間人釣魚防禦 (MFA Fatigue & AiTM Phishing Defense)

## 案發現場破題

近年來，多因素驗證（Multi-Factor Authentication, MFA）已成為企業身分防線的黃金標準，有效遏阻了 99% 的傳統認證憑證填充（Credential Stuffing）與密碼外洩攻擊。然而，攻擊者並未止步於此，而是演化出兩大突破 MFA 的主要戰術：
1. **MFA 疲勞轟炸攻擊 (MFA Fatigue / Push Bombing, MITRE ATT&CK T1621)**：在深夜連續發送數十至數百次推播確認，誘使受害者因煩躁、誤觸或半夢半醒間按下「核准（Approve）」。
2. **即時反向代理中間人釣魚 (Adversary-in-the-Middle, AiTM, MITRE ATT&CK T1566 / T1539)**：使用 Evilginx2 等工具攔截受害者與真實 IdP 之間的通訊，偷渡由 IdP 簽發的 Session Cookie，實現「零密碼、無視 MFA」的即時會話劫持。

```
[受害者瀏覽器] ──── 連線 ────► [Evilginx2 AiTM 釣魚代理] ──── 轉發 ────► [Microsoft 365 IdP]
      │                                   │                                     │
      │ ── 1. 輸入密碼與 MFA 驗證碼 ───►  │ ────── 2. 轉發憑證與 MFA 驗證 ────►  │
      │                                   │                                     │
      │ ◄── 4. 偽造重導向 (成功登入) ────  │ ◄───── 3. 回傳 Session Cookie ──────┘
      │                                   │
      └───────────────────────────────────┴──► [攻擊者直接匯入 Cookie 接管雲端會話]
```

### 痛點場景
- **傳統 MFA 形式脆弱（Weak MFA Factors）**：基於 SMS 簡訊驗證碼、單純按鈕推播（Push Notification）或 TOTP 6 位動態碼的機制，在面對 AiTM 中間人反向代理時毫無防禦能力。
- **警報盲區與誤報干擾**：若使用者最終在推播通知上按下同意，系統只會記錄一次「成功的多因素驗證登入（Event ID 4624 / Azure Sign-in Success）」，SOC 分析師難以察覺該次核准前曾發生數十次失敗與取消。
- **後續橫向移動迅速**：一旦攻擊者取得 Session Cookie，可立即以該身分註冊自身裝置至租戶、發送內部魚叉式釣魚郵件、或建立長期有效的應用程式委派。

## 第一動：攻擊原理與中間人攔截剖析 (MFA Fatigue & AiTM Mechanics)

```
+-----------------------------------------------------------------------------------------------+
| MFA 攻擊型態對比                                                                               |
|                                                                                               |
| 1. MFA Fatigue (Push Bombing)                                                                 |
|    - 攻擊前置：已取得受害者帳號與靜態密碼                                                    |
|    - 手法特徵：透過自動化腳本於短時間內發動高頻 Push 請求                                    |
|    - 致命弱點：推播通知未包含情境資訊 (如地理位置、請求應用、數字匹配)                        |
|                                                                                               |
| 2. Adversary-in-the-Middle (AiTM)                                                             |
|    - 攻擊前置：架設反向代理 (Reverse Proxy) 鏡像真實登入頁面                                   |
|    - 手法特徵：動態代理 TLS 流量，攔截 HTTP 回應標頭 Set-Cookie (如 ESTSAUTH, ESTSAUTHPERSISTENT)|
|    - 致命弱點：驗證機制未綁定 TLS 傳輸層通道與網域名稱 (Non-Phishing Resistant)                |
+-----------------------------------------------------------------------------------------------+
```

### 攻擊特徵與行為指標

| 攻擊手法類型 | 典型特徵與日誌表現 | 關鍵威脅指標 (IoC / IoA) |
| :--- | :--- | :--- |
| **MFA Fatigue (T1621)** | 短時間內連續出現大量「MFA denied」或「MFA timeout」，隨後緊接一次「MFA completed」。 | - 5 分鐘內超過 10 次推播拒絕。<br>- 登入時間點處於非上班時段或深夜（23:00 - 05:00）。 |
| **AiTM Reverse Proxy (T1539)** | - 登入 IP 屬於常見雲端 VPS (DigitalOcean, Linode, AWS)。<br>- User-Agent 存在指紋異常。<br>- 無對應之 Microsoft Authenticator 裝置憑證。 | - 登入網址非合法 IdP 網域（如 `login.microsoftonline.com.attacker.com`）。<br>- 短期內出現「新奇連線地理躍遷（Impossible Travel）」。 |

## 第二動：紅隊測試手法與模擬腳本 (Attack Emulation: Push Flood & AiTM)

### 1. MFA 推播疲勞轟炸模擬 (PowerShell API 呼叫)
紅隊在取得帳號密碼後，利用腳本持續觸發驗證挑戰：
```powershell
# 模擬對目標使用者發動連續 15 次 MFA 推播請求
$targetUser = "victim@corp.com"
$password = $env:TARGET_PASSWORD # 從環境變數讀取，避免硬編碼金鑰

for ($i = 1; $i -le 15; $i++) {
    Write-Host "[*] 發送第 $i 次 MFA 挑戰請求給 $targetUser..." -ForegroundColor Yellow
    # 呼叫身分驗證端點觸發推播 (示意調用)
    Invoke-RestMethod -Uri "https://login.microsoftonline.com/common/oauth2/token" -Method Post -Body @{
        client_id = "1b730954-1685-4b74-9bfd-dac224a7b894"
        grant_type = "password"
        username = $targetUser
        password = $password
        scope = "openid"
    } -ErrorAction SilentlyContinue
    Start-Sleep -Seconds 3
}
```

### 2. Evilginx2 Phishlet 抓取之 Session Cookie 特徵
在 AiTM 攔截成功後，攻擊者取得的主要 Session 標記如下：
```http
HTTP/1.1 200 OK
Set-Cookie: ESTSAUTH=0.AXAA...; path=/; domain=login.microsoftonline.com; secure; HttpOnly
Set-Cookie: ESTSAUTHPERSISTENT=0.AXAA...; path=/; domain=login.microsoftonline.com; secure; HttpOnly
```
攻擊者將上述 Cookie 直接貼入一般無痕瀏覽器，即可完全避開密碼與 MFA 驗證，直接存取使用者信箱。

## 第三動：日誌遙測分析與審計設定 (Telemetry Configuration: Entra ID Logs)

在 Microsoft Entra ID (Azure AD) 中，必須啟用詳細的身分保護與登入日誌遙測。

### 關鍵欄位與錯誤代碼
- **`ResultType`**:
  - `500121`: 身分驗證期間發生錯誤（使用者拒絕 MFA 推播或逾時）。
  - `50140`: Keep Me Signed In (KMSI) 中斷。
  - `0`: 登入成功。
- **`AuthenticationDetails`**:
  - 記錄每次認證步驟使用的驗證方式（如 `Mobile app notification`, `Password`）與驗證結果。
- **`RiskEventTypes`**:
  - `anomalousToken`, `unfamiliarFeatures`, `impossibleTravel`。

## 第四動：SIEM 關聯規則與即時獵捕分析 (Splunk & KQL Queries)

### 1. Splunk SPL：偵測高頻 MFA 拒絕後突發成功 (MFA Fatigue Detection)
```spl
index=azure_ad sourcetype="azure:aad:signin"
| eval MFA_Failed=if(ResultType="500121", 1, 0)
| eval MFA_Success=if(ResultType="0" AND match(AuthenticationDetails{}.authenticationMethod, "Mobile app notification"), 1, 0)
| stats sum(MFA_Failed) as DeniedCount, sum(MFA_Success) as SuccessCount, 
        earliest(_time) as FirstAttempt, latest(_time) as LastAttempt, 
        values(IPAddress) as SrcIPs by UserPrincipalName
| where DeniedCount >= 5 AND SuccessCount >= 1
| eval AttackDurationSeconds=LastAttempt - FirstAttempt
| where AttackDurationSeconds <= 900
| convert ctime(FirstAttempt) ctime(LastAttempt)
| table FirstAttempt, LastAttempt, UserPrincipalName, DeniedCount, SuccessCount, SrcIPs
```

### 2. Azure Log Analytics (KQL)：偵測 AiTM 偽冒會話與不可能的旅行 (Impossible Travel)
```kusto
SigninLogs
| where TimeGenerated > ago(24h)
| where RiskLevelDuringSignIn in ("high", "medium") or RiskEventTypes_string has "anomalousToken"
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AppDisplayName, ResourceDisplayName, RiskEventTypes_string
| join kind=inner (
    SigninLogs
    | where TimeGenerated > ago(24h)
    | summarize PreviousIP=make_set(IPAddress), PreviousLocation=make_set(Location) by UserPrincipalName
) on UserPrincipalName
```

### 3. Sigma 偵測規則：Potential MFA Fatigue Attack Pattern
```yaml
title: Potential MFA Fatigue Push Bombing Pattern
id: 4c3114ba-d6b0-4521-a3f1-f09dfd248b11
status: production
description: 偵測同一帳號在短時間內出現多次 MFA 驗證失敗/拒絕後緊接驗證成功的異常行為
logsource:
    product: azure
    service: signinlogs
detection:
    selection_fail:
        ResultType: '500121'
    selection_success:
        ResultType: '0'
    timeframe: 15m
    condition: selection_fail | count() by UserPrincipalName > 5 then selection_success
level: critical
```

## 第五動：身分安全升級與防釣魚 MFA 治理 (Hardening: Phishing-Resistant MFA)

```
[傳統弱 MFA (易受 AiTM/Fatigue 攻擊)]            [抗釣魚強身分驗證 (Phishing-Resistant)]
  ├─ SMS 簡訊驗證碼 (可被攔截/SIM Swap)    ──►    ├─ FIDO2 硬體金鑰 (YubiKey)
  ├─ 單純推播按鈕 (Approve / Deny)                ├─ Windows Hello for Business
  └─ 傳統 6 位 TOTP Authenticator                └─ 憑證式身分驗證 (CBA)
                                                        │
                                                        ▼
                                       (基於 WebAuthn / 公私鑰挑戰與 Origin 綁定)
```

### 1. 強制啟用「數字匹配（Number Matching）」與情境推播
在 Microsoft Authenticator 原則中全域強制套用：
- **Number Matching**：要求使用者在手機上輸入登入螢幕顯示的 2 位隨機數字，徹底終結單純點擊「核准」的盲目操作。
- **Show Application Name**：推播時明確標註是哪個應用程式在發起存取。
- **Show Geographic Location**：明確顯示連線請求發起的地理位置與 IP。

### 2. 升級至「抗釣魚多因素驗證（Phishing-Resistant MFA）」
- **全面導入 FIDO2 / WebAuthn (YubiKey) 或 Windows Hello for Business**：
  - WebAuthn 通訊協定會在用戶端直接比對瀏覽器傳入的 `Origin` 網域名稱。若攻擊者使用 Evilginx2 釣魚網址（如 `login.microsoft.attacker.com`），金鑰硬體將拒絕簽署挑戰，中間人反向代理完全失效。

### 3. 條件式存取原則：阻斷非合規裝置與高風險會話
- 要求存取機密資源（M365, AWS, VPN）必須滿足「裝置已加入混合式 Azure AD (Hybrid Azure AD Join)」或「經 Intune 標記為相符（Compliant）」。即便 Session Cookie 外洩，攻擊者在非公司列管主機上亦無法使用該 Cookie 建立有效連線。

## 靶場實戰：MFA 疲勞轟炸事件應變與處置演練

### 靶場環境情境
- **目標使用者**: `cfo_finance@corp.local` (企業財務長)
- **警報觸發**: SOC 輪值收到 Splunk 告警：凌晨 02:14 至 02:22 期間，該帳號連續產生 14 次 MFA 驗證逾時（500121），隨後於 02:23 出現一次成功登入（ResultType 0），登入來源 IP 來自俄羅斯 VPN 節點。

### 實戰步驟一：確認威脅並即刻阻斷
1. **立即強制登出並撤銷所有 Refresh Token**：
   ```powershell
   Revoke-MgUserSignInSession -UserId "cfo_finance@corp.local"
   ```
2. **重設使用者密碼並暫時停用帳號**，阻斷攻擊者利用已知密碼重複觸發推播。

### 實戰步驟二：鑑識調查受害活動
1. 檢視該帳號在 02:23 之後的 `SignInLogs` 與 `AuditLogs`：
   - 是否曾註冊新的 MFA 裝置（如由攻擊者控制的 Authenticator）？
   - 是否新增了信箱轉寄規則或透過 Graph API 下載機密財務報表？
2. 檢查結果確認攻擊者在 02:25 嘗試建立名為「ForwardAll」的轉寄規則，但被端點防護攔截。

### 實戰步驟三：防禦機制加固
1. 為財務團隊全面啟用 FIDO2 硬體金鑰，停用 SMS 與單純推播驗證。
2. 於條件式存取原則中強制啟用「Require compliant or hybrid Azure AD joined device」。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **攻擊原理理解**：能透徹說明 MFA Fatigue 與 AiTM 反向代理釣魚突破傳統多因素驗證的底層技術途徑。
- [ ] **弱點成因認知**：能清楚解釋為何 FIDO2 / WebAuthn 具備「抗釣魚（Phishing-Resistant）」特性，而 SMS / TOTP / 單純推播無法抵禦 AiTM。
- [ ] **SIEM 關聯分析**：能熟練撰寫 Splunk / KQL 規則，透過狀態代碼（如 500121 與 0）的時間序列比對精準辨識推播轟炸。
- [ ] **事件處置應變**：熟練掌握 `Revoke-MgUserSignInSession` 及身分撤銷手續，能在 5 分鐘內切斷受害會話。
- [ ] **身分治理強化**：能於雲端 IdP 中落實數字匹配（Number Matching）、情境顯示及條件式存取相符裝置檢驗。
