## 🧩 第一動：底層機制解剖——krbtgt 信任基石與 PAC 簽名機制

### 1.1 `krbtgt` 帳號的至高角色
在 Active Directory 樹系建立時，系統會自動生成一個特殊的內建帳號 **`krbtgt` (Key Distribution Center Service Account)**：
- **密鑰本質**：該帳號的密碼金鑰（NTLM Hash 或 AES Key），是全網域所有 Kerberos 票證的「主印信」。
- **職責**：KDC（金鑰發行中心）在核發任何 TGT 給客戶端時，均使用 `krbtgt` 金鑰對 TGT 進行對稱加密與數位簽章。
- **失陷後果**：一旦 `krbtgt` 帳號的密碼雜湊外洩，攻擊者就等同於掌握了網域的「印鈔機」，可以隨意離線偽造任意身分的 TGT 票據！

### 1.2 PAC (Privilege Attribute Certificate) 與簽名結構
微軟在 Kerberos 標準之上引入了 **PAC (特權屬性證書)**，封裝於票據的 `AuthorizationData` 欄位中。PAC 記載了使用者所有的安全識別碼（SIDs），包括所屬群組：
- **Domain Admins**：`S-1-5-21-...-512`
- **Enterprise Admins**：`S-1-5-21-...-519`
- **Schema Admins**：`S-1-5-21-...-518`

為了保證 PAC 不被客戶端惡意篡改，PAC 尾端附帶了兩組關鍵的數位簽章：
1. **Server Signature (服務簽名)**：使用目標服務帳號的密碼金鑰進行簽名。
2. **KDC Signature (KDC 簽名)**：使用 `krbtgt` 帳號的密碼金鑰進行簽名。

```
┌───────────────────────────────────────────────────────────┐
│                 Kerberos 偽造票據物理對決                 │
├─────────────────────────────┬─────────────────────────────┤
│  🪙 黃金票據 (Golden Ticket) │  🥈 白銀票據 (Silver Ticket) │
├─────────────────────────────┼─────────────────────────────┤
│ • 偽造標的：TGT (認證授權票據)│ • 偽造標的：TGS / ST (服務票據)│
│ • 所需密鑰：krbtgt 帳號 Hash │ • 所需密鑰：特定服務帳號 Hash │
│ • 涉及互動：需聯繫 DC 索取 TGS│ • 涉及互動：完全不與 DC 互動！ │
│ • 破壞範圍：全網域所有伺服器 │ • 破壞範圍：僅限該單一目標伺服器│
│ • 核心特徵：有 TGS-REQ 但無  │ • 核心特徵：DC 安全日誌完全空白│
│   前置對應的 AS-REQ (4768)   │   (4768/4769 皆無，僅端點 4624)│
└─────────────────────────────┴─────────────────────────────┘
```

## 💻 第三動：現場追兇——作戰指令與自動化檢驗工具

### 3.1 PowerShell 與 Klist 票據快取實戰

#### 步驟 1：檢驗本機記憶體中快取的 Kerberos 票據屬性
在可疑工作站或跳板機上以管理員身分執行：
```cmd
:: 列出當前記憶體中所有的 Kerberos 票據及其有效期間
klist
```
檢查輸出中的關鍵欄位：
- **`Renew Time` / `End Time`**：正常網域原則預設為 10 小時（或 7 天續訂）。若看到結束時間為 2036 年或未來數年，即為 Mimikatz 鍛造的黃金票據！
- **`Server Name`**：若含有 `krbtgt/CORP.LOCAL` 且過期時間異於常態，即為假 TGT。

#### 步驟 2：使用 Splunk SPL 獵捕「有 TGS 但無 TGT」的時序孤兒日誌
```spl
index=wineventlog EventCode=4769
| eval target_user=lower(TargetUserName)
| join type=left target_user [
    search index=wineventlog EventCode=4768
    | eval target_user=lower(TargetUserName)
    | stats latest(_time) as tgt_time by target_user
]
| eval time_diff = _time - tgt_time
| where isnotnull(time_diff) AND (time_diff > 36000 OR isnull(tgt_time))
| table _time, TargetUserName, ServiceName, ClientAddress, TicketEncryptionType
```

### 3.2 自動化 Kerberos 票據異常 Lifetime 審計工具 (`audit_golden_tickets.py`)

以下 Python 腳本分析導出的 Windows 事件日誌 CSV 報表，自動計算票據有效時長，標記超過常規限制（>10 小時）的惡意偽造票據：

```python
#!/usr/bin/env python3
"""
audit_golden_tickets.py - Automated Detection of Forged Kerberos Tickets
Parses Event ID 4768/4769 logs to identify anomalous ticket lifetimes and missing TGT references.
"""

import sys
import csv
from datetime import datetime
from pathlib import Path

# Standard Domain Kerberos Policy defaults: 10 hours max ticket lifetime
STANDARD_MAX_LIFETIME_SECONDS = 10 * 3600 + 300  # 10 hours + 5 min clock skew

def parse_time(ts_str: str):
    try:
        return datetime.fromisoformat(ts_str.replace("Z", ""))
    except Exception:
        return None

def analyze_ticket_logs(csv_file: Path):
    print(f"[*] Analyzing Kerberos Event CSV: {csv_file.name}")
    suspect_count = 0
    
    with open(csv_file, "r", encoding="utf-8-sig", errors="ignore") as f:
        reader = csv.DictReader(f)
        for row in reader:
            event_id = row.get("EventID", row.get("Id", ""))
            user = row.get("TargetUserName", "")
            service = row.get("ServiceName", "")
            start_time_str = row.get("StartTime", row.get("TicketStartTime", ""))
            end_time_str = row.get("EndTime", row.get("TicketEndTime", ""))
            
            if not start_time_str or not end_time_str:
                continue
                
            start_dt = parse_time(start_time_str)
            end_dt = parse_time(end_time_str)
            
            if not start_dt or not end_dt:
                continue
                
            duration = (end_dt - start_dt).total_seconds()
            duration_hours = duration / 3600.0
            
            # Check for excessive lifetime (> 11 hours)
            if duration > STANDARD_MAX_LIFETIME_SECONDS:
                suspect_count += 1
                print(f"\n🚨 [GOLDEN/SILVER TICKET DETECTED]")
                print(f"    Target User       : {user}")
                print(f"    Service Name      : {service}")
                print(f"    Ticket Start Time : {start_time_str}")
                print(f"    Ticket End Time   : {end_time_str}")
                print(f"    Forged Lifetime   : {duration_hours:.1f} hours ({duration_hours / 24:.1f} days!)")
                print(f"    Verdict           : Highly anomalous (Mimikatz / Rubeus default)")
                
    print("=" * 80)
    print(f"[+] Audit completed. Total anomalous forged tickets identified: {suspect_count}")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python audit_golden_tickets.py <kerberos_events.csv>")
        sys.exit(1)
    analyze_ticket_logs(Path(sys.argv[1]))
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (被偽裝身分)**：票據上的身分是已離職人員、不存在的使用者、還是高危 RID 500 (Administrator)？
2. **What (有效期限)**：票據的 Lifetime 是符合 GPO 預設的 10 小時，還是數百天甚至 10 年？
3. **Where (使用目的地)**：攻擊者拿著該票據存取了哪台核心資產（如 `DC-01`、Exchange 或 SQL）？
4. **When (前置關聯)**：在產生該服務存取事件前，DC 是否存在任何對應的 Event ID 4768 認證事件？
5. **Why (動機分析)**：攻擊者是否已取得 `krbtgt` 雜湊，正企圖建立長期無限制的隱蔽後門？
6. **How (鍛造手法)**：是黃金票據（打擊全網）還是白銀票據（針對特定單一服務）？
7. **Impact (受害深度)**：全網所有網域控制站與成員主機皆處於不設防狀態。
8. **Confidence (研判信心度)**：已停用帳號成功通過 Kerberos 驗證 + 壽命超限，研判信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：黃金票據的唯一死穴——`krbtgt` 雙重輪換 SOP
黃金票據是使用 `krbtgt` 的密碼雜湊簽發的。**只要 `krbtgt` 密碼不改，已偽造的假票據在 10 年內永遠有效**！但微軟為了保證正在通訊中的合法票據不中斷，維護了兩代密碼歷史（當前密碼與上一代密碼）。
因此，必須嚴格執行 **「雙重輪換 (Double Reset)」**：

```powershell
# 官方推薦使用微軟官方腳本: New-KrbtgtKeys.ps1
# 第一次重設 krbtgt 密碼 (舊票據依然可用，新票據使用新金鑰)
.\New-KrbtgtKeys.ps1 -Mode Reset

# ⚠️ 等待 10 ~ 24 小時 (確保全網域所有 DC 完整完成目錄複製，且現有合法的 10 小時票據自然過期)
Start-Sleep -Seconds 86400

# 第二次重設 krbtgt 密碼 (徹底將攻擊者手中的舊金鑰踢出歷史記錄，所有舊黃金票據瞬間暴斃無效！)
.\New-KrbtgtKeys.ps1 -Mode Reset
```

### 2. 第二步：全面強制清除所有端點的票據快取
在全網域下發批次指令，清除受害主機記憶體中的假票據：
```cmd
:: 清空本機記憶體中所有 Kerberos 快取票證
klist purge
```

### 3. 第三步：架構加固——開啟嚴格 PAC 簽名驗證 (CVE-2022-37967 / KB5020805)
- **部署微軟強制 PAC 驗證更新**：在所有網域控制站上安裝安全更新，強制啟用全域 PAC 簽名驗證（Enforcement Phase）。
- **加固效果**：當成員伺服器接收到服務票據時，會主動向 KDC 查詢該 PAC 簽名的真實性，徹底阻斷白銀票據繞過 DC 的盲區！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：為什麼攻擊者一旦取得 `krbtgt` 帳號的密碼雜湊，就能偽造出「全網域通行無阻且永不過期」的黃金票據（Golden Ticket）？其背後的密碼學原理為何？**
  > **標準答案**：
  > 1. **對稱密鑰共享基石**：在 Kerberos 架構中，KDC（網域控制站）簽發 TGT 票據時，是使用 `krbtgt` 帳號的密碼雜湊作為對稱金鑰進行加密與數位簽名。
  > 2. **完全離線自主簽發**：既然金鑰在攻擊者手中，攻擊者便不再需要聯繫真實的 KDC。他可以在自己的離線電腦上，自行構建一個包含任意使用者名稱、任意高權限 SID（如 Domain Admins 512）的假 TGT，並用竊得的 `krbtgt` 金鑰完成完美的密碼學加密與簽名。
  > 3. **無條件信任**：當攻擊者拿著這張自製的假 TGT 向網域控制站請求存取任何服務時，DC 使用自己庫存的 `krbtgt` 金鑰驗證簽名，發現密碼學驗證完全通過，便會誤以為這是自己當初合法簽發的票據，從而無條件頒發存取權限。

- [x] **Q2：黃金票據（Golden Ticket）與白銀票據（Silver Ticket）在「偽造標的」、「所需密鑰」與「網路流量與日誌特徵」上有何根本區別？**
  > **標準答案**：
  > 1. **偽造標的與金鑰不同**：
     - 黃金票據偽造的是 **TGT (認證授權票據)**，需要全網域唯一的 **`krbtgt` 帳號金鑰**。
     - 白銀票據偽造的是特定服務的 **TGS / ST (服務票據)**，只需該**特定目標伺服器或服務帳號的密碼金鑰**（如 `sql_svc` 或主機的電腦帳號金鑰）。
  > 2. **與網域控制站（DC）的互動差異**：
     - 黃金票據在使用時，客戶端**必須連線至 DC**，向 DC 發送 TGS-REQ 索取目標服務票據。
     - 白銀票據在使用時，**完全不與 DC 發生任何通訊**！攻擊者拿著偽造的服務票據，直接直連目標伺服器（如直連檔案伺服器的 445 埠）。
  > 3. **日誌特徵差異**：
     - 黃金票據會在 DC 留下 Event ID 4769，但其**缺少前置的 Event ID 4768 (TGT 請求)**。
     - 白銀票據在 DC 端**完全不會產生任何日誌（0 記錄）**，唯一的痕跡僅留在目標伺服器本身的 Event ID 4624 登入日誌中。

- [x] **Q3：在處置黃金票據失陷事件時，為什麼必須對 `krbtgt` 帳號進行「連續兩次密碼重設 (Double Reset)」，且兩次之間必須間隔一段時間？直接改一次不行嗎？**
  > **標準答案**：
  > 1. **微軟雙重密碼歷史機制**：為了避免在日常維護修改 `krbtgt` 密碼的瞬間，導致全公司成千上萬名正在辦公的合法使用者手上的票據集體暴斃中斷，Active Directory 設計上**同時維護兩代 `krbtgt` 密碼**（當前密碼與前一次歷史密碼）。
  > 2. **只改一次的致命漏洞**：如果只改一次密碼，被攻擊者竊取的舊金鑰會被移入「上一代歷史密碼」中，攻擊者手上的黃金票據**依然完全合法有效**！
  > 3. **必須改兩次的原理**：只有執行第二次重設，原本外洩的舊金鑰才會被徹底擠出歷史儲存區，使攻擊者的假票據徹底失效。
  > 4. **間隔時間的必要性**：兩次重設之間必須間隔一段時間（通常為 10 到 24 小時），一是確保全網所有跨地域的網域控制站完成目錄複製同步，二是讓企業內部正常合法使用者的 10 小時舊票據自然到期換新，避免業務大面積癱瘓。

- [x] **Q4：在 Windows 安全日誌中，如何透過 Event ID 4769 的欄位特徵識破 Mimikatz 預設偽造的黃金票據？**
  > **標準答案**：
  > 1. **票據存活時間異常 (Lifetime Anomaly)**：Windows 網域群組原則預設規定的 Kerberos 票據最大壽命為 **10 小時**（36,000 秒）；而 Mimikatz 在下達 `kerberos::golden` 時，其內建預設的票據有效期限長達 **10 年**！比對 `StartTime` 與 `EndTime`，凡是超長壽命的票據 100% 為偽造。
  > 2. **時序斷鏈特徵**：正常使用者登入，必定是先向 DC 索取 TGT（產生 Event ID 4768），隨後在數小時內拿著 TGT 索取各種服務（產生 Event ID 4769）。黃金票據因為 TGT 是在離線端點自製的，因此在 DC 日誌中會出現「**憑空冒出 Event ID 4769，且往前檢索數天均查無該帳號的 Event ID 4768**」的致命悖論。

- [x] **Q5：微軟近年針對 Active Directory 推出的 Kerberos PAC 簽名強化更新（如 CVE-2022-37967 / KB5020805），在底層是如何從架構上封殺白銀票據（Silver Ticket）的？**
  > **標準答案**：
  > 1. **傳統白銀票據的漏洞根源**：在過去，目標伺服器收到客戶端發來的服務票據時，只會用自己的密碼解密外層並驗證服務簽名，**根本不會去聯繫 DC 確認這張票據到底是不是 DC 發的**，給予白銀票據可乘之機。
  > 2. **PAC 擴展屬性與完整性校驗**：新版安全更新在 PAC 中強制引入了新的票證簽章演算法與票證元資料（包含更嚴格的 KDC 全域簽名）。
  > 3. **強制回呼驗證機制**：在全面強制執行階段（Enforcement Phase），目標伺服器如果收到未具備有效 KDC 完整性簽名的服務票據，或者發現 PAC 缺少必要的目錄屬性，會直接拒絕該連線；或主動向 DC 發起 RPC 驗證回呼（PAC Validation），徹底消除了白銀票據繞過 DC 盲區的生存空間。
