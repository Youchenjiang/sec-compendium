## 🧩 第一動：底層機制解剖——Kerberos 認證體系與預驗證本質

### 1.1 Kerberos 基礎認證流程 (AS-REQ / AS-REP)
Kerberos 是 Active Directory 的核心驗證協定（基於 RFC 4120）。當客戶端向金鑰發行中心（KDC，即網域控制站）請求訪問網域資源時，第一步是取得 **TGT (Ticket Granting Ticket，票據授權票據)**：
1. **AS-REQ (Authentication Service Request)**：客戶端發送請求至 KDC 的 Kerberos 服務（通訊埠 88）。
2. **AS-REP (Authentication Service Response)**：KDC 驗證身分後，回傳兩部分資料：
   - 第一部分：**TGT 票據**（使用只有 KDC 知道的 `krbtgt` 帳號密碼 NTLM/AES 金鑰加密）。
   - 第二部分：**登入會話金鑰與元資料 (Encrypted Session Key)**（**使用請求者自己的密碼雜湊值進行對稱加密**！）。

### 1.2 預驗證機制 (Pre-Authentication, PA-DATA) 的安全守護
在標準的 Kerberos 流程中，為了防止攻擊者隨意嗅探加密回覆進行離線破解，微軟強制推行了 **Kerberos 預驗證機制 (Pre-Authentication)**：
- 客戶端在發送 AS-REQ 時，必須在 `padata` (Pre-Authentication Data) 欄位中附帶一組 **`PA-ENC-TIMESTAMP` (預驗證時間戳)**。
- 此時間戳是由客戶端**使用自己帳號的密碼雜湊值（NTLM/AES Key）加密當前的 UTC 時間**而得。
- KDC 收到後，先用資料庫中該使用者的密碼金鑰嘗試解密時間戳：
  - 若解密成功且時間誤差在 5 分鐘以內（防止重放攻擊），KDC 才會簽發 AS-REP。
  - 若解密失敗，KDC 直接回傳 `KDC_ERR_PREAUTH_FAILED`，根本不會發送後續加密數據！

### 1.3 弱點成因：`DONT_REQ_PREAUTH` (UserAccountControl 0x400000)
在某些大型企業中，維運人員為了相容舊版 Unix/Linux 系統、老舊應用程式、或特定的多重身分驗證（MFA）整合解決方案，會在 Active Directory 中針對特定帳號勾選 **「不要求 Kerberos 預先驗證」**：
- 在 LDAP 目錄屬性中，該帳號的 `userAccountControl` (UAC) 旗標會被加上 **`0x400000` (`DONT_REQ_PREAUTH`)**。
- **致命後果**：任何人只要知道這個帳號的名稱（可透過 RID Cycling 或 LDAP 匿名列舉獲得），就能向 KDC 發送一個無預認證的 AS-REQ，KDC 會毫無防備地奉上包含該帳號密碼加密數據的 AS-REP 封包！

## 💻 第三動：現場追兇——作戰指令與自動化檢驗工具

### 3.1 PowerShell 與 CLI 實戰指令庫

#### 步驟 1：使用 PowerShell 稽核網域中所有未啟用預驗證的帳號
在網域管理機或任何加域工作站上執行（無需特權，一般網域使用者即可列舉）：
```powershell
# 使用 ActiveDirectory 模組搜尋開啟 DONT_REQ_PREAUTH 的所有使用者帳號
Get-ADUser -Filter {DoesNotRequirePreAuth -eq $True} -Properties DoesNotRequirePreAuth, Description, PasswordLastSet, MemberOf | 
    Select-Object SamAccountName, DoesNotRequirePreAuth, PasswordLastSet, Description
```

#### 步驟 2：使用 ADSI 原生 LDAP 查詢（免安裝 AD 模組）
```powershell
# 利用 UserAccountControl 位元運算 (4194304 = 0x400000 DONT_REQ_PREAUTH)
$Searcher = [ADSISearcher]"(userAccountControl:1.2.840.113556.1.4.803:=4194304)"
$Searcher.FindAll() | ForEach-Object {
    [PSCustomObject]@{
        SamAccountName = $_.Properties["samaccountname"][0]
        DistinguishedName = $_.Properties["distinguishedname"][0]
    }
}
```

#### 步驟 3：監控網域控制站 Event ID 4768 安全日誌
```powershell
# 檢索預驗證類型為 0 (PreAuthType = 0) 的可疑 TGT 索取事件
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    Id = 4768
} | Where-Object {
    $_.Message -match "預先驗證類型:.*0" -or $_.Message -match "Pre-Authentication Type:.*0"
} | Select-Object TimeCreated, Message -First 10
```

### 3.2 自動化 AS-REP Roasting 稽核與 Hashcat 格式生成器 (`asreproast_auditor.py`)

以下 Python 腳本使用純 LDAP 協定查詢網域內所有具有弱配置的帳號，評估其最後密碼修改時間，並提供對應的加固建議：

```python
#!/usr/bin/env python3
"""
asreproast_auditor.py - Active Directory AS-REP Roasting Vulnerability Scanner
Scans Active Directory LDAP for accounts configured with DONT_REQ_PREAUTH.
"""

import sys
import argparse
from ldap3 import Server, Connection, ALL, NTLM

# UserAccountControl bit flag: DONT_REQ_PREAUTH = 0x400000 (4194304)
UAC_DONT_REQ_PREAUTH = 4194304

def scan_asrep_roastable_users(dc_ip: str, domain: str, user: str, password: str):
    print(f"[*] Connecting to Domain Controller: {dc_ip} ({domain})")
    server = Server(dc_ip, get_info=ALL)
    conn = Connection(server, user=f"{domain}\\{user}", password=password, authentication=NTLM, auto_bind=True)
    
    # LDAP filter matching bit 22 of UserAccountControl
    ldap_filter = f"(&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:={UAC_DONT_REQ_PREAUTH}))"
    
    # Convert domain to base DN (e.g. corp.local -> DC=corp,DC=local)
    base_dn = ",".join([f"DC={part}" for part in domain.split(".")])
    
    print(f"[*] Querying LDAP Base DN: {base_dn}")
    conn.search(base_dn, ldap_filter, attributes=["samAccountName", "userAccountControl", "description", "pwdLastSet"])
    
    vulnerable_accounts = conn.entries
    print("=" * 80)
    print(f"{'Vulnerable Account':<25} | {'Description':<35} | {'Status'}")
    print("-" * 80)
    
    if not vulnerable_accounts:
        print("[+] Excellent! Zero accounts configured with DONT_REQ_PREAUTH found.")
    else:
        for entry in vulnerable_accounts:
            sam_name = str(entry.samAccountName)
            desc = str(entry.description) if "description" in entry else "None"
            desc = (desc[:32] + "..") if len(desc) > 32 else desc
            print(f"🚨 {sam_name:<23} | {desc:<35} | Vulnerable to AS-REP Roasting")
            
    print("=" * 80)
    print(f"[+] Total vulnerable accounts: {len(vulnerable_accounts)}")
    conn.unbind()

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="Audit AD accounts vulnerable to AS-REP Roasting.")
    parser.add_argument("--dc", required=True, help="IP or FQDN of Domain Controller")
    parser.add_argument("--domain", required=True, help="Domain NetBIOS or FQDN (e.g. CORP.LOCAL)")
    parser.add_argument("-u", "--user", required=True, help="Domain username")
    parser.add_argument("-p", "--password", required=True, help="Domain password")
    
    args = parser.parse_args()
    scan_asrep_roastable_users(args.dc, args.domain, args.user, args.password)
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (被請求帳號)**：被索取 TGT 的帳號為何？該帳號是否擁有網域特權（如 Domain Admins 或本地管理員群組）？
2. **What (請求參數)**：Event ID 4768 中的「預先驗證類型」是否為 `0`？加密類型是否降級為 `0x17` (RC4)？
3. **Where (來源 IP)**：發起請求的來源 IP 位於哪一個網段？是否來自未安裝 EDR 的訪客 WiFi 或非受管設備？
4. **When (觸發頻率)**：該來源是否在數分鐘內密集索取了多個不同服務帳號的 TGT？
5. **Why (業務背景)**：該帳號為何被配置為不需要預認證？內部系統架構是否有任何技術文件佐證？
6. **How (後續行為)**：在 TGT 簽發後，該客戶端是否有進一步發起 Event ID 4769 (TGS 請求)？（**若無後續請求，99% 為純粹擷取 Hash 離線破解**！）
7. **Impact (損害估計)**：該帳號的密碼強度如何？是否為弱密碼或曾遭外洩密碼？
8. **Confidence (研判信心度)**：Event ID 4768 PreAuthType=0 且無後續 TGS 請求，研判信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：強制取消危險弱配置 (取消勾選)
- **取消 `DONT_REQ_PREAUTH`**：
  ```powershell
  # 透過 PowerShell 將目標帳號的 DoesNotRequirePreAuth 重設為 False
  Set-ADAccountControl -Identity "svc_backup" -DoesNotRequirePreAuth $False
  ```
- **加固效果**：一旦重新啟用預驗證，KDC 便會嚴格要求客戶端在 AS-REQ 中提供正確密碼加密的時間戳，攻擊者將再也無法免密碼索取加密憑據。

### 2. 第二步：受害帳號立即強制更換密碼
- **長度與複雜度提升**：若該帳號曾被攻擊者索取過 AS-REP，其密碼雜湊很可能已在離線 GPU 叢集中被破解。必須立即重設為 **25 字元以上** 的高隨機密碼（有效抵禦 Hashcat 離線字典與暴力破解）。

### 3. 第三步：推動 Group Managed Service Accounts (gMSA)
- **淘汰傳統服務帳號**：將所有的定時排程、備份服務、資料庫連接帳號，遷移至 **群組受管理服務帳戶 (gMSA)**。
- **物理免疫**：gMSA 的密碼是由網域控制站自動生成之 120 字元隨機字串，每 30 天自動輪換，且完全無法被手動登入或關閉預驗證，在架構層面徹底終結 AS-REP Roasting！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：何謂 Kerberos 預驗證（Pre-Authentication）？為什麼微軟要將其設計為預設啟用的安全防線？**
  > **標準答案**：
  > 1. **預驗證的本質**：預驗證是 Kerberos 認證的第一道安全閘門。客戶端在向 KDC 索取 TGT 之前，必須先在請求封包中附帶一段「用自己密碼金鑰加密當前時間戳」的數據（`PA-ENC-TIMESTAMP`）。
  > 2. **設計動機與防護目的**：如果沒有預驗證，任何網路上的使用者只要知道一個帳號名稱，就可以隨意向 KDC 索取該帳號的 AS-REP 認證回覆。由於 AS-REP 回覆中包含使用該帳號密碼加密的數據，攻擊者便可將該封包攔截並帶到離線環境中進行無限制的暴力破解。因此，預驗證的本質就是「先證明你知道密碼，KDC 才會把加密票據發給你」，徹底阻斷離線嗅探。

- [x] **Q2：為什麼 AS-REP Roasting 攻擊在執行時，不會觸發 Active Directory 的「帳號鎖定原則 (Account Lockout Threshold)」？**
  > **標準答案**：
  > 1. **破解戰場轉移至離線**：在 AS-REP Roasting 中，攻擊者向網域控制站發送的是一個合法合規的、沒有附帶預認證的 AS-REQ 請求。
  > 2. **KDC 端的判定邏輯**：因為該帳號在 AD 中被明確標記為 `DONT_REQ_PREAUTH`（豁免預驗證），所以 KDC 認為這是一個「完全成功的合法請求」，直接回傳 AS-REP，在 DC 端完全**沒有發生任何一次登入失敗**！
  > 3. **無鎖定機制**：攻擊者隨後在自己的個人電腦或雲端 GPU 上執行數億次的密碼嘗試，這些計算完全發生在攻擊者的本地機器上，網域控制站根本無從知曉，因此帳號永不鎖定。

- [x] **Q3：在 Windows 安全事件日誌中，Event ID 4768 與 Event ID 4769 分別代表什麼含義？如何單憑這兩筆日誌判定攻擊者正在實施 AS-REP Roasting？**
  > **標準答案**：
  > 1. **Event ID 4768**：代表客戶端向 KDC 索取了 **TGT (Ticket Granting Ticket，認證授權票據)**。
  > 2. **Event ID 4769**：代表客戶端拿著 TGT，向 KDC 索取訪問特定伺服器服務的 **ST / TGS (Service Ticket，服務票據)**。
  > 3. **判定 AS-REP Roasting 的組合拳特徵**：
     - 特徵 1：Event ID 4768 中的「預先驗證類型」為 `0`（或 `0x0`，未驗證）。
     - 特徵 2（致命異常）：在 Event ID 4768 成功產生後，**系統完全沒有緊接著記錄到任何該帳號發起的 Event ID 4769（TGS 請求）**！正常使用者索取 TGT 是為了存取檔案共用、郵件等服務；如果索取完 TGT 就立刻悄無聲息，證明攻擊者僅是為了擷取加密封包進行離線爆破。

- [x] **Q4：在 AS-REP Roasting 攻擊中，為什麼攻擊者會偏好請求 RC4-HMAC (Encryption Type 0x17) 而非 AES-256 (0x12)？在防禦端該如何封殺此特徵？**
  > **標準答案**：
  > 1. **GPU 離線運算難度差異**：RC4-HMAC 演算法的底層僅使用 MD4 雜湊運算，在現代高階 GPU 叢集（如 RTX 4090）上的暴力破解速度可達每秒數十億次；而 AES-256 結合了 PBKDF2 與 4096 次迭代，計算成本極高，破解速度比 RC4 慢上數百倍甚至上千倍。
  > 2. **攻擊者手段**：攻擊者在發送 AS-REQ 時，會在支援加密清單中刻意只聲明支援 RC4，迫使 KDC 降級加密。
  > 3. **防禦封殺方案**：在網域群組原則（GPO）中配置：`電腦設定` ➔ `Windows 設定` ➔ `安全性設定` ➔ `本機原則` ➔ `安全性選項` ➔ `網路安全性: 設定 Kerberos 允許的加密類型`，**徹底勾除 RC4_HMAC_MD5**，僅允許 AES128_HMAC_SHA1 與 AES256_HMAC_SHA1，全面阻斷加密降級！

- [x] **Q5：既然 AS-REP Roasting 危害如此嚴重，為何許多歷史悠久的大型企業中依然存在勾選 `DONT_REQ_PREAUTH` 的帳號？資安團隊該如何安全無損地推動改善？**
  > **標準答案**：
  > 1. **歷史技術債成因**：早期舊版非 Windows 系統（如十幾年前的某些 Solaris/AIX 系統、早期嵌入式印表機、或某些老舊的 Java 應用程式認證庫）在實作 Kerberos 客戶端時，未正確支援 RFC 4120 的預驗證協定擴展，維運人員為求「系統能通」，便妥協勾選了豁免。
  > 2. **安全無損推動步驟**：
     - **第一階段（盤點與日誌審查）**：使用 PowerShell 列出全域所有受影響帳號，透過 SIEM 監視過去 90 天內是哪些 IP 在發起 PreAuthType=0 的請求，確認背後的真實業務系統。
     - **第二階段（架構升級）**：協同應用維護團隊，將老舊客戶端升級為支援 Kerberos AES/Pre-Auth 的現代版本；或者將傳統帳號改為 gMSA。
     - **第三階段（分批關閉與強密碼保護）**：對於暫時無法改寫的業務，先將該帳號密碼改為 30 碼以上不可破密碼，隨後在非高峰期正式取消勾選並驗證業務可用性。
