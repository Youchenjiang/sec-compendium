## 🚨 案發現場破題 (The Incident Scenario)

> **情境帶入**：  
> 週二下午 14:40，某跨國銀行 SOC 的 SIEM 關聯規則突然觸發了一筆嚴重的高風險身分警報：  
> Active Directory 網域控制站 `DC-HQ-01` 上的安全事件日誌在短短 **15 秒內爆發了 48 筆 Event ID 4769 (已要求 Kerberos 服務票證)**！  
> 
> 分析師火速調出原始日誌進行維度鑽取：  
> - 請求的來源帳號為研發部一位普通約聘人員的帳號 `contractor_john`。  
> - 請求的目標服務名稱（ServiceName）清一色為掛載在網域使用者帳號下的高權限服務：`MSSQLSvc/sql-prod.corp.local:1433`、`HTTP/sharepoint.corp.local`、`TERMSRV/backup-srv`。  
> - 最關鍵的物理破綻在於：該客戶端在索取服務票據時，**「票證加密類型 (Ticket Encryption Type)」** 竟然全部為 **`0x17` (RC4-HMAC)**，而該企業的伺服器早已全線強制部署 AES-256！  
> - 隨後，該端點根本沒有向目標 MSSQL 伺服器的 1433 連接埠發起任何 TCP 三向交握！  
> 
> 這不是正常的業務連線，這是全網域橫向移動中最經典的絕殺技——**Kerberoasting (服務票據離線雜湊提取與破解)**！  
> 任何只要擁有基本「網域使用者（Domain Users）」身分的合法帳號，都可以合法向網域控制站索取任何註冊了 **SPN (Service Principal Name)** 的服務票據（TGS）。而微軟 Kerberos 協定為了讓目標伺服機能夠解密該票據，此 TGS 票據的內容是**直接使用該「服務帳號自身的密碼雜湊值（NTLM Hash）」進行加密**！  
> 攻擊者將記憶體中的 TGS 匯出成檔案帶走，在離線環境使用 Hashcat 進行每秒數億次的字典比對，一旦服務帳號密碼過於簡單，攻擊者便能在不觸碰目標伺服器的情況下，直接斬獲該服務的明文密碼，進而接管核心資料庫與伺服器！  
> 
> **本手冊的使命**：深入剖析 Kerberos TGS-REQ / TGS-REP 封包結構與 SPN 註冊物理機制，掌握 Event ID 4769 的 4 大異常識別指紋（RC4 降級、批量掃描、高頻低耗、無後續連線），提供 PowerShell、Rubeus 偵測語法與 Splunk SPL 規則，並建立全網域 gMSA 遷移加固 SOP。

## 🧩 第一動：底層機制解剖——SPN 服務主體名稱與 TGS 加密本質

### 1.1 何謂 SPN (Service Principal Name)？
在 Active Directory 樹系中，當某個伺服器（例如 Microsoft SQL Server 或 IIS）需要以 Kerberos 協定提供雙向身分驗證時，必須在 Active Directory 中註冊一個唯一標識符，此標識符稱為 **SPN (服務主體名稱)**。

#### SPN 標準格式語法：
```text
ServiceClass / Hostname [:Port] [/ArbitraryPath]
例如：
MSSQLSvc/sql-prod.corp.local:1433
HTTP/intranet.corp.local
```
- **帳號對象的巨大差異**：
  - **電腦帳號 (Computer Account, 如 `SQL-SRV$`)**：密碼由 Windows 自動生成，長達 120 位元隨機字串，每 30 天自動輪換。即便被抓出 TGS，Hashcat 也絕對無法在有生之年破解。
  - **使用者帳號 (User Account, 如 `svc_sql`)**：由網管人員手動建立，通常為了維護方便，往往設定了永久不變的弱密碼或字典常見密碼！**這就是 Kerberoasting 的核心打擊標的**！

### 1.2 Kerberos TGS-REQ / TGS-REP 協定交互機制
1. 客戶端已持有合法的 TGT，想要連線到 SQL 資料庫。
2. 客戶端向 KDC（DC 通訊埠 88）發送 **`TGS-REQ`**，指明要訪問目標 SPN（`MSSQLSvc/sql-prod.corp.local:1433`）。
3. KDC 在目錄資料庫中查找該 SPN 究竟綁定在哪一個帳號名下。
4. KDC 生成 **`TGS-REP`** 回傳給客戶端：
   - 票據內部包含了客戶端身分、權限 PAC (Privilege Attribute Certificate)。
   - **關鍵致命物理機制**：KDC 使用**該服務帳號自身的密碼金鑰（NTLM Hash 或 AES Key）**對該票據實施對稱加密！

```
┌───────────────────────────────────────────────────────────┐
│     Kerberoasting 攻擊物理機制 (TGS-REQ / TGS-REP)        │
├───────────────────────────────────────────────────────────┤
│ Attacker (僅需一般使用者權限)       Domain Controller (KDC) │
│   │                                  │                    │
│   │ 1. TGS-REQ (索取目標服務之 SPN 票據)│                    │
│   │─────────────────────────────────>│                    │
│   │                                  │ 2. 查得 SPN 綁定在  │
│   │                                  │    svc_sql 帳號名下 │
│   │ 3. TGS-REP (回傳用 svc_sql 密碼  │                    │
│   │    雜湊值加密的服務票據 ST)       │                    │
│   │<─────────────────────────────────│ (完全合法的 AD 流量)│
│   │                                  │                    │
│   ▼                                                       │
│ [Attacker 萃取票據 $krb5tgs$23$ 格式，移至 GPU 離線暴力破解] │
└───────────────────────────────────────────────────────────┘
```

## 🧭 第二動：解碼意圖——Kerberoasting 鑑識異常特徵速查表

| 事件與協定特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **Event 4769 且 TicketEncryption 為 `0x17` (RC4)** | **密碼編譯降級 (Kerberoasting Encryption Downgrade)**：<br>客戶端刻意聲明僅支援 RC4，誘使 DC 使用最脆弱的 MD4 Hash 加密。 | • **影響**：大幅縮短離線破解時間（數小時內出密碼）。<br>• **處置優先級**：高（封殺 RC4 並排查索取帳號）。 |
| **單一來源 IP 在數分鐘內請求數十個不同 SPN** | **全網域批量 Roasting 探測 (Mass Kerberoasting)**：<br>攻擊者使用 `Rubeus kerberoast` 或 Invoke-Kerberoast 批量導出。 | • **影響**：全內網所有服務帳號同時面臨失陷威脅。<br>• **處置優先級**：緊急（立即在防火牆隔離該來源端點）。 |
| **請求之 SPN 歸屬於非電腦帳號 (`ServicePrincipalName`)** | **針對性服務帳號攻擊 (Targeted User SPN Access)**：<br>攻擊者專門過濾掉不可能破解的電腦帳號，直撲人工維護帳號。 | • **影響**：精確打擊高權限業務服務帳號。<br>• **處置優先級**：高（盤點帳號權限並強制輪換）。 |
| **索取 TGS 票據後，無任何針對目標伺服器的網路流量** | **純擷取無後續連線異常 (No Subsequent Service Traffic)**：<br>正常存取必然伴隨 SMB/RPC/MSSQL 連線；只拿票不連線即為竊密。 | • **影響**：100% 證明為離線攻擊行為。<br>• **處置優先級**：緊急（終結使用者 Session 並隔離主機）。 |

## 💻 第三動：現場追兇——作戰指令與自動化檢驗工具

### 3.1 PowerShell 與 SIEM SPL 實戰指令庫

#### 步驟 1：使用 PowerShell 盤點網域中所有「註冊在使用者名下」的危險 SPN
```powershell
# 僅搜尋 objectClass=user 且排除電腦帳號 (sAMAccountType=805306368)
Get-ADUser -Filter {ServicePrincipalName -like "*"} -Properties ServicePrincipalName, PasswordLastSet, MemberOf | 
    Where-Object {$_.DistinguishedName -notmatch "OU=Domain Controllers|CN=Computers"} |
    Select-Object SamAccountName, ServicePrincipalName, PasswordLastSet
```

#### 步驟 2：使用 Splunk SPL 監控高頻 Event ID 4769 與 RC4 降級
```spl
index=wineventlog EventCode=4769 Ticket_Encryption_Type=0x17 Service_Name!="*$"
| bin _time span=1m
| stats count dc(Service_Name) as unique_spns values(Service_Name) as targets by src_ip, TargetUserName, _time
| where unique_spns > 3
| sort - unique_spns
```

### 3.2 自動化 SPN 脆弱度評估工具 (`audit_spn_accounts.py`)

以下 Python 腳本連接 AD LDAP，列出所有非電腦帳號的 SPN，分析其加密支援旗標（msDS-SupportedEncryptionTypes），並標記高危弱點：

```python
#!/usr/bin/env python3
"""
audit_spn_accounts.py - Audits Kerberoastable User Accounts in Active Directory
Identifies SPNs mapped to user accounts and analyzes encryption type baselines.
"""

import sys
import argparse
from ldap3 import Server, Connection, ALL, NTLM

def audit_spns(dc_ip: str, domain: str, username: str, password: str):
    print(f"[*] Connecting to Domain Controller: {dc_ip}...")
    server = Server(dc_ip, get_info=ALL)
    conn = Connection(server, user=f"{domain}\\{username}", password=password, authentication=NTLM, auto_bind=True)
    
    base_dn = ",".join([f"DC={p}" for p in domain.split(".")])
    # Filter for users with SPNs, excluding computer objects
    ldap_filter = "(&(objectCategory=person)(objectClass=user)(servicePrincipalName=*)(!(userAccountControl:1.2.840.113556.1.4.803:=8192)))"
    
    conn.search(base_dn, ldap_filter, attributes=["samAccountName", "servicePrincipalName", "msDS-SupportedEncryptionTypes", "pwdLastSet"])
    
    print("=" * 85)
    print(f"{'User Account':<20} | {'Registered SPN':<40} | {'Encryption Policy'}")
    print("-" * 85)
    
    count = 0
    for entry in conn.entries:
        count += 1
        sam = str(entry.samAccountName)
        spns = entry.servicePrincipalName.values
        primary_spn = spns[0] if spns else "None"
        primary_spn = (primary_spn[:37] + "..") if len(primary_spn) > 37 else primary_spn
        
        # msDS-SupportedEncryptionTypes: 0x18 includes AES128/AES256, 0 or empty often falls back to RC4
        enc_types = entry["msDS-SupportedEncryptionTypes"].value or 0
        enc_status = "✅ AES Supported" if (enc_types & 0x18) else "⚠️ RC4 Fallback Risk"
        
        print(f"🚨 {sam:<18} | {primary_spn:<40} | {enc_status}")
        
    print("=" * 85)
    print(f"[+] Total Kerberoastable User Accounts Identified: {count}")
    conn.unbind()

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="Audit AD accounts vulnerable to Kerberoasting.")
    parser.add_argument("--dc", required=True, help="IP or FQDN of Domain Controller")
    parser.add_argument("--domain", required=True, help="Domain FQDN (e.g. CORP.LOCAL)")
    parser.add_argument("-u", "--user", required=True, help="Domain username")
    parser.add_argument("-p", "--password", required=True, help="Domain password")
    
    args = parser.parse_args()
    audit_spns(args.dc, args.domain, args.user, args.password)
```

## ⚖️ 第四動：研判分水嶺——正常集中化排程存取 vs 惡意批量 Roasting

### 4.1 核心研判決策流程
```
[DC 記錄到密集爆發之 Event ID 4769 服務票證請求]
                       │
                       ▼
          [發起帳號是否為中央整合服務?]
        (如 SCCM / Backup Exec / 漏洞掃描器)
             /                   \\
          (是)                   (否)
          /                         \\
[核對預排維運時間與清單]         [檢查 Ticket_Encryption_Type 是否為 0x17?]
(是否在每週備份窗口發起)                 /                    \\
      /            \\                  (是)                  (否)
   (吻合)        (不符)                 │                     │
    │               │                   ▼                     ▼
    ▼               ▼           🚨 確鑿 Kerberoasting 攻擊    [檢查 AES 降級異常]
[正常維運排除]  [權限過大改善]     (立即隔離來源並鎖定 Session)
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (索取者身分)**：發起請求的使用者帳號是普通職員、約聘人員、還是未受監控的訪客帳號？
2. **What (加密演算法)**：`TicketEncryptionType` 欄位是否呈現 `0x17` (RC4-HMAC)？
3. **Where (來源 IP)**：連線發起自主機網段、VPN 遠端撥入、還是未受信任的終端？
4. **When (速度與頻率)**：是否在數秒至數分鐘內連續索取多個跨業務領域的 SPN？
5. **Why (業務存取正當性)**：該使用者職責是否需要同時存取 HR 伺服器、ERP 資料庫與備份主機？
6. **How (後續連線驗證)**：在向 DC 索取 TGS 票據後，網路核心交換機與主機防火牆是否有記錄到該來源連線至目標伺服器的業務通訊埠？（**無後續連線 = 100% 離線竊密**）
7. **Impact (目標服務特權)**：遭請求的 SPN 帳號是否隸屬於 Domain Admins、Enterprise Admins 或本機管理員？
8. **Confidence (研判信心度)**：Event ID 4769 RC4 降級 + 批量請求 + 無後續流量，信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：緊急受害帳號密碼輪換
- **更換遭請求帳號密碼**：將遭到 Roasting 的服務帳號密碼，立即更換為 **30 字元以上之高複雜度隨機密碼**。
- **長度抵禦計算**：Kerberos 票據破解仰賴字典比對。只要長度超過 25 字元且包含隨機符號，GPU 的爆破計算在現今數學與物理限制下將完全無法在有效時間內解密。

### 2. 第二步：全面推行 gMSA (群組受管理服務帳戶)
- **淘汰人工使用者 SPN**：將原本註冊在一般使用者名下的 SPN，全數遷移至 **Group Managed Service Accounts (gMSA)**。
- **不可破解機制**：gMSA 的密碼由 KDC 自動指派 120 碼隨機字元，定期自動輪換，且該帳號不允許互動式登入，從根本上讓 Kerberoasting 徹底絕跡。

### 3. 第三步：布設 HoneySPN (身分誘餌蜜罐)
- **建立高特權虛假帳號**：在 AD 中建立一個誘餌使用者（如 `svc_backup_admin`），將其加入 Domain Admins 群組，並隨意註冊一個虛假的 SPN（如 `MSSQLSvc/backup-dc.corp.local:1433`）。
- **即時通報觸發**：該服務在企業中完全不存在，任何正常系統都絕不會索取其票據。只要 SIEM 記錄到任何一次針對此 SPN 的 Event ID 4769，**即可 100% 斷定內網存在攻擊者正在執行自動化 Kerberoasting 掃描**，立即封鎖來源 IP！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：為什麼任何一個最底層的「網域使用者 (Domain Users)」帳號，在不需要任何特殊管理特權的情況下，都能夠合法向網域控制站索取所有服務帳號的 TGS 票據？**
  > **標準答案**：
  > 1. **Kerberos 設計哲學**：Kerberos 協定建立於「分散式服務存取」的架構上。其核心設計原則假定：任何合法的使用者，在日常辦公中都可能需要存取網域內的列印機、共用資料夾、SQL 資料庫或內部網站。
  > 2. **KDC 的授權邊界**：KDC（金鑰發行中心）只負責「驗證使用者身分（Authentication）」並簽發載有使用者權限 PAC 的票據，**KDC 本身並不負責判定該使用者「是否有權存取該特定服務的資料（Authorization）」**。
  > 3. **服務端驗證原則**：真正的權限判斷（例如你能不能讀取 SQL 的薪資表）是由目標伺服器在接收到票據後自行決定的。因此，只要使用者持有合法的 TGT，KDC 依據 RFC 4120 標準必須無條件為其簽發任何註冊了 SPN 的服務票據。

- [x] **Q2：在 Kerberoasting 攻擊中，為什麼註冊在「電腦帳號 (Computer Account)」名下的 SPN 通常不會成為攻擊者的目標？**
  > **標準答案**：
  > 1. **密碼複雜度與長度的降維打擊**：Windows 電腦帳號（如 `WS-01$`）的密碼並非由人工設置，而是由作業系統在加域時隨機生成之 **120 個位元組的高熵隨機字串**。
  > 2. **自動定期輪換機制**：電腦帳號的密碼每隔 30 天會由本機 Netlogon 服務與 DC 自動重新協商輪換。
  > 3. **密碼學破解極限**：使用 Hashcat 破解 120 碼包含高隨機特徵的密碼，即便調用全球所有超級電腦運算數萬年也無法解密。因此，攻擊者只會針對由網管人員手動建立、往往包含字典弱密碼的「**使用者帳號 (User Account)**」SPN 發起攻擊。

- [x] **Q3：在 Windows 安全事件日誌中，監控 Kerberoasting 為什麼要特別聚焦於「Ticket Encryption Type: 0x17 (RC4-HMAC)」？**
  > **標準答案**：
  > 1. **運算複雜度天差地遠**：RC4-HMAC 演算法（`0x17`）的核心僅是簡單的 MD4 運算，現代 GPU（如 RTX 4090）單卡破解速度可突破每秒數十億次；而微軟現代預設的 AES-128（`0x11`）與 AES-256（`0x12`）結合了 PBKDF2 與 4096 次 HMAC-SHA1 迭代，破解速度極其緩慢。
  > 2. **攻擊工具預設行為**：主流滲透工具（如 Rubeus、Invoke-Kerberoast）在發送 TGS-REQ 請求時，為了大幅降低後續字典比對的時間成本，會在請求標頭中特意宣告自身僅支援 RC4，迫使 KDC 以 `0x17` 簽發票據。
  > 3. **高信度告警指紋**：在全面推行 Windows 10/11 與現代 Server 的環境中，正常的應用程式連線幾乎全部協商為 AES；此時若突然冒出針對特定使用者 SPN 的 `0x17` 請求，即可直接判定為惡意攻擊。

- [x] **Q4：何謂「HoneySPN (身分誘餌蜜罐)」技術？它如何實現對內網橫向移動的「零誤報」早期預警？**
  > **標準答案**：
  > 1. **技術實現**：在 Active Directory 中建立一個虛構的使用者帳號（如 `sql_admin_service`），隨意綁定一個看似具備高價值的 SPN（如 `MSSQLSvc/prod-core-db.corp.local:1433`），但不為其部署任何真實的伺服器或業務。
  > 2. **零誤報原理**：因為該服務在企業的實際業務拓撲中**根本不存在**，任何正常的員工、管理員或自動化腳本都絕對沒有理由去索取這個 SPN 的服務票據。
  > 3. **早期捕獲能力**：攻擊者在進入內網後，通常使用自動化工具對全網進行無差別的 SPN 廣播掃描。一旦 SIEM 監視到有任何人向 DC 索取了該 HoneySPN 的 Event ID 4769，即可 100% 斷定有未授權人員正在內網執行 Kerberoasting，立即實施主機隔離。

- [x] **Q5：為什麼群組受管理服務帳戶 (gMSA) 能夠徹底終結傳統服務帳號的 Kerberoasting 威脅？其運作機制為何？**
  > **標準答案**：
  > 1. **消除人為弱密碼**：gMSA 完全由 Active Directory 集中託管，其密碼是由 KDC 自動計算之 120 字元高強度字串，徹底剝奪了人為設定「Password123」等人性弱點的可能。
  > 2. **全自動無感輪換**：KDC 預設每 30 天自動為 gMSA 輪換密碼，無需人工介入重開服務或維護設定檔。
  > 3. **強制限制身分存取**：只有獲得授權的特定電腦主機才能透過安全通道向 KDC 索取該 gMSA 的密碼使用權，攻擊者即使抓到票據也無法破解，更無法手動使用該帳號登入系統，在架構底層完全阻斷了憑證轉儲與離線破解。
