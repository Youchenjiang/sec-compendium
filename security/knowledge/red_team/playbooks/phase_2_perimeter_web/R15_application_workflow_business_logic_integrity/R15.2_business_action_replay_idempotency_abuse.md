# R15.2 業務操作重放與等冪性控制濫用分析 (Business Action Replay & Idempotency Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**業務操作重放 (Action Replay)** 與**等冪性控制濫用 (Idempotency Abuse)** 發生於金融交易、積分扣減、優惠券兌換等關鍵業務介面缺乏防重放機制時。其本質為：**「在分散式系統中，等冪性 (Idempotency) 指的是『多次執行同一操作所產生的業務結果與僅執行一次完全相同』；當後端 API 缺乏全域唯一的等冪性防重放鍵 (Idempotency Key) 或資料庫唯一約束時，攻擊者可藉由循序或併發重複發送同一封合法請求，達成雙重兌換、重複退款、虛擬資產刷取等嚴重業務損失」**。

```
[攻擊者] ── 1. 提交一次性儲值代碼請求 (POST /api/redeem {"code": "GIFT-100"}) ──► [Web 伺服器]
       │                                                                               │
       │                                                                               ▼ 執行加值 $100
       │                                                                        [用戶餘額: $100]
       │
       ├── 2. 重放該請求 (POST /api/redeem {"code": "GIFT-100"}) ────────────────────► [Web 伺服器]
       │                                                                               │ (未檢驗代碼是否已消費)
       │                                                                               ▼ 二次加值 $100
       │                                                                        [用戶餘額: $200]
       │
       └── 3. 循序重放 10 次 ➔ 餘額無故膨脹至 $1,000！
```

### 核心作戰決策與邊界
- **核心威脅**：代金券重複消費、點數反覆領取、重放退款請求、重放發送 SMS 簡訊轟炸。
- **作戰決策心流**：
  1. **定位非等冪性寫入端點**：鎖定金融轉帳、禮品卡核銷、邀請碼獎勵等核心 POST 端點。
  2. **測試重放窗口**：短時間循序發送相同請求，檢查伺服器是否回傳重複成功。
  3. **等冪鍵強度檢驗**：若系統要求 `Idempotency-Key` 標頭，測試將該標頭移除、設為空值、或變異數值是否能重放操作。
- **技術邊界**：
  - **與併發競態 (R15.3) 差異**：R15.2 側重在「系統缺乏業務去重與等冪性邏輯，即使間隔數秒循序重放依然成功」；R15.3 側重在「利用毫秒級微小時間窗突破執行緒同步與鎖競爭」。

## 🔬 第一動：等冪性語意與分散式重放機制全景解剖 (Mechanics & Idempotency Flaws)

### 四大等冪性防禦崩潰模式對照表

| 缺陷模式 | 架構實現盲區 | 攻擊利用方式 |
| :--- | :--- | :--- |
| **1. 裸 API (無防重機制)** | 後端直接執行 SQL `UPDATE balance = balance + 100`，未記錄流水號 | 直接循序重發封包，伺服器無限次累積加值 |
| **2. 鍵值與載荷解耦** | Redis 快取了 `Idempotency-Key`，但未綁定請求 Body 內容 Hash | 攻擊者複用舊 Key，更換 Body 參數進行偽造操作 |
| **3. 提前釋放防重鎖** | 操作處理失敗時提前將 Key 刪除，缺乏失敗狀態鎖定 | 誘導伺服器逾時以觸發重放漏洞 |
| **4. 資料庫缺乏唯一約束** | 僅在應用層以 `SELECT` 檢查是否存在，未建立 DB `UNIQUE` 索引 | 在循序與微小延遲下依然寫入重複紀錄 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式與利用手法 | 典型請求特徵 | 突防原理與作用標記 |
| :--- | :--- | :--- |
| **直球循序重放** | `POST /api/wallet/claim-bonus`<br>`{"bonus_id": 998}` (重複發送 5 次) | 業務端點完全未做重複領取校驗。 |
| **Idempotency-Key 剝離** | 刪除 HTTP 標頭中的 `Idempotency-Key` 或設為空 | 後端防重中介軟體存在「未傳入 Key 即略過檢查」的缺陷。 |
| **鍵值前綴碰撞/偽造** | 變更標頭為 `Idempotency-Key: rand_001`, `rand_002` | 後端僅校驗 Key 本身是否重複，未將 Key 與交易本體鎖定。 |
| **第三方 Webhook 重放** | 重放金流通知封包：`POST /webhook/payment/paypal` | 伺服器未校驗通知流水號 (Notification ID) 的唯一性。 |
| **簡訊/OTP 重放轟炸** | 重放 `POST /api/auth/send-sms {"phone": "138..."}` | 介面無間隔冷卻限制，重放發送造成簡訊資費消耗。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **分散式代理重放**：
  - 透過不同代理 IP 循序重發同一業務請求，繞過基於 IP 的簡單 Rate Limiting 頻率限制。
- **標頭大小寫混淆**：
  - 測試非標標頭：`X-Idempotency-Key`、`Idempotent-Token`、`x-request-id`。
- **鑑識與日誌遙測特徵**：
  - **完全相同的交易指紋**：日誌中出現多筆請求，其請求參數、金額、收件人完全相同，且來源 Session 相同。
  - **異常激增的成功交易流水**：同一用戶帳號在短時間內產生大量重複業務流水號，資料庫餘額變更與真實儲值紀錄嚴重脫節。

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Redis 原子等冪鍵與載荷雜湊綁定 (Python 範例)
```python
import hashlib, redis

r = redis.Redis(host='localhost', port=6379, db=0)

def process_transaction_idempotent(idempotency_key: str, payload_dict: dict):
    # 1. 將請求 Body 內容計算 SHA256 雜湊，綁定鍵值與資料
    payload_hash = hashlib.sha256(str(sorted(payload_dict.items())).encode()).hexdigest()
    redis_key = f"idempotency:{idempotency_key}"
    
    # 2. 使用 SET NX 原子操作鎖定 120 秒
    acquired = r.set(redis_key, payload_hash, nx=True, ex=120)
    if not acquired:
        # 鍵值已存在，拒絕重複執行
        cached_hash = r.get(redis_key).decode()
        if cached_hash == payload_hash:
            return {"status": "CONFLICT", "message": "Duplicate request ignored"}
        else:
            return {"status": "ERROR", "message": "Idempotency key payload mismatch"}
            
    # 3. 執行實質業務處理...
    return {"status": "SUCCESS"}
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`replay_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import json

BALANCE = 0
USED_TOKENS = set()

class ReplayHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        global BALANCE
        length = int(self.headers.get('Content-Length', 0))
        data = json.loads(self.rfile.read(length).decode())
        token = data.get("token")
        
        safe = "safe=1" in self.path
        if safe:
            # 安全防禦：校驗 Token 唯一性
            if token in USED_TOKENS:
                self.send_response(409); self.end_headers(); self.wfile.write(b"Token already used!\n"); return
            USED_TOKENS.add(token)
            
        # 缺陷：每次收到請求皆累加餘額
        BALANCE += 50
        self.send_response(200); self.end_headers()
        self.wfile.write(f"Claimed $50. Total: {BALANCE}\n".encode())

ThreadingHTTPServer(("127.0.0.1", 8152), ReplayHandler).serve_forever()
```

### 2. 三步驗證流程

1. **首次領取獎勵**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8152/" -d '{"token": "PROMO_9988"}'
   # 回顯: Claimed $50. Total: 50
   ```
2. **重放該請求 2 次**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8152/" -d '{"token": "PROMO_9988"}'
   curl -s -X POST "http://127.0.0.1:8152/" -d '{"token": "PROMO_9988"}'
   # 回顯: Claimed $50. Total: 150 ➔ 成功重放領取！
   ```
3. **驗證加固端點**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8152/?safe=1" -d '{"token": "SAFE_123"}'
   curl -s -X POST "http://127.0.0.1:8152/?safe=1" -d '{"token": "SAFE_123"}'
   # 二次請求回顯: Token already used!，重放攻擊失效！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 業務操作中的「等冪性 (Idempotency)」定義為何？**  
  *分析思路*：同一個操作無論向伺服器提交 1 次、10 次或 100 次，對系統後端產生的資源狀態與業務副作用完全相同，不會因為重發而發生重複扣款或重複發券。

- [ ] **Q2. 為什麼單純在 Redis 快取 `Idempotency-Key` 還不夠，必須同時比對 Payload Hash？**  
  *分析思路*：防止「鍵值重用偽造攻擊」；若攻擊者拿同一個合法等冪鍵發送了完全不同的交易參數（如修改收件人或金額），若不校驗資料雜湊，伺服器可能將錯誤的舊結果回傳，或導致業務邏輯混淆。

- [ ] **Q3. 簡述業務操作重放 (Replay) 與並發競態條件 (Race Condition) 在時間特性上的根本區別？**  
  *分析思路*：重放攻擊側重於「缺乏防重去重標記」，攻擊者即便每隔 5 秒鐘悠閒地手動重發一次依然能成功；並發競態則側重於「缺乏排他鎖」，必須在微秒或毫秒級的時間窗口內同時送達請求才能打破同步。

- [ ] **Q4. 金融金流 Webhook 回呼端點如何徹底防範重放攻擊？**  
  *分析思路*：
  1. 金流商在回呼請求中提供唯一的通知流水號 (Notification Event ID)；
  2. 伺服器端將已處理的 Event ID 寫入資料庫並設置唯一索引；
  3. 每次收到通知先校驗簽章，再以原子方式檢查 Event ID 是否已處理。

- [ ] **Q5. 企業架構中防範業務重放的雙重防線基線為何？**  
  *分析思路*：
  1. 第一道防線：在 API 閘道/中介軟體引入基於 Redis 的分佈式等冪鎖 (`SET NX EX`)；
  2. 第二道防線：在資料庫交易層建立實質的 `UNIQUE` 唯一複合約束，確保萬一快取失效，資料庫引擎仍能以硬性約束拒絕重複插入。
