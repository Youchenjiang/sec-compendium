# R15.1 工作流與狀態機跳躍繞過分析 (Workflow & State-Transition Bypass)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**工作流與狀態機跳躍 (Workflow & State-Transition Bypass)** 發生於業務流程（如電商結帳、審批流、身分驗證向導）的狀態流轉控制失守時。其本質為：**「企業業務邏輯本質上是有限狀態機 (Finite State Machine, FSM)；當伺服器端控制器各自獨立處理 API，未在後端強制作業狀態的前提條件 (Prerequisite / Guard) 檢查，或盲信客戶端回傳的狀態參數時，攻擊者可透過直接調用終端 API、修改狀態代碼或逆向回溯，直接跳過關鍵檢查（如略過付款步驟直接標記為已支付、跳過主管審核直接觸發撥款）」**。

```
[標準合法流程]
[購物車 (CART)] ──► [填寫地址 (ADDRESS)] ──► [付款審核 (PAYMENT)] ──► [發貨完成 (FULFILLED)]
                                                      │ (需支付 $10,000)
                                                      ▼
[攻擊者繞過流程]
[購物車 (CART)] ── 1. 產生訂單 ID: 8891
       │
       └─► 2. 直接發送 POST /api/order/8891/fulfill ──────────────────► [發貨完成 (FULFILLED)]
              (後端未驗證當前狀態是否為 PAYMENT_SUCCESS，直接完成交易！)
```

### 核心作戰決策與邊界
- **核心威脅**：無成本獲取商品、繞過 KYC/MFA 驗證關卡、偽造審批流程。
- **作戰決策心流**：
  1. **繪製目標狀態轉移圖**：梳理業務從「起點」到「終點」的所有狀態代碼與 API 路由。
  2. **測試端點解耦與前置檢查**：直接對後續步驟 API 發送請求（如未付款即呼叫確認收貨或發貨）。
  3. **測試客戶端狀態篡改**：檢查請求主體中是否包含 `status`、`step`、`is_approved` 等可覆寫欄位。
- **技術邊界**：
  - **與物件授權 (IDOR) 差異**：IDOR 著重在「存取他人數據」；狀態機繞過著重在「自身流程的時間序列合法性被打破」。

## 🔬 第一動：有限狀態機 (FSM) 缺陷全景解剖 (Mechanics & State Machine Flaws)

### 狀態機四種致命設計缺陷對照表

| 缺陷模型 | 脆弱架構模式 | 攻擊利用方式 |
| :--- | :--- | :--- |
| **1. 守衛條件缺失 (Missing Guard)** | 後端僅驗證目前請求參數，未核驗「當前資料庫內存狀態」 | 在狀態為 `CREATED` 時直接呼叫 `SETTLED` API |
| **2. 客戶端驅動狀態 (Client-Driven)** | 伺服器依據請求參數直接寫入：`UPDATE orders SET status = req.body.status` | 提交 `{"status": "PAID"}` 篡改狀態 |
| **3. 亂序跳躍 (Out-of-Order Execution)** | 多步驟向導（Step 1 ➔ Step 2 ➔ Step 3）未驗證中間 Token | 直接從 Step 1 跳躍至 Step 3 提交完成 |
| **4. 逆向非法回溯 (Illegal Rollback)** | 訂單已處於終態 (`REFUNDED`)，但特定 API 仍允許操作 | 對已退款之訂單呼叫出貨或重新發貨 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式與利用手法 | 典型請求構造 | 突防原理與作用標記 |
| :--- | :--- | :--- |
| **端點直調 (Step Skip)** | `POST /api/checkout/step4-complete`<br>`{"order_id": "ORD-123"}` | 完全跳過 Step 2 (付款) 與 Step 3 (審核) 端點。 |
| **狀態參數直接注入** | `PATCH /api/orders/ORD-123`<br>`{"status": "PAID", "payment_verified": true}` | 利用後端批量賦值或弱校驗，將狀態強制刷成已付款。 |
| **二階狀態競態 (Race Transition)** | 併發發送 `POST /order/cancel` 與 `POST /order/ship` | 在鎖競爭下使訂單同時處於取消退款與發貨狀態。 |
| **審批流虛假簽署** | `POST /api/workflow/approve`<br>`{"ticket_id": 99, "action": "AUTO_BYPASS"}` | 偽造內部系統調用標記或權限識別碼。 |
| **逆向重入 (State Re-entry)** | 對已結案訂單發起 `POST /api/orders/ORD-123/reopen` | 將終態訂單重啟至中間態，二次榨取優惠券或點數。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **API 版本與行動端盲區**：
  - Web 端可能具備嚴格的狀態檢查，但舊版 API (`/v1/`) 或專供 App 使用的端點未及時同步狀態守衛邏輯。
- **鑑識與日誌遙測特徵**：
  - **異常極短的時間間隔 (Time-to-Complete)**：資料庫稽核日誌中，從訂單建立 (`CREATED`) 到出貨 (`FULFILLED`) 的時間差小於 100 毫秒（人類不可達，且無第三方金流回呼記錄）。
  - **缺失審計日誌軌跡 (Audit Log Gaps)**：審核表中完全不存在 `PAYMENT_GATEWAY_CALLBACK` 事件，卻突發出現 `ORDER_SHIPPED` 事件。

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **直接跳步執行** | 業務日誌中特定前置事件計數為 0 | 伺服器端強制實施有限狀態機 (FSM) 檢查 | 尋找不同業務子系統之間的狀態同步延遲 |
| **狀態參數篡改** | API 收到不應由前台提交的特權欄位 | 強制實施輸入 DTO 白名單；狀態完全由內部維護 | 尋找後台內部管理 API 的未授權存取漏洞 |
| **終態逆向回溯** | 處於 `TERMINATED` 的實體被再次操作 | 資料庫層定義嚴格的狀態流轉條件約束 | 轉向尋找多租戶切換過程中的狀態初始化漏洞 |
| **審核流繞過** | 高額交易缺少主管審批流水號 | 關鍵步驟必須由非對稱簽章 Token 驅動 | 審批憑證私鑰若遭硬編碼洩漏則全面失守 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 伺服器端有限狀態機 (FSM) 嚴格約束 (Python 範例)
```python
# 嚴格定義狀態轉移圖與守衛條件
ALLOWED_TRANSITIONS = {
    "CREATED": ["ADDRESS_CONFIRMED"],
    "ADDRESS_CONFIRMED": ["PAYMENT_PENDING"],
    "PAYMENT_PENDING": ["PAID", "CANCELLED"],
    "PAID": ["FULFILLED"],
    "FULFILLED": [],   # 終態
    "CANCELLED": []   # 終態
}

def transition_order_state(order, new_state: str):
    current = order.status
    # 核心檢查：新狀態必須在當前狀態允許的轉移白名單中！
    if new_state not in ALLOWED_TRANSITIONS.get(current, []):
        raise ValueError(f"Illegal state transition from {current} to {new_state}")
    
    order.status = new_state
    db.save(order)
```

### 2. 資料庫樂觀鎖與原子條件更新 (SQL 實踐)
```sql
-- 確保只有在符合前置狀態時才允許更新，杜絕客戶端亂序跳轉
UPDATE orders 
SET status = 'FULFILLED', updated_at = NOW() 
WHERE id = :order_id AND status = 'PAID';
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`workflow_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import json

ORDERS = {"ORD-001": "CREATED"}

class WorkflowHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get('Content-Length', 0))
        data = json.loads(self.rfile.read(length).decode())
        order_id = data.get("id")
        
        safe = "safe=1" in self.path
        if self.path.startswith("/pay"):
            ORDERS[order_id] = "PAID"
            self.send_response(200); self.end_headers(); self.wfile.write(b"Paid\n"); return
            
        if self.path.startswith("/fulfill"):
            # 缺陷端點：未校驗當前狀態是否為 PAID
            if safe and ORDERS.get(order_id) != "PAID":
                self.send_response(400); self.end_headers(); self.wfile.write(b"Error: Must pay first!\n"); return
            ORDERS[order_id] = "FULFILLED"
            self.send_response(200); self.end_headers(); self.wfile.write(b"Fulfilled without payment!\n")

ThreadingHTTPServer(("127.0.0.1", 8151), WorkflowHandler).serve_forever()
```

### 2. 三步驗證流程

1. **直接呼叫出貨端點（跳過付款）**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8151/fulfill" -d '{"id": "ORD-001"}'
   # 回顯: Fulfilled without payment! (證實未付款直接出貨成功)
   ```
2. **驗證加固端點**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8151/fulfill?safe=1" -d '{"id": "ORD-001"}'
   # 回顯: Error: Must pay first!，成功阻斷！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是有限狀態機 (FSM) 中的「守衛條件 (Guard Condition)」？**  
  *分析思路*：守衛條件是在執行狀態轉移前必須滿足的布林表達式（如「訂單必須處於已付款且款項到帳確認」）；若不滿足則強行中止轉移並拋出例外。

- [ ] **Q2. 為什麼依賴前端向導（如第 1 步隱藏「下一步」按鈕）無法防止狀態機繞過？**  
  *分析思路*：前端介面控制僅是用戶體驗設計；攻擊者使用 Burp Suite 或 cURL 可直接向後續步驟的 API 端點發送 HTTP 請求，完全繞過前端的 UI 流程限制。

- [ ] **Q3. 在微服務架構中，狀態機跳躍繞過通常是由何種分散式架構缺陷引起的？**  
  *分析思路*：不同微服務（如訂單服務、金流服務、出貨服務）之間透過非同步事件通訊，若出貨服務只盲信訊息佇列收到的通知或直接暴露對外 REST 端點，而未主動回查訂單服務的權威當前狀態，即會被穿透。

- [ ] **Q4. 稽核人員如何從日誌特徵快速篩查疑似狀態機跳躍的交易？**  
  *分析思路*：篩查交易生命週期中「建立時間」至「完成時間」異常短暫（如秒級完成需人工作業的審批）、或缺少關鍵前置流程專屬日誌（如金流回呼日誌為空）的異常流水紀錄。

- [ ] **Q5. 徹底防禦工作流狀態跳躍的最佳工程架構為何？**  
  *分析思路*：
  1. 後端引入中央狀態機引導所有業務變更，嚴格限定狀態轉移矩陣；
  2. 資料庫操作採用條件更新 (`WHERE status = 'PREV_STATE'`) 確保原子性；
  3. 狀態變更一律由伺服器內部事件觸發，嚴禁由客戶端傳入參數直接指定。
