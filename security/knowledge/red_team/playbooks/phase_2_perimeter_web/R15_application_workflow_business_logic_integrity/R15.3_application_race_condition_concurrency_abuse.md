# R15.3 應用層競態條件與併發控制濫用分析 (Application Race Condition & Concurrency Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**應用層競態條件 (Race Condition)** 與**併發控制濫用 (Concurrency Abuse)** 發生於多執行緒或分散式服務處理並行請求時。其本質為：**「檢查時間與使用時間存在脫鉤視窗 (Time-of-Check to Time-of-Use, TOCTOU)；當後端系統在『驗證資源是否可用（如檢查餘額、確認優惠券是否已領取）』與『執行扣減/標記使用』之間缺乏嚴密的排他鎖 (Exclusive Lock) 或原子操作時，攻擊者透過高併發同步發送多筆請求，迫使多個執行緒在狀態更新前同時通過驗證，達成超額提款、重複兌換或突破次數限制」**。

```
[攻擊者] ── 同時併發發送 2 筆扣款 $100 請求 (帳戶餘額僅有 $100)
    │
    ├── 請求 A (執行緒 1) ──► 1. 讀取餘額: $100 (足夠) ──┐
    │                                                    ├── [TOCTOU 漏洞空窗期 (10ms)]
    └── 請求 B (執行緒 2) ──► 2. 讀取餘額: $100 (足夠) ──┘   (兩執行緒皆判定餘額充足！)
                                 │
                                 ├── 3. 執行緒 1 扣款 ➔ 餘額設為 $0 ➔ 發放商品 A
                                 ▼ 4. 執行緒 2 扣款 ➔ 餘額設為 $0 ➔ 發放商品 B
                    [結果：花費 $100 買到價值 $200 的兩件商品！]
```

### 核心作戰決策與邊界
- **作戰武器演進**：從早期的多執行緒 Python 併發，進化至現代基於 **HTTP/2 單封包攻擊 (Single-Packet Attack)**，能將 30~50 個請求壓縮在同一 TCP 封包中傳輸，抵達目標伺服器的時間差縮小至微秒 (Microsecond) 級別。
- **目標高危場景**：優惠券兌領、點數提現、限購商品搶購、投票計數、檔案上傳殺毒掃描競爭。
- **技術邊界**：
  - **與業務重放 (R15.2) 差異**：業務重放即使間隔數秒循序發送也能成功（缺乏防重標記）；競態條件則必須在**微秒至毫秒級的時間窗口內同時送達**才能觸發鎖失效。

## 🔬 第一動：TOCTOU 競態物理窗口全景解剖 (Mechanics & Single-Packet Physics)

### 1. TOCTOU 執行緒交錯時間軸

```
時間軸 (t)      執行緒 1 (Thread 1)                執行緒 2 (Thread 2)
  t0           SELECT balance (得 100)             
  t1           檢查 100 >= 100 (通過)             SELECT balance (得 100)
  t2           [業務邏輯處理中...]                 檢查 100 >= 100 (通過)
  t3           UPDATE balance = 0                 [業務邏輯處理中...]
  t4           發放商品 1                         UPDATE balance = 0
  t5                                              發放商品 2 (超賣/超額提款成立！)
```

### 2. HTTP/2 單封包攻擊物理原理 (Single-Packet Attack)
在傳統 HTTP/1.1 中，受網路抖動 (Jitter) 影響，多個請求難以在同一微秒到達後端。利用 HTTP/2 多工訊框 (Multiplexing) 特性：
- 攻擊者將 30 個請求透過同一條 TCP 連線發送；
- 前期發送請求標頭，但刻意扣留最後 1 位元組；
- 最後將所有請求的最後 1 位元組打包在同一個 TCP 封包中釋放；
- 後端伺服器在同一瞬間（微秒級）同時觸發所有請求的處理流程，TOCTOU 穿透率接近 100%。

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **連線預熱 (Connection Pre-Warming)**：
  - 在發起單封包攻擊前，先發送 5~10 個普通合法請求預熱 TCP 連線與後端執行緒池，消除 TLS 握手與資料庫連線池初始化延遲。
- **鑑識與日誌遙測特徵**：
  - **微秒級密集日誌**：Access Log 中同一用戶在同一毫秒 (Millisecond) 內發起數十次完全相同的操作請求。
  - **資料庫死鎖告警 (Deadlock Exceptions)**：資料庫監控中突發出現大量 `Deadlock found when trying to get lock` 錯誤日誌。
  - **異常數值**：資料庫出現非預期的負數欄位（如 `balance < 0` 或 `stock < 0`）。

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 資料庫層級：原子條件更新 (Atomic Update - 最優先推薦)
```sql
-- 徹底消除 TOCTOU 空窗：將「檢查」與「扣減」合併為單一原子 SQL 語句
UPDATE accounts 
SET balance = balance - 100, updated_at = NOW() 
WHERE id = :user_id AND balance >= 100;
-- 透過檢查受影響行數 (Affected Rows):
-- 若為 1 ➔ 扣款成功；若為 0 ➔ 餘額不足，立即中斷業務！
```

### 2. 悲觀鎖機制 (Pessimistic Locking - 適用複雜商業邏輯)
```sql
BEGIN TRANSACTION;
-- 查詢時強制鎖定該行資料，其他執行緒必須排隊等待釋放
SELECT balance FROM accounts WHERE id = :user_id FOR UPDATE;

-- 執行業務檢查與計算...
UPDATE accounts SET balance = balance - 100 WHERE id = :user_id;
COMMIT;
```

### 3. Redis 分散式鎖 (Lua 腳本保證原子釋放)
```lua
-- 原子性檢查並設置使用者業務鎖
if redis.call("set", KEYS[1], ARGV[1], "NX", "EX", 5) then
    return 1
else
    return 0
end
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`race_lab.py`，極簡 30 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import time, threading

BALANCE = 100
LOCK = threading.Lock()

class RaceHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        global BALANCE
        safe = "safe=1" in self.path
        
        if safe:
            # 安全防禦：悲觀互斥鎖
            with LOCK:
                if BALANCE >= 100:
                    time.sleep(0.05) # 模擬業務耗時
                    BALANCE -= 100
                    self.send_response(200); self.end_headers(); self.wfile.write(b"Success\n")
                else:
                    self.send_response(400); self.end_headers(); self.wfile.write(b"Insufficient balance\n")
        else:
            # 缺陷：存在 TOCTOU 空窗
            if BALANCE >= 100:
                time.sleep(0.05) # 漏洞空窗期！
                BALANCE -= 100
                self.send_response(200); self.end_headers(); self.wfile.write(b"Success\n")
            else:
                self.send_response(400); self.end_headers(); self.wfile.write(b"Insufficient balance\n")

ThreadingHTTPServer(("127.0.0.1", 8153), RaceHandler).serve_forever()
```

### 2. 三步驗證流程

1. **以平行執行緒發起併發扣款 (模擬攻擊)**：
   ```bash
   python -c '
   import threading, urllib.request
   def hit():
       try:
           r = urllib.request.urlopen("http://127.0.0.1:8153/", data=b"")
           print("扣款結果:", r.read().decode().strip())
       except Exception as e:
           print("失敗:", e)
   threads = [threading.Thread(target=hit) for _ in range(3)]
   for t in threads: t.start()
   for t in threads: t.join()
   '
   ```
   **預期回顯**：
   - 看到多次 `扣款結果: Success`，本金僅 $100 卻扣減了兩次以上！
2. **驗證加固端點**：
   將請求目標改為 `http://127.0.0.1:8153/?safe=1` 重新發起併發：
   - 僅有一筆成功，其餘均回傳 `HTTP 400: Insufficient balance`，防護生效！

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是 TOCTOU 漏洞？在 Web 應用中最常見的發生點在哪？**  
  *分析思路*：Time-of-Check to Time-of-Use，即「狀態驗證」與「狀態寫入」之間存在非原子性的時間差；最常見於檢查餘額後才扣款、檢查是否已領優惠券後才發券的業務場景。

- [ ] **Q2. HTTP/2 單封包攻擊 (Single-Packet Attack) 為何能大幅提高競態條件的利用成功率？**  
  *分析思路*：利用 HTTP/2 多工特性將數十個請求壓縮於單一 TCP 封包發送，排除了跨網路傳輸的延遲抖動，迫使所有請求在同一微秒抵達伺服器網卡，最大化命中 TOCTOU 空窗。

- [ ] **Q3. 為什麼「在應用層使用 Python/Java 的 `synchronized` 或 `Lock`」在分散式微服務架構中會失效？**  
  *分析思路*：語言層面的記憶體鎖僅能在「單一進程/單一實例」內生效；現代架構通常部屬數十個 Pod 或叢集節點，分佈在不同伺服器上的執行緒依然會並行讀寫同一個資料庫，必須依賴分佈式鎖或資料庫行級鎖。

- [ ] **Q4. 為什麼說「原子條件更新 (`UPDATE ... WHERE balance >= 100`)」優於悲觀鎖 (`FOR UPDATE`)？**  
  *分析思路*：原子更新由資料庫行級排他鎖在單一 SQL 語句內完成判斷與寫入，不需要維持長事務 (Long Transaction)，效能極高且不會產生事務間複雜的死鎖 (Deadlock) 風險。

- [ ] **Q5. 針對檔案上傳的防毒掃描競爭，最穩健的防禦隔離基線為何？**  
  *分析思路*：上傳的暫存檔案絕對禁止儲存於 Web 伺服器可對外訪問的公開目錄；檔案必須暫存在隔離的臨時磁區，待掃描、清洗與重命名完成後，再透過內部非同步管線搬移至存儲服務。
