# R13.3 主機與轉發標頭路由與源站選擇信任濫用分析 (Host & Forwarded-Header Routing / Origin-Selection Trust Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**主機與轉發標頭信任濫用 (Host & Forwarded Trust Abuse)** 發生於反向代理（Nginx/Envoy/ALB）與後端服務之間。其本質為：**「轉發標頭（`Host`, `X-Forwarded-Host`, `Forwarded`）僅是用戶端的自述宣告，邊界未校驗連線來源 IP 信任鏈即盲目引用該標頭進行路由分派或 URL 生成，致使攻擊者能切換內部源站或投毒業務連結」**。

```
[攻擊者] ── 1. 發送請求: (Host: public.corp | X-Forwarded-Host: admin.internal) ──► [入口反向代理]
                                                                                             │
                                            ┌────────────────────────────────────────────────┴────────────────────────────────────────────────┐
                                            ▼ (安全架構：強制剝離客戶端轉發標頭)                                                             ▼ (缺陷架構：盲信 XFH 決定上游)
                             [強制覆寫 XFH: public.corp]                                                                     [依據 XFH 路由至 admin.internal]
                                            │                                                                                                 │
                                            ▼                                                                                                 ▼
                             [路由至公開服務 (403/正常)]                                                                      [成功穿透邊界，存取內部管理叢集！]
```

### 核心作戰決策與邊界
- **常見危害**：內部源站切換（穿透邊界存取內網）、密碼重置連結投毒（竊取 Token）、動態代理出站 SSRF。
- **作戰決策心流**：
  1. **保持連線不變，單獨變異標頭**：TCP 連線至公網 Gateway，逐一變換 `X-Forwarded-Host`、`Forwarded`、`X-Original-Host`。
  2. **觀察路由與回應特徵**：檢測是否觸發內部叢集回應頭、狀態碼突變、或跳轉 URL 網域被替換。
- **技術邊界**：
  - **與虛擬主機爆破 (R05.5) 差異**：R05.5 是直接改變外層 `Host` 找同伺服器站台；R13.3 則是透過「中繼代理轉發標頭的信任缺陷」改變路由路徑或業務鏈結。

---

## 🔬 第一動：底層機制與標頭解析衝突 (Mechanics & Precedence)

### 1. 轉發標頭信任鏈缺陷 (Provenance Chain Failure)
- 代理或後端在讀取 `X-Forwarded-Host` 時，**未檢查連線對等點 IP (Remote Peer IP) 是否來自內部受信任的代理 CIDR**。
- 若伺服器直接對公網開放，外部攻擊者可隨意偽造標頭欺騙後續邏輯。

### 2. 標頭解析優先權衝突矩陣 (Header Precedence)

| 衝突情境 | 典型反向代理行為 | 典型後端框架行為 (Django/Rails/Spring) |
| :--- | :--- | :--- |
| **Host vs. XFH** | 路由通常依據外層 `Host` | 部分框架預設啟用 `USE_X_FORWARDED_HOST` 時優先取 XFH |
| **XFH vs. Forwarded** | 優先讀取 `X-Forwarded-Host` | 現代標準微服務優先讀取 RFC 7239 `Forwarded` 標頭 |
| **重複多重 Host** | 某些代理取第一個放行 | 後端可能取最後一個，引發 HTTP 參數污染 (HPP) |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式 | 關鍵標頭構造 (Payload) | 作用與突防原理 |
| :--- | :--- | :--- |
| **內部源站路由切換** | `Host: public.corp`<br>`X-Forwarded-Host: admin-internal.corp` | 反向代理依據 XFH 將請求分發至受限管理集群。 |
| **密碼重置連結投毒** | `X-Forwarded-Host: evil-attacker.com` | 後端生成郵件跳轉連結時引用 XFH，洩漏重置 Token 至攻擊者 C2。 |
| **動態代理出站 SSRF** | `X-Forwarded-Host: 169.254.169.254:80` | 反向代理配置 `proxy_pass http://$http_x_forwarded_host`，直打雲端 IMDS。 |
| **RFC 7239 標準走私** | `Forwarded: host=internal.corp;proto=https` | 規避僅檢查 `X-Forwarded-Host` 的舊式 WAF 規則。 |
| **絕對 URI 覆寫** | 請求行：`GET http://internal.corp/ HTTP/1.1`<br>`Host: public.corp` | 利用 Request Line 優先於 Host 標頭的解析特性繞過過濾。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **標頭變體清單**：
  - 若 `X-Forwarded-Host` 被阻斷，測試相容標頭：`X-Forwarded-Server`、`X-Original-Host`、`X-Host`、`X-Cluster-Client-Host`。
- **正規化字符繞過**：
  - 尾端 FQDN 點號：`Host: target.com.`（可繞過弱正則匹配）。
  - 預設連接埠干擾：`Host: target.com:443`。
- **鑑識特徵**：
  - 邊界日誌記錄到外網 IP 傳入包含非本組織網域之 `X-Forwarded-Host`。
  - 後端日誌中 Client IP 顯示為內部代理 IP，但處理的虛擬主機卻是內部未授權系統。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **源站路由切換** | 公網介面收到包含內部網域名稱之 XFH 標頭 | 邊界反向代理強制剝離所有公網傳入之轉發標頭 | 尋找未受管轄的邊界端點或次要 Gateway |
| **密碼重置投毒** | 密碼重置請求的跳轉 URL 指向非官方外部網域 | 應用程式全面改用靜態設定檔網域生成絕對 URL | 尋找未套用標準 URL 生成工具之遺留端點 |
| **動態代理 SSRF** | 代理主機產生朝向內部 IP 或 IMDS 之異常連線 | 嚴禁在 `proxy_pass` 中使用變數；採用固定 upstream | 尋找支援自訂轉發規則之第三方外掛 |
| **RFC 7239 偽造** | 監控系統捕獲異常的 `Forwarded` 標頭值 | 邊界強制覆寫 `Forwarded`，移除任何來自公網的宣告 | 內部代理鏈路若有遺漏節點仍可利用 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Nginx 邊界強制剝離與安全轉發配置
```nginx
server {
    listen 443 ssl http2;
    server_name public.company.com;

    location / {
        # 1. 嚴禁在 proxy_pass 中直接使用客戶端標頭變數！
        proxy_pass http://public_backend_pool;
        proxy_http_version 1.1;

        # 2. 強制以邊界真實狀態覆寫轉發標頭，清除公網偽造值
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $remote_addr;

        # 3. 清空潛在的非標路徑覆寫標頭
        proxy_set_header X-Original-URL "";
        proxy_set_header X-Rewrite-URL "";
        proxy_set_header Forwarded "";
    }
}
```

### 2. 後端代碼安全基線 (Python / Django 範例)
```python
# Django settings.py 安全配置
# 1. 嚴格綁定允許的主機名稱
ALLOWED_HOSTS = ['public.company.com']

# 2. 僅在確定前方只有受信任代理且邊界已淨化標頭時才開啟
USE_X_FORWARDED_HOST = False  # 預設維持關閉，避免盲信 XFH

# 3. 業務 URL 生成一律使用靜態 CANONICAL_URL
CANONICAL_DOMAIN = "https://public.company.com"
def build_reset_link(token):
    return f"{CANONICAL_DOMAIN}/reset?token={token}"
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`routing_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

class RoutingHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        # 脆弱邏輯：優先讀取 X-Forwarded-Host 決定源站路由
        target_host = self.headers.get("X-Forwarded-Host", self.headers.get("Host", "public"))
        
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.end_headers()
        
        if "admin.internal" in target_host:
            self.wfile.write(b"ADMIN_SECRET_AREA: Access Granted via Host Spoofing!\n")
        else:
            self.wfile.write(b"PUBLIC_AREA: Welcome normal user.\n")

ThreadingHTTPServer(("127.0.0.1", 9143), RoutingHandler).serve_forever()
```

### 2. 三步驗證流程

1. **發送標準公開請求**：
   ```bash
   curl -s "http://127.0.0.1:9143/" -H "Host: public.company.com"
   # 回顯: PUBLIC_AREA: Welcome normal user.
   ```
2. **偽造 X-Forwarded-Host 實施源站切換**：
   ```bash
   curl -s "http://127.0.0.1:9143/" \
     -H "Host: public.company.com" \
     -H "X-Forwarded-Host: admin.internal"
   # 回顯: ADMIN_SECRET_AREA: Access Granted via Host Spoofing!
   # 證實成功利用轉發標頭突破邏輯分區，存取受限內部介面！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼轉發標頭（如 `X-Forwarded-Host`）不能作為公網請求的信任依據？**  
  *分析思路*：轉發標頭是由 HTTP 用戶端自由構造的文字宣告；若無邊界反向代理驗證對等點 IP 並進行強制覆寫，外部攻擊者可隨意偽造標頭進行欺詐。

- [ ] **Q2. 密碼重置連結投毒 (Password Reset Poisoning) 的運作流程為何？**  
  *分析思路*：後端在發送重置信件時，引用未校驗的 `Host` 或 `X-Forwarded-Host` 拼裝重置網址（如 `https://{Host}/reset?token=XYZ`）；受害者點擊後，機密 Token 直接發送至攻擊者受控的伺服器。

- [ ] **Q3. 什麼是動態反向代理 SSRF？**  
  *分析思路*：反向代理配置中直接以變數設定目標（如 Nginx `proxy_pass http://$http_x_forwarded_host`），使攻擊者能傳入內部 IP 或雲端 IMDS 網址，將代理轉為內網攻擊跳板。

- [ ] **Q4. 為什麼僅在 WAF 過濾 `X-Forwarded-Host` 往往無法防禦此漏洞？**  
  *分析思路*：後端框架支援多種歷史相容標頭（如 `X-Forwarded-Server`、`X-Original-Host`）或新式 RFC 7239 `Forwarded` 標頭；攻擊者更換標頭即可繞過單一正則過濾。

- [ ] **Q5. 徹底防禦主機與轉發標頭信任濫用的黃金架構基線為何？**  
  *分析思路*：邊界反向代理強制剝離所有公網傳入之轉發標頭並由代理本機重寫；後端代碼生成絕對 URL 一律使用靜態設定檔，嚴禁讀取請求標頭拼裝網址。
