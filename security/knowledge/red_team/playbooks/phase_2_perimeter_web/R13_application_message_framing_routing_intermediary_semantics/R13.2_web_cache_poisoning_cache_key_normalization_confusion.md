# R13.2 網頁快取投毒與快取鍵正規化混淆機制分析 (Web Cache Poisoning via Cache-Key & Normalization Confusion)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**網頁快取投毒 (Web Cache Poisoning, WCP)** 發生於中繼快取（CDN/反向代理）與後端伺服器之間。其本質為：**「後端伺服器依賴了『未納入快取鍵計算的輸入 (Unkeyed Input)』生成頁面內容，攻擊者藉由操作該輸入，將惡意回應（XSS / 重導向 / 錯誤狀態）灌入共用快取層，導致所有合法造訪該網址的用戶全域受害」**。

```
[攻擊者] ── 1. 發送含未鍵值標頭請求 (X-Forwarded-Host: evil.com) ──► [CDN / 快取伺服器]
                                                                        │
                                             ┌──────────────────────────┴──────────────────────────┐
                                             ▼ (快取 MISS：計算標準 Cache Key: GET /index)         │
                                    [轉發至後端伺服器 (包含未鍵值標頭)]                                    │
                                             │                                                     │
                                             ▼ (後端動態引用生成: <script src="//evil.com/a.js">)   │
                                    [回傳帶毒內容並標記可快取]                                             │
                                             │                                                     │
                                             ▼                                                     ▼
                                    [快取伺服器將帶毒回應綁定至 Key: GET /index，快取 TTL=3600s] ◄┘
                                             │
[正常用戶] ── 2. GET /index (完全無惡意標頭) ┼──► 快取判定 HIT！直接吐出帶毒頁面
                                             ▼
                                    [瀏覽器載入 evil.com 腳本 ➔ Cookie 被竊]
```

### 核心作戰決策與邊界
- **必要前提**：端點必須被快取（`Cache-Control: public`），且後端引用了未鍵值輸入。
- **作戰紅線**：測試時**必須使用 Cache-Buster 參數**（如 `?cb=probe123`），嚴禁直接污染線上生產環境主頁！
- **技術邊界**：
  - **與快取欺騙 (Cache Deception) 差異**：投毒是「將攻擊者惡意資料灌入快取害別人」；欺騙是「誘騙快取儲存受害者個資讓攻擊者偷看」。

## 🔬 第一動：底層機制與快取鍵模型 (Vulnerability Mechanics & Normalization)

### 1. 鍵值輸入 (Keyed) vs. 未鍵值輸入 (Unkeyed)

| 輸入類別 | 常見代表項目 | 快取系統處理方式 | 安全風險 |
| :--- | :--- | :--- | :--- |
| **鍵值輸入 (Keyed)** | HTTP Method, Host, Path | 納入雜湊計算生成 Cache Key | 無法直接引發快取混淆 |
| **未鍵值輸入 (Unkeyed)** | `X-Forwarded-Host`, `User-Agent`, 協定標頭 | 被快取雜湊演算法完全忽略 | 後端若引用生成內容，極易導致快取投毒 |

### 2. 快取鍵正規化歧異 (Normalization Discrepancy)
- **URL 編碼時機不一致**：CDN 在計算 Key 時不解碼（保留 `%2f..%2f`），後端在路由時先解碼（解析為 `/admin`），導致管理頁面內容被快取在非預期路徑下。
- **尾端斜線處理不同**：CDN 視 `/user` 與 `/user/` 為不同 Key，後端自動重導向引發快取循環。

### 3. 快取投毒拒絕服務 (CPDoS)
- **HTTP Header Oversize (HHO)**：CDN 支援 16KB 標頭，後端僅支援 8KB。攻擊者發送 12KB 畸形標頭，後端拋出 `400 Bad Request`，該 400 錯誤被 CDN 快取，造成全站用戶無法存取。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式 | 關鍵標頭 / 參數 | 作用與突防原理 |
| :--- | :--- | :--- |
| **主機標頭覆寫** | `X-Forwarded-Host: attacker.com` | 後端生成靜態資源連結時引用，造成 Stored XSS。 |
| **協定覆寫** | `X-Forwarded-Proto: http` (向 HTTPS 發送) | 引發 `301 Moved Permanently` 循環重導向快取。 |
| **路徑覆寫標頭** | `X-Original-URL: /admin` 或 `X-Rewrite-URL` | 框架支援路徑覆寫，將管理頁面內容快取至首頁。 |
| **CPDoS 標頭溢位** | `X-Oversized: [8KB 大小字元]` | 誘導後端返回 400 錯誤並被持久快取。 |
| **Fat GET 參數混淆** | `GET /blog?id=1`（Body 夾帶 `id=2`） | 快取以 URL 的 `id=1` 儲存，後端以 Body 的 `id=2` 處理。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **參數隱蔽規避**：
  - 分號參數分隔符：`/page?v=1;evil=2`，快取視為單一參數，後端特定框架（Ruby/Python）自動解耦。
  - 非標標頭替換：`X-Forwarded-Server`、`X-Original-Host`。
- **鑑識與日誌特徵**：
  - **快取序列異動**：同一 URI 快速呈現 `MISS ➔ STORE ➔ HIT`，且 `STORE` 請求帶有異常轉發標頭。
  - **日誌與流量脫鉤**：前台受害請求量暴增，但後端 Access Log 完全看不到請求（全由 CDN HIT 處理）。
  - **狀態碼異常翻轉**：原本 200 的首頁突然持續回傳 400（CPDoS 特徵），且持續時間等同快取 TTL。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **未鍵值主機投毒** | CDN 存取日誌中出現外部 `X-Forwarded-Host` | 邊界強制剝離 (Strip) 所有公網傳入之轉發標頭 | 尋找未被列管之自訂中繼標頭 (`X-Host`) |
| **CPDoS 標頭癱瘓** | 監控系統告警靜態資源集中回傳 400 | **嚴禁快取任何 4xx / 5xx 狀態碼**；限制標頭上限 | 利用極端畸形字元觸發 500 內部錯誤 |
| **正規化混淆** | 存取 URL 包含異常 `%2f`、`%2e` 字符 | CDN 與後端實施一致的 URL 解碼標準化管線 | 尋找不同伺服器對路徑矩陣參數 (`;`) 歧異 |
| **靜態資源劫持** | JS/CSS 內容被修改為外部惡意來源 | 靜態資源由絕對路徑提供，禁止動態拼接網域 | 若框架預設啟用絕對路徑補全則仍有破綻 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Nginx 邊界剝離未鍵值標頭與禁止錯誤快取
```nginx
server {
    listen 443 ssl http2;
    server_name www.company.com;

    location / {
        proxy_cache my_cache;
        proxy_cache_key "$scheme$host$request_uri";

        # 1. 徹底禁止快取 4xx 與 5xx 錯誤（杜絕 CPDoS）
        proxy_cache_valid 200 302 10m;
        proxy_cache_valid 400 403 404 500 0s;

        # 2. 強制清空所有客戶端不可信標頭
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Host "";
        proxy_set_header X-Original-URL "";
        proxy_set_header X-Rewrite-URL "";

        proxy_pass http://backend_upstream;
    }
}
```

### 2. 後端代碼安全基線 (Python 範例)
```python
# 嚴格使用靜態設定宣告資產網域，禁止讀取 Request Headers
CANONICAL_DOMAIN = "https://www.company.com"

@app.route("/page")
def page():
    # 正確做法：資產網址寫死或基於配置生成
    asset = f"{CANONICAL_DOMAIN}/static/app.js"
    res = make_response(f'<script src="{asset}"></script>')
    res.headers["Cache-Control"] = "public, max-age=600"
    return res
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`cache_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

CACHE = {}

class CacheLabHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        url = self.path
        if url in CACHE: # 快取命中
            self.send_response(200)
            self.send_header("X-Cache", "HIT")
            self.end_headers()
            self.wfile.write(CACHE[url].encode())
            return

        # 模擬後端：引用未鍵值標頭 X-Forwarded-Host
        host = self.headers.get("X-Forwarded-Host", "trusted.internal")
        content = f'<html><script src="http://{host}/a.js"></script></html>'
        CACHE[url] = content # 寫入快取
        
        self.send_response(200)
        self.send_header("X-Cache", "MISS")
        self.end_headers()
        self.wfile.write(content.encode())

ThreadingHTTPServer(("127.0.0.1", 9141), CacheLabHandler).serve_forever()
```

### 2. 三步差分驗證流程

1. **獲取基準線 (Cache MISS)**：
   ```bash
   curl -i "http://127.0.0.1:9141/?cb=p1"
   # 回顯: X-Cache: MISS，載入 trusted.internal/a.js
   ```
2. **發送未鍵值投毒請求**：
   ```bash
   curl -i "http://127.0.0.1:9141/?cb=p2" -H "X-Forwarded-Host: evil.attacker.com"
   # 回顯: X-Cache: MISS，內容帶入 evil.attacker.com/a.js 並寫入快取
   ```
3. **驗證無辜用戶是否受害 (Cache HIT)**：
   ```bash
   curl -i "http://127.0.0.1:9141/?cb=p2"
   # 回顯: X-Cache: HIT，內容依然包含 evil.attacker.com/a.js，證實投毒成功！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是「未鍵值輸入 (Unkeyed Input)」？為何它是快取投毒的根本原因？**  
  *分析思路*：快取鍵僅由 Method、Host、Path 計算，而忽略未鍵值標頭（如 `X-Forwarded-Host`）。當後端引用未鍵值輸入生成回應時，該惡意回應會被快取在正常快取鍵中，引發全域投毒。

- [ ] **Q2. 滲透測試快取投毒時為何必須使用 Cache-Buster？**  
  *分析思路*：Cache-Buster（如 `?cb=123`）可確保測試只在隔離快取槽位中進行；直接在生產主頁測試一旦投毒成功，全網用戶皆會受害中斷業務。

- [ ] **Q3. 快取投毒 (WCP) 與快取欺騙 (WCD) 的本質差異為何？**  
  *分析思路*：WCP 是攻擊者把惡意內容塞入快取害其他人看；WCD 是攻擊者誘使快取儲存受害者的個人隱私資料，再由攻擊者去讀取。

- [ ] **Q4. CPDoS 的 HHO 攻擊如何癱瘓網站？**  
  *分析思路*：利用 CDN 支援大標頭（如 16KB）而後端只支援小標頭（如 8KB）的差異，發送超大標頭迫使後端回傳 400；若 CDN 快取 400，全站用戶存取皆報錯。

- [ ] **Q5. 徹底防範快取投毒的兩大黃金配置為何？**  
  *分析思路*：邊界代理強制剝離所有客戶端傳入之轉發標頭；快取伺服器配置**嚴格禁止快取 4xx / 5xx 錯誤狀態碼**。
