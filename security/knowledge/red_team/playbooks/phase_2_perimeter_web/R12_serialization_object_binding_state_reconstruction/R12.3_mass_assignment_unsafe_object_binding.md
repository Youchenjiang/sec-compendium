# R12.3 批量賦值與不安全物件綁定機制分析 (Mass Assignment & Unsafe Object Binding)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**批量賦值 (Mass Assignment / Model Binding)** 發生於 Web 框架（Spring Boot, ASP.NET, Rails, Laravel 等）自動將 HTTP 請求參數反射綁定至後端領域物件時。其本質為：**「應用程式未嚴格區分『用戶端可寫屬性』與『伺服器內部特權屬性』，直接將整包 HTTP 請求對映至 ORM 資料庫實體，攻擊者透過注入未公開的私有屬性（如 `role: "admin"`、`is_vip: true`），直接篡改持久化狀態實現特權提升」**。

```
[攻擊者] ── 1. PATCH /api/profile (含未授權欄位 role: admin) ──► [Web 控制器]
                                                                        │
                                                                        ▼ 呼叫模型自動綁定
                                                           [框架 DataBinder 引擎]
                                                                        │
                                                                        ├── 遍歷所有 JSON 鍵值
                                                                        ▼ 反射調用 setRole('admin')
                                                           [ORM 實體物件 (Entity)]
                                                                        │
                                                                        ▼ ORM 觸發 SQL UPDATE
                                                           [資料庫 (DB)] (權限提升持久化！)
```

### 核心作戰決策與邊界
- **常見場景**：註冊、個人資料更新、訂單建立、租戶設定。
- **作戰決策心流**：
  1. **屬性收集**：檢視 Swagger 文檔、前端 JS 打包檔或 GET 回傳之全量 JSON，提煉內部私有屬性清單。
  2. **欄位注入**：在普通請求中附帶特權鍵值（如 `"is_admin": true`）。
  3. **獨立讀回驗證**：**不可單憑當前請求回顯判定**！必須發送二次 `GET` 請求或執行特權操作，確認欄位真正落地資料庫。
- **技術邊界**：
  - **與反序列化 (R12.1) 差異**：批量賦值不依賴 Gadget Chain 與代碼執行，而是透過正規欄位賦值破壞商業資料完整性。

## 🔬 第一動：底層機制與框架自動綁定 (Mechanics & Reflection)

### 主流框架模型自動綁定特性速查表

| 框架 | 預設綁定機制 | 核心風險成因 | 推薦防禦架構 |
| :--- | :--- | :--- | :--- |
| **Spring MVC** | `WebDataBinder` / `BeanWrapper` | 控制器直接宣告 `@ModelAttribute User entity` | 使用專用 Request DTO，禁止直接綁定 JPA Entity |
| **ASP.NET Core** | `ComplexTypeModelBinder` | 動作方法宣告 `Task<IActionResult> Update(User user)` | 使用 `[Bind("name,email")]` 或專屬 ViewModel |
| **Ruby on Rails** | `ActiveRecord` 屬性賦值 | 未使用 Strong Parameters，直接 `User.update(params)` | 強制使用 `params.require(:user).permit(:name)` |
| **Laravel / PHP** | Eloquent `Model::create($req->all())` | Model 未配置 `$fillable` 白名單 | 強制定義 `$fillable`，禁止使用全開放 `$guarded = []` |

### 常用高危險屬性字典速查表

| 攻擊目標 (Tactic) | 典型注入鍵值對 (Candidate Payloads) | 業務影響 |
| :--- | :--- | :--- |
| **垂直越權提權** | `{"role": "admin"}`, `{"is_admin": true}`, `{"user_type": "superadmin"}` | 直接取得後台系統最高管理者身分 |
| **認證狀態繞過** | `{"is_verified": true}`, `{"email_verified": true}`, `{"mfa_enabled": false}` | 繞過郵件確認或多因子認證關卡 |

| **租戶跨界竊密** | `{"tenant_id": 1}`, `{"org_id": "root_corp"}`, `{"company_id": 0}` | 跨越多租戶邊界存取其他企業資料 |
| **安全標記清除** | `{"banned": false}`, `{"locked": false}`, `{"failed_attempts": 0}` | 解除帳號鎖定與封禁狀態 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **命名空間嵌套規避**：
  - 某些框架支援以點號存取嵌套物件：`{"profile.user.role": "admin"}` 或 `{"role.id": 1}`。
- **大小寫與底線混淆**：
  - 若 `is_admin` 被黑名單攔截，嘗試 `isAdmin`、`is_Admin`、`IsAdmin`（框架屬性映射器往往不區分大小寫）。
- **鑑識特徵**：
  - **日誌無報錯**：HTTP 請求合法，狀態碼回傳 `200 OK`，無常規攻擊特徵碼。
  - **資料庫審計日誌 (CDC)**：出現非正常介面允許修改的敏感欄位值變更記錄（如一般用戶修改資料時產生包含 `role='admin'` 的 SQL UPDATE）。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **注入特權屬性提權** | DB 審計發現普通 API 修改了 `role` 欄位 | 強制實施輸入 DTO 架構，阻斷所有未授權欄位 | 尋找未套用 DTO 的遺留舊版 API 端點 |
| **嵌套屬性注入** | 請求 Body 中包含點號標記語法 (如 `user.id`) | 停用框架的嵌套物件自動綁定功能 | 嘗試陣列索引形式注入 (`user[role]`) |
| **多租戶 ID 篡改** | 租戶存取日誌中出現 Cross-Tenant 記錄 | 租戶 ID 一律由伺服器 Session/Token 提取決定 | 尋找支援以 Header 覆寫租戶的次要模組 |
| **覆寫驗證狀態** | 新註冊帳戶無郵件驗證記錄直接變成已驗證 | 敏感狀態由狀態機驅動，嚴禁映射至公開端點 | 透過密碼重置端點進行二階批量賦值 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Spring Boot：徹底解耦 Controller 與 JPA Entity (DTO 模式)
```java
// 1. 定義安全輸入 DTO（僅暴露允許用戶修改的屬性）
public class UserUpdateDTO {
    private String displayName;
    private String bio;
    // 嚴格不提供 role, isVerified 等敏感屬性的 Setter！
    public String getDisplayName() { return displayName; }
    public void setDisplayName(String displayName) { this.displayName = displayName; }
}

// 2. 控制器嚴格接收 DTO，禁止直接宣告 User Entity
@PatchMapping("/profile")
public ResponseEntity updateProfile(@AuthenticationPrincipal User authUser, 
                                     @RequestBody UserUpdateDTO dto) {
    authUser.setDisplayName(dto.getDisplayName());
    userRepository.save(authUser);
    return ResponseEntity.ok().build();
}
```

### 2. Rails / Laravel：強型別白名單宣告
```ruby
# Rails Strong Parameters 白名單機制
def user_params
  params.require(:user).permit(:displayName, :bio) # 僅放行白名單欄位，其餘自動丟棄
end
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`mass_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import json

USER_DB = {"name": "Alice", "role": "user"}

class MassHandler(BaseHTTPRequestHandler):
    def do_PATCH(self):
        length = int(self.headers.get('Content-Length', 0))
        data = json.loads(self.rfile.read(length).decode())
        
        safe = "safe=1" in self.path
        if safe:
            # 安全防禦：僅提取允許白名單
            if "name" in data: USER_DB["name"] = data["name"]
        else:
            # 缺陷：直接以字典批量覆蓋物件
            USER_DB.update(data)
            
        self.send_response(200); self.end_headers()
        self.wfile.write(b"Profile updated\n")

    def do_GET(self):
        self.send_response(200); self.end_headers()
        self.wfile.write(json.dumps(USER_DB).encode() + b"\n")

ThreadingHTTPServer(("127.0.0.1", 8123), MassHandler).serve_forever()
```

### 2. 三步驗證流程

1. **發送批量賦值請求注入特權欄位**：
   ```bash
   curl -s -X PATCH "http://127.0.0.1:8123/" -d '{"name": "Alice", "role": "admin"}'
   ```
2. **獨立讀回驗證 (GET)**：
   ```bash
   curl -s "http://127.0.0.1:8123/"
   # 回顯: {"name": "Alice", "role": "admin"} ➔ 證實 role 已被篡改為 admin！
   ```
3. **驗證加固端點**：
   ```bash
   curl -s -X PATCH "http://127.0.0.1:8123/?safe=1" -d '{"role": "user"}'
   curl -s "http://127.0.0.1:8123/"
   # 檢查 role 依然維持原狀，加固生效！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 批量賦值 (Mass Assignment) 漏洞的本質危害是什麼？**  
  *分析思路*：框架自動將未經篩選的 HTTP 參數對映並寫入持久化資料庫實體中，讓攻擊者能篡改本不應由客戶端控制的特權屬性（如 `role`、`is_admin`、`balance`）。

- [ ] **Q2. 為什麼滲透測試驗證批量賦值時「不能單憑當前更新請求的回顯」判定成功？**  
  *分析思路*：許多 API 會單純回顯前端提交的 JSON 物件；只有透過獨立發起二次 `GET` 請求或執行高權限操作，才能證實該欄位真正被後端寫入資料庫生效。

- [ ] **Q3. 黑名單機制（如忽略 `role`、`admin`）為何無法徹底防範批量賦值？**  
  *分析思路*：黑名單無法預知未來資料庫新增的所有敏感欄位；且易遭框架命名空間嵌套（如 `user.role`）或大小寫混寫繞過。

- [ ] **Q4. 鑑識視角下，批量賦值攻擊為何難以透過傳統 WAF 偵測？**  
  *分析思路*：注入的載荷為完全合法的 JSON 結構與正規業務命名，無 SQL 注入、XSS 載荷或二進位特徵，流量特徵與正常更新操作無異。

- [ ] **Q5. 徹底防範批量賦值的黃金架構基線是什麼？**  
  *分析思路*：全面廢除 Controller 直接綁定 ORM Entity 的做法，強制引入專用的 Request DTO（Data Transfer Object），僅在 DTO 中定義白名單屬性。
