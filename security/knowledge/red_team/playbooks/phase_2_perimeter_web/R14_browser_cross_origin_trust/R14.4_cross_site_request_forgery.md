# R14.4 跨站請求偽造機制與防禦分析 (Cross-Site Request Forgery, CSRF)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**跨站請求偽造 (Cross-Site Request Forgery, CSRF)** 是利用瀏覽器「環境權限 (Ambient Authority)」機制的客戶端攻擊。其本質為：**「瀏覽器在向目標網域發起跨站 HTTP 請求時，會自動攜帶該網域已建立的認證憑證（Cookie / HTTP 認證）；攻擊者透過惡意第三方網站誘騙受害者瀏覽器發送特製請求，伺服器無法分辨該請求是否出自受害者的真實意願，從而盲目執行狀態變更操作（如轉帳、修改密碼、更換綁定郵箱）」**。

```
[攻擊者網站 (evil.com)] ── 1. 受害者瀏覽惡意網頁 (內嵌自動提交表單)
       │
       ▼ 2. 瀏覽器背景向 bank.com 發起跨站 POST /transfer
[受害者瀏覽器] ── 3. 自動附帶 bank.com 的 Session Cookie ──► [目標銀行伺服器 (bank.com)]
                                                                  │
                                                                  ▼ 4. 驗證 Cookie 合法 ➔ 執行轉帳！
                                                              [資料庫狀態變更 (轉帳完成)]
```

### 核心作戰決策與邊界
- **攻擊特性**：只管執行、無法讀取（One-way State Changing）。受同源政策 (SOP) 限制，攻擊者**無法讀取跨站回應內容**，只能單向盲目觸發狀態改變。
- **作戰決策心流**：
  1. **確認認證依據**：目標操作是否僅依賴 Cookie 識別身分？（若使用自訂 Header 如 `Authorization: Bearer <Token>` 則天然免疫傳統 CSRF）。
  2. **檢查 SameSite 屬性**：目標 Cookie 是否設定 `SameSite=Strict` 或 `Lax`？
  3. **評估防偽 Token**：是否存在 Anti-CSRF Token？Token 是否能被置空、替換或跨帳號重用？
- **技術邊界**：
  - **與 XSS (R14.1-R14.3) 差異**：XSS 能在目標 Origin 內執行任意代碼並讀取回應；CSRF 無法在目標網域執行 JS，僅能偽造非預期請求。

## 🔬 第一動：底層機制與瀏覽器隱含認證 (Mechanics & Ambient Authority)

### 現代瀏覽器 Cookie SameSite 行為對比速查表

| SameSite 設定值 | 跨站子請求 (img/iframe/ajax) | 頂層跨站跳轉 (Top-Level GET 導航) | 跨站 POST 表單提交 |
| :--- | :--- | :--- | :--- |
| **None** (需配 Secure) | 自動攜帶 Cookie | 自動攜帶 Cookie | 自動攜帶 Cookie（完全易受攻擊） |
| **Lax** (現代瀏覽器預設) | **不攜帶 Cookie** | **自動攜帶 Cookie** | **不攜帶 Cookie**（防禦常規 POST CSRF） |
| **Strict** | **不攜帶 Cookie** | **不攜帶 Cookie** | **不攜帶 Cookie**（最高安全級別） |

> **注意 (Lax-under-top-level 容錯)**：部分 Chromium 瀏覽器對未明確設定 SameSite 的新建立 Cookie，提供 2 分鐘的頂層跨站 POST 容錯視窗，可能被紅隊利用。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式與情境 | 典型 Payload / 利用方式 | 適用場景與繞過目標 |
| :--- | :--- | :--- |
| **GET 隱式請求** | `<img src="https://bank.com/api/transfer?to=attacker&amount=1000">` | 目標業務違規使用 GET 處理狀態變更 |
| **POST 表單自動提交** | `<form id="f" action="https://bank.com/profile" method="POST"><input name="email" value="pwn@evil.com"></form><script>f.submit()</script>` | 目標端點未配置 CSRF Token 且 Cookie 為 `SameSite=None` |
| **JSON CSRF 偽造** | `<form action="..." method="POST" enctype="text/plain"><input name='{"amount":1000,"dummy":"' value='"}'>` | 後端寬容接受 `text/plain` 格式的 JSON 請求 |
| **Token 置空繞過** | 攔截請求並刪除 `csrf_token` 參數發送 | 後端校驗邏輯存在「Token 為空時略過校驗」的缺陷 |
| **Token 池跨帳號重用** | 以攻擊者帳號產生的合法 Token 替換受害者的 Token | 後端僅驗證 Token 格式或全局有效性，未與 Session 綁定 |
| **雙重 Cookie 覆寫** | 利用同父網域下的 XSS 漏洞寫入 `cookie_csrf=attacker_token` | 繞過 Double Submit Cookie 防禦架構 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **Referer 標頭剝離規避**：
  - 攻擊者在惡意網頁中加入 `<meta name="referrer" content="no-referrer">`，迫使瀏覽器不發送 Referer 標頭，繞過依賴 Referer 存在的檢查邏輯。
- **Top-Level GET 鏈式跳轉**：
  - 目標 POST 端點受 `SameSite=Lax` 保護，但若後端存在可被覆寫 Method 的端點（如支援 `GET /action?_method=POST`），攻擊者透過頂層導航觸發 GET 請求達成繞過。
- **鑑識特徵**：
  - **Origin / Referer 異常**：POST/PUT 等狀態變更請求的 `Origin` 或 `Referer` 標頭指向非本組織網域（如 `https://evil-attacker.com`）。
  - **Sec-Fetch 標頭特徵**：請求帶有 `Sec-Fetch-Site: cross-site` 且 `Sec-Fetch-Mode: navigate`。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **跨站表單自動提交** | `Origin` 與 `Host` 網域不一致 | 啟用 Synchronizer Token；Cookie 設為 `SameSite=Lax` | 同網域存在 XSS 時可直接讀取並附帶 Token |
| **Referer 剝離跳轉** | 請求缺少 `Referer` 與 `Origin` 標頭 | 伺服器端若缺少安全標頭一律視為非法拒絕 | 某些企業代理會強制剝離 Referer 引發誤判 |
| **雙重 Cookie 偽造** | 請求中 Cookie 與 Header 數值相同 | Token 必須由伺服器端加密簽章 (HMAC) | 子網域遭接管時可能被寫入同名覆蓋 Cookie |
| **GET 狀態變更** | 靜態資源請求引發資料庫寫入操作 | 嚴格遵循 RFC，狀態變更**僅允許 POST/PUT/DELETE** | 前端採用預載機制 (Prefetch) 意外觸發操作 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Synchronizer Token Pattern (防偽權杖校驗)
```python
import hmac, hashlib, secrets

# 核心原則：CSRF Token 必須隨機、不可預測，且與當前用戶 Session 嚴格綁定
def generate_csrf_token(session_id: str, secret_key: str) -> str:
    nonce = secrets.token_hex(16)
    signature = hmac.new(secret_key.encode(), f"{session_id}:{nonce}".encode(), hashlib.sha256).hexdigest()
    return f"{nonce}:{signature}"

def validate_csrf_token(token: str, session_id: str, secret_key: str) -> bool:
    try:
        nonce, signature = token.split(":")
        expected = hmac.new(secret_key.encode(), f"{session_id}:{nonce}".encode(), hashlib.sha256).hexdigest()
        return hmac.compare_digest(signature, expected)
    except Exception:
        return False
```

### 2. Cookie 邊界與 SameSite 配置基線
```http
Set-Cookie: session_token=abc12345; Path=/; Secure; HttpOnly; SameSite=Lax
```

### 3. 基於 Sec-Fetch-Site 標頭的現代防護 (Fetch Metadata)
```python
def check_fetch_metadata(request_headers: dict) -> bool:
    sec_fetch_site = request_headers.get('Sec-Fetch-Site', '')
    # 阻斷所有跨站發起的狀態變更請求
    if sec_fetch_site in ('cross-site',):
        return False
    return True
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`csrf_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from urllib.parse import parse_qs

BALANCE = 1000

class CSRFHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        global BALANCE
        length = int(self.headers.get('Content-Length', 0))
        params = parse_qs(self.rfile.read(length).decode())
        
        safe = "safe=1" in self.path
        if safe:
            # 安全防禦：校驗自訂標頭與 Origin
            if self.headers.get("Origin") != "http://127.0.0.1:8144":
                self.send_response(403); self.end_headers(); self.wfile.write(b"CSRF Blocked"); return

        amount = int(params.get('amount', [0])[0])
        BALANCE -= amount
        self.send_response(200); self.end_headers()
        self.wfile.write(f"Transferred. New Balance: {BALANCE}\n".encode())

    def do_GET(self):
        self.send_response(200); self.send_header("Set-Cookie", "auth=admin; SameSite=None; Secure")
        self.end_headers()
        self.wfile.write(f"Current Balance: {BALANCE}\n".encode())

ThreadingHTTPServer(("127.0.0.1", 8144), CSRFHandler).serve_forever()
```

### 2. 三步驗證流程

1. **取得受害者工作階段**：
   ```bash
   curl -i -s "http://127.0.0.1:8144/"
   # 回顯: Current Balance: 1000
   ```
2. **跨站偽造 POST 轉帳請求 (攻擊者視角)**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8144/" -H "Origin: http://evil-attacker.site" -d "amount=200"
   # 回顯: Transferred. New Balance: 800 (證實非同源偽造請求被執行！)
   ```
3. **驗證加固端點**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8144/?safe=1" -H "Origin: http://evil-attacker.site" -d "amount=200"
   # 回顯: CSRF Blocked，成功防護！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼 CSRF 攻擊無法讓攻擊者直接讀取使用者的銀行帳戶餘額？**  
  *分析思路*：瀏覽器的同源政策 (SOP) 限制跨源讀取回應內容；CSRF 僅能利用瀏覽器自動帶憑證的特性觸發目標伺服器執行寫入操作，但無法將伺服器的回應內容回傳給攻擊者。

- [ ] **Q2. `SameSite=Lax` 預設防禦策略在面對何種場景時會失效？**  
  *分析思路*：`SameSite=Lax` 僅對跨站子請求（如 POST 表單或 AJAX）阻斷 Cookie，但在頂層 GET 跳轉（如 `<a href="...">` 或 302 重導向）時依然會自動攜帶 Cookie；若目標敏感操作錯誤使用 GET 處理，防禦將直接失效。

- [ ] **Q3. 什麼是「雙重 Cookie 驗證 (Double Submit Cookie)」？其最大弱點是什麼？**  
  *分析思路*：伺服器在 Cookie 與請求參數/標頭中各放置一份相同數值的 Token，比對兩者是否一致。弱點在於若目標的同源或子網域存在任何 XSS 或 Cookie 注入漏洞，攻擊者可覆寫受害者的 Cookie，從而使惡意偽造的 Token 通過校驗。

- [ ] **Q4. 現代前端以 JWT 置於 `Authorization: Bearer <Token>` 標頭傳輸，為何能天然免疫 CSRF？**  
  *分析思路*：瀏覽器在發送跨站請求時，只會自動攜帶 Cookie 與 HTTP 基礎認證，**絕不會自動附帶自訂的 `Authorization` 標頭**；自訂標頭必須由前端 JS 手動賦值，而跨站第三方頁面無法以 JS 存取受害網域的 LocalStorage。

- [ ] **Q5. 防範 CSRF 最健全的縱深防禦基線包含哪些要素？**  
  *分析思路*：
  1. 敏感狀態操作強制要求隨機且與 Session 綁定的 Synchronizer Token；
  2. 關鍵 Cookie 強制啟用 `SameSite=Lax` 或 `Strict`；
  3. 伺服器端校驗 `Origin` / `Referer` 與現代 `Sec-Fetch-Site` 標頭；
  4. 狀態變更絕不允許使用 GET 方法。
