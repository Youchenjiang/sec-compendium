# R09.4 功能層級存取控制失效與垂直越權 (Function-Level Authorization Bypass)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**功能層級存取控制失效 (Broken Function Level Authorization, BFLA / 垂直越權)** 的物理成因在於**系統將「前端介面隱藏 (UI Obfuscation)」誤當作「後端存取控制 (Server-side Enforcement)」**。現代單頁應用 (SPA) 與微服務常透過前端判斷動態隱藏管理員按鈕；然而，當低權限或未授權使用者直接向後端發送特權 API 呼叫（如 `/api/v1/admin/users/delete`）時，後端中介層若未在路由或控制器層級強制校驗主體之角色 (Role) 與權限 (Permission)，將導致普通使用者直接執行最高管理員特權功能。

```
[低權限普通使用者 (Role: User)] ── 透過分析前端 JavaScript Bundle 逆向出管理員端點
                                                │
                                                ▼ 直接發送特權呼叫: POST /api/admin/system/reboot
[前端 UI 邊界 (無法防禦)] ──────────────────────► 繞過前端「隱藏管理選單」之假性安全
                                                │
                                                ▼ 抵達後端 API 路由控制器
[授權中介層 (Middleware)] ─────────────────────► 【關鍵缺陷】僅校驗 Token 合法，未校驗 Role == Admin！
                                                │
                                                ▼ 執行特權業務邏輯
[全系統完全垂直接管] ──────────────────────────► 成功執行系統重啟、資料庫備份倒出、新增管理員帳號！
```

## 🔬 第一動：功能授權架構與路由守衛物理機制 (Mechanics & Access Control)

### 1. 垂直越權常見成因與架構脆弱點

| 脆弱架構模式 | 漏洞觸發機制 | 攻擊利用物理條件 |
| :--- | :--- | :--- |
| **前端偽安全 (Client-Only)** | 僅在前端 Vue/React 依據 `user.role` 隱藏 DOM 元件 | 後端 API 缺乏 `@PreAuthorize` 守衛，直接曝露端點 |
| **HTTP 動詞轉換瑕疵** | 中介層僅對 `POST /admin/config` 進行管理員攔截 | 攻擊者改用 `GET`、`PUT` 或 `PATCH` 繞過過濾器鏈 |
| **路由模式比對不一致** | WAF 或中介層配置 `/admin/*`，忽略了 `/admin` 或 `/admin/` | 利用路徑結尾斜線或參數綴詞 (Trailing Slash) 繞過比對 |
| **反向代理偽標頭信任** | 內部微服務信任 `X-Role: Admin` 標頭 | 攻擊者於外部 HTTP 請求中直接注入該標頭並穿透邊界 |

    -H "X-Authenticated-User: root" \
    -H "X-User-Role: SuperAdmin"

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **預設拒絕原則 (Default Deny Architecture)**：
   - 路由守衛應預設封閉所有端點；僅針對顯式標註 `@PermitAll` 的端點開放，其餘一律強制要求身分與指定角色權限。
2. **聲明式宣告伺服器端守衛 (Declarative Access Control)**：
   - 在控制器與方法層強制執行宣告式鑑權，切勿僅依賴邊界路徑正規匹配：
     ```java
     // 安全: Spring Security 方法級強制校驗
     @PreAuthorize("hasRole('ROLE_SUPERADMIN')")
     @PostMapping("/api/admin/users/purge")
     public ResponseEntity<?> purgeUsers() { ... }
     ```
3. **內部網格信任標頭清洗 (Header Sanitization)**：
   - 邊界反向代理 (Nginx / Envoy) **必須強制移除**客戶端傳入的所有敏感內部標頭（如 `X-User-Role`, `X-Account-Type`），避免標頭偽造注入。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡垂直越權脆弱端點 (Python Flask, 20 行)
```python
# app.py
from flask import Flask, request, jsonify

app = Flask(__name__)

@app.route("/api/admin/reset_db", methods=["POST"])
def reset_db():
    # 脆弱點：僅檢查是否具備授權標頭，但未校驗是否為 admin 權限！
    auth_header = request.headers.get("Authorization")
    if not auth_header:
        return jsonify({"error": "missing token"}), 401
    
    # 後端誤認前端已隱藏此按鈕，故不再檢查 role，直接執行敏感管理操作
    return jsonify({
        "status": "success",
        "action": "database_wiped",
        "flag": "FLAG{BFLA_VERTICAL_ESCALATION_PWNED}"
    })

if __name__ == "__main__":
    app.run(port=8888)
```

### 2. 三步作戰驗證流程
```bash
# 步驟 1: 啟動靶機
python3 app.py

# 步驟 2: 低權限使用者持普通 Token 直接向管理端點發起 POST 調用
curl -X POST http://127.0.0.1:8888/api/admin/reset_db \
    -H "Authorization: Bearer valid_low_priv_user_token"
# 驗證輸出：{"action":"database_wiped","flag":"FLAG{BFLA_VERTICAL_ESCALATION_PWNED}","status":"success"}

# 步驟 3: 驗證修復（後端補上 role 判斷: if decode(token).get("role") != "admin": return 403）
# 驗證輸出：返回 403 Forbidden，垂直越權被成功阻絕
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：為何即使前端單頁應用程式 (SPA) 代碼經過 Uglify / Webpack 混淆，仍無法抵擋 BFLA 偵察？**
  - **戰術思維**：編譯混淆主要針對變數名與函數名，但所有發送 HTTP 請求的 **API 路徑字串 (如 `"/api/v1/admin/delete"` )** 依然以純明文字元常數存在於 JS Bundle 之中，透過正則搜尋或自動化爬取工具即可 100% 提取。
- [ ] **Q2：何謂 HTTP 請求動詞覆寫 (HTTP Method Override)，其如何破壞功能授權？**
  - **戰術思維**：許多框架支援透過 `X-HTTP-Method-Override: DELETE` 標頭或 `_method=DELETE` 參數將原本的 `POST` 請求重寫為 `DELETE`。若授權過濾器僅對原生 `DELETE` 方法設定管理員保護，攻擊者可改用 `POST` 傳入覆寫標頭繞過檢查。
- [ ] **Q3：在 Spring Security 中，`antMatchers("/admin/**")` 與 `regexMatchers` 有何常見設定疏漏？**
  - **戰術思維**：若規則配置為 `/admin/*`，只會保護一級子路徑，而不會保護多級深層路徑 `/admin/users/delete`；此外若缺少結尾斜線比對，可能因路徑語意不一致導致特定 URL 脫離保護鏈路。
- [ ] **Q4：微服務架構中，若邊界 Gateway 與內部微服務由不同團隊維護，最常引發何種 BFLA 問題？**
  - **戰術思維**：邊界團隊認為微服務內部會進行 RBAC 角色判定，而微服務團隊則認為「既然請求能通過 Gateway 就代表是合法的」，雙方責任邊界割裂導致「零防禦真空 (Authorization Gap)」。
- [ ] **Q5：若管理員端點被配置為「僅限特定 IP 存取」，紅隊有何嘗試突破之戰術手法？**
  - **戰術思維**：測試中間代理信任缺陷，偽造客戶端來源標頭（如 `X-Forwarded-For: 127.0.0.1`、`X-Real-IP: 10.0.0.1`），或利用應用程式本身的 SSRF 弱點由內部本機代為發起請求。
