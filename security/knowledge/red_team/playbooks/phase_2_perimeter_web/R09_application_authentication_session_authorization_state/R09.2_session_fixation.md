# R09.2 應用程式會話固定與預先綁定劫持 (Session Fixation)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**會話固定 (Session Fixation)** 的物理本質為**應用程式未在身分特權狀態變更 (Authentication State Transition) 時重置會話識別碼 (Session Token)**。攻擊者預先自伺服器獲取或主動生成一個合法的「匿名會話識別碼 (Known Session ID)」，透過特定載體將其植入受害者的瀏覽器；當受害者隨後成功完成登入時，伺服器直接將已驗證的使用者身分綁定至該預設會話上，攻擊者即可持手中已知的識別碼直接接管該帳號。

```
[攻擊者] ── 1. 預先建立匿名 Session (SID: 0xDEADBEEF)
    │
    ▼ 2. 誘騙受害者點擊帶有固定 SID 之連結 / 透過子網域 Cookie Tossing 植入
[受害者瀏覽器] ── 3. 攜帶 SID: 0xDEADBEEF 訪問應用系統
    │
    ▼ 4. 受害者輸入個人帳號密碼成功登入
[應用認證伺服器] ── 5. 【關鍵缺陷】未輪替 SID！直接將登入權限授權給 0xDEADBEEF！
    │
    ▼ 6. 攻擊者持 0xDEADBEEF 發起業務請求
[帳號完全接管] ──► 攻擊者直接繼承受害者的已登入身分與權限！
```

## 🔬 第一動：會話固定時序與植入載體物理機制 (Mechanics & Injection Carriers)

### 1. 攻擊時序與載體矩陣

| 植入載體 | 傳遞機制 | 成功前提條件 | 防禦阻斷難度 |
| :--- | :--- | :--- | :--- |
| **URL 參數傳遞** | `https://target/login?sessionid=ATTACKER_ID` | 應用程式啟用 URL 傳遞 Session (如 PHP `use_trans_sid`) | 低 (停用 URL Session 即阻斷) |
| **CRLF 標頭注入** | 透過 HTTP Response Splitting 注入 `Set-Cookie: sessionid=...` | 存在未過濾換行符號之重新導向端點 | 中 (需修復輸入過濾) |
| **子網域 Cookie 拋擲** | 在攻陷之 `blog.corp.com` 寫入 `Domain=.corp.com; Path=/` | 應用程式 Cookie 未綁定嚴格主機名 | 高 (受瀏覽器 Cookie 覆蓋規則制約) |
| **XSS 惡意寫入** | 透過 DOM XSS 執行 `document.cookie="sessionid=..."` | Session Cookie 未設定 `HttpOnly` 標誌 | 高 (依賴 XSS 防禦能力) |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **認證成功後強制輪替 Session ID (Mandatory Session Rotation)**：
   - 使用者登入成功時，**必須**銷毀舊有 Session ID 並生成全新 Token：
     ```php
     // PHP 原生修復
     session_regenerate_id(true); // 傳入 true 以刪除舊的 Session 儲存檔案
     ```
2. **完全禁止從 URL 參數接受 Session 識別碼**：
   - 伺服器配置中強制禁用 URL Session (例如 PHP `ini_set('session.use_only_cookies', 1)`)。
3. **Cookie 安全屬性強制約束**：
   - 全面附加 `HttpOnly`（阻斷 XSS 讀取與寫入）、`Secure`（僅允許 HTTPS）、`SameSite=Lax/Strict`（阻斷第三方跨站傳遞）。
4. **客戶端指紋與連線綁定 (Fingerprint Binding)**：
   - 在 Session 中綁定客戶端初始 IP 網段與 User-Agent Hash，當關鍵屬性劇變時強制終止會話。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡會話固定脆弱端點 (Python Flask, 20 行)
```python
# app.py
from flask import Flask, request, jsonify, make_response
import uuid

app = Flask(__name__)
sessions = {}  # 記憶體 Session 儲存：sid -> username

@app.route("/login", methods=["POST"])
def login():
    # 脆弱點：若客戶端提供 Cookie 則直接復用，未在認證時生成新 sid！
    sid = request.cookies.get("session_id") or str(uuid.uuid4())
    username = request.json.get("username")
    sessions[sid] = username  # 授權已存在的 sid
    resp = make_response(jsonify({"status": "ok", "user": username}))
    resp.set_cookie("session_id", sid)
    return resp

@app.route("/profile")
def profile():
    sid = request.cookies.get("session_id")
    user = sessions.get(sid)
    if user:
        return jsonify({"status": "authorized", "user": user, "flag": "FLAG{SESSION_FIXATION_PWNED}"})
    return jsonify({"error": "unauthorized"}), 401

if __name__ == "__main__":
    app.run(port=8888)
```

### 2. 三步作戰驗證流程

# 驗證輸出：{"flag":"FLAG{SESSION_FIXATION_PWNED}","status":"authorized","user":"victim_boss"}

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：Session Fixation 與 Session Hijacking (會話劫持) 的物理分水嶺為何？**
  - **戰術思維**：會話劫持 (Hijacking) 是在使用者登入**之後**，透過竊聽、日誌洩漏或 XSS 偷取伺服器所簽發之合法 Token；會話固定 (Fixation) 是在使用者登入**之前**，由攻擊者預設一個 Token 並強迫受害者使用，使其在登入後被「點石成金」合法化。
- [ ] **Q2：若目標已啟用 HTTPS 且 Cookie 具備 `Secure` 屬性，同網域 HTTP 能否覆寫 Cookie？**
  - **戰術思維**：歷史上部分瀏覽器允許未加密的 HTTP 回應寫入同名 Cookie（即便該 Cookie 原本具備 Secure 標籤）。現代瀏覽器已引入 **Cookie Prefixes (`__Secure-` / `__Host-`)** 機制，禁止不安全來源覆寫安全 Cookie。
- [ ] **Q3：在跨站腳本 (XSS) 存在的情況下，`HttpOnly` 能否阻斷會話固定？**
  - **戰術思維**：雖然 `HttpOnly` 可以防止 JavaScript「讀取」Cookie，但在部分瀏覽器實作中，若攻擊者透過 `document.cookie = "SID=fixed"` 寫入同名 Cookie，可能產生覆蓋或重複 Header，仍有機會觸發固定攻擊。
- [ ] **Q4：微服務使用 JWT 時，是否還存在 Session Fixation 的風險？**
  - **戰術思維**：無狀態 JWT 通常由伺服器在登入成功後於 HTTP Response Body 傳回，並由客戶端主動儲存於 LocalStorage 或替換 Header，天生不依賴由客戶端預先提供的會話標籤，因此經典會話固定在標準 JWT 架構中極罕見。
- [ ] **Q5：現代框架（如 Spring Security、Django）預設採取何種機制杜絕此威脅？**
  - **戰術思維**：預設啟用 `migrateSession` 或 `newSession` 策略，即在認證成功之單一動作內，強制廢棄舊 Session 物件，並在底層自動調用 `changeSessionId()` 產生全新識別碼，從工程根本杜絕固定問題。
