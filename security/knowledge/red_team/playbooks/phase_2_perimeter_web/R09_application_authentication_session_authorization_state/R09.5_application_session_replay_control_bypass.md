# R09.5 應用程式會話重放控制繞過 (Application Session Replay-Control Bypass)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**應用程式會話重放控制繞過 (Session Replay-Control Bypass)** 的物理本質為**安全關鍵憑據（如密碼重設 Token、一次性密碼 OTP、OAuth 授權碼或交易憑證）缺乏嚴格的「單次消耗 (Single-Use)」保證或「時效新鮮度 (Freshness)」限制**。當後端服務未以原子性操作作廢已使用過之憑據，或在分散式叢集節點間存在快取同步延遲時，攻擊者可透過攔截、重播或並行重放同一憑據，達成未授權存取或重複執行關鍵業務操作。

```
[使用者完成身分認證/交易] ── 產生一次性憑證 (Token: 0x9A4F, TTL: 5min)
                                        │
                                        ▼ [第 1 次使用: 合法請求抵達節點 A]
[分散式節點 A] ────────────────────────► 驗證成功，並向非同步快取發出「標記已作廢」訊息
                                        │
                                        ▼ 【物理競態/重放時間差 (Replay Window)】
[攻擊者重放請求 (持 Token: 0x9A4F)] ──► 發送第 2 次請求至節點 B
                                        │
                                        ▼ [節點 B 本地快取尚未同步作廢狀態！]
[授權重放校驗通過] ─────────────────────► 再次執行特權動作 (如重複修改管理員密碼、重複兌領資金)！
```

## 🔬 第一動：重放防護架構與狀態同步物理機制 (Mechanics & Freshness Controls)

### 1. 重放防禦控制要素矩陣

| 控制要素 | 物理實作機制 | 脆弱性來源 | 攻擊破局路徑 |
| :--- | :--- | :--- | :--- |
| **隨機數 (Nonce)** | 伺服器要求每次請求攜帶全域唯一隨機字串 | Nonce 存於客戶端且未在伺服器記錄消耗狀態 | 重複提交相同 Nonce 或偽造隨機數 |
| **時戳 (Timestamp)** | 請求簽章包含伺服器時間，限制有效視窗 (如 60s) | 伺服器時鐘容許偏移過大 (Clock Skew > 10min) | 在容許時窗內密集重播請求 |
| **單次憑據 (One-Time)**| 密碼重設或驗證碼使用後立即作廢 | 非同步快取或無狀態架構未即時落盤寫入 | 於叢集同步完成前發起微秒級並行重放 |
| **Token 綁定** | Token 與當前 TCP/TLS 或 IP/User-Agent 綁定 | 僅單純校驗字串，缺乏通道綁定 (Channel Binding)| 竊取 Token 後直接於遠端重播 |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **原子性憑據消耗 (Atomic Consumption)**：
   - 驗證與作廢必須在單一資料庫交易內完成，利用行鎖 (Row Lock) 確保單次性：
     ```sql
     -- 安全: 原子性鎖定並立即標記已使用
     UPDATE tokens SET used = 1, used_at = NOW() WHERE token_id = :tid AND used = 0;
     -- 若影響行數 (rows affected) 為 0，立即拒絕該次請求
     ```
2. **分散式 Nonce 快取 (Redis SETNX)**：
   - 伺服器接收到 Nonce 後，調用 `SET nonce_value 1 EX 60 NX`。若 Key 已存在則直接拒絕。
3. **嚴格 RFC 6749 OAuth 2.0 實作**：
   - Authorization Code 兌換一次即強制作廢；若伺服器偵測到同一個 Code 被嘗試使用第二次，**必須立即吊銷先前以此 Code 簽發之所有 Access/Refresh Tokens**！

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡重放漏洞靶機端點 (Python Flask, 20 行)
```python
# app.py
from flask import Flask, request, jsonify

app = Flask(__name__)
# 模擬重設密碼 Token 資料庫
reset_tokens = {"valid_reset_token_123": {"user": "admin", "consumed": False}}

@app.route("/api/reset", methods=["POST"])
def reset():
    token = request.json.get("token")
    record = reset_tokens.get(token)
    if not record:
        return jsonify({"error": "invalid token"}), 400
    
    # 脆弱點：驗證成功後未將 consumed 設為 True，允許無限次重放修改密碼！
    return jsonify({
        "status": "password_reset_success",
        "user": record["user"],
        "flag": "FLAG{SESSION_REPLAY_CONTROL_BYPASS_PWNED}"
    })

if __name__ == "__main__":
    app.run(port=8888)
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：OAuth 2.0 規範 (RFC 6749) 對於重放的 Authorization Code 有何嚴厲反制要求？**
  - **戰術思維**：規範明確規定，若授權伺服器發現同一個 Authorization Code 被嘗試使用超過一次，伺服器**必須視為嚴重入侵事件，不僅拒絕本次請求，更必須立即撤銷該 Code 先前已兌換出的所有 Access Token 與 Refresh Token**。
- [ ] **Q2：為何在金融交易 API 中，僅在請求中加上時間戳 (Timestamp) 仍不足以抵禦重放？**
  - **戰術思維**：時間戳只能證明「請求何時產生」，但只要在伺服器允許的容錯視窗（例如 30 秒或 60 秒）內，攻擊者若攔截到該請求並迅速發起 10 次重放，10 次請求皆落在有效時間內。因此必須搭配 **全域唯一隨機數 (Nonce)** 才能徹底抵禦重放。
- [ ] **Q3：在分散式無狀態架構中，若多個 API 伺服器各自持有本機快取，會引發何種重放攻擊？**
  - **戰術思維**：若沒有使用如 Redis 等集中式共用快取或資料庫行鎖，攻擊者可將同一個 One-Time Token 並行打到背後的 Node 1 與 Node 2，兩台主機在各自本機記憶體檢查時均判定 Token 尚未被使用，造成雙重消耗 (Double Spending)。
- [ ] **Q4：簡訊驗證碼 (SMS OTP) 的有效時間若設為 10 分鐘，紅隊有何組合利用策略？**
  - **戰術思維**：10 分鐘的超長視窗給予了紅隊充裕的攻擊時間。結合缺乏頻率限制 (Rate Limiting)，紅隊可在這 10 分鐘內對 4 位數或 6 位數純數字驗證碼發動暴力猜測與重放測試。
- [ ] **Q5：現代 TLS 1.3 協定中的 0-RTT (Early Data) 為何容易引入應用層重放風險？**
  - **戰術思維**：TLS 1.3 的 0-RTT 允許客戶端在握手完成前直接發送應用層資料以加速連線；然而 0-RTT 資料缺乏前向保密與防重放保證，若被中間人攔截，伺服器可能重複執行非冪等的 HTTP 請求（如轉帳）。
