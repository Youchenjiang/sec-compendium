# R09.1 應用程式會話狀態偽造與校驗繞過 (Application Session-State Forgery & Validation Bypass)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**應用程式會話狀態偽造與校驗繞過 (Session-State Forgery)** 的核心在於**無狀態 (Stateless) 憑證之密碼學簽章邊界崩潰**。當現代 Web 與微服務架構採用 JSON Web Token (JWT) 或客戶端簽章 Cookie 儲存授權狀態時，若驗證邏輯存在「演算法混淆 (Algorithm Confusion)」、「未驗證簽名 (None Algorithm)」、「密鑰暴力破解 (Weak Secret)」或「金鑰識別碼注入 (JKU/KID Injection)」，攻擊者即可在未持有私鑰之情況下偽造任意身分宣告 (Claims)，實現全系統身分偽裝。

```
[原始合法憑證] ── JWT: {"alg": "RS256", "typ": "JWT"}.{"user": "alice", "role": "user"}.[Sig]
                        │
                        ▼ [紅隊發起演算法混淆或簽名剝離攻擊]
┌───────────────────────┴───────────────────────────────────────┐
│ 向量 A: 演算法混淆 ── 將 alg 改為 HS256，以公開發布之公鑰作為 HMAC 密鑰計算簽名 │
│ 向量 B: 空演算法 ──── 將 alg 改為 "none"，直接剝離簽名區段 (Signature Stripping) │
│ 向量 C: KID/JKU 注入 ─ 在 Header 注入攻擊者受控之公開金鑰 URL (jwks.json)       │
└───────────────────────┬───────────────────────────────────────┘
                        ▼
[應用程式鑑權中介層 (Middleware)] ── 信任偽造 Header 且未校驗演算法一致性
                        │
                        ▼ 驗證通過！解析 Claims: {"user": "admin", "role": "superadmin"}
[核心業務邏輯] ────────► 完全以最高特權身分執行機密操作！
```

## 🔬 第一動：JWT 密碼學結構與簽章驗證物理原理 (Mechanics & Cryptographic Flow)

### 1. JWT 結構與校驗弱點維度

| 欄位區段 | 物理結構 | 弱點機制 | 攻擊利用手法 |
| :--- | :--- | :--- | :--- |
| **Header** | `Base64URL({"alg":"...","typ":"JWT"})` | 未強制比對預期演算法 | 改為 `"none"` 或非對稱轉對稱演算法 (`RS256` 轉 `HS256`) |
| **Payload** | `Base64URL({"sub":"...","role":"..."})` | 明文可見、無機密性保證 | 篡改 `role: "admin"`、`tenant_id: 1` 提升權限 |
| **Signature** | `HMACSHA256(H + "." + P, secret)` | 依賴後端金鑰強度與驗證函數 | 若後端僅調用 `jwt.decode(verify=False)` 則簽章形同虛設 |
| **Key Injection**| `Header: {"jku": "https://...", "kid": "..."}` | 信任客戶端傳入之外部金鑰伺服器 | 導向攻擊者受控 JWKS 或以路徑穿越注入已知字串 |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **嚴格白名單演算法綁定**：在解碼函式中顯式指定允許的演算法（如僅允許 `algorithms=["RS256"]`），絕不在執行期信任 Token Header 中的 `alg` 宣告。
2. **高強度密鑰存儲與長度要求**：HMAC 對稱密鑰必須具備至少 256 位元熵（Entropy），並自安全金鑰管理系統 (KMS) 載入，杜絕寫死於代碼。
3. **金鑰來源白名單化 (JWKS Pinning)**：禁止載入客戶端自訂之 `jku` 或 `x5u`；所有公開金鑰必須從伺服器內部固定配置的端點取得。
4. **過期時間強制驗證 (Strict Lifetime Validation)**：強制校驗 `exp` (Expiration Time) 與 `nbf` (Not Before)，並設定時鐘偏移容許值 (Clock Skew) 不得超過 60 秒。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 JWT 脆弱驗證端點 (Python Flask + PyJWT, 20 行)
```python
# app.py
from flask import Flask, request, jsonify
import jwt

app = Flask(__name__)
SECRET_KEY = "weaksecret"  # 脆弱點 1: 弱密鑰容易被暴力破解

@app.route("/api/admin")
def admin_data():
    token = request.headers.get("Authorization", "").replace("Bearer ", "")
    try:
        # 脆弱點 2: 允許任意演算法，缺乏顯式白名單演算法綁定
        payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256", "none"], options={"verify_signature": True})
        if payload.get("role") == "admin":
            return jsonify({"status": "access_granted", "flag": "FLAG{JWT_ALG_CONFUSION_PWNED}"})
        return jsonify({"status": "denied", "msg": "User role insufficient"}), 403
    except Exception as e:
        return jsonify({"error": str(e)}), 401

if __name__ == "__main__":
    app.run(port=8888)
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：JWT 演算法混淆攻擊 (Algorithm Confusion) 的物理核心條件是什麼？**
  - **戰術思維**：後端原本期望使用非對稱加密 (`RS256`)，但解碼函數直接讀取 Header 的 `alg`；若攻擊者改為 `HS256`，後端會錯誤地將伺服器的「RSA 公鑰」當作「HMAC 對稱密鑰」進行簽章驗證。由於公鑰在網路上完全公開，攻擊者即可拿該公鑰作為金鑰簽發任意 Token。
- [ ] **Q2：為何在部分框架中，剝離第三段 Signature 仍能成功通過驗證？**
  - **戰術思維**：部分早期函式庫在實作時，若檢測到簽名為空字串，會直接跳過密碼學校驗邏輯，並直接解碼 Payload 回傳資料，此即為著名的「簽名剝離 (Signature Stripping)」漏洞。
- [ ] **Q3：在微服務架構中，內部服務間傳遞的 JWT 若不驗證簽名，會引發何種攻擊？**
  - **戰術思維**：若內部微服務誤以為「邊界 API Gateway 已經驗證過 JWT」而在內部調用時省略簽名驗證，一旦邊界 Gateway 存在解析瑕疵，或攻擊者突破任意一個內部節點，即可橫向漫遊偽造任意身分。
- [ ] **Q4：KID (Key ID) 參數除了路徑穿越外，還有何種高階利用手法？**
  - **戰術思維**：若後端使用 SQL 查詢資料庫提取對應 KID 的金鑰（如 `SELECT key FROM keys WHERE kid = '$kid'`），若未過濾 KID 則會觸發 **SQL 注入**，攻擊者可透過 `UNION SELECT 'known_secret'` 將已知密鑰注入驗證邏輯。
- [ ] **Q5：JWT 的「無狀態」特性在使用者登出與權限被撤銷時會帶來何種安全挑戰？**
  - **戰術思維**：因無伺服器端狀態，除非引入全域黑名單 (Token Revocation List / Redis) 或縮短 `exp` 壽命搭配 Refresh Token，否則即使使用者已修改密碼或登出，已簽發的 JWT 在過期前將永遠有效。
