# R09.3 物件層級存取控制失效與水平越權 (Object-Level Authorization Bypass)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**物件層級存取控制失效 (Broken Object Level Authorization, BOLA / IDOR)** 的物理本質為**應用程式資料存取層 (Data Access Layer) 割裂了「身分鑑權 (Authentication)」與「資料所有權驗證 (Authorization)」的邊界**。後端伺服器在確認請求者持有有效 Session/Token 後，直接採信客戶端請求中所提供的「物件識別碼 (Object ID)」，未校驗當前操作主體是否具備該目標物件的存取權益，導致同權限使用者間的「水平越權 (Horizontal Escalation)」或跨租戶 (Multi-tenant) 資料外洩。

```
[合法使用者 Alice (Token: Valid)] ── 請求查看自身合約: GET /api/contract/1001
                                                │
                                                ▼ 伺服器驗證 Alice 身分合法 ➔ 回傳合約 1001
[Alice 惡意篡改物件 ID] ─────────────► 請求查看他人合約: GET /api/contract/1002
                                                │
                                                ▼ [後端代碼: Contract.findById(req.params.id)]
[資料存取層 (DAL)] ────────────────────────────► 【關鍵缺陷】僅校驗 ID 是否存在，未比對 owner_id！
                                                │
                                                ▼ 資料庫執行 SELECT * FROM contracts WHERE id = 1002
[資料洩漏與越權篡改] ──────────────────────────► Alice 成功獲取 Bob 或競業之機密合約資料！
```

## 🔬 第一動：物件識別碼傳遞與授權鏈路物理架構 (Mechanics & Access Control)

### 1. IDOR 脆弱架構 vs 安全架構對照表

| 架構維度 | 脆弱實作架構 (Vulnerable) | 安全工程架構 (Hardened) |
| :--- | :--- | :--- |
| **資料庫查詢條件** | `SELECT * FROM orders WHERE id = :id` | `SELECT * FROM orders WHERE id = :id AND user_id = :current_user` |
| **物件識別碼形態** | 自增長連續整數 (`1001, 1002, 1003`) | 密碼學隨機 UUIDv4 或加鹽間接參考映射表 (Indirect Reference Map) |
| **API 端點設計** | `/api/user_data?account_id=99` | `/api/me/user_data` (識別碼由伺服器 Session 自動注入) |
| **權限判斷位置** | 僅於邊界 Gateway 檢查 Token 是否過期 | 於 Domain Service / Repository 層強制執行基於屬性的存取控制 (ABAC) |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **資料存取層強制約束主體邊界 (Context Enforced Scoping)**：
   - 杜絕僅透過單一主鍵 ID 查詢；強制附加當前認證主體之身分約束：
     ```python
     # 安全: 強制附加 owner_id 限制
     document = db.session.query(Document).filter_by(id=doc_id, owner_id=current_user.id).first_or_404()
     ```
2. **採用不可預測之隨機識別碼 (UUIDv4)**：
   - 全面棄用自動遞增連續整數 (Auto-increment IDs)，降低被盲目遍歷枚舉之風險。
3. **實作間接參考映射表 (Indirect Reference Maps)**：
   - 在會話中建立隨機映射表（例如前端僅可見 `id="A8F1"`，由後端 Session 映射至真實 DB 主鍵 `1002`），攻擊者無法藉由推測 ID 發起水平越權。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 IDOR 脆弱端點靶機 (Python Flask, 20 行)
```python
# app.py
from flask import Flask, request, jsonify

app = Flask(__name__)
# 模擬資料庫合約資料表 (id, owner, content)
contracts = {
    "101": {"owner": "alice", "data": "Alice public profile"},
    "102": {"owner": "bob", "data": "FLAG{BOLA_OBJECT_LEVEL_BYPASS_CONFIRMED}"}
}

@app.route("/api/contract/<cid>")
def get_contract(cid):
    auth_user = request.headers.get("X-User", "guest")
    # 脆弱點：僅檢查是否有傳入帳號，但未檢查 auth_user 是否等於 contract['owner']！
    record = contracts.get(cid)
    if not record:
        return jsonify({"error": "not found"}), 404
    return jsonify({"contract_id": cid, "content": record["data"]})

if __name__ == "__main__":
    app.run(port=8888)
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：將連續整數 ID 改為 UUIDv4 是否就能徹底防範 BOLA/IDOR？**
  - **戰術思維**：**不能**。UUID 僅能增加「猜測難度」，但無法提供「授權校驗」。若 UUID 透過其他 API 洩漏（如公開使用者清單、分享連結、日誌或 Referer），攻擊者只要拿到該 UUID 依然可直接存取他人資源。真正的核心防禦在於伺服器端資料庫層的擁有權比對。
- [ ] **Q2：何謂垂直越權 (Vertical Escalation) 與水平越權 (Horizontal Escalation) 的本質差異？**
  - **戰術思維**：水平越權（如 BOLA）發生在**同等級角色**之間（普通使用者 A 存取普通使用者 B 的私有資料）；垂直越權（如 BFLA）發生在**不同特權階級**之間（普通使用者直接調用管理員特權 API，如刪除資料庫）。
- [ ] **Q3：在微服務架構中，GraphQL API 為何更容易爆發 BOLA 漏洞？**
  - **戰術思維**：GraphQL 允許客戶端自由組合查詢圖譜 (Graph Traversal)。開發者往往僅在根查詢節點 (Root Query) 做權限驗證，卻忽略了子解析器 (Child Resolvers) 於巢狀關係節點上深層載入關聯物件時的權限校驗。
- [ ] **Q4：在批次更新或多筆處理端點中，IDOR 通常以何種形式出現？**
  - **戰術思維**：在如 `/api/invoices/batch_pay` 端點傳入陣列 `[101, 102, 103]`。後端往往只驗證第一筆資料的歸屬權，在遍歷後續 ID 時卻直接批次更新，造成批次越權操作。
- [ ] **Q5：若 API 遵循 RESTful 設計為 `/api/v1/users/{user_id}/orders/{order_id}`，應防範何種常見瑕疵？**
  - **戰術思維**：防範後端實作時「僅驗證了 `{user_id}` 等於當前使用者，但在查詢 orders 時僅執行了 `SELECT * FROM orders WHERE id = order_id`」，導致 `{order_id}` 根本不屬於該 `{user_id}` 仍被成功讀取。
