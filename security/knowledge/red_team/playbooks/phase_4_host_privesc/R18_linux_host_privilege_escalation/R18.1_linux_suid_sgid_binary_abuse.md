# R18.1 Linux SUID/SGID 特權二進位與 GTFOBins 濫用 (SUID Privilege Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**Linux SUID/SGID 特權二進位濫用** 的物理本質為**利用 Linux 檔案系統特殊權限位元組（Set-UID 4000），當普通使用者執行該程式時，進程會自動繼承檔案擁有者（通常為 `root`）的有效使用者識別碼 (EUID 0)**。在紅隊實戰中，若系統管理員或安裝的軟體錯誤地為具備 Shell 執行、檔案讀寫或直譯器功能的二進位檔案設置了 SUID 位元，低權限攻擊者即可直接打破作業系統安全邊界，在不需任何密碼的情況下將權限直接提升為最高特權 `root`。

```
[取得低特權本機 Shell: uid=1001(user)] ── 搜尋具備 SUID/SGID 屬性之全系統檔案
                                               │
                                               ▼ 執行權限過濾與 GTFOBins 特徵匹配
┌──────────────────────────────────────────────┴──────────────────────────────────────────────┐
│ 1. 系統預設合規 SUID: /usr/bin/passwd, /usr/bin/sudo, /usr/bin/newgrp (常規安全二進位)     │
│ 2. 非預期配置或自定義 SUID: find, bash, cp, vim, python, nmap, env, awk, base64            │
│ 3. 檢查檔案可執行權限與參數機制: 驗證是否支援 -exec, --eval, 交互 Shell 或直接讀寫 /etc/shadow │
└──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                               ▼
[匹配到可逃逸特權二進位 (如: find / cp)] ─────────► 調用特權子進程或覆寫特權系統檔案
                                               │
                                               ▼ 執行 /bin/sh -p 繼承 EUID 0
[獲取系統至高無上特權: euid=0(root)] ───────────► 成功完成本機立足點垂直權限提升！
```

## 🔬 第一動：底層權限模型、EUID 繼承與 SUID 物理架構 (Mechanics & EUID Structs)

### 1. POSIX 憑證三元組與核心進程權限

在 Linux 核心中，每個進程的 `task_struct->cred` 包含三組關鍵 UID：
- **RUID (Real UID)**：發起該進程的真實使用者 ID（如普通帳號 `uid=1001`）。
- **EUID (Effective UID)**：核心決定進程是否有權存取檔案或發起 Syscall 的主要依據。
- **SUID (Saved UID)**：保存的特權位元，用於進程暫時降權後的特權復原。

```
標準檔案權限八進制:
├── 04000 (Set-UID / SUID) : 執行時 EUID 被替換為檔案 Owner UID (0 = root)
├── 02000 (Set-GID / SGID) : 執行時 EGID 被替換為檔案 Group GID
└── 01000 (Sticky Bit)     : 僅擁有者或 root 可刪除該目錄內檔案 (/tmp)
```

當一個可執行檔具備 `-rwsr-xr-x` 屬性且屬於 `root` 時，任何使用者執行該檔案，核心呼叫 `execve()` 都會將該進程的 `euid` 設為 `0`。若該程式支援子命令衍生且未在呼叫前主動放棄特權（如未調用 `setuid(getuid())`），攻擊者便能直接衍生出特權 Shell。

### 2. GTFOBins 經典二進位檔案提權語義對照表
| 目標二進位檔 | 提權武器化指令 | 突防打擊原理 |
| :--- | :--- | :--- |
| **`find`** | `find . -exec /bin/sh -p \; -quit` | 利用 `-exec` 參數在特權進程內直接執行 `/bin/sh -p` |
| **`bash`** | `bash -p` | 攜帶 `-p` 參數強制保留 SUID 有效使用者身分不降權 |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **掛載點全面啟用 `nosuid` 標記**：
   - 對所有允許使用者上傳或可寫入的分區（如 `/tmp`, `/var/tmp`, `/home`, `/dev/shm`），在 `/etc/fstab` 中強制添加 `nosuid` 掛載選項。
2. **最小化 SUID 檔案分佈基準**：
   - 定期審計全盤 SUID 檔案；對非必要包含 SUID 的常規工具（如 `vim`, `find`, `nmap` 等），執行 `chmod u-s <path>` 拔除特權。

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：Linux 核心中 RUID、EUID 與 SUID 在執行 SUID 檔案時如何變化？**
  - **戰術思維**：RUID 保持為發起使用者的 ID，而 EUID 被替換為檔案擁有者（root，UID 0）。核心在進行權限校驗時是以 EUID 為準，因此進程具備 root 權限。
- [ ] **Q2：為何在現代 Linux 系統中執行自編的 SUID Shell 腳本常無法提權？**
  - **戰術思維**：現代 Linux 核心（如 Ubuntu/Debian）會在執行 `#!` 解釋型 Shell 腳本時強制忽略 SUID 位元，以防止環境變數注入與競態條件漏洞；SUID 僅對編譯後的 ELF 二進位檔生效。
- [ ] **Q3：在執行 `bash -p` 時，`-p` 參數的具體底層作用為何？**
  - **戰術思維**：Bash 在啟動時若發現 EUID != RUID，預設會主動將 EUID 重設為 RUID（自動降權以保護系統）；帶上 `-p` 參數可強制告知 Bash 保留 EUID 不進行降權。
- [ ] **Q4：若發現 `/usr/bin/cp` 具有 SUID 權限，如何不透過 Shell 直接提權？**
  - **戰術思維**：可利用特權 `cp` 將 `/etc/shadow` 或 `/etc/passwd` 讀取並覆寫，直接在 `/etc/passwd` 末尾寫入一個具有 `root:0:0` 特權且無密碼的新帳號。
- [ ] **Q5：如何在全系統維運中自動化阻斷非預期 SUID 提權向量？**
  - **戰術思維**：在 `/etc/fstab` 中為使用者目錄與暫存目錄配置 `nosuid`，並部署 AIDE 或 Tripwire 對全盤 `/bin`, `/usr/bin` 建立定期校驗雜湊基準線。
