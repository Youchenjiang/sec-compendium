# R10.2 作業系統命令與 Shell 解譯器語法注入 (OS Command & Shell Injection)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**作業系統命令注入 (OS Command Injection)** 的物理成因在於**應用程式未嚴格隔離資料流與指令解譯器環境**。當高階語言調用底層作業系統介面時，若透過 Shell（如 `/bin/sh -c` 或 `cmd.exe /c`）動態拼接未過濾之不可信參數，Shell 詞法分析器將解譯字元（Metacharacters）識別為控制邏輯，導致攻擊者能夠脫離原定程式碼邏輯，於主機系統上執行任意作業系統層級之子行程 (Subprocess)。

```
[客戶端未過濾字串輸入] ── 127.0.0.1; cat /etc/passwd
                                │
                                ▼ [後端代碼: os.system("ping -c 1 " + ip)]
[Shell 剖析引擎 (sh/cmd)] ─────► 識別到分號 (;) 或管線符 (|) 中斷原始命令語義
                                │
                                ▼ 解析生成兩個獨立執行單元
┌───────────────────────────────┴───────────────────────────────┐
│ [命令單元 1]: /bin/ping -c 1 127.0.0.1 (原定合法功能)          │
│ [命令單元 2]: cat /etc/passwd (注入之惡意子行程指令)           │
└───────────────────────────────┬───────────────────────────────┘
                                ▼
[核心行程呼叫 (execve/CreateProcess)] ──► 惡意指令於 Web 服務帳號權限下完全執行！
```

## 🔬 第一動：Shell 詞法解析機制與分離子行程原理 (Mechanics & Shell Parser)

### 1. POSIX 與 Windows 解譯器控制元 (Metacharacters) 矩陣

| 控制符 | 解析語意 | 執行條件 | 典型利用場景 |
| :--- | :--- | :--- | :--- |
| `;` / `&` | 順序串聯 / 背景執行 | 不論前項成敗接續執行 (Windows 僅支援 `&`) | `input=10.0.0.1; whoami` |
| `&&` | 邏輯與 (AND) | 僅在前項回傳狀態碼為 `0` (成功) 時執行 | `input=127.0.0.1 && id` |
| `\|\|` | 邏輯或 (OR) | 僅在前項回傳狀態碼為非 `0` (失敗) 時執行 | `input=invalid_ip || id` |
| `\|` | 標準輸出管線 (Pipe) | 將前項標準輸出導向前項標準輸入 | `input=127.0.0.1 \| cat /etc/shadow` |
| `` `cmd` `` / `$()` | 指令替換 (Command Substitution) | 優先於主指令執行，並將輸出結果作為引數帶入 | `input=$(cat /flag.txt)` |
| `>` / `<` | 重定向 (Redirection) | 輸出入資料流覆寫或讀取 | `input=1 > /tmp/pwned` |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **嚴禁使用 Shell 中介包裝 (No Shell Execution)**：
   - 使用陣列傳參取代字串拼裝，並顯式關閉 Shell：
     ```python
     # 安全: 直接調用二進位檔案，argv 陣列傳遞，shell=False
     subprocess.run(["/usr/bin/ping", "-c", "1", user_ip], shell=False)
     ```
2. **輸入白名單嚴格驗證**：IP 或主機名稱應使用型態驗證庫 (如 Python `ipaddress.ip_address`) 進行正規化檢查，拒絕任何非預期字符。
3. **作業系統層級最小化沙箱 (Sandboxing)**：
   - 啟用 **AppArmor / SELinux** 限制 Web Daemon 禁止執行 `/bin/sh` 或 `/bin/bash`。
   - 容器化環境全面啟用唯讀根檔案系統 (`readOnlyRootFilesystem: true`) 與 Drop All Capabilities。

### 1. 極簡命令注入靶機 (Python Flask, 20 行)
```python
# app.py
from flask import Flask, request, jsonify
import subprocess

app = Flask(__name__)

@app.route("/api/ping")
def ping_host():
    target = request.args.get("target", "127.0.0.1")
    # 脆弱點：直接啟用 shell=True 並拼接字串
    cmd = f"ping -c 1 {target}"
    try:
        out = subprocess.check_output(cmd, shell=True, stderr=subprocess.STDOUT, timeout=5)
        return jsonify({"stdout": out.decode(errors="ignore")})
    except Exception as e:
        return jsonify({"error": str(e)}), 500

if __name__ == "__main__":
    app.run(port=8888)
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：當後端程式碼使用 Java `Runtime.getRuntime().exec(String command)` 時，注入 `; whoami` 為何常常失敗？**
  - **戰術思維**：Java `exec(String)` 預設使用 `StringTokenizer` 依空白分割引數，並透過 `ProcessBuilder` 直接呼叫底層系統 API，**並未啟動 Shell (如 `/bin/sh`)**。因此 `;` 僅被視為合法引數之一部分而非 Shell 控制元。欲破局需後端顯式傳入 `sh -c` 或存在引數注入 (Argument Injection)。
- [ ] **Q2：若目標系統完全封鎖 Outbound 網路且無任何命令輸出回顯，如何確認命令注入成功？**
  - **戰術思維**：利用**時間盲注 (Time-based Blind)**，注入延遲指令如 `; sleep 10` 或 `; ping -c 10 127.0.0.1`。若 HTTP 回應延遲精確增加 10 秒，即可 100% 證明指令成功執行。
- [ ] **Q3：何謂引數注入 (Argument Injection)，其與命令注入之本質差異為何？**
  - **戰術思維**：命令注入是脫離原指令執行全新命令；引數注入是在**未啟用 Shell 的安全呼叫下**，攻擊者輸入以 `-` 或 `--` 開頭之字串被解析為原指令的危險參數（如 `tar --checkpoint-action=exec=sh` 或 `ssh -o ProxyCommand=...`），進而達成 RCE。
- [ ] **Q4：在 Windows 環境中，`%COMSPEC%` 與 `powershell.exe` 在解析換行符號時有何利用差異？**
  - **戰術思維**：`cmd.exe` 無法直接透過換行字元 `%0a` 串聯命令，通常需依賴 `&`；而 PowerShell 與 Linux Bash 則將換行字元視為獨立語句結束符，可規避僅過濾 `&` 與 `;` 之簡單防禦過濾器。
- [ ] **Q5：為何在 Bash 中輸入 `IFS=,;cmd='cat,/etc/passwd';$cmd` 可以完全杜絕空白字元？**
  - **戰術思維**：Bash 依賴環境變數 `$IFS` 決定單詞邊界 (Word Splitting)。將其覆寫為逗號 `,` 後，直譯器遇到逗號即視同空白分割，可完美穿透任何以正則過濾空白之 WAF。
