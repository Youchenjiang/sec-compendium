# R07.6 Kerberos 認證票證離線偽造與黃金票證 (Golden Ticket)

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**黃金票證 (Golden Ticket / TGT 偽造)** 的物理本質為**利用 Active Directory 核心服務帳號 `krbtgt` 的密鑰材料，於本機離線偽造並簽署具備全網任意特權的 Kerberos 認證票證 (TGT)**。由於 KDC 在發放與驗證 TGT 時，全權仰賴 `krbtgt` 的密鑰進行票證加密與特權屬性憑證 (PAC) 簽署；一旦攻擊者透過 DCSync 或備份還原獲取 `krbtgt` 的 NTLM 雜湊或 AES-256 金鑰，即可**完全脫離網域控制站 (DC)**，在離線端任意宣告主體身分、偽造高達數十年的超長有效期限，並注入 Enterprise Admins 等頂級群組 SID，達成物理級的終極網域持久化。

```

                                        │
                                        ▼ 轉移至外部離線環境
[攻擊者離線控制台] ───────────────────── 1. 呼叫 ticketer.py / Mimikatz golden
                                        │
                                        ▼ 2. 本地偽造 PAC 並以 krbtgt 金鑰完成雙重簽章
[生成偽造之 Golden Ticket] ────────────► (可自訂身分: Administrator, 有效期: 10 年)
                                        │
                                        ▼ 3. 持偽造 TGT 向 KDC 請求任意服務票證 (TGS)
[網域控制站 KDC (TCP 88)] ─────────────► 【完美驗證】KDC 使用本地 krbtgt 金鑰解密，確認合法！
                                        │
                                        ▼
[全網域永久幽靈後門] ──────────────────► 即使全網使用者變更密碼，黃金票證依然永恆有效！
```

## 🔬 第一動：krbtgt 密鑰角色與 PAC 雙重簽署物理機制 (Mechanics & PAC Signatures)

### 1. PAC 簽章結構與黃金票證構造維度

| 結構區段 | 物理簽署金鑰 | 作用與驗證機制 | 偽造控制要點 |
| :--- | :--- | :--- | :--- |
| **TGT enc-part** | `krbtgt` 帳號密鑰 | 加密 Client/Server Session Key 與主要身分宣告 | 必須持有正確之 `krbtgt` NTLM 或 AES256 金鑰 |
| **Server Signature** | `krbtgt` 帳號密鑰 (TGT 階段) | 保護 PAC 內容完整性，防止客戶端竄改 | 離線計算 HMAC-MD5 或 HMAC-SHA1 填入 |
| **KDC Signature** | `krbtgt` 帳號密鑰 | 防止未授權主體偽造 PAC 授權屬性 | 離線計算 KDC 簽名填入 |
| **Group SIDs (PAC)** | 明文嵌入於 PAC 結構 | 宣告該使用者所屬之全部群組權限 | **直接注入 512 (Domain Admins)、519 (Enterprise Admins)** |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **實施 krbtgt 帳號密碼雙重輪替計畫 (Dual krbtgt Reset)**：
   - 由於 Active Directory 保留兩組 `krbtgt` 密碼歷史；當發生嚴重洩漏時，**必須間隔數小時連續重置兩次 krbtgt 密碼**，才能徹底將所有已偽造之黃金票證強制失效。
2. **部署 Microsoft Defender for Identity (MDI)**：
   - MDI 具備深度記憶體與網路封包檢查能力，能精確比對 PAC 簽署時點與網域歷史，即時識別離線生成的偽造票證。
3. **特權存取工作站 (PAW) 與 Tier-0 嚴格隔離**：
   - 阻斷網域控制站對外網路連線，防止 DCSync 攻擊發起，從源頭守護 `krbtgt` 密鑰安全。

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：為何即使全網域所有管理員更換密碼，黃金票證 (Golden Ticket) 依然有效？**
  - **戰術思維**：因為 TGT 票證是使用網域核心帳號 **`krbtgt`** 的密鑰進行加密與簽章；使用者本人的密碼變更完全不會改變 `krbtgt` 的金鑰，因此 KDC 依舊能成功解密並信任該 TGT。
- [ ] **Q2：為何應對黃金票證威脅時，必須「連續兩次」重置 `krbtgt` 帳號密碼？**
  - **戰術思維**：Active Directory 為了保證進行中的 Kerberos 票證不中斷，預設會保留上一版本的 `krbtgt` 金鑰作為歷史快取。只重置一次時，攻擊者持舊金鑰偽造的票證依然能被接受；必須重置第二次才能徹底沖刷掉舊金鑰。
- [ ] **Q3：何謂鑽石票證 (Diamond Ticket)，其相比黃金票證在隱蔽性上有何飛躍？**
  - **戰術思維**：黃金票證是「純離線生成」，缺乏先前的 AS-REQ 紀錄；鑽石票證則是**先向 KDC 發送合法的 AS-REQ 取得真實 TGT，再用 krbtgt 金鑰解密並在記憶體中修改 PAC 權限後重新加密**，完美補齊了 AS 請求事件鏈。
- [ ] **Q4：在鍛造黃金票證時，若將有效期限設為 10 年，會帶來何種嚴重鑑識風險？**
  - **戰術思維**：現代 EDR 與 SIEM 均部署了針對異常票證有效期的靜態規則；一旦發現 TGT 結束時間與起始時間差距超過 10 小時，會立刻觸發「高可信度黃金票證利用」最高警報。
- [ ] **Q5：使用 AES-256 相比 NTLM 鍛造黃金票證有何優勢？**
  - **戰術思維**：微軟官方於近期更新中加強了對 Kerberos 加密協定的審計；若環境中大多使用 AES，但突然出現 RC4 加密的 TGT 申請特權服務，會引發強烈的密碼降級警報。
