# R07.5 Kerberos 服務票證重放與目標資源劫持 (Service-Ticket Replay)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**Kerberos 服務票證重放 (Service-Ticket Replay / TGS Replay)** 的物理本質為**利用 Kerberos 在服務存取階段 (AP Exchange / AP-REQ)「目標應用伺服器與 KDC 完全不需即時聯網驗證」的解耦設計**。當使用者已取得針對特定服務主體（如 `cifs/fileserver` 或 `http/portal`）的服務票證 (TGS) 後，該票證是由目標服務之密碼金鑰加密。只要攻擊者自本機記憶體或網路流量中攔截到該 TGS 票證與對應的 Session Key，即可直接向目標應用伺服器重播發起 AP-REQ，**完全繞過網域控制站 (DC) 審計且在 KDC 離線狀態下依然能成功建立存取會話**。

```
[攻擊者自已攻陷主機萃取有效 TGS] ── 取得針對 cifs/fileserver.corp 之服務票證
                                            │
                                            ▼ 【關鍵物理特性: 繞過 KDC】
[攻擊者直連目標應用伺服器 (Port 445)] ◄───── 1. 直連目標主機發送 KRB_AP_REQ (Ticket + Authenticator)
                                            │
                                            ▼ 2. 目標主機以本機服務金鑰直接解密 Ticket
[目標應用伺服器 (fileserver)] ─────────────► 【驗證成功】目標主機無需向 DC 詢問票證真偽！
                                            │
                                            ▼ 3. 建立特權 SMB 會話
[資源劫持與機密外洩] ──────────────────────► 攻擊者直接讀取機密共享目錄或執行檔案操作！
```

## 🔬 第一動：AP-REQ 握手機制與重放快取物理特性 (Mechanics & AP Exchange)

### 1. AP-REQ 與驗證器 (Authenticator) 結構

| 欄位組件 | 加密金鑰 | 作用與驗證機制 | 重放防護設計與繞過 |
| :--- | :--- | :--- | :--- |
| **Ticket (TGS)** | 目標服務金鑰 (Service Key) | 包含 PAC、使用者身分與 Client/Server Session Key | 只要在票證壽命內（預設 10 小時），目標伺服器皆認可 |
| **Authenticator** | Client/Server Session Key | 包含客戶端產生的即時時間戳與 Nonce | 目標伺服器檢查時鐘偏差（通常允許 ±5 分鐘） |
| **Replay Cache** | 目標主機本地記憶體 | 記錄最近 5 分鐘內已接收過之 Authenticator 雜湊 | 若伺服器停用快取或重播時間未重疊，防護失效 |

### 1. 服務票證重放特徵消減表

| 規避面向 | 原始觸發特徵 | 變形隱蔽手法 | 原理解析 |
| :--- | :--- | :--- | :--- |
| **DC 稽核留存** | 請求 TGS 產生 Event 4769 | 直接重播已存在的既有服務票證 | **網域控制站 (DC) 日誌中零記錄 (Zero Footprint)** |
| **重放快取碰撞** | 同一 Authenticator 被目標伺服器判定重複 | 重新利用 Session Key 封裝生成全新時間戳之 Authenticator | 避開目標伺服器之本機 Replay Cache 攔截 |
| **帳號狀態變更** | 使用者帳號已被網域管理員停用 (Disabled) | 在 TGS 票證過期前直接重放 | 目標服務不向 DC 查詢即時狀態，停用帳號仍可通行！ |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **強制啟用目標端 Kerberos Replay Cache**：
   - 確保所有 Windows 伺服器之 Kerberos 子系統啟用本機 Authenticator 快取，嚴格丟棄 5 分鐘內完全相同的重放封包。
2. **啟用 SMB 簽署 (SMB Signing) 與通道繫結**：
   - 強制全網伺服器要求 SMB 封包簽章，防止中間人攔截並轉發 TGS 票證。
3. **縮減服務票證存活期 (Service Ticket Lifetime)**：
   - 針對高敏感服務（如財務系統、資料庫），將其 TGS 有效時間配置為 1 小時以內，壓縮票證被竊取後的重放視窗。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 AP-REQ 票證重放校驗模擬腳本 (Python, 20 行)
```python
# ap_req_validator.py
import time

replay_cache = set()  # 本機記憶體重放快取: 記錄 (client_name, timestamp)

def process_ap_req(client_name, auth_timestamp):
    current_time = int(time.time())
    # 檢查時鐘偏差 (允許 ±300 秒)
    if abs(current_time - auth_timestamp) > 300:
        return "REJECT: KRB_AP_ERR_SKEW (時鐘偏差過大)"
    
    # 檢查是否於快取中碰撞 (防重放核心)
    cache_key = (client_name, auth_timestamp)
    if cache_key in replay_cache:
        return "REJECT: KRB_AP_ERR_REPEAT (偵測到重複票證重放！)"
    
    replay_cache.add(cache_key)
    return "SUCCESS: AP-REQ 驗證通過，建立服務連線"

# 模擬測試
t = int(time.time())
print(process_ap_req("admin@corp", t))      # 首次存取
print(process_ap_req("admin@corp", t))      # 攻擊者惡意重放
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：重放 TGS 服務票證時，為何目標伺服器不需要連線網域控制站 (DC)？**
  - **戰術思維**：因為 TGS 票證在當初由 KDC 發放時，就已經使用**該目標服務帳號自身的密碼金鑰**進行了加密；目標伺服器只需用自己的私鑰即可成功解密並驗證 PAC，整個過程完全本機化。
- [ ] **Q2：若目標使用者已被網域管理員在 AD 中停用或刪除，已簽發的 TGS 為何仍能成功重放？**
  - **戰術思維**：由於 AP-REQ 階段不與 DC 進行任何連線，目標伺服器無法得知該帳號在 AD 中的即時狀態，只要票證在有效時間內且簽名正確，目標伺服器依然會無條件放行。
- [ ] **Q3：何謂 Kerberos Replay Cache 的核心防護原理與侷限？**
  - **戰術思維**：Replay Cache 會記錄 Authenticator 中的時間戳與隨機數；其侷限在於若攻擊者竊取到了 Client/Server Session Key，攻擊者可自行構造包含「全新當前時間戳」的合法 Authenticator 繞過快取碰撞。
- [ ] **Q4：TGS 服務票證重放與 Silver Ticket (白銀票證) 的本質差異為何？**
  - **戰術思維**：TGS 重放是**偷取並重播由 KDC 正式簽發的真實票證**；白銀票證則是攻擊者在攻陷服務帳號雜湊後，**完全在本地端自行偽造簽發的虛假票證**。
- [ ] **Q5：藍隊 SIEM 如何透過日誌關聯分析獵捕 TGS 異常重放行為？**
  - **戰術思維**：比對「目標應用伺服器上的 Event 4624 登入事件」與「網域控制站上的 Event 4769 票證發放事件」；若應用端出現登入，但 DC 在近期完全沒有對應 SPN 的發證紀錄，即為顯著重放跡象。
