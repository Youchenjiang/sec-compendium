# R07.1 Kerberos AS-REP 雜湊材料收割 (AS-REP Roast Material Acquisition)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**AS-REP 雜湊材料收割 (AS-REP Roasting)** 的物理本質為**利用使用者帳號未啟用「Kerberos 預先認證 (Pre-Authentication)」之配置瑕疵**。在標準 Kerberos 流程中，用戶端向 KDC 申請 TGT (AS-REQ) 時必須以自身密碼金鑰加密當前時間戳 (PA-ENC-TIMESTAMP) 以證明身分。若某帳號設定了 `DONT_REQ_PREAUTH` (不要求 Kerberos 預先驗證)，**任何未經認證的外部攻擊者皆可直接向 KDC 請求該帳號的 AS-REP 票證**。KDC 回傳的 AS-REP 加密區段 (`enc-part`) 是由該目標帳號的密碼金鑰加密而成，攻擊者即可將此材料下載至離線環境進行無限制密碼破解。

```
[未認證之外部攻擊者] ── 發送無預先認證之 AS-REQ (KRB_AS_REQ) ──► [網域控制站 KDC (TCP/UDP 88)]
                                                                    │
                                                                    ▼ 檢查 LDAP userAccountControl
                                                        [命中 DONT_REQ_PREAUTH 旗標！]
                                                                    │
                                                                    ▼ 略過身分驗證，直接生成 AS-REP
[攻擊者控制台] ◄── KDC 回傳 KRB_AS_REP (含由使用者密碼加密之 enc-part) ┘
      │
      ▼ 提取密文轉換為 Hashcat 格式 ($krb5asrep$23$...)
[離線 GPU 叢集] ──► 實施極速字典暴力破解，零告警還原目標明文密碼！
```

## 🔬 第一動：預先認證機制與 AS-REP 加密層物理結構 (Mechanics & Pre-Auth Flow)

### 1. 預先認證通訊差異對照表

| 通訊階段 | 預設安全流程 (Pre-Auth Enabled) | AS-REP Roast 脆弱流程 (Pre-Auth Disabled) |
| :--- | :--- | :--- |
| **AS-REQ (PA-DATA)** | 包含以使用者密碼金鑰加密的時間戳 (`PA-ENC-TIMESTAMP`) | **無任何 PA-DATA 驗證材料** (完全未認證) |
| **KDC 校驗邏輯** | 解密時間戳並比對時鐘（容錯 5 分鐘） | 檢查 `userAccountControl` 具備 `0x4194304` 旗標直接放行 |
| **AS-REP 內容** | 回傳 TGT 與以使用者金鑰加密之 Session Key (`enc-part`) | 同樣回傳 TGT 與以使用者金鑰加密之 `enc-part` |
| **防禦能見度** | 需先具備帳號密碼才能獲取封包 | **全網任一訪客皆可匿名批次拉取全網特定帳號之密文** |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **全面強制啟用 Kerberos 預先認證**：
   - 透過 PowerShell 定期清查網域內所有帳號，移除 `DONT_REQ_PREAUTH` 旗標：
     ```powershell
     # 安全: 清查並修復脆弱帳號
     Get-ADUser -Filter {DoesNotRequirePreAuth -eq $True} | Set-ADUser -DoesNotRequirePreAuth $False
     ```
2. **長密碼複雜度要求 (Passphrase Policy)**：
   - 對於因特殊遺留系統必須關閉預先認證的帳號，強制其密碼長度超過 30 字元，使離線字典與暴力破解在算力上不可行。
3. **部署虛假誘餌帳號 (Canary Accounts)**：
   - 故意建立一個關閉預先認證但無任何權限的誘餌帳號，一旦其收到 AS-REQ 請求立即觸發最高級安全事件響應。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 AS-REP Roast 脆弱帳號 LDAP 檢查腳本 (Python, 20 行)
```python
# check_asrep.py
from ldap3 import Server, Connection, ALL

server = Server("127.0.0.1", get_info=ALL)
conn = Connection(server, user="corp\\guest", password="Password123!", auto_bind=True)

# 搜尋所有 UAC 包含 DONT_REQ_PREAUTH (bit 4194304) 的帳號
search_filter = "(&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))"
conn.search(search_base="DC=corp,DC=internal", search_filter=search_filter, attributes=["sAMAccountName", "userAccountControl"])

print("[*] 掃描脆弱且可被 AS-REP Roast 的帳號清單:")
for entry in conn.entries:
    print(f"[!] 發現高危帳號: {entry.sAMAccountName} (可被未認證攻擊者離線收割密文！)")
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：AS-REP Roasting 與 Kerberoasting 在攻擊發起先決條件上有何根本差異？**
  - **戰術思維**：Kerberoasting 必須具備「有效之合法網域帳號」登入後向 KDC 申請服務票證 (TGS)；而 AS-REP Roasting 只要知道帳號名稱，**完全不需要任何網域憑證**即可向 KDC 匿名發起 AS-REQ 拉取密文。
- [ ] **Q2：為何關閉預先認證會導致使用者密碼處於極端危險狀態？**
  - **戰術思維**：因為 KDC 直接將「以該使用者密碼金鑰加密的憑證區塊」明文發給網路上任何索取者；攻擊者即可在本地擁有無限次猜測機會，且完全不會觸發網域控制站的「帳號密碼錯誤次數鎖定原則」。
- [ ] **Q3：在 Hashcat 模式 18200 中，雜湊開頭的 `$krb5asrep$23$` 代表何種加密協定？**
  - **戰術思維**：代表使用 **RC4-HMAC (etype 23)** 加密。相較於 AES128/AES256，RC4 的演算法結構簡單且計算成本低，在現代 GPU 上每秒可嘗試數十億次破解。
- [ ] **Q4：如果目標帳號啟用「Protected Users」群組，對 AS-REP Roasting 有何防禦效果？**
  - **戰術思維**：加入 Protected Users 後，帳號將強制要求預先認證，且強制作廢 RC4 加密協定，並切斷無預先驗證的票證發放，可徹底免疫此攻擊。
- [ ] **Q5：若攻擊者從網際網路直連企業外曝的 Port 88 發起 AS-REP 請求，防禦者如何快速定性？**
  - **戰術思維**：檢視 Event 4768 的 Client Address；若來自外部公網 IP 且 PreAuthType=0，100% 為外部威脅行為者正在實施廣泛的認證材料收割。
