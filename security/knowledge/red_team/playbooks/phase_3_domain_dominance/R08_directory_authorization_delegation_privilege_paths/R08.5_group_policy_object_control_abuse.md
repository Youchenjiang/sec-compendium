# R08.5 群組原則物件控制權濫用與全域程式碼派發 (Group Policy Object Control & Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**群組原則物件控制權濫用 (Group Policy Object Abuse)** 的物理本質為**利用 Active Directory 核心組態派發機制對大量受管端點實施「一對多」的特權程式碼注入**。當低權限使用者或受控服務帳號對某個已連結 (Linked) 至重要 OU（如 Domain Controllers 或重要伺服器）的 GPO 具備寫入權限（如 `GenericAll`, `WriteDacl`, `WriteProperty`）時，攻擊者可直接竄改儲存於 SYSVOL 共用目錄下的原則組態檔，注入即時排程工作或啟動腳本。當客戶端觸發群組原則更新 (`gpupdate`) 時，注入的酬載將以最高特權 **`NT AUTHORITY\SYSTEM`** 於全網目標端點批次執行。

```
[攻擊者受控帳號] ── 發現對重要 GPO (如 {31B2F340-...}) 具備 Write 權限
                            │
                            ▼ 透過 SMB 存取 SYSVOL: \\corp\sysvol\Policies\{GUID}\
┌───────────────────────────┴───────────────────────────────────────────┐
│ 1. 寫入惡意組態: 建立 Scheduled Tasks XML 檔案 (即時排程工作)          │
│ 2. 遞增版本編號: 修改 gpt.ini 將 Version 欄位數值累加，觸發客戶端強制同步 │
└───────────────────────────┬───────────────────────────────────────────┘
                            ▼
[全網網域成員主機] ─────────► 背景定時 (預設 90 分鐘) 或手動觸發 gpupdate
                            │
                            ▼ 客戶端延伸模組 (CSE) 解析惡意 XML
[批次特權執行] ─────────────► 以 LocalSystem 權限執行攻擊者指令，全網瞬間淪陷！
```

## 🔬 第一動：GPO 雙軌儲存架構與客戶端延伸機制 (Mechanics & CSE Engine)

### 1. GPO 架構核心元件對照表

| 元件名稱 | 物理儲存位置 | 存取協定 | 弱點與利用機制 |
| :--- | :--- | :--- | :--- |
| **GPC (容器)** | LDAP: `CN=Policies,CN=System,DC=corp...` | LDAP (389/636) | 儲存 GPO 屬性、版本號、連結狀態與 DACL |
| **GPT (範本)** | SMB: `\\corp\SYSVOL\corp\Policies\{GUID}` | SMB (445) | 儲存實際原則檔案 (腳本、排程、登錄檔) |
| **gpt.ini** | GPT 根目錄之設定檔 | 文字格式 | 必須與 GPC 之 `versionNumber` 同步遞增才能觸發更新 |
| **CSE (延伸模組)**| 客戶端本機動態函式庫 (`gpsvc.dll`) | 本機 API | 解析特定原則 (如 Scheduled Tasks CSE: `{CAB54552-...}`) |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **嚴格限制 GPO 物件委派寫入權 (Restrict GPO Delegation)**：
   - 確保僅有 `Domain Admins` 與 `Enterprise Admins` 對 GPO 具備寫入、修改或建立權限；徹底清除一般帳號與非特權群組的 `CreateGPO` 權利。
2. **採用微軟進階群組原則管理 (AGPM, Advanced Group Policy Management)**：
   - 將 GPO 納入版本控制與雙人簽核流程 (Change Approval Workflow)，阻斷對 SYSVOL 與 GPC 的直接手動覆寫。
3. **啟用 SYSVOL 檔案完整性監控 (FIM)**：
   - 部署檔案完整性監控系統，對 SYSVOL 內部所有的 `.xml`, `.bat`, `.ps1` 進行即時雜湊比對與防竄改告警。

## 🧪 實戰演練環境搭建 (Environment & Lab Setup)

### 1. 極簡 GPO gpt.ini 版本遞增模擬腳本 (Python, 20 行)
```python
# gpt_bumper.py
import configparser

ini_path = "gpt.ini"
# 讀取現有 GPO 版本設定
config = configparser.ConfigParser()
config.read(ini_path)

current_version = int(config.get("General", "Version", fallback="0"))
# 版本號位元運算：高 16 位元為使用者設定，低 16 位元為電腦設定
new_computer_version = (current_version & 0xFFFF) + 1
new_total_version = (current_version & 0xFFFF0000) | new_computer_version

config.set("General", "Version", str(new_total_version))
with open(ini_path, "w") as f:
    config.write(f)

print(f"[*] 成功遞增 GPO 版本: {current_version} -> {new_total_version}")
print("[+] 客戶端下次執行 gpupdate 時將強制拉取惡意組態！")
```

### 2. 三步作戰驗證流程
```bash
# 步驟 1: 建立模擬 gpt.ini
echo -e "[General]\nVersion=1" > gpt.ini

# 步驟 2: 執行版本遞增腳本
python3 gpt_bumper.py
# 驗證輸出：[*] 成功遞增 GPO 版本: 1 -> 2

# 步驟 3: 驗證檔案狀態
cat gpt.ini
# 驗證輸出：確認 Version 已更新為 2，符合客戶端強制同步之觸發條件
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：GPO 濫用中，為何竄改 `Default Domain Policy` 比竄改一般 GPO 更具破壞力？**
  - **戰術思維**：`Default Domain Policy` 預設直接連結 (Linked) 至整個網域的根節點 (Domain Root)，其原則設定會無差別繼承套用至全網域**所有的伺服器、網域控制站與個人電腦**，注入一次即可實現全域同步收網。
- [ ] **Q2：若僅修改了 SYSVOL 中的組態檔案，卻未修改 LDAP 中的 GPC 版本號，會發生何事？**
  - **戰術思維**：客戶端在執行 `gpupdate` 時，會優先比對本地快取的版本號與 LDAP GPC 中的 `versionNumber`；若 LDAP 中的版本號未增加，客戶端會認定原則無變更，**完全不會主動連線 SYSVOL 下載遭篡改的原則檔案**。
- [ ] **Q3：在 GPO 注入中，使用 Immediate Task (即時工作) 相比傳統排程有何戰術優勢？**
  - **戰術思維**：Immediate Task 會在客戶端收到原則更新的**當下瞬間立即觸發執行**，無須等待特定時間點；且執行完成後可透過組態配置在完成後立即自我刪除，大幅降低鑑識採樣殘留。
- [ ] **Q4：若目標環境啟用了「封鎖繼承 (Block Inheritance)」，注入的 GPO 是否仍會生效？**
  - **戰術思維**：若目標 OU 啟用了封鎖繼承，父級 GPO 將無法套用；但若攻擊者對具備「強制 (Enforced)」屬性的 GPO 進行竄改，該 GPO 將無視封鎖繼承，強制在所有子節點執行。
- [ ] **Q5：為何微軟在後續修補中強制要求安裝 KB3159398，這如何影響了 GPO 濫用？**
  - **戰術思維**：該安全修補要求客戶端電腦必須以「電腦帳號 (Domain Computers)」身分讀取 GPO；若 GPO 的存取權限中移除了 `Authenticated Users` 或 `Domain Computers` 的讀取權，客戶端將拒絕套用該原則。
