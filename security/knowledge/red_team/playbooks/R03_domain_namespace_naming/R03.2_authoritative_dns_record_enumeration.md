# R03.2 權威 DNS 資源記錄列舉與區域傳送驗證 (Authoritative DNS Enumeration)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**權威 DNS 資源記錄列舉 (Authoritative DNS Enumeration & AXFR)** 的物理本質為**直接向目標組織的權威名稱伺服器 (Authoritative Nameservers) 發起全量標準記錄查詢，並測試是否存在「DNS 區域傳送 (AXFR, Zone Transfer)」設定疏失**。若目標 DNS 伺服器未嚴格限制複製權限，攻擊者發送單一 AXFR 請求即可在數秒內無損獲取目標網域的**所有主機名、內部伺服器、私有 IP 映射與隱密路由**；即使 AXFR 受限，深入解析 SPF、TXT 與 SRV 記錄亦能萃取出企業雲端供應商與內部活動目錄拓撲。

```
[攻擊者控制台] ── 1. 查詢目標權威 NS: dig NS corp.internal
                        │
                        ▼ 獲取權威伺服器: ns1.corp.internal (TCP/UDP 53)
┌───────────────────────┴───────────────────────────────────────────────┐
│ 測試 A: DNS 區域傳送 (AXFR) ───► 【高危漏洞】發送 AXFR 複製請求          │
│                                  若配置不當，直接回傳全域數千筆完整記錄！ │
│ 測試 B: 資源記錄深度收割 ──────► 查詢 TXT (SPF 網段、SaaS 驗證標記)     │
│ 測試 C: 服務定位器 (SRV) ──────► 查詢 _ldap._tcp, _kerberos._tcp 提取 DC │
└───────────────────────┬───────────────────────────────────────────────┘
                        ▼
[全面解析 DNS 資源矩陣] ────────► 掌握全網隱密拓撲、雲端租戶服務與內部認證端點！
```

## 🔬 第一動：DNS 階層解析架構與 AXFR 複製物理機制 (Mechanics & DNS Records)

### 1. 核心 DNS 資源記錄型態與作戰價值

| 記錄類型 | 協定語法規範 | 物理內涵 | 紅隊作戰利用價值 |
| :--- | :--- | :--- | :--- |
| **AXFR** | `dig axfr @ns domain` (TCP 53) | DNS 區域複製協定，同步主從伺服器資料庫 | **致命資訊洩漏** (單一封包直接獲取全網拓撲) |
| **TXT / SPF** | `v=spf1 ip4:203.0.113.0/24 include:...`| 宣告授權發送郵件之合法 IP 與第三方服務 | **直接暴露企業擁有的公網 IP 網段與外部 SaaS** |
| **SRV** | `_service._proto.name TTL Priority Weight Port Target` | 宣告提供特定網路服務之主機與監聽埠 | **直接精確定位內部網域控制站 (DC) 與 SIP 主機** |
| **CNAME** | 網域名稱別名映射 | 指向第三方雲端端點 (如 S3、GitHub Pages) | **檢查是否存在子網域劫持 (Subdomain Takeover)** |

## ⚡ 第二動：戰術執行與工具鏈操作 (Attack Vectors & Automation)

### 1. 核心權威 DNS 列舉指令速查表 (Dig / DNSRecon)

```bash
# 1. 測試目標權威名稱伺服器是否存在 AXFR 區域傳送漏洞
dig axfr @ns1.corp.internal corp.internal

# 2. 自動化列舉目標所有常見 DNS 資源記錄 (DNSRecon)
dnsrecon -d corp.internal -t std -a -j dns_records.json

# 3. 專門提取 SPF 記錄中定義的所有 IP 網段與第三方授權服務
dig TXT corp.internal +short | grep "v=spf1"

# 4. 探測 Active Directory 核心服務定位器 (SRV Records)
dig SRV _ldap._tcp.dc._msdcs.corp.internal +short
dig SRV _kerberos._tcp.corp.internal +short
```

## 🥷 第三動：防禦規避與日誌特徵操控 (Evasion & Recursive Masking)

### 1. DNS 探測防禦規避策略表

| 規避面向 | 原始觸發特徵 | 變形隱蔽手法 | 原理解析 |
| :--- | :--- | :--- | :--- |
| **直連權威 NS 監控** | 攻擊機 IP 直接連線目標 NS 留下查詢日誌 | **遞迴公共 DNS (1.1.1.1 / 8.8.8.8)** | 查詢流量由公共快取伺服器發送，目標僅見 Google IP |
| **DNS 封包被劫持** | 本地 ISP 污染或防火牆重置明文 DNS 53 | 改採 **DNS-over-HTTPS (DoH)** 發起解析 | 將 DNS 查詢封裝於加密 TLS (443) 流量中 |
| **AXFR 頻率告警** | 重複發起區域傳送請求引發 SOC 告警 | 僅在偵察初期待命執行一次，失敗後立即停止 | 避免在不支援 AXFR 的環境下產生無效雜訊 |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **全面封閉未經授權之 DNS 區域傳送 (Restrict AXFR)**：
   - BIND 配置：在全域或區域設定中嚴格限制僅允許次級名稱伺服器 (Secondary NS) 複製：
     ```named
     // 安全: 嚴禁公網發起 AXFR
     zone "corp.internal" {
         type master;
         file "corp.internal.zone";
         allow-transfer { 10.0.0.2; }; // 僅允許指定的備份伺服器 IP
     };
     ```
2. **清理過期 SPF 與 TXT 驗證標籤**：
   - 定期審查 SPF 記錄中的 `ip4:` 與 `include:`，移除已退役的舊機房網段與不再使用的雲端服務驗證字串 (如舊 Google Site Verification)。
3. **部署 DNSSEC (Domain Name System Security Extensions)**：
   - 為權威區域簽署數位簽章，防止 DNS 快取投毒與中間人篡改記錄。

# 模擬 dig TXT 獲取之典型企業 SPF 記錄

# 正規表達式萃取所有 IPv4 網段與單一 IP

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：為何 DNS 區域傳送 (AXFR) 必須使用 TCP Port 53 而非 UDP？**
  - **戰術思維**：因為傳統 UDP 封包大小受限於 512 位元組；而區域傳送涉及整個資料庫的大規模同步，回傳的資源記錄通常達數十 KB 甚至數 MB，必須仰賴具備可靠串流傳輸能力的 **TCP 53** 進行傳輸。
- [ ] **Q2：若目標企業將內部網域也託管在公網 DNS 上，紅隊如何一鍵鎖定其網域控制站 (DC)？**
  - **戰術思維**：查詢專屬的 Active Directory SRV 記錄（例如 `_ldap._tcp.dc._msdcs.DOMAIN`）；Windows DC 在加入網域時會自動註冊該記錄，回傳結果將直接指名所有 DC 的完整主機名稱與 IP。
- [ ] **Q3：在分析 SPF 記錄時，`include:` 語法對紅隊繪製供應鏈拓撲有何價值？**
  - **戰術思維**：`include:` 代表目標組織授權了哪些第三方服務代為發送郵件（例如 `include:mailgun.org`, `include:sendgrid.net`, `include:spf.protection.outlook.com`），能直接揭露企業當前使用的 SaaS 與雲端供應鏈。
- [ ] **Q4：TXT 記錄中常見的 `docusign-domain-verification=` 等驗證標籤有何情報意義？**
  - **戰術思維**：這些字串是企業在採用特定企業級軟體時所配置的網域歸屬驗證憑據；分析這些標籤能讓紅隊精確繪製出該企業正在使用的內部協同系統（如 Atlassian, Miro, DocuSign），為精準社工釣魚提供情資。
- [ ] **Q5：若目標 DNS 伺服器啟用了「Split-Horizon DNS (雙面 DNS)」，公網查詢有何侷限？**
  - **戰術思維**：雙面 DNS 會根據來源 IP 提供不同的解析結果；來自公網的查詢只能看到 DMZ 區的少量公開伺服器，所有內部私有主機名（如 `intranet.corp`）只有在內網 IP 查詢時才會回傳。
