# R11.3 本地檔案包含機制與安全防禦分析 (Local File Inclusion Mechanics & Defense)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在動態 Web 應用程式架構中，為了實現模組化設計與程式碼重用，伺服器端直譯語言（如 PHP、Node.js、Python）普遍提供在執行時期動態引用外部檔案的機制。當應用程式允許使用者輸入直接或間接決定被載入的檔案路徑，且未進行嚴謹的型態驗證與白名單過濾時，便會衍生**本地檔案包含 (Local File Inclusion, LFI)** 弱點。

與單純讀取檔案內容的路徑遍歷 (Path Traversal) 不同，檔案包含弱點的核心威脅在於**執行環境的上下文接管**——被包含的檔案內容會被伺服器端的直譯引擎視為可執行程式碼進行解析。本手冊旨在深入剖析檔案包含的直譯層底層原理、串流封裝協議 (Stream Wrappers) 之解析行為，並建立嚴密的防禦偵測與程式碼安全重構模型。

```
[客戶端請求] ── 1. 提交模組/檔案參數 ──► [Web 應用程式 (動態載入邏輯)]
                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 │                                                             │
                 ▼ (安全設計：嚴格靜態映射)                                     ▼ (缺陷設計：字串直接拼接)
    [查表白名單字典 (Map/Dict)]                                    [呼叫直譯器載入指令 (include/require)]
                 │                                                             │
                 ▼                                                             ▼
     [載入預定義合法模板/檔案]                                      [VFS 尋址：本機任意檔案 / 串流協議]
                                                                               │
                                                                               ▼
                                                          [直譯引擎以伺服器特權執行該內容]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統採用動態路由或外掛模組架構（如 `?module=contact`），後端在參數後自動追加固定副檔名（如 `.php` 或 `.tpl`）。
- **決策心流**：
  1. **確認副檔名限制機制**：
     - 若後端存在硬編碼副檔名拼接，評估是否能透過串流協議（如 `php://filter`）以特定編碼讀取原始碼，抑或利用路徑長度截斷（主要存在於舊版本系統）。
  2. **分析直譯環境能力**：
     - 檢查環境是否支援虛擬串流（Stream Wrappers，例如 `data://`、`input://`、`phar://`）。
  3. **評估上下文可控資料源**：
     - 分析系統中是否存在由使用者控制並落地於本機磁碟的資料（例如：會話檔案 Session Files、暫存上傳檔、應用程式日誌）。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. 直譯器執行時期動態解析原理
以典型動態語言（如 PHP）為例，檔案包含函數（`include`, `require`, `include_once`, `require_once`）並非單純調用作業系統的 `read()` 系統調用，而是將目標檔案送入語言核心的 **詞法分析 (Lexing)** 與 **語法編譯 (Parsing/Opcode Generation)** 流程：

```
+-----------------------------------------------------------------------------------------------+
| 直譯器檔案包含執行管線 (Interpreter Inclusion Pipeline)                                       |
|                                                                                               |
| 1. 輸入路徑：include($_GET['page']); ➔ 例如 page = "user_profile.php"                          |
|                                                                                               |
| 2. 虛擬檔案系統 (VFS) 串流解析 (Streams Layer):                                               |
|    - 檢查是否帶有協議 Scheme (如 file://, php://, data://)                                    |
|    - 若無協議前綴，預設使用 file:// 包裝器調用本機 libc stat() / open() 獲取檔案指標 (Stream)   |
|                                                                                               |
| 3. Zend 核心編譯與執行階段:                                                                   |
|    - open_file_for_scanning() 獲取原始位元組串流                                               |
|    - 詞法分析器尋找語言開頭標籤 (如 <?php 或 <?=)                                            |
|    - 標籤外內容：直接輸出至 HTTP Response Body (此特性導致非程式碼檔案可被洩漏讀取)            |
|    - 標籤內內容：編譯為 Opcode 虛擬機指令並立即在當前進程上下文執行                           |
+-----------------------------------------------------------------------------------------------+
```

### 2. 串流過濾器 (Stream Filters) 內部機制
許多現代執行環境支援「串流過濾鏈」，允許在資料讀取或寫入串流時進行即時轉換。例如 `php://filter` 是 PHP 內部提供的中繼資料處理機制：

```text
資源定位符格式：
php://filter/read=convert.base64-encode/resource=config.php
│            │                             │
└─ 協議方案  └─ 過濾鏈 (Filter Chain)       └─ 目標資源路徑
```

- **安全影響**：當直接包含 `config.php` 時，直譯引擎會執行其中的程式碼，使用者只能看到執行結果而無法看見原始碼中的機密金鑰；然而透過 `convert.base64-encode` 轉換後，檔案內容在抵達詞法分析器前已全數被轉為 Base64 字元序列，直譯器因找不到程式碼標籤而將其視為純文字全數輸出，造成原始碼逆向暴露。

## ⚡ 第二動：弱點驗證與分析技術 (Vulnerability Analysis & Vectors)

### 1. 核心向量與技術變體速查表

| 機制變體 | 核心輸入範例 | 底層行為與風險分析 |
| :--- | :--- | :--- |
| **原始碼安全讀取 (Filter Wrappers)** | `php://filter/read=convert.base64-encode/resource=index.php` | 利用唯讀串流過濾器將目標資源轉碼為 Base64，繞過直譯器執行階段，將伺服器端腳本源碼完整萃取。 |
| **內聯資料協議 (Data Stream)** | `data://text/plain;base64,PD9waHAgcGhwaW5mbygpOz8+` | 當環境配置允許 `allow_url_include = On` 時，直接將 Base64 編碼的內容作為虛擬檔案載入直譯引擎執行。 |
| **輸入串流協議 (Input Stream)** | `php://input` (POST 包含代碼) | 讀取原始 HTTP 請求主體 (Raw POST Data) 作為包含內容。需搭配 `allow_url_include = On` 配置。 |
| **會話檔案包含 (Session Inclusion)** | `/var/lib/php/sessions/sess_{SESSION_ID}`<br>`/tmp/sess_{SESSION_ID}` | 當應用程式將可控字串寫入 Session 變數，且攻擊者得知其 Session ID 時，包含系統會話檔案以觸發特定邏輯。 |
| **暫存檔競態分析 (Upload Tempfile)** | `/tmp/phpXXXXXX` | 檔案上傳過程中，系統建立的暫時檔案在腳本結束前會短暫存在，在特定高併發時差下引發安全評估挑戰。 |

### 2. 診斷與安全分析腳本 (安全審計用途)

```python
#!/usr/bin/env python3
# 本地檔案包含診斷腳本 (LFI Safe Audit & Baseline Scanner)
import requests
import base64
import sys

TARGET_URL = "http://target-app.local/view.php"
PARAM_NAME = "page"

def audit_source_leak(target_file):
    """
    測試是否存在過濾器串流洩漏弱點
    """
    payload = f"php://filter/read=convert.base64-encode/resource={target_file}"
    params = {PARAM_NAME: payload}
    headers = {"User-Agent": "Security-Audit-Tool/2.0"}

    try:
        r = requests.get(TARGET_URL, params=params, headers=headers, timeout=5)
        # 尋找輸出中是否存在 Base64 特徵字串
        for token in r.text.split():
            if len(token) > 40:
                try:
                    decoded = base64.b64decode(token).decode('utf-8', errors='ignore')
                    if "<?php" in decoded or "include" in decoded:
                        print(f"[!] 成功偵測到原始碼暴露弱點！")
                        print(f"    目標檔案: {target_file}")
                        print(f"    原始碼預覽:\n{decoded[:150]}...\n")
                        return True
                except Exception:
                    continue
    except Exception as e:
        print(f"[-] 連線異常: {e}")
    return False

if __name__ == '__main__':
    print("[*] 開始進行本地檔案包含安全性診斷...")
    audit_source_leak("index.php")
```

## 🥷 第三動：防禦規避與反鑑識分析 (Evasion & Anti-Forensics Analysis)

### 1. 規避過濾模式之特徵分析
- **絕對路徑與正規化前綴繞過**：
  若後端程式碼強制要求開頭為特定的目錄字串（例如 `include("templates/" . $_GET['page']);`），分析者常利用 `templates/../../../../etc/hosts` 滿足開頭驗證，再透過相對路徑跳出邊界。
- **路徑編碼與協議嵌套**：
  部分 WAF 僅比對標準路徑關鍵字，未能解析多重 URL 編碼（如 `%252e%252e%252f`）或包含協議封裝（`compress.zlib://`、`php://filter/`），導致封包檢驗與伺服器端解析脫鉤。

### 2. 鑑識視角下的日誌殘留分析
- **Web Access Log 異常參數特徵**：
  在 HTTP GET 請求參數中出現 `php://`、`data://` 或長串 `../` 時，Web 伺服器存取記錄檔會留下清晰的明文特徵。
- **檔案系統時間戳記與 Inode 變動**：
  包含暫存檔或特定檔案時，作業系統會更新該檔案的存取時間（Access Time, atime），鑑識人員可透過 `stat` 指令比對檔案存取時間點與 Web 存取記錄檔的時間序列關聯。

| 攻擊與測試向量 (Vector) | 系統遙測指標 (Telemetry & Artifacts) | 防禦檢測規則 (Detection Signature) | 安全架構加固措施 (Remediation Architecture) |

| **遠端/資料協議注入 (`data://`)** | 請求中出現 `data:text` 或 HTTP POST 主體傳遞 PHP 標籤代碼。 | 偵測 Web 請求參數包含 `<?php` 或特定協議 Scheme (OWASP CRS 931110)。 | 在 `php.ini` 強制設定 `allow_url_fopen = Off` 及 `allow_url_include = Off`。 |
| **會話檔案包含嘗試** | 存取記錄出現指向系統暫存目錄（如 `/tmp/sess_*` 或 `/var/lib/php/`）。 | 監控 Web 進程存取非公開 Web 目錄之檔案行為 (Auditd / AppArmor 違規)。 | 設定 `open_basedir` 限制進程檔案系統存取邊界；採用獨立的快取資料庫（如 Redis）儲存 Session。 |
| **高頻路徑跳躍測試** | 短時間內產生大量 HTTP 404 或 500 錯誤回應，伴隨大量 `../`。 | SIEM 告警關聯規則：單一 IP 於 1 分鐘內觸發超過 20 次檔案載入錯誤。 | 啟用速率限制 (Rate Limiting) 與自動化 IP 暫時封鎖機制。 |

## 🛡️ 第五動：安全加固與程式碼重構 (Hardening & Remediation Baseline)

### 1. 脆弱程式碼 vs. 安全白名單架構重構

#### ❌ 脆弱的實現方式 (易受攻擊)
```php
// 嚴重安全隱患：直接由客戶端輸入拼接路徑
$page = $_GET['page'];
include("templates/" . $page . ".php");
```

#### ✅ 工業級安全防護實現 (安全字典對齊)
```php
// 安全架構：強制白名單查表法 (Strict Whitelist Mapping)
$allowed_pages = [
    'home'     => '/var/www/html/templates/home.php',
    'about'    => '/var/www/html/templates/about.php',
    'contact'  => '/var/www/html/templates/contact.php'
];

$requested_page = $_GET['page'] ?? 'home';

if (array_key_exists($requested_page, $allowed_pages)) {
    // 僅載入明確定義在白名單中的絕對路徑
    include($allowed_pages[$requested_page]);
} else {
    // 預設安全回退
    http_response_code(404);
    include('/var/www/html/templates/404.php');
}
```

### 2. 伺服器與直譯環境加固基線
1. **php.ini 關鍵安全參數**：
   ```ini
   allow_url_fopen = Off
   allow_url_include = Off
   open_basedir = "/var/www/html/:/tmp/"
   expose_php = Off
   display_errors = Off
   ```
2. **作業系統層級權限限制**：
   - 確保 Web 伺服器執行使用者（如 `www-data`）對系統關鍵設定檔僅具備最低存取權限，禁止對非必要目錄擁有讀取權限。
   - 啟用 AppArmor / SELinux 限制 Web 伺服器跨越應用程式根目錄之外的讀取能力。

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 檔案包含弱點 (LFI) 與目錄遍歷 (Path Traversal) 在伺服器底層處理機制上有何根本差異？**  
  *分析思路*：目錄遍歷僅透過檔案系統 API (如 `read`) 輸出目標檔案的二進位或文字內容；而檔案包含是將目標檔案直接交付給直譯引擎（如 Zend Engine、V8 或 Python VM）解析，若檔案中包含符合語言規範的語法結構，會直接在伺服器端進程中被編譯並執行。

- [ ] **Q2. 為什麼在現代安全加固規範中，強制要求將 `allow_url_include` 設為 `Off`？**  
  *分析思路*：`allow_url_include` 啟用時，直譯器會將 `http://`、`ftp://` 以及 `data://` 等外部串流包裝器視為合法的包含來源，這允許任意遠端腳本或使用者輸入的內聯資料直接進入執行管道，造成嚴重的遠端代碼載入風險。

- [ ] **Q3. 使用 `php://filter/read=convert.base64-encode/resource=file.php` 讀取檔案時，為什麼能夠避免該檔案內的 PHP 程式碼被執行？**  
  *分析思路*：因為串流過濾器是在檔案讀取至記憶體的過渡階段生效。Base64 編碼過濾器將檔案內的每一個位元組轉換為 ASCII 字母數字符號，當轉換後的字串進入詞法分析階段時，直譯器已無法識別原本的 `<?php` 開始標籤，因此將整個內容視為純靜態文字直接輸出。

- [ ] **Q4. 伺服器端配置 `open_basedir` 的核心防護機制是什麼？它能抵禦哪些攻擊情境？**  
  *分析思路*：`open_basedir` 在直譯器層級掛鉤了所有檔案系統系統調用，強制檢查目標檔案的物理真實路徑是否落在允許的目錄前綴內。即使應用程式存在目錄遍歷或檔案包含漏洞，一旦試圖存取 `/etc/` 或其他非授權目錄，直譯層便會直接拒絕並拋出安全警告。

- [ ] **Q5. 針對動態檔案包含弱點，最徹底、唯一推薦的架構級防禦方案是什麼？為什麼？**  
  *分析思路*：採用「硬編碼白名單字典對齊 (Strict Whitelist Mapping)」。拒絕直接使用任何客戶端傳入的字串拼接檔案路徑，而是透過鍵值（Key）映射到伺服器預先定義的絕對檔案路徑。不符合鍵值的請求一律拒絕或導向預設頁面，從根本上消除路徑不可控的風險。
