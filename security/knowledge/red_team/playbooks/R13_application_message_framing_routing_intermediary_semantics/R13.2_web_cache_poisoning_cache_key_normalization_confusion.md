# R13.2 網頁快取投毒與快取鍵正規化混淆機制分析 (Web Cache Poisoning via Cache-Key & Normalization Confusion)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代高併發分散式 Web 架構中，內容傳遞網路 (CDN，如 Cloudflare、Akamai、AWS CloudFront) 與反向代理快取伺服器 (如 Varnish、Nginx `proxy_cache`) 是抵禦流量海嘯、降低後端資料庫負載不可或缺的核心基礎設施。快取伺服器的基本運作邏輯在於**「資源等價性判定」**：當客戶端請求到達時，快取引擎依據特定的**快取鍵 (Cache Key)** 演算法計算雜湊值。若該快取鍵已存在且未過期，快取伺服器直接向客戶端回傳預先儲存的 HTTP 回應，而不再將請求轉發至後端原始伺服器 (Origin Server)。

當系統架構存在以下兩大缺陷的交集時，便會衍生**網頁快取投毒 (Web Cache Poisoning, WCP)** 與**快取鍵正規化混淆 (Cache-Key Normalization Confusion)** 弱點：
1. **非鍵值輸入盲信 (Unkeyed Input Blind Trust)**：後端原始伺服器在生成動態頁面或重導向位址時，引用了某些 HTTP 請求標頭或參數，但前置快取伺服器的 Cache Key 演算法**並未將這些輸入納入雜湊計算**。
2. **快取鍵正規化歧異 (Normalization Discrepancy)**：快取層與後端伺服器在處理 URL 編碼、尾端斜線、大小寫或查詢參數時，採用了不同的規範化（Normalization）規則，造成「快取層視為資源 A，而後端伺服器解讀為資源 B」的語意脫鉤。

攻擊者得以藉此精心構造單一請求，將包含惡意腳本 (Stored XSS)、錯誤重導向、或毀損狀態 (CPDoS) 的回應**永久灌入中繼共用快取層**。在快取的有效存活時間 (TTL) 內，所有存取該頁面的正常使用者都將持續接收到被污染的惡意內容，形成「單點發起、全域擴散」的災難性打擊。

```
[攻擊者用戶端] ── 1. 提交夾帶未鍵值惡意標頭的請求 (例如 X-Forwarded-Host: evil.com) ──► [中繼快取伺服器 (CDN / Varnish)]
                                                                                               │
                               ┌───────────────────────────────────────────────────────────────┴───────────────────────────────────────────────────────────────┐
                               │                                                                                                                               │
                               ▼ (快取判定: MISS)                                                                                                              ▼ (計算 Cache Key)
             [依據標準 Cache Key 尋址 (Host + Path)]                                                                                             [僅將 Host 與 Path 納入 Hash 計算]
                               │                                                                                                                               │ (完全忽略未鍵值標頭: X-Forwarded-Host)
                               ▼                                                                                                                               │
            [將原始請求完整轉發至後端伺服器]                                                                                                                  │
                               │                                                                                                                               │
                               ▼                                                                                                                               │
            [後端原始伺服器 (Origin Server)]                                                                                                                   │
                               │ (動態引用未鍵值標頭生成回應: <script src="http://evil.com/app.js">)                                                           │
                               ▼                                                                                                                               │
            [回傳包含惡意 Payload 的 HTTP 回應]                                                                                                                │

                               ▼                                                                                                                               │
             [快取伺服器接收回應並依據 Key 存入記憶體] ◄───────────────────────────────────────────────────────────────────────────────────────────────────────┘
                               │
                               ▼ (致命狀態建立: Cache Key 被惡意內容污染，TTL = 3600s)
                   [共用快取庫: Key [GET /index] => 儲存帶有 evil.com 的回應]
                               │
[受害使用者正常請求] ────────── 2. 發送標準 GET /index (無任何惡意標頭) ────────────────────────────────────────────────────────────────────────────────────────┐
                                                                                                                                               │
                                                                                                                                               ▼
                                                                                                                                  [快取判定: HIT!]
                                                                                                                                               │

                                                                                                                                  [快取直接吐出帶毒頁面給受害者]

```

### 作戰痛點與決策分支
- **痛點場景**：目標系統的前端 XSS 反射點僅在特定非標準標頭（如 `X-Forwarded-Host`、`X-Original-URL`、`X-Rewrite-URL`）中觸發，傳統反射型 XSS 無法透過直接釣魚連結點擊利用。
- **決策心流**：
  1. **快取體系確認與快取消除器 (Cache-Buster Isolation)**：
     - 在探測時**必須使用專屬的 Cache-Buster 參數**（例如 `?cb=probe_123`），確保測試封包僅在隔離的快取槽位中驗證，**嚴禁污染生產環境的全域首頁**！
  2. **未鍵值輸入識別 (Unkeyed Input Discovery)**：
     - 測試各類轉發標頭是否被後端反射至回應（HTML 標籤、重導向 Location），並檢查該標頭是否未被納入快取層的 Cache Key 計算。
  3. **快取接納狀態檢驗 (Cache Admission Proof)**：
     - 確認後端回應是否帶有允許快取的標頭（如 `Cache-Control: public, max-age=...`），並透過接續發送的「無標頭純淨請求」驗證是否觸發 `X-Cache: HIT` 且回傳帶毒內容。
  4. **技術邊界鑑別 (Boundary Seams)**：
     - **非 Web Cache Deception (WCD)**：WCD 是利用路徑混淆誘騙快取層存儲受害者的私密個資；WCP 則是將攻擊者的惡意輸入灌入快取讓他人受害。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. HTTP 快取鍵生成架構與未鍵值隱患 (Cache Key Generation Architecture)
依據 RFC 7234 (HTTP/1.1 Caching) 與 RFC 9111 規範，快取伺服器透過將請求的特定維度串聯並進行雜湊（如 MD5 或 MurmurHash），生成唯一的索引標識：

```
+---------------------------------------------------------------------------------------------------+
| 快取鍵 (Cache Key) 物理組裝架構解剖                                                                |
|                                                                                                   |
| 典型 HTTP 請求:                                                                                   |
| GET /static/app.js?v=2 HTTP/1.1                                                                   |
| Host: example.com                                                                                 |
| User-Agent: Mozilla/5.0 ...                                                                       |
| X-Forwarded-Host: evil.internal                                                                    |
| Accept-Encoding: gzip, deflate                                                                    |
|                                                                                                   |
| 快取鍵分流判定 (Cache Key Partitioning):                                                           |
| ┌──────────────────────────────────────────────┐ ┌──────────────────────────────────────────────┐ |
| │ 鍵值輸入 (Keyed Inputs - 納入 Hash 計算):     │ │ 未鍵值輸入 (Unkeyed Inputs - 被快取引擎忽略):   │ |
| │ 1. HTTP Method: GET                          │ │ 1. 轉發標頭: X-Forwarded-Host, X-Original-URL  │ |
| │ 2. Host 標頭: example.com                    │ │ 2. 協定標頭: X-Forwarded-Proto, X-Forwarded-Port│ |
| │ 3. Request Path: /static/app.js              │ │ 3. 用戶識別: User-Agent (若無 Vary: User-Agent)│ |
| │ 4. 查詢參數: ?v=2 (視配置而定)               │ │ 4. 自訂標頭: X-Requested-With, X-Host           │ |
| └──────────────────────────────────────────────┘ └──────────────────────────────────────────────┘ |
|                                                                                                   |
| 致命根源: 後端依賴未鍵值輸入生成內容，而快取層對未鍵值輸入「視而不見」！                          |
| ➔ 帶毒請求與純淨請求擁有完全相同的 Cache Key Hash: MD5("GET|example.com|/static/app.js|?v=2")    |
+---------------------------------------------------------------------------------------------------+
```

### 2. 快取鍵正規化混淆 (Cache-Key Normalization Confusion)
除了未鍵值標頭外，**快取層與後端對 URL 路徑的正規化演算法歧異**是近代最隱蔽的投毒根源：

```
+---------------------------------------------------------------------------------------------------+
| 快取鍵正規化歧異時序分析 (Normalization Discrepancy Matrix)                                        |
|                                                                                                   |
| 攻擊者發送: GET /profile%2f..%2fadmin HTTP/1.1                                                    |
|                                                                                                   |
| 1. CDN / 快取層處理行為 (不解碼 URL):                                                             |
|    - 原始字串直接作為 Cache Key: Key = "/profile%2f..%2fadmin"                                    |
|    - 快取判定: 該路徑非靜態資源，亦非敏感路徑，允許快取。                                         |
|                                                                                                   |
| 2. 後端 Web 伺服器 (如 Tomcat/Nginx 自動解碼規範化):                                              |
|    - 自動進行 URL Decode: /profile/../admin ➔ 規範化為 /admin                                     |
|    - 後端執行 /admin 邏輯，回傳管理員相關頁面或未授權錯誤。                                       |
|                                                                                                   |
| 3. 投毒結果:                                                                                      |
|    - 管理員回應被快取在 Key "/profile%2f..%2fadmin" 之下。                                        |
|    - 攻擊者誘導他人存取該編碼連結，直接越權取得快取之機密內容。                                   |
+---------------------------------------------------------------------------------------------------+
```

#### 常見正規化歧異維度
1. **URL 解碼時機差異**：CDN 在計算 Key 時不解碼（保留 `%2e%2e`），而後端在路由前先解碼（解析為 `..`）。
2. **尾端斜線處理 (Trailing Slash Discrepancy)**：CDN 將 `/home` 與 `/home/` 視為兩個完全不同的 Cache Key，而後端框架（如 Spring/Django）自動重導向或視為同一處理器。
3. **查詢參數排序與忽略 (Query Parameter Stripping)**：CDN 設定配置了「忽略所有 UTM 追蹤參數（如 `utm_source`）以提高命中率」，但後端應用將 `utm_source` 作為渲染模板的一部分未經跳脫輸出。

### 3. 快取投毒拒絕服務 (Cache Poisoning Denial of Service - CPDoS)
投毒不僅能注入 XSS，更常被紅隊用於**直接癱瘓企業重要端點**。攻擊者誘使後端伺服器拋出 `400 Bad Request` 或 `500 Internal Error`，而快取伺服器卻將該錯誤狀態長期快取：

```
+---------------------------------------------------------------------------------------------------+
| CPDoS 核心架構與三大攻擊手法                                                                     |
|                                                                                                   |
| 1. HTTP 標頭過長 (HTTP Header Oversize - HHO):                                                    |
|    - CDN 允許單一 Header 達到 16 KB；但後端 Apache/Nginx 限制為 8 KB。                            |
|    - 攻擊者發送 12 KB 的超大標頭 ➔ CDN 正常轉發 ➔ 後端拋出 400 Bad Request ➔ CDN 將 400 儲存快取! |
|    - 後續正常用戶存取該網址，全數收到 400 錯誤，業務完全癱瘓！                                   |
|                                                                                                   |
| 2. 標頭中繼覆寫 (HTTP Method Override - HMO):                                                     |
|    - 發送 GET 請求，但帶有標頭: X-HTTP-Method-Override: POST                                      |
|    - CDN 依據 GET 進行快取，後端以 POST 處理並回傳 405 Method Not Allowed ➔ 405 被快取。          |
|                                                                                                   |
| 3. 協定中繼混淆 (HTTP Header Meta - HHM):                                                         |
|    - 傳入 X-Forwarded-Proto: gopher 造成後端找不到路由拋出 502/400 錯誤並被快取。                  |
+---------------------------------------------------------------------------------------------------+
```

## ⚡ 第二動：弱點驗證與分析技術 (Vulnerability Analysis & Vectors)

### 1. 核心向量與技術變體速查表

| 機制變體 | 關鍵注入標頭 / 參數構造 | 突防原理與作用標記 |
| :--- | :--- | :--- |
| **未鍵值主機標頭投毒 (Unkeyed Host)** | `X-Forwarded-Host: evil.com`<br>`X-Host: evil.com` | 後端生成靜態資源連結（如 `<script src="http://{HOST}/a.js">`）時採用該標頭，污染快取造成儲存型 XSS。 |
| **協定覆寫強制循環重導向** | `X-Forwarded-Proto: http` (發送到 HTTPS 端點) | 後端判定為 HTTP 請求，生成 `301 Moved Permanently to https://...`，造成永久重導向循環快取。 |
| **路徑覆寫標頭注入** | `X-Original-URL: /admin/console`<br>`X-Rewrite-URL: /admin/console` | 某些框架（如 Symfony / ASP.NET）支援該標頭覆寫路由，使首頁快取鍵快取了管理介面的內容。 |
| **CPDoS (HHO 超大標頭癱瘓)** | 注入 8 KB 長度的無效標頭：<br>`X-Oversized-Header: aaaa...` | 穿透 CDN 後引發後端伺服器拋出 `400 Bad Request`，該 400 回應被快取，導致全域正常使用者無法存取該頁面。 |
| **參數解耦混淆 (Fat GET / Query Confusion)** | `GET /blog?id=1`，但在 HTTP Body 中傳送 `id=2` | 快取鍵以 URL 上的 `id=1` 計算，後端某些框架卻優先讀取 Body 內的 `id=2`，造成資料混淆快取。 |

### 2. 精確差分探測流程 (CLI / cURL 驗證法)

在評估快取投毒時，**嚴格遵循 Cache-Buster 隔離三步驟**：

#### 步驟 1：建立專屬隔離鍵並獲取乾淨基準線 (Baseline)
```bash
# 使用隨機數 cb=probe_001 確保僅存取獨立快取槽
curl -i "https://target.internal/app.js?cb=probe_001"
# 觀察回應標頭：確認 X-Cache: MISS (初次未命中)
```

#### 步驟 2：發送包含無害 Canary 標記的未鍵值注入請求
```bash
# 注入自訂標記，檢驗後端是否將其反射至回應內容中
curl -i "https://target.internal/app.js?cb=probe_001" \
  -H "X-Forwarded-Host: audit-canary.internal"
# 觀察回應：檢查是否產生 X-Cache: MISS，且內容中包含 audit-canary.internal
```

#### 步驟 3：發送「純淨無標頭請求」驗證快取是否被真正污染
```bash
# 再次發送該 Cache-Buster 請求，但完全移除 X-Forwarded-Host 標頭！
curl -i "https://target.internal/app.js?cb=probe_001"
```
**判定依據**：
- 若回應標頭顯示 **`X-Cache: HIT`**，且回應主體中**依然殘留**了 `audit-canary.internal` 標記，即 100% 確證存在網頁快取投毒漏洞！

## 🥷 第三動：防禦規避與反鑑識分析 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與快取鍵偵測之技巧
- **參數隱蔽轉移 (Parameter Cloaking)**：
  部分快取伺服器（如特定版本的 Akamai 或 Varnish）在處理以 `?` 或 `&` 開頭的參數時具備特殊解析邏輯。例如使用分號 `;`（如 `/page?param=1;evil_param=2`），快取層視為單一參數，而後端 Ruby on Rails 或 Python 卻自動將分號解析為參數分隔符。
- **標頭註解與大小寫變形**：
  若 WAF 阻斷 `X-Forwarded-Host`，嘗試使用非標標頭變體：
  `X-Forwarded-Server`、`X-Original-Host`、`X-Forwarded-Scheme`。
- **無效 Content-Type 走私**：
  發送 GET 請求但夾帶 `Content-Type: application/x-www-form-urlencoded` 與 Form Body，部分後端會解析 Body 內的參數並覆寫 Query 參數，而快取層對 GET 請求的 Body 採取完全忽略策略。

### 2. 鑑識視角下的日誌殘留與遙測特徵
快取投毒的網路活動與常規攻擊存在顯著差異，其遙測指標集中在中繼層：

1. **快取狀態生命週期異常 (Cache State Telemetry)**：
   - 在 CDN/反向代理日誌中，針對同一 URI 出現典型的 **`MISS ➔ STORE ➔ HIT`** 序列，且觸發 `STORE` 的該筆請求帶有異常的自訂標頭。
2. **後端存取日誌與前台訪問量脫鉤 (Origin Log Discrepancy)**：
   - 投毒成功後，雖然前台有數萬名受害者存取該頁面，但後端伺服器的 Access Log 中**完全看不到這些請求**（全數被快取層直接響應 `HIT`），導致後端工程師誤判為無異常。
3. **異常 HTTP 狀態碼分佈 (CPDoS 特徵)**：
   - 監控系統（如 Datadog、Prometheus）偵測到特定高頻靜態資源的 HTTP 狀態碼突然由 `200 OK` 轉變為長達數小時的持續 `400 Bad Request`，且持續時間恰好與 CDN 的快取 TTL 一致。

| **正規化混淆 (URL Encoding 歧異)** | • 請求 URL 出現 `%2f`、`%2e`、或異常路徑片段。<br>• 靜態資源快取槽位中儲存了動態管理頁面內容。 | **Snort 規則**：<br>`alert http any any -> any any (msg:"Path Traversal in Cache Key"; content:"%2f..%2f"; nocase; sid:2140001;)` | • 在 CDN 邊界與後端實施**一致的 URL 解碼與正規化管線**（Canonicalization Pipeline）。 |
| **路徑覆寫標頭 (X-Original-URL)** | • 存取靜態副檔名（如 `/logo.png`），但帶有覆寫標頭，後端回傳 HTML 頁面。 | **WAF 規則**：<br>嚴格禁止非授權邊界傳入 `X-Original-URL` 與 `X-Rewrite-URL`。 | • 框架層全域關閉對微軟/第三方路徑覆寫標頭的支援。 |

## 🛡️ 第五動：安全加固與程式碼重構 (Hardening & Remediation Baseline)

### 1. 脆弱配置 vs. 工業級加固基線

#### ❌ 脆弱的反向代理快取配置 (Nginx / Varnish)
```nginx
# Nginx 脆弱配置：直接使用預設快取鍵，未鍵值標頭直接穿透
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m;

server {
    listen 80;
    location / {
        proxy_cache my_cache;
        # 缺陷：快取鍵僅由 scheme, host, request_uri 組成
        # 完全未鍵值化任何轉發標頭，且允許快取錯誤頁面！
        proxy_cache_key "$scheme$proxy_host$request_uri";
        proxy_pass http://backend_upstream;
    }
}
```

#### ✅ 工業級架構加固方案 (邊界標頭淨化與精確快取鍵)

##### 1. 剝離不可信未鍵值標頭 (Strip Untrusted Forwarded Headers)
在最外層邊界 CDN 或入口 Nginx 上，**強制移除客戶端偽造的轉發標頭**，禁止外部不可信輸入滲透至後端：

```nginx
# Nginx 工業級防護配置：
server {
    listen 443 ssl http2;
    server_name www.company.com;

    location / {
        proxy_cache my_cache;
        proxy_cache_key "$scheme$host$request_uri";

        # 1. 嚴禁快取任何非 200/301/302 回應，防禦 CPDoS
        proxy_cache_valid 200 301 302 10m;
        proxy_cache_valid 400 403 404 500 0s; # 絕對不快取錯誤！

        # 2. 強制清空客戶端傳入之不可信未鍵值標頭，由反向代理重寫
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Host "";
        proxy_set_header X-Original-URL "";
        proxy_set_header X-Rewrite-URL "";

        # 3. 尊重 Vary 標頭
        proxy_ignore_headers "Set-Cookie";
        proxy_pass http://backend_upstream;
    }
}
```

##### 2. 後端應用程式安全實作 (避免盲信 Host 標頭)
```python
# Python / Flask 安全實作：嚴格基於內部靜態設定生成 URL，禁止盲信請求標頭
from flask import Flask, request, url_for
app = Flask(__name__)

# 安全原則：伺服器靜態綁定網域名稱，嚴禁使用 request.headers.get('X-Forwarded-Host')
CANONICAL_DOMAIN = "https://www.company.com"

@app.route("/profile")
def profile():
    # 正確安全做法：始終使用固定的 Canonical Domain 載入資產
    asset_url = f"{CANONICAL_DOMAIN}/static/js/app.js"
    
    # 確保回傳正確的快取控制標頭
    response = app.make_response(f'<html><script src="{asset_url}"></script></html>')
    # 若內容與特定輸入相關，必須宣告 Vary 標頭！
    response.headers["Cache-Control"] = "public, max-age=3600"
    response.headers["Vary"] = "Accept-Encoding"
    return response
```

### 1. 靶場核心拓撲搭建 (Nginx 與 後端配置)

#### (1) 後端脆弱服務 (`origin_server.py`，極簡 15 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

class OriginHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        # 脆弱邏輯：後端盲目引用 X-Forwarded-Host 生成 JavaScript 引用
        host = self.headers.get("X-Forwarded-Host", "trusted.internal")
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.send_header("Cache-Control", "public, max-age=60")
        self.end_headers()
        self.wfile.write(f'<html><script src="http://{host}/tracker.js"></script></html>\n'.encode())

ThreadingHTTPServer(("127.0.0.1", 9142), OriginHandler).serve_forever()
```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是快取鍵中的「鍵值輸入 (Keyed Input)」與「未鍵值輸入 (Unkeyed Input)」？兩者的失衡為何會引發快取投毒？**  
  *分析思路*：鍵值輸入是快取伺服器用來計算 Cache Key 雜湊值的請求維度（如 Host、Path、特定 Query 參數）；未鍵值輸入則是快取演算法完全忽略的請求部分（如多數自訂 HTTP 標頭）。當後端伺服器在生成動態頁面內容時參考了未鍵值輸入，而快取伺服器卻認為不同未鍵值輸入的請求具有「完全相同的快取鍵」時，攻擊者便可將帶毒的回應綁定到正常快取鍵中，引發全域投毒。

- [ ] **Q2. 在安全稽核與滲透測試中，為什麼探測快取投毒時「必須嚴格使用 Cache-Buster」？若直接在生產環境的主頁進行測試會造成何種後果？**  
  *分析思路*：Cache-Buster（如 `?cb=nonce_123`）能確保探測流量被限制在獨立、未被其他使用者存取的專屬快取槽位中。若直接在生產環境向不帶參數的核心路由（如 `/` 或 `/login`）發送帶有惡意或錯誤標頭的請求，一旦投毒成功，所有存取該業務的真實使用者將在 TTL 存活期間內持續載入攻擊者的惡意腳本或遭遇 400/500 服務中斷 (CPDoS)，造成嚴重的生產事故。

- [ ] **Q3. 簡述「快取投毒 (Web Cache Poisoning)」與「快取欺騙 (Web Cache Deception)」在威脅模型與受害機制上的根本區別？**  
  *分析思路*：
  1. **快取投毒 (WCP)** 的本質是「攻擊者將惡意資料灌入共用快取，讓無辜受害者讀取受害」，受害者存取的是攻擊者製造的內容。
  2. **快取欺騙 (WCD)** 的本質則是「攻擊者誘使無辜受害者存取特定畸形連結，讓快取層錯誤地將受害者的個人隱私資料（如包含信用卡號的個人頁面）快取起來，隨後攻擊者再去讀取該快取」，受害的是受害者的機密隱私資料。

- [ ] **Q4. 什麼是快取投毒拒絕服務 (CPDoS)？攻擊者如何利用「HTTP 標頭過長 (HHO)」癱瘓整個網站？**  
  *分析思路*：CPDoS 是利用快取層與後端伺服器在處理極限請求時的行為差異。在 HHO 攻擊中，攻擊者利用 CDN 允許較大標頭（例如 16KB）但後端伺服器限制較小標頭（例如 8KB）的配置失衡，發送一個 12KB 大小的畸形標頭。CDN 轉發該請求後，後端因超過上限直接拋出 `400 Bad Request`。若 CDN 配置錯誤將此 400 狀態碼儲存快取，此後所有存取該頁面的正常使用者都會直接收到 400 錯誤，達成全域拒絕服務。

- [ ] **Q5. 針對網頁快取投毒，企業最徹底且架構級的縱深防禦措施為何？**  
  *分析思路*：
  1. **邊界標頭淨化**：反向代理與 CDN 必須在轉發前全面剝離或重寫所有不可信的轉發標頭（如 `X-Forwarded-*`、`X-Original-URL`）。
  2. **嚴格禁止錯誤快取**：快取層配置嚴格禁止快取任何 4xx / 5xx 狀態碼。
  3. **動態內容宣告規範**：後端若使用任何非標準標頭生成內容，必須在回應中明確標記 `Vary` 標頭（將該標頭納入 Cache Key），或宣告 `Cache-Control: private, no-store` 禁止共用快取儲存。
