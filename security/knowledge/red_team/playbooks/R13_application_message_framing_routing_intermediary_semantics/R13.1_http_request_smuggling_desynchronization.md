# R13.1 HTTP 請求走私與反向代理去同步化機制分析 (HTTP Request Smuggling & Desynchronization)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代雲端原生與微服務架構中，單一 Web 服務極少直接暴露於公網，而是普遍部署多層中繼代理架構（例如：CDN / WAF ➔ 反向代理負載平衡器 Nginx / Envoy / AWS ALB ➔ 後端應用伺服器 Tomcat / Gunicorn / Node.js）。為了提升網路 I/O 吞吐量並降低 TCP 3-Way Handshake 與 TLS 加解密帶來的巨大資源開銷，前置反向代理（Front-end Proxy）與後端伺服器（Back-end Server）之間普遍採用 **HTTP/1.1 管線化 (Pipelining)** 與**長連線池複用機制 (Keep-Alive TCP Connection Pooling)**——即將多個外部獨立用戶端發送的 HTTP 請求，循序打包透過同一條既有的持久化 TCP 連線管道傳輸給後端處理。

此高效架構高度依賴一個致命的協同假設：**「鏈路上所有的 HTTP 剖析器，對同一串位元組串流中的請求邊界（Message Framing Boundary）必須具備 100% 絕對一致的長度解析判定」**。

當邊界反向代理與後端伺服器在解讀 RFC 7230 規範中的傳輸長度標頭（`Content-Length` 與 `Transfer-Encoding`）時產生語意分歧，便會觸發**HTTP 請求走私 (HTTP Request Smuggling, HRS)** 與**連線串流去同步化 (Connection Desynchronization)**。攻擊者得以將第二個惡意請求的「前綴代碼（Smuggled Prefix）」悄無聲息地注入到共用的 TCP 連線快取佇列中，使其直接拼接在下一個無辜使用者的正常請求前端，達成**竊取他人認證憑證 (Session Hijacking)**、**繞過前端 WAF / 路徑存取控制**、**投毒反向代理快取 (Web Cache Poisoning)**、甚至是**竄改 API 回應實施任意 XSS**。

```
[攻擊者用戶端] ── 1. 提交二義性邊界請求 (CL-TE / TE-CL) ──► [邊界反向代理 (Front-end Proxy)]
                                                                      │
                                   ┌──────────────────────────────────┴──────────────────────────────────┐
                                   │ (依據 Parser A 判定請求結束)                                         │
                                   ▼                                                                     ▼
                      [轉發完整位元組串流至後端 TCP 管道]                                  [複用既有持久化連線 (Keep-Alive)]
                                   │                                                                     │
                                   └──────────────────────────────────┬──────────────────────────────────┘
                                                                      ▼
                                                        [後端應用伺服器 (Back-end Server)]
                                                                      │ (依據 Parser B 判定邊界)
                                                                      ├─► [處理前半段請求 ➔ 回應攻擊者]
                                                                      │
                                                                      ▼ (致命去同步化：殘留殘片留在 TCP 緩衝區)
                                                        [TCP Socket Buffer 殘留: 走私之惡意請求前綴]
                                                                      │
[受害使用者正常請求] ────────── 2. 發送 GET /index.html ───────────────┼─────────────────────────────────────┐
                                                                      ▼                                     │
                                                        [惡意前綴 + 受害請求 拼裝為畸形請求]               │
                                                                      │                                     ▼
                                                                      ▼                        [後端執行未授權操作]
                                                        [後端將包含受害者 Cookie/Token 的內容洩漏]         或
                                                                      │                        [直接回傳給受害者惡意 Payload]
                                                                      ▼
                                                        [攻擊者捕獲敏感 Session / 完成越權打擊]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統的前端部署了雲端 WAF（如 Cloudflare、AWS WAF）或反向代理，對直接存取敏感路由（如 `/admin`、`/internal/api`）實施了嚴格的路徑白名單或身份驗證攔截。
- **決策心流**：
  1. **拓撲連線複用探測 (Connection Reuse Verification)**：
     - 確認前端與後端之間是否存在持久化 TCP 複用通道。若後端每處理完一次請求即強制關閉連線 (`Connection: close`)，則難以造成跨請求佇列污染。
  2. **二義性解析分流 (Parsing Differential Identification)**：
     - **CL.TE 模式**：前端以 `Content-Length` (CL) 為準，後端以 `Transfer-Encoding` (TE) 為準。
     - **TE.CL 模式**：前端以 `Transfer-Encoding` (TE) 為準，後端以 `Content-Length` (CL) 為準。
     - **TE.TE 模式**：前後端均支援 TE，但其中一方能透過標頭混淆（Header Obfuscation）被誘導降級使用 CL。
     - **H2.CL / H2.TE (HTTP/2 降級走私)**：用戶端透過 HTTP/2 發送請求，前端在將其降級轉換為 HTTP/1.1 轉發時，注入了衝突的長度標頭。
  3. **安全審計與探測隔離原則 (Operational Safety Seam)**：
     - **嚴禁在生產環境隨機攔截一般使用者佇列**！合規測試必須採用基於**時延差分 (Timing-based Differential)** 探針，或在受控的專屬標記連線中完成單點閉環驗證。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. RFC 7230 訊息邊界規範與二義性根本成因
HTTP/1.1 規範 (RFC 7230 Section 3.3.3) 明確定義了訊息主體長度的計算優先權：

> **RFC 7230 §3.3.3 核心規則**：
> 1. 若請求中存在 `Transfer-Encoding` 標頭且最終編碼為 `chunked`，則必須忽略 `Content-Length` 標頭。
> 2. 若請求同時包含不相容的 `Content-Length` 與 `Transfer-Encoding`，這屬於潛在的語意二義性走私威脅，**代理伺服器在轉發前「應移除 Content-Length」或直接「拒絕該請求並回傳 400 Bad Request」**。

#### 漏洞發生的底層根源
現實中許多中繼代理軟體（尤其是混合搭配不同廠牌的架構，如 Nginx 前置 + Apache Tomcat 後端，或 HAProxy + WebLogic）為了歷史相容性或解析寬容度（Robustness Principle），未嚴格拋出 400 錯誤，而是各自遵循了不同的 Fallback 邏輯，造成**協定解讀脫鉤**。

### 2. CL.TE 與 TE.CL 去同步化物理時序解剖

#### (1) CL.TE 去同步化物理流程 (Front-end: Content-Length / Back-end: Transfer-Encoding)

```
+---------------------------------------------------------------------------------------------------+
| CL.TE 去同步化位元組串流結構 (CL.TE Byte-Stream Dissection)                                        |
|                                                                                                   |
| 攻擊者發送之 Raw HTTP 請求:                                                                       |
| POST / HTTP/1.1\r\n                                                                               |
| Host: vulnerable-bank.internal\r\n                                                                |
| Content-Length: 13\r\n           <--- [前端代理看見 CL=13]                                        |
| Transfer-Encoding: chunked\r\n   <--- [前端忽略 TE，認為 Body 總長度剛好為 13 位元組]              |
| \r\n                                                                                              |
| 0\r\n                            <--- [後端以 TE 解析: 長度為 0 的區塊 (0\\r\\n\\r\\n)]           |
| \r\n                                  後端判定「第一個請求已完整結束」！                          |
| G                                <--- [殘留於 TCP 緩衝區之走私位元組 (Smuggled Byte)]              |
|                                                                                                   |
| ------------------------------------------------------------------------------------------------- |
| 下一個無辜使用者的正常請求到達同一條 TCP 連線:                                                    |
| POST /login HTTP/1.1\r\n                                                                          |
| Host: vulnerable-bank.internal\r\n                                                                |
| ...                                                                                               |
|                                                                                                   |
| 後端伺服器在 TCP 佇列中看見的「第二個請求」被強制拼接變形為:                                     |
| GPOST /login HTTP/1.1\r\n        <--- [請求方法變成非法的 GPOST!]                                 |
| Host: vulnerable-bank.internal\r\n                                                                |
| ➔ 後端直接回傳 "Unrecognized method GPOST" 405/400 錯誤，造成服務拒絕或狀態暴露！                |
+---------------------------------------------------------------------------------------------------+
```

#### (2) TE.CL 去同步化物理流程 (Front-end: Transfer-Encoding / Back-end: Content-Length)

```
+---------------------------------------------------------------------------------------------------+
| TE.CL 去同步化位元組串流結構 (TE.CL Byte-Stream Dissection)                                        |
|                                                                                                   |
| 攻擊者發送之 Raw HTTP 請求:                                                                       |
| POST / HTTP/1.1\r\n                                                                               |
| Host: vulnerable-target.internal\r\n                                                              |
| Content-Length: 4\r\n            <--- [後端看見 CL=4，只讀取到 '5\\r\\nZ']                         |
| Transfer-Encoding: chunked\r\n   <--- [前端代理以 TE 解析: 正確讀取完所有 Chunk 直到 0 區塊結束] |

| 5c\r\n                           <--- [前端視為合法 Chunk，轉發整個封包給後端]                    |

| Host: vulnerable-target.internal\r\n  後續所有字串被當作「連線緩衝區中的下一個獨立請求」！        |
| Content-Length: 15\r\n                                                                            |
| \r\n                                                                                              |
```

### 3. TE.TE 標頭混淆技巧 (Transfer-Encoding Obfuscation Matrix)
當前端與後端**預設皆支援 `Transfer-Encoding: chunked`** 時，攻擊者可透過刻意製造符合 RFC 容錯模糊地帶的畸形 Header，誘騙其中一個代理軟體無法識別 TE 標頭而「退回使用 `Content-Length`」，將情境轉化為 CL.TE 或 TE.CL：

```
1. 標頭鍵前置/後置空白或 Tab:
   Transfer-Encoding: [Space]chunked
   Transfer-Encoding[\t]: chunked
   Transfer-Encoding : chunked

2. 垂直換行與行折疊 (Line Folding):
   Transfer-Encoding:
    chunked

3. 雙重標頭衝突與無效編碼 (Multiple Headers with Invalid Fallback):
   Transfer-Encoding: chunked\r\n
   Transfer-Encoding: identity

4. 標頭大小寫混用:
   Transfer-encoding: chunked
   transfer-encoding: chunked

5. 封裝垃圾字元繞過正則比對:
   Transfer-Encoding: xchunked
   X: X[\n]Transfer-Encoding: chunked
```

### 4. HTTP/2 降級走私架構 (H2.CL / H2.TE Downgrading Smuggling)
在現代架構中，許多 CDN 與負載平衡器對外部用戶端支援 **HTTP/2**，但在與後端通訊時，為了節省重新架構成本，會實施 **HTTP/2 降級至 HTTP/1.1 (HTTP/2 Cleartext Downgrade)**：

```
+---------------------------------------------------------------------------------------------------+
| HTTP/2 降級走私機制 (HTTP/2 Downgrade Vector)                                                     |
|                                                                                                   |
| [用戶端] ──────(HTTP/2 傳輸)──────► [邊界負載平衡器] ──────(降級為 HTTP/1.1)──────► [後端伺服器]   |
|                                                                                                   |
| 1. HTTP/2 具有嚴格的 Frame 長度:                                                                  |
|    - HTTP/2 不依賴 Content-Length 或 Chunked 劃分邊界，其 DATA Frame 長度由二進位 Header 明確指定  |
|                                                                                                   |
| 2. 注入衝突標頭:                                                                                  |
|    - 攻擊者在 HTTP/2 請求中故意注入自訂的 :authority 或自訂 Header:                               |
|      "content-length": "0" (但 DATA Frame 中實質帶有惡意 Body)                                    |
|                                                                                                   |
| 3. 邊界代理降級轉換缺陷:                                                                          |
|    - 邊界代理將 HTTP/2 串流轉換為 HTTP/1.1 純文字格式時，未剔除攻擊者傳入之 content-length 偽標頭! |
|    - 代理直接拼接:                                                                                |
|      POST /api HTTP/1.1\r\n                                                                       |
|      Content-Length: 0\r\n          <--- 攻擊者注入之數值                                         |
|      \r\n                                                                                         |
|      SMUGGLED_BODY...               <--- 後端直接將此視為管道中的下一個請求！                     |
+---------------------------------------------------------------------------------------------------+
```

### 2. 時延差分診斷腳本 (安全審計用途)

在生產環境進行走私檢測時，**絕對不可發送破壞性走私封包污染真實用戶連線**。合規的審計方式是採用 **時延差分檢測法 (Timing-Based Differential Detection)**：

```python
#!/usr/bin/env python3
"""
R13.1 HTTP 請求走私安全時延差分探測工具 (Safe Timing-Based Smuggling Probe)
用途：透過精確的 Socket 原始位元組串流，安全檢驗前後端剖析器邊界二義性，絕不污染生產佇列。
"""

import socket
import ssl
import time
import sys

TARGET_HOST = "target.internal"
TARGET_PORT = 443
USE_SSL = True

def send_raw_probe(probe_bytes, timeout_threshold=5):
    """發送原始位元組串流並精確計時"""
    start_time = time.time()
    try:
        sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        sock.settimeout(timeout_threshold + 2)
        if USE_SSL:
            context = ssl.create_default_context()
            context.check_hostname = False
            context.verify_mode = ssl.CERT_NONE
            sock = context.wrap_socket(sock, server_hostname=TARGET_HOST)
            
        sock.connect((TARGET_HOST, TARGET_PORT))
        sock.sendall(probe_bytes)
        
        # 嘗試讀取回應
        response = sock.recv(1024)
        elapsed = time.time() - start_time
        sock.close()
        return elapsed, response
    except socket.timeout:
        elapsed = time.time() - start_time
        return elapsed, b"TIMEOUT"
    except Exception as e:
        return 0, str(e).encode()

def audit_cl_te():
    """
    CL.TE 時延探針原理：
    若後端以 TE 處理，讀取到 'X' (長度為 1) 後，會持續等待下一行的 CRLF 與下一個 Chunk，
    導致連線發生顯著的 Read Timeout (延遲約 5-6 秒)！
    若後端以 CL 處理，讀完 4 位元組後會立即回傳回應 (耗時 < 1 秒)。
    """
    probe_cl_te = (
        b"POST / HTTP/1.1\r\n"
        b"Host: " + TARGET_HOST.encode() + b"\r\n"
        b"Content-Type: application/x-www-form-urlencoded\r\n"
        b"Content-Length: 4\r\n"
        b"Transfer-Encoding: chunked\r\n"
        b"\r\n"
        b"1\r\n"
        b"Z\r\n"
        b"Q"  # 後端在此等待後續 Chunk，引發逾時
    )
    
    print("[*] 正在發送 CL.TE 安全時延探針...")
    elapsed, resp = send_raw_probe(probe_cl_te, timeout_threshold=5)
    print(f"    探測耗時: {elapsed:.2f} 秒 (回應特徵: {resp[:20]}...)")
    
    if elapsed >= 4.5:
        print("[!] 警告：偵測到顯著連線延遲！目標系統極可能存在 CL.TE 去同步化弱點！")
        return True
    return False

def audit_te_cl():
    """
    TE.CL 時延探針原理：
    若後端以 CL 處理 (CL=6)，讀取完前置字串後，會持續等待補齊 6 個位元組，引發逾時。
    """
    probe_te_cl = (
        b"POST / HTTP/1.1\r\n"
        b"Host: " + TARGET_HOST.encode() + b"\r\n"
        b"Content-Type: application/x-www-form-urlencoded\r\n"
        b"Content-Length: 6\r\n"
        b"Transfer-Encoding: chunked\r\n"
        b"\r\n"
        b"0\r\n"
        b"\r\n"  # 前端在此結束；但後端若依賴 CL=6，尚缺資料，導致讀取掛起逾時
    )
    
    print("[*] 正在發送 TE.CL 安全時延探針...")
    elapsed, resp = send_raw_probe(probe_te_cl, timeout_threshold=5)
    print(f"    探測耗時: {elapsed:.2f} 秒 (回應特徵: {resp[:20]}...)")
    
    if elapsed >= 4.5:
        print("[!] 警告：偵測到顯著連線延遲！目標系統極可能存在 TE.CL 去同步化弱點！")
        return True
    return False

if __name__ == "__main__":
    print(f"[*] 開始對目標主機發起 HTTP 請求走私時延架構審計: {TARGET_HOST}:{TARGET_PORT}")
    is_cl_te = audit_cl_te()
    is_te_cl = audit_te_cl()
    
    if is_cl_te or is_te_cl:
        print("\n[!] 結論：目標架構具備嚴重的請求走私風險，需立即實施協定加固。")
        sys.exit(1)
    else:
        print("\n[+] 結論：未偵測到明顯的時延去同步化特徵。")
        sys.exit(0)
```

## 🥷 第三動：防禦規避與反鑑識分析 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與反向代理正規化之特徵分析
- **換行符號變體走私 (Line Ending Desync)**：
  部分 WAF 嚴格要求 RFC 標準的 `\r\n` (CRLF) 作為標頭分界。若後端伺服器（如 Node.js 或部分 Golang 早期版本）寬容地接受純 `\n` (LF) 作為換行，攻擊者在標頭中使用純 `\n` 即可讓 WAF 將整個走私載荷視為「單一巨大的 Header Value」放行，但後端卻將其解析為獨立的 Body。
- **Transfer-Encoding 標頭值大小寫與逗號分割**：
  - `Transfer-Encoding: chunked, identity`
  - `Transfer-Encoding: identity, chunked`
  - 部分代理若只比對第一個或最後一個逗號分割項，便會產生邏輯判定衝突。
- **雙重 Content-Length 數值分歧**：
  若攻擊者傳入兩個 `Content-Length` 標頭：
  ```http
  Content-Length: 4
  Content-Length: 100
  ```
  某些反向代理預設取第一個數值，而後端應用預設取最後一個數值，同樣能形成長度衝突走私。

### 2. 鑑識視角下的日誌殘留與遙測特徵
當請求走私發生時，受害系統會出現跨層級的非典型異常指標：

1. **前端與後端日誌請求計數嚴重失衡 (Request Count Discrepancy)**：
   - **核心特徵**：在同一條持久化 TCP 連線上，前端反向代理記錄了 $N$ 個請求，但後端應用伺服器卻記錄了 $N+1$ 個甚至更多請求！
2. **非預期 HTTP 狀態碼暴增 (400 / 404 / 405 Spikes)**：
   - 走私前綴與後續正常用戶請求拼裝時，極易產生非法的 HTTP Method（如 `GPOST`、`adminGET`）或不存在的 URL 路徑，導致後端短時間內大量產生 `405 Method Not Allowed` 或 `400 Bad Request`。
3. **TCP 連線非正常重置 (TCP RST Flags)**：
   - 當後端伺服器發現 HTTP 管線中的位元組流無法被合規語法解析時，會直接發送 TCP RST 封包中斷該連線池，監控設備可捕捉到異常密集的 `Connection Reset by Peer` 事件。
4. **網路封包 (PCAP) 解構特徵**：
   - 在網路鑑識封包分析中，比對同一 TCP Stream，可清晰觀察到多個 HTTP 請求標頭區塊（連續出現多個 `POST /` 或 `GET /`）直接緊密排列在同一個 TCP Payload 內部，且缺乏標準長度聲明。

## 🛡️ 第五動：安全加固與程式碼重構 (Hardening & Remediation Baseline)

### 1. 脆弱架構 vs. 工業級安全防護重構

#### ❌ 脆弱的架構配置 (混合協定與寬容轉發)
```nginx
# Nginx 脆弱反向代理配置範例：
http {
    upstream backend_pool {
        server 10.0.0.10:8080;
        keepalive 32; # 啟用後端 TCP 連線池複用，但未嚴格規範化長度標頭
    }
    server {
        listen 80;
        location / {
            # 缺陷：未校驗 HTTP/1.1 標頭二義性，直接透傳給後端
            proxy_pass http://backend_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
        }
    }
}
```

#### ✅ 工業級架構加固實現 (端到端強制規範化與連線隔離)

##### 1. 邊界嚴格拒絕二義性請求 (Zero-Tolerance Protocol Ambiguity)
在所有入口反向代理層（Nginx、Envoy、HAProxy）強制啟用嚴格 RFC 校驗，凡同時帶有 `Content-Length` 與 `Transfer-Encoding` 者一律阻斷：

```nginx
# Nginx 工業級加固配置：
http {
    # 1. 停用非標標頭的寬容解析，阻斷帶有底線或異常字元的標頭
    ignore_invalid_headers on;
    underscores_in_headers off;

    # 2. 針對二義性標頭進行嚴格阻斷
    map $http_transfer_encoding $has_te {
        default 0;
        "~.+"   1;
    }
    map $http_content_length $has_cl {
        default 0;
        "~.+"   1;
    }

    server {
        listen 443 ssl http2;
        server_name api.company.com;

        # 若同時存在 Transfer-Encoding 與 Content-Length，直接回傳 400
        set $smuggle_check "${has_te}${has_cl}";
        if ($smuggle_check = "11") {
            return 400 "Bad Request: Ambiguous Transfer-Encoding and Content-Length";
        }

        location / {
            proxy_pass http://backend_servers;
            proxy_http_version 1.1;

            # 3. 強制前端代理重新規範化長度標頭：
            # 轉發給後端時，一律由 Nginx 重新計算 Content-Length，消除客戶端偽造可能
            proxy_set_header Transfer-Encoding "";
            proxy_set_header Connection "";
        }
    }
}
```

##### 2. 全鏈路端到端 HTTP/2 (End-to-End HTTP/2 Architecture)
根治請求走私的最優解法是**徹底廢除中繼降級**。在代理與後端之間全面啟用 HTTP/2：
- HTTP/2 使用長度前綴的二進位訊框 (Binary Frames) 進行多工傳輸 (Multiplexing)，每個 Stream 具備獨立的 Stream ID，在協定層面徹底消除了 HTTP/1.1 文字型標頭的二義性邊界歧異。

##### 3. 停用後端持久化連線複用 (Disable Upstream Keep-Alive)
若系統無法全面升級 HTTP/2，且中繼軟體難以達成百分之百一致的 RFC 實作，最穩健的保底策略是**停用與後端伺服器的長連線池**：
```nginx
location / {
    proxy_pass http://backend_servers;
    # 強制每次請求後中斷 TCP 連線，絕不將多個使用者的請求串流在同一個 TCP 連線中！
    proxy_set_header Connection "close";
}
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗展示一個專屬的兩層受控沙盒環境，模擬前置代理 (CL 優先) 與後端應用 (TE 優先) 在面對二義性位元組時的去同步化物理現象。

### 1. 受控沙盒伺服器搭建 (`smuggling_lab.py`)
```python
#!/usr/bin/env python3
"""
R13.1 HTTP 請求走私受控演練沙盒 (Request Smuggling Lab Fixture)
包含：模擬反向代理層 (Port 9131) 與後端伺服器層 (Port 9132)
"""
import socket
import threading
import time

BACKEND_HOST = "127.0.0.1"
BACKEND_PORT = 9132
PROXY_HOST = "127.0.0.1"
PROXY_PORT = 9131

def run_backend_server():
    """模擬後端伺服器：優先遵循 Transfer-Encoding: chunked 規範"""
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind((BACKEND_HOST, BACKEND_PORT))
    s.listen(10)
    print(f"[*] 後端伺服器就緒於 {BACKEND_HOST}:{BACKEND_PORT}")

    while True:
        client, addr = s.accept()
        # 持續在該持久化 TCP 連線上讀取請求
        buffer = b""
        while True:
            try:
                data = client.recv(1024)
                if not data:
                    break
                buffer += data
                
                # 模擬 TE 解析器：檢查是否包含 0\r\n\r\n 區塊結尾
                if b"0\r\n\r\n" in buffer:
                    # 找到第一個 Chunked 請求結尾
                    req1_end = buffer.find(b"0\r\n\r\n") + 5
                    req1_bytes = buffer[:req1_end]
                    # 殘留緩衝區
                    buffer = buffer[req1_end:]
                    
                    print(f"[BACKEND] 處理請求 1 成功 (長度: {len(req1_bytes)})")
                    client.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 15\r\n\r\nREQ1_PROCESSED\n")
                    
                    # 若緩衝區中殘留位元組，且包含完整 HTTP 方法，立即將其視為「請求 2」！
                    if len(buffer) > 0:
                        print(f"[BACKEND] [!] 警告：偵測到管道殘留走私資料: {buffer[:30]}...")
                        # 處理走私請求
                        client.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 17\r\n\r\nSMUGGLED_SUCCESS\n")
                        buffer = b""
            except Exception:
                break
        client.close()

def run_proxy_server():
    """模擬前端代理：優先遵循 Content-Length 規範，並維護對後端的長連線"""
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind((PROXY_HOST, PROXY_PORT))
    s.listen(10)
    print(f"[*] 前端反向代理就緒於 {PROXY_HOST}:{PROXY_PORT}")

    # 維護對後端的單一持久化連線
    backend_conn = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    time.sleep(0.5)
    backend_conn.connect((BACKEND_HOST, BACKEND_PORT))

    while True:
        client, addr = s.accept()
        raw_req = client.recv(4096)
        
        # 前端粗暴地將整個封包直接透傳至後端 TCP 長連線
        backend_conn.sendall(raw_req)
        resp = backend_conn.recv(1024)
        client.sendall(resp)
        client.close()

if __name__ == "__main__":
    t_back = threading.Thread(target=run_backend_server, daemon=True)
    t_proxy = threading.Thread(target=run_proxy_server, daemon=True)
    t_back.start()
    t_proxy.start()
    print("[*] R13.1 演練靶場啟動完成。按 Ctrl+C 結束。")
    while True:
        time.sleep(1)
```

### 2. 演練與驗證步驟

#### 步驟 1：發送 CL.TE 走私請求
構造包含合法標頭長度但隱藏走私前綴的 Raw Socket 請求：
```bash
python3 -c '

# 構造標準 CL.TE 測試載荷
# 前端依照 Content-Length=33 轉發全部字串
# 後端依照 0\r\n\r\n 提前結束第一個請求，剩餘的 "GET /smuggled" 滯留在 TCP 管道中！
payload = (
    b"POST / HTTP/1.1\r\n"
    b"Host: 127.0.0.1:9131\r\n"
    b"Content-Length: 33\r\n"
    b"Transfer-Encoding: chunked\r\n"
    b"\r\n"
    b"0\r\n"
    b"\r\n"
```

**預期回顯**：

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼 HTTP 請求走私 (HRS) 必須依賴「反向代理與後端伺服器之間啟用持久化連線池 (Keep-Alive)」這項先決條件？**  
  *分析思路*：請求走私的根本機制是在共用的 TCP 位元組串流中造成「請求邊界判定脫鉤」。若前後端之間每次處理完請求就立即執行 TCP 4-Way Handshake 關閉 Socket (`Connection: close`)，任何殘留在緩衝區中的走私字串都會隨著 Socket 的銷毀而被作業系統核心直接丟棄，無法留存至下一個請求，因此無法達成跨請求佇列污染。

- [ ] **Q2. 在 CL.TE 漏洞模式中，為什麼攻擊者構造的 Body 必須以 `0\r\n\r\n` 作為開頭？底層解析器的行為是什麼？**  
  *分析思路*：後端伺服器在此模式下以 `Transfer-Encoding: chunked` 為準。在 Chunked 編碼規範中，`0\r\n\r\n` 代表「終止區塊 (Terminating Chunk)」，標誌著當前 HTTP 請求主體在此刻正式終結。後端看見此標記即認為第一個請求已接收完畢，立即結束讀取並執行商業邏輯；而後續緊隨的所有字串則被直接歸類為「同一條 TCP 管道中尚未處理的下一個全新 HTTP 請求」。

- [ ] **Q3. 在生產環境進行安全巡檢時，為什麼絕不能直接發送完整的惡意走私請求去驗證漏洞？合規的「時延差分檢測 (Timing-based Probe)」原理為何？**  
  *分析思路*：在線上環境發送未閉環的走私請求，殘留前綴會被隨機拼接到其他真實使用者的下一個請求上，造成無辜使用者的連線中斷、帳號資料洩漏或交易異常，構成嚴重的非受控業務破壞。時延差分檢測則是透過發送故意缺損長度的邊界標頭（如宣告 Chunk 長度為 1 卻不給足位元組），迫使後端解析器陷入阻塞等待逾時（Timeout 約 5 秒），透過純粹的「網路往返時間 (RTT)」確認二義性存在，全程不留殘留位元組給其他連線。

- [ ] **Q4. 許多現代架構採用 CDN 支援 HTTP/2 並在邊界將其降級 (Downgrade) 為 HTTP/1.1 轉發至後端。為什麼這種降級轉換極易衍生新的走私漏洞 (H2.CL / H2.TE)？**  
  *分析思路*：HTTP/2 採用二進位訊框 (Frame)，其長度是由 Frame 標頭明文定義的，本質上不需要 `Content-Length` 或 `Transfer-Encoding` 來劃分邊界。但邊界代理在降級重組為 HTTP/1.1 文字字串時，若盲目保留了攻擊者在 HTTP/2 自訂標頭中注入的 `content-length` 或 `transfer-encoding`，就會產生「前端依據 H2 訊框長度轉發、後端依據注入的 H1 標頭解析」的全新二義性脫鉤。

- [ ] **Q5. 針對企業分散式中繼代理架構，徹底根治 HTTP 請求走私的最優防禦架構為何？**  
  *分析思路*：最徹底的架構級解法是**全面實施全鏈路端到端 HTTP/2 或 HTTP/3 (End-to-End HTTP/2+)**，從公網邊界到內部微服務全面廢除純文字型 HTTP/1.1，統一採用二進位訊框長度模型。若短期架構受限於歷史系統，次優防線是在邊界代理實施**零容忍二義性標頭阻斷**（只要同時出現 CL 與 TE 一律回傳 400 Bad Request），並在與後端通訊時**強制重新計算並覆寫標準長度標頭**，或**停用後端連線池複用 (`proxy_set_header Connection "close"`)**。
