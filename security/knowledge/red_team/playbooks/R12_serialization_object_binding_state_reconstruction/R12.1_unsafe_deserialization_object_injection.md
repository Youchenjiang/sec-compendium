# R12.1 不安全反序列化與物件注入機制分析 (Unsafe Deserialization & Object Injection Analysis)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代分散式系統、微服務架構、企業快取層（如 Redis/Memcached）以及遠端程序調用 (RPC / RMI) 體系中，應用程式需要頻繁地在網路中傳輸複雜的記憶體資料結構。**序列化 (Serialization)** 是將記憶體中的即時物件圖譜（Object Graph）扁平化為連續的二進位位元組串流或文字字串的程序；而**反序列化 (Deserialization)** 則是將該串流重新還原為執行環境記憶體中可運作物件的逆向過程。

當應用程式接收來自未授權邊界的不可信資料，並直接調用直譯器或虛擬機的原生反序列化介面時，便會觸發**不安全反序列化 (Unsafe Deserialization)** 與**物件注入 (Object Injection)** 弱點。此弱點的核心威脅在於：**反序列化過程並非單純賦值欄位，而是具備「隱式執行（Implicit Execution）」特性的物件實體化過程**。在物件重建期間，直譯器會自動觸發目標類別的生命週期鉤子（Lifecycle Hooks / Magic Methods，如 Java 的 `readObject`、Python 的 `__reduce__`、PHP 的 `__wakeup`）。若類別路徑 (Classpath) 中存在可被串聯調用的特定類別，攻擊者無須在目標系統上傳任何新檔案，即可利用既有的合法程式碼片段組裝出**利用鏈 (Gadget Chain)**，達成任意遠端代碼執行 (RCE) 或伺服器狀態劫持。

```
[客戶端/攻擊者] ── 1. 投送特製序列化二進位/文字串流 ──► [Web/RPC 端點 (反序列化 Sink)]
                                                              │
                    ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
                    │                                                                                   │
                    ▼ (安全防禦架構：純資料 DTO + Schema 驗證)                                           ▼ (脆弱架構：原生多型反序列化)
       [嚴格型別資料傳輸物件 (DTO)]                                                       [虛擬機/直譯器底層反序列化引擎]
                    │                                                                                   │
                    ▼                                                                                   ▼
       [無邏輯純資料提取與白名單校驗]                                                    [遍歷串流標頭：動態尋找 Classpath 目標類別]
                    │                                                                                   │
                    ▼                                                                                   ▼
       [安全更新內部狀態 / 拒絕非預期類別]                                                [隱式觸發魔術方法 (readObject / __reduce__)]
                                                                                                        │
                                                                                                        ▼
                                                                                           [鏈式調用反射/動態代理/系統命令]
                                                                                                        │
                                                                                                        ▼
                                                                                           [取得伺服器進程控制權 (RCE) / 記憶體破壞]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統端點接收 Cookie (如 Java JSESSIONID、Shiro RememberMe)、HTTP 請求標頭、Message Queue (Kafka/RabbitMQ) 訊息或快取資料，且資料特徵符合特定序列化協定特徵（如 Base64 編碼的二進位魔術位元組）。
- **決策心流**：
  1. **協定特徵識別 (Protocol Fingerprinting)**：
     - 檢查輸入串流是否帶有特定語言原生序列化的 Magic Bytes（如 Java `0xACED`、Python Pickle `0x80`、.NET `AAEAAAD/////`、PHP `O:<len>:`、YAML `!!python/object`）。
  2. **類別路徑環境勘察 (Classpath & Gadget Availability)**：
     - 分析目標伺服器執行環境與相依套件版本（例如是否依賴 Apache Commons-Collections、Spring Framework、Jackson、Fastjson、Groovy 等）。
  3. **反序列化過濾策略判定 (Filter Evaluation)**：
     - 評估目標是否配置了 JEP 290 物件過濾器、黑名單檢驗或安全包裝器。
     - 若黑名單僅阻斷已知 Sink（如 `Runtime.getRuntime().exec`），分析是否能透過其他替代鏈（如 JNDI 注入、BCEL 動態載入、檔案任意寫入鏈）繞過限制。

### 1. Java 原生物件序列化串流協定 (Java Object Serialization Stream Protocol)
根據 Oracle Java 官方規範，Java 原生序列化二進位位元組串流具備高度嚴謹的結構定義：

```
+---------------------------------------------------------------------------------------------------+
| Java 序列化二進位協定結構解剖 (Java Serialization Protocol RFC / Spec)                             |
|                                                                                                   |
| 欄位位移 (Offset) | 欄位值 (Hex)      | 符號常數 (Constant)       | 語意與底層行為分析           |
| :---------------- | :---------------- | :------------------------ | :--------------------------- |
| 0x00 - 0x01       | AC ED             | STREAM_MAGIC              | 宣告此二進位串流為 Java 序列化 |
| 0x02 - 0x03       | 00 05             | STREAM_VERSION            | 串流協定版本號 (當前標準為 5)  |
| 0x04              | 73                | TC_OBJECT                 | 宣告接下來將實體化一個全新物件 |
| 0x05              | 72                | TC_CLASSDESC              | 宣告該物件的類別描述符       |
| 0x06 - 0x07       | 00 1E             | (Length = 30)             | 類別全域名稱字串長度         |
| 0x08 - 0x25       | 6F 72 67 2E ...   | "org.apache.commons..."   | 類別全限定名稱 (FQCN)         |
| 0x26 - 0x2D       | 1A 2B 3C ...      | serialVersionUID          | 類別版本相容性校驗雜湊值     |
| 0x2E              | 02                | classDescFlags (SC_SERIAL)| 類別特性旗標 (支援 Serializable)|
| 0x2F - 0x30       | 00 02             | (Field Count = 2)         | 物件內部成員屬性數量         |
+---------------------------------------------------------------------------------------------------+
```

#### 根本缺陷分析：JVM 實體化與 `readObject` 調用管線
當伺服器端調用 `objectInputStream.readObject()` 時，底層虛擬機的執行管線如下：
1. **類別載入**：根據串流中的類別名稱調用 `Class.forName(className, false, classLoader)`，從當前環境的 Classpath 載入對應類別。
2. **非建構子記憶體分配**：JVM 調用內部 API（如 `Unsafe.allocateInstance()` 或父類別的無參建構子）在堆積記憶體 (Heap) 中直接分配物件空間，**完全繞過目標類別本身的建構子保護邏輯**。
3. **魔術方法反射調用**：若該類別覆寫了私有的 `readObject(ObjectInputStream in)` 方法，JVM 會透過反射**主動調用該方法**以還原物件欄位。
4. **利用鏈組裝 (The Gadget Chain)**：若該類別在 `readObject` 內部實作了諸如「讀取 Map 內容」、「比較物件 HashCode」或「觸發動態代理調用 (InvocationHandler)」等看似正常的邏輯，便會連鎖觸發下游物件的特定方法，最終導向執行惡意二進位命令的危險 Sink（如 `TemplatesImpl.newTransformer()` 或 `Runtime.exec()`）。

### 2. Python Pickle 虛擬機堆疊架構 (Python Pickle VM Architecture)
Python 的 `pickle` 模組本質上並非靜態資料剖析器，而是一個**基於堆疊的微型虛擬機 (Stack-Based Virtual Machine)**：

```
+---------------------------------------------------------------------------------------------------+
| Python Pickle VM 執行位元組碼解剖                                                                  |
|                                                                                                   |
| 位元組碼 (Opcode) | 運算元 (Operand)                 | Pickle 堆疊虛擬機內部操作行為                |
| :---------------- | :------------------------------- | :------------------------------------------- |
| c (GLOBAL)        | os\nsystem\n                     | 將 os 模組的 system 函數物件推入虛擬機堆疊   |
| ( (MARK)          | (空)                             | 在堆疊頂端壓入一個 MARK 標記邊界             |
| S (STRING)        | 'id'\n                           | 將參數字串 'id' 壓入堆疊                     |
| t (TUPLE)         | (空)                             | 收集 MARK 標記以上的所有物件，組裝為 Tuple   |
| R (REDUCE)        | (空)                             | 從堆疊彈出 Tuple 與 Callable，執行:          |
|                   |                                  | ➔ os.system('id') 立即觸發執行！             |
| . (STOP)          | (空)                             | 終止 Pickle 虛擬機並回傳頂端運算結果         |
+---------------------------------------------------------------------------------------------------+
```

- **`__reduce__` 協定漏洞本質**：Python 允許類別定義 `__reduce__()` 方法以自訂序列化邏輯。該方法規範回傳一個可調用物件 (Callable) 及參數元組 (Tuple)。當 `pickle.loads()` 解析到 `R` (REDUCE) 操作碼時，會**無條件調用該 Callable 並傳入參數**，使攻擊者只需控制序列化字串即可在受害進程中執行任意 Python 內建或匯入之函數。

### 3. PHP 物件注入與 POP 利用鏈機制 (PHP Property-Oriented Programming)
在 PHP 中，`unserialize($input)` 能夠將字串重新還原為 PHP 物件實體：

```
序列化字串結構範例：
O:4:"User":2:{s:4:"name";s:5:"admin";s:4:"role";s:7:"manager";}
│ │   │    │  │    │     │    │
│ │   │    │  │    │     └─ 屬性值字串與內容
│ │   │    │  └─ 屬性名稱字串
│ │   │    └─ 屬性數量 (2 個成員屬性)
│ │   └─ 類別名稱 ("User")
│ └─ 類別名稱長度 (4 字元)
└─ 物件型態標記 (O = Object)
```

- **魔術方法調用鏈 (Magic Methods Dispatch)**：
  - `__wakeup()`：在 `unserialize()` 執行時立即觸發。
  - `__destruct()`：當物件被銷毀或 PHP 腳本執行完畢時自動觸發。
  - `__toString()`：當物件被視為字串處理（如 `echo $obj` 或字串拼接）時觸發。
  - `__call()`：調用物件不存在之方法時觸發。
- **POP 利用鏈 (Property-Oriented Programming)**：攻擊者透過精確構造巢狀的序列化物件屬性，將不同類別的成員變數相互鏈接，當反序列化觸發起點的 `__wakeup` 或 `__destruct` 時，便會如多米諾骨牌般層層傳遞，最終觸發具備代碼執行能力的危險函數（如 `eval`、`system`、`call_user_func`）。

### 2. 診斷與安全分析腳本 (安全審計用途)

本腳本用於安全稽核環境中，透過非破壞性的方式偵測目標 HTTP 端點是否盲目接受二進位/多型序列化輸入，並檢驗伺服器是否暴露危險的反序列化 Sink：

```python
#!/usr/bin/env python3
"""
R12.1 不安全反序列化端點安全診斷與協定嗅探腳本 (Deserialization Audit Probe)
用途：無害化稽核端點對各語言序列化特徵的處理模式，評估物件注入風險。
"""

import requests
import base64
import sys

TARGET_ENDPOINT = "http://target-api.internal/api/v1/session/restore"
HEADERS = {"User-Agent": "Security-Audit-Probe/1.0 (Deserialization-Detector)"}

# 1. 構造各語言的無害化序列化標記 (Canary Probes - 僅載入原生安全基礎型別)
# Java: 序列化一個標準的 java.lang.String 物件 (不含任何 Gadget)
JAVA_STRING_PAYLOAD = bytes.fromhex(
    "aced000574001041554449545f43414e4152595f544f4b454e" # String: AUDIT_CANARY_TOKEN
)

# Python: 序列化一個無害的純資料 dict: {'audit': 'canary'}
PYTHON_SAFE_PICKLE = b"\x80\x04\x95\x15\x00\x00\x00\x00\x00\x00\x00}\x94\x8c\x05audit\x94\x8c\x06canary\x94s."

# PHP: 序列化一個空陣列 a:1:{s:5:"audit";s:6:"canary";}
PHP_SAFE_SERIALIZED = b'a:1:{s:5:"audit";s:6:"canary";}'

def probe_serialized_acceptance(probe_name, payload_bytes, is_base64=False):
    """測試端點對特定序列化輸入的處理與回顯狀態"""
    data = base64.b64encode(payload_bytes).decode('ascii') if is_base64 else payload_bytes
    
    try:
        # 測試以 POST Body 或特定 Header 傳遞
        resp = requests.post(TARGET_ENDPOINT, data=data, headers=HEADERS, timeout=5)
        
        print(f"[*] 測試協定探針: [{probe_name}]")
        print(f"    狀態碼: {resp.status_code}, 回應長度: {len(resp.content)}")
        
        # 鑑識關鍵字：是否拋出反序列化特定的異常或堆疊追蹤
        error_indicators = [
            "ClassNotFoundException", "InvalidClassException", "java.io.ObjectInputStream",
            "pickle.UnpicklingError", "unserialize(): Error at offset",
            "TypeNameHandling", "Newtonsoft.Json.JsonSerializationException"
        ]
        
        for err in error_indicators:
            if err in resp.text:
                print(f"[!] 警告：端點回顯包含反序列化內部錯誤堆疊 [{err}]！")
                print(f"    證實底層引擎直接處理了不可信輸入，存在高度物件注入暴露風險。")
                return True
                
        if resp.status_code == 200:
            print(f"[?] 端點接受了序列化載荷且正常回傳 200，需進一步審查程式碼處理邏輯。")
            
    except requests.exceptions.RequestException as e:
        print(f"[-] 探針測試異常: {e}")
        
    return False

if __name__ == "__main__":
    print(f"[*] 開始對目標端點發起反序列化介面特徵審計: {TARGET_ENDPOINT}")
    v1 = probe_serialized_acceptance("Java Native Base64", JAVA_STRING_PAYLOAD, is_base64=True)
    v2 = probe_serialized_acceptance("Python Pickle Binary", PYTHON_SAFE_PICKLE, is_base64=False)
    v3 = probe_serialized_acceptance("PHP Serialized String", PHP_SAFE_SERIALIZED, is_base64=False)
    
    if v1 or v2 or v3:
        print("\n[!] 結論：偵測到潛在的反序列化處理漏洞，應立即採取防禦加固。")
        sys.exit(1)
    else:
        print("\n[+] 結論：未發現明顯的反序列化異常暴露特徵。")
        sys.exit(0)
```

## 🥷 第三動：防禦規避與反鑑識分析 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與簽章過濾之特徵分析
- **協定多重編碼與封裝走私**：
  許多 WAF 僅檢查傳輸層最外圍的明文字串。若序列化資料被放置在多層結構中（例如：HTTP 請求傳輸 GZIP 壓縮資料 ➔ 外層包裹 Base64 ➔ 內部為 Java 序列化二進位），未具備深度解包能力的防禦設備將無法識別 `0xACED0005` 特徵。
- **Python Pickle 操作碼混淆與異構編碼**：
  Pickle 支援 0 至 5 共 6 種協定版本。攻擊者可利用極端冷門的操作碼（如將全域名稱分割為 Unicode 轉義或多次動態拼裝堆疊）取代傳統的 `c` 操作碼，使基於正則比對 `cos\n` 的 IDS/IPS 規則失效。
- **PHP 序列化 `S` 型態十六進位轉義**：
  PHP 序列化字串支援大寫 `S` 作為字串標記（如 `S:4:"\61\64\6d\69"`），允許使用十六進位表示字元。若防禦過濾器採用黑名單比對危險類別名稱（如 `SplFileObject`），攻擊者將關鍵字元轉換為 `\53\70\6c...` 即可完全規避純文字比對。
- **多型 JSON/YAML 的 Unicode 與換行填充**：
  Fastjson 或 Jackson 等解析器支援在屬性鍵值中混入 Unicode 轉義（如 `\u0040\u0074\u0079\u0070\u0065` 等同於 `@type`）或大量空行，藉此脫鉤 WAF 模式比對。

### 2. 鑑識視角下的日誌殘留與遙測特徵
反序列化利用會留下極為獨特且難以抹除的主機記憶體與進程層級足跡：

1. **異常類別載入與 JVM 異常日誌**：
   - 應用程式日誌中頻繁出現 `java.lang.ClassNotFoundException`、`java.io.InvalidClassException` 或 `java.lang.ClassCastException`。這通常是攻擊者在探測遠端 Classpath 中存在的依賴庫版本所產生的殘留特徵。
2. **進程樹異常衍生 (Process Lineage - Sysmon Event ID 1 / Auditd `execve`)**：
   - Web 服務父進程（如 `java.exe`、`w3wp.exe`、`gunicorn`、`php-fpm`）直接衍生出作業系統指令直譯器（`cmd.exe`、`powershell.exe`、`/bin/sh`、`/bin/bash`）。這是 RCE 最明確的行為遙測特徵。
3. **出站連線遙測 (Network Egress - Sysmon Event ID 3)**：
   - 若利用鏈依賴 JNDI 注入（如 Fastjson/Log4j/Spring 利用鏈），受害主機會向外部伺服器發起非預期的 **LDAP (TCP 389/636)** 或 **RMI (TCP 1099)** 出站請求。
4. **記憶體核心轉儲 (Heap Dump) 鑑識**：
   - 在數位鑑識分析中，對 JVM 或 Python 進程進行 Heap Dump 萃取，可清晰檢視記憶體中殘留的畸形物件圖譜（如大量嵌套的 `BadAttributeValueExpException`、`ChainedTransformer` 結構）。

## 🛡️ 第五動：安全加固與程式碼重構 (Hardening & Remediation Baseline)

### 1. 脆弱程式碼 vs. 工業級安全防護重構

#### ❌ 脆弱的實現方式 (動態多型還原不可信輸入)
```python
# Python 範例：極度危險的原生反序列化
import pickle
import base64

def restore_user_session(cookie_data):
    # 嚴重弱點：直接反序列化不可信的客戶端 Cookie
    # 攻擊者透過構造帶有 __reduce__ 的載荷可直接取得伺服器控制權
    raw_bytes = base64.b64decode(cookie_data)
    user_session = pickle.loads(raw_bytes)
    return user_session
```

```java
// Java 範例：未加防護的原生 ObjectInputStream
public Object readSession(byte[] untrustedBytes) throws Exception {
    // 嚴重弱點：只要 Classpath 中存在 Commons-Collections 等相依庫，即刻面臨 RCE
    ObjectInputStream ois = new ObjectInputStream(new ByteArrayInputStream(untrustedBytes));
    return ois.readObject();
}
```

#### ✅ 工業級安全防護實現 (資料傳輸物件 DTO + 嚴格型別架構)
在安全系統架構中，防禦反序列化漏洞的唯一根本途徑是：**完全廢止原生物件多型序列化機制，將資料傳輸與程式碼執行徹底解耦**。

```python
# Python 安全重構：基於 Pydantic 的純資料 DTO (Data Transfer Object)
from pydantic import BaseModel, Field, ValidationError
import json
import base64

class UserSessionDTO(BaseModel):
    user_id: int = Field(..., ge=1)
    username: str = Field(..., min_length=3, max_length=50)
    role: str = Field(..., pattern="^(user|auditor|operator)$")
    theme: str = Field(default="light", pattern="^(light|dark)$")

def restore_user_session_safe(json_str: str) -> UserSessionDTO:
    """
    安全反序列化：僅解析純資料格式，絕無程式碼執行或物件魔術方法觸發可能
    """
    try:
        # 1. 僅使用安全之純資料剖析器
        data_dict = json.loads(json_str)
        
        # 2. 嚴格模式匹配與型別防護驗證 (Schema Validation)
        validated_session = UserSessionDTO(**data_dict)
        return validated_session
        
    except (json.JSONDecodeError, ValidationError) as e:
        # 安全失敗 (Fail-Safe)：記錄稽核日誌並拒絕服務
        raise ValueError(f"傳入資料未符合安全規範: {e}")
```

#### ✅ 深入防禦：若短期必須使用原生序列化（白名單過濾機制）
若因歷史相容性或複雜架構暫時無法替換原生序列化，必須實施**極其嚴格的類別白名單控制**：

##### Java JEP 290 序列化過濾器 (Serialization Filtering)
```java
// Java 原生安全過濾器配置 (JEP 290)
ObjectInputStream ois = new ObjectInputStream(untrustedStream);

// 建立嚴格的類別白名單過濾器：僅允許 java.lang.String 與自訂 DTO
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "com.company.app.dto.UserSessionDTO;java.lang.String;!*" // 結尾 !* 表示拒絕其他一切類別
);
ois.setObjectInputFilter(filter);

Object obj = ois.readObject();
```

##### PHP 類別白名單限制
```php
// PHP 7+ 安全 unserialize 配置
// 僅允許特定安全類別被還原，禁止載入非預期類別
$allowed_classes = ['UserDTO', 'ThemeDTO'];
$obj = unserialize($untrusted_data, ["allowed_classes" => $allowed_classes]);

// 若僅需純陣列/變數，全面禁用所有物件還原：
$data = unserialize($untrusted_data, ["allowed_classes" => false]);
```

### 2. 系統與執行時期環境硬化基線
1. **最小權限執行帳戶**：
   Web 伺服器與 RPC 進程嚴禁以 `root` 或 `SYSTEM` 權限運行，應建立專屬的受限服務帳戶（如 `appuser`）。
2. **網路出口防禦 (Egress Blocking)**：
   許多現代反序列化鏈（如 JNDI/Fastjson）依賴受害伺服器出站連線至攻擊者架設的 LDAP/RMI 伺服器。出口防火牆必須預設阻斷 DMZ 伺服器主動發起外部 TCP 389、636、1099 等非業務連接埠連線。
3. **依賴套件定期審查與裁減**：
   使用 Maven Dependency Check / Snyk 自動掃描並移除 Classpath 中已廢棄、含有已知 Gadget 的函式庫（如老舊版本之 Commons-Collections、Xalan、Groovy）。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗展示一個受控的沙盒環境，對比原生反序列化之風險與基於 DTO 架構之安全加固驗證。

### 1. 受控沙盒伺服器搭建 (`deserialization_lab.py`)
```python
#!/usr/bin/env python3
"""
R12.1 實戰演練沙盒環境 (Deserialization Lab Sandbox)
"""
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import json
import base64
import pickle

class SafeUserProfile:
    def __init__(self, username, theme="light"):
        self.username = username
        self.theme = theme

class LabHandler(BaseHTTPRequestHandler):
    def _send_json(self, status, payload):
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(json.dumps(payload).encode("utf-8"))

    def do_POST(self):
        content_length = int(self.headers.get("Content-Length", 0))
        raw_body = self.rfile.read(content_length)

        # 端點 1：脆弱原生反序列化端點
        if self.path == "/api/v1/vulnerable/restore":
            try:
                # 缺陷設計：直接使用 pickle 載入客戶端上傳之二進位
                obj = pickle.loads(raw_body)
                self._send_json(200, {
                    "status": "restored",
                    "type": str(type(obj)),
                    "theme": getattr(obj, "theme", "unknown")
                })
            except Exception as e:
                self._send_json(500, {"error": str(e)})

        # 端點 2：工業級加固 DTO 端點
        elif self.path == "/api/v1/secure/restore":
            try:
                # 安全設計：僅解析 JSON，並做嚴格白名單比對
                data = json.loads(raw_body.decode("utf-8"))
                if not isinstance(data, dict) or "theme" not in data:
                    self._send_json(400, {"error": "Invalid format"})
                    return
                
                theme = data.get("theme")
                if theme not in ["light", "dark"]:
                    self._send_json(400, {"error": "Invalid theme value"})
                    return
                
                self._send_json(200, {
                    "status": "accepted",
                    "applied_theme": theme
                })
            except Exception as e:
                self._send_json(400, {"error": "JSON parse error"})
        else:
            self._send_json(404, {"error": "Not found"})

if __name__ == "__main__":
    server = ThreadingHTTPServer(("127.0.0.1", 9121), LabHandler)
    print("[*] R12.1 演練沙盒啟動於 127.0.0.1:9121...")
    server.serve_forever()
```

### 2. 演練與驗證步驟

#### 步驟 1：向脆弱端點發送原生序列化狀態載荷
```bash
# 構造包含合法物件的序列化資料並提交至脆弱端點
python3 -c '
import pickle, sys
class SafeUserProfile:
    def __init__(self, username, theme):
        self.username = username
        self.theme = theme
sys.stdout.buffer.write(pickle.dumps(SafeUserProfile("alice", "dark")))
' | curl -X POST --data-binary @- http://127.0.0.1:9121/api/v1/vulnerable/restore
```
**預期回顯**：
- 伺服器成功還原物件並回傳 `{"status": "restored", "type": "<class '__main__.SafeUserProfile'>", "theme": "dark"}`，證實系統具備動態還原外部型別之能力。

#### 步驟 2：驗證安全端點對原生序列化載荷之免疫力
將相同的二進位 Pickle 串流提交至安全加固端點 `/api/v1/secure/restore`：
```bash
python3 -c 'import pickle, sys; sys.stdout.buffer.write(pickle.dumps({"theme": "dark"}))' | \
curl -X POST --data-binary @- http://127.0.0.1:9121/api/v1/secure/restore
```
**預期回顯**：
- 伺服器直接拒絕解析並回傳 `{"error": "JSON parse error"}`，二進位多型串流完全無法穿透純資料剖析防線。

#### 步驟 3：驗證安全 DTO 規範化純資料處理
```bash
curl -X POST -H "Content-Type: application/json" \
  -d '{"theme": "dark"}' \
  http://127.0.0.1:9121/api/v1/secure/restore
```
**預期回顯**：
- 系統正確解析純文字資料並套用配置 `{"status": "accepted", "applied_theme": "dark"}`，在徹底杜絕物件注入威脅的同時保留完整業務功能。

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 原生二進位反序列化（如 Java `readObject`、Python `pickle.loads`）與純文字 JSON 解析在底層物件生命週期上有何本質差異？**  
  *分析思路*：
  1. **純文字 JSON 解析** 本質上是純粹的「文字至資料結構」映射器（字串、數字、布林值、陣列、字典）。解析器只負責提取欄位鍵值對，**不包含類別型別中繼資料，不會自動從 Classpath 載入任意類別，亦絕不觸發任何執行期的魔術方法或生命週期鉤子**。
  2. **原生二進位反序列化** 則是「記憶體狀態重組器」。串流中攜帶了類別全限定名稱 (FQCN) 與內部欄位。反序列化引擎在還原過程中會動態載入目標類別、分配記憶體，並**強制調用其內部的自訂還原方法（如 `readObject` 或 `__reduce__`）**，在應用程式真正接觸該資料前即自動執行了類別內部預設的程式碼路徑。

- [ ] **Q2. 為什麼在 Java 反序列化攻擊中，即使應用程式本身的業務代碼完全沒有漏洞，僅靠環境 Classpath 中包含的第三方通用函式庫（如 Apache Commons Collections），攻擊者就能達成遠端代碼執行？**  
  *分析思路*：
  1. Java 反序列化機制在還原物件時，具備動態查詢當前進程 ClassLoader 的特性。只要第三方庫打包在應用程式相依項中，該函式庫內的類別對反序列化引擎而言皆屬於「合法可載入目標」。
  2. 第三方庫中某些類別在實作 `readObject` 或相關生命週期方法時，設計了用於動態變換資料、反射調用或處理事件的邏輯（如 `ChainedTransformer`、`LazyMap`）。
  3. 攻擊者將這些零散分佈在第三方函式庫中的合法類別像積木般拼接成「利用鏈 (Gadget Chain)」，將資料流一步步導引至執行系統命令的最終 Sink（如 `InvokerTransformer`），因此根本無須依賴業務程式碼本身的邏輯漏洞。

- [ ] **Q3. Python `pickle` 模組的底層虛擬機 (Pickle VM) 與 `__reduce__` 協定是如何在底層實現代碼執行的？**  
  *分析思路*：
  1. Python `pickle` 是一個基於堆疊運算的微型虛擬機，具有專屬的操作碼 (Opcodes)。
  2. `__reduce__()` 是 Python 物件模型定義的序列化介面，規範物件在序列化時回傳一個可調用對象 (Callable，如函數或類別) 與一組引數元組 (Tuple of arguments)。
  3. 當 Pickle VM 在解析還原過程中讀取到操作碼 `R` (REDUCE) 時，會主動從堆疊中取出該 Callable 與參數，並直接以底層 C 語言等級執行 `callable(*args)`。因此只要控制串流中的 Callable 為 `os.system` 或 `subprocess.Popen`，即可在反序列化發生的瞬間立即觸發命令執行。

- [ ] **Q4. Java JEP 290 序列化過濾器的工作機制是什麼？為什麼說單純依賴「黑名單 (Blacklisting)」類別過濾永遠無法提供絕對的安全保證？**  
  *分析思路*：
  1. JEP 290 提供了一種在反序列化期間攔截類別載入的機制 (`ObjectInputFilter`)。在每個類別被實體化前，先將類別名稱傳入過濾器進行比對判定（REJECTED / ALLOWED / UNDECIDED）。
  2. **黑名單的致命缺陷** 在於 Classpath 的動態性與利用鏈的無窮演進。黑名單只能阻斷「已公開已知」的危險類別（如 Commons-Collections 3.1 的特定類別）。
  3. 一旦相依套件更新、引入新的函式庫，或是安全研究員在 JDK 核心類別及次要套件中發掘出全新的 Gadget 組合，黑名單便會立刻被繞過。唯有採取「預設全數拒絕，僅放行業務必需之自訂 DTO」的**嚴格白名單 (Strict Whitelisting)** 才能徹底阻斷風險。

- [ ] **Q5. 在現代高併發、大規模的企業微服務架構中，若欲徹底杜絕不安全反序列化弱點，最權威且推薦的架構級演進方案為何？**  
  *分析思路*：
  1. **全面廢止原生物件多型序列化**：在全組織標準中明令禁止使用 Java `ObjectInputStream`、Python `pickle`、PHP `unserialize()`、.NET `BinaryFormatter`。
  2. **採用強型別結構化純資料通訊協定**：全面遷移至 **Protocol Buffers (Protobuf)**、**gRPC** 或標準純資料 **JSON Schema**。這些協定天生具備嚴格的 IDL (Interface Definition Language) 編譯期型別約束，不傳遞程式碼邏輯與類別中繼資訊。
  3. **邊界輸入實施不可變資料傳輸物件 (Immutable DTO)**：所有外部輸入一律先進入無行為能力的 DTO 模型，經過型別、長度、正則與業務邊界校驗通過後，方可由內部領域服務轉換為核心實體物件，從架構層面實現「資料」與「執行邏輯」的絕對隔離。
