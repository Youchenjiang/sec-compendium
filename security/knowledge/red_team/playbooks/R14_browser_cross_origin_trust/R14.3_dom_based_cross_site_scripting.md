# R14.3 DOM 型跨站腳本攻擊機制與防禦分析 (DOM-Based Cross-Site Scripting)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**DOM 型跨站腳本 (DOM-Based XSS, DOM XSS)** 是完全發生在客戶端瀏覽器記憶體與 JavaScript 直譯環境中的代碼注入漏洞。其本質為：**「前端 JavaScript 腳本從不受信任的來源（Source，如 `location.hash`、`location.search`、`postMessage`）讀取不可信資料，未經適當校驗或淨化，直接將該資料傳遞至具備代碼或 HTML 執行能力的危險輸出點（Sink，如 `innerHTML`、`eval`、`document.write`），觸發瀏覽器執行未授權腳本」**。

```
[攻擊者] ── 1. 誘騙受害者開啟帶有 Hash 的 URL (https://target.com/#<img src=x onerror=...>)
                                                              │
                                                              ▼ (URL Fragment # 不會傳送給伺服器！)
[邊界 WAF / 反向代理] ◄── 2. GET / HTTP/1.1 (WAF 看到的請求完全正常，無任何攻擊特徵碼)
         │
         ▼ 3. 伺服器回傳乾淨的靜態 HTML 與前端 bundle.js
[受害者瀏覽器]
         │
         ├── 4. 瀏覽器載入 bundle.js 並執行
         ├── 5. 前端代碼讀取 Source: let val = location.hash.slice(1);
         ▼ 6. 資料流未經淨化直接流入 Sink: document.getElementById('view').innerHTML = val;
[DOM Tree 突變] ➔ 觸發 onerror 事件直譯執行 JavaScript ➔ Cookie / Token 外洩！
```

### 核心作戰決策與邊界
- **最大戰術優勢**：**天然免疫網路層 WAF**。當 Payload 位於 URL Fragment (`#`) 中時，瀏覽器根本不會將 `#` 後方的位元組隨 HTTP 請求發送給伺服器，網路流量與後端日誌中完全不存在攻擊特徵。
- **作戰決策心流**：
  1. **定位前端 Source**：分析 JS 檔案中存取 `location.href`、`location.hash`、`document.referrer`、`window.postMessage` 的邏輯。
  2. **追蹤污點傳播鏈 (Taint Flow)**：透過靜態代碼審查或瀏覽器 DevTools 追蹤變數是否流向危險 Sink。
  3. **閉合與突變執行**：針對具體 Sink（HTML、代碼執行、URL 跳轉）選擇對應載荷。
- **技術邊界**：
  - **與反射型 (R14.1) 差異**：反射型 XSS 的 Payload **必須經過後端伺服器並包含在 HTTP 回應 Body 中**；DOM XSS 伺服器端回應內容可為純靜態頁面，污染完全在前端形成。

## 🔬 第一動：底層機制與 Source-Sink 污染流 (Mechanics & Sources/Sinks)

### 1. 常見前端來源 (Sources) 與危險接收端點 (Sinks)

| 類別 | 端點名稱 | 安全風險與特性 |
| :--- | :--- | :--- |
| **輸入來源 (Sources)** | `location.hash` | **WAF 盲區**：資料不發往伺服器，純前端解析。 |
| | `location.search` | 查詢參數，可被後端與前端同時存取。 |
| | `document.referrer` | 上一頁來源 URL，常用於動態返回按鈕。 |
| | `window.postMessage` | 跨視窗/iframe 通訊，若未校驗 `event.origin` 即遭偽造。 |
| | `localStorage` / `sessionStorage` | 本地快取資料（若曾遭次要注入則形成二階 DOM XSS）。 |
| **HTML 執行 (Sinks)** | `element.innerHTML`<br>`element.outerHTML` | 將字串作為 HTML 元素插入，自動解析標籤與事件監聽器。 |
| | `document.write()` | 覆寫整個 DOM 結構，可直接插入 `<script>` 標籤。 |
| **代碼直譯 (Sinks)** | `eval()`<br>`setTimeout()` / `setInterval()` | 將傳入之字串直接交由 JavaScript 直譯引擎執行。 |
| **導航跳轉 (Sinks)** | `location.href`<br>`location.assign()` | 若傳入 `javascript:...` 偽協定，將立即觸發腳本執行。 |

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心注入向量速查表

| 模式與 Sink 類型 | 典型 Payload | 作用與突防原理 |
| :--- | :--- | :--- |
| **`innerHTML` 注入** | `#<img src=x onerror=alert(document.domain)>` | HTML5 規範禁止 `innerHTML` 執行 `<script>`，但 `<img>`、`<svg>` 等事件仍會執行。 |
| **`eval()` 污染** | `?callback=alert(1)//` | 前端將參數直接傳入 `eval("data = " + callback)`，以註解符 `//` 截斷語法。 |
| **`location.href` 跳轉** | `?redirect=javascript:alert(document.domain)` | 前端未驗證 URL 協定，直接跳轉引發偽協定執行。 |
| **`postMessage` 偽造** | `win.postMessage('<img src=x onerror=...>', '*')` | 目標前端監聽 `message` 事件未檢驗 `e.origin`，直接將 `e.data` 寫入 DOM。 |
| **DOM Clobbering 輔助** | `<a id="config" href="javascript:alert(1)">` | 覆寫未初始化的全域變數 `window.config`，誘導前端呼叫其惡意屬性。 |

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **前端字串過濾繞過**：
  - 若前端使用 `val.replace("<script>", "")`：使用雙寫標籤或改用事件標籤 `<svg onload=...>`。
  - 若前端過濾括號 `()`：利用反引號模板字串 `alert\`1\`` 或 `throw onerror=alert,1`。
- **鑑識與監控特徵**：
  - **後端日誌無痕跡**：傳統 Web Access Log 完全看不到基於 `#` 的 Payload，常規 SIEM 規則完全失效。
  - **前端錯誤遙測**：Sentry / Datadog RUM 等前端 APM 監控捕獲到異常的 JavaScript 語法錯誤（如 `Uncaught SyntaxError` 或未預期的 DOM 突變）。
  - **CSP 違規報告 (CSP Violation Reports)**：若啟用 `report-uri`，前端會向後端回報違規嘗試與觸發行號。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **Hash 碎片注入** | 後端無日誌；前端 APM 報錯 | 全面改用 `textContent` 替代 `innerHTML` | 尋找允許寫入屬性之次要 Sink (`setAttribute`) |
| **偽協定跳轉** | RUM 監測到非預期外聯或跳轉 | 強制驗證跳轉 URL 僅允許 `http:` / `https:` | 利用特殊編碼或白名單子網域繞過 |
| **postMessage 偽造** | 跨網域通訊頻繁觸發異常 | 監聽器嚴格檢查 `event.origin === TRUSTED_DOMAIN` | 受信任網域自身存在 XSS 時遭跨源借道利用 |
| **DOM Clobbering** | 全域變數型態與預期不符拋出例外 | 變數宣告強制使用 `const`/`let`，禁止依賴 window 屬性 | 針對老舊瀏覽器或特定框架內部全域物件碰撞 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 安全 DOM 賦值 API 基線
```javascript
// ❌ 脆弱寫法：直接指派至可執行 HTML 的 Sink
document.getElementById("output").innerHTML = location.hash.slice(1);

// ✅ 加固寫法 1：純文字節點賦值（自動跳脫所有 HTML 語法）
document.getElementById("output").textContent = location.hash.slice(1);

// ✅ 加固寫法 2：若必須渲染富文字，引入 DOMPurify
document.getElementById("output").innerHTML = DOMPurify.sanitize(location.hash.slice(1));
```

### 2. postMessage 接收端安全校驗基線
```javascript
window.addEventListener("message", (event) => {
    // 1. 嚴格白名單比對 Origin（絕對禁止使用萬用字元 *）
    if (event.origin !== "https://trusted-partner.company.com") {
        console.warn("Blocked untrusted postMessage from: " + event.origin);
        return;
    }
    
    // 2. 嚴格進行型態校驗，禁止直接寫入 DOM
    if (typeof event.data === "string") {
        document.getElementById("status").textContent = event.data;
    }
});
```

### 3. 新世代防禦：Trusted Types API 與 CSP
```http
# 強制所有危險 Sink 必須經過 Trusted Types 策略過濾
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types default;
```

## 🧪 實戰演練環境導引 (Hands-on Range Lab Walkthrough)

### 1. 靶場核心代碼 (`dom_xss_lab.html`，極簡 20 行)
```html
<!DOCTYPE html>
<html>
<head><title>DOM XSS Lab</title></head>
<body>
    <h1>使用者歡迎面板</h1>
    <div id="greeting"></div>

    <script>
        // 脆弱 Source: location.hash
        const hash = window.location.hash.slice(1);
        if (hash) {
            const isSafe = window.location.search.includes("safe=1");
            if (isSafe) {
                // 安全防禦：textContent 純文字渲染
                document.getElementById("greeting").textContent = decodeURIComponent(hash);
            } else {
                // 缺陷端點：直接傳入 innerHTML Sink
                document.getElementById("greeting").innerHTML = decodeURIComponent(hash);
            }
        }
    </script>
</body>
</html>
```

### 2. 三步驗證流程

1. **本機啟動靜態伺服器**：
   ```bash
   python -m http.server 8143
   ```
2. **瀏覽器觸發 DOM XSS**：
   在測試瀏覽器中開啟帶有 Hash 的網址：
   ```
   http://127.0.0.1:8143/dom_xss_lab.html#<img src=x onerror=alert(document.domain)>
   ```
   - 瀏覽器載入頁面，執行腳本讀取 Hash，立即觸發 `alert` 彈窗！
3. **驗證加固參數**：
   開啟加固 URL：
   ```
   http://127.0.0.1:8143/dom_xss_lab.html?safe=1#<img src=x onerror=alert(document.domain)>
   ```
   - 頁面將載荷完整渲染為純文字字串，不觸發任何腳本執行，加固生效！

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 為什麼基於 `location.hash` 的 DOM XSS 能夠 100% 繞過傳統邊界 WAF 與後端審查？**  
  *分析思路*：依據 HTTP 規範，URL 中的 Fragment (`#`) 屬於客戶端本地錨點，瀏覽器在發起 HTTP 請求時根本不會將 `#` 後方的字串發送給伺服器；因此 WAF 與伺服器日誌完全接收不到攻擊載荷。

- [ ] **Q2. 為什麼在 DOM XSS 中，透過 `innerHTML` 注入 `<script>alert(1)</script>` 往往無法觸發，而必須使用 `<img src=x onerror=...>`？**  
  *分析思路*：HTML5 規範明確規定，透過 `innerHTML` 動態插入的 `<script>` 標籤不應被執行；然而，`<img>`、`<svg>` 等多媒體標籤在被插入 DOM Tree 時，瀏覽器會立即嘗試解析其屬性並載入資源，載入失敗觸發的 `onerror` 事件處理器不屬於腳本標籤限制範疇，因此會被正常執行。

- [ ] **Q3. 什麼是 DOM Clobbering？它在 DOM XSS 攻擊鏈中扮演何種輔助角色？**  
  *分析思路*：利用具有 `id` 或 `name` 屬性的 HTML 元素（如 `<form id="x">`、`<a>`）覆寫 JavaScript 全域命名空間中未初始化的全域變數或物件屬性；攻擊者可藉此操控前端邏輯的判斷流程，迫使前端代碼調用惡意構造的 URL 或物件，最終流向危險 Sink 觸發 XSS。

- [ ] **Q4. 在監聽 `window.addEventListener("message", ...)` 時，最致命的安全缺陷是什麼？**  
  *分析思路*：未驗證傳入訊息的來源來源（未檢查 `event.origin`），導致網路上任何第三方惡意網頁皆可透過 `iframe.contentWindow.postMessage` 向受害頁面投遞偽造資料，若後續代碼直接將 `event.data` 寫入 DOM Sink，即引發跨源 DOM XSS。

- [ ] **Q5. 徹底根治 DOM XSS 的最現代化標準與工程防線是什麼？**  
  *分析思路*：全面改用安全 API（如 `textContent` 代替 `innerHTML`）；必須渲染 HTML 時使用經過審查的 DOMPurify 白名單過濾；架構層級部署 CSP `require-trusted-types-for 'script'`（Trusted Types API），由瀏覽器引擎層面強制攔截所有未經型態包裝的危險 Sink 賦值。
