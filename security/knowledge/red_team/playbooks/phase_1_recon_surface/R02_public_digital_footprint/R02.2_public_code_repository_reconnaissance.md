## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

## 🔬 第一動：Git 物件模型、Commit DAG 與機密遺留物理機制 (Mechanics & Git Objects)

### 1. Git 內部儲存架構與機密殘留機制

| Git 物件類型 | 物理儲存機制 | 密碼學特性 | 機密外洩原理解析 |
| :--- | :--- | :--- | :--- |
| **Blob (二進位大物件)**| 儲存具體檔案內容之原始二進位串流 | 以內容 SHA-1/SHA-256 命名 | 即使檔案在當前分支被刪除，歷史 Blob 依然完好留存 |
| **Commit (提交物件)** | 記錄樹物件指標、作者、父提交 SHA | 有向無環圖 (DAG) 結構 | 任何歷史版本皆可藉由 `git checkout <hash>` 完整還原 |
| **Reflog (引用日誌)** | 記錄本機 HEAD 游標變更歷史 | 留存於本地 `.git/logs/` | 即使執行 `git reset --hard`，孤立物件在垃圾回收前依然可讀 |
| **GitHub Search API** | 對公開公共代碼庫實施分詞倒排索引 | 限制檢索結果與速率 | 僅支援檢索預設分支，歷史 Commit 需拉取本地掃描 |

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **部署強制性 Pre-commit 本機攔截機制**：
   - 團隊全面配置 **pre-commit** 工具鏈並集成 `gitleaks` 或 `detect-secrets`；在程式碼提交至本地 Git 前強制掃描，禁止任何包含金鑰之代碼落地。
2. **採用統一機密保管庫 (Secret Management Vault)**：
   - 全面推行 HashiCorp Vault、AWS Secrets Manager 或 Azure Key Vault；應用程式透過 IAM 角色動態取得短期憑證，杜絕程式碼硬編碼。
3. **歷史提交深度物理清洗 (Git History Scrubbing)**：
   - 若機密已推送到遠端，僅刪除該檔案無效；必須使用 `git-filter-repo` 或 **BFG Repo-Cleaner** 重寫全部歷史 Commit，並在後端立即輪換該金鑰。

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：開發者在發現機密外洩後，立即執行 `git rm secret.txt` 並推送新 Commit，為何無法解決問題？**
  - **戰術思維**：因為 Git 是基於快照的有向無環圖 (DAG)；新 Commit 只是記錄「此版本不再包含此檔案」，但**先前的舊 Commit 物件與對應的 Blob 仍然完好保存在 Git 資料庫中**，任何人只要 `git checkout HEAD~1` 即可完整提取該機密。
- [ ] **Q2：何謂「香農熵 (Shannon Entropy)」，其在機密掃描工具中扮演何種角色？**
  - **戰術思維**：香農熵用來度量字串中資訊的**隨機度與混亂程度**。一般英文單詞的熵值較低，而經過密碼學強雜湊或加密生成的私鑰/Token（如 Base64/Hex 金鑰）具有極高的熵值；藉由計算熵值，工具能在未定義專門正則的情況下挖掘出未知的高隨機性金鑰。
- [ ] **Q3：搜尋 GitHub 企業代碼時，為何針對「個人使用者帳號」的檢索常比企業官方 Repo 收穫更大？**
  - **戰術思維**：企業官方組織帳號通常受嚴格的 CI/CD 與安全掃描管制；而員工在家加班或進行離線測試時，常順手將公司代碼上傳至其**未受企業管轄的個人 GitHub 帳號或公開 Gist**，成為最致命的防線漏洞。
- [ ] **Q4：TruffleHog 的 `--only-verified` 參數具備何種關鍵作戰價值？**
  - **戰術思維**：該參數在掃描到金鑰特徵時，會**自動向對應的官方雲端 API (如 AWS STS, Slack, Stripe) 發起輕量驗證**，直接回報該金鑰「是否依然有效存活」，大幅節省紅隊手動驗證假陽性的寶貴時間。
- [ ] **Q5：若目標企業將程式碼託管在私有內網 GitLab 上，紅隊如何被動尋找外洩線索？**
  - **戰術思維**：檢索外部工程師社群（如 StackOverflow、Issue 討論區）；開發者在提問除錯時，常將包含公司內部網域、私有 API 路徑甚至連線 Token 的日誌截圖或設定檔片段黏貼於公開問答中。
