## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**DNS 候選主機名枚舉與置換推導 (Active Subdomain Brute-Forcing & Permutation)** 的物理本質為**利用高速非同步 DNS 解析引擎（如 PureDNS / MassDNS），將字典暴力窮舉與語意置換規則（如 `dev-`、`-prod`、`01`、`02`）相結合，向全球成千上萬個公開遞迴解析器併發發送百萬級 DNS 查詢，藉以挖掘被動情報庫中完全不存在之隱密端點**。紅隊必須在數秒內精確識別並剔除「萬用字元解析 (Wildcard DNS / Catch-All)」所造成的假陽性干擾，收割出真正具備實體 IP 綁定之深層子網域。

```

┌───────────────────────────────────────────────┴───────────────────────────────────────────────┐

                                                │
                                                ▼ 【關鍵演算法】自動偵測並過濾萬用字元解析 (Wildcard)
[精準收割真實活躍之深層子網域] ────────────────► 捕獲內部新上線之微服務、影子資料庫與專屬後台！

## 🔬 第一動：萬用字元解析機制與置換演算法物理架構 (Mechanics & Permutations)

### 1. 萬用字元 DNS (Wildcard DNS) 物理機制與過濾演算法

| 解析架構狀態 | 伺服器 DNS 配置 | 隨機不存在域名 (`uuid123.corp.com`) 應答 | 紅隊過濾判定演算法 |
| :--- | :--- | :--- | :--- |
| **無萬用字元 (Normal)** | 僅定義具體 A 記錄 | 回傳 `NXDOMAIN` (代碼 3) | 凡回傳 `NOERROR` 且有 A 記錄者即為真實存在 |
| **全域萬用字元 (Catch-All)**| `*.corp.com IN A 1.2.3.4` | 回傳 `NOERROR` 並給出固定 IP | **必須先發送隨機 UUID 取得萬用字元 IP 基線**，過濾所有命中該 IP 之結果 |
| **動態負載萬用字元** | 萬用字元回傳隨機輪替之 IP 池 | 回傳隨機 IP 集合 | 透過多次抽樣建立萬用字元 IP 集合 (IP Set) 實施集合排除 |

# 1. 產生純淨的高可信公用 DNS 解析器清單 (避免污染與投毒干擾)
dnsvalidator -tL https://public-dns.info/nameservers.txt -threads 100 -o resolvers.txt

# 2. 透過 PureDNS 實施高速字典枚舉 (自動濾除 Wildcard 萬用字元干擾)
puredns bruteforce /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt corp.internal \
    -r resolvers.txt -w puredns_brute.txt

# 3. 基於已知資產發動置換推導 (Gotator 語意延伸)
gotator -sub known_seeds.txt -perm permutations.txt -depth 1 -numbers 3 -mindup | \
    puredns resolve - -r resolvers.txt -w permutation_results.txt

# 4. 底層極致高效能 MassDNS 解析 (百萬條目秒級驗證)
massdns -r resolvers.txt -t A -o S candidate_domains.txt -w massdns_raw.txt
```

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **謹慎配置萬用字元解析 (Careful Wildcard Deployment)**：
   - 評估業務必要性；非必要切勿在公開根網域配置 `*.corp.com` 萬用字元記錄，避免掩蓋未授權端點與干擾內部排錯。
2. **制定標準化、不可預測之命名原則 (Secure Naming Conventions)**：
   - 杜絕使用簡單規律主機名（如 `dev1`, `dev2`, `staging-vpn`）；敏感內部測試環境應改用隨機雜湊前綴（如 `t9x-dev.corp.com`）。
3. **部署內部 DNS 查詢審計與蜜罐記錄**：
   - 在 DNS 區域中埋設從未正式使用的「蜜罐主機名」；一旦有外部或內部主機發起解析請求，立即告警並定位洩漏源頭。

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：在 DNS 暴力枚舉中，為何使用「公共解析器清單 (Resolvers List)」比直接向目標權威 NS 查詢安全得多？**
  - **戰術思維**：若用單一攻擊機直接向目標權威 NS 每秒發送數萬次查詢，目標伺服器日誌會瞬間被攻擊機 IP 填滿並觸發 RRL 限速；將查詢分發給 5,000 個全球公共 DNS 伺服器，目標權威 NS 看到的來源是全球分散的遞迴快取伺服器，完全隱蔽攻擊機真實 IP。
- [ ] **Q2：萬用字元 DNS (Wildcard DNS) 對傳統枚舉工具會造成何種毀滅性「假陽性」災難？**
  - **戰術思維**：若目標配置了萬用字元，所有隨意拼湊的無效主機名（如 `asdf1234zxcv.corp.com`）都會回傳 `NOERROR` 與 A 記錄；若工具缺乏過濾演算法，會將字典中的數百萬個詞彙「全數誤報為真實存在」，徹底癱瘓後續分析。
- [ ] **Q3：何謂「0x20 編碼」，其在 DNS 查詢防禦規避中有何特殊物理意義？**
  - **戰術思維**：DNS 協定在理論上不區分大小寫。利用 ASCII 編碼中大小寫相差第 5 個位元 (0x20) 的特性，在查詢時隨機大小寫交替（如 `aPi-DeV.cOrP.cOm`）；若回應封包能精確鏡像保留該隨機大小寫，可用於防止中間人偽造與快取投毒。
- [ ] **Q4：在 Gotator 置換演算法中，為何通常不建議將深度 (Depth) 設為大於 2？**
  - **戰術思維**：因為置換組合數隨深度呈**指數級爆炸 (Combinatorial Explosion)**。深度為 1 產生數萬個候選，深度設為 3 可能產生上億個無效條目，不僅耗盡網路頻寬與記憶體，更會大幅降低單兵作戰效率。
- [ ] **Q5：PureDNS 相比傳統 Sublist3r 或 DNSRecon 在架構上有何革命性突破？**
  - **戰術思維**：PureDNS 底層基於 **MassDNS** 的高效 C 語言非同步 socket 引擎，並在 Go 語言層封裝了高度精準的「智慧型萬用字元動態偵測演算法」與「無效解析器自動剔除池」，兼具每秒數萬解析吞吐與極致的低誤報率。
