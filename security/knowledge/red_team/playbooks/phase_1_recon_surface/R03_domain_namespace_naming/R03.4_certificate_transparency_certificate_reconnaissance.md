# R03.4 憑證透明度日誌與 TLS 憑證情資檢索 (Certificate Transparency Reconnaissance)

---

## 🎯 作戰任務破題 (Tactical Objective & Mental Workflow)

**憑證透明度情資檢索 (Certificate Transparency, CT)** 的物理本質為**利用全球公開憑證授權機構 (CA) 依 RFC 6962 規定必須將所有新簽發之 X.509 憑證公開寫入「僅可追加之密碼學默克爾樹日誌 (Append-Only Merkle Tree Logs)」的產業強制要求，在「零網路發包、完全被動」的前提下，100% 完整收割目標組織的所有公開與內部子網域名稱**。開發者在為內部測試站 (`dev-sso.corp.com`) 申請免費 Let's Encrypt 或商業憑證的瞬間，該主機名即刻被全網廣播，成為紅隊最新鮮、零滯後的攻擊目標來源。

```
[目標工程師為新內部站申請 TLS 憑證] ── 向 Let's Encrypt / DigiCert 提交 CSR
                                                │
                                                ▼ CA 簽發前【強制要求】寫入公有 CT 日誌
[全球公開 Merkle Tree 日誌 (Google CT / Cloudflare)] ◄── 廣播包含 SAN 擴充屬性之 X.509 證書
                        │
                        ▼ 紅隊被動監聽 (crt.sh / Certstream)
┌───────────────────────┴───────────────────────────────────────┐
│ 1. 檢索主體替代名稱 (SAN): dev-internal.corp.com, vpn-test.corp.com│
│ 2. 即時捕獲新增資產: 數秒內捕捉到幾分鐘前才剛上線之全新伺服器 │
│ 3. 識別發證 CA 與有效時序: 判定是否為企業內部測試還是正式資產  │
└───────────────────────┬───────────────────────────────────────┘
                        ▼
[高精度子網域字典自動擴充] ─────► 繞過傳統字典枚舉猜測，精確命中 100% 真實存在之主機名稱！
```

## 🔬 第一動：RFC 6962 規範、SCT 機制與 SAN 欄位物理結構 (Mechanics & CT Physics)

### 1. 憑證透明度日誌物理結構對照表

| 元件/欄位 | 結構規範 | 物理運作機制 | 紅隊情資萃取價值 |
| :--- | :--- | :--- | :--- |
| **SCT (簽署時間戳)** | `SignedCertificateTimestamp` | CA 證明該憑證已提交至 CT 日誌之密碼學承諾 | 瀏覽器強制校驗，確保持續全網公開 |
| **SAN 擴充欄位** | `subjectAltName: dNSName` | 單一憑證綁定之多個二級、三級乃至多級子域名 | **情報核心** (一次性洩漏數十個內部主機名) |
| **Append-Only Log** | 密碼學 Merkle Tree Hash | 歷史記錄只增不減，任何人無法刪除或篡改 | **永恆留存** (即使網站已下線，記錄永遠在冊) |
| **萬用字元 (Wildcard)**| `*.corp.internal` | 覆蓋所有同級子域名，隱藏具體主機名 | **藍隊唯一能阻斷 CT 情報洩漏之憑證型態** |

## ⚡ 第二動：戰術執行與工具鏈操作 (Attack Vectors & Automation)

### 1. 核心憑證透明度檢索指令速查表 (crt.sh / Certstream / Amass)

```bash
# 1. 透過 crt.sh JSON API 提取目標網域之全部子域名與 SAN 記錄
curl -s "https://crt.sh/?q=%.corp.internal&output=json" | jq -r '.[].name_value' | sed 's/\*\.//g' | sort -u > ct_subdomains.txt

# 2. 即時監聽全球最新簽發之 SSL 憑證資料流 (Certstream 實時雷達)
certstream --json | jq -r 'select(.data.leaf_cert.all_domains[] | contains("corp.internal")) | .data.leaf_cert.all_domains[]'

# 3. 專門針對 CT 日誌進行快速子域名萃取 (CTFR Python 工具)
python3 ctfr.py -d corp.internal -o ct_output.txt

# 4. OWASP Amass 整合多重 CT 日誌提供商進行高覆蓋率被動枚舉
amass enum -passive -d corp.internal -include-unresolvable -o amass_ct.txt
```

## 🛡️ 第五動：工程級防禦基線 (Hardening Baselines)

1. **全面推行萬用字元憑證 (Mandatory Wildcard Certificates)**：
   - 內部與測試系統一律簽發 `*.corp.internal` 萬用字元憑證；**嚴禁為特定伺服器簽發包含具體主機名 (如 `secret-api.corp.internal`) 的單一憑證**，阻斷主機名稱外洩。
2. **部署 DNS CAA 記錄 (Certification Authority Authorization)**：
   - 在 DNS 根節點配置 CAA 記錄，嚴格限定僅允許指定的商業 CA 為企業簽發證書：
     ```dns
     corp.internal. IN CAA 0 issue "digicert.com"
     corp.internal. IN CAA 0 iodef "mailto:security@corp.internal"
     ```
3. **建立即時 CT 日誌主動監控管道**：
   - 整合即時 CT 監控系統，一旦發現有外部 CA 為企業網域簽發了非預期證書，10 分鐘內啟動內部資產排查。

## 🎯 作戰驗收檢查點 (Operational Checkpoints)

- [ ] **Q1：為何主流瀏覽器（如 Chrome, Safari）強制要求所有公開 TLS 憑證必須具備 SCT？**
  - **戰術思維**：歷史上曾發生 DigiNotar 等 CA 遭入侵並私下偽造 Google/Yahoo 偽憑證實施中間人攻擊。SCT 與 CT 日誌制度迫使 CA 在簽署憑證時「必須公開入庫受全網監督」，徹底杜絕黑箱簽發。
- [ ] **Q2：使用萬用字元憑證 (Wildcard, 如 `*.corp.com`) 為何是防禦 CT 洩漏的唯一物理手段？**
  - **戰術思維**：因為寫入 CT 日誌的主體替代名稱 (SAN) 就只會是純粹的 `*.corp.com` 字串，**完全不包含特定主機名稱**。外部攻擊者從日誌中完全無法獲知背後究竟存在 `dev` 還是 `admin`。
- [ ] **Q3：在 CT 日誌中發現包含特定連接埠綴詞之網域（如 `jira.corp.com:8443`）代表何事？**
  - **戰術思維**：代表後端特定非標準埠服務同樣掛載了合法公開憑證，為紅隊直接指明了傳輸層非標準埠位的存在，節省了全埠位掃描的大量時間。
- [ ] **Q4：Certstream 工具在紅隊持續性威脅情報 (Threat Intelligence) 中有何核心價值？**
  - **戰術思維**：Certstream 是 WebSocket 串流服務，它實時消費全球所有 CT 日誌的最新事件。紅隊可在背景常駐監聽，**在目標企業剛為新系統申請憑證的 5 秒之內**，自動收到告警並啟動無痕攻擊。
- [ ] **Q5：DNS CAA 記錄能否直接阻止現有 CT 日誌的洩漏？**
  - **戰術思維**：**不能阻止現有記錄的洩漏**，但它能限制「誰可以簽發證書」。透過 CAA 封鎖免費無門檻的自動化 CA（如 Let's Encrypt），能有效阻止內部員工私自申請證書，從源頭減少影子資產進入 CT 日誌的機會。
