## 🚨 案發現場破題 (The Incident Scenario)

> **情境帶入**：  
> 週五下午 17:30，距離下班只剩半小時。SOC 告警看版突然跳出一條中級告警：  
> `[SIEM Alert] Potential Lateral Movement Activity on Host: DC-PRIMARY-01`  
> 
> 分析師打開這台核心網域控制站（DC）的事件日誌。  
> 雖然防毒軟體沒有發出任何報警，但系統日誌（System Log）中赫然記錄下一筆 **Event ID 7045（新服務安裝）**：  
> - **服務名稱**：`PSEXESVC`  
> - **服務檔案路徑**：`%SystemRoot%\PSEXESVC.exe`  
> - **服務啟動類型**：需求啟動（Demand Start）  
> - **服務帳戶**：`LocalSystem`  
> 
> 緊接著，在安全日誌（Security Log）中，連續出現了數筆 **Event ID 4688（新處理程序建立）**：  
> - 衍生出的進程為 `cmd.exe`，其後續執行的命令列參數竟然是：  
>   `cmd.exe /c "powershell -enc JABjAGwAaQBlAG4AdAA... && net user backup_admin Password123! /add"`  
> 
> 攻擊者正透過 PsExec 工具，利用合法 Windows 服務控制管理器（SCM）進行橫向移動，並以 SYSTEM 最高權限在背景靜默下發惡意 PowerShell 腳本、甚至直接新增了網域後門帳號！  
> 為什麼很多企業的 SIEM 雖然收了幾千萬筆 4688 日誌，卻完全看不到黑客下了什麼命令（命令列一片空白）？  
> 服務安裝的背後，登錄檔到底動了哪裡？身為防守方，我們該如何透過 7045 與 4688 的神級聯防，在幾秒鐘內還原黑客在終端機敲下的每一個字？
>
> **本手冊的使命**：帶你深入 Windows 服務底層架構（SCM）與進程建立審計機制，掌握 GPO 開啟「命令列參數完整記錄」的關鍵開關，並運用 PowerShell 與 Splunk 撰寫獵殺橫向移動、惡意持久化服務與 Base64 混淆指令的作戰查詢。

## 🧩 第一動：底層機制解剖——服務安裝與進程建立的物理痕跡

在 Windows 系統中，軟體安裝為服務或執行命令列，會在作業系統核心留下兩組不可磨滅的基石日誌：**System Log 中的 7045** 與 **Security Log 中的 4688**。

### 1.1 Event ID 7045（新服務安裝）底層架構

Windows 服務由 Service Control Manager（SCM，進程為 `services.exe`）統一管理。當透過 `sc create`、PowerShell 或 PsExec 建立新服務時，SCM 會將服務資訊寫入登錄檔：  
`HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>`，並**立即在 System 日誌中產生 Event ID 7045**：

```yaml
Event ID: 7045 (A service was installed in the system)
Source:   Service Control Manager
Log:      System

Service Information:
  Service Name:  PSEXESVC                  <-- [關鍵 1: 服務名稱，常為隨機亂碼或黑客工具名稱]
  Service File:  %SystemRoot%\PSEXESVC.exe <-- [關鍵 2: 執行路徑！是否為 cmd.exe / powershell.exe？]
  Service Type:  user mode service         <-- 核心驅動 (kernel driver) 還是用戶態服務？
  Start Type:    demand start              <-- 自啟動 (auto start) 還是手動/需求啟動？
  Account Name:  LocalSystem               <-- [關鍵 3: 運行身分！多為 SYSTEM 最高特權！]
```

---

### 1.2 Event ID 4688（新處理程序建立）與命令列記錄

預設情況下，Windows Security 日誌雖然會記錄 4688，但**預設「不包含」命令列參數（Process Command Line 為空）**！這意味著你看得到黑客打開了 `powershell.exe`，卻看不到他執行了什麼惡意代碼！

- **開啟關鍵開關**：必須透過 GPO 或登錄檔開啟 `Include command line in process creation events`。
- **4688 核心欄位解構**：

```
[Event ID 4688 核心結構]
├── Subject (發起者身分)
│   ├── Security ID / Account Name (誰執行了這個命令？)
│   └── Logon ID (可用於回溯 Event ID 4624 登入來源！)
├── Process Information (被建立的新進程)
│   ├── New Process ID (新進程的十六進位 PID，如 0x1A4)
│   ├── New Process Name (新進程絕對路徑，如 C:\Windows\System32\cmd.exe)
│   ├── Token Elevation Type (權杖提升類型：管理員特權還是普通權限)
│   └── Process Command Line (★ 靈魂所在！完整執行的命令列參數！)
└── Parent Process Information (生出此進程的母體)
    ├── Process ID (母進程 PID)
    └── Parent Process Name (★ 母進程路徑！若是 Word/Excel 生出 cmd.exe，必為巨集病毒！)
```

## 🧭 第二動：解碼意圖——服務與命令列異常速查表

在分析 7045 與 4688 日誌時，你該如何區分是微軟官方更新，還是黑客在植入後門？

### 2.1 服務與進程異常速查表

| 日誌特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **7045 服務路徑為 `cmd.exe /c` 或 `powershell.exe`** | **非標準二進位服務（Script as Service）**：<br>攻擊者不編譯標準的 Windows 服務二進位檔，直接將命令列腳本註冊為服務以執行無檔案持久化或反彈 Shell。 | • **影響**：攻擊者以 SYSTEM 權限執行任意腳本。<br>• **處置優先級**：緊急（立即停止服務並刪除該服務鍵值）。 |
| **7045 服務名稱為 `PSEXESVC` 或 8-10 位隨機英數字** | **PsExec / Impacket 橫向移動**：<br>微軟 PsExec 預設服務名為 `PSEXESVC`；而開源滲透庫 Impacket `psexec.py` 會隨機生成類似 `bHjKqWzx` 的無意義名稱。 | • **影響**：內網跳板正在攻陷該主機。<br>• **處置優先級**：高（定位來源 IP 並斬斷 SMB/RPC 管道）。 |
| **7045 服務類型為「核心驅動程式 (kernel driver)」** | **BYOVD 攻擊 (自帶脆弱驅動提權/盲化 EDR)**：<br>黑客安裝一個帶有合法微軟簽名、但存在已知漏洞的舊版驅動程式，藉此在核心層幹掉防毒軟體或 EDR。 | • **影響**：核心層完全失陷，安全軟體失效。<br>• **處置優先級**：緊急（排查驅動 SHA256 並撤銷加載）。 |
| **4688 母進程為 `WINWORD.EXE` 或 `EXCEL.EXE`，子進程為 `powershell.exe`** | **Office 釣魚惡意巨集啟動 (Maldoc Execution)**：<br>受害者打開釣魚郵件中的 Office 誘餌文檔，巨集（VBA）或外部物件直接衍生出命令提示字元執行代碼。 | • **影響**：使用者端點遭釣魚郵件攻陷。<br>• **處置優先級**：高（隔離該端點，抓取郵件附件樣本）。 |
| **4688 命令列包含 `-enc`, `-EncodedCommand`, `IEX`, `DownloadString`** | **PowerShell Base64 混淆與無檔案下載**：<br>攻擊者使用 Base64 編碼規避字串檢測，並在記憶體中遠端拉取惡意 Stager 執行。 | • **影響**：端點正在載入未知記憶體木馬。<br>• **處置優先級**：高（解碼 Base64 字串還原真實攻擊命令）。 |

## 💻 第三動：現場追兇——作戰指令與檢驗腳本

身為現場調查員，你必須掌握配置開啟命令列記錄，以及在海量日誌中秒級定位惡意服務的技能。

### 3.1 確保環境已開啟「命令列完整審計」（必備前置作業）

如果端點未開啟命令行審計，4688 的價值將大打折扣。在主機上檢查並強制開啟：

```powershell
# 1. 透過登錄檔直接啟用「進程建立命令列審計」(免重開機即時生效)
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit" -Name "ProcessCreationIncludeCmdLine_Enabled" -Value 1 -Type DWord

# 2. 確保進程建立審計原則已開啟 (成功/失敗均記錄)
auditpol /set /subcategory:"處理程序建立" /success:enable /failure:enable
```

### 3.2 PowerShell 現場排查指令庫

#### 步驟 1：抓出最近 24 小時內所有新安裝的服務（Event ID 7045）
```powershell
# 提取過去 24 小時內的 7045 事件並結構化輸出
Get-WinEvent -FilterHashtable @{
    LogName   = 'System'
    Id        = 7045
    StartTime = (Get-Date).AddHours(-24)
} | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        ServiceName = ($data | Where-Object { $_.Name -eq 'ServiceName' }).'#text'
        ImagePath   = ($data | Where-Object { $_.Name -eq 'ImagePath' }).'#text'
        ServiceType = ($data | Where-Object { $_.Name -eq 'ServiceType' }).'#text'
        StartType   = ($data | Where-Object { $_.Name -eq 'StartType' }).'#text'
        AccountName = ($data | Where-Object { $_.Name -eq 'AccountName' }).'#text'
    }
} | Format-Table -AutoSize
```

#### 步驟 2：獵殺 4688 中的危險 LOLBAS 命令與 Base64 混淆指令
```powershell
# 搜尋帶有混淆、下載或高危工具調用的 4688 進程命令列
$StartTime = (Get-Date).AddHours(-6)
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4688
    StartTime = $StartTime
} | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    $cmd = ($data | Where-Object { $_.Name -eq 'CommandLine' }).'#text'
    $parent = ($data | Where-Object { $_.Name -eq 'ParentProcessName' }).'#text'
    $proc = ($data | Where-Object { $_.Name -eq 'NewProcessName' }).'#text'
    
    # 篩選特徵：包含 Base64、curl、certutil、rundll32 或異常父進程
    if ($cmd -match "(-enc|base64|certutil|rundll32|bitsadmin|net user|IEX)" -or $parent -match "(winword|excel)") {
        [PSCustomObject]@{
            TimeCreated = $_.TimeCreated
            User        = ($data | Where-Object { $_.Name -eq 'TargetUserName' }).'#text'
            Parent      = $parent
            NewProcess  = $proc
            CommandLine = $cmd
        }
    }
} | Format-List
```

#### 步驟 3：自動化橫向服務獵殺腳本 (`service_lateral_hunter.ps1`)
```powershell
<#
.SYNOPSIS
    自動掃描 7045 服務日誌並獵殺可疑橫向服務
#>
param (
    [int]$Hours = 24
)

$Since = (Get-Date).AddHours(-$Hours)
Write-Host "[*] 正在掃描過去 $Hours 小時內安裝的新服務 (Event 7045)..." -ForegroundColor Cyan

$Filter = @{
    LogName   = 'System'
    Id        = 7045
    StartTime = $Since
}

$SuspiciousPatterns = @(
    'psexesvc',
    'powershell',
    'cmd.exe',
    '\\ADMIN\$',
    '\\C\$',
    'AppData\\Local\\Temp',
    'C:\\Windows\\Temp'
)

Get-WinEvent -FilterHashtable $Filter | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    $name = ($data | Where-Object { $_.Name -eq 'ServiceName' }).'#text'
    $path = ($data | Where-Object { $_.Name -eq 'ImagePath' }).'#text'
    $account = ($data | Where-Object { $_.Name -eq 'AccountName' }).'#text'
    
    $isSuspicious = $false
    foreach ($pat in $SuspiciousPatterns) {
        if ($name -match $pat -or $path -match $pat) {
            $isSuspicious = $true
            break
        }
    }
    
    # 檢查 Impacket 隨機名特徵 (8-10 位英數亂碼且路徑在 System32)
    if ($name -match '^[a-zA-Z0-9]{8,10}$' -and $path -match '\.exe$') {
        $isSuspicious = $true
    }
    
    if ($isSuspicious) {
        Write-Host "[!] 🚨 發現可疑服務安裝!" -ForegroundColor Red
        Write-Host "    時間: $($_.TimeCreated)"
        Write-Host "    服務名稱: $name"
        Write-Host "    執行路徑: $path"
        Write-Host "    運行身分: $account"
    } else {
        Write-Host "[+] 正常服務: $name ($path)" -ForegroundColor Gray
    }
}
```

### 3.3 Splunk SPL 關聯獵捕語法

#### 偵測情境：服務安裝後隨即衍生特權命令（7045 聯防 4688）
> **邏輯**：當系統安裝了新服務（7045），隨後 2 分鐘內該服務的進程孵化出了 `cmd.exe` 或 `powershell.exe`（4688），判定為 **橫向移動執行命令**！

```splunk
index=wineventlog (EventCode=7045 OR EventCode=4688)
| eval service_installed=if(EventCode==7045, ServiceName, null())
| eval cmd_executed=if(EventCode==4688, CommandLine, null())
| transaction host maxspan=2m
| search service_installed=* AND cmd_executed=*
| table _time, host, service_installed, ImagePath, cmd_executed
```

## ⚖️ 第四動：研判分水嶺——正常 IT 維護 vs 惡意服務橫向？

在企業環境中，軟體自動更新、IT 部署工具（如 SCCM、PDQ Deploy）也會在背景註冊臨時服務並執行命令列。你該如何區分？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | 伺服器安裝了未在官方白名單中的服務（Event ID 7045），或偵測到危險命令列參數。 |
| **Q2. 服務檔案路徑**（執行檔存放在哪裡？） | 是位於 `%SystemRoot%\System32\`、`%ProgramFiles%`，還是位於 `\Windows\Temp\`、`\Admin$\`、`C:\Users\`？**臨時目錄安裝服務必為惡意！** |
| **Q3. 服務名稱規律**（命名是否具有惡意特徵？） | 是否為已知黑客工具（`PSEXESVC`、`WCE`、`MIMIKATZ`），或完全由隨機 8 位十六進位亂碼組成？ |
| **Q4. 執行命令內容**（4688 的完整參數為何？） | 命令列是否包含建立隱藏帳號（`net user ... /add`）、關閉防毒（`Set-MpPreference -DisableRealtimeMonitoring`）？ |
| **Q5. 母進程親緣**（生出該進程的母體是誰？） | 4688 的母進程是正常的 `services.exe`，還是來自瀏覽器下載目錄或 Office 文檔（`WINWORD.EXE`）？ |
| **Q6. 關聯前置登入**（該服務是誰登入安裝的？） | 拿著發起帳號的 `LogonId` 去比對 Event ID 4624：該帳號是不是剛剛透過 **LogonType = 3 (SMB 網路共享)** 連入的？ |
| **Q7. 橫向連鎖波及**（全網還有哪些機器出現相同服務？） | 搜尋全網 SIEM，該服務名稱或執行檔 Hash 是否在過去 10 分鐘內同時擴散至數十台主機？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 立即停止並刪除惡意服務；2. 終止由該服務衍生的子進程；3. 隔離來源主機與受害主機。 |

## 🛡️ 第五動：處置阻斷與系統加固 SOP (Mitigation & Hardening)

確認存在惡意服務或橫向移動跡象時，依循以下標準作業程序進行處置：

### 1. 現場緊急拔除惡意服務
不要只用工作管理員結束程式，必須從 SCM 與登錄檔中徹底抹除：
```powershell
# 1. 強制停止正在運行的惡意服務
Stop-Service -Name "PSEXESVC" -Force

# 2. 從 Service Control Manager 中永久刪除該服務註冊
sc.exe delete "PSEXESVC"

# 3. 刪除磁碟上的實體惡意二進位檔案
Remove-Item -Path "C:\Windows\PSEXESVC.exe" -Force
```

### 2. 網路層加固：封鎖內網未授權的 SMB / RPC 橫向通道
- **阻斷端點之間互連**：工作站之間（Workstation-to-Workstation）嚴禁開啟 TCP 445 (SMB) 與 TCP 135 (RPC)。
- **透過 Windows 防火牆下發 GPO**：僅允許管理跳板機（PAW）存取伺服器的管理通訊埠，斬斷 PsExec 的橫向擴散基石。

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

請帶著剛才學到的 7045/4688 聯防技巧，進入真實主機事件日誌鑑識靶場：

### 推薦靶場：[HTB Sherlocks - Logjammer (Windows Event Log Forensic)](https://app.hackthebox.com/sherlocks/Logjammer)
- **靶場背景**：一台關鍵伺服器的事件日誌遭到部分清除，但攻擊者在利用 PsExec 提權時仍留下了殘餘軌跡。
- **作戰任務**：
  1. 使用 [Chainsaw](https://github.com/countercept/chainsaw) 或 Event Viewer 打開 `System.evtx`，過濾 Event ID 7045，找出黑客橫向移動時安裝的惡意服務名稱與執行路徑。
  2. 打開 `Security.evtx`，搜尋對應時間點的 Event ID 4688，找出該服務啟動後執行的第一條命令列參數。
  3. 將命令列中的 Base64 字串進行解密，提取出黑客企圖下載二進位 Payload 的外部 C2 IP 與檔案名稱。
  4. 記錄發起該服務安裝的登入帳號名稱，完成取證調查報告。

## 📋 過關驗收檢查點 (Mastery Checklist)

以下為本專案的 5 大實戰驗收問題與標準專家解析：

- [x] **Q1：在 Windows 預設安裝下，雖然安全日誌會記錄 Event ID 4688，但為什麼分析師通常看不到黑客執行的具體命令列（Process Command Line 為空）？你該如何透過 GPO 開啟此核心遙測？**
  > **標準答案**：
  > 1. **預設隱私與相容考量**：微軟在 Windows 預設組態中，考慮到命令列可能包含使用者密碼或敏感資料，且記錄命令列會稍微增加日誌儲存量，因此預設僅記錄「進程建立」與執行檔路徑，而將「命令列參數」欄位留空。
  > 2. **GPO 開啟標準路徑**：
  >    - 打開群組原則管理編輯器（`gpedit.msc`）。
  >    - 導航至：`電腦設定` ➔ `系統管理範本` ➔ `系統` ➔ `稽核程序建立` (Audit Process Creation)。
  >    - 雙擊開啟 **「在程序建立事件中包含命令列」 (Include command line in process creation events)**，將其設定為 **已啟用 (Enabled)**。
  > 3. **即時登錄檔生效**：亦可透過下發登錄檔鍵值即時生效：
  >    `reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit" /v ProcessCreationIncludeCmdLine_Enabled /t REG_DWORD /d 1 /f`。

- [x] **Q2：Event ID 7045 是記錄在 System Log 還是 Security Log？在橫向移動攻擊（如 PsExec）中，7045 與 4624 (Logon Type 3) 通常呈現什麼樣的時間先後關聯？**
  > **標準答案**：
  > 1. **所屬日誌通道**：Event ID 7045 是由 Windows Service Control Manager（SCM）發出，固定記錄在 **System Log（系統日誌）** 中，而非 Security 日誌。
  > 2. **PsExec 橫向移動的時間先後脈絡**：
  >    - **第一步（4624 Type 3 網路登入）**：攻擊者首先透過 SMB（TCP 445）連線至受害主機的 `ADMIN$` 共享資料夾，產生一筆 **Event ID 4624 (Logon Type = 3)**。
  >    - **第二步（檔案傳輸）**：攻擊者將 `PSEXESVC.exe`（或隨機命名的二進位檔）上傳至 `C:\Windows\`。
  >    - **第三步（7045 服務註冊）**：攻擊者透過 RPC 呼叫 SCM 遠端註冊並啟動服務，系統立即在 System 日誌產生 **Event ID 7045**。
  >    - **第四步（4688 特權命令）**：服務啟動後孵化 `cmd.exe`，在 Security 日誌中產生 **Event ID 4688**。
  > 3. **時序關係**：4624 (Type 3) 通常領先 7045 數秒至數十毫秒發生。

- [x] **Q3：黑客若在 7045 服務中將 `ImagePath` 設為 `C:\Windows\System32\cmd.exe /c powershell -enc ...`，為什麼這種服務被稱為「非標準服務」？在實戰排查中為什麼它具有最高優先級的威脅特徵？**
  > **標準答案**：
  > 1. **標準 Windows 服務本質**：正規的 Windows 服務必須是符合 Service API 規範編譯的二進位程式（實現了 `ServiceMain` 與 `HandlerEx` 回呼函數），能夠在啟動時向 SCM 回報 `SERVICE_RUNNING` 狀態。
  > 2. **非標準服務成因**：黑客為了實現無檔案攻擊或快速反彈 Shell，不想在磁碟上編譯和丟棄專門的 `.exe` 服務檔案，而是直接利用 SCM 的執行權限，將原生直譯器（`cmd.exe` 或 `powershell.exe`）搭配參數註冊為服務 ImagePath。
  > 3. **最高優先級威脅原因**：
  >    - 此類服務通常會在幾秒後因為無法向 SCM 回報運行狀態而崩潰（產生 Event ID 7034），但黑客的 Payload 早已由子進程執行完畢。
  >    - 任何將 Shell 直譯器直接當成服務執行的行為，在生產環境中 99.9% 都是黑客持久化或橫向移動執行命令的鐵證。

- [x] **Q4：在 Event ID 4688 中，Token Elevation Type（權杖提升類型）數值為 `%%1936` (Type 1)、`%%1937` (Type 2)、`%%1938` (Type 3) 分別代表什麼特權意義？你該如何用它判定該命令是否以管理員特權執行？**
  > **標準答案**：
  > 1. **代碼涵義全解**：
  >    - **`%%1936` (Type 1 - Default / Full Token)**：進程運行於不受 UAC 限制的完整權杖下（例如停用 UAC 時的環境，或是以內建 `LocalSystem`、`NetworkService`、以及 RID 500 的內建 Administrator 帳戶啟動）。
  >    - **`%%1937` (Type 2 - Elevated / UAC Elevated)**：使用者在啟用 UAC 的情況下，透過「以系統管理員身分執行」並通過了 UAC 提權確認對話框，進程獲得了**提升後的管理員權杖 (Full Administrator Privilege)**。
  >    - **`%%1938` (Type 3 - Limited / Filtered Token)**：進程以標準受限權杖運行（例如管理員登入但未經提權的日常程式、一般非管理員使用者的普通進程）。
  > 2. **管理員特權判定直覺**：只要看到 `%%1936` 或 `%%1937`，即代表該命令列具備本機管理員等級以上的破壞力，分析師需嚴密審查其命令合法性。

- [x] **Q5：什麼是 BYOVD（Bring Your Own Vulnerable Driver）攻擊？黑客在安裝這種惡意核心驅動時，系統會產生 Event ID 7045 嗎？此時 7045 中的 `Service Type` 會呈現什麼特殊值？**
  > **標準答案**：
  > 1. **BYOVD 攻擊原理**：自 Windows 64-bit 起，微軟實施了驅動程式簽章強制原則（Driver Signature Enforcement, DSE），未簽名的惡意驅動無法載入核心態。攻擊者遂蒐集歷史上曾獲得微軟合法數位簽名、但存在已知記憶體讀寫漏洞的合法舊版驅動程式（例如微星、技嘉或防毒軟體歷史驅動）帶到受害機器上安裝，再透過用戶態程式利用該驅動漏洞執行任意核心態代碼（通常用於殺死 EDR 或關閉系統安全機制）。
  > 2. **日誌產生機制**：驅動程式在 Windows 底層本質上也是一種服務（Kernel Driver Service）。安裝驅動時 SCM 同樣會將其註冊並寫入登錄檔，因此**必然會產生 Event ID 7045**！
  > 3. **Service Type 特殊標記**：常規應用程式服務的 `Service Type` 為 `user mode service`（用戶態服務）；而 BYOVD 攻擊安裝的驅動程式，其 `Service Type` 會明確標記為 **`kernel driver`（核心驅動程式）** 或 **`file system driver`**，這是藍隊捕獲內核級對抗的關鍵指標。
