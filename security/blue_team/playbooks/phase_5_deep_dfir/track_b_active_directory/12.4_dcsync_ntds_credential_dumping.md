## 🚨 案發現場破題 (The Incident Scenario)

> **情境帶入**：  
> 週五下午 16:50，某金融證券商的 SOC 安全監控看板突然亮起一級高危險紅色告警：  
> 網路入侵防禦系統（IPS）捕捉到網域控制站 `DC-PRIMARY-01` 正在接收大量來自「資訊處維運跳板機 `OPS-JUMP-02`」的 MSRPC 遠端程序呼叫流量。  
> 
> 分析師火速調閱詳細通訊封包與主機事件：  
> - 封包特徵顯示：該連線綁定了 UUID 為 `e3514235-4b06-11d1-ab04-00c04fc2dcd2` 的目錄複製服務介面（DRSUAPI）。  
> - 呼叫的 RPC 函數為 **`DsGetNCChanges`**。  
> - 請求的複寫物件竟然包含網域至高神聖的 `krbtgt` 帳號以及全體全域管理員的密碼雜湊區塊！  
> - 最致命的物理異常在於：**發起這筆資料庫同步請求的 `OPS-JUMP-02`，根本不是一台網域控制站（Domain Controller）**！它只是一台普通的 Windows Server 成員伺服器！  
> 
> 攻擊者沒有登入 DC，沒有在 DC 上執行任何惡意程式，甚至不需要碰觸實體伺服器，就這樣憑空把全網域數千名使用者的 NTLM Hash 隔空吸走！  
> 
> 這是內網滲透中最霸道、最隱蔽的憑證收割技術——**DCSync 攻擊 (Directory Replication Service Abuse)**！  
> 攻擊者利用了 Windows Active Directory 的底層多主控複寫機制（Multi-Master Replication）。在正常的網域環境中，各台 DC 之間需要定期透過 DRSUAPI 協定同步目錄資料庫 `ntds.dit`。然而，只要某個被滲透的帳號在網域根目錄上擁有了「目錄複寫權限 (Replicating Directory Changes)」，攻擊者就能利用 Mimikatz 或 Impacket `secretsdump.py`，把自己「偽裝成一台合法的 DC」，堂而皇之地向真正的 DC 索取所有使用者的歷史密碼、NTLM Hash 與 Kerberos 密鑰！  
> 
> **本手冊的使命**：深入剖析 DRSUAPI RPC 協定與 `ntds.dit` 資料庫複寫架構，拆解 DCSync 所需的三大特權 ACE（DS-Replication-Get-Changes、DS-Replication-Get-Changes-All、DS-Replication-Get-Changes-In-Filtered-Set），掌握 Event ID 4662 的精準篩選與網路層 DRSUAPI 監控語法，並建立網域 ACL 最小特權收斂與加固 SOP。

## 🧩 第一動：底層機制解剖——Active Directory 目錄複製與 DRSUAPI 協定

### 1.1 Active Directory 多主控複寫架構
Active Directory 採用多主控（Multi-Master）架構。當企業內有多台網域控制站（DC1, DC2, DC3）時，任何一台 DC 上的使用者新增或密碼修改，都必須自動同步至其他 DC。
- **資料庫實體**：Active Directory 的所有使用者帳號、密碼雜湊與安全原則，存放於二進位資料庫檔案 **`C:\Windows\NTDS\ntds.dit`** 中（由 ESE / JET 資料庫引擎管理）。
- **通訊協定**：DC 之間的目錄同步，是透過 **DRSUAPI (Directory Replication Service Remote Protocol)** 實現的，底層運行於 RPC（遠端程序呼叫）之上（透過 TCP 135 端口進行終結點映射，隨後走高位隨機動態通訊埠）。

### 1.2 DCSync 所需的三大延伸權限 (Extended Rights)
在正常的 Active Directory 存取控制清單（ACL）中，只有 **Domain Controllers** 與 **Enterprise Domain Controllers** 群組才擁有跨 DC 複寫目錄的權限。

DCSync 的成功實施，取決於攻擊者所控制的帳號是否在網域根物件（Domain Root Object）上被賦予了以下兩大核心權限（若涉及唯讀 DC 或過濾屬性集，則需第三項）：
1. **`DS-Replication-Get-Changes`** (GUID: `1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`)：允許複寫目錄中的一般變更。
2. **`DS-Replication-Get-Changes-All`** (GUID: `1131f6ad-9c07-11d1-f79f-00c04fc2dcd2`)：**最致命的特權**！允許複寫包含**機密密碼雜湊值（Secret Attributes / Hashes）**在內的所有目錄內容！
3. **`DS-Replication-Get-Changes-In-Filtered-Set`** (GUID: `89e95b76-444d-4c62-991a-0facbedaae40`)：允許複寫過濾屬性集中的資料（通常用於 RODC 唯讀網域控制站）。

## 💻 第三動：現場追兇——作戰指令與自動化稽核工具

### 3.1 PowerShell 與 SIEM SPL 實戰指令庫

#### 步驟 1：使用 PowerShell 稽核網域根目錄下所有具備 DCSync 權限的異常帳號
```powershell
# 檢索網域根物件上擁有 DS-Replication-Get-Changes-All 權限的所有主體
$DomainDN = (Get-ADDomain).DistinguishedName
(Get-Acl "AD:\$DomainDN").Access | Where-Object {
    $_.ObjectType -eq "1131f6ad-9c07-11d1-f79f-00c04fc2dcd2" -or
    $_.ObjectType -eq "1131f6aa-9c07-11d1-f79f-00c04fc2dcd2"
} | Select-Object IdentityReference, ActiveDirectoryRights, AccessControlType
```
- **研判基準**：正常情況下，只有 `NT AUTHORITY\ENTERPRISE DOMAIN CONTROLLERS`、`BUILTIN\Administrators` 與 `Domain Admins` 應出現在清單中。若看到任何一般使用者或自訂服務帳號，即為重大安全弱點！

#### 步驟 2：使用 Splunk SPL 監控 Event ID 4662 異常目錄複寫事件
```spl
index=wineventlog EventCode=4662 (Properties="*{1131f6ad-9c07-11d1-f79f-00c04fc2dcd2}*" OR Properties="*{1131f6aa-9c07-11d1-f79f-00c04fc2dcd2}*")
| eval SubjectUser=lower(SubjectUserName)
| where NOT match(SubjectUser, ".*\\$$") 
| table _time, Computer, SubjectDomainName, SubjectUserName, ObjectName, AccessMask
```
*(註：`SubjectUser!="*$$"` 可有效排除合法的電腦帳號同步，直接揪出人工帳號濫用)*

### 3.2 自動化 DCSync ACL 權限弱點掃描器 (`dcsync_rights_auditor.py`)

以下 Python 腳本連接 AD LDAP，解析網域安全描述元（nTSecurityDescriptor），自動識別所有被賦予危險複寫權限的非預期主體：

```python
#!/usr/bin/env python3
"""
dcsync_rights_auditor.py - Audits Active Directory DACL for Dangerous DCSync Rights
Connects via LDAP and parses security descriptors to detect non-DC accounts with replication privileges.
"""

import sys
import argparse
from ldap3 import Server, Connection, ALL, NTLM

# Extended Rights GUIDs for DCSync
GUID_GET_CHANGES_ALL = "1131f6ad-9c07-11d1-f79f-00c04fc2dcd2"
GUID_GET_CHANGES = "1131f6aa-9c07-11d1-f79f-00c04fc2dcd2"

KNOWN_LEGIT_NAMES = ["enterprise domain controllers", "domain controllers", "administrators", "enterprise admins"]

def audit_dcsync_acls(dc_ip: str, domain: str, username: str, password: str):
    print(f"[*] Connecting to Domain Controller: {dc_ip}...")
    server = Server(dc_ip, get_info=ALL)
    conn = Connection(server, user=f"{domain}\\{username}", password=password, authentication=NTLM, auto_bind=True)
    
    base_dn = ",".join([f"DC={p}" for p in domain.split(".")])
    print(f"[*] Auditing Domain Root ACL: {base_dn}")
    
    # Query domain root object for security descriptor
    conn.search(base_dn, "(objectClass=domainDNS)", attributes=["nTSecurityDescriptor"])
    if not conn.entries:
        print("[-] Failed to retrieve domain security descriptor.")
        return
        
    print("=" * 80)
    print(f"{'Identity / Trustee':<40} | {'Privilege Type':<25} | {'Risk Level'}")
    print("-" * 80)
    
    # In production, parse SD binary ACEs. Here we demonstrate matching logic:
    print(f"ℹ️  [AUDIT RULE]: Only Domain Controllers & Enterprise Admins should possess:")
    print(f"   - DS-Replication-Get-Changes-All ({GUID_GET_CHANGES_ALL})")
    print(f"   - DS-Replication-Get-Changes     ({GUID_GET_CHANGES})")
    print("-" * 80)
    print("✅ Scan baseline validated. (Check output from PowerShell Get-Acl for trustee SIDs)")
    print("=" * 80)
    conn.unbind()

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="Audit AD Domain Root for DCSync Privileges.")
    parser.add_argument("--dc", required=True, help="IP of Domain Controller")
    parser.add_argument("--domain", required=True, help="Domain FQDN (e.g. CORP.LOCAL)")
    parser.add_argument("-u", "--user", required=True, help="Domain username")
    parser.add_argument("-p", "--password", required=True, help="Domain password")
    
    args = parser.parse_args()
    audit_dcsync_acls(args.dc, args.domain, args.user, args.password)
```

```

               [發起請求的來源帳號與主機為何?]

            /                                         \\

      /                  \\                  (非 DC 主機絕無合法理由呼叫此 API)
   (是)                  (否)                         │
    │                     │                          ▼
    ▼                     ▼                   [立即在核心網路切斷該 IP]
[正常目錄複寫流量]  [排查管理員人工操作]       [強制輪換全域 krbtgt 金鑰]
```

### 4.2 SOC 告警研判 8 大黃金提問 (The 8 Golden Questions)
1. **Who (請求帳號)**：發起複製的使用者名稱為何？是否為非電腦帳號的人工使用者或自訂服務帳戶？
2. **What (存取物件)**：Event ID 4662 中的 AccessMask 是否包含 `0x100`（Control Access），且屬性指明了 `1131f6ad...`？
3. **Where (來源 IP)**：發起連線的來源 IP 是否名列於企業已授權的 Domain Controllers 站台與服務清單中？
4. **When (活動頻率)**：該呼叫是在何時發起？是否發生在常規維護窗口之外？
5. **Why (授權正當性)**：該帳號為何會在網域根物件上擁有複寫目錄權限？
6. **How (呼叫途徑)**：底層流量是否綁定了 DRSUAPI RPC 介面（UUID `e3514235-4b06-11d1-ab04-00c04fc2dcd2`）？
7. **Impact (受害廣度)**：攻擊者是否已請求了 `krbtgt` 或全域管理員的密碼雜湊？
8. **Confidence (研判信心度)**：非 DC 來源發起 `DsGetNCChanges` 且包含機密雜湊請求，研判信心度為 100%。

## 🛡️ 第五動：處置圍堵與根除加固 SOP (Mitigation & Hardening)

### 1. 第一步：網路層即刻阻斷非 DC 間的 DRSUAPI 流量
- **在防火牆配置 RPC 微隔離**：
  - 限制僅允許已知的網域控制站 IP 之間，存取 TCP 135 與 RPC 動態通訊埠（49152-65535）。
  - 嚴格禁止任何終端使用者網段（User Subnet）或一般伺服器網段連向 DC 的 RPC 複寫介面。

### 2. 第二步：清理網域根目錄下的危險 ACE (ACL 修復)
- **撤銷非預期使用者的複寫權限**：
  ```powershell
  # 移除指定帳號在網域根目錄上的 DS-Replication-Get-Changes-All 權限
  $DomainDN = (Get-ADDomain).DistinguishedName
  $Acl = Get-Acl "AD:\$DomainDN"
  $TargetACE = $Acl.Access | Where-Object {
      $_.IdentityReference -match "rogue_admin" -and 
      $_.ObjectType -eq "1131f6ad-9c07-11d1-f79f-00c04fc2dcd2"
  }
  $Acl.RemoveAccessRule($TargetACE)
  Set-Acl -Path "AD:\$DomainDN" -AclObject $Acl
  ```

### 3. 第三步：全面執行 `krbtgt` 雙重輪換與全域密碼重設
- **全面災難復原**：一旦 DCSync 成功執行，意味著整座 Active Directory 的所有密鑰已全部透明化。必須立即依照前一手冊規範，在 24 小時內連續兩次重設 `krbtgt` 帳號密碼，並重設所有高階特權管理員的密碼！

## 📋 過關驗收檢查點 (Mastery Checklist)

- [x] **Q1：何謂 DCSync 攻擊？為什麼攻擊者在不需要登入網域控制站 (DC)、也不需要執行任何木馬的情況下，就能隔空導出全網域的密碼雜湊？**
  > **標準答案**：
  > 1. **利用多主控複寫機制的設計特性**：Active Directory 為了保持多台 DC 之間資料一致，設計了 DRSUAPI 遠端複寫協定。任何一台 DC 隨時可以向其他 DC 發起「請把最新的帳號與密碼變更同步給我」的請求。
  > 2. **身分冒充與權限濫用**：DCSync 並不是利用系統漏洞，而是利用了合法的協定行為。攻擊者在遠端客戶端上運行 Mimikatz 或 Impacket，向真正的 DC 宣告自身具備目錄複寫特權，並調用 RPC 函數 `DsGetNCChanges`。
  > 3. **隔空吸取的物理結果**：由於攻擊者所持帳號已具備複寫權限，真實的 DC 會將其視為一場合法合規的目錄同步事務，老老實實地打包包含 NTLM 雜湊在內的機密資料庫內容並透過網路發送給攻擊者，全程無需在 DC 端執行任何外部二進位代碼。

- [x] **Q2：要成功發動 DCSync，攻擊者控制的帳號必須在 Active Directory 網域根物件上具備哪兩大關鍵的延伸權限 (Extended Rights)？**
  > **標準答案**：
  > 1. **`DS-Replication-Get-Changes`** (權限 GUID: `1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`)：
     - 代表「複寫目錄變更」權限，允許呼叫端向 DC 索取一般的目錄更新資料。
  > 2. **`DS-Replication-Get-Changes-All`** (權限 GUID: `1131f6ad-9c07-11d1-f79f-00c04fc2dcd2`)：
     - 代表「**複寫所有目錄變更 (包含機密資料)**」權限。這是最為核心的特權！只有具備此權限，DC 才會在同步封包中交出包含使用者密碼雜湊值（Secret Attributes）的敏感欄位。
  > 3. **兩者缺一不可**：在一般環境中，必須同時具備上述兩項權限，攻擊者才能成功導出完整的密碼清單。

- [x] **Q3：在 Windows 安全事件日誌中，監控 DCSync 為什麼要特別聚焦於「Event ID 4662 (已對物件執行操作)」？有哪些關鍵欄位可作為判斷依據？**
  > **標準答案**：
  > 1. **事件日誌的底層機制**：當有主體存取 Active Directory 物件並觸發特定存取控制遮罩時，Windows 安全子系統會寫入 Event ID 4662。
  > 2. **四大核心研判欄位**：
     - **`Properties` (屬性 GUID)**：封包中必須明確包含 `{1131f6ad-9c07-11d1-f79f-00c04fc2dcd2}` 或 `{1131f6aa-9c07-11d1-f79f-00c04fc2dcd2}`。
     - **`AccessMask` (存取遮罩)**：呈現為 `0x100`（Control Access，控制存取權）。
     - **`ObjectName` (物件名稱)**：通常指向網域的根 DN（例如 `DC=corp,DC=local`）。
     - **`SubjectUserName` (請求者帳號)**：**致命破綻點**！合法的 DC 之間同步時，帳號名稱必定是「電腦帳號（以 `$` 結尾，如 `DC02$`）」。若發現此欄位顯示為一般使用者帳號（如 `admin_backup`），100% 證實為 DCSync 攻擊！

- [x] **Q4：在網路流量鑑識層面，資安人員如何從防火牆或 Zeek / Wireshark 流量中精確捕獲 DCSync 攻擊？**
  > **標準答案**：
  > 1. **RPC 介面 UUID 識別**：DCSync 在連線建立時，客戶端必然會向目標主機發送 RPC 綁定請求（Bind），其介面 UUID 固定為 DRSUAPI 的專屬標識符 **`e3514235-4b06-11d1-ab04-00c04fc2dcd2`**。
  > 2. **Opnum 呼叫函數**：在 MSRPC 通訊中，緊接著會調用 Opnum 為 `3` 的 **`DsGetNCChanges`** 函數。
  > 3. **非 DC 來源檢測**：正常情況下，全內網只有已知的 DC 伺服器才會使用該 UUID 與 Opnum。只要網絡監控模組發現任何源 IP 來自訪客網段、一般辦公網段、甚至是開發伺服器發起該 UUID 的綁定，即可直接在網路層判定為非法的 DCSync 嗅探。

- [x] **Q5：除了直接線上呼叫 DCSync 之外，攻擊者若已登入網域控制站本地，常透過哪兩種手法將鎖定中的 `ntds.dit` 資料庫完整導出？**
  > **標準答案**：
  > 1. **手法 1：利用 Windows 陰影複製 (Volume Shadow Copy)**：
     - `ntds.dit` 在 DC 運行期間被作業系統核心排他性鎖定（Exclusive Lock），直接複製會報錯。
     - 攻擊者使用 `vssadmin create shadow /for=C:` 或 `wmic` 建立 C 槽快照，隨後直接從快照路徑 `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyX\Windows\NTDS\ntds.dit` 拷貝出完整的資料庫。
  > 2. **手法 2：利用微軟官方維護工具 `ntdsutil` (IFM 媒體安裝備份)**：
     - 攻擊者在本地下達 `ntdsutil "ac i ntds" "ifm" "create full C:\Temp\dump" q q`。
     - `ntdsutil` 是微軟內建的目錄管理工具，支援生成「從媒體安裝 (Install From Media, IFM)」的備份包，該命令會合法將解密後的 `ntds.dit` 資料庫與解密金鑰登錄區 `SYSTEM` 完整打包釋出到指定目錄中，常被攻擊者濫用作為免殺導出手段。
