## 一、 為什麼需要用 Wireshark？

日常工作與生活中，網路通訊常常像一個黑盒子：
- 網頁開不起來，大家只能猜：是辦公室網路卡、電信商出包、還是伺服器當機？
- 系統開發時，前端工程師說「我確定有呼叫 API」，後端工程師說「我的伺服器 Log 裡根本沒看到」。
- 懷疑電腦中毒時，不知道到底有沒有程式在背後偷偷對外傳送資料。

### Wireshark 在做什麼？
Wireshark 是一款**網路封包側錄與協定分析軟體**。  
它透過作業系統底層的封包擷取驅動（Windows 下的 Npcap 或 Linux 下的 libpcap），直接側錄進出你電腦網路卡的每一個封包，並自動把二進位資料解析為 Ethernet、IP、TCP、UDP、HTTP、DNS 等協定格式。

> **核心觀念**：系統日誌可能會漏記，口頭溝通可能會有誤解，但實際通過網路卡的封包是確認事實的最直接途徑。

## 二、 語法不用死背：善用 AI 幫你寫過濾式

剛學 Wireshark 最容易卡關的地方，就是誤以為要背下幾百個過濾語法標籤（例如 `tcp.analysis.flags`、`http.request.method`）。

在有生成式 AI 工具（如 ChatGPT、Claude、Gemini）的今天，**請不要花時間死背過濾語法！**

### 人與 AI 的分工方式：
- **你的任務**：**把你想排查的情境與條件想清楚**（例如：「我想抓出所有發往 192.168.1.50 的 HTTP POST 請求」）。
- **AI 的任務**：**將你的需求轉成正確的 Wireshark Display Filter（顯示過濾式）**。
- **你的任務**：**把過濾式貼進 Wireshark，查看封包內容並解決問題**。

### 常用 AI 提問模板（直接複製使用）：

```text
請幫我寫出 Wireshark 的顯示過濾條件（Display Filter）：
1. 我想排查的情境：[描述想看的封包，例如：找出帶有密碼的 HTTP 表單提交]
2. 目標主機或 IP：[例如：目標 IP 是 192.168.1.1，或排除內網 192.168.0.0/16]
3. 協定或特殊條件：[例如：只要看 TCP 重傳，或是只要看 DNS 查詢]
請只給我最精準的過濾語法，並簡短說明每個關鍵字的作用。
```

## 三、 Wireshark 介面結構快速導覽

打開 Wireshark 並雙擊你的連線網卡（如 Ethernet 或 Wi-Fi）開始錄製，介面主要由三塊區域組成：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ 🔍 顯示過濾列 (Display Filter)：在此輸入條件（或貼上 AI 產生的過濾語法）   │
├─────────────────────────────────────────────────────────────────────────────┤
│ ① 上方：封包清單 (Packet List)                                             │
│    No. | Time | Source | Destination | Protocol | Length | Info            │
│    ───────────────────────────────────────────────────────────────────────  │
│    1   | 0.00 | 192.168.1.100 -> 93.184.216.34 | TCP | 66 | 54321 -> 80...│
│    2   | 0.02 | 93.184.216.34 -> 192.168.1.100 | TCP | 66 | 80 -> 54321...│
│    3   | 0.03 | 192.168.1.100 -> 93.184.216.34 | HTTP| 210| GET / HTTP/1.1 │
├─────────────────────────────────────────────────────────────────────────────┤
│ ② 中間：協定細節 (Packet Details)                                         │
│    ▶ Frame 3: 210 bytes on wire (實體網卡層)                                 │
│    ▶ Ethernet II, Src: 00:1a:2b:3c:4d:5e, Dst: e4:5d:51:aa:bb:cc (MAC 位址) │
│    ▶ Internet Protocol Version 4, Src: 192.168.1.100, Dst: 93.184.216.34    │
│    ▶ Transmission Control Protocol, Src Port: 54321, Dst Port: 80           │
│    ▼ Hypertext Transfer Protocol (HTTP 應用層內容！點開查看 Header 與 Body) │
│        GET / HTTP/1.1\r\n                                                   │
│        Host: example.com\r\n                                                │
├─────────────────────────────────────────────────────────────────────────────┤
│ ③ 下方：原始位元組 (Packet Bytes)                                         │
│    0000  00 1a 2b 3c 4d 5e e4 5d  51 aa bb cc 08 00 45 00  ..+<M^.]Q...E. │
│    0010  00 c4 1a 2b 40 00 40 06  b2 1a c0 a8 01 64 5d b8  ...+@.@......d]. │
│    0020  d8 22 d4 31 00 50 12 34  56 78 9a bc de f0 50 18  .".1.P.4Vx....P. │
│    0030  01 f5 b4 12 00 00 47 45  54 20 2f 20 48 54 54 50  ......GET / HTTP │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **上方清單**：看整體流向（誰送給誰、走什麼協定、大小多少）。
- **中間細節**：最常使用的區域。點選特定封包後，點開箭頭查看詳細欄位內容。
- **下方 Raw Data**：顯示底層真實的 Hex Dump 與 ASCII 字元。平常排錯通常看中間就足夠。

## 四、 常見實戰排錯情境

### 情境 1：網頁打不開或卡頓？排查 TCP 重傳 (Retransmission)

#### 現象：
使用者反映網頁載入很久，每次都要轉圈圈 5 到 10 秒。但伺服器主機 CPU 與記憶體使用率都非常低。

#### 排查步驟：
1. 在 Wireshark 上方的過濾列輸入：
   ```text
   tcp.analysis.flags
   ```
2. 檢查封包清單中是否出現大量黑色背景紅字標記：
   - `[TCP Retransmission]`（重傳封包）
   - `[TCP Dup ACK]`（重複確認）

#### 原因與處置：
- TCP 具有可靠傳輸保證。發送端送出資料後，如果在一定時間內沒有收到接收端回覆的 ACK 確認，就會判定封包遺失並啟動超時重傳。
- 這代表**問題出在實體網路線路、WiFi 訊號不良、或是交換機設備丟包**，並非應用程式效能不足。
- **處置**：將抓包紀錄存檔，提供給網路維運人員或電信商排查線路問題。

---

### 情境 2：為什麼不能用未加密協定？HTTP 明文帳密側錄

#### 現象：
在區域網路內登入只支援 HTTP（未加密）的老舊網站。

#### 排查步驟：
1. 在過濾列輸入：
   ```text
   http.request.method == "POST"
   ```
2. 點選登入請求的封包，在中間的 `Hypertext Transfer Protocol` 區塊展開 `HTML Form URL Encoded`。
3. 表單欄位內容完全以純文字顯示：
   ```text
   Form item: "username" = "admin"
   Form item: "password" = "MySecretPassword2026!"
   ```

#### 結論：
- HTTP 通訊完全沒有加密，同網段的任何人只要側錄封包就能直接看見帳號密碼。
- 現代所有 Web 服務與 API 一律應改用 **HTTPS (TLS 加密)**。

---

### 情境 3：實用技巧：Follow TCP Stream 重組完整對話

#### 痛點：
網路傳輸常會把一份資料拆成數十個 1500 bytes 的 TCP 封包碎片。如果要一個個封包點開看非常麻煩。

#### 操作方式：
1. 在任何一個感興趣的 TCP 或 HTTP 封包上，**按滑鼠右鍵**。
2. 選擇 **`Follow` ➔ `TCP Stream`**（或 HTTP Stream）。
3. 彈出對話視窗：
   - 🔴 **紅色文字**：客戶端送出的完整內容（Request Header 與資料）。
   - 🔵 **藍色文字**：伺服器端回傳的完整內容（Response Status 與 JSON/HTML 資料）。

#### 用途：
- 軟體工程師可以用此功能快速確認前端到底送出了什麼參數、後端回傳了什麼錯誤訊息，3 秒完成前後端 API 責任確認。

---

### 情境 4：電腦沒在用卻有流量？排查異常外連與 DNS

#### 現象：
電腦處於待機狀態，沒有開啟瀏覽器或背景下載，但網路卡持續有連線流量。

#### 排查步驟：
1. 輸入過濾條件：
   ```text
   dns
   ```
2. 檢查是否有規律查詢奇怪的外部網域名稱（例如隨機英文字母組成的域名）。
3. 接續過濾該連線目標 IP：
   ```text
   ip.addr == [目標IP]
   ```
4. 觀察是否每隔固定時間（例如 10 秒）向外發送微小封包（惡意軟體常見的心跳回報 Beaconing）。

#### 處置：
- 惡意程式即便在工作管理員中隱藏行程，只要它連網就必須經過實體網卡。查出目標 IP 與網域名稱後，可加入防火牆阻斷清單，並隔離該主機進行掃毒。

## 五、 加密之後還能看到什麼？HTTP vs. HTTPS

| 檢查項目 | HTTP（未加密） | HTTPS（TLS 加密） |
| :--- | :--- | :--- |
| **傳輸內容 (Payload)** | 純文字，完全看得見 | 加密成隨機亂碼，看不到內容 |
| **完整 URL 路徑與參數** | 完全看得見 | 看不到（內容已加密） |
| **目標伺服器 IP 與 Port** | 完全看得見 | 完全看得見 |
| **訪問的網域名稱** | 在 Host 標頭看得見 | 在 TLS Client Hello 的 SNI 欄位看得見 |
| **傳輸時間與資料量大小** | 完全看得見 | 完全看得見 |

> **重點**：Wireshark 無法直接破解 HTTPS 內容，但中繼資料（連線對象、時間、流量特徵）對於網管排錯與資安威脅識別依然非常有用。

## 六、 課後複習題

請嘗試回答以下 3 個實務問題：

### Q1：前端工程師說有打 API，後端工程師說沒收到，在 Wireshark 上該怎麼看？
> **參考解答**：  
> 在伺服器端（或前端電腦）開啟 Wireshark 抓包，過濾該 API 的路徑或目標 IP。找到封包後按滑鼠右鍵選擇 `Follow TCP Stream`，即可看見雙方發送與回應的完整文字，確認請求是否有發出以及回傳狀態碼。

### Q2：看到封包清單出現連續的黑底紅字 `[TCP Retransmission]`，代表什麼意思？
> **參考解答**：  
> 代表發送端送出 TCP 封包後，在預期時間內沒有收到接收端的回應 (ACK)，判定中途掉包而重新發送。這通常是實體線路、WiFi 訊號或網路設備負載問題，不是後端程式碼問題。

### Q3：既然現在網站大多使用 HTTPS，為什麼我們還需要學 Wireshark？
> **參考解答**：  
> 雖然 HTTPS 內容被加密，但封包的外部資訊（來源/目的 IP、訪問的網域名稱 SNI、連線頻率、傳輸量與 TCP 交握狀態）完全清晰可見，足以用來排查網路延遲、掉包、以及識別異常程式的外連行為。
