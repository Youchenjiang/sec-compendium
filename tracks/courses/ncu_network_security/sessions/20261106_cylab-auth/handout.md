# 伺服器憑什麼相信你是誰

Lesson 4 把可歸責性（Accountability）拆成兩件事：身分識別（Identification，你宣稱自己是誰）與認證（Authentication，證明你真的是）。網站上最常見的認證是登入：你送出帳號密碼，伺服器確認無誤後，發給瀏覽器一張「憑證」，通常放在 cookie 裡；之後你每一次請求，瀏覽器都自動把這張憑證帶回去，伺服器看憑證就知道你是誰。

所以要冒用別人的身分，不一定要知道對方的密碼。憑證本身被改掉、被偷走，登入這一步被繞過，或密碼其實猜得到，結果都一樣：伺服器把你當成另一個人。這份講義用 CyLab 上的 **logon** 示範第一種情況，走的是：**登入 → 拿到憑證 → 帶著憑證請求 → 伺服器依憑證決定你是誰**，並在每一步問同一個問題：伺服器到底驗證了什麼？

走完這份講義，你應該能做到：

- 用瀏覽器的開發者工具（devtools）查看與修改 cookie。
- 說出一張登入憑證存在哪裡、由誰保管、伺服器怎麼使用它。
- 在不用額外工具的情況下，送出自己指定內容的請求。
- 判斷一個認證流程信任了哪些「其實可以被使用者控制」的東西。

---

## 步驟一：看題目給了什麼

在 CyLab 的 Challenge Library 找到 logon，啟動後會得到一個網址，沒有附檔。題目說：這間工廠對使用者隱藏了一些東西，請以 Joe 的身分登入，看看他在看什麼。提示則是一個疑問：它好像不檢查任何人的密碼，除了 Joe 的？

打開網址是一個登入表單，有帳號和密碼兩欄。

## 步驟二：照提示試登入

先照題目的要求，帳號填 `Joe`、密碼隨便填。伺服器拒絕了，回覆的意思是 Joe 的密碼非常安全，這條路進不去。

再換一個任意帳號，例如 `test`，密碼一樣隨便填，甚至留空。這次成功登入，頁面轉到 `/flag`，但看不到 flag。

到這裡可以確定一件事：除了 Joe，這個網站根本不驗密碼。那它登入之後，是靠什麼決定給不給你看 flag？

## 步驟三：打開憑證來看

按 F12 打開 devtools。Chrome 在 **Application → Cookies**，Firefox 在 **Storage → Cookies**，點選這個網站，會看到登入後伺服器存進瀏覽器的三個 cookie（伺服器請瀏覽器保存、之後每次請求自動帶回的小段資料）：

| 名稱 | 值 | 意思 |
|---|---|---|
| `username` | 你剛才填的帳號 | 你宣稱的身分 |
| `password` | 你剛才填的密碼 | 原樣存著，沒有任何處理 |
| `admin` | `False` | 你是不是管理員 |

這張表就是這個網站的「憑證」，而且三項全都存在你的電腦上、由你保管。特別是 `admin`：決定你權限的那個值，伺服器交給了使用者自己保存。

## 步驟四：改掉憑證，再請求一次

在 devtools 裡雙擊 `admin` 的值，把 `False` 改成 `True`，大小寫照伺服器原本的寫法（首字大寫），然後重新整理 `/flag`。這次頁面上出現了 flag。

不用 devtools 也做得到。cookie 只是請求裡的一個標頭（header，請求附帶的額外欄位），用 `curl` 自己帶上就好：

```bash
curl -s --cookie "admin=True" <題目網址>/flag | grep picoCTF
```

連登入都不必，因為伺服器只看你帶來的 `admin` 是什麼。

## 步驟五：讀懂它錯在哪

回頭看整個流程，伺服器在每一步驗證了什麼：

| 步驟 | 伺服器驗證了什麼 |
|---|---|
| 登入 | 除了 Joe，什麼都沒驗 |
| 發憑證 | 把帳號、密碼、權限原樣寫進 cookie |
| 之後每次請求 | 直接相信 cookie 裡的 `admin` |

問題不在 cookie 本身，而在於伺服器**把需要它自己判斷的事，交給了使用者回報**。比較安全的做法是：瀏覽器裡只放一個難以猜到的 session ID（工作階段編號），身分與權限記在伺服器那一端；或者讓伺服器對 cookie 內容簽章（用只有伺服器知道的金鑰算出的檢查碼），使用者一改，簽章就對不上。

## 換個角度：憑證還可能在哪裡出問題

logon 是「憑證內容被竄改」。同一條流程上，還有幾種常見的失守方式：

| 出問題的地方 | 情況 | 伺服器該做的事 |
|---|---|---|
| 憑證的內容 | 權限、身分寫在 client 端，改了就生效 | 權限留在伺服器，或對 cookie 簽章 |
| 憑證的保管 | session ID 外洩，或永遠不會過期 | 不公開 session、設定逾時、登出即作廢 |
| 登入這一步 | 留有測試用的後門，帶上特定標頭就放行 | 上線前移除，任何人都不該有捷徑 |
| 密碼本身 | 用生日、名字、暱稱組成，從個資就能猜到 | 限制嘗試次數、要求強度、加上第二個因素 |

## 用得上的操作

下面這些都只需要瀏覽器或 Python，不用另外安裝攔截工具：

| 想做什麼 | 操作 |
|---|---|
| 看網頁原始碼裡的註解 | 在頁面按 Ctrl+U |
| 看、改 cookie | devtools → Application（Chrome）／Storage（Firefox）→ Cookies |
| 看某個請求送了哪些標頭、回了什麼 | devtools → Network，點選該請求 |
| 自己送一個帶特定標頭的請求 | devtools → Console，輸入 `fetch("/路徑", {method: "POST", headers: {"標頭名稱": "值"}}).then(r => r.text()).then(console.log)` |
| 解開位移、base64 等編碼 | [CyberChef](https://gchq.github.io/CyberChef/)（A2 用過） |
| 算一個字串的雜湊來比對 | `python -c "import hashlib; print(hashlib.sha1(b'候選密碼').hexdigest())"` |

`fetch` 是瀏覽器內建的發送請求方式。在題目網站的頁面上開 Console 執行，請求會自動帶上這個網站的 cookie，回應內容會印在 Console 裡。
