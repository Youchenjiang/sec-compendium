# 伺服器憑什麼相信你是誰

Lesson 4 把可歸責性（Accountability）拆成兩件事：身分識別（Identification，你宣稱自己是誰）與認證（Authentication，證明你真的是）。網站上最常見的認證是登入：你送出帳號密碼，伺服器確認無誤後，發給瀏覽器一張「憑證」，通常放在 cookie 裡；之後你每一次請求，瀏覽器都自動把這張憑證帶回去，伺服器看憑證就知道你是誰。

前兩次實作，你們已經用現成的漏洞利用程式進到別人的主機。這一次換個方向：不攻擊程式的漏洞，而是攻擊「伺服器怎麼認人」這套流程。這份講義先用 CyLab 上的 **logon** 示範一張完全沒有保護的憑證，再看真實系統常加上的幾種保護，以及它們各自怎麼失效。整條線是：**登入 → 拿到憑證 → 帶著憑證請求 → 伺服器依憑證決定你是誰**，每一步都問同一個問題：伺服器到底驗證了什麼？

走完這份講義，你應該能做到：

- 用瀏覽器的開發者工具（devtools）查看與修改 cookie。
- 解開一個有簽章的 cookie，看懂它裝了什麼，以及偽造它需要什麼。
- 用 Python 送出自己指定標頭與內容的請求，並寫成迴圈重複嘗試。
- 看到一種保護措施時，指出它依賴什麼，以及那個東西是不是落在使用者手裡。

## 一、沒有保護的憑證：logon

### 看題目給了什麼

在 CyLab 的 Challenge Library 找到 logon，啟動後會得到一個網址，沒有附檔。題目要你以 Joe 的身分登入，看看他在看什麼；提示則問：它好像不檢查任何人的密碼，除了 Joe 的？

### 照提示試登入

帳號填 `Joe`、密碼隨便填，伺服器拒絕了，回覆的意思是 Joe 的密碼非常安全。換一個任意帳號，例如 `test`，密碼隨便填甚至留空，這次成功登入，頁面轉到 `/flag`，但看不到 flag。

除了 Joe，這個網站根本不驗密碼。那它登入之後，是靠什麼決定給不給你看 flag？

### 打開憑證來看

按 F12 打開 devtools。Chrome 在 **Application → Cookies**，Firefox 在 **Storage → Cookies**，點選這個網站，會看到登入後伺服器存進瀏覽器的三個 cookie（伺服器請瀏覽器保存、之後每次請求自動帶回的小段資料）：

| 名稱 | 值 | 意思 |
|---|---|---|
| `username` | 你剛才填的帳號 | 你宣稱的身分 |
| `password` | 你剛才填的密碼 | 原樣存著，沒有任何處理 |
| `admin` | `False` | 你是不是管理員 |

決定你權限的 `admin`，伺服器交給了你自己保存。

### 改掉憑證，再請求一次

雙擊 `admin` 的值，把 `False` 改成 `True`（照原本的大小寫），重新整理 `/flag`，flag 出現了。cookie 其實只是請求裡的一個標頭（header，請求附帶的額外欄位），所以用 `curl` 自己帶上也一樣，連登入都不必：

```bash
curl -s --cookie "admin=True" <題目網址>/flag | grep picoCTF
```

伺服器在這個流程裡驗證了什麼？登入時除了 Joe 什麼都沒驗，之後每次請求都直接相信 cookie 裡的 `admin`。問題不在 cookie 本身，而在伺服器**把需要它自己判斷的事，交給使用者回報**。

## 二、加上保護之後

真實系統不會這麼毫無防備。下面是四種常見的保護，每一種都有明確的用意；但每一種也都依賴某個前提，前提一旦落在使用者手裡，保護就形同虛設。

| 保護措施 | 用意 | 它依賴什麼 | 依賴的東西被掌握時 |
|---|---|---|---|
| 對 cookie 簽章 | 使用者改了內容，伺服器會發現 | 簽章金鑰只有伺服器知道 | 金鑰猜得到，攻擊者就能自己簽 |
| 限制登入失敗次數 | 擋住一直猜密碼 | 能正確辨認「同一個來源」 | 辨認依據由使用者自己填，換一個值就重新計算 |
| 密碼存成雜湊 | 資料庫外洩也看不到原文 | 雜湊無法反查 | 沒加 salt 的常見密碼，查現成的對照表就還原 |
| 雙因素驗證 | 只知道密碼還不夠 | 第二個因素只有本人拿得到 | 驗證碼被送到瀏覽器，等於把答案交給攻擊者 |

下面把每一種保護的原理與相關工具講清楚。

### 簽章：cookie 改不了，除非你有金鑰

簽章（signature）是伺服器用一把只有自己知道的金鑰，對 cookie 內容算出的一段檢查碼，跟內容一起放進 cookie。使用者改了內容，檢查碼就對不上，伺服器會拒絕。要注意的是，簽章只防「改」，不防「看」：內容通常只是編碼過，任何人都能解開來讀。

Python 的 Flask 框架預設就把 session 存在這種有簽章的 cookie 裡，cookie 名稱是 `session`。工具 `flask-unsign`（`pip install flask-unsign`）可以處理它，三個動作分別是：

```bash
flask-unsign --decode --cookie '<cookie 值>'                        # 讀出內容，不需要金鑰
flask-unsign --unsign --cookie '<cookie 值>' --wordlist <候選金鑰檔>  # 拿一份候選清單逐一試金鑰
flask-unsign --sign --cookie "<新的內容>" --secret '<金鑰>'           # 用找到的金鑰簽一個新的 cookie
```

候選清單一行放一個字。所以簽章的安全完全取決於金鑰：金鑰如果是從一小份可預測的清單裡挑的，`--unsign` 幾秒就能試完。

### 嘗試次數限制：伺服器怎麼知道是同一個人

伺服器要「同一個來源失敗太多次就鎖住」，得先決定怎麼辨認來源，最常見的是看 IP。但網站前面常有代理伺服器（proxy，替使用者轉送請求的中間機器），伺服器看到的連線來源會是代理的 IP；代理因此會加上一個 `X-Forwarded-For` 標頭，註明原始使用者的 IP。

這個標頭只是請求裡的一行文字。如果請求沒有經過伺服器自己信任的代理，標頭裡填什麼，完全由送出請求的人決定。

用 Python 的 `requests` 送一個帶自訂標頭、內容是 JSON 的請求，寫法是：

```python
import requests

r = requests.post(
    "<網址>/login",
    json={"email": "user@example.com", "password": "guess"},
    headers={"X-Forwarded-For": "10.0.0.1"},
)
print(r.status_code, r.text)
```

把它放進 `for` 迴圈，就能對一份清單逐一嘗試，每次帶不同的標頭值。

### 雜湊與 salt：相同的密碼，相同的雜湊

雜湊（hash）把密碼轉成固定長度的值，無法直接算回原文。但如果沒有加 salt（每個帳號各自加在密碼上的隨機字串），同一個密碼永遠得到同一個雜湊值，於是只要事先把常見密碼都算好，查表就能找到原文。[CrackStation](https://crackstation.net/) 這類網站就是這樣的對照表；外洩密碼清單 `rockyou.txt` 則是最常被拿來當候選的密碼集。

自己驗證一個候選密碼對不對：

```bash
python -c "import hashlib; print(hashlib.sha256(b'候選密碼').hexdigest())"
```

若資料存在 SQLite 資料庫檔（`.db`），可以用 `sqlite3 <檔名>.db` 打開，再用 `.tables` 列出資料表、`SELECT * FROM <資料表>;` 看內容。

### 雙因素：第二個因素在誰手上

雙因素驗證（2FA）在密碼之外，再要求一個只有本人拿得到的東西，常見的是寄到手機或信箱的一次性驗證碼。它有效的前提是：驗證碼只出現在本人的手機或信箱裡。檢查一個 2FA 實作時，就去找驗證碼除了那裡，還出現在哪裡，例如 cookie、網頁原始碼，或某個請求的回應。

## 用得上的操作

| 想做什麼 | 操作 |
|---|---|
| 看網頁原始碼 | 在頁面按 Ctrl+U |
| 看、改 cookie | devtools → Application（Chrome）／Storage（Firefox）→ Cookies |
| 看某個請求送了什麼、回了什麼 | devtools → Network，點選該請求，看 Headers 與 Payload |
| 讀、試、簽 Flask cookie | `flask-unsign --decode`／`--unsign`／`--sign` |
| 帶自訂標頭重複送請求 | Python `requests` 加 `for` 迴圈 |
| 解開 base64 等編碼 | [CyberChef](https://gchq.github.io/CyberChef/)（A2 用過） |
| 驗證雜湊、查常見密碼 | `hashlib`、CrackStation |
